# Research: 新项目开发工作流 -- 文档冗余与跨文档矛盾分析

- **Query**: 多文件描述同一内容的情况，已完全被取代但仍保留的内容，跨文档矛盾
- **Scope**: Internal (跨文档交叉比对)
- **Date**: 2026-05-23

## Findings

### H-01: test-first 状态描述跨文档矛盾

| 字段 | 内容 |
|------|------|
| 严重程度 | **HIGH** |
| 文件 | `阶段状态机与强门禁协议.md` vs `通俗版.md` / `cursor/README.md` / `plan.md` / `check.md` / `opencode/README.md` / `codex/README.md` |
| 问题描述 | 阶段状态机协议明确声明 test-first 已合并到 implementation（第 57 行），但 6+ 处文档仍将其描绘为独立入口或独立阶段。这是跨文档矛盾中影响最广的一处。详细清单见 doc-staleness-obsolete-refs.md H-01。 |
| 建议处理 | 以阶段状态机协议为权威源，全面清理 test-first 独立阶段/入口引用。 |

### M-01: "start" vs "continue" 术语跨文档不统一

| 字段 | 内容 |
|------|------|
| 严重程度 | **MEDIUM** |
| 文件 | `通俗版.md`、`命令映射.md` vs `工作流嵌入执行规范.md`、`CLI原生适配边界矩阵.md` |
| 问题描述 | 1) 通俗版.md 多处使用 "start" 作为 implementation 入口（L0->start, "回到 start 修复", "进入 start"）；2) 命令映射.md 下一步推荐用 "start" 兜底（第 468 行）；3) 但工作流嵌入执行规范.md 和 CLI原生适配边界矩阵.md 均声明 start 是 legacy 命令，fresh baseline 应使用 continue（含 Phase Router 增强）。这种术语不统一在面向用户的通俗版中尤为有害。 |
| 建议处理 | 以 CLI原生适配边界矩阵.md 和阶段状态机协议为权威，将所有面向用户的文档中的 "start" 替换为 "continue"，必要时附注 "continue 替代了旧版 start"。 |

### M-02: 阶段出口条件在总纲、命令映射、通俗版中重复描述且措辞有差异

| 字段 | 内容 |
|------|------|
| 严重程度 | **MEDIUM** |
| 文件 | `工作流总纲.md`、`命令映射.md`、`通俗版.md` |
| 问题描述 | brainstorm 阶段的出口条件（必须补齐项目级粗估、customer-facing-prd.md 等）在总纲、命令映射、通俗版中都有描述，但措辞和详细程度不同：1) 总纲描述最完整但嵌入在长正文中；2) 命令映射只提概要；3) 通俗版简化为口诀。三者之间不是简单的引用关系，而是各自独立重写，增加了维护负担和不同步风险。 |
| 建议处理 | 总纲作为权威规则层保留完整描述；命令映射和通俗版改为引用总纲的具体章节号，而非独立重写。至少在命令映射中加 "详见总纲 §2.3" 类引用。 |

### M-03: 变更管理规则在总纲、需求变更管理执行卡、命令映射中重复

| 文件 | `工作流总纲.md`、`需求变更管理执行卡.md`、`命令映射.md`、`plan.md` |

| 建议处理 | 总纲仅保留变更管理的一句话声明 + 执行卡引用链接，删除内联的详细步骤。执行卡作为唯一详细载体。 |
