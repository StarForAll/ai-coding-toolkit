# 深度审查 workflow-design.md v34 设计稿（按 §0.1 约束面）

## Goal

按 `docs/workflows/workflow-design.md` 自身 §0.1「设计稿自身的约束」对**该文件当前内容（frontmatter v34，含 v34 审查修复）**做深度审查，找出后续实现方案 / 模块实现 / AI 执行时会**被迫中途修改**的设计层问题，产出可被作者反驳检验的缺陷报告；报告确认后的问题在本任务内继续修复（用户已说明本任务后续可能承载修复）。

## Background

- 该设计稿已跨 v25→v34 十余轮审查收口，v34 刚完成“判定源唯一化 + 满足判定收口 + 附录 C 纪律”一轮修复；`ariadne` 级别的明显重复已清，剩余问题只可能出现在**新引入的收口规则与既有规则的交界**、**角色/镜像用例的未覆盖侧**、**防御态修复动作自身的合法性**。
- 本仓库有专门的审查协议与谓词登记表：`.trellis/spec/guides/design-review-thinking-guide.md`（四道过滤器、反驳验证、必附排除候选）与 `.trellis/spec/docs/index.md`（谓词登记表 + 8 条探针）。审查必须按其证据门槛执行，否则产出的是候选清单而不是审查。
- 上一轮审查的关键教训：主发现里混入可被一句 § 引文反驳的项即算失败；报告必须能通过“作者反驳”检验。

## Requirements

1. 审查对象**仅**为 `docs/workflows/workflow-design.md` 当前版本；`1.2-零补丁嵌入方案.md` 内容按用户要求忽略（仅可作版本交叉核对）。
2. 按 §0.1 审查口径 1–9 执行：先判承载；只受理内部矛盾 / 跑不通 / 与不变量冲突 / 与真实场景不符四类来源；不把有意取舍、留白、工具选型、实现细节当缺陷；结论必须引用具体 § / 表 / 行。
3. 按 `design-review-thinking-guide.md` 执行四道过滤器（F1 层过滤 / F2 决策日志过滤 / F3 留白 vs 冲突 / F4 失败模型过滤）+ 三步反驳验证（反驳检索、端到端模拟、最简合规实现测试、作者反驳）。
4. 跑完 `.trellis/spec/docs/index.md` 的 8 条谓词探针，作为“重复判定已收口”的事实基线，并把结果写进报告（探针通过与否是客观证据，不是结论本身）。
5. 交叉核对配套文档 `依赖机制设计说明.md` 的 `design` 字段（同版 ✓）与 `1.2-零补丁嵌入方案.md` 的版本标注（v20，漂移）；版本结论单独报告，不混进主发现。
6. 结论格式按 §0.1 口径 9：约束编号（A/B/§）+ 证据（§/表/行）+ 来源类型 + 影响（会在哪个阶段被迫改）+ 建议（优先补判定 / 删重复 / 改措辞；新增机制须标“超出本设计”）。
7. 报告必须含四部分：主发现、措辞/精度项、**排除候选（含理由）**、版本核对。
8. 用户口径：实事求是，不吹毛求疵；琐碎项一律进排除候选或措辞节，不许用推测的“实现成本”抬高严重度。

## Acceptance Criteria

- [x] 报告含 `## Review conclusion`（计数）、主发现、措辞/精度、排除候选表（逐条给理由）、版本核对五部分。
- [x] 8 条探针实测结果记录在报告内；任一探针红则先作为主发现处理。
- [x] 报告落盘到本任务目录 `review-report.md`，并通过 `trellis-check` 的自检口径（判据可定位、无悬空引用、无重复定义项）。
- [x] 排除候选表覆盖所有被否掉的高频误报族（留白、有意取舍、实现自由、外部篡改、派生层问题）。
- [x] 不改动 `workflow-design.md`（审查阶段只读）；修复另阶段进行。
