# 审查方法与证据标准（技术设计）

## 边界

- 只读 `docs/workflows/workflow-design.md`；不改产品文档。配套文档 `依赖机制设计说明.md` 只作反驳检索的语料与版本交叉核对，不作判定源（§0.1 口径 6、8）。
- 交付物是本任务目录下的 `review-report.md`；不进产品仓库，除用户另行要求修复。

## 审查面分解（把 §0.1 变成可执行检查项）

审查按 §0.1 的 A1–A6 / B1–B10 逐条“先判承载、再判满足”：

| 承载 | 审查动作 |
|---|---|
| 设计稿承载条目 | 按正文判定：查内部矛盾（同一情形的两条规则）、查出口缺失（诚实可达场景是否走到死路）、查不变量冲突、查与真实场景不符 |
| 实现方案 / 目标项目承载条目 | 只查“有没有写清交给谁、验收什么”，不要求命令 / 探针 / 测试 |

重点高风险面（按 v34 刚改动的交界预判）：

1. 新增写作纪律（§0）与既有“表内粗体是判据要点”的关系；
2. 刚泛化为“按 §3 无效”的入口行与其后的行集遮蔽关系（死行 / 悬空）；
3. 刚收口到 §4.3 的满足判定与“正常但未归档”这条防御态在各出口（类型 1/3、表 4-2 行 6、重连加边）的合法性；
4. 角色继承的镜像用例：收尾任务有“由人重新定义”条款、返工任务有“继承返工来源”条款，P 有无对应条款；
5. 引用体系：`id_scheme` 声明的“只追加”覆盖到哪些表、被数字引用的表是否都在覆盖内；
6. B1 的“凡需人判断处均标明‘由人决定’”逐处核对（h2 大步 + 分叉判断点）。

## 判定流程（每个候选都走完）

1. 记候选：精确 §/表/行、被违反的规则、触发场景、期望 vs 实际。不写影响。
2. 四道过滤器：F1 层过滤（有没有更省的最简合规实现）→ F2 决策日志（是否 §0 事实边界 / §0.1 口径 3 的有意取舍）→ F3 留白 vs 冲突（“没写”不算，只有两条规则冲突或规则无出口才算）→ F4 失败模型（诚实使用还是外部篡改 / 反规绕过）。
3. 反驳验证：`rg` 反驳检索（正文 + 配套 + 附录 + 示例）→ 端到端模拟到文档自己给出的出口 → 最简合规实现测试 → 写作者反驳句。
4. 存活 → 定级并给最小修复；写不出反驳句才算主发现；能写出 → 降措辞或进排除表。

## 输出契约

`review-report.md`：

```markdown
## Review conclusion   （主发现 / 措辞项 / 排除项 / 探针 / 版本核对计数）
## Main findings       （F#: 约束编号 / 证据 / 来源类型 / 影响 / 最小修复）
## Wording and precision
## Excluded (not defects)   （候选 + 排除理由，要求覆盖误报族）
## Probe results
## Version check (report only)
```

## 取舍

- 严重度只由“诚实使用可达性 × 被迫改的阶段”决定，不用推测的实现成本抬高度。
- 双重防御态（防御态的防御态）上的缺口仍可报，但必须标出可达链，不得按常态定级。
- 不为了凑数把留白写成缺陷；宁可主发现少于 3 条。
