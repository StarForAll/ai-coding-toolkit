# 审计并修复新项目开发工作流中的过度设计机制

## 目标

以 `/tmp/trellis-0.5.17-2` 这个已执行 `trellis init` 并嵌入 `docs/workflows/新项目开发工作流/` 的临时目标项目为证据对象，审计并修复源工作流中的过度设计问题。

## 修改边界

- 只允许修改 `docs/workflows/新项目开发工作流/`
- 不直接修改 `/tmp/trellis-0.5.17-2`
- 不修改当前仓库该工作流目录之外的其他目录
- 如果问题本质上是 Trellis 原生行为与工作流增强层冲突，只能在该工作流内通过补丁脚本、安装链或命令文档修复

## 需要验证的候选问题

1. `degraded-active-task` 机制是否违背了原生 Trellis “无 session identity 时直接失败并提示用户”的正确失败模式，并在已嵌入目标项目中制造额外边界情况。
2. `strong-gate` / `awaiting_user_confirmation` 是否只是对正常阶段确认机制作了过度包装，并通过额外状态机、补丁和文档把复杂度放大到不必要的程度。
3. 是否存在与上述两类问题同型的过度设计：
   - 将原生失败模式改造成复杂 fallback/recovery 层
   - 将正常阶段确认机制包装成额外状态机、补丁链或命名体系
   - 由上述设计引出的补丁、文档、测试和安装链冗余

## 证据要求

- 源工作流：`docs/workflows/新项目开发工作流/`
- 已嵌入目标项目：`/tmp/trellis-0.5.17-2`
- 必须区分：
  - source repo
  - generated target project（嵌入后状态）
  - runtime command output

## 修复要求

- 只修复经证据确认真实存在的问题
- 修复时同步处理同类问题，避免留下半套机制
- 删除或回退过度设计时，保持安装器、补丁脚本、命令文档、测试之间一致
- 不能引入新的失效路径、死代码、失配文档或失真的测试

## 完成标准

1. 对两个候选问题给出明确结论：真实问题 / 误报 / 部分成立。
2. 若问题真实存在，源工作流中完成对应修复，并同步处理同类问题。
3. 运行与该工作流相关的最小必要验证，至少覆盖：
   - 工作流安装/补丁相关测试
   - 被修改脚本的直接测试或回归测试
4. 最终结论需要明确：
   - 已完成
   - 未完成
   - 风险与后续建议
