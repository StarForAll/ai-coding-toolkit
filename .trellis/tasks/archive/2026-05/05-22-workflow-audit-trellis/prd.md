# 工作流审计：深度分析对原生 Trellis 的修改

## 审计目标

深度分析 `docs/workflows/新项目开发工作流` 对原生 Trellis 0.5.17 框架的修改情况，判断修改的性质、合理性和影响。

## 审计范围

### 1. 版本信息
- 工作流兼容版本：`0.5.17`（来自 `workflow_assets.py`）
- 当前 Trellis 版本：`0.5.17`
- 版本门禁：**通过**

### 2. 对比目标
- `/tmp/trellis-0.5.17-1`：纯 `trellis init` 基线（对照组）
- `/tmp/trellis-0.5.17-2`：嵌入工作流后的状态（实验组）

### 3. 关注点

#### 3.1 修改性质判断
- 哪些修改是**破坏性的**（改变了 Trellis 原生行为）
- 哪些修改是**合理补充**（在 Trellis 基础上增强）
- 是否存在**过度修改**（把不存在的问题包装成问题）

#### 3.2 设计偏离分析
- 经过一百多次修改后，是否偏离了原始设计意图
- 是否变得庞杂混乱，难以维护
- 是否引入了不必要的复杂度

#### 3.3 外包项目处理逻辑
- 检查是否包含外包项目特定的处理逻辑
- 如果包含，这些逻辑是否影响个人项目的使用

#### 3.4 个人项目流程顺畅度
- 对于个人私人项目，流程执行是否顺利
- 是否存在不必要的门禁或约束

#### 3.5 已知正确项
- ✅ 强制 2 个 push URL 的前置条件（用户确认正确）
- ✅ 状态机学习成本（用户确认不是问题）

## 审计方法

### Step 2a: 理解目标系统机制
- 工作流权威文档：`workflow_assets.py`、`CLI原生适配边界矩阵.md`、`装后隐藏目录与托管边界核对清单.md`
- Trellis 基线机制：`.trellis/` 运行时真相层、隐藏平台目录承载模型
- 工作流托管边界：patch-baseline、overlay-baseline、added-command、shared-script

### Step 2b: 静态证据收集
- 读取工作流核心文档
- 分析 `workflow_assets.py` 定义的托管资产
- 检查工作流嵌入规范和前置条件

### Step 2c: 结构化差距分析
- 对比两个临时项目的文件系统差异
- 分析工作流注入的资产类型和数量
- 判断修改是否符合"补充而非破坏"的原则

### Step 5: 运行时验证（已有临时项目）
- 检查 `/tmp/trellis-0.5.17-1` 的 baseline 状态
- 检查 `/tmp/trellis-0.5.17-2` 的 workflow-installed 状态
- 对比差异，归类为：
  - Trellis 原生基线
  - 工作流托管资产
  - 项目手动维护资产

## 预期输出

### 审计报告结构
1. **审计边界**
   - 版本信息
   - 审计范围
   - 证据来源

2. **确认的发现**（按优先级）
   - P0：阻塞性问题
   - P1：有实际行为影响的漂移
   - P2：表面不一致，无行为影响

3. **非缺陷项**（False Alarms）
   - 看起来像问题但实际合理的设计
   - 用户已确认正确的项

4. **修改性质总结**
   - 破坏性修改列表
   - 合理补充列表
   - 过度修改列表

5. **设计偏离评估**
   - 是否偏离原始设计
   - 复杂度评估
   - 维护性评估

6. **外包 vs 个人项目**
   - 外包项目逻辑的隔离程度
   - 个人项目流程顺畅度

7. **修复建议**
   - 需要修复的问题
   - 建议的修复方向
   - 优先级排序

## 证据要求

每个发现必须包含：
- **结论**：问题描述
- **证据源**：带源层标签（`source repo` / `generated target project` / `runtime command output`）
- **验证动作**：如何发现的
- **影响范围**：影响哪些功能或场景
- **修复方向**：建议如何修复

## 成功标准

审计完成后，应能回答：
1. 工作流对 Trellis 的修改是补充还是破坏？
2. 哪些修改是必要的，哪些是过度的？
3. 经过一百多次修改后，设计是否仍然清晰？
4. 外包项目逻辑是否影响个人项目使用？
5. 个人项目的流程是否顺畅？
