# Design

## Boundary

产品改动仅为 `docs/workflows/wf-framework-design.md` 与 `.index.md`。执行材料落在本任务 `research/`；模拟程序、项目文件与 Git 仓库只存在于独立 `/tmp/wf-closure-sim-*` 根下。使用 `/softwares/python/bin/python3` 与标准库。

这是设计可执行推演：临时控制器只表达本轮所需的批准、范围、单执行候选、检查快照、暂停恢复和归档次序，不作为 wf 运行件，也不扩展正式命令或 schema。框架发行、宿主 discovery、人判真实性和语义检索效果不由它证明。

## Product changes

1. §5.6 原紧急句改为 wf 内遵守原门禁、wf 外按外部变更处置接入。
2. §8.2 增加紧急边界、spec 跨任务复用、暂停插单恢复三行正反例；实际使用观察补充切换准备及恢复成本。
3. 索引只回写实际新增的词面候选和语义消费，保持 107 个现有条目的职责，不增一套定义。

## Simulation

- 样例业务为一个标准库 Python 小模块及行为测试，使用子进程运行，退出码和断言为事实。
- 知识路径：生产任务落盘 spec 与索引；消费者新 Python 进程仅从项目文件选取/读取 spec 并执行与约定对应的业务检查，记录读取内容/版本。此进程隔离不等于新 AI 会话。
- 任务路径：规划材料 → 显式模拟批准 → 开工 → 业务修改 → Check → 模拟 finish/归档；模拟批准和 finish 均清楚标为夹具输入，不伪造人的实际操作。
- 切换路径：A 在 Check 后留下脏改动，切 B 应拒绝；仅在隔离夹具中做实验提交后暂停 A、执行 B、恢复 A。B 无关改动保留 A 快照；再以同路径改动验证旧快照失效并重检。
- 应急路径：未批准的 wf 内任务不得借紧急开工；夹具中的无 wf trailer 外部应急提交保持外部属性，按影响判断重检或回 Plan。
- Git 提交仅发生在一次性 /tmp 测试仓库，使用命令局部测试身份，不改用户 Git 配置；不触碰源仓库历史。

## Evidence and cleanup
