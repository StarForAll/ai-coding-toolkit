### 2.1 补充硬约束：spec 变更必须有完整本地主路径

**覆盖面。** 初始化/bootstrap、新增、修改、拆分、合并、改名、删除、index 与 paths/status/verified_at 等元数据同步，连同变更依据的获取、检查及 Finish，均不能要求外部 MCP 可用。不能只保证最后写文件是本地操作，却把前面的架构分析、去重、影响判断或验收交给必需的 GitNexus/ABCoder 等服务；本地运行同类 CLI、预建知识图谱也不能成为绕开该要求的必需前置。

**实现边界建议。** AI 从项目源码/测试/现有 spec、任务记录、Git diff/log 与人的明确约定获取依据；普通本地脚本完成路径匹配、哈希、索引一致性和结构校验。默认流程不探测或调用 MCP，不要求先安装服务、配置账号、创建索引。用户自行使用的辅助工具不改变框架完整的本地执行路径，也不产生 wf 必需的适配层。本地不能确认的事实保留未核实及原因，不能要求配置 MCP 才能继续，更不能凭空补出规则。

**对当前稿的审查判断。** §1.1（审查基线 L38） 的普通脚本、§6.2（审查基线 L494） 的纯库匹配和 §6.3 的本地 spec 写入方向相容；但“agent 无关”不自动等于“外部工具无依赖”，正文尚未明确覆盖上述全过程。后续修订应把本条作为明确约束，并在 §7.4 原语改编与 §8 验收中消费，不能仅靠“借鉴 Trellis 骨架”隐式保证。原 F1–F6 保留，本补充不冒充已发现某段 wf 代码正在调用 MCP。

**Trellis 的事实范围。** 本地 `0.7.0-beta.4` 的 [spec-bootstrap](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/bundled-skills/trellis-spec-bootstrap/SKILL.md:11) 与 [repository-analysis](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/bundled-skills/trellis-spec-bootstrap/references/repository-analysis.md:5) 把 GitNexus/ABCoder 写进推荐分析路径；[mcp-setup](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/bundled-skills/trellis-spec-bootstrap/references/mcp-setup.md:3) 同时声明它们是工具选择、不是平台要求，该配置文档末尾又安排了写 spec 前的服务可见性与查询核验。常规 [update-spec](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/skills/update-spec.md:98) 则是读取已有 spec 后编辑并同步索引，没有列出 GitNexus 前置。故不能据这些文件概括为“Trellis 的所有 spec 更新必需 GitNexus”；本次未做其禁用 MCP 的端到端实测。wf 直接采用用户更明确的本地主路径要求，不继承这些推荐或配置步骤。

## 3. 实质发现

### F1 · P1：主动触发/共存承诺，与安装后全历史的强制归属冲突

**证据。** §1.1（审查基线 L39） 承诺“不调用即等于不存在”；§3 共存策略（审查基线 L232） 允许每个会话由人选择其他流程，且不启用 wf 的会话不受其约束。相反，§4.2（审查基线 L301） 扫描安装锚点后全部提交，规定无活动任务期间不得产生业务提交，其余提交必须归属 wf 任务或满足系统豁免；§5.4（审查基线 L416） 下一次 start 就消费该扫描并阻断。

**支持场景中的反例。**

1. 存量项目装 wf，完成一项 wf 任务并正常归档。
2. 人开启 Trellis 或普通会话，没有调用 wf-start，合法修复业务代码并提交；无 `wf-task` trailer。
3. 下一次启用 wf，提交不属于 wf 任务，也不是系统提交；启动被阻断，要求归属到一个未归档的 wf 任务。

用户遵守了主动触发与共存规则，却必须补建 wf 任务认领另一流程的历史。卸载后用普通流程开发再保留数据重装，也会产生同类冲突。因此这是控制范围矛盾，不能定性为用户越轨，亦不能只靠 D-2“先观察两周”解决。

**同一边界的另一症状。** §1.1 的自检（审查基线 L52） 只看持久活动指针；上一 wf 会话没收尾便换到未启用 wf 的会话时，指针仍有效，不能证明本会话调用过 start。它只证明“项目有未完成任务”。这一点应如实降为会话调用纪律，不能把指针当会话启用凭证。

**最小建议。** 保留主动触发与共存的核心，收窄“必须有 wf 归属”的控制面。可用既有归属裁决容纳人明确确认的非 wf 提交，或把强制归属限制到明确纳入 wf 的任务工作面；具体选择由人裁决。两者都必须确保外部改动不会被悄悄算入 wf 任务，也不会保留旧 Check 当作当前证据。不能反向改成“安装后所有开发必须经 wf”，那会改变本框架初衷。

**验证。** 成对夹具：未启用 wf 的独立业务提交 → 下一次允许启用并显式处理接续；已启用任务里的意外漏 trailer → 仍报告归属问题。再覆盖默认卸载→普通开发→保留数据重装。会话指针场景按约定层验证，不宣称无宿主支持的强防误触。

### F2 · P1：建任务与实现许可名义上分开，开工条件却没有批准最新规划

**证据。** §1.4（审查基线 L138） 与 §4.2（审查基线 L299） 保留“建任务许可 ≠ 实现许可”。但紧邻的 开工门禁（审查基线 L298） 只检查产物存在、合法阶段、前置与基线登记，随后表述“开工门禁通过才进入 Execute”。§4.1 人工介入点（审查基线 L279） 有分级判定，没有明确的规划批准。人选择轻量/复杂并不等于同意方案内容。

**反例。** 人只同意建任务，AI 起草 PRD/design/implement，再在合法字段和满足前置下自行运行开工命令。全部现有结构条件满足，却没有人同意当前方案；即使早先批准过，PRD 实质改动后也没有定义批准是否仍有效。

**上游可吸收点。** Trellis 的 [brainstorm 第 8–9 步](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/skills/brainstorm.md:62) 明确先展示最终规划并停止，再由后续用户明确批准进入实施；这是源流程的关键语义，当前压缩丢失了。

**最小建议。** 明确 Plan 完成 = 规划收敛并经人批准当前方案；开工只消费该批准。可与现有 Plan 末分级一次确认，避免额外轮询。记录批准对应的规划版本/范围，实质改变范围、契约或风险才重新确认；不要求每次机械编辑都重批。仅凭字段不能证明真人批准，继续按 §1.5 诚实口径留痕，不新增身份/签名系统。

**验证。** 文件齐全但未批准 → 拒绝开工；已批准当前规划 → 放行；批准后实质扩范围 → 回 Plan；已有授权且规划未变 → 不重复请求批准。轻量 PRD-only 同样适用。

### F3 · P1：归属隔离被用作证据隔离，会遗漏交替任务对同一文件的修改

**证据。** §4.2 Check 关卡（审查基线 L303） 一面要求归档时指纹一致，一面明确“只有归属本任务的后续提交才触发失配，其他任务的提交不串味”；已提交路径取提交内容哈希。§1.3（审查基线 L123） 允许未归档任务切换，§4.2 归属定义（审查基线 L300） 正是为这种交替而设计。

**反例。**

1. A 修改 `src/config.py` 并 Check pass，提交后暂不归档。
2. 切到 B，B 合法修改同一个文件并提交，`wf-task` 指向 B；B 的任务验收未覆盖 A 的保证。
3. 恢复 A，工作区干净，A 自己没有新增提交。按“只有本任务后续提交”的判据，A 的旧指纹仍然有效。
4. 但当前 HEAD 中该文件已是 B 的版本，A 的旧测试不能证明当前交付树仍满足 A。

这是内容级的失效可发现问题，不是要求构建语义证据链。把其他任务的提交排除出 A 的归属是正确的；把其他任务改写 A 已检查内容的影响也排除，则违背“证据对最终状态有效”。

**最小建议。** 保留 trailer 的归属集合，区分它与检查有效性。A 的已检查路径在恢复/归档时，与当前 HEAD/工作区的实际内容比较；同一路径被任何任务改变、删除或替换，均失效并重跑 Check。不要求因 B 修改完全无关的文件而重检，也不引入调用图调度或整仓证据链。

**验证。** B 改同一路径 → A 旧 Check 失效；B 只改无关路径 → A 指纹保持；B 改后恢复到相同内容 → 按内容一致判定。补删除/改名用例，避免仅比较“文件仍存在”。

### F4 · P1：合法返工会形成启动校验明令拒绝的组合

**证据。** §1.3 指针切换（审查基线 L123） 规定被切走的挂起任务不记暂停；§5.6 返工（审查基线 L462） 规定 T 加挂起但任务状态不变，R 作为普通任务开工。可是 §5.4 组合识别③（审查基线 L416） 拒绝“多个执行中且未暂停的任务”。与之相邻的 §5.3 指针推导（审查基线 L399） 实际排除了挂起与暂停，两个谓词不同。

**反例。** 执行中 T 返工挂起，人切到 R 并开工。T = 执行中/挂起/未暂停；R = 执行中/未挂起/未暂停。合法流程产生两个“执行中且未暂停”，下一次换 CLI start 被要求 repair；人并未产生两个并发执行任务。

**最小建议。** 组合识别与指针候选复用同一谓词：执行中且未挂起且未暂停，候选数大于一才冲突。保留“挂起不自动暂停”的既有语义，无需新状态或检测运行中的会话。

**验证。** T 挂起/R 执行跨会话恢复 → 通过；T 与 R 都未挂起未暂停 → 阻断；返工归档后 T 清挂起 → 只剩 T 可恢复。应在现有三夹具中的任一个加入此正常返工用例。

### F5 · P2：将真实失败作为 spec 唯一准入，截断新项目的正向知识沉淀

**证据。** §6.3（审查基线 L512） 的双门槛把“真实失败”写为所有 spec 的必需条件。来源 [skills/SCOPE.md](/home/xzc/projects/other/skills/SCOPE.md:7) 实际是在筛选给其共享 skill 产品提的改进意见。Trellis 的 [update-spec](/home/xzc/projects/other/Trellis/packages/cli/src/templates/common/skills/update-spec.md:35) 则明确包括功能契约、成功建立的模式和已确定约定，不只包括事故。

**反例。** 新项目首次实现配置加载，测试验证了优先级和错误语义；人正式决定以后遵守该契约。没有失败会话，也没有需要 bootstrap 的既有代码。按当前门槛不能沉淀为 spec，其他任务只能重复探索或等第一次踩坑。

**最小建议。** 把第一门槛改为“有可追溯的真实项目依据”，容纳已观察失败、经验证的契约/模式、人的明确长期约定。每条仍需说明后续谁消费、避免何种错、依据是什么，并保留反例、去重、禁止空泛建议和允许零结果。不放宽成“任何觉得有用的经验都收”。

**验证。** 已实现并验证的契约即使没有事故也可收；人确认的项目约定可收；纯假设性最佳实践拒收；与现有条目冲突者先裁决。此项直接服务目标 3，而非新增知识平台。

### F6 · P2：升级三态没有闭合正常模板更新，接受本地偏离后的行为也不明确

**证据。** §6.1（审查基线 L489） 和 §7.2（审查基线 L574） 将存在且与模板相同归为不变，不同归为本地修改冲突；保留本地版时把基线哈希更新成该本地内容。但未区分旧版发行模板、已接受本地基线与新版发行模板。[Trellis analyzeChanges](/home/xzc/projects/other/Trellis/packages/cli/src/commands/update.ts:1009) 正好明确比较新内容、当前内容与存储旧哈希，单列可自动更新。

**两个正常场景。**

- 用户从未改文件，旧版内容 O，新版内容 N，O ≠ N。如果“模板”指 N，则正常升级被当本地冲突；如果指 O，则归为不变，却没有说明何时更新成 N。
- 用户保留本地版本 L 并将基线哈希写成 L，下次远端又变。L 等于已登记基线，不能据此推出 L 等于旧版发行模板，更不能据此授权新模板覆盖已接受的本地偏离。

**最小建议。** 在机制文档落地前固定一张小动作表，至少包含：已经是新版→无动作；本地未改且上游更新→更新；本地已改→人裁决；已接受偏离且新版相关内容再变→再次报告该新冲突；缺失→按既定删除策略。接受偏离的信息不能被改写后的一个哈希抹平。无需引入 Trellis 完整迁移系统。

**验证。** 原样旧文件可升级；本地独有内容不被覆盖；同版重复升级不重复询问；新版发生新冲突时重新询问；用户删除仍尊重。这里确认的是设计分支不全，未声称当前不存在的升级脚本已损坏数据。

## 4. 还值得吸收的点，以及不再增加什么

优先从上游补回 F2、F5、F6 的判断，而不是再复制更多 skill。正文已经覆盖短入口、原语组合、持久任务、三时点 spec、诚实降级、handoff、反例与回收；这些无需重新立项。

另外保留两项低成本候选，均仅用于 authoring 验收，不加目标项目新门禁：
