# 深度审查 workflow-design.md v39 设计稿（按 §0.1 约束面）

## Goal

按 `docs/workflows/workflow-design.md` 自身 §0.1「设计稿自身的约束」对该文件**当前内容（frontmatter v39，含 v39 审查修复）**做深度审查，找出后续实现方案 / 模块实现 / AI 执行时会**被迫中途修改**的设计层问题，产出可被作者反驳检验的缺陷报告。

流程约定（用户明确要求，硬约束）：

1. 审查阶段结束、报告落盘后**中断**，等人工审查确认，不直接进修复；
2. 人工确认后，**先判根因**（直接机制 + 共同根因 + 此前修复为何没根治）再动手，避免同一问题反复修；
3. 修复执行完**不做收尾**（不跑 finish-work、不归档、不提交），等人工审查通过并明确要求后才收尾；
4. 本轮是**新开且唯一**的 Trellis 任务，后续修复也在此任务内进行，不另起任务。

## Background

- 该设计稿已跨 v25→v39 十余轮审查收口。v39 刚完成一轮修复：§8.4 接手第三段改引 §9.1 两表（兄弟位点同步）；§6.5「改为放弃」补出一般任务删边（置空替换指向、改写说明、删边、归档）与项目层任务 P 新建替代两路，类型 5 与 §7.8 按走向收口；§0 写作约定与口径 11 把「副本清单」变成强制产出。
- 明显重复已清，剩余问题只可能出现在：**v39 新引入的收口与既有规则的交界**（改为放弃两路 × 类型 5 × §7.8 字段时机 × 组合表）、**角色/镜像用例的未覆盖侧**、**防御态修复动作自身的合法性**、**审查口径（尤其 11–14）自身的可执行性**。
- 本仓库有专门的审查协议与谓词登记表：`.trellis/spec/guides/design-review-thinking-guide.md`（四道过滤器、三步反驳验证、必附排除候选、已知结构盲点 1–9 与误报族 1–6）与 `.trellis/spec/docs/index.md`（`workflow-design.md` 谓词登记表 + 探针 + 传播清单 + 普通使用缺陷边界）。
- 上一轮同类任务：`.trellis/tasks/archive/2026-10/10-25-review-workflow-design-v37/`（report + acceptance-sweep + root-cause + fix-notes）；其遗留「P2 情形矩阵」等事项需在本轮复核是否已被 v38/v39 消化。

## Requirements

1. 审查对象**仅**为 `docs/workflows/workflow-design.md` 当前版本；`1.2-零补丁嵌入方案.md` 内容按用户要求忽略（仅作版本交叉核对）。
2. 按 §0.1 审查口径 1–14 执行：先判承载；只受理内部矛盾 / 跑不通 / 与不变量冲突 / 与真实场景不符四类来源；不把有意取舍、留白、工具选型、实现细节当缺陷；结论必须引用具体 § / 表 / 行。
3. 审查前先执行口径 10 的验收面全量审计（四项：人判点标记、P 的全部可达处置通路入口与出口、修复类型 1–5 产出态合法性、情形矩阵唯一口径），结果写入独立文件 `acceptance-sweep.md`。
4. 按 `design-review-thinking-guide.md` 执行四道过滤器（F1 层 / F2 决策日志 / F3 留白 vs 冲突 / F4 失败模型）+ 三步反驳验证（反驳检索、端到端模拟、最简合规实现测试）+ 作者反驳。
5. 跑 `.trellis/spec/docs/index.md` 的谓词探针（全部），记录实测值与预期值差异；v39 修复涉及的探针须逐个实测。
6. **按口径 11 对同一判定的所有副本做全量比对**（主稿内部 + 配套 `依赖机制设计说明.md`），按清单格式逐行给出：判定 / 副本位置 / 结果；按口径 12 回放 v39 新增或改写的全部「按 §N」引用；按口径 13/14 复核 v39 涉及的崩溃窗口与残留态识别项。
7. 交叉核对配套文档 `design` 字段与 `1.2-零补丁嵌入方案.md` 的版本标注；版本结论单独报告，不混进主发现。
8. 结论格式按 §0.1 口径 9：约束编号（A/B/§）+ 证据（§/表/行）+ 来源类型 + 影响（会在哪个阶段被迫改）+ 建议（优先补判定 / 删重复 / 改措辞；新增机制须标「超出本设计」）。
9. 报告必须含五部分：Review conclusion（计数）、主发现、措辞/精度项、**排除候选（含理由）**、版本核对。
10. 用户口径：实事求是，不吹毛求疵；琐碎项一律进排除候选或措辞节，不许用推测的「实现成本」抬高严重度。
11. 修复阶段（人工确认后）必须先写**根因判定** `root-cause.md`（直接机制 + 共同根因 + 为何此前的修复没根治），再动手。

## Acceptance Criteria

- [ ] 验收面全量审计（口径 10 四项）执行完毕，结果落盘到 `acceptance-sweep.md`。
- [ ] 口径 11 全量副本比对（主稿内部 + 跨文档，含清单格式）与口径 12 引用回放执行完毕，结果落盘，缺口转主发现。
- [ ] 口径 13/14 复核 v39 涉及窗口与识别项：每个窗口的残留态都能被启动自检 / 组合表行内注记 / 类型识别句唯一命中。
- [ ] 谓词探针实测结果记录在报告内；任一探针红则先作为主发现处理。
- [ ] 每条主发现都引用具体 § / 表 / 行，写明触发场景与「会被迫改的阶段」，并附作者反驳尝试与反驳失败说明（或已降级为措辞项）。
- [ ] 报告含 `## Review conclusion`（计数）、主发现、措辞/精度、排除候选表（逐条给理由）、版本核对五部分，落盘 `review-report.md`。
- [ ] 排除候选表覆盖高频误报族（留白、有意取舍、实现自由、外部篡改、派生层问题），引用 guide 的已知误报族编号。
- [ ] 审查阶段不改动 `workflow-design.md` 与配套文档（只读）。
- [ ] 审查完成后**中断**，等待人工审查确认。
- [ ] 修复阶段开工前落盘 `root-cause.md`，且修复后不执行收尾（只停手等人工审查）。
