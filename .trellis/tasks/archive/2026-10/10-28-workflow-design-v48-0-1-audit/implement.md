# 执行计划

## 初始审查

1. 等待用户对本任务规划摘要作明确批准；批准前保持 `planning`，不运行 `task.py start`。Codex 当前为 inline 模式，按项目规范跳过 JSONL 上下文清单；批准后使用 `task.py start 10-28-workflow-design-v48-0-1-audit --allow-empty-context`。
2. 获准启动后，重新读取主稿全文和 frontmatter，记录执行时版本；核对配套文档的 `design` 字段。不得打开或检索被排除的 `1.2-零补丁嵌入方案.md`。
3. 复读 `.trellis/spec/docs/index.md`、设计审查指南及其 predicate registry；从近期归档任务和会话历史提取相关既有决定、已修问题与保留风险，并逐条对照当前主稿，不沿用未经复核的旧结论。
4. 在候选缺陷收集之前完成并记录 §0.1 口径 10 六项全量审计，覆盖任务定义类产生路径、字段轴、角色路径和同一对象的重复操作窗口。
5. 完成口径 11–14 的适用检查：主稿内部与必要的配套副本；判定、动作序列、状态清单；共享状态位的副本与自有探针清单（如有）；每条引用的目标前提；每个多步写入的残留签名、识别入口与向前完成路径。
6. 收集候选并逐项执行证据记录、反证搜索、四道过滤、端到端推演、最简合规实现和作者反驳测试。记录被排除的候选，避免将精度或实现选择升级为缺陷。
7. 形成 `research/review-report.md`，按设计稿约束编号与具体 § / 表 / 行组织结论，分别记录主发现、精度项、排除项、版本核对、根因线索和证据边界。
8. 检查审查期间的工作树与任务文件 diff，确认主稿、配套文档、探针和实现方案没有被本轮修改；完成后停止，等待人工审查。

## 后续修复门（仅在用户审查后明确要求时）

1. 对用户批准修复的每个问题单独判断直接触发、结构性根因、同类载体和为何既有闸口未捕获；将证据与完整修复面写入本任务 research 记录。
2. 先检查该根因是否已有处理决定 / 禁区，再枚举唯一源、同文副本、配套镜像、探针、自检、窗口和引用调用位；方案不能解释复发机制时不得开始编辑。
3. 仅实施用户明确授权的最小修复，并执行与风险相称的验证；按任务约束修复后立即停下，等待人工复核。
4. 只有人工审查通过且用户随后明确要求收尾，才进入 Trellis 收尾步骤；否则不提交、不归档、不 finish。

## 验证

- 规划阶段：检查 `prd.md`、`design.md`、`implement.md` 完整，任务保持 `planning`，任务目录唯一。通用 `task.py validate` 因 inline 模式的两个 JSONL 清单为空会失败；该平台按规范跳过清单，并在用户批准后用 `task.py start --allow-empty-context`。
- 审查阶段：报告包含六项扫描证据与逐项结论；任务文件 diff 不包含目标产品文档改动。
- 后续修复阶段：按获准修复的具体文件和约束制定验证；不以一次定向 probe 的零发现代替其未覆盖审查轴。
