# wf 框架设计补充：Python 执行器、Trellis 冲突阻断与固定流程程序化

## Goal

把三条经访谈裁决的要求补充进 `docs/workflows/wf-framework-design.md`，不引入新问题、不产生缺漏或与既有条款冲突，并按第 0 章维护协议同步配套索引与设计期机检。

## Requirements

### R1 自定义 Python 执行器

- 配置层级：项目级 `.wf/project-config.json` 新增 `python_executable` 键优先；未设置时读全局配置 `~/.wf/config.json`（新增全局配置层，须按维护协议登记为新机制入口）；再未设置回退系统 `python3`。
- 生效范围：框架全部自有脚本（安装、升级、卸载、日常入口脚本、设计期机检器）统一经解析出的执行器运行。
- 配置时校验路径存在且可执行；解析失败仅阻断依赖脚本执行的判断与入口，不得静默换回系统 `python3` 继续跑。
- 卸载与 repair 入口因仅依赖标准库，在自定义执行器失效（如指向的 venv 已删除）时可回退系统 `python3` 运行，保证始终能退出/修复框架。
- 全局配置文件是用户机器层数据，不进 Git、不随发行模板投放；项目配置仍按 §3 既有契约（Git 跟踪、`wf-baseline` 通道变更、框架升级不覆盖）。

### R2 Trellis 项目下禁用 wf 流转

- 仅针对 Trellis：其 hook 会自动加载并向会话注入上下文，同一会话内无法与 wf 流转隔离。
- 安装环节：检测到 Trellis 资产（`.trellis/` 或已装 hook）时预览并提示共存风险，由人确认后仍可安装（保留数据层供未来迁移），不强制拒绝。
- 启用环节：`/wf-start` 检测到 Trellis hook 处于激活即输出阻断三要素（原因、决定性事实、下一步出口），不启用当前会话；已装 wf 的项目后引入 Trellis 同样在 start 阻断。
- 其他框架的共存策略（§3 共存策略）不变；本条是对 Trellis 的特例，不改写通用共存契约。
- 卸载与 repair 不受此阻断，始终可用。

### R3 固定流程用程序逻辑而非提示词

- 在 §1.1 增补明确原则：凡流程语义已固定、无语义分叉的环节必须由脚本实现，不得写进 skill 正文让 AI 临场决定。
- 固定流转清单（须在正文明确列举）：状态/阶段迁移、门禁结构判定、指针切换与暂停写入、归档移动、依赖建边/删边校验、三方升级匹配。
- §8.1 的“required 步骤须标注对应执行/检查面（enforcement 行），无 enforcement 行按缺口处理”据此执行。
- 语义分叉点（范围语义存疑、规划语义变更、知识准入冲突等）仍按 §1.5 走人或需人裁决档，不并入程序化清单，不吞掉“脚本管结构、人/AI 管语义”的既有分工。

### R4 维护协议合规

- 新增机制入口与判定字段（`python_executable`、全局配置层、Trellis 检测）按第 0 章维护协议登记定义、写者、消费点、失败出口和正反例，双向回扫消费点。
- 同步 `docs/workflows/wf-framework-design.index.md` 索引。
- §8.2 验收场景表补 Trellis 冲突与 Python 执行器解析的应允许/应拒绝行。
- 跑 `scripts/validate-wf-design.py`，定义/消费命中率不降阈值（90%），不降低现有检查迁就修订。
