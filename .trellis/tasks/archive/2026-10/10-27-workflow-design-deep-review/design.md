# 技术设计：workflow-design.md 深度审查与分阶段门禁

## 1. Design objective

本任务的“实现”不是修改产品文档，而是建立一条可复核、低误报的审查流水线，并把审查、根因分析、修复、收尾拆成需要人工明确放行的阶段。核心目标是：一次识别问题族，而不是围绕单个表象反复打补丁。

## 2. Authority and evidence hierarchy

从高到低使用以下证据：

1. `workflow-design.md` §0/§0.1 的审查边界、不变量和规范正文；
2. 主设计正文 §1–§10 的唯一源、表格和合法流转；
3. `.trellis/spec/docs/index.md` 的唯一判定源注册表与探针约定；
4. `.trellis/spec/guides/design-review-thinking-guide.md` 的过滤和反驳协议；
5. `依赖机制设计说明.md` 的同版镜像、机制细节、决策记录与实现口径；
6. 两份文档的附录修订历史，仅用来识别有意决策和核对“已同步”声明，不作为新的规范定义源。

`1.2-零补丁嵌入方案.md` 被明确排除，不进入任何证据链。

## 3. Review pipeline

### 3.1 Baseline inventory

- 固定当前磁盘版本、规范区和附录区边界。
- 核对主设计 `version` 与配套 `design` 字段。
- 提取 §0 的有意取舍、A/B 验收表、唯一源注册表、已确定实现口径和 v25–v45 修订决策，形成“不能重复提出”的决策日志。

### 3.2 Acceptance-surface sweep before candidates

按 §0.1 口径 10 的六项固定扫描建立六张可追踪清单：

1. 人判点及“由人决定”标记；
2. P 的角色解析、正常与异常终点、继任形态、归档前后入口/出口；
3. 对账修复类型 1–5 的输入、步骤、产出组合与恢复入口；
4. 同一情形的重叠规则矩阵，至少覆盖承重字段、角色、归档态和继任者存在性；
5. 封闭断言到全部产生路径的映射；
6. 识别字段 × 角色 × 修复入口的允许写入、禁止条件和受控恢复例外交集。

六项扫描的结果必须先写入报告草稿，再允许形成候选。

### 3.3 Structural integrity checks

- 按 spec 注册表执行文本探针并核对实际上下文，不把命中数量当结论。
- 以“判定、动作序列、状态清单”为单位列出唯一源、主稿摘要、主稿兄弟位点、配套镜像和历史记录；判断每个位置是定义、引用、镜像或仅历史记录。
- 对每条有效引用沿 `§N` 走到目标，检查调用场景是否满足目标的角色、归档态、账本态和前置条件。
- 对返工、替换、放弃、类型 1–5 等多步动作枚举提交窗口，验证残留态具备唯一签名、首步标记和可达恢复入口。
- 对同一对象重复执行动作，验证持久事实足以区分新旧登记和恢复意图。

### 3.4 Candidate adjudication

每个候选按固定顺序过闸：

1. 设计层/实现层/目标项目承载过滤；
2. §0 有意取舍和历史决策过滤；
3. 留白与冲突过滤；
4. 正常诚实使用与恶意篡改过滤；
5. 全文与配套反驳搜索；
6. 端到端场景模拟；
7. 最简合规实现测试；
8. 带具体 § 的作者反驳测试。

只有无法被上述步骤排除、且命中 PRD R4 四类来源之一的候选进入主发现。措辞问题、版本漂移和排除项分别记录。

### 3.5 Synthesis and quality gate

最终报告必须让读者可以从结论反向追溯到清单、场景、条款和探针结果。综合时：

- 合并同一根因的问题，不把同一规则漂移拆成多条“发现数量”；
- 对每个主发现给出最小改善方向，不在审查阶段设计补丁；
- 明确列出被排除候选，证明审查做过自我反驳；
- 明确证据边界，不宣称已覆盖未枚举的未知失效模式。

## 4. Work partition

审查执行可在同一个 Trellis 任务内并行拆成三个只写任务研究文件的独立研究面，但不得新建 Trellis 子任务：

- **审查面 A**：人判点、P 全路径、类型 1–5 产出态；
- **审查面 B**：情形矩阵、封闭断言、字段/角色/修复权限、唯一源/副本/引用/探针；
- **审查面 C**：决策日志、正常使用场景模拟、最简合规实现、作者反驳与伪问题排除。

综合者读取三份研究结果与原始证据，去重并生成 `research/review-report.md`。所有研究者只能写任务目录内互不冲突的研究文件，禁止修改产品资产。

## 5. Artifact contracts

| Artifact | Purpose | Mutation boundary |
|---|---|---|
| `research/sweep-a.md` | 审查面 A 的枚举与候选 | 仅任务目录 |
| `research/sweep-b.md` | 审查面 B 的矩阵、探针与候选 | 仅任务目录 |
| `research/sweep-c.md` | 审查面 C 的反驳与排除 | 仅任务目录 |
| `research/review-report.md` | 面向人工的最终审查报告 | 仅任务目录 |
| `research/root-cause-analysis.md` | 人工接受发现后、修复前的根因与影响面 | 未来条件触发 |
| `research/fix-notes.md` | 未来修复的源/副本/探针同步记录 | 未来条件触发 |

## 6. Human gates and state transitions

### Gate G1 — planning approval

当前三份规划产物经人工明确批准后，才允许 `task.py start` 并执行审查。

### Gate G2 — review approval

`review-report.md` 交付后立即停止。人工决定每条发现是接受、驳回、降级还是需要补证据。未获决定不得修改产品文档。

### Gate G3 — root-cause approval

人工要求修复后，先产出 `root-cause-analysis.md`。根因必须定位到问题族、唯一源、所有消费者和现有防逃逸机制为何没有捕获。人工确认根因与修复边界后才可编辑。

### Gate G4 — post-fix review

未来修复完成并验证后立即停止，不提交、不归档、不 finish。人工复核 diff、探针和报告。

### Gate G5 — explicit close-out

只有人工明确表示审查通过并要求收尾，才进入 Trellis spec 判断、提交计划、提交与 finish/archive 流程。

## 7. Future repair strategy

若未来获准修复，每条接受的问题必须按以下顺序处理：

1. 从可达场景追到根因，不从表面措辞直接下手；
2. 识别唯一源和问题族的全部同类载体；
3. 先改唯一源；
4. 将摘要、兄弟位点和配套镜像降为正确引用或同步镜像；
5. 更新/新增能够捕获根因的探针和预期；
6. 最后写修订记录，只记录源和跟随位置，不重定义规则；
7. 运行全量口径 10–14 和注册探针；
8. 生成 `fix-notes.md`，等待人工复核。

该策略禁止在多个位置叠加补充句，也禁止用“第一命中”“按顺序读取”等覆盖手段掩盖重叠条件。

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| 把实现自由报成设计缺陷 | 承载层过滤 + 最简合规实现测试 |
| 被历史措辞或修订记录误导 | 正文规范优先；附录只作决策日志 |
| 文本探针通过但语义仍冲突 | 探针后强制做输入域、权限和可达性核对 |
| 同一缺陷拆成多条噪声 | 按根因与唯一源合并 |
| 漏掉跨文档或主稿内副本 | 口径 11 清单逐项列位置和结果 |
| 修复一个面后下一版再补另一个面 | 根因分析先枚举同类载体、角色六面、路径和窗口 |
| 审查后自动进入修改或收尾 | G2/G3/G4/G5 四道显式人工门禁 |
