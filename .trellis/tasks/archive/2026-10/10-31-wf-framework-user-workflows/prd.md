# wf 框架工作流扩展与持久隔离契约

## Goal

补充 `docs/workflows/wf-framework-design.md`，明确 wf 的设计与演进基调、用户自定义工作流的零框架改造契约、工作流/普通任务之间的隔离，以及跨会话和会话压缩后的持久接续要求。

## Background

- 当前 wf 是独立的单人、本机、单一工作线框架；不以 Trellis 基底或宿主 hook 为运行前提。
- 旧 Trellis 内嵌 wf 方案通过 workflow 变体、上游配置写入、任务元数据和适配实现承载特定流程。使用者仅为定义 0→1 项目流程就需要修改 Trellis 相关内容并设计集成方案，违背本框架独立、轻量的目标。
- 用户要求自定义工作流成为框架直接支持的能力：使用者定义流程即可在框架中选择、执行、暂停和接续，不为每条流程修改框架代码或另做集成方案。
- 同一项目可有多个自定义工作流、多个工作流实例和普通任务；流程间不得串用状态、步骤、授权和产物。普通任务也必须能够持久接续。
- 单个 AI 会话只绑定并执行一个普通任务，或一个工作流实例；该会话内不得切换到另一个任务/工作流。其他任务或工作流须在该项目下的新 AI 会话中启动。
- 会话压缩仍是原会话，须保留其绑定对象与进度；新开会话有独立绑定，可继续既有工作流或启动另一任务/工作流。会话/任务绑定及进度以持久项目记录为准，运行态指针不得作为唯一事实。
- 用户已确认同一项目只允许单工作区串行写入：不同会话可分别绑定不同任务/工作流，但同一时刻只有一个会话持有项目写入权；其他会话可查看和准备，须等待写入权释放才能修改项目，避免共享工作树上的交错改动。
- 持久项目文件是任务状态、批准、工作流进度和恢复所需信息的事实来源；当前会话指针只能用于定位。
- 同一工作区中的业务文件和 spec 仍可能共享。若其他任务改变当前工作流依赖的路径，必须按既有检查有效性规则复核，不能保证共享内容变化后仍无影响。

## Requirements

1. 在设计与演进基调中明确：保持单人长期使用的范围；新增机制须对应具体能力缺口；优先复用既有控制核心；完整性（含失败、恢复、审查和必要控制）不能为形式上的精简而削弱；改进须考虑实现、使用、理解、维护、兼容与恢复的全生命周期成本；满足目标后停止无证据的扩展。已确认的复杂任务审查要求不得因轻量化而弱化。
2. 用户自定义工作流是项目内用户数据，与框架发行资产分离。框架提供一套通用定义格式、校验与执行能力；在该格式和能力范围内，创建或修改工作流只需操作用户工作流定义，不修改框架代码、Trellis/宿主受管文件、平台变体或流程专用脚本，也不需要用户另写框架集成方案。
3. 工作流定义至少能表达用途/适用条件、输入、顺序步骤、步骤产物与完成条件、所需验证和必须由人处理的决策点。定义使用顺序式、声明式能力；任意代码、插件、开放式 DSL、工作流嵌套、循环和并发执行不默认纳入首版。
4. 工作流可覆盖一个任务内部的步骤，也可组织由计划产生的多个普通任务；框架通过通用执行器、任务绑定及既有依赖能力推进，不为 0→1、重构、全代码审查等场景分别增加框架机制。
5. 工作流定义与执行实例分离。实例保存所用定义版本/快照、输入、步骤位置、关联任务、产物位置、完成/失败状态和下一步；定义修改不得静默改变现有实例。普通任务不自动绑定工作流，任务至多归属一个执行实例；跨流程复用必须显式引用，不能由另一流程重新推进或归档该任务。
6. 一个项目内不同工作流定义、实例和普通任务在执行进度、已批准范围、步骤指令、产物命名/落点和失败状态上相互隔离。每个 AI 会话至多绑定一个普通任务或工作流实例；该会话内禁止切换绑定对象。每个推进操作必须验证当前会话绑定且只作用于该对象；定义查询/编辑、另一实例的存在或普通任务完成不得隐式切换、推进或授权当前对象。
7. 普通任务和工作流任务统一使用持久项目记录跨会话接续。压缩后的原会话继续使用原绑定；新会话可在明确选择后绑定另一任务/实例，或在旧会话释放/显式移交写入权后接续已有对象。start 能从项目文件恢复目标、批准范围、决定、下一步、未决事项、验证结果以及工作流实例信息，不依赖完整聊天历史、运行态指针或要求用户重述已记录事实。恢复时核实真实 Git/文件状态；中断结果不明时先核对再继续，不盲目重做。
8. 对共享代码、spec、基线或配置的变更，隔离不能掩盖其对其他任务的真实影响。恢复时发现相关检查对象变化，按既有检查有效性规则使旧结果失效并复核；不自动归属、覆盖、暂存或丢弃其他工作。
9. 项目写入权应有明确且可恢复的单一所有者。获取、释放和显式交接只能在工作区边界满足时进行；其他会话不得同时推进共享工作树。写入权移交须使旧所有者的后续写操作失效；未知所有者是否仍活动时不得按超时自动抢占。无稳定宿主会话身份时不得退化为项目全局当前任务指针；需说明受控降级或阻断路径。无实时宿主拦截时，声明其通过入口/步骤核验及纪律控制，不宣称能阻止直接工具写入。
10. 本次设计改动仅限 `wf-framework-design.md` 及其唯一定义索引 `wf-framework-design.index.md`；不修改旧 Trellis 内嵌 wf 设计/实现方案，不实现脚本、CLI、工作流运行时或宿主适配。
11. 设计编辑和机械核验通过后，提供变更与证据供用户人工审查。用户明确审查通过前不执行 Trellis finish、归档、提交或其他收尾操作；未获批准的设计分歧不得由执行者代替用户决定。

## Open Questions

## Resolved Decisions

- 同一会话永久绑定一个普通任务或一个工作流实例，不得切换；多会话可分别绑定不同对象。
- 同一项目共享工作区串行写入；一个会话持有写入权时，其他会话只能读取/准备，不得执行项目写入。新会话接手既有对象须显式取得写入权并使旧会话令牌失效。
- 不引入并行 worktree/分支或自动合并。稳定会话身份缺失和写入权中断的处理必须 fail closed，不可使用共享全局指针或自动超时抢占。

## Out of Scope

- 本任务不实现用户工作流运行时、命令、脚本、安装器或任何平台/Trellis 集成；本任务只定义设计契约与所需验收。
- 不修改旧 Trellis 内嵌 wf 的 `workflow-design.md` / `workflow-implementation.md`，也不要求使用者为每条流程设计这些集成方案。
- 不引入任意脚本执行、插件系统、开放式工作流 DSL、嵌套/循环工作流、调度器或团队审批功能。
- 不重造任务状态机或依赖图；工作流跨任务组织复用统一任务生命周期和依赖机制。
- 跨独立工作区/分支的并行编辑与自动合并不纳入；项目级单一工作区写入权按用户已确认契约设计。

## Acceptance Criteria

- [ ] 设计基调可用于评估新增或移除能力，且没有把“轻量”解释为削弱已承诺的完整控制。
- [ ] 使用者可通过项目内定义描述新工作流并由通用框架机制选择和执行；在支持范围内不需改框架代码、Trellis 资产、平台集成或流程专属脚本。
- [ ] 单任务与多任务工作流、定义与实例、多个实例与普通任务的所有权和状态边界明确，不产生第二套任务生命周期或竞争事实源。
- [ ] 明确多个会话的任务/工作流绑定如何保存；每会话最多一个对象且不能会话内切换，其他会话绑定不得串用进度、步骤、批准、产物及故障状态。
- [ ] 会话压缩保留原绑定；新会话能显式接续旧对象或选择另一对象；普通任务和工作流均可跨会话恢复。
- [ ] 明确多会话对共享工作区的写入权获取、释放、显式交接和中断恢复；任一时刻至多一个写入者，不引入并行 worktree/分支。
- [ ] 同一会话永久绑定单一任务/工作流，完成后不能切换；新会话可显式创建其他绑定或接管已释放对象，旧会话不能使用失效写入权继续改动。
- [ ] 明确稳定会话身份不可用、写入权损坏或所有者中断时的阻断/恢复出口；不默默退回项目全局指针、不按超时抢占、不宣称无 hook 可防直接工具绕过。
- [ ] 普通任务和工作流执行均可仅依项目持久记录跨新会话/压缩恢复；共享路径变化会触发已有检查失效处理。
- [ ] 已将自定义定义的所有权、位置或定位方式、定义版本与现有发行资产/用户数据升级边界衔接起来；细节属于设计阶段且不得默认收编到发行资产。
- [ ] 同步维护唯一索引的定义/消费条目和 §8.2 正反验收场景；列出新增跨节引用并回扫被消费定义的词面与语义索引。
- [ ] `/softwares/python/bin/python3 scripts/validate-wf-design.py` 与 `git diff --check` 通过；最终报告明确仅证明文档/索引机械一致，不宣称已实现或运行验收。
- [ ] 用户人工审查通过前，任务保持未归档、未提交且未执行 finish。
