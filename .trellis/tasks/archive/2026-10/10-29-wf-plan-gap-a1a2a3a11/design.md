## A1 基线流程：说了不实现，实际实现了

**事实**

- §3.7 第一段③ 写"需要改基线 → 回设计稿 §5.5（本模块只输出指引，**不实现基线流程**）"。
- 但 §3.5 完整定义了 `wf baseline --light`（前置、原生调用、写入、提交组），附录 A 把它列为副作用命令，§8.2 P1 认领它。

**设计依据**：设计稿 §9.1 第一段③ 是**旁路**——"需要改基线 → 回到 §5.5"；而 §5.5 的轻量用法本身是三个写动作（新建任务、继承前置集合、默认重连下游）。人不手工做，`wf route` 的指引落地不了。

**选项**

| # | 做法 | 代价 |
|---|---|---|
| ① | 保留命令；§3.7 ③ 改为输出"回到设计稿 §5.5"的**指引 + 入口**，并按 §5.5 两分支分派：仍成立 → `wf baseline --light`；不再成立 → `wf replace` / `wf abandon` | 需改 §3.7 文案，删掉"不实现基线流程"半句 |
| ② | 真删命令（§3.5 行、附录 A、§8.2 P1 全删），人手工按 §5.5 做 | 三步写操作手工做，极易漏重连或写成非法组合 |
| ③ | 保留但不进路由：只作"可选便捷入口"，route 仅给提示 | 命令与判定脱钩，等于半实现 |

**推荐 ①**。理由：入口存在而不被路由，是当前矛盾的正解方向；两分支都在模块内，才能保证不出现"直接把旧任务归档"那类非法组合。

**影响面**：§3.7（③ 行与后续）、§3.5（文案），新增探针 W24（基线入口：两分支各跑一次，断言旧任务保留或异常归档符合各自分支）。

## A2 `wf check` / `wf route` 标只读，却会写账本

**事实**

- §2.4 表、§3.5 表、§3.6 第 1 条、附录 A、变体 §2.4 都把 `check` / `route` 列为**只读**，并据此允许"自动触发无风险"。
- 但 §3.8 第一步、§3.7 第二段都让入口执行"派生清除挂起"（表 4-2 行 3，`dep_state: suspended → 无记录`），§3.4 的提交场景表里**没有**这一行。

**设计依据**：设计稿 §7.7 原话是"**除此派生清除外**，启动只识别/报告，不写账本"——即派生清除是**被允许的例外写入**，只是它不该和普通只读混为一类。

**选项**

| # | 做法 | 代价 |
|---|---|---|
| ① | 新增类别"**只读 + 派生写入**"：只在满足表 4-2 行 3 全部条件时写，写前走 §3.4 洁净检查，提交组=机制组、消息 `chore(wf): unsuspend <任务目录>`；写入失败就报告留待 `wf repair`；同步 §2.4 / §3.5 / §3.6 / §3.7 / §3.8 / §3.4 / 附录 A / 变体 §2.4 | 要动 8 处文案，但保留"入口一次跑完即可继续" |
| ② | 拆出 `wf unsuspend`：`route` 只报"该清挂起了"，人显式跑 | 新增命令；`route` 真正只读；但每次清挂起多一步，且人可能忘 |
| ③ | 入口完全不写，清挂起只在 `wf close` / `wf repair` 里做 | 与设计稿 §9.1 第二段冲突：挂起会一直挂着，除非人主动跑 repair |

**推荐 ①**。③ 最省但和设计稿第二段直接打架；② 干净但把设计里"派生"的免手动特性丢了。

**影响面**：上述 8 处文案 + W14（已有"归档待对账"，补一条"派生清除后提交"断言）。

## 分析补充（第二轮）：逐项证据与结论

A11 已定 ①，本节只分析 A1 / A2 / A3。

### A1 `wf baseline --light` 到底有没有用

**设计稿把它的每一步都算成机制动作，不是人工手工操作：**

| 证据 | 原文 | 含义 |
|---|---|---|
| §4.4「继承类」 | "返工、替换、放弃-新建替代、类型 1 补建、**基线变更新建任务（§5.5 明写继承前置）**——被继承者可已归档" | 新建任务的"继承前置"是一种**有分类的建任务方式**，和建边、任务定义并列；实现必须能执行它 |
| §4.4「重连类」 | "替换 / 放弃实施、类型 1 补建的继任者重连、**基线变更轻量用法的默认重连**" | 默认重连同样被列为机制动作 |
| §5.5 第 2 步 | "默认把全部未归档下游重连到新任务"；"人决定保留部分下游时，只对要转移的下游按 §7.5 边变更逐条建边到新任务、自旧任务删边" | 默认路径是批量改指向；人工要逐条 `set-meta` 改 JSON |
| §5.5 第 2 步末 | "**不得把旧任务直接归档**"（会命中非法组合）、"**不得对旧任务自动放弃**" | 手工做最容易踩的两条禁令，正是入口要挡的东西 |

**如果删掉命令**：一次基线变更 = 1 次 `task.py create` + 1 次 `set-meta wf.deps`（要自己拼继承来的 `prereqs` JSON，还要正确带 `in_graph`）+ 下游每条一次 `set-meta` + 若干 `edge` 校验，且全在洁净检查之外。人工成本高、出错面大、没有 fail-closed。

**如果留着**：一次入口，前置校验、继承、默认重连、分步提交组都在命令里；路由只需按 §5.5 两分支分派。

**使用频率不构成删除理由**：基线变更在单人单线里确实不常发生，但 §8.3 的"不新增机制清单"里没有 `baseline`，留着不违反任何边界；反而删掉后 §4.4 的两条分类会变成"有分类、无实现"。

**结论：有用，应当保留**。真正要修的是 §3.7 ③ 的措辞与路由分派，不是命令。若选保留，验收要有 W24 挡两条禁令。

### A2 清挂起到底该不该由入口写

**设计稿明确说它"不是独立动作"，且给了失败语义：**

| 证据 | 原文 | 含义 |
|---|---|---|
| §4.3 末 | "**挂起清除不是独立动作**，是表 4-2 行 3 的转移" | 不用新命令；挂在既有评估点上 |
| §6.4 第 5 步 | "评估点为 R 收尾、放弃/替换的删边与重连、**启动对账**、**入口第二段**" | 入口本来就在评估点列表里 |
| §6.4 第 5 步 | "清除失败/崩溃由下次评估补做，不要求跨任务原子" | 失败语义已给：下次评估补做 |
| §7.7 | "对无登记阻断的未归档挂起按 §6.4 第 5 步评估**并持久化**；除此派生清除外，启动只识别/报告，不写账本" | 派生清除是**被允许的唯一例外写入** |

**具体写入面**（选 ① 时）：只在五个条件同时成立时发生——T 未归档、账本=`suspended`、无未完成返工登记、返工集合非空且无未归档成员、T 前置全正常；只改一个字段 `dep_state: suspended → 键删除`。

**三个选项的实际差别**

| | ①入口派生写 | ②`wf unsuspend` | ③只在 close/repair |
|---|---|---|---|
| 与 §4.3"不是独立动作" | 一致 | **冲突**（造出独立动作） | 冲突 |
| 自动触发是否安全 | 窄条件 + 洁净检查 + 失败留 repair | 安全（人显式跑） | 安全 |
| 人的步数 | 0 | 每次清挂起 +1 步，忘了就卡住 | 忘了卡住，且与 §6.4 评估点脱节 |
| 失败语义 | 报告 + 下次评估补做（照 §6.4） | 同左 | 下次评估**不会**补做（评估点不含它） |
| 文档改动 | 8 处文案 | 8 处 + 新命令 + 附录 A | 8 处 + §3.7/§3.8 重写 |

**结论**：设计层已经定了"派生、不独立"，所以 ②③ 都要在设计之外加台阶。**推荐 ①**；④ 的唯一真代价是"`route` 不再纯粹只读"，用新类别名把它写实即可。

### A3 §9.7 的具体情况

**内容**：T1/T2/T3 三段边界、"为什么切在这里"、M1–M3 三处修正、两条传递决策。

**与 §8.2 的关系**：§9.7 自述"§8.2 已按本节裁决同步改写"——即 §8.2 P0 行现在**已包含同样内容**（①–⑫ 条目、探针归属、最小 close）。

| 事实 | 结论 |
|---|---|
| P0 条目在 §8.2 与 §9.7 T3 各写一遍 | 已存在**重复源**，现在只靠"§9.5 说改过"维系 |
| §9.7 的 M1–M3 是"已裁决的修正" | 属裁决留痕，按 §9 的定位应在 §9.5 |
| T1/T2/T3 是实施拆分 | 属实施路线，应在 §8.2 |
| front-matter 只承认 §0–§8 为规范 | §9.7 实际被当规范用 |

**三种做法**

- ① 只补 normative 一句：重复源留着，下次改 P0 仍要改两处。
- ② 拆开：实施方案（T1/T2/T3、为什么这么切）进 §8.2；M1–M3 并入 §9.5 已有对应行；§9.7 删掉或留一行指向。**重复源消失，效力与位置一致**。
- ③ 降为非规范 + 正文重述：正文与登记两处，还是重复。

**结论**：② 最干净，且能顺手消掉一处结构隐患。

## A2 细节（第三轮，供判断用）

A1 已定 ①（保留 `wf baseline --light`），A3 已定 ②（拆进 §8.2/§9.5）。本节只讲 A2。

### 1. 到底有哪几个"评估点"

设计稿 §6.4 第 5 步把评估点列成四处。落到命令：

| 评估点 | 在哪个命令里跑 | 那个命令本来写不写账本 |
|---|---|---|
| R 收尾后 | `wf close`（R 的收尾路径） | **写**（账本写"正常"） |
| 放弃 / 替换的删边与重连 | `wf abandon` / `wf replace` / `wf repair` | **写**（异常 + 重连） |
| 启动对账 | `wf check` | 不写（当前标只读） |
| 入口第二段 | `wf route` | 不写（当前标只读） |

**所以"派生写入"只在后两处才是新问题**；前两处的清挂起从来就是写命令的一部分。这也解释了为什么设计说它"不是独立动作"——它只是同一判据在不同评估点的复用。

### 2. 具体写什么

- 只做一件事：把 `ledger.entries[<T>]` 整个键删掉（表 4-2 行 3：挂起 → 无记录）。
- 不写 `task.json`、不写 `meta`、不动任务状态。
- 提交：单文件单路径，消息 `chore(wf): unsuspend <任务目录>`。
- 前置五条全满足才写：T 未归档、账本 `suspended`、无未完成返工登记、返工集合非空且无未归档成员、T 前置集合全正常；外加 §3.4 洁净检查（账本有无关未提交变更 → 拒绝写）。

### 3. 三个选项在同一天里的差别

**场景（同一件事，三种走法）**：R 已归档正常，`wf close`(R) 成功，但提交挂起清除那一步被 Ctrl-C 打断，账本仍是 `suspended`，而五条件其实已满足。

| 步骤 | ①入口派生写 | ②新命令 `wf unsuspend` | ③只在 close/repair |
|---|---|---|---|
| 人下次跑 `wf route` | 输出"命中第二段：条件已满足 → 已清挂起"并继续给出下一步 | 输出"条件已满足，跑 `wf unsuspend <T>`" | 输出"仍挂起"，第二段继续绕在挂起里 |
| 人要做什么 | 什么都不用做 | 多敲一条命令 | 敲 `wf repair`（人工专用 + 令牌）或再 close 一个任务 |
| 忘记做的后果 | 无 | 下游一直不可用，直到发现 | 同左，且 `wf repair` 门槛更高 |
| 下一轮自动评估会不会补 | 会（每次 route/check 都评估） | 会评估，但只为提示 | **不会**（评估点不含它） |

**另一个场景（R 还在跑，条件未满足）**：三者都只报告、都不写——差别只在条件满足之后。

**第三个场景（账本脏）**：① 命中洁净检查 → 不写，报"该清挂起但账本有未提交变更"，流程继续，账本干净后下次自动补；② 命令直接报错退出；③ 同 ②。

### 4. 风险对照

| 风险 | ① | ② | ③ |
|---|---|---|---|
| `route` 被 skill 自动触发时写盘 | 是（但只这一种、只删一个键、幂等、写完立即提交） | 否 | 否 |
| 误清挂起 | 五条件唯一判据，与手工等价 | 同 | 同 |
| 与设计 §4.3"不是独立动作" | 一致 | **冲突**，须登记 §9 | 冲突 |
| 与设计 §6.4"评估点含入口" | 一致 | 入口只评估不执行，实际是拆开 | 入口不评估，**脱节** |
| 失败补做 | 照 §6.4"下次评估补做" | 无自动补做 | 无自动补做 |
| 文档改动面 | 8 处文案 + §3.4 新增一行提交 | 8 处 + 新命令（§3.5/附录 A/§4 变体/探针） | 8 处 + §3.7/§3.8 重写 |

### 5. 若选 ①，`route` 的"只读"怎么改才不误导

- 类别改名为"**只读 + 派生写入**"，并在 §3.5 表里写明"唯一写入 = 表 4-2 行 3，五条件 fail-closed"。
- §3.6 第 1 条从"只读自动触发无风险"改为"只读与派生写入都允许自动触发；派生写入受五条件与洁净检查约束"。
- skill 正文里 `route` / `check` 标"只读 + 可能清挂起（会提交）"，让人看得出它会写。
- 探针补：W14 增"派生清除发生后账本已提交、下游视为满足"；W26 增"条件不全时不写"。

### 6. 若选 ②，等价改动

新增 `wf unsuspend <task>`（前置五条件、洁净检查、单键写、单独提交组），`route` 的 next_action 输出该命令，`check` 只报不做；并在 §9 登记"把 §4.3 的'不是独立动作'拆为'独立命令'"这一偏离。
