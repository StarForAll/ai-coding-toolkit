## A. 矛盾与缺漏（按重要性排序）

### A1.【矛盾/缺口】审查 fail 转返工，与返工挂载点定义冲突；2 轮上限后的处置未定义

- §6.5 写"`fail` 转返工（§5.6）"，但 §5.6 返工的适用定义是"发现**未归档前置任务** T 的产物缺陷"，且 §4.3 返工判定模块明确"模型发现**前置任务的产物缺陷**→ 由人确认发起"。审查 fail 针对的是**当前任务自身**的产物缺陷——挂载点不是任何前置任务，现定义接不住这个对象。
- "上限 2 轮"之后仍 fail 的出口未写（workflow-implementation.md §8.5.5 的同源契约有"到 2 轮仍 fail 转 wf rework"的明确出口）。
- 为何重要：这是主干 Check→Finish 闭环上的定义断点，实现时必然要临时裁决，且审查 fail 是高频路径。
- 建议：在 §5.6 增补"自我返工"变体（挂载点 = 当前任务自身，R 继承当前任务前置、当前任务记挂起、加 R 为前置——图结构上无环，语义与"挂起只挡收尾"一致）；或改 §6.5 为"审查 fail 按段内回退回 Execute"并说明与 Check fail 处置为何不同。同时补写 2 轮上限后仍 fail 的出口（返工或人裁决）。

### A2.【缺漏】存量项目（无既有流程）入口缺"基线活文档"与"git 就绪"的产生通道

- §7.1 存量入口（无既有流程）只规定 `wf-bootstrap` 反向萃取初始 spec；但 §4.2 范围闸门是**双层锚点**（任务 PRD + 项目层基线活文档），§3 只把基线的建立挂在**新项目初始化任务**上。存量项目走 bootstrap 后，项目层基线（范围、"明确不做"、验收口径、技术基线）从何而来、由谁写入、是否走 `wf-baseline` 通道，全文未规定——范围闸门的项目级锚点在存量项目落空。
- 同样，"git 就绪"只列在新项目 0→1 产物里；Check 用 git diff、一致性校验比对 git 历史、finish 提交顺序约定都以 git 存在为前提。存量项目若不是 git 仓库，wf 的机制面直接失效，而 bootstrap 入口没有 git 前提校验或 `git init` 步骤。
- 为何重要：直接对应核心需求 2（存量项目可用）与需求 4（范围闸门、Check 关卡失效）。
- 建议：§7.1 bootstrap 入口补两件事：① git 前提校验（无 git 时先 `git init` + 首次提交，或显式声明只读模式并禁用依赖 git 的校验项——前者更简单）；② 存量初始化同样产出基线活文档（从 README/代码萃取草稿，人审后经入口脚本落盘，萃取内容标 `extracted`），使范围闸门双层锚点在存量项目同样成立。

### A3.【外部矛盾】依赖全局 multi-cli-review* 做加性适配，与同仓库 workflow-implementation.md §8.5.7 的"全面移除"计划冲突

- wf §2.2/§6.5/§8 把"按 wf 契约加性适配全局 `multi-cli-review` / `multi-cli-review-action`"列为 P0 排期、finish 门禁的外部依赖；但同一仓库 workflow-implementation.md §8.5.7 明文计划"内部版落地后，全局 `skills/multi-cli-review*` **全面去除**……全仓 grep 清零"。两个产物共用一个 authoring 仓库：若内嵌 wf 模块的内部审查 skill（`wf-task-review*`）先落地，独立框架 P0 的适配对象将被删除，§8 的适配清单成为空文。
- §8 只考虑了"适配完成前门禁空转"，没有考虑"适配对象先消失"。§0 说"先建后定、两者并存"，但这条资源冲突是可预见的，不属于"框架稳定后再决"的范畴。
- 为何重要：P0 依赖在自家仓库内就有被拆除的排期，属计划层面的硬冲突。
- 建议：在 wf-framework-design.md §2.2 或 §8 登记此冲突并裁决其一：① 独立框架 vendor 自有审查 skill 对（与 §7.4 vendor 纪律一致，代价是"不新造 review skill"的自我约定让位）；② 或与内嵌模块的实施排期约定保留全局成对 skill、内嵌模块不执行 §8.5.7 的移除步骤；③ 或把适配目标改为内嵌模块的 `wf-task-review*` 契约。三选一，落 §8 清单。

### A4.【缺漏】任务切分"怎么拆"无判据（需求 4 的半边）

- §4.2 体积上限（≥8 文件 / ±400 行 / 整文件重写）触发"应拆分"检查点，但**怎么拆**全文没有任何指引；§5 只有拆完之后的图机制。上游有现成且验证过的判据可吸收（skills 仓库）：
  - to-tickets 的 slice 规则：每个 slice 独立可验证、**大小适配一个新上下文窗口**、**垂直切片**（按用户可见行为切）而非水平分层切（`~/projects/other/skills/skills/engineering/to-tickets/SKILL.md` vertical-slice-rules 块）；
  - wide refactor 的 expand–contract 序（同文件）：先兼容旧接口、再迁调用方、最后删旧——直接适配存量项目改造任务的切分。
- 为何重要："单任务可控"不只是门禁卡住大任务，还要让拆分动作本身可控；否则检查点触发后模型只能自由发挥。
- 建议：§4.2 拆分检查点的输出指引吸收上述两条（结构可借、文本自写，skills 为 MIT）；expand–contract 同时补进 §7.1 存量入口的实施纪律。

### A5.【缺漏】"可选复盘"无内容形状，浪费了一次 spec 沉淀入口

- §4.2 Finish 只有一句"可选复盘"。mcode-stack trajectory-review（`~/projects/other/mcode-stack/stacks/ronny/skills/trajectory-review/SKILL.md`）提供了现成且界内（单会话人自查、无 hook）的复盘形状：回看轨迹而非只看结果——未验证假设、绕路重试、漏看信号、**压缩后丢约束（instruction drift）**；"找第一个出错点/最脆弱步"；每项发现映射"最廉价的持久修复"（与 `wf-spec-update` 天然衔接）。
- 为何重要：需求 3 的沉淀闭环目前只依赖"任务做完总有教训"的隐含假设；复盘没有形状就等于沉淀入口失灵。成本极低。
- 建议：§4.2 复盘补一句触发条件（如返工后、审查 fail 后、连续调试≥N 次后强制）与上述清单作为骨架。

### A6.【缺漏】spec 准入缺 no-op 判据；索引一致性只查单向

- §6.3 准入双门槛可补第三门槛（skills 仓库 writing-for-agents 的 no-op 测试：**逐条问"它是否改变模型默认行为？"——模型相对，非读者相对，靠实测裁决**；`.../productivity/writing-for-agents/SKILL.md`）。上游同文件还有"环境即事实源"排除判据（`package.json`、`--help` 查得到的留给环境，只缓存查不到的）——直接补进 §6.3 排除面。前者防"只加安全"的沉淀噪音，后者防 spec 变成环境的手抄本，双双服务需求 3。
- §6.1/§5.4 一致性校验目前只报"三段式缺失"（发行模板形态）；Trellis spec-bootstrap 的 Done Criteria 是**双向**核对（"index 行指向的文件必须存在，spec 文件必须被索引"，`~/projects/other/Trellis` 的 trellis-spec-bootstrap SKILL 模板）——服务长期 spec 健康，吸收成本低。
- 建议：§6.3 加第三门槛与排除判据；§5.4 启动校验加索引双向核对。

### A7.【缺漏】Check 与策展加载缺 spec 内容指纹比对

- §6.2 三时点拉取制没有"策展后 spec 又被改"的检测。Trellis inject-spec-context 的决策引擎用 `sha256(spec bytes)` 做指纹（`~/projects/other/Trellis` packages/cli 内 inject-spec-context.py），变更即重教。无 hook 移植法很直接：start 策展时在任务记录记哈希，Check 时点③比对，不一致进 §1.5 WARN 清单。
- 为何重要：需求 3 的"加载到上下文中的 spec 可以少，但必须准确"——策展清单是静态的，spec 是活的，缺这条则"准确"只保证在策展瞬间。
- 建议：§6.2 补指纹字段与比对时点（字段进 §8 机制文档清单）。

### A8.【缺漏】提交顺序约定未含"未识别脏文件"分类纪律

- §4.2 只有"提交顺序约定"四个字。Trellis workflow.md Phase 3.4 的实装纪律值得吸收（该文件在自身模板中记录过两次真实跳步事故）：脏文件分"本会话 AI 改过 / 未识别"两类，**未识别者单独列出、绝不静默进提交**；提交计划一次性确认，被拒即停、不二次提案。
- 为何重要：单人 + 多 CLI 环境下工作区常有非本会话改动（另一 CLI 的遗留），静默捎带是真实风险；对应需求 4。
- 建议：§4.2 Finish 的提交顺序约定按此细化；同时吸收 Trellis 的事故教训成文为 wf 实现纪律：**每个 required 步骤必须在入口脚本的输出中有对应 enforcement 行**（门禁不在模型每轮实际读到的通道里 = 不存在）。

### A9.【缺漏】反例字段无结构；Check 反模式缺"反刷证据"条款

- §6.1 `counterexample` 是自由文本。stop-that-shit 的案例模板（`~/projects/other/stop-that-shit/cases/_template.md`）给出更强结构：**决定性事实**（哪单个事实使判定成立）+ **翻转条件**（改哪个最小事实会颠倒结论）。建议反例字段规定这两段式——它与 §4.2 "改一个事实结论就应颠倒"的既有要求正好互为表里。
- §4.2 Check 段反模式（"失败被表述成基本通过"）可补 stop-that-shit 的反刷证据条款："不相关的成功命令不能顶替缺失的证据；换方法只有当它能补上缺口时才算数"（`.../skills/stop-that-shit/SKILL.md` Resolve uncertainty 段）——防"换个命令跑通就当验证过"。
- 两条均小而准，一句话级改动。

### A10.【缺漏】交接骨架未含"从真实来源收集"与"接续复述"两条纪律

- §4.4 交接骨架吸收了 mcode-stack handoff-doc 的字段结构，但漏了两条执行纪律（`.../stacks/ronny/skills/handoff-doc/SKILL.md` §1/§3）：① 写交接前先从 `git status/log/diff`、真实测试结果收集，不可核实标 unverified，**不凭对话记忆写交接**；② 新会话接续时**先复述 goal 与 next step 再动手**。跨 CLI 多会话场景下（需求 1、4）成本极低、直接有效。
- 建议：§4.4 补这两句。

### A11.【缺漏】外部依赖无 hard/soft 分级

- §2.2 对 multi-cli-review 是单点声明。skills 仓库 ADR 0001（`~/projects/other/skills/.agents/adr/0001-*.md`）给出成熟分级法：每个外部依赖标注"缺失时输出错误（hard）还是只是变钝（soft）"及各自降级形态。wf 的外部依赖不止一对：审查 skill、`wf spec --file` 依赖的匹配引擎（自建）、初始化探测的构建命令（探测不到留空）——逐个标注 hard/soft 使 §2.2 系统化。
- 建议：机制文档（§8 第 1 项）给外部依赖表加分级列；设计层不必展开。

### A12.【实现期警示（非文档缺陷，但应留痕）】

- **指针失效路径**：Trellis 的 `completed` 状态面包屑是 DEAD 代码（archive 同一调用内改状态+移目录，指针解析随之失效，workflow.md 131–137 自认）——wf 归档动作同样是"写终态+移目录+清指针"一体，§1.3 "指向归档视为无活动任务"的定义正确，但实现须验证它在归档动作的**每个中断时点**成立（§5.6 失败窗口）。
- **vendor code-review 改编后的理由改写**：原版"两轴结论不合并"的论证包含"并行子代理上下文互不污染"；wf 改顺序执行后该理由消失，仅"强轴掩盖弱轴"仍成立——§7.4 改编差异说明要改写理由，验收时不得拿原版理由自证（skills 报告提醒）。
- **否定式禁令是反模式**（skills writing-for-agents 实证结论：禁令把被禁行为拉进上下文，可能半读成指示）——wf **skill 正文**（非设计文档）的写作规范应正面表述；设计文档本身大量"禁止/不得"不必改。
- **skill 正文写作规范**：wf 设计未规定 skill 正文的写作理论（指针 vs 正文、leading words、pruning、no-op）——实现期写 `wf-*` skill 时应把 skills 仓库 writing-for-agents 当参照（§8 第 4 项 vendor 工作可一并做）。

### 已核查、不成立的疑点（避免后续重查）

- §5.4 挂起任务的替换/放弃守卫与 §5.6 步 5 的"T 未归档"前提：文档已用"先清挂起再发起"的定案闭合，无矛盾。
- §6.5 finish 门禁第 4 项 spec 处置留痕与 §5.3 写者纪律：Check 入口脚本写入，划界一致。
- §1.3 机制名登记（含 `wf-baseline`、`wf repair`）与 §4.2/§5.5 引用：核对无缺。
- 归档区"已归档+挂起残留"组合：§5.4 状态收尾规则已在校验层排除，无泄漏路径。

## B. 四个上游项目的"仍可吸收 / 无需吸收"结论

| 上游 | 结论 | 要点 |
|---|---|---|
| **skills**（MIT） | **仍有 6 点值得吸收** | ① to-tickets 切分尺寸/垂直切片/expand–contract（A4）；② no-op 测试与环境即事实源（A6）；③ 否定式禁令反模式（A12）；④ hard/soft 依赖分级（A11）；⑤ code-review 的 Fowler smell baseline——vendor code-review（§7.4）适配存量项目（可能无 coding standard）的兜底，应随 vendor 带入并登记；⑥ setup 的问答形状（先探测再问、一节一答、推荐答案先行、人改草稿后才落盘）——初始化任务与 bootstrap 萃取的交互模板 |
| **Trellis**（AGPL-3.0，只借结构） | **仍有 4 点值得吸收** | ① 提交计划"未识别脏文件"分类（A8）；② spec 内容指纹（A7）；③ 索引双向一致性（A6）；④ finish-work 的活动区滞留任务清点（"看起来已完成但未归档"批量确认归档）——wf 周期性巡检（§5.4）只覆盖归档区与 spec，活动区积压无发现时机，建议并进周期性清点 |
| **stop-that-shit** | **仍有 3 点值得吸收** | ① 反例字段结构化：决定性事实+翻转条件（A9）；② 反刷证据条款进 Check 反模式（A9）；③ 成对评测方法论（16 案×3 臂×3 次，instruction 臂分离纯文本效果）——wf 无 hook 方案唯一可用的效果评估法，配套"只测窄命题、不估普遍性"的证据诚实纪律，可作 §7.4 vendor 验收与纪律效果声明的口径 |
| **mcode-stack** | **仍有 3 点值得吸收** | ① handoff-doc 从真实来源收集+接续复述（A10）；② trajectory-review 复盘形状（A5）；③ harness-experiment 最小实验纪律（假设一句话、一次一改、看翻转任务而非平均分）——§7.5 吸收决策与 §7.4 vendor 验收的廉价增强。**许可注意**：其 `engineering-*` 系改编自 Google Engineering Practices（CC-BY 3.0，stacks/ronny/NOTICE.md），吸收拆分策略须"结构可借、文本自写" |

**明确的越界项（已核实不吸收，勿在实现期回潮）**：stop-that-shit 的 Guard hook 三态/五类硬决策/委托预算/runtime sidecar/多宿主适配器（全部依赖 hook/后台/多平台）；Trellis 的 `trellis mem` 跨会话对话检索（等价平台矩阵、与"任务记录唯一恢复源"冲突）、task.json 生命周期钩子（第二套副作用源）、四层变体链；mcode-stack 的 lifting-loops 定时扫描/私有 ledger（常驻进程+双事实源）、tool-budget/context-tax 的 Mode B（wf 不构建 harness）；skills 的外部 issue tracker 状态机、并行子代理原语、多 harness 元数据双轨。

## C. 上游的警示教训（对 wf 的印证）

- **stop-that-shit 的复杂度自反**：为极端场景写出 609 个测试与 52KB 适配合同，正是它自己定义的 hypothetical hardening。wf 的"新机制四问"（§1.5）必须持续用于 wf 自身机制（§5.6 幂等键、§5.4 组合识别都在其射程内）。
- **Trellis 的 fail-open + 仅 stderr**：注入失败 exit 0 无 stdout，告警进不了模型上下文——wf WARN 清单（§1.5）走"正常输出可见"是正确规避，实现勿回退。
- **mcode-stack 的被动触发不可靠**：靠 description 塞 trigger 关键词提命中率，恰恰证明"指望模型记得"是弱机制——wf 的主动触发制（§1.3）勿倒退。
- **skills 的分发层是持续痛点**（ADR 0002 双轨分发）：佐证砍分发 CLI 的正确性；其"长期空转会让人误以为机制在工作"的自警同样适用于 wf 所有 unavailable 回退路径——回退留痕（§6.5）要坚持记。
