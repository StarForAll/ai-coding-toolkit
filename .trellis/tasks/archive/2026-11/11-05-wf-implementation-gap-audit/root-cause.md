# 归因：为什么"该消失的资产"会漏掉

> 本文件回答"为什么会出现这个遗漏"，是执行修复前的前置动作（人要求）。只对被批准的 R1-1（`multi-cli-review*` 清理）与 `workflow-scan` / `workflow-repair` 的用户全局残留做归因；不提修复方案以外的改动。

## 1. 两个事实

| 对象 | 仓库层 | 用户全局层 |
|---|---|---|
| `multi-cli-review` / `-action` | 仍在 `skills/`（设计稿 §7.4 要求适配后移除） | 仍在 `/home/xzc/ops/data/ai/skills/agents-skills/`（与仓库副本逐字节相同） |
| `workflow-scan` / `workflow-repair` | 2026-10-28 已 `git rm` | 仍在同一全局库 |

## 2. 逐层归因

### 2.1 设计稿把它写成"有前件的后续动作"，但没有给触发点
- §7.4 原文：「适配完成后由原产物按**既有清理计划**移除，清理不得早于自有副本投放与验收完成」。
- 这句话定义了两个**条件**（适配完成、验收完成），却没定义**谁在什么时候执行**、也没定义**执行完的判据**。结果它落到"人想起来的语义动作"这一档——而首轮的收口机制（`round1-closure-plan.md` 的 A/B/C/D/E 五条轨道）全部是"代码与文档缺陷修复"，**没有"资产销毁"这一类**。缺轨道，就不会被排进队列。

### 2.2 "本仓库全局"这句话掩盖了分层
- §7.4 只写"本仓库全局 `skills/multi-cli-review*`"，而真实载体有三层：仓库源资产 / 用户全局共享库 / 目标项目投放副本（`wf-review*`）。
- 三层里只有**第一层**被写进判据。执行时按"删了仓库就等于删了"的直觉收工，正好漏掉唯一会影响"下次会话是否还能调用"的那一层。
- 实测：`~/.claude/skills/multi-cli-review` 是指向 `/home/xzc/ops/data/ai/skills/agents-skills/multi-cli-review` 的符号链接，与仓库副本 `sha256` 相同（`6d409e74…`）。删仓库不改这一层。

### 2.3 所有自检都是"存在性/一致性"，没有"该消失的消失了没有"
- `validate-skills.sh`：校验**存在**的 skill 结构；
- `trellis-library validate`：校验 manifest 与已登记资产的同步；
- `validate-wf-design.py` / `check-doc-refs.py`：校验**引用**是否悬空；
- `build-wf-release.py --verify`：校验发行树与源树字节一致。
- 四类全是"正向断言"。**没有任何一项会因为"某个早该删的目录还在"而失败**。所以绿灯不暴露这一类遗漏——这也解释了为什么首轮自检全绿而 R1-1 仍成立。

### 2.4 退役任务的判据范围只到"仓库内三个根"
- 2026-10-28 的退役任务判据 A4/A5 原文是 `grep -rln "新项目开发工作流" skills/ .claude/skills/ .agents/skills/` → 0、四个 skill 目录不存在。
- 这里 `.claude/skills/` 指的是**仓库内**的 `.claude/skills/`，不是用户 home 下的同名目录。判据按字面通过，用户全局库不在视野内。
- 根因与 2.2 是同一个：**"仓库"被当成了"机器"**。

### 2.5 交叉验证缺一个方向
- `validation.md` 的验收项都是"新能力是否成立"，没有一条读"旧能力的残留"。
- 因此即使某轮审查想起这件事，也没有现成的检查面可以挂。

## 3. 一句话归因

**这类遗漏不是执行者疏忽，而是机制缺一类事实**：`资产销毁` 与 `跨仓库层的残留` 既不在设计稿的可执行清单（无触发点/无判据），也不在任何自检或验收项（全是正向断言），还不属于本轮收口轨道的任何一类（只有代码/文档缺陷）。三者都缺 → 它必然沉底。

## 4. 由此得到的通用处置（本次只落两处，其余登记）

- 本次执行：分层清理 + 引用同批更新 + 以"grep 归零"与"目录不存在"作为完成判据（补上"该消失的消失"这一方向的检查）。
- 登记（不在本次做）：若要防止同类问题再发生，需要一个**分层资产清单 + 反向存在性判据**（仓库 / 用户全局 / 目标项目三个根），并挂进收口轨道；这属新增检查面，须按 charter T6 顺序（先改既有产物 → 造确定性机检 → 新增规则）。
