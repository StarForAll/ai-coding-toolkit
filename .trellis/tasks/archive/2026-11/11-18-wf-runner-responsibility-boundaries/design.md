# 运行器职责与结论设计（审查稿）

## 1. 使用契约

入口名称与 T1–T3 的调用顺序沿用现有纪律。资源策略由调用者实际选择的功能决定，在现有 full 计划与独立 repro 计划中规范化并冻结。内嵌 repro 消费父计划。避免新增运行档位，避免用散落的环境开关表达同一个资源决策。

| 请求 | 本次消费与存储 |
| --- | --- |
| 子集、dev 全量或独立 repro 的常规执行 | 新结果目录、本次夹具、必要的本次 dev 发行副本和本次日志。模板可在本次执行中复用。历史结果和持久模板缓存均无读写。 |
| dev `--no-build` | 显式只读消费预备好的共享测试发行，继续核验输入和树摘要并持消费期租约。缺失、陈旧或未完成事务由 `wf_test_release.py --ensure` 显式准备或恢复后重试。直接 CLI 的发布与恢复协议保留。 |
| full 的 `--template-cache` | 显式申请跨次模板复用，使用现有 `acquire` 及其事务。保留 `--no-template-cache` 和 `WF_NO_TEMPLATE_CACHE=1`，负开关继续禁止跨次缓存，冲突在写前诊断。`--no-template` 继续禁用模板。复用材料的身份和可重定位性按 §2 验证。 |
| dev 显式 `red`、`both` 或 `auto` | 有合格 red 相位时输出可跨次使用的证明。auto 还先读同主体证明决定相位。无参数的独立 repro 继续执行 both，本次证据保存在本次目录。`green` 不读写共享 proof。full 已支持的 `WF_REPRO_MODE` 继续等价于显式选择。 |
| 候选 `green` 或 `auto` | 消费已明确选择的候选仓库。auto 只读匹配的 dev red 证明。候选结果记录本次已验证的提交和相位。 |
| 盘点、轮转与退役 | 维护入口按需显式调用。结果轮转提供候选报告，结果删除通过现有精确退役入口。结果和夹具的授权规则见 §2。模板与测试发行缓存继续使用各自的维护入口。 |

固定 `WF_RESULTS_DIR`、`WF_REPRO_RESULTS` 或独立 repro 的 `--results-dir` 时，应用 §2 的目录认领规则。默认生成的路径继续使用已有 cache 布局及 `run-`、`repro-` 前缀，使用新执行身份防止 PID 重用造成同名。测试发行共享路径配置继续用于显式消费和维护。跨次夹具模板只有一个主动启用项，过去用于禁用的参数保持有效。旧结果和旧证明按原样读取。

## 2. 目录认领与历史材料授权

### 2.1 新执行与计划镜像的目录规则

| 指定目的地状态 | 真实执行 | 支持显式输出的计划预览 |
| --- | --- | --- |
| 安全路径下不存在，或无 owner 且完全为空的真实目录 | 认领一次，创建本代结果 | 创建一次计划镜像 |
| 已有 plan-only owner 或计划镜像 | 拒绝并保留预览，包括同一命令的预览 | 拒绝覆盖。新预览可用新路径 |
| finished、active、初始化未完整、旧格式、非空无主、异常类型或越界 | 拒绝，保留已有材料 | 拒绝，保留已有材料 |

普通 help/list/dry-run 无显式镜像时保持零写入。独立 repro 的清单模式沿用只显示清单的行为。已有目录导致拒绝时，使用新目的地即可执行，旧目录可独立盘点。结果与预览共用 `resource_lifecycle` 的认领前置判定，取得租约后核对实际目标，拒绝发生在写 owner 或 plan 之前。删除执行阶段的旧代 prepare 清理路径。

`wf_test_paths` 继续负责解析和校验路径。真实执行在冻结计划前只分配一次执行身份，用于隐式路径和 owner。当前代临时结果、pycache 和夹具继续受原有路径、安全锁及 namespace 约束。需回收的本代资源由 controller 监督，或在有清理所有者后创建。既有显式保留语义继续有效。

### 2.2 本次使用的发行和模板

- dev 默认发行在本次私有工作路径中使用既有构建、验证与消费方法。版本与 ref 解析规则沿用现有逻辑。发布和恢复一个共享缓存只发生在显式共享缓存操作中。worker 可达的所有发行和模板挂载视图都必须只读，包括可写结果树下的别名。优先使用分离的工作根。锁 sidecar、构建 staging 和 namespace 下的同址引用一并验证。
- 显式模板缓存继续从已核发行与模板内容派生身份，克隆时重指向本次安装路径并验证空态和发行身份。不同本次路径有相同输入时，用冷/热对照验证缓存命中符合当前规则。无法确认模板重定位时拒绝该副本，按现有校验失败路径报告，并给出改用本次模板执行的方式。dev HEAD 不可读时沿用已登记的本次模板路径，摘要准确标来源。

### 2.3 历史结果与夹具的删除授权

名称、类型、前缀和后缀只用于发现、分类和诊断。有效 owner、同代且一致的状态记录或夹具 marker 只建立根级归属。可核验的 plan-only 或旧记录按各自已有的根身份判断。缺少根证据、记录互相矛盾、根被替换或有活引用时拒绝。根级归属不会传递给目录内任意文件，包括后来加入的 `logs/` 或替换的 `summary.json`。

| 入口 | 授权范围与证据 |
| --- | --- |
| 普通执行、预览 | 仅认领 §2.1 允许的新目的地。当前执行可以用现有清理判定回收本代临时资源。 |
| `inventory-results`、`prune-results` | 只读。保留 prune 的筛选和 `--keep` 语义用于报告候选。报告指向现有精确退役入口。普通运行移除相关调用。 |
| `retire-results --retirement-mode safe-legacy` | 仅做可单独证明的旧 marker 和空壳收尾。存在其他子项的结果树或夹具进入精确人工确认。空目录仅以空目录操作移除。 |
| `retire-results --retirement-mode manual-retained` | 对确有根归属且无活引用的历史树，包括可验证的非空旧格式根，先展示所选根及其全部条目并计算内容快照摘要，再由操作员通过现有 TTY 方式授权这份具体清单。列表可见的同名手工文件属于用户审查的删除范围，没被选中的根及没有出现在确认快照中的材料保持原样。 |

现有结果 inventory/selection 和退役报告承载确认，不给普通运行增加持久产物清单。批量盘点可浅扫，实际退役前由精确盘点生成全树范围及摘要。快照包括真实根和子项身份、相对路径、类型、文件摘要和链接本身。复用现有树清单能力，按精确根读取并避免跟随链接或跨挂载。旧 selection 只有 owner/state 摘要时，重新盘点后才可确认。清单不可读或不能闭合时拒绝。

在执行同域租约下复验待确认集合，并在 TTY 确认后、删除前再核对归属、活引用和精确快照。摘要变化时取消整次删除。结果/历史夹具退役只删除逐项确认的条目，通过已核父目录定位并拒绝替换链接。已确认的链接只移除链接本身。目录从底向上以空目录方式移除。发现新条目或身份漂移立即停止，保留未确认材料并写现有部分完成报告。非协作进程同时写入不在租约保障内，疑似仍有外部写入的现场应先停止写入再盘点。模板和测试发行的既有专用事务恢复和维护保持原有范围。

## 3. 一次执行、一次判定

### 3.1 清理、候选核验与取消

保留既有进程监督和锁域。controller 持有本代执行身份，在进程退出后汇总命令终态与清理证据；清理以这份事实授权，仅操作本代资源。独立记录候选终核、结果门禁及发布失败。候选校验失败、取消短路或相位报告坏损均有归因，然后仍走同一清理出口。根监督丢失或回收许可缺失时保留本代相关路径。控制器显示真实的 `cleaned/failed/unknown`，并保留原有目标失败和信号退出语义。

候选初核照常阻止非法输入启动。终核用于接受候选结论与 proof。已经取消时终核可标记未完成或取消；候选有可核到的身份差异时才报告漂移。候选终核、证明写入和结论发布均需服从本代取消，清理事实在它们失败时仍然可见。进入最终成功决策前的取消先于正向提交。已提交的单条合格 red 证明仍是独立的相位事实，沿用原先对后续失败的处理。

本次私有发行在候选/证明所需的输入核验全部完成后才回收，包含本次有归属的 staging 与 sidecar。回收跟随同一 controller 的资源收尾，保全未确认路径。共享发行与候选根仅释放本次消费租约。本次发行的回收失败进入清理事实并阻断正式成功。

### 3.2 repro 事实与复用证明

`validate_repro` 基于冻结 bundle 为全部预期相位建立应答，再逐用例核验结果、日志与收据。合法包下缺失或异常的记录只影响对应相位，意外记录另计结构问题。相位必须先核本代、状态、命令身份和监督/本地回收，再判定日志断言结果。已验证的目标断言失败计 `failed`；未启动、取消、基础设施错误、证据缺失、不一致或未确认清理计 `unverified`。非法 bundle 显式报错并保留原材料，摘要相位计数为 null。报告、门禁与写证明复用这份判定。合法 bundle 下报告允许失败，同时每个相位保持计数守恒。

默认、显式与内嵌三条路径使用同一证明写入条件。显式写入复用现有唯一 writer，并在写前完成输入和当次终态验证。可以有其他 case 发生已确认的断言失败，合格 case 可以独立写入；取消已到达、清理或证据不完整、候选漂移与状态存储错误均阻断本次证明更新。schema 5 proof 继续按现有身份校验可读，旧格式保持历史语义；无复用请求时不加载共享状态。

### 3.3 正式结论的提交点

让 `summary.json` 成为本代整次判定的唯一持久结果，保留 `summary.status=ok|failed` 和主要统计字段。`run-state.json` 负责生命周期、归属及已观察的清理事实，`.runner.json` 负责监督和诊断。新版职责和兼容迁移按 §3.4。

控制器先准备本代诊断和生命周期记录、核验其内容，再将完整 summary 写入同目录临时文件并校验，按取消结论原子发布。成功 summary 的原子替换是正式提交点，随后只输出同一结论并退出。取消或必需写入失败时输出明确失败，文件系统仍可用时尽量发布失败摘要；无可发布摘要时以非零退出和已留诊断为准。对于已经有合法 plan/bundle 而部分输入缺失的失败运行，失败摘要允许记缺项，不能通过成功输入核验。新目录协议使本次发布失败不会暴露上一代的成功摘要。暂不承诺断电级持久性。

| 当前字段与写入者 | 已核实的读者或约定 | 新契约与迁移 |

## 4. 验收来源与分母

- 完成模式、tag/group 与代表集选择后，在 `plan.py` 对所有可执行单元应用同一候选资格。精确请求 dev-only 单元明确拒绝。全量/代表集显示排除 ID 和原因，零匹配失败。repro 沿用 `repro_select` 的已安装断言资格。候选 audit、source coverage 和注册表读取同一资格，并核对所记录的实际来源。候选资格允许真实试跑取证后变更，审计试跑的未认证条目不可进入正式通过分母。
- `f0`、`p5_spec` 和 T3 中安装 repro 的候选链必须通过实际候选入口验证。候选全量逐个审核 flow/extra。R72 的现有 dev 卸载路径保留。若 R72 有合格候选入口，须实际使用候选安装器与请求 ref 后才登记并计数。候选的已排除项目及 dev 证据均可追溯。
- 将 `r67_tests.py` 的运行器假树断言并入现有运行器契约测试，匹配已有行为时复用已有对照，缺失时迁移。产品侧写权、baseline 与清单断言仍在 R67。核对迁移前后每项断言的验收去向和相应分母。按实际结果更新期望数、候选审计及覆盖基线。

## 5. 防止职责再次偏移

把以下机制写入现有 `wf-delivery-discipline.md`，同步可运行的用法和已有契约测试。

1. 默认执行的行为测试预置旧结果、模板、发行缓存与 proof，观察当前运行的实际读写范围。正向对照证明显式缓存和维护仍可用。
2. 运行器变更必须说明受影响的使用场景、当前 run 消费的材料、判定所有者及失败/取消出口。影响本次执行范围、历史写权限、正式结论或验收来源的改变，更新对应的入口契约测试和交付纪律。无法指向具体调用者的状态层或公共开关没有纳入本设计。
3. 测试断言面向用户可观察事实，包括范围、退出码、结果、保留路径和历史字节。仅用于诊断的内部调用计数无需维持正式契约。删除被替代路径与相应断言，防止新旧机制并行。已有 runner 测试能覆盖时就地扩展。

## 6. 审查时已知的取舍与证据界限

- 历史结果会累积。老的无人值守结果轮转会变成候选报告，有删除需求时要精确盘点并显式退役。固定路径调用者需给新的执行或预览目标。执行预算不作门禁。仓库内的 CI 与 pre-push 未发现这些字段的消费者，仓库外消费者未验证。
- 沿用产品树只读、宿主 git 身份、解释器事实和 SUT 隔离约束；旧结果只用于读取、明确盘点和核验后维护。
