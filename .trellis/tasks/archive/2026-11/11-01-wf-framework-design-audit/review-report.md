## 一、结论摘要

共 15 条问题：**阻断 0 条、高 4 条、中 7 条、低 4 条**（修复状态见第十二节）（A1 经人工澄清后撤回；A2 经三轮澄清后由阻断降为中，见第十节、10.1、10.2；D4 见第九节）。核心判断：

1. **设计最薄的一层不是规则数量，而是"规则到可判定物"的最后一跳**——令牌、原因码、"模板占位"、未提交路径归属这四个直接被门禁消费的判定物，正文要求了却没有定义，也没有进 §8.1 交付清单（B3）。
2. **（A1 已撤回）** skill 投放根与 `.wf/` 的分工在 §1.2/§7.1 已经明确：skill 投宿主可读根（默认 `.agents/skills/`），`.wf/` 承载脚本、流程文档、模板与项目数据；此前判定的冲突不成立，只留一条不计数的术语备注。
3. **复杂任务审查链路已由人裁决「降级为框架自有资产（随发行投放、随卸载移除），全局 skill 只作适配源」，但 §6.5 的适配源仍指向会被另一产物清理的作者侧路径，§7.4 仍写着待裁决，交付与验收项也缺这一环**（A2，复核后为中）。
4. **验收层是"有名无物"**：72 条场景行对 141 条索引行没有映射，三夹具没有可观测判定物，"每项门禁至少一条应拒绝/应放行场景"因此无法核对（C4、C5）。这与"避免同一问题反复修"直接冲突：没有映射，每轮修订只能靠人工回扫。
5. 机检器本身有可修的盲区（D1–D3），而它正是 §0 维护协议里唯一的机械护栏。

## 二、原阻断级条目（复核后：A1 撤回、A2 降为中，见第十节）

### A1（已撤回）资产落点：skill 投放根与 `.wf/` 的分工

人工两次澄清：① 本框架的 skill 投送目标就是宿主可读根（默认 `.agents/skills/`）；② `.wf/` 是通用层存储（脚本、流程文档、模板、项目数据）。据此原判撤回：

- §1.2 L58 已明确 skill 根的默认候选；§7.1 L502 的「skill 根/`.wf/` 骨架」是两个落点，不是矛盾；§7.2/§7.3 的托管路径与卸载范围按"已登记的框架资产"处理，覆盖得到这些路径。
- 上一稿的"项目外根与'禁止写出项目边界'冲突"读得过宽（L530 限制的是符号链接逃逸）；"与用户全局同名 skill 遮蔽"也不成立（自有副本可沿用框架自身的 `wf-*` 命名）。
- 仅留一条**术语备注（不计入问题清单）**：§7.3 L540「不得猜删外部 skill 根」的"外部"建议写成"非本框架投放的根"，避免被读成"项目外路径"。

**结论：A1 撤回，不计入问题数。**

### A2 复杂任务审查链路：适配源与所有权（人工已裁决降级为自有资产，复核后降为中）

- 位置：§6.5 L473、L475；§7.4 L550；§8.1 L563。
- 原文：
  - L475「以本仓库 `skills/multi-cli-review*` 为适配源……两侧须加性支持 `--task-id`……**未适配前不宣称可用**」——把适配源固定为该全局 skill。
  - L550「实际采用 vendor 独立副本或调整依赖前**须人裁决**；不得修改/删除另一个产物来让本框架安装成功」——承认选择未定，且内嵌模块有计划移除它。
  - §8.1 L563 只要求"核对成对契约"，未要求"交付可用的审查适配产物"。
- 影响（原判，已被下方复核修订覆盖）：§6.5 是复杂任务正常归档的强制项（charter T4 不可削减），而它依赖一个"改动归属未裁决 + 与另一产物资源冲突 + 当前未适配"的资产，开发顺序因此不可确定。
- 根因：**R1 + R2**——强制链路的关键依赖只在"审查文件协议"一节被固定，其所有权变化没有被登记为 §6.5 的消费点，两节各自成文。
- 建议方向（与人工裁决一致）：把审查 skill 对作为框架自有资产交付（与内嵌模块 `wf-task-review*` 同构），§6.5 改为"以本框架自带的审查适配副本为协议源，参数契约见 §8.1 交付项"；同时把"审查适配产物可用"写成 §8.1 的一项独立交付与 §8.2 的一条场景行。


**复核修订（2026-11-01，口径更正后重判）**：先澄清"参考 `workflow-implementation.md` 的做法"，随后更正为「`multi-cli-review*` 要像该文档那样**降级到该控制流程中、而非留在全局**」。即审查 skill 对由框架自己持有，与内嵌模块的 `wf-task-review*` 同构（随发行投放、随卸载移除、纳入三方升级），本仓库全局 `skills/multi-cli-review*` 只作一次性适配源。据此：

- **原阻断理由（归属未裁决）与上一轮的高危理由（与内嵌模块的删除计划冲突）都消失**：两个产物各自持有副本，删除全局副本不再与依赖冲突，反而与 §7.4 的「自有副本、不依赖全局同名 skills」原则一致。**降为中。**
- 剩下三件属"写清楚 + 交付项"，不再涉及跨产物对抗：
  1. §6.5 L475 把适配源写成"本仓库 `skills/multi-cli-review*`"，是**作者侧路径**，会被另一产物的清理（§8.5.7、R11、决策记录 2026-10-29）删除。迁移后产品契约必须指向框架自有副本，否则留下一个会消失的指针；建议写成"适配完成后以框架自有副本承载，全局副本仅作一次性来源"。
  2. §7.4 L550 仍写「须人裁决」「不得修改/删除另一个产物」——按决定改为记录结论与改造范围（自有副本、命名前缀、随发行投放）。
  3. 交付与验收缺环：§8.1 第 3 项只要求"核对成对契约"，应加"自有副本作为发行资产交付，含三方升级与卸载覆盖"；§8.2 补一行断言（缺副本时复杂任务不得完成 / 卸载后不残留）。
- **顺序约束**：全局副本的清理动作必须与"正文改指自有副本"同批或在其之后执行；先清理会把适配源删在迁移前。

## 三、高级

### B1 启动时"挂起复评"要写项目状态，但启动会话可能没有写权

- 位置：§5.4 L303、L311；§5.6 L331；§4.4 L228。
- 原文：
  - L311「挂起复评在每次归档成功后及**启动结构校验通过后**执行，按 §5.6 的挂起清除判断」。
  - L331 挂起清除是状态变更动作，且「若 T 将成为执行候选且已有其他执行候选，同一动作给 T 记"等待人恢复"的暂停」——明确是**写**。
  - L228「**未持有者只读**或在项目树外准备，**不推进项目状态**」。
  - L303 启动校验本身是只读核对，不取得写权。
- 影响：一个刚 `start`、未持写权的会话，要么跳过复评（违反"启动后执行"），要么写别的任务记录（违反写权唯一）。"复评的写者身份与授权范围"没有定义。
- 根因：**R2**——写权条款在 §4.4 定义，复评触发点在 §5.4 定义，两者之间的"谁来写、在哪个写者类别下写"没有被登记为消费点。
- 建议方向：在 §5.4 挂起复评处补一句语义出口：仅在"当前会话已持有写权且目标任务在其可写范围内"时执行，否则只输出"待复评"事实并给出取得写权后的重入路径；或在 §4.4 增加"复评由归档者（finish，持写权）执行"。

### B2 首次安装的"初始维护持有"没有落点

- 位置：§4.4 L234；§3 L143；§7.1 L502；§5.3 L293。
- 原文：L234「首次安装确认无既有 wf 数据后，在**同一最小协调范围**先建立初始维护持有，再投放并释放为空闲；这只豁免初始化协调记录前置」；L502 安装流程是"预览 → 取得维护持有 → 投放"；L293 写权记录位置是 `.wf/writer.json`。
- 影响：`.wf/` 与 `.wf/writer.json` 恰恰是"投放"的产物。首装时"先持有、后投放"的记录必须写在某个已存在的容器里，正文未定义（`.wf/` 预建？项目根临时文件？宿主临时目录？）。选错会让首装失败后的状态落在框架自己定义的"未知写者"分支里，正是 §4.4 L238 想避免的情形。
- 根因：**R1 + R4**——协调记录被假定为"项目数据"，但首装时尚无项目数据边界。
- 建议方向：明确首装协调记录的落点与生命周期（例如"项目根 `.wf/` 由安装入口创建，`writer.json` 作为首个写入且必须在预览清单中列出，安装失败时按 §4.4 待恢复处置"），并把该文件纳入预览项而非隐式副作用。

### B3 四个门禁判定物没有定义，也没进 §8.1 交付清单

| 判定物 | 被引用处 | 缺失内容 |
|---|---|---|
| 本次预览令牌 | L90、L236、L540、§8.1 L562 速查 | 由谁生成、如何校验、失败出口；§8.1 L561 机制设计清单无此项 |
| 原因码 | L107「输出原因码」 | 码表、稳定性约定、归属文档；§8.1 清单无此项 |
| "非模板占位" | L187 开工门禁 | 模板/占位的可判定标记集（脚本如何识别） |
| 未提交路径"明确归属本任务" | L193 触碰路径 | 判定规则（按批准 `touch_paths`？按交接记录？） |
- 影响：这四个都是**入口脚本必须机械判定**的输入，现文只给结论不给判定物，实现者只能自造；自造后 §8.2 无对应断言，验收无法核对。
- 根因：**R1**——判定细节下沉到机制设计，但 §8.1 交付清单没有同步扩容，形成"下沉即丢失"。
- 建议方向：在 §8.1 第 1 项机制设计清单里成组补入这四项，并在 §8.2 各加一行断言；原因码可先只要求"码表随机制设计交付、已用码不得改义"。

### B4 审查材料发往异种 CLI 模型服务，没有外发授权与数据边界

- 位置：§6.5 L473；对照 §5.7 L351、L361；§1.1 L37。
- 原文：L473 主会话向 reviewer 提供 diff、需求与测试结果，reviewer 可只读仓库覆盖契约/spec 轴；§5.7 只写「定义不授予工具、提交、**外发**或扩范围的权限」，即"外发"是存在的动作类别，但没有任何条款规定**谁**、在什么范围内批准把项目内容交给两个外部审查 CLI。
- 影响：项目私有代码与 PRD 会经两个第三方模型服务处理；这在单人本机环境里通常是默认外发。框架对敏感性/脱敏/范围/记录无要求，与 §1.5"强度如实声明"和 §4.4"不复制秘密正文"的谨慎口径不一致。
- 根因：**R1**——审查链路被当作"工具可用性"问题（§6.5 不可用处置），没有把"数据离开本机"当作需要授权的操作类别登记。
- 建议方向：在 §6.5 增加一条：审查发起即人明确授权外发本次审查材料，记录材料范围与目标 CLI；机制设计给出"最小材料集"与"排除项（凭据、私密配置）"的检查点；§8.2 增加"未授权外发被拒绝"的断言行。

## 四、中级

### C1 预算机制只覆盖 spec，流程文档与 skill 正文没有预算和"未完整装载"标记

- 位置：§6.2 L443（唯一的预算定义）；§1.5 L109（把"预算挤出的正文/提醒/汇总"当作通用降级对象）；§1.1 L42（流程细节集中在 `.wf/workflows/`）。
- 影响：§1.5 的降级可见性读起来是全局约定，实际只有 spec 有预算键。流程文档、charter/设计文档、skill 正文本体都可能超长，而每次推进都要求"读当前步骤正文"（§4.1 L168），截断时没有"未完整装载"标记，等于允许半读放行。
- 根因：**R1**——单一机制的落点（spec）被写成通用原则（§1.5）。
- 建议方向：要么把 §1.5 的降级对象限定为 spec 并说明其余文档"必须完整读取"，要么给流程文档定义同一套预算与标记；同时把预算键在 §3 项目配置与发行骨架里补齐（现在只写 spec 预算）。

### C2 三方升级的 O（旧模板）只有哈希，内容恢复没有出口

- 位置：§7.2 L516（O/L/N 只记"身份/哈希"）、L530（「按已安装发行版本重取原始模板可恢复发行依据」）、L514（发行身份=专用引用+清单）。
- 影响：冲突行"预览差异，人选择保留/恢复/合并"需要 O 的内容；"恢复"也需要 O。若旧发行引用已被删除、仓库不可达或离线，正文没有给出口（只给了"安装记录丢失时由人确认重建清单"，那是清单不是 O）。首次安装的本地偏离与"恢复为发行版"动作会永久卡住。
- 根因：**R1**——"可恢复性"被当作发行源属性，没有要求在本地保存足以重建 O 的最小事实。
- 建议方向：明确 O 的内容随投放保存在可重建位置（例如安装记录内按路径保存模板副本或可追溯的发行引用+提交），或在 §7.2 增加"O 不可取得"的显式阻断出口与人工处置路径。

### C3 会话标识复用没有检测，终身绑定可能误锁

- 位置：§1.3 L80（身份要求"压缩后保持不变且新会话不同"）、L82（绑定终身、同一会话不能换对象）、§5.4 L307（"同会话绑定冲突"）。
- 影响：若宿主在某类重开/迁移后复用同一标识，新会话会被判为"已绑定旧对象"，而设计禁止改绑，唯一出口是 repair；设计未定义这种复用如何被识别（§5.4 只有"记录缺失或冲突"），也没有可对照的会话实例证据。
- 根因：**R2**——身份契约由宿主保证，但框架侧没有任何"同一标识、不同实例"的判别依据。
- 建议方向：绑定时同时保存一个低成本会话实例证据（首次绑定时间 + 进程/宿主会话非密标识），不一致时输出"需人裁决"而不是直接当作已绑定；补一行 §8.2 断言。

### C4 §8.2 场景行与定义行没有映射，"每项门禁至少一条场景"不可核对

- 位置：§8.1 L564「每项门禁至少有一条应拒绝和最近的应放行场景」；§8.2 L576–L649（72 条三列场景行）；索引 141 行（134 设计 + 7 charter）。
- 事实：三列表格 72 条数据行对 141 条定义；机检只核对 charter 条目必须在 §8.2 有带 `charter Tn` 的行（`validate-wf-design.py:238-249`），设计侧**没有任何覆盖核对**。抽样核对：`spec 单位`、`匹配排序`、`周期清点`、`项目判定` 等定义在场景表里找不到字面行，是否存在语义对应（如“周期清点”↔“策展引用统计”）无法确定——这本身即问题：映射没有被登记，覆盖与否只能靠人逐条推断。
- 同一缺口的实例：§4.4 L236 与 §5.4 L303 都把「维护组状态与记录不符」判给交人裁决，但三档表 13 行里最接近的「WIP 去向或维护范围未明」待决事实不同（路径归属 / 维护是否触碰 WIP），没有承载「回执与实际状态不符」的行。
- 影响：这正是"反复修复"的温床——每轮修订新增定义后无人知道它有没有验收面；§8.1 自称的交付要求实际上无法被核对。
- 根因：**R3 + R5**——验收层靠语义命名，没有登记映射。
- 建议方向：在索引表增一列"验收场景行"（或反向在 §8.2 每行首列写定义号），让"定义 → 场景"可机械核对；机检增加"每个门禁类定义至少被一行场景引用"的断言，缺则 FAIL。

### C5 三个验收夹具没有可观测判定物

- 位置：§8.2 L572（三夹具）、L669（无 MCP 夹具须覆盖的动作清单）、L671（夹具绑定）。

## 五、低级（机检器缺陷与文本一致性）

### D1 § 引用正则只匹配两级，三级引用会被截断后放行

- 位置：`scripts/validate-wf-design.py:101` `re.findall(r"§(\d+(?:\.\d+)?)", ln)`。
- 事实：`§1.3.4` 只会校验 `§1.3` 是否存在，`§8.5.3` 同理；越深的错误引用不会被发现。另 L98 对含外部文档名的整行跳过校验，同一行内的本文档 `§` 引用也一并免检（残差 2 行即此机制产物）。
- 影响：§0 与 revision-gate gate 2 都要求机检"断言自身覆盖"，这条正则使"引用可解析"的结论偏强。
- 建议方向：用 `§(\d+(?:\.\d+)*)` 捕获全层级并在层级 >2 时报错（或至少校验紧邻字符不是 `.`）；跳过外部文档行时只跳过外部引用而非整行。

### D2 索引第六列"核对状态"未被校验

- 位置：`validate-wf-design.py:171-191`（`check_index` 只校验列数与 § 引用）；索引 L5 规定三种状态与"已核对·有消费必须给出节号与理由"。
- 影响：空白、错拼或"已核对"无后缀都能通过；这正是 revision-gate gate 3 明确禁止的"用空白冒充后两类"。
- 建议方向：校验取值 ∈ {未核对, 已核对·有消费, 已核对·仅定义节}；"有消费"行第 5 列必须含 §，且与第 3 列至少有一个交集，否则 FAIL。

### D3 消费命中率的口径与"无自测"削弱了阈值的证明力

- 位置：`validate-wf-design.py:266-292`（按定义名在正文出现判定消费）、索引 L7；`scripts/tests/` 只有 `__init__.py`，机检器无回归测试。
- 事实：命中率把"名字在别节偶然出现"也算作已登记消费；常见词定义（如"项目配置""项目基线"）几乎必然 100%。阈值 ≥90% 被当作 pass 条件，却没有任何反例夹具证明它能把真实缺项压到 0。
- 影响：绿灯的语义强度低于它给人的印象；且无法防止未来修改把机检改弱（revision-gate gate 1/2）。
- 建议方向：加最小自测——用"故意删一条消费点/改一个章节号/写一个三级引用"的临时副本断言机检必须 FAIL；把词面命中率降级为参考指标，改以"定义→场景映射"（C4）和"每行第 5 列可反向定位"作为 pass 条件。

### D4 §5.2 对"写权记录保存什么"的列举已被 §4.4 的新定义超过

- 位置：§5.2 L272；§4.4 L236。
- 原文：L272「§4.4 的写权只保存当前会话/维护所有者及其范围、代次和恢复检查点，各自不复制任务状态/批准」；L236 已让同一文件承载「维护结果字段：操作标识、精确变更路径、操作前后状态/哈希、暂存区/HEAD 差异和结果」。
- 影响：§5.2 是"单一事实源"的定义处，读者据其列举判断 `writer.json` 允许装什么。现在列举与实际不一致，实现者会怀疑维护回执该不该放在写权记录里（合法读法指向"不该"），而这正是 §4.4 明确要求的唯一落点。
- 根因：R2（同一记录在两节各写一次形状，新增字段时只回写了定义处）。
- 建议方向：把 L272 的列举改为"所有权类事实（…）＋ §4.4 维护变更持久化的回执与待处理状态"，或直接改为一指向 §4.4 的引用而不再列举。
