# 审查方法设计

## 审查轴（四轴，轴内按章节顺序扫）

| 轴 | 回答的问题 | 主要证据 |
|---|---|---|
| A 可实现性 | 实现者能否只凭正文做出一个确定实现？哪些点必须自造规则？ | 正文条款 × §8.1 交付清单 × §8.2 场景 |
| B 一致性 | 同一门禁/字段/边界是否在多处一致；设计↔charter↔索引↔机检器是否同口径 | 交叉引用回扫、同义段对比 |
| C 覆盖性 | 门禁是否有验收行、夹具是否有可观测判定物、交付项是否都有归属 | §8.1 四项交付 × §8.2 两表 × 索引行 |
| D 机检可信度 | 机检器证明的是结构还是语义；绿灯能推出什么 | `scripts/validate-wf-design.py` 逐检查项复核 |

## 判定口径

- **可核对事实优先**：每条结论给出 `文件:行号` 与原文片段；推断标注"推断"。
- **严重度**：
  - 阻断：不裁决就无法开始/继续实现，或两种实现互斥。
  - 高：会产生产品缺陷或验收歧义，需要在机制设计前定案。
  - 中：增加返工概率或验收成本，可带条件推进。
  - 低：表述/一致性缺陷，改动小但会累积漂移。
- **不收**：纯风格、可自然补全的命名细节、"再加一层机制"式建议（charter T6 减法）。

## 根因分类（用于避免反复修复）

| 代号 | 根因 | 典型表现 |
|---|---|---|
| R1 交付下沉但清单未扩容 | 判定细节下沉到机制设计，§8.1 交付清单没同步 | 令牌、原因码、会话身份载体无归属 |
| R2 同门禁多处成文无消费登记 | 一个门禁在 2–3 节各写一段，没有像索引那样登记"消费点" | repair 令牌、挂起复评写权 |
| R3 语义覆盖靠人工回扫 | 机检只证结构/词面，694 行 141 定义规模下人工漏检 | 场景行与定义行无映射 |
| R4 两套资产边界混用 | 项目内 Git 数据 与 宿主 skill 根 两套所有权规则并用 | 安装落点、升级/卸载边界 |
| R5 验收先有名后无物 | 先写场景名，后无夹具对象与预期输出 | §8.2 三夹具不可复现 |
