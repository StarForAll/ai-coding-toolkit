## 逐项核实、根因与修订决定

| 意见 | 核实与根因 | 修订决定 |
|---|---|---|
| P2-1：升级/repair 结果没有提交或待提交规则 | 成立。§4.4 维护 writer 定义到“完成保存实际结果并释放”，§7.2 也只定义完成释放和中断恢复；§4.2 可待提交类别没有维护操作结果。根因是写入权生命周期与 Git 持久化生命周期被当成同一件事处理，且工作区边界只识别当前任务控制记录和业务 WIP。 | 在 §4.4/§5.3 复用既有维护操作标识与 writer 记录，按路径记录实际变化、前后状态摘要及是否待持久化；repair 复用同一口径。只有升级/repair 已完整应用且结果可核实时才可释放维护 writer：未获明确提交授权时记录并报告具体路径后释放；应用/验证中断且结果不完整或不明时保持待恢复，不能当作空闲。提交授权单独且精确覆盖 Git 提交及路径，apply/repair 令牌不兼作授权。§4.2 将匹配该操作记录的变更视为有归属的待持久化差异，不当成无归属改动；其他任务不得暂存/提交这些路径，触碰同一路径或实际状态与记录不符时先交人处理，复用 §5.6 的提交、已完成反向修正或具名任务承接出口；入口须将确认去向和真实路径状态写回原结果后才解除待处理。这样允许无路径交叉的普通任务继续，避免放宽整个 `.wf/`、把提交混入其他任务，或因 writer 释放而遗失维护结果。修订不建立独立账本。 |
| P2-2：一般维护要求与损坏 writer 卸载例外冲突 | 成立。§1.3 的无限定句覆盖所有人直调维护；§7.3 明确损坏 writer 时不伪造代次的独立卸载。根因是例外仅写在卸载出口，没有由写权所有者 §4.4 统一定义，调用权清单又用了绝对措辞。 | §4.4 定义常规维护与独立卸载例外的边界；§1.3 指向该定义。损坏例外只保留预览确认的独立卸载，不允许 repair/upgrade/其他写入借用，不绕开最小互斥。 |
| P2-3：收工恢复句可能废除所有旧 pass | 成立。§4.4 把路径变化与旧 pass 句子压在同一复合句中；§4.2 则规定无关路径改变不自动失效，且同路径内容有效性由统一指纹决定。根因是恢复流程重核真实 WIP 的纪律与 Check 结果效力规则没有显式分工。 | 在 §4.4 明确本节只要求核对真实 WIP/归属，pass 效力一律由 §4.2 判断；不引入“任何恢复都重跑 Check”或“无变化必然有效”的新例外。 |
| P2-4：两列场景没有全部指向三档表 | 成立。§8.2 规定二值场景在语义未决时引用独立三档表，但当前历史锚点、日常收工、Trellis 互斥、机读触碰面、审查完成、spec 准入六个场景缺对应场景名指针。根因是“见下方”只在部分行落地，且验收表作为两类输出的连接面未逐行反查。 | 给用户指出的六行补具体三档场景名引用；并将其余已有泛化指针及维护、旧写者恢复、工作流定义的直接消费点改为具名指针，使每个可进入第三档的语义场景都能从对应二值行反查，不修改允许/拒绝结论。checker 当前只覆盖表结构及完整度，本轮不改 checker，避免引入需要另行测试的脆弱场景名硬编码。 |
