# wf 设计修订方案（第四轮已实施，待人工复审）

## 第四轮：升级/repair 待持久化、维护例外、Check 有效性与验收指针

本轮由用户明确要求在原任务中审查并修订 P2-1 至 P2-4，产品边界仍为设计稿和索引。当前第三轮产品内容是审查基线；逐项证据、根因和方案取舍记录在 [revision-4-review.md](./revision-4-review.md)。

- P2-1 成立：§7.2 规定升级应用、释放及中断恢复，但没有定义操作生成的资产/记录差异如何进入 §4.2 的逐路径工作区判定；repair 同样缺结果持久化口径。根因是写入权生命周期与 Git 持久化生命周期被当成同一件事处理，且工作区边界只识别当前任务控制记录和业务 WIP。复用 §4.4 维护操作标识和 §5.3 现有 `.wf/writer.json`，保存每次维护实际改变的路径、前后状态摘要、暂存区/HEAD 差异及待提交/已处置状态；writer 自身不递归哈希。操作成功且用户未明确授权提交时，维护 writer 仍释放并逐路径报告待处理结果；中断继续处于待恢复，不提前释放为空闲。§4.2 将这些变更识别为有归属的待持久化差异，不误报成无归属差异；不同任务只能操作互不重叠的路径，不能暂存或提交这组路径。路径重叠或状态与记录不符时交人处理，并复用 §5.6 的提交、已完成反向修正或具名任务承接出口；只有入口把确认去向和真实路径状态写回原结果后才解除待处理。这样允许无路径交叉的普通任务继续，避免放宽整个 `.wf/`、把提交混入其他任务，或因 writer 释放而遗失维护结果。修订不建立独立账本，也不把升级/repair 自动变成提交授权。
- P2-2 成立：§1.3 的常规维护要求应指向 §4.4 的所有者定义；将损坏 writer 的独立卸载作为该定义明确且范围受限的例外，保留 §7.3 的最小互斥、人确认、仅退出资产范围条件，不把例外扩展到 repair、upgrade 或普通推进。
- P2-3 成立：§4.4 恢复段明确真实 WIP/归属核对与 Check pass 有效性分工；是否保留旧 pass 完全由 §4.2 唯一定义判定，未变化对象仍依原规则有效。
- P2-4 成立：用户指出的六个缺失指针已补齐；为使统一规则不产生新缺口，又把原有泛化指针和维护、旧写者恢复、工作流定义等直接对应项全部改为三档表中的具体场景名。所有可判定的第三档场景都能从相应二值场景回查。checker 现有机械责任仅检查三档表结构/完整性，本轮只修文档交叉引用，不引入脆弱的场景名硬编码校验。

本轮不改 checker、charter、运行实现、Trellis skill 或其他项目文件；不提交、不执行 finish/归档。产品条款修订完后运行设计 checker、`git diff --check`，并逐条人工回扫引用及索引语义消费；只证明文档结构/契约相容，不声称并发、repair 或升级已运行验证。完成后停在待人工复审。

## F2：定义、批准、执行与恢复

§5.7 持有动作/验证消费规则；§5.8 保留两类步骤及完整四阶段。首轮未补齐实际消费且重复来源集合，第二轮已删除重复集合并在 §5.8 明确实际核对/三档消费，再登记索引；此处不把原有方案文字当作已执行证据。

1. 动作说明：任务内有限顺序动作是供 AI 在当前批准范围和门禁内执行的工作说明；人判由人实际作答。脚本管理固定状态/游标，不把定义或输入当程序求值；未知步骤类型不解释成 shell、插件等扩展。
2. 验证引用：复用已有项目命令、当前批准 Plan 的检查、前序正常工作建立的持久声明，不新建注册库。消费前核对来源/版本、具体调用、工作目录和输入绑定。输入作为数据，不拼成可执行正文；项目已有脚本/构建命令仍按项目与任务批准使用，不全面禁止 shell 或把项目脚本误判为工作流扩展。
3. 权限与结果：定义不授予工具、提交或外发权限。调用语义、范围、验收实质变化回 §4.2；缺失、失败、未结束按原规则阻断，不自动换命令或记 pass。
4. 恢复：复用 §4.4 交接、§5.7 实例步骤及真实产物/结果。已核实完成才衔接，结果不明先核对，不盲目重放有副作用业务动作。§5.4 固定控制流幂等保证不扩张到任意业务命令。

字段、参数编码、命令格式和进程实现仍交机制设计；这里只固定允许什么、谁执行、凭什么继续、何时停止。
