## B 级发现（实现不可判定或缺漏）

### B1 `check_anchor` 的 `touch_paths_digest` 指代二义（§0.2 与 §3.2 互相冲突）

- 定位：机制稿 §0.2 行 53；§3.2 行 262。
- 证据：
  - §0.2 行 53 在 check_anchor 键集合里列出 `touch_paths_digest`，并**另行**定义 `paths_digest=H("wf-check-paths-v1", C(paths))`，两者并列 → 暗示这是两个不同的摘要。
  - §3.2 行 262 先写「保存 `paths_digest=H("wf-check-paths-v1", C(paths))`（paths 为去重排序后的触碰路径数组）与 `content_digest=…`」，紧接着写「`touch_paths_digest` 与 `content_digest` 即上述路径集合哈希与指纹哈希（`touch_paths_digest` 取等价链两端规范化后相等的路径集合哈希）」。
- 二义点：`touch_paths_digest` 到底取哪个输入？
  - 读法 A（照「即上述路径集合哈希」）：取**本次实际触碰路径集合**（§3.2 的 `paths`）。此时括号里「取等价链两端规范化后相等的路径集合哈希」不可执行——实际触碰路径不是从 PRD 派生的，不存在「两端规范化相等」的比较对象。
  - 读法 B（照括号）：取**批准/entry_snapshot 的 touch_paths glob 集合**（这才是等价链两端可比对的对象）。此时「即上述路径集合哈希」为假，且该值与 `entry_snapshot_digest`（已含 `touch_paths`）冗余。
- 影响：check_anchor 是审查报告新鲜度判据（设计稿 §6.5、机制稿 §9.1 的 `check-anchor` 字段）与规则/内容类回执 P 的输入。两种读法给出不同失效语义：读法 A 下「交付路径集合变化」使审查报告失效；读法 B 下不会（只由内容指纹与批准面决定）。实现者按任一种落地，都会在另一处判据上得出与人预期相反的新鲜度结论，且此类偏差不可事后由机检发现。
- 建议（需人裁，因改变判定语义）：在 §3.2 明确 `touch_paths_digest` 取**批准/开工快照规范化后的 touch_paths 集合**（与等价链归一自洽），并另以 `paths_digest` 表示本次实际触碰路径集合；随后统一 §0.2 行 53 的键名表述，使两处对同一字段只留一种解释。

### B2 §3.2「保存 `paths_digest`/`content_digest`」在 check 结构里没有字段落点

- 定位：机制稿 §3.2 行 262；§3.5 行 282（check 结构）；设计稿 §4.2 行 203。
- 证据：
  - §3.2 行 262：「保存 `paths_digest=…` … 与 `content_digest=…`」。
  - §3.5 行 282：check 结构为 `{id, anchor, started_at, ended_at, result, commands, acceptance_results, internal_review, tdd_evidence, invalidation}` —— **没有** `paths_digest`/`content_digest` 字段；二者只作为 `check_anchor` 的哈希输入存在。
  - 设计稿 §4.2 行 203：「由脚本写 pass/fail、逐项命令/摘要和**内容指纹**」；§6.5 门禁 2：「内容指纹与当前交付状态、验收和相关规范版本一致」。
- 影响：设计稿把「内容指纹」列为 Check 必须写入的产物；机制稿一边要求「保存」，一边没有承载字段。实现者只有两条路：私自扩 check schema（§0.2 禁止未登记字段），或只依赖 `check_anchor` 的嵌套哈希——后者无法在报告/审查/复盘中单独列出「本次检查覆盖了哪些路径、指纹是多少」，而 §11.2 `task.changes-persisted` 的 P 又直接引用 `content_digest` 与 `paths`，两者取值来源因此不唯一。
- 建议：在 §3.5 的 check 结构补 `paths_digest` 与 `content_digest`（或补一个 `objects` 子结构保存逐项指纹并按 §3.2 计算），并把 §3.2 的「保存」句改为指向该字段；若判定「只需 anchor 内嵌、不必单列」，则同步改写设计稿口径或明确「内容指纹以 check.anchor 承载」，避免两处要求不一致。

### B3 四处哈希域输入结构未逐键定义，违反本文 §1.1 自定的硬规则

- 定位：机制稿 §1.1 行 74（硬规则）；涉及 §2.3 行 222（`wf-plan-v1`）、§5.1 行 368/376（`wf-action-v1`）、§10.2 行 753（`wf-effective-rules-v1`）、§11.3 行 920（`targets_digest`）。
- 证据：
  - 行 74：「任何作为哈希输入、匹配键或清单成员的结构，必须在所属 schema 处**逐键给出名称与取值域**……散文式列举（『某某等组成某结构』）不构成定义。」
  - 行 222：`plan.version=H("wf-plan-v1", C({artifact_digests, plan_block, complexity, complexity_reasons, tdd}))`；其中 `artifact_digests` 仅说明「包含 PRD 整文件及适用的 design/implement，且不包含带有本 version 的控制记录」——未给成员键名、排序与去重；`complexity_reasons`（行 120）为「逐项保存四个分级条件的 true/false/unknown 和事实」并在降级时「追加降级条目 `{downgrade: true, reason, evidence}`」——同一数组并存两种元素形状，未逐键。
  - 行 368/376：`id=H("wf-action-v1", C({owner_ref, base_revision, kind, normalized_inputs, approval_ref}))`；`normalized_inputs` 只有散文「包括预先生成并已保存的所有新 id、路径、版本和决策」。
  - 行 753：`effective_rule_version=H("wf-effective-rules-v1", C({rules_digest, installed_assets}))`；`installed_assets` 只见「按安装登记的逻辑根标识和相对路径排序，记录每份实际投放资产的类型、执行位、存在状态及内容摘要」。
  - 行 920：`targets_digest` 是「action.targets 去除回执/写入标记**递归字段**后的规范 JSON 哈希」——「递归字段」未枚举，剔除口径随实现而变。
- 影响：这四个值都是**写入记录并长期参与后续比对**的键：`plan.version` 进入 `plan.approval`、等价链、`check_anchor`、内容类回执 P；`action.id` 是幂等键（重入必须复算同一 id，§5.1 行 368「相同请求重入复用该值」）；`effective_rule_version` 决定全部规则类回执是否失配（§10.2 行 753、§11.2 行 887）。结构由实现者自定后，任何后续重构、字段增删或排序调整都会使**旧记录不可复算**：在途 action 无法按原 id 恢复、等价链断裂导致重复人批准、规则类回执集体失效。同时 §1.1 声称机检核对「域名—逐键定义段」的对应关系，而现在这四个域名根本没有可核对象，机检只能空过。
- 建议：为四个输入补逐键定义段（例如 `artifact_digests: [{path, digest}]` 按 path 排序；`complexity_reasons: [{condition, value, fact}]` 且降级条目单列 `downgrades`；`normalized_inputs` 给出键名与规范化顺序；`installed_assets: [{root_ref, target_relative, kind, executable, exists, digest}]`；`targets_digest` 改为「剔除 `write_mark`、`action`、`revision` 三个键后」的显式枚举）。结构一旦冻结即按 §1.1 的域名管理，改动须按 §0.2 登记并重算。

### B4 治理面在机制稿没有载体、没有算法，但被三处上位判据消费

- 定位：设计稿 §3 行 135（治理面登记）、§4.2 行 205（范围闸门）、§4.3 行 213（复杂度条件①）、§6.5 门禁 1 行 491、场景行 667（复杂度分级一致性）；机制稿仅在行 958、973 提及「治理面」二字。
- 证据：
  - 设计稿行 135：「**治理面登记**：基线内受特别约束的路径，初始候选包括 spec、构建配置、对外接口、记录 schema；由人审定……」；行 205：「任务 PRD 的意图与机读触碰面、**项目基线与治理面共同限界**」；行 213：「四项任一为是即按复杂：**①触碰路径命中治理面**……反例：只改两个文件，但改动 `touch_paths` 语义或门禁判定 → 复杂」；行 491 门禁 1：「实际交付路径均匹配，**范围/治理面未越界**」。
  - 机制稿 §1.3 行 120 只要求 `complexity_reasons` 保存四个条件的 true/false/unknown 与事实；§9.3 门禁 1（行 707）只写「当前 plan.version/批准、entry_snapshot 对应的触碰面、实际路径与复杂度有效」，**无治理面判定项**；全文没有任何治理面的记录类型、字段、载体格式或匹配算法；基线在设计稿 §3 行 133 是「活动文档」，也未给机读段。
- 影响（实际开发视角最重的一条）：
  1. 条件①无判定依据 → 实现只能恒填 `unknown`，而机制稿 §1.3 规定「任一 true 或 unknown 提出 complex」→ **所有任务默认复杂**，直接抹掉设计稿 §4.3 的轻量路径与「分级按事实核对」的承诺；或恒填 false → 治理面永不触发，违反「审级宁高不低」。
  2. 门禁 1 的「治理面未越界」在 §9.3 缺项 → 归档时不会检治理面越界；设计稿「治理面变更须在当前 PRD 明确声明」（行 135）也因此没有机核落点。
  3. 若由实现者自造格式，基线（活动文档）无法稳定解析，且跨版本升级不兼容。
- 建议：指定治理面的机读载体（建议在基线内以 `<!-- wf-governance:v1 -->` + 紧邻 JSON 块登记 `paths`（复用 §3.1 安全语法）、理由与审定人/时间，与 §7.1 定义块同一做法），并同批登记写者（初始化/bootstrap 生成、后续经 `baseline.apply` 人审提案变更）、消费点（复杂度①、范围闸门、门禁 1、§3.2 检查对象用途）、失败出口（非法条目按 §3.1；缺失按 unknown→complex 并可见报告）。若确定「治理面只能由人判」，则须在 §1.3 明写①为人判并把依据写入 `complexity_reasons.fact`，并在 §9.3 门禁 1 注明该项由人判声明承载，不得留空白。

## C 级发现（可改进，不阻断实现）

### C1 §2.1 机制操作归属表缺 continue 的四类操作

- 定位：机制稿 §2.1 行 178（continue 行）；设计稿 §1.3 行 92；机制稿 §11.3 行 905–918。
- 证据：设计稿行 92 把「绑定内定位、归属裁决、建边/删边、Check/审查结论/策展记录、已绑定任务范围内的定义编辑/校验」都归 continue；机制稿 §2.1 的 continue 行只写「批准、开工、Check、暂停/恢复/收工、基线提案、边/返工/替换/放弃、实例推进/终止、审查记录」，缺 `run.locate`、`task.attribute`、`task.curate`、`definition.validate` 与「实例内暂停」；§11.3 只列操作集合，不给归属入口。
- 影响：设计稿 §8.1 明确要求机制稿交付「skill/机制操作归属」。按现文实现，`task.attribute` 这类操作会被挂到哪个入口全靠实现者推断，容易出现「归属裁决被挂到 start」这类与设计稿分工相反的接线。
- 建议：补齐 §2.1 continue 行（含只读断言 `run.locate`/`definition.validate`），或在 §11.3 每行补「归属入口」列，使归属只有一个来源。

### C2 写入标记缺「命令」位（设计稿 §5.3 三项之一）

- 定位：机制稿 §1.2 行 88（`write_mark`）；设计稿 §5.3 行 299。
- 证据：设计稿行 299：「判定字段每次变更记录**命令**、写入前 HEAD 与本次变更摘要/标识」；机制稿 `write_mark = {operation, owner, generation, before_head, changed_fields, action_id}` —— `operation` 是机制操作名，不是调用形态；`action_id` 是派生哈希，不可反读参数。
- 影响：同一 operation 的不同范围/参数（例如两次 `task.transition`、不同 `spec.update` 目标）在标记里不可区分；恢复与审计时无法回答「这条记录由哪个入口带什么参数写」。设计稿把命令与 HEAD、摘要并列为三项，机制稿只落了两项。
- 建议：`write_mark` 增 `invocation`（入口名 + 关键参数/范围摘要，可复用 `action.scope` 与 `inputs_digest`），或在 §1.2 明确「operation + action_id + changed_fields 即设计稿『命令』的等价编码」并说明为何无需原始 argv。

### C3 `.wf/out-of-scope/` 拒绝项没有字段 schema

- 定位：设计稿 §6.3 行 463；机制稿 §8.4 行 638、§10.1 行 730。
- 证据：设计稿行 463：「一概念一文件，记**原因与可重议条件**……重提先对照旧拒绝的事实差异，并**追加进旧文件的既往请求记录**」；机制稿只重复「一概念一文件，重提追加旧记录」并给落点，全文无该记录的字段定义。
- 影响：「原因持久」「可重议条件存在」「追加不新建文件」三条都无法机核，周期巡检的知识治理只能人工读自由文本；实现者各自发明格式，与 §0.2 的登记纪律相悖（有消费者、无字段）。
- 建议：给最小 schema（如 `{concept, path, reason, reconsider_when, history: [{at, request, decision, decision_ref}]}`，或 JSON 块 + frontmatter），并指定写者（spec-update / continue 的知识处置）与消费点（重提对照、巡检知识治理）。

### C4 安装/升级自检缺「运行态确实被忽略」的核验

- 定位：设计稿 §7.1 行 512；机制稿 §10.4 行 775、§10.2 行 745。
- 证据：设计稿行 512：「自检需**确认运行态确被忽略**，规则顺序被后续否定时报告具体匹配问题，**不能只检查标记存在**」；机制稿 §10.4 自检项为「资产哈希/已接受偏离、skill 路由、required 步骤与脚本接口、gitignore 托管段（标记串定位、不重复追加、段内容不符按偏离）、基础引导与坏配置下恢复」——没有「实际忽略是否生效」。
- 影响：`.gitignore` 后续规则（例如 `!.wf/`、`!/.wf-lock`）可使运行态被跟踪，而自检仍报成功；随后 §3.3 未提交路径、§4.4 工作区分类、§5.3 记录分类都会把运行态当交付/待提交，产生误报甚至误提交，恰好推翻设计稿「运行态不承载唯一事实、gitignore」的分层。
- 建议：自检增加对 §10.1 登记的每条运行态路径做实际忽略判定（`git check-ignore` 等价只读检查），被否定时报告命中的否定规则与位置并拒绝启用；同时在 §10.2 `gitignore_managed` 的消费说明里登记该项。

### C5 `content_version` 没有消费算法

- 定位：机制稿 §7.1 行 473、§1.5 行 159；§0.2 行 36。
- 证据：行 473：「`workflow_id`、`content_version`：稳定局部 id；正整数，**每次源内容改变递增**；快照哈希同时覆盖完整文件」；实例记录（行 159）只保存它，实例选择与迁移一律按快照 `digest`/哈希。全文再无 gate 或比对消费它。
