## 1. 逐条复核

### R17｜`spec-update` 的动作授权（原判 1）——成立，但「触碰面」这一条要改口径

**成立的部分（代码事实）**：`cmd_spec_update` 只做目标前缀（`.wf/spec/`）+ 真实落点校验，**没有**核任务阶段、规划批准与暂停状态；`not_started`/`plan`、`paused=true`、未批准的任务可以新增 `.wf/spec/outside-approval.md` 并返回 `WF_OK`。这与「批准范围内编辑」相反。

**需要改写的部分**：评审说「触碰面仅为 `src/**` 却写 `.wf/spec/**` 属越界」。按设计稿 §6.3，知识变更正是任务在 Execute 期学到规则后的正常写入，`spec` 路径本来就不在业务 `touch_paths` 内；如果要求每个 spec 目标都被 `touch_paths` 匹配，普通任务的知识沉淀会被整体堵死。**所以越界判定不应落在 `touch_paths`，而应落在「阶段 + 批准 + 未暂停 + 目标类别 + 真实落点」这五项**（基线入口的 `touch_paths` 规则适用于基线/配置，因为那些目标通常就在批准触碰面内；两者目标面不同，不能照搬）。

**处置（R17）**：`spec-update` 复用基线入口的前三项判定——阶段 ∈ `execute`/`check`、规划有效批准（`gates.verify_step("task.plan-approved")`）、`paused`/`suspended` 为假；保留目标类别（`.wf/spec/**`）与真实落点；改名/删除的**旧端与新端**都过同一套校验（当前已过路径校验，补上授权判定）。不引入 `touch_paths` 要求。

### R18｜核实门禁的覆盖面（原判 2）——成立

**代码事实**：`_spec_coverage` 只对「自动匹配命中且 `verified_at` 为 `null`/`extracted`」的条目要求人判：
- 已过核实周期（默认 90 天，项目可配）的日期没有参与判定；
- 显式策展但未被自动匹配命中的条目完全不进入这项检查。

**契约依据**：设计稿 §6.4「本任务命中的到期条目须核实或明确记录『依赖但未核实』及原因，交 finish 人判」「extracted 表示永久待核实」。

**处置（R18）**：
- 判定集合改为 **命中 ∪ 策展**（并集），逐条判 `verified_at`：`extracted`/空 → 未核实；日期距今超过周期 → 到期；其余通过。
- 未核实/到期项要求人判覆盖（`subject` 整词 + 绑定当前规划，沿用 R12 的匹配器），覆盖证据落到检查记录（`check.spec_review`），不静默刷新日期。
- 周期取项目配置（缺省 90 天；配置非法按缺省并记 warning）。

### R19｜同批改名的目标碰撞（原判 3）——成立，属数据覆盖

**代码事实**：`validate_changes` 逐条对**当前磁盘**校验（源存在、目标不存在），不看整批候选结果；`a→b` 与 `c→b` 两条在同一批里都通过预校验，应用时 `os.rename` 第二条覆盖第一条，最终 `b` 只剩 `c` 的内容、`a` 与 `c` 都消失。

**处置（R19）**：预校验增加整批冲突检查——
- 同一批内 `old_paths` 不得重复（同一源被两次改名/删除）；
- 同一批内 `new_paths` 不得重复（两个结果抢同一目标）；
- 任一变更的 `new_paths` 不得与另一变更的 `old_paths` 相同（链式改名按声明顺序仍不允许，避免隐式依赖）；
- 冲突 → `WF_TARGET_COLLISION`（facts 列出冲突的两条变更与路径），**零写入**。

### R20｜改名与历史引用（原判 4）——成立

**代码事实**：`_sync_curation_paths` 用 `tasks.iter_tasks` 遍历，**不过滤归档**；探针确认已归档任务的 `task.json` 被改写。

**契约依据**：设计稿 §6.3「改名同步所有当前索引与**活跃**策展引用……已归档任务的旧路径是历史证据，不强改旧档案」；机制稿 §8.4「关联任务仅合并许可的引用字段、不覆盖其已有 action，若目标有未完冲突动作则先恢复，不并行叠写」。

**处置（R20）**：
- `_sync_curation_paths` 只同步**活动**任务（`status` 非 `archived`，且 `terminal` 为空）；
- 关联任务若存在未完成动作（`actions.pending`）→ 该次改名**不写入**该任务，按机制稿 §8.4 先恢复；事实里列出被跳过的任务与原因，且该跳过着实为阻断（`WF_ACTION_INCOMPLETE`），因为跳过会留下指向旧路径的活引用。

### R21｜Check 结束前的范围重算（原判 5）——成立

**代码事实**：`run_check` 结束只比较**检查对象**指纹（`fingerprint.items`），新增的 c 类文件不在对象集合里，前后指纹不变 → 仍可 pass。

**契约依据**：机制稿 §3.5「检查结束前重算一次本核对，路径、分类、外部变更结论或治理面声明结论变化即本次检查不判 pass」。

**处置（R21）**：结束前重跑完整范围核对（分类 a–f、外部变更、治理面声明），与开始时保存的结果比对；任一项变化 → `WF_CHECK_STALE`（facts 给变化前后分类与新增路径），不判 pass。执行验证新增的范围外文件因此会被抓住。

### R22｜TDD 证据结构（原判 6）——成立

**代码事实**：`run_check` 与 `gates.task.tdd-verified` 都只判「`tdd_evidence` 非空」；`{"note": "no red/green references"}` 也能通过。

**契约依据**：机制稿 §3.5 要求 `{assertion, red_command_ref, red_reason, green_command_ref, properties}`，且「核确有针对同一行为的红/绿运行，红不是环境启动失败」。

**处置（R22）**：抽一个校验函数（Check 与门禁共用）——
- 五个字段齐全且非空；`red_command_ref`/`green_command_ref` 必须能解析到本次 `check.commands` 中的对应验证/命令记录；
- `assertion` 与 `properties` 为字符串（`properties` 需说明可红、确定性、快速、可无人执行四项之一以上）；
- 结构不符 → `WF_CHECK_FAILED`（facts 给缺项），门禁同判。

### R23｜归档提交失败后的续做（原判 7 前半）——成立

**代码事实**：`cmd_archive` 在「记录已移入归档、记录组提交失败」后重入，走 `task.status == "archived"` 分支：`archive_persisted` 为假时返回 `WF_PERSISTENCE_FAILED` + 「交人核对」，**不按已保存的 `commit_grants` 续做提交**。

**处置（R23）**：该分支内若 `archive_persisted` 为假且记录中有覆盖记录目录的 `commit` 授权 → 用 `_commit_paths` 续做记录组提交（幂等：已提交则无操作），再重算 `archive_persisted` 并按结果返回 `WF_OK`/`WF_PERSISTENCE_FAILED`；无授权时才回到「交人核对」。

### R24｜放弃时的真实处置（原判 7 后半）——成立

**代码事实**：`cmd_task_abandon` 只核 `disposition` **列出了**每个未提交路径、`pending` 为空，然后直接写 `terminal=abnormal`、移动目录、返回 `WF_OK`；既没有提交（即使有 `commit` 授权），也没有核对持久化，工作树里的改动原样留下。

**契约依据**：机制稿 §6.4「未提交改动须已授权提交或由人实际处置……不扩张为放弃后遗留无主 WIP」。

**处置（R24）**：写终态前逐条落实——
1. 有 `commit` 授权覆盖的路径 → 用 `_commit_paths` 实际提交（路径限定、幂等）；
2. 其余路径 → 必须已被人工处置（不再出现在 `scope.uncommitted_paths`）；
3. 仍有残留 → `WF_WORKSPACE_UNRESOLVED`（facts 列出残留路径与缺少的授权），**不写终态、不移动目录**；
4. 全部落实后写终态并核对记录已落盘；报告区分「退出完成」与「保留风险」。

## 3. 边界（不做）

- 不引入 spec 写入的 `touch_paths` 要求（见 R17 的口径修正）：知识面与业务触碰面不是同一授权对象。
- 不为「到期」新增配置键族：复用项目配置里的核实周期设置，缺省 90 天。
- 不让 Check 自动改写 spec 元数据（不刷新日期）：核实只能由人判或实际对照证据后更新。
- 不改归档历史：改名只同步活动引用，归档按历史路径解释。
