## 1. 逐条复核

### R7｜`baseline-apply` 的写入边界（原判 1）——成立

**代码事实**（`tasks.py::cmd_baseline_apply`）
- 只核：会话绑定、写权持有、条目形状（`path`/`content`）、`paths.normalize`、前缀 `(.wf/, spec/, docs/)`。
- **不核**：任务阶段、规划是否已批准、目标是否落入批准的 `touch_paths`。
- 前缀 `.wf/` 覆盖全部控制记录：`.wf/writer.json`、`.wf/tasks/**`、`.wf/session-bindings/**`、`.wf/install/**`、`.wf-lock` 都能作为写入目标。
- 没有真实落点核对：`paths.normalize` 只拒绝 `..` 段，不解析符号链接；父目录是指向项目外的符号链接时仍会写入。

**契约依据**：机制稿 §3.4「入口核绑定/写权/范围后以 `baseline.apply` 固定活文件的前后像和批准引用」；基线/配置提案必须带「旧指纹、目标内容及批准引用」。

**处置（R7）**：写入前增加四项必过判定，任一不过即零写入——
1. 阶段与批准：任务处于 `execute`/`check`/`finish`，且当前规划有有效批准（沿用 `gates` 的同源判定，不新增状态值）。
2. 目标类别：只允许「基线文件、项目配置、治理面所在基线」三类（按机制稿 §3.4 的定义取路径，不按前缀猜）；命中控制记录（`.wf/writer.json`/`.wf/tasks/**`/`.wf/session-bindings/**`/`.wf/install/**`/`.wf-lock`/`.wf/.runtime/**`）一律拒绝。
3. 触碰面：每个目标必须被批准 `touch_paths` 匹配（与范围闸门同一匹配函数）。
4. 真实落点：`os.path.realpath(目标)` 必须仍在 `realpath(项目根)` 之下（父目录符号链接解析后再比较），否则 `WF_PATH_INVALID`。

### R8｜`spec-update` 的目标类别（原判 1 附项）——成立

**代码事实**：`spec.validate_changes` 只做 `paths.normalize`（拒绝 `..`），**没有任何前缀或类别限制**；把 `.wf/writer.json` 作为 `add`/`update` 目标会被接受并写入。

**处置（R8）**：`spec-update` 的写入目标限定在 spec 根（`.wf/spec/**`），命中其他路径一律 `WF_SCOPE_UNRESOLVED`；同样加真实落点核对。改名/删除的源与目标都要在同一类别内。

### R9｜改名/删除的续做识别（原判 2）——成立

**代码事实**：`validate_changes` 在「识别 pending 动作」之前就按首次执行校验（改名要求源存在、目标不存在；删除要求源存在）。因此「改名成功 → 索引写入失败 → `WF_PERSISTENCE_FAILED` → 同变更集重入」会在校验阶段被判 `WF_PATH_INVALID`。

**处置（R9）**：校验接受一个「已完成步骤」视图——
- 存在同类未完成动作且变更集摘要一致时，用动作里记录的已完成步骤（而非工作树初态）判定前置：改名源已不存在但目标已存在且摘要吻合 → 视为该步已完成，跳过；删除同理。
- 前置不满足且不属于「已完成」→ 仍按原规则报错（不放松）。
- 验收：制造「改名成功、索引写失败」→ 重入后完成剩余步骤且不重复改名；变更集不同 → `WF_ACTION_INCOMPLETE` 不变。

### R10｜双轴必须实际通过（原判 3）——成立

**代码事实**：`_parse_review_notes` 只要求两轴 `conclusion` 非空；`passed = not failed_commands and not acceptance_failed and internal_review is not None and tdd_ok`——两轴填 `fail` 仍满足 `internal_review is not None`。

**契约依据**：机制稿 §3.5「internal_review 分别记录标准轴、需求轴的结论与依据；**两轴均完成才可 pass**」「计算有效性……**两轴通过**」。

**处置（R10）**：两轴 `conclusion` 必须为 `pass`；`fail` → check `fail`；`undecided`/缺失/无法解析 → 不算通过（保持未决，不自动降级）。facts 记两轴结论。

### R11｜必需 Finish 验证必须实际执行（原判 4）——成立

**代码事实**：`run_check` 对 `consume_at == "finish"` 的验证直接跳过；`archive` 只核就绪，不要求结果。规划可以让验收项由独立人判覆盖，从而出现「必需的命令从未执行、Check 仍 pass」。

**契约依据**：机制稿 §3.5 第 245 行「check：task.check 对全部批准必要验证及被验收引用的项核实际就绪，再实际执行并写 check.commands/acceptance_results。**consume_at=finish 只延后最后重核的时点，不豁免必要业务验证在 Check 中通过**；缺就绪/结果不明就不能 pass。只有与验收无关、明确非必需的声明可留 not_run 并显示原因。」

**处置（R11）**：Check 执行全部 `required=true` 与被验收引用的验证（含 `consume_at=finish`），结果写 `check.commands`；`consume_at=finish` 只在归档前做「结果仍在、锚点未变」的重核。未执行/无结果 → 不得 pass。

### R12｜人判绑定对象与规划版本（原判 5）——成立

**代码事实**：`_manual_command` 用 `verification_id in str(decision["subject"])` 子串匹配，且不核规划版本；`v1` 会接受针对 `v10`、旧规划版本的 `passed` 决定，并把当前锚点写进条目。

**处置（R12）**：改为精确匹配——
- `subject` 必须以「验证 id 整词」出现（按分隔符切分后精确相等，不做子串）；
- 决定必须覆盖当前规划版本（`Decision` 的 `object_digest` 与当前 plan 版本/Digest 一致，或显式声明 `plan_version` 且等于当前有效批准版本）；
- 失配即保持未决（`status=not_run`，facts 记匹配置信度与原因），不写锚点。

### R13｜Check 期的 spec 兜底（原判 6）——成立

**代码事实**：`spec_read_state` 只核「已在策展清单里的文件是否读过、哈希是否一致」；Check 路径没有按真实触碰路径重新匹配 spec 索引，也不处理 extracted/到期条目。

**契约依据**：设计稿 §6.2「Check：按真实触碰路径重新匹配，核对读取记录、版本、过期与缺失」；§6.5 人判覆盖未核实项。

**处置（R13）**：Check 增加两步（复用既有匹配函数，不新增机制）——
1. 用本次 Check 对象的实际触碰路径重新跑 spec 匹配；命中但不在策展清单 → 阻断（`WF_SPEC_INCOMPLETE`），出口是补策展并重读；
2. 策展条目中点「到期/extracted」且未被处置的，按「未核实项」处理：要么人判覆盖，要么阻断。已读正文不能替代处置。

### R14｜归档持久化只认任务记录（原判 7）——成立

**代码事实**：`archive_persisted` 只要下界之后有提交改动归档目录下**任意文件**即返回 `persisted=true`；探针只提交 `review/notes.md` 也被判已持久化。

**处置（R14）**：改为要求「本次归档动作对应的任务记录进入提交」——提交的变更集合必须包含 `record_rel/task.json`，且该提交中的记录终态为 `normal`、必要结构（终态、归档时间、任务 id）可解析；目录内其他文件的变化不构成证据。facts 记命中的提交与记录路径。

### R15｜锁按 §4.1 重做（原判 8）——成立，推翻上一轮结论

**代码事实**：`lock.acquire` 用 `O_CREAT`（非排他）打开，取得 flock 后若内容为空就补写标记；只有「非空且不等于标记」才拒绝。

**契约依据（机制稿 §4.1 原文）**：
- 「已存在文件**只在完整内容等于 `wf-lock-v1\n`、普通文件且真实落点属于项目根时复用**」；
- 「**首次创建以排他创建方式**打开锁文件」；
- 「并发观察到空/不完整标记者退出报告初始化未完成，**输出 `WF_CAPABILITY_UNAVAILABLE`**，facts 记锁标记不完整及路径，**不将它当空闲锁、不覆写未知内容**」；
- 「创建进程中断留下不完整标记时，**人核实后处置**同名文件；**普通入口不自动认领**」。

**结论**：我上一轮关于「空锁自愈属良性窗口」的记录**与冻结契约冲突**，必须撤回。`validation.md` §21 把锁错误映射为 `WF_ASSET_DECISION` 也不对——§4.1 指定的是 `WF_CAPABILITY_UNAVAILABLE`。

**处置（R15）**：
1. 首次创建用 `O_CREAT|O_EXCL`；`FileExistsError` 走「已存在」分支，不当作新建。
2. 已存在：必须是普通文件、真实落点属于项目根、内容完整等于标记，三条同时满足才复用；否则 `WF_CAPABILITY_UNAVAILABLE`（facts：锁标记不完整/未知、路径），**不写、不覆盖、不认领**。
3. `repair.py`/`uninstall.py` 自带 `Lock` 同步为同一语义（令牌对等检查随发行校验）。
4. 文档：`maintenance-flow.md` 撤回「空锁自愈」表述，改为「人为核实后处置同名文件、普通入口不自动认领」。
5. 验收：「空文件 → `WF_CAPABILITY_UNAVAILABLE`」「部分标记 → 同」「合法标记 → 正常」「人删除后重新创建成功」「两份自含实现行为一致」。

### R16｜运行期用例没有固化进仓库（评审附注）——成立

**事实**：`scripts/tests` 的 19 项只覆盖文档机检；本轮及前两轮的运行期用例都在 `/tmp`（`f1_init.py`、`cp1..cp5`、`r1r2`、`r35`…），随会话丢失，无法作为可复跑的回归资产。

**处置（R16）**：把运行期用例整理进仓库（`scripts/tests/wf_runtime/`），自带夹具构建脚本与「无 MCP、无网络」约束，`unittest discover` 可选择性执行（默认跳过需要写 `~/.wf` 的用例，需显式开关）；至少固化：初始化闭环、普通闭环、Check 边界（R10–R13）、归档持久化（R14）、锁（R15）、维护与卸载（R5）。

## 3. 边界（不做）

- 不新增状态值、原因码族或命令：R7–R15 全部复用既有码；锁的 `WF_CAPABILITY_UNAVAILABLE` 是机制稿 §4.1 已指定的码，不是新增。
- 不引入事务引擎：R9 只做「已完成步骤识别」，不做回滚或两阶段提交。

- 不在本轮实现文档级「自动修复」：R15 明确普通入口不自动认领，人工处置是契约的一部分。
