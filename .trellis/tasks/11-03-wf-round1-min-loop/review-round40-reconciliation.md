# 第四十轮外部评审的复核与修正（4 条处置 + 1 条状态）

- 处置编号 R76；实跑见 `validation.md` §66
- 判定：1 成立（语义反向）、2 成立、3 成立（部分闭环）、4 成立、5 是状态陈述（不改代码）

## 1. 回收候选的判定方向反了（成立，P1）

设计稿 §6.2 的口径是「**最近连续 N 个正常归档任务的完整策展清单都未引用**，且无活动任务引用」，我写成「被引用次数 ≥ N」——**把长期在用的 spec 标成可回收**，方向正好相反。

按设计稿重写：
- 只取**正常归档**（`terminal=normal`）的记录，按 `(archived_at, id)` 稳定排序，取最近 N 个作观察窗口；异常归档与未开工任务不作样本；
- 某 spec 在窗口内**全部样本都未引用**且**没有活动任务引用**才列入候选；
- 样本不足、样本缺 `curation` 字段或条目不可解析 → 记 `unknown`（不静默当零）；
- spec 存在起点按当前文件集合；改名/合并无法可靠映射时同样记 `unknown`。

## 2. 巡检周期触发的基数（成立）

原来用 `len(archived) % every`，把正常与异常归档混在一起。按机制稿 §8.4 改为**只数正常归档**（按 `archived_at, id` 累计），异常归档不计也不重置；输出里把 `normal_archived` 与 `abnormal_archived` 分开列，便于人核对。

## 3. 存活探测只到"函数存在"（成立，已补闭环）

上一轮加了 `lock.verify_holder()`，但**运行时与两个独立入口都没消费**——等于只有工具没有流程。

现在 `repair`/`uninstall` 在锁内先做存活探测：登记的持锁者仍存活即 `WF_WRITER_BUSY` 并指出 pid，"人在预览里点确认"不再能清空一个还活着的写者。实现稿正文与 §2.3.11 的表述同步（原先把同一件事写成"已实现"又列在"未实现"段落，自相矛盾）。
