## 1. 逐条复核

### R25｜归档续做的写权（原判 1）
代码事实：`cmd_archive` 的「已归档未持久化」分支位于 `ctx.require_held()` 之前，按历史 `finish_decision` 直接提交；R23 用例还先释放写权再断言成功，固化了错误前提。历史授权可以沿用，但不能替代当前写权。处置：续做前 `require_held(task=...)`，写权/代次不满足即返回对应码、不提交。

### R26｜spec 的触碰面口径（原判 2）
设计稿 §4.2 明文：`touch_paths` 覆盖业务、文档、spec、基线与配置；固定职责豁免只限任务自身规划/控制记录/审查报告/运行态，以及改名同步、依赖解除这类窄写入。我上一轮按「知识面与业务触碰面不同」放过 spec 目标，**属于对契约的误读**；而且代码自相矛盾（入口允许写、Check 判 c 类未处置）。处置：spec 目标必须被批准 `touch_paths` 匹配；实现稿同步改写。若日后确实要改授权模型，须正式裁决并同步上位契约，而不是在实现层豁免。

### R27｜TDD 的红/绿（原判 3）
`tdd_evidence_problem` 只核引用可解析，红绿可指向同一条通过命令。处置：绿引用须对应本次 `check.commands` 中实际通过的命令；红引用须对应历史检查（`check_history` 或即将被替换的当前检查）中实际失败的命令；两者不得相同。历史红运行与当前最终结果分开保留。

### R28｜核实配置与证据（原判 4）
`load_project_config` 返回 `(config, problems)`，被当成字典调用后异常被静默吞掉并回退 90 天；`check.spec_review` 从未写入。处置：正确解包（problems 记入 coverage）；未来日期记 `future-date`；成功 Check 保存 `spec_review`（matched/curated/needs/period/evidence）。

### R29｜放弃的持久化（原判 5）
上一轮只修好了业务 WIP 处置，异常归档本身仍未提交记录。处置：移入归档后提交记录组并用 `git ls-files` + 目录无未提交差异核对；失败报 `WF_PERSISTENCE_FAILED` 停在待持久化。

### R30｜冲突判定的时机（原判 6）
`_sync_curation_paths` 在判断任务是否真正引用旧路径之前就拒绝其 pending 动作，且发生在文件已改名之后。处置：把冲突判定前移到 `validate_changes`，只对**真正引用这些路径**的活动任务阻断；无关任务不阻断；本次任务自身的在途动作不算冲突（实现中新发现，见 `validation.md` §26.4 N-R15）。

## 2. 边界

- 不为「未来日期」新增状态值：复用 `needs` 的 reason 文本。
- 不让 Check 自动刷新核实日期。
- 不改归档历史与历史授权语义，只补当前写权与持久化核对。
