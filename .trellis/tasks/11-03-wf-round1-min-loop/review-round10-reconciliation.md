## 1. 逐条复核

### R43｜新增命中规则未进入有效性（原判 1）——成立
`check.spec_versions()` 只遍历本任务策展清单；`gates` 的 Check 有效性只比重算后的 `check_anchor`。探针：Check 通过后由另一提交新增匹配 `src/**` 的 active spec，交付内容未变 → 锚点不变 → 门禁仍判满足。

**处置**：`spec_versions` 改为「策展 ∪ 本次交付路径实际命中的 spec」（复用 `spec.match`），命中集合变化即改变 `check_anchor`，门禁按 `WF_CHECK_STALE` 要求重检；符合机制稿 §3.5「spec_versions 为当前命中/策展 spec 的 {path,digest} 排序集合」。

### R44｜glob 重叠导致错误认领（原判 2）——成立
`wip_blockers` 对每个活动任务独立分类未提交路径；两个任务批准 glob 都覆盖同一路径时，同一文件会被同时记到两者名下。探针：A 已用 `stop keep` 明确保存 `src/a.py` 的归属，B（触碰面同为 `src/**`、无自身 WIP）仍被列为阻塞者。

**处置**：先建立「显式归属表」（各任务 `handoff.wip.paths` 的 path → task id），计算某任务的未登记脏改动时**排除已被其他任务显式记录的路径**；显式归属优先于 glob 匹配。无显式归属且被多个任务覆盖时仍按现状列出（facts 标明来源），由人裁决——脚本不擅自认领。

### R45｜已持久化的删除被误拒（原判 3）——成立
`task-resume` 在指纹比较之外还有一条「路径仍在差异中或仍存在」的判断：删除在未提交时能恢复，提交删除后该路径既不在差异也不存在 → 被当作「去向不明」拒绝。

**处置**：把「记录即删除」（保存指纹 `exists: false`）单独识别——当前仍不存在且已不在差异中即视为「合法删除、已持久化」，放行并在 `handoff.wip.resolved` 写回 `{choice: resume-after-disposal, evidence: {deleted: [...]}}`；只有「记录为存在、现在既无差异也不存在」才继续按去向不明拒绝。

## 3. 边界

- 不改锚点算法本身，只改 `spec_versions` 的输入集合（机制稿已定义该集合为「命中/策展」）。
- 不新增字段：归属表由既有 `handoff.wip.paths` 推导，facts 只做标注。
- 不对删除做自动认领或回滚：只识别「记录与现状一致且已持久化」。

## 4. 对收口状态的影响

三条都属「判据输入不完整」：R43 让规则集合真正进入有效性，R44 让归属优先于 glob 重叠，R45 修正删除场景的误判。落地后需重跑：Check 相关（CP1/CP3/CP5、R10–R13、R21、R34）、WIP 相关（R37–R42）、恢复相关（CP1、R24、R29、R37、R45）与三夹具全流程、F0。
