# `task-rework` 权威冲突（待裁）

## 一、冲突的两方

**甲方：v42 §4「必须删除的旧机制」**（`analysis/solution-review-v42.md`）
把 `task-rework` 列为要删的旧机制，理由是 v42 认为返工语义由 **K2 租约 + 收敛谓词** 覆盖：
任务失败后不再需要"建 R 挂起 T"这套编排，重启由写权接管与重新进入表达。

**乙方：机制稿 §6.2 + `payload/workflows/instance-flow.md`**
把 `control.task.rework` 声明为 `[required · repeatable]` 的两轮交付步骤，正文四行：

```
### control.task.rework [required · repeatable]
- 时点：返工动作结束
- enforcement: wflib/cli.py::task-rework（第二轮）
- 动作：建 R、继承原前置、给 T 挂起，并按实例/普通任务分别处置定位与写权。
- 出口：候选图不合法 → WF_DEPENDENCY_UNMET；T 挂起未完成 → 阻止 R 提前执行。
```

此外设计稿 §5.6（异常归档/返工）与 charter T4 的"最小完整闭环"也提及返工路径。

## 二、为什么不能单方面选一边

| 动作 | 后果 |
|---|---|
| **删命令 + 删步骤**（按 v42 彻底删） | 部署自检通过，但**拿掉设计稿 §5.6 承诺的返工能力**：机制稿 §6.2 的步骤没了，第二轮"返工"交付项消失。属删承诺，需按设计稿 §1.5 交人裁。 |
| **只删命令**（我第一版干的事） | **部署直接报废**：自检报 `handler entry missing: task-rework / required_step: control.task.rework` → `WF_CAPABILITY_UNAVAILABLE`，writer 停在维护持有，之后所有命令 `WF_WRITER_BUSY`。演练实测。 |
| **保留命令桩**（当前状态） | 部署正常，`task-rework` 调用返回"第二轮未交付"的能力不可用码。代价：v42 §4 那条"删除"没兑现，属**已登记偏差**。 |

## 三、需要你裁的三选一

### 选项 A：保留（当前）
- 改动：无（桩已在，注释里写明冲突）。
- 语义：返工仍是机制稿 §6.2 的承诺，等第二轮真正实现。
- 代价：v42 §4 的删除条目记为**有意例外**（我会写进 P4 偏差表）。

### 选项 B：删命令 + 删步骤（彻底执行 v42）
- 改动：删 `cli.COMMANDS["task-rework"]`、`gates.py` 的三处登记（REQUIRED 列表、STEP_CODES、ROUND）、
  `workflows/instance-flow.md` 的整节；同时要处理设计稿 §5.6 与 charter T4 的相关表述。
- 前提：确认"返工"能力由 K2 租约 + 收敛谓词**完全覆盖**（我需要你确认这条判断，否则就是拿掉能力）。
- 代价：跨三份上位文档的删除，属于 **charter T4/T6 级别**的变更。

### 选项 C：保留命令、把步骤降级
- 改动：把 `control.task.rework` 从 `[required]` 降为"可选/后续交付"，`ROUND` 保持 2。
- 效果：自检仍要求 handler 存在（桩在），但不把它当强制交付项。
- 代价：机制稿要加一句"该步骤可延后"，仍是机制稿语义变更。
