## 1. 我上一轮为什么判 0（自证闭环）

首轮三个审查面 + 补做面 D 全部报「0 主发现」，但我复核后发现三处共同盲区，导致三条真实缺陷被排除：

### 1.1 只按「机制会拦的路径」推演，创建期写入是盲区

- §7.5 的边校验入口只列「建边 / 返工加边 / 替换·放弃的重连」（`:609`）；**任务创建时写 deps 不在其中**。
- 后果：规则文本写错也不会被任何机制链路抓到——创建期写进去就生效，而设计稿又依赖创建期承载「继承」语义。
- 我在 F1 的排除理由里写「诚实使用下不可达 / 防御态」，正是把「机制不会拦」当成了「不会发生」。

### 1.2 收尾角色没有任何验收位

- A1（`:78`）只写 P 的继任路径；B9（`:97`）不含收尾；§10 自检（`:891`）只有「建收尾」与「替换收尾」，**没有「放弃收尾 + 重定义」**。
- `.trellis/spec/docs/index.md` 的注册表与全部探针中，「收尾」出现 **0 次**（实测 `rg -c` = 0）。
- 因此 F1 的第二面（收尾放弃后重定义无合法前置来源）落在所有扫法的空隙里。

### 1.3 把「断言被核对过」当成「断言为真」

- 口径 10⑤ 要求「封闭断言逐条列出覆盖的全部产生路径并核对」。我在核对时用的路径族是「建图 / 继承 / R 加边 / 重连 / 迭代建边 / 删边 / 类型 4 修复分域」，**没有「任务定义（建任务时写 deps）」这一族**。
- 于是「这条断言我核对过」被混同为「这条断言为真」，F1 恰是漏掉那一族的产物。
- 这符合用户指出的「自证闭环」：v45 拿自己的审计「0 缺陷」当通过依据，而我的首轮也拿自己的六项扫法「已跑」当覆盖依据。

## 2. 对 F1/F2/F3 的独立复核结论

我未采信转述，逐条回到当前磁盘文本核对。

### 2.1 F1 成立（严重度：中偏低）

**事实 A — 两份清单成员集不一致（硬矛盾，非措辞）**

| 位置 | 已归档任务作为前置的合法来源 |
|---|---|
| §4.4 `:308` | 0→1 建图、**返工**、**替换与放弃-新建替代**、**类型 1 补建的继承**、活动期建边后随任务归档（**5 个成员**） |
| §7.5 `:602` | 0→1 建图、返工与替换继承、活动期建边后该前置归档（**3 个成员**） |
| §0 `:45` 事实边界 | 同 §7.5（3 个成员） |
| 配套 `:28` / `:216` | 同 §7.5（3 个成员） |

§7.5 那句是**机制校验句**（`:609` 的边变更统一校验以此为前置条件），照它字面判，「放弃-新建替代」与「类型 1 补建」产生的已归档前置边不合法；而 §4.4 与 §6.5/§6.6 明确要求产生这类边。**§4.4 与 §7.5 对同一条边给出相反判定**，命中 §0.1 允许的第一类来源（内部矛盾）。

我上一轮把它判为「措辞/不可达」是错的：这不是留白，是两份规范对同一对象给出不同成员集。

**事实 B — 收尾任务放弃后重定义，无任何清单成员可用**

- §6.7 `:528` 明写收尾「依赖最后一个实现任务」，`:533` 明写「收尾任务自身被替换或放弃时，由人重新定义收尾任务」。
- 放弃的**删边变体**（`:514`）会把最后一个实现任务留在归档区（旧任务异常归档），不作重连。
- 此时新收尾任务的前置是**已归档任务**，而它的产生方式是「任务定义（人重新定义收尾）」——既不在 §4.4 的 5 个成员里，也不在 §7.5 的 3 个成员里。
- 想走建边又必然撞 `:602`「两端都必须在活动区」+ `:603`「前置必须尚未完工」。
- **这是可达的诚实使用场景**（用户现场已构造），且没有合法来源 → 命中第二类来源（跑不通）+ 第四类（与真实场景不符）。

我上一轮认为「不会必然跑不通，因为创建期写 deps 不校验」，这个观察本身正确，但**用错了方向**：它说明真实系统靠「创建期不校验」侥幸成立，反而坐实了规则文本是错的，而且使缺陷更隐蔽。用户对此的定性（内部矛盾 + 与真实场景不符，严重度中偏低）我采纳。

**结论**：F1 成立。最小修复方向（采纳用户方案）：把来源清单定为**唯一源**并补齐成员，让「任务定义」作为独立产生族受控纳入，§7.5 只作引用。

### 2.2 F2 成立（严重度：中；入口缺一格）

- §3 `:195` 的指针无效清单 = {指向已归档、规划中且前置未满足、未归档且账本异常、正常但未归档}，**不含「进行中且前置未满足」** → 指针不释放。
- §9.1 两表当前任务行（`:792`、`:804`）是命令式「继续当前任务……进行中且前置不全正常时工作不停、收尾等前置」，`§9.1` 开头明写「逐段判定，命中即停止」。
- §7.6 `:617` 选择只在**没有当前任务**时进行。
- 于是「给进行中任务追加前置后，下一步该去跑那个前置」在路由表里**没有一格**：当前任务行只说「继续 + 等前置」，选择规则又不启动。
- `:607` 给的出口是「人按删边或替换 / 放弃处置」——这不是「去执行前置」，而是撤销顺序约束。

**反驳尝试**（我按作者立场构造，未撤销）：「指针只是提示，以 DAG 与账本为准」（§3）+ 建边由人发起，人在场能自己开工前置。这使它不是硬死锁，但 B1（`:89`）要求「AI 仅凭设计稿与基底机制就能执行」，而路由行是命令式且「命中即停止」，AI 单跑会停在「报等待」。用户现场（113 进行中等 115，115 从未执行，报告判「卡点：无」）正好演示了这一点。

**结论**：F2 成立（跑不通 / 入口缺一格）。修复是给两表当前任务行补一格路由，而不是新增机制。

### 2.3 F3 成立（严重度：低，防御型缺口）

- §7.8 `:680` 写入前校验的唯一源枚举只列「替换 / 放弃-新建替代 / 类型 1 P 预写指向，及据指向建任务前」，**没有返工登记准备**（R 的预生成标识，见 §6.4 `:423`「预生成 R 的依赖标识」）。
- §6.4 `:424` 只校验**稳定定位**占用（「位置占用…停止」），**不校验依赖标识**是否被占用。
- §7.8 矩阵（`:686`–`:700`）是「写入路径 / 写入时点 / 指向终值 / 说明·原因终值 / 依据」五列，**没有「依赖标识」行**；类型 4 恢复边界（`:704`）也只谈指向 / 返工来源 / 说明，冲突后**没有改回标识的路**。
- 触发链：标识重生成 bug（用户现场 B15 已发生过同类簿记错误 d33e103）→ 返工预写撞号无关卡拦截 → 发布把重号写进任务记录 → 解析歧义且类型 4 改不动。

**反驳尝试**（成立，故只降严重度不撤销）：雪花 ID 全局唯一、撞号概率极低；影子副本随标记入库后预写扫描能看见。所以是**防御型缺口**，不构成日常阻塞。但它正是 §0.1 口径 10⑥ 的目标形态（识别字段 × 角色 × 修复入口），且「依赖标识」是识别条件依赖的字段却不在矩阵里，与 §10 `:880` 类迁移义务的字面要求不一致。

**并入的副本陈旧**：配套 §6.4 `:163`、§6.5 `:193` 的发起静态校验清单未同步 v44 增补的占用校验（即我上轮的 W-1），实现者照配套写会漏。这条不是独立发现，是 F3 的镜像面。

**结论**：F3 成立（内部矛盾 / 防御缺口，低概率）。

## 3. 根因（为什么这三条穿过整套验收面）

按用户修正版根因，我核对后确认其成立，并补一条我上一轮没写的机制：

1. **校验只挂在机制入口，创建期写入在整个设计里没有任何校验。** §7.5 的边校验只列建边 / 返工加边 / 重连，任务创建时写 deps 不在其中。后果是规则写错不会被真实链路抓到（S5、S11 都是「写进去就过」，167 那条与 §7.5 直接相反的边照样跑通）。**这是缺陷的生存位置**——修一处、留一类。
2. **收尾是唯一没有任何验收位的角色。** A1 只写 P、B9 不含收尾、§10 自检只建与替换收尾、spec 注册表与 38 条探针中「收尾」0 次。F1 的第二面正落在这里，且它是唯一连「替换 / 新建替代」后门都没有的路径。
3. **「能跑通的路径」被当成「规则成立」。** 两批 15 组场景全绿、封闭断言逐条标「已核对」，但路径族里没有「任务定义」这一族，所以「核对过」≠「为真」。
4. **枚举按来源写而不是按规则写。** 同一清单有 4 份副本、3 种成员集（§0 3 个 / §4.4 5 个 / §7.5 3 个 / 配套无成员），每次只补被点到的那一处。
5. **类迁移义务只在被点到的那一格执行。** v40 把 §7.4 换成字段谓词，同类的边与创建一条没迁移；v41–v45 只查识别字段，没查「来源清单」这类同类载体。

**一句话根因**：缺陷的生存位置是「整个创建期不校验」，所以修一处留一类；而链路测试与六项扫法只照机制会拦的地方，照不到写进去就过的地方。
