## A. 核心发现

### R1【实现单元映射缺口 · 优先】§8.1 机制设计清单缺 repair 交付单元

**证据**。§5.5 定义了完整的受控修复契约（repair 是人直调入口、预览-确认-验证-留痕四段、不可解析记录处置、秘密去除义务），§5.4 启动校验发现非法组合时"其余给具体 repair 出口"（L256）、周期巡检"发现问题交 repair"（L262）、§5.5 修复后全图验证。但 §8.1 机制设计条目（L428）列举为：任务 schema、批准触碰面与写者、路径集合与内容指纹、依赖动作/幂等恢复、记录兼容、项目配置、本地 spec 变更与持久引用统计、最终门禁——**无 repair**。§8.1 实现方案条目（L429）列举 skill/原语、自包含脚本、资产/项目数据布局、不可变发行清单、安装/升级/卸载与来源记录——也无 repair。§8.1 第 3 条审查适配亦不含。索引第 58 条（repair 契约）的语义消费点列 §1.3/§1.5/§5.1/§5.4/§5.5/§5.6/§7.2/§7.3，**不含 §8**。

**影响**。§1.3 把 repair 列为机制入口之一且属人直调破坏性入口（须交互终端确认与令牌）；按 §8.1"每项门禁至少一条应拒绝/应放行场景"的验收精神，无交付单元意味着：实现者按 §8 清单交付后，repair 将处于"契约存在但无验收对象"状态——恰是 §8.3 候选机制被有意推迟时的形态，而 repair 不在 §8.3 候选清单里，它是正文已承诺的机制。

**建议**。§8.1 机制设计条目补"受控修复（repair：预览-确认-验证-留痕、不可解析记录处置）"；索引第 58 条语义消费点补 §8.1。这是映射补全，不是新机制。

### R2【实现单元映射缺口】§6.2 spec 加载机制族在 §8.1 机制设计清单中无对应条目

**证据**。§6.2 定义了四个机制：三时点加载表、**读取留痕**（运行态侧车，字段含路径/内容哈希/时间，"当前哈希与所读不符或没有读取记录须先重读"）、**匹配排序**（字面段数/通配符数量/长度/路径 tie-break 的确定排序）、**预算降级**（码点软预算、逐级退避、被截断对象可见）。§8.1 机制设计条目只有"本地 spec 变更与持久引用统计"（L428），它覆盖 §6.3/§6.4（变更流程与回收统计），不覆盖 §6.2 的加载侧。索引第 71-73 条（读取留痕/匹配排序/预算降级）的语义消费点均不含 §8。

**影响**。读取留痕是 Check 门禁第 4 项（"命中 spec 已读当前内容"）的判据输入；匹配排序是"同路径多规则命中时谁先生效"的确定性来源；预算降级承载 §1.5 降级可见性的典型对象。三者无一进入交付清单，则"先交付一个能走通的真实任务闭环"（§8.1 step 2）中的"走通"不含 spec 加载判定的机械部分，Check 兜底（"核对读取记录"）无可验收对象。

**建议**。§8.1 机制设计条目补"spec 三时点加载、读取留痕侧车、匹配排序与预算降级"；索引第 71/72/73 条语义消费点补 §8.1。

### R3【三夹具验收规划缺口】场景表行未绑定夹具，夹具特有正反例缺失

**证据**。§8.2（L437-445）声明"三个隔离夹具：全新项目、存量无流程、存量有其他流程"，但场景表的 14 行是**按机制维度**组织（规划授权/机读触碰面/共存与重装/……），没有任何一行标注"仅在哪个夹具中验证"。而正文中有相当一部分机制只在特定夹具形态下才会走到：

- 全新项目夹具特有：§7.1 Git 就绪（git init、首个 HEAD、README 不卷入、无提交许可时"只落盘并报告待就绪"）、初始化任务自举（豁免基线前置）、`.gitignore` 托管段的**首次**追加；
- 存量无流程夹具特有：bootstrap 清点、`verified_at: extracted` 全流程（依赖时按未核实处置、核实后转日期）、"没有现成命令的项标缺失并给核验出口"；
- 存量有流程夹具特有：共存正例（其他框架提交被外部变更处置消化、不追认成 wf 任务）、不写 AGENTS.md 托管块、D-1 不读其他流程规范。

这些正例中，**初始化自举与 extracted 依赖处置没有任何对应场景行**（场景表"spec 正向积累"行只覆盖准入门槛，不覆盖 extracted→日期的转换链）；"共存与重装"行覆盖了共存的部分反例，但未覆盖"其他流程的提交经外部变更处置核对后无交集不阻断"这一正例。r4 报告 §5 曾要求"尤其要有合法共存能继续的用例"，现行场景表只补了反例方向。

**影响**。三夹具声明与场景表之间缺少映射层：实现者可以从场景表拿不到"每个夹具各自必须额外跑什么"，验收执行时三个夹具容易退化为同一套场景跑三遍。

**建议**（低成本，映射补全而非重写）：
1. §8.2 场景表增两行——初始化自举（应允许：初始化任务在无基线/配置下开工产出全套骨架；应拒绝：跳过人批准或 Git 未就绪开工业务）；extracted 生命周期（应允许：extracted 条目人核实后转日期；应拒绝：未实际对照证据就刷新日期——§6.4 已有此语义但未入场景表）。
2. 在场景表后补一句夹具绑定说明：列出上表各行中"仅在某夹具才有真实路径"的行（Git 就绪/共存/自举/extracted/无 MCP），其余行三夹具均适用。不新造表格。

### R4【三夹具验收规划缺口】repair 与升级/发行类场景缺少"三夹具 × 二态"覆盖的说明

**证据**。§8.2 场景表"升级三方判断"与"发行身份"两行不区分夹具，但全新项目夹具里"升级"是从安装版本起步、存量夹具里升级可能遭遇历史遗留偏离（如旧发行模板从未见过）；"数据与恢复"行有"缓存丢失重读、动作中断幂等、保留数据卸载"，但 repair 类非法组合（多执行候选、空返工集合挂起、归档残留未决挂起，§5.4 L256 已定义）在场景表中无对应行——只有"返工接续"行覆盖了其中两个反例。

**影响**。与 R1 同源：repair 契约存在但验收规划不含其对象；实现后无法按 §8.2 声称"repair 已验收"。

**建议**。§8.2 场景表增一行"受控修复"：应允许——repair 修复合法结构错误后全图可用且留痕；应拒绝——repair 替代日常操作（如借 repair 修内容性变更）。索引第 58 条同步。

### R5【机制表述含混 · 低优先】§5.4 启动校验"归档终态"与 §5.3 归档分层"仅被引用时解析"的范围界定不清

**证据**。§5.4 启动校验（L254）要求核对"归档终态"；§5.3 归档分层（L250）规定"活动区常规校验，归档记录**仅被引用时解析**；周期巡检补全长期检查"。两处对归档区的扫描范围口径不同：启动校验若全量解析归档区，与"仅被引用时解析"矛盾；若只解析被引用者，"归档终态"的核对范围是哪些（被未归档任务前置引用的？被策展引用的？）未定义。长期使用下归档区会持续增长（每月一目录），全量解析成本随年限线性上涨——这不是吹毛求疵：单工作线（§3）意味着启动频繁而归档量大。

**建议**。在 §5.4 启动校验中明确"归档终态核验范围 = 被活动区任务前置/返工引用的归档成员 + 周期巡检增量"；与 §5.3 的"仅被引用时解析"对齐为同一谓词。一句话修正，机制设计阶段落地。

### R6【机制缺漏 · 低优先】阻断协议无"需人批准"中间档

**证据**。§1.5 阻断协议（L91）输出三要素（原因码、决定性事实、下一步出口），§4.2 范围闸门"发现需要范围外路径……阻断继续执行，回 Plan 扩范围**或确认必要变更**"——后者语义上是"需人批准后放行"，但阻断协议的输出形态只有阻断；touch_paths glob 对"语义是否在范围内"（如宽 glob 命中但产品语义越界，L174 自己承认"不能以命中宽目录证明语义合规"）没有中间输出档位。来源：STS `decision.cjs` 的四级结果（allow/deny/**report_and_defer**/**require_user_approval**），其 MUTABILITY_UNPROVEN 等分支正是"机器不能定夺时交人"。

**影响**。现设计下"需人确认"的操作形态被塞进"阻断+出口=人调用某入口"的组合里，能走通；缺的是**输出的显式档位**——AI 在"glob 命中但语义存疑"时应输出"需人裁决"而非二选一地要么放行要么阻断。这与 §6.2 匹配排序"语义冲突须人裁决"（L310）已有立场同构，只是未延伸到门禁输出。

**建议**。机制设计期把门禁输出枚举定为三档：通过 / 阻断（带三要素）/ 需人裁决（带待决事实与出口）。正文只需在 §1.5 阻断协议补一句，属低成本。不吸收 STS 的 reasonCode 全家桶（ST2 仅作机制设计期参考，fixed 优先级排序对多失败并列的可测试性有益，但可留给实现）。

## C. 与四条初衷的偏离校验

4. **单任务流程执行可控**：T1/R6/ST5/S3/S4/S5 强化可控性；未增加实时拦截或常驻机制。

无一条建议要求 hook、子代理派发、外部 MCP、平台分支或并发检测——与 §2.2 明确不做清单一致。
