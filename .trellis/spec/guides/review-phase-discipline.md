# Review-Phase Discipline（方案审查阶段的纪律）

> 相关：[`main-agent-initiative.md`](./main-agent-initiative.md)（谁掌握闭环与节奏）、[`proposal-self-review.md`](./proposal-self-review.md)（方案自查十条）。
>
> 来源：2026-11-11 的 wf ⑥「修复中」方案审查。审查期间我做了两类越界动作：
> **改实现代码**（13 个提交，事后整批回退 `e49da16`）、**跑实现级验证**（单元测试、
> 全量 repro、release 重建）。两次都是"我判断这在帮你"，实际都在破坏审查阶段的意义。
> 以下规则用这次代价写成，必须机械执行。

---

## 0. 先判阶段：这句话属于哪个阶段

任何动作前先回答一个问题：**现在处于"方案审查阶段"还是"实施阶段"？**

| 阶段 | 进入条件 | 允许改什么 | 允许跑什么 |
|---|---|---|---|
| **方案审查** | 默认状态；只要用户没明确说"审查通过 / 开始实施 / 按方案改代码" | **只有 `docs/**`**（方案、裁定、机制稿、spec） | **只读检索 + 纯文档校验**（见 §3） |
| **实施** | 用户**明确**说"审查通过 / 开始实施" | 实现路径（`payload/`、`release/`、`scripts/`、`scripts/tests/`） | 单测、repro、release 构建、gate |

**判定规则**：用户说"继续修方案 / 再审一轮 / 把这条改掉（指方案文本）"→ **仍是审查阶段**。
"修"这个词在审查阶段的宾语**只能是文档**，不能是实现。

---

## 1. 审查阶段禁改实现（含"我只是顺手修个 bug"）

**禁止**修改：`docs/workflows/*/payload/**`、`docs/workflows/*-release/**`、
`scripts/**`（含 `scripts/tests/**`）、任何 `*.py` / `*.sh` / JSON 配置。

**为什么**：

- 实现先于批准落地，会让"这次审查到底批了什么"说不清；评审下一轮会把已改的实现当基线，
  于是审查对象漂移；
- 门禁/查询行为变化一旦落地，就无法用"回退"恢复"审查前的事实"，只能靠 git 历史回溯；
- 我在提案里写下过这条禁忌（门禁改动先于提案批准落地 = H1），却自己去犯——**规则不写成文件就会被再犯**。

**评审报出产品级缺陷时的正确动作**：把它**登记进方案**，三件套齐全即可——

1. 证据位置（文件 + 行为，含可复算的复现路径）；
2. 若要修，修法（机制侧一句话）；
3. 验收断言（能被后续实现验证）。

然后继续审查。**不要动代码，也不要"先修好再汇报"。**

---

## 2. 审查阶段禁跑实现级验证（含"我只想确认一下"）

**禁止**：`run_all.sh`、任何 `scripts/tests/**`、`python -m unittest`、
`build-wf-release.py`（含 `--version` 重建）、任何会写文件或耗时的校验。

**为什么**：这类动作既慢（repro 全量分钟级），又等于**用执行给实现做背书**——
审查阶段的成果是"方案可被批准"，不是"实现现在能过"。

**典型越界（真实发生）**：回退实现后启动 `run_all.sh` 想"确认回退没问题"。
**回退的正确判据不是"测试绿"，而是 `git diff <baseline> -- <paths>` 为空**（见 §4）。

---

## 3. 审查阶段允许的动作（白名单）

| 允许 | 说明 |
|---|---|
| 读文件、`grep`/`glob` 检索 | 取证、核对事实、定位行号 |
| `git status` / `git diff` / `git log` / `git show` | 只读历史与差异（**不含** `git add` 实现路径） |
| `git checkout <baseline> -- <paths>` | **仅用于回退**，见 §4 |
| `scripts/check-doc-refs.py`、`scripts/validate-wf-design.py` | 纯文档校验，只读、秒级 |
| 写 `docs/**`（方案 / 裁定 / spec） | 审查阶段的唯一产出 |

白名单之外的一切，**默认禁止**；需要时先问用户。

---

## 4. 回退实现的正确做法

1. 找回基线：`8da2f23` 这类"审查开始前一刻"的提交（用 `git log` 定位）；
2. `git checkout <baseline> -- <实现路径>`（只列实现路径，**不要**把 `docs/**` 带进去）；
3. **唯一判据**：`git diff <baseline> -- <实现路径>` **为空**；
4. 提交信息写清"回退至 `<baseline>`"与回退行数；
5. **不跑测试**（§2）。需要跑的时候，是实施阶段，且由用户批准。

**注意**：回退后文档里所有"已实现 / 已落地 / commit X"的表述都要同批清理，改成
"本提案要求（未实现）"，否则文档会声称一个不存在的实现。

---

## 5. 违反后的处置（不要遮掩）

1. 立刻回退实现改动（§4）；
2. 在回复里**主动列出**越界清单（提交号 + 文件 + 行数），不淡化、不夹带在别的话题里；
3. 清理文档中的实现声明；
4. 把这次的教训落成规则（本节就是产物）；
5. **不重复索取同一授权**：用户说过"审查阶段不动实现"，后续每一轮都适用，不必每轮再问，
   也不得因为"这次缺陷更严重"就自行升级授权。

---

## 6. 反模式清单（自查用）

- [ ] "评审发现了真实缺陷，我先修了再说" → 越界（§1）
- [ ] "我只跑一个套件确认没坏" → 越界（§2）
- [ ] "重建 release 让 `--verify` 过" → 越界（§2）
- [ ] "回退后跑全量确认绿" → 越界（§2），正确判据是 diff 为空（§4）
- [ ] "方案里的『已完成』行先写着，反正后面会实现" → 文档必须如实（§4 末段）
- [ ] "用户没说审查通过，但也没说不许改" → **默认禁止**，不是默认允许（§0）

**核心原则**：审查阶段只产出文字；文字要如实反映实现状态；任何执行都是成本，都要有明确授权。
