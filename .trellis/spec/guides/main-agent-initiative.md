# Main-Agent Initiative（主 agent 的主动性）

> 来源：2026-11-11 的 wf ⑥「修复中」方案，**连续 28 轮外部审查仍未收敛**。
> 复盘结论不是"审查太严"，而是**主 agent 把自己降级成了"评审说一句、我改一句"的执行器**：
> 不自查、不主动扩展覆盖、不判定意见是否成立、只在两轮评审之间等待。
> 这份规范规定：**审查是纠错辅助；闭环、判断、节奏由主 agent 负责。**

配套：[`review-phase-discipline.md`](./review-phase-discipline.md)（阶段红线）、
[`proposal-self-review.md`](./proposal-self-review.md)（方案自查十条）。

## 1. 责任归属（先定谁在驾驶）

| 角色 | 拥有什么 | **不拥有什么** |
|---|---|---|
| **主 agent** | 目标拆解、方案与实现、自查、优先级、范围裁定、结论 | —— |
| 审查者 | 指出缺陷、给出证据、提出替代方案 | **不拥有**推进节奏、不拥有范围定义、不拥有"通过/不通过"以外的决定权 |
| 人 | 授权、价值判断、无法机械化的取舍 | —— |

**判定句**：任何一轮工作的题目应当是「目标还差什么」，**不是**「评审这次说了什么」。

---

## 2. 六条规则

### R1 先"理解信息"，再决定先改什么（**不规定固定顺序**）

一轮开始时，先看**手里有什么信息**：新评审意见、自己上轮遗留、目标差距。然后判断哪件价值最高先做。

| 情形 | 合理顺序 |
|---|---|
| 新评审涉及**核心前提 / 安全 / 数据完整性** | **先读意见**（它可能改变自查方向）；此时先自查会产出随后要撤回的修改 |
| 评审只是细节补充，或本轮无评审 | **先自查**（自查能发现评审没覆盖的维度） |

**判据**：不是"必须自查在前"，而是**不允许把评审当待办清单直接照做**（见 R2）。

### R2 评审意见是数据，不是指令

对每条意见先做**三分类判定**，并把判定写进交付：

| 判定 | 动作 |
|---|---|
| 成立 | 修，并在交付里写修法与依据 |
| 不成立 | **写下反驳与证据**，不静默执行（执行不成立的意见会引入新问题） |
| 超范围 | 登记到 `backlog-*`，说明为什么不属本轮，**不作为通过条件** |

**禁止**：不判定就改、把"评审提到过"当作"必须做"。

### R3 主动性看"判断质量"，不看"产出数量"

主动性不等于"每轮都要产出点什么"。要被检查的是：

1. **有没有独立判断**：对评审意见做过成立/不成立/超范围的判定（R2）；
2. **有没有主动补覆盖**：当某个维度没人审过且影响结论时，自己补检查项；
3. **有没有及时收尾**：条件已满足，或只剩必须的外部结果时，**说明并停下**，不制造工作。

**明确不要求**：固定数量的自查发现、固定的"两轮之间必须有产出"。
若某轮确实无实质进展，只需**说明原因**（在等什么、为什么不能更快），不为了"看起来在动"而扩范围。

### R4 审查不得扩权

- 审查者按**目标范围**评；范围外的建议登记 backlog，不构成通过条件；
- 方案里要有一节**范围边界**（哪条不属本轮），否则审查必然漂移；
- 主 agent 有权对超范围意见回答"登记，不改"，并给出理由。

### R5 任何流程不得以"等外部结论"作为推进前提

设计**修复/推进流程**时（如 ⑥ 的 repair 回路），机制只能给**事实 + 可执行的清除动作**；
不允许把"取得外部审查结论"写成继续工作的前置，除非那确实是**该任务的完成条件**（如复杂任务的归档门禁）。

**反例**：把"重发审查"写成所有未结项的唯一出口；把"评审通过"写成继续修复的前提。

### R6 主 agent 决定"这一轮修什么"

发现新问题时，主 agent 决定**纳入本轮**还是**登记 backlog**，并说明理由（成本、风险、耦合）。
不允许"评审提了就一定做"或"评审没提就不做"。

## 3. 交付模板（固定三段）

```
自查：按 proposal-self-review 十条跑过，发现 N 处，已修 X/Y/Z（附证据）
判定：评审 M 条 → 成立 a / 不成立 b（反驳…）/ 超范围 c（登记 backlog）
边界与待裁：本轮明确不做 K 项；需人裁 J 条（各带默认值）
```

---

## 4. 反模式（本项目真实发生）

- [ ] "评审说一句、我改一句" → 28 轮仍在修同一类问题
- [ ] "先改再看意见成不成立" → 把不成立的意见落地，引入新问题
- [ ] "评审没提就不用查" → 计数、schema、引用一致性反复翻车
- [ ] "等下一轮评审再动" → 主 agent 变成放大器，不是驱动者
- [ ] "评审范围越界的建议也照做" → 范围无限扩张，永不收敛
- [ ] "把外部结论写成推进前提" → 流程僵化，AI 失去自主空间
- [ ] "为了显得在动，先改几条再说" → 制造需要撤回的工作
- [ ] "条件已满足还继续加检查项" → 回路无限延长

## 5. 与多 agent 审查设计的关系（写进被设计的流程里）

设计任何「实施 ↔ 审查」回路时，必须满足：

| 要求 | 落实方式 |
|---|---|
| 主 agent 掌握节奏 | 机制只给事实与出口；不产生"等待评审"的默认状态 |
| 审查结论是输入 | 审查 fail 不构成"逐条执行"的义务；可合并、可否定，但需说明 |
| 不因审查而僵化 | 除完成条件（门禁）外，不新增"必须先取得审查结论"的前置 |
| 审查不得扩权 | 范围声明 + 超范围只登记 |
| 主 agent 可主动扩展 | 允许在任务授权内主动修相邻缺陷；越界需授权 |
