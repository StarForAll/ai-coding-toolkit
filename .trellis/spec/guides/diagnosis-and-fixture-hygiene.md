# Diagnosis & Fixture Hygiene（取证与夹具卫生）

> 来源：2026-11-09/10 的 wf 控制流修复。那一轮我因为**取证方法**错了，连续四次把
> "夹具/环境问题"误判成"产品缺陷"，浪费了大量往返。以下四条是当时用代价换来的规则。

---

## 1. 先取事实，再形成假设

**规则**：任何"为什么失败"的判断，第一步必须是拿到 `code + facts` 原文（或异常文本），
而不是先假设成因再去找证据。

**反面样本**（同一轮真实发生）：

| 我先猜 | 实际 |
|---|---|
| 红在"删除类指纹" | `NameError: name 'after' is not defined` |
| 红在"历史摘要规则" | 回执账本没进提交 |
| 红在"能力门不可用" | `session already bound` |
| 红在"写权没释放" | 漏跑 `f1_init`，`project-config` 不存在 |

四次都是"打印原文"一步定案。**没有原文就不下结论**，包括"大概率是 X"这种。

## 2. 复现必须与 harness 同序

**规则**：单独复跑某个套件时，顺序必须与 `run_all.sh` 一致：
`wf_fixture.sh <dir>` → `f1_init.py` → 目标套件，且 `WF_FIX=<dir>`。
少了任一步，拿到的是**假失败**，据此修的代码会引入真缺陷。

**旁证**：同一轮里 `r31r34`、`r59` 在补齐顺序后直接全绿——它们此前"是红的"完全是因为我的复现方式。

## 3. 改夹具前先分清"正向步骤"与"负路径断言"

**规则**：夹具里有些调用是**期望失败**的（断言写在后面的 `rec()`）。把它们包成"失败即停"
等于抹掉测试意图，会让套件"看起来在跑，实际在验证错误的东西"。

**判据**：该调用后面 3 行内有没有 `rec(...)` 断言非 `WF_OK` 的码？有 → 不能包成必须成功。

同一轮我在 `task-check` / `archive` / `writer release` 三处连犯，每次都靠打印和 `rec` 结果才纠正。

## 4. 批量修改必须逐个验证生效

**规则**：批量插入同一段调用（例如给 12 个套件补抽样前置）时，**每一处都要带对上下文参数**
（会话 id、实时代次），且至少抽验两处真的生效。

**反面样本**：批量插入的采样调用没带该套件的 `sid`、也没用实时代次 → 静默失败 →
归档被"抽样未做"拦住 → 表象像产品缺陷（`cp2/cp3/cp4/cp5/r31r34` 一起红）。

## 5. 测量失败 ≠ 被测对象失败

**规则**：harness 的记账必须区分"没测到"和"测到失败"。
- 结果行缺失 = 测量失败 → 先重跑一次拿确定结果，重跑仍缺再计失败；
- 套件红 = 被测对象失败。

两者混在一起时，CI 会红一片且没人相信红灯（本轮 `run_all.sh` 因此加了串行重跑与必过门分层）。

## 6. 静默失败是排查成本的主要来源

**规则**：测试与夹具里凡是"下一步依赖它成功"的调用，失败就要**立刻出声**
（打印原文并停止），不要让它以 `KeyError` / `IndexError` / `BrokenPipe` 的形式在几层之后暴露。

本轮 4 个套件的根因都是靠这一条**一次定位**（`review-launch` / `review-import` /
`uninstall` 子进程 / 暂存目录查找）。
