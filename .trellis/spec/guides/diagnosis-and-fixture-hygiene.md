# Diagnosis & Fixture Hygiene（取证与夹具卫生）

> 来源：2026-11-09/10 的 wf 控制流修复。那一轮我因为**取证方法**错了，连续四次把
> "夹具/环境问题"误判成"产品缺陷"，浪费了大量往返。以下四条是当时用代价换来的规则。

---

## 1. 先取事实，再形成假设

**规则**：任何"为什么失败"的判断，第一步必须是拿到 `code + facts` 原文（或异常文本），
而不是先假设成因再去找证据。

**反面样本**（同一轮真实发生）：

| 我先猜 | 实际 |
|---|---|
| 红在"删除类指纹" | `NameError: name 'after' is not defined` |
| 红在"历史摘要规则" | 回执账本没进提交 |
| 红在"能力门不可用" | `session already bound` |
| 红在"写权没释放" | 漏跑 `f1_init`，`project-config` 不存在 |

四次都是"打印原文"一步定案。**没有原文就不下结论**，包括"大概率是 X"这种。

## 2. 复现必须与 harness 同序

**规则**：单独复跑某个套件时，顺序必须与 `run_all.sh` 一致：
`wf_fixture.sh <dir>` → `f1_init.py` → 目标套件，且 `WF_FIX=<dir>`。
少了任一步，拿到的是**假失败**，据此修的代码会引入真缺陷。

**旁证**：同一轮里 `r31r34`、`r59` 在补齐顺序后直接全绿——它们此前"是红的"完全是因为我的复现方式。

## 3. 改夹具前先分清"正向步骤"与"负路径断言"

**规则**：夹具里有些调用是**期望失败**的（断言写在后面的 `rec()`）。把它们包成"失败即停"
等于抹掉测试意图，会让套件"看起来在跑，实际在验证错误的东西"。

**判据**：该调用后面 3 行内有没有 `rec(...)` 断言非 `WF_OK` 的码？有 → 不能包成必须成功。

同一轮我在 `task-check` / `archive` / `writer release` 三处连犯，每次都靠打印和 `rec` 结果才纠正。

## 4. 批量修改必须逐个验证生效

**规则**：批量插入同一段调用（例如给 12 个套件补抽样前置）时，**每一处都要带对上下文参数**
（会话 id、实时代次），且至少抽验两处真的生效。

**反面样本**：批量插入的采样调用没带该套件的 `sid`、也没用实时代次 → 静默失败 →
归档被"抽样未做"拦住 → 表象像产品缺陷（`cp2/cp3/cp4/cp5/r31r34` 一起红）。

## 5. 测量失败 ≠ 被测对象失败

**规则**：harness 的记账必须区分"没测到"和"测到失败"。
- 结果行缺失 = 基础设施失败 → 本轮直接计失败，保留日志；修明原因后另开一轮，不自动覆盖原尝试；
- 套件红 = 被测对象失败。

两者混在一起时，CI 会红一片且没人相信红灯（本轮 `run_all.sh` 因此加了串行重跑与必过门分层）。

## 6. 静默失败是排查成本的主要来源

**规则**：测试与夹具里凡是"下一步依赖它成功"的调用，失败就要**立刻出声**
（打印原文并停止），不要让它以 `KeyError` / `IndexError` / `BrokenPipe` 的形式在几层之后暴露。

本轮 4 个套件的根因都是靠这一条**一次定位**（`review-launch` / `review-import` /
`uninstall` 子进程 / 暂存目录查找）。

## 7. 断言要锚行为，不锚排版

**规则**：测试里不要断言"某个字符串出现在某个 `def` 之后"这类**实现布局**。
布局会随重构变化，断言会把"正确重构"判成失败。

**真实事故**：一条测试断言 `item.get("outcome") == "escalated"` 必须出现在 `def final_gate` 之后。
把这段判定抽成 helper（行为完全不变、门禁契约完好）后测试立刻变红——它测的不是契约，是排版。

**替代写法**：
- 断言行为：调用入口函数，看返回的 `code/facts`；
- 断言"谁引用了谁"用 `inspect.getsource(func)`（**函数级**，随函数走，不随文件行号走）；
- 需要"只在这里、不在那里"时，对每个不该管的函数逐个断言其 source 不含该概念。

## 8. 挪动结构后必须复跑全文断言类测试

**规则**：把函数从 A 挪到 B、把内联逻辑抽成 helper、调整模块导入方向——
这些"行为不变"的改动**最容易**让排版类断言假红。改完必须重跑**完整**测试命令，
而不是只跑改动相关的子集。

**真实事故**：我先跑子集测试通过，再挪 helper 位置，然后直接提交并声明"302 单测全绿"——
HEAD 实际是 1 条红。**声明的验证必须是提交内容上跑过的验证**，不是"印象里跑过"。

## 10. 共享夹具的竞态：单跑过、全量偶发失败先查夹具

**症状**：某套件单独跑 100% 通过，全量跑偶发失败且报错与业务无关（如 `KeyError: 'directory'`、`INIT-FAILED`），重跑又通过。

**成因**：套件共用固定夹具目录（本仓库是 `/tmp/wf-fixtures/*`）与发行仓库副本（`~/.cache/wf-release-repo`）。
并行阶段与串行阶段、或两份全量脚本同时跑，会互相重建/清理对方的夹具。

**判定顺序**：
1. 单跑该套件（`WF_SUITES="<name>" bash run_all.sh`，走同一 harness 以便重建夹具）；
2. 若无并发时全量通过，判为夹具竞态，**不是被测对象缺陷**；
3. 记录该次失败的报错原文与时间，别用"重跑通过"抹掉它——它可能在掩盖真实缺陷。

**纪律**：全量脚本独占夹具目录，同一时刻只跑一份；不要直接 `python3 rXX_tests.py` 绕过 harness 重建。

## 9. 验证前先核对产物来源和写入面

当前 `run_all.sh` 的 T1/T2 只构建或复用测试发行缓存，不写 `docs/workflows/wf-release/`；`--no-build` 校验源摘要，陈旧即拒绝。候选验证使用独立带 tag 的候选仓库。测试仍会写缓存、结果和临时夹具，不能视为只读命令。

收口时先核对构建可复现性，再跑完整回归，最后检查产品发行树摘要和 Git diff。详见 [wf 交付纪律](../docs/wf-delivery-discipline.md)。

**夹具隔离检查**：user namespace 只能隔离挂载，不能把宿主夹具父目录 bind 回私有 `/tmp`。只挂共享结果与只读输入；字段断言迁移后逐条映射，不能仅用套件数量证明覆盖等价。用户配置测试使用合成测试确认集合，绝不复制或改写真人确认记录。
