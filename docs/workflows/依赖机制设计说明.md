# 依赖机制设计说明

> 文档性质：设计层说明，不描述具体实现。
> 定位：工作流层的顺序保障机制，以 Trellis 的任务、归档与产物机制为基底；不修改基底内部状态字段，不引入调度与并行。
> 适用：0→1 阶段必选；后续阶段可选。只要使用，就必须遵守本文。
> 同步版本：随主设计 [workflow-design.md](./workflow-design.md) v33 同步；状态表、返工/替换/放弃、对账与恢复以本文为准；设计层约束冲突以主设计为准。

---

## 1. 要解决的问题

- 0→1 阶段的任务必须按既定顺序执行，不能换序。
- 返工需要插队，但不能打乱已定顺序。
- 任务被替换或放弃时，下游不能被错误解锁。
- 替换/放弃实施失败时，不能倒回旧状态，也不能让下游看到“已正常”。
- 重入或崩溃后，必须能确定“下一个该做谁”。

## 2. 边界

- 只表达顺序，形态是 DAG，不能有环。
- **边只表达尚未满足的顺序**：建边的两端都必须在活动区，前置必须未完工；已归档任务作为前置只来自继承或活动期建边后该前置归档，删边仍可对归档目标（主设计 §7.5）。
- 不做资源隔离、并行调度、优先级排序、跨项目依赖。
- 图内任务的开工与收尾只走依赖机制入口；原生入口只用于图外任务。
- 依赖状态记录在机制自己的账本里，不用基底的任务状态字段表达。
- 依赖机制自包含：基底升级时，只要求任务目录可解析、任务元数据被保留。
- **替换/放弃是前向操作**：人发起；实施前可做静态校验；实施后只允许向前完成，不回退到替换前。
- **已归档任务不可替换、不可放弃、不可重开**；已归档任务不直接返工，其产物缺陷由当前未归档任务承载。
- **状态写入必须合法**：任何依赖状态写入都必须符合主设计表 4-2 的合法转移；非法转移拒绝并报告（主设计不变量 12、§7.5）。
- **原子性边界**：机制只保证自己写入状态的提交原子与下游可见顺序；不嵌入基底事务，归档与机制写入不保证跨系统原子。
- **写入即持久化**：账本、前置集合、替换指向与返工来源的写入必须随机制动作持久化；持久化 = 写入 + 提交（§3）；机制只提交自己写入的状态，不代替基底提交工作改动；未持久化的变更不参与判定。

## 3. 术语

任务状态由基底表达，只有规划中 / 进行中 / 已归档；本说明只定义依赖状态。

| 术语 | 含义 |
|---|---|
| 依赖标识 | 全局唯一标识（雪花 ID），只在依赖机制内使用，映射到任务目录；不随目录名变化 |
| 前置集合 | 本任务依赖的任务标识集合；**唯一事实源** |
| 下一个集合 | 由前置集合派生，仅用于异常时重连下游 |
| 依赖账本 | 记录任务标识、依赖状态（正常/异常/挂起）、说明、替换指向 |
| 持久化 | 账本 / 前置集合 / 替换指向 / 返工来源写入受版本控制的文件并完成一次版本库提交；机制只提交自己写入的状态；工作改动与归档提交仍由基底流程驱动 |
| 暂存 | 写入工作区但不提交；未提交不参与判定，失败时回滚 |
| DAG 视图 | 由前置集合 + 账本派生：节点、边、组件、就绪集 |
| 图内任务 | 参与依赖机制的任务：P、实现任务、返工任务、收尾任务，以及迭代期建过依赖边的任务；开工 / 收尾走机制入口 |
| 图外任务 | 不参与依赖机制的任务：无关任务、无依赖的迭代任务；走原生流程 |
| 建边 | 迭代期给任务新增一条前置边的机制入口动作；两端都必须在活动区，只表达“尚未满足的顺序”（§6.7） |
| 当前任务 | 会话正在执行或最近登记的、由基底活动任务指针登记的任务；可能是图内或图外任务；指针是**提示**，指向已归档、规划中且前置未满足、未归档且账本为“异常”（替换/放弃未完成）、或账本为“正常但未归档”的任务时视为无当前任务；入口判定以 DAG 视图与账本为准；重启 / 换 CLI 后可能为空，也可能残留 |
| 就绪 | 前置集合全部为“正常”，且该任务未完成、未归档，且账本为“无记录”（“正常但未归档”按 §8 类型 3 处理，“异常”属未完成的替换/放弃、按 §8 类型 5 处置，均不构成就绪）；挂起清除后，任务回到就绪（即使已开工） |
| 挂起 | 账本状态；该任务等待返工任务，暂不满足就绪；基底任务状态不变；挂起同时阻断该任务自身与下游 |
| 返工任务（返回任务，简称 R） | 为修复该任务的问题而新建；**挂载点必须是未归档任务 T**；前置集合 = T 当前的前置集合；任务记录标注“返工来源 = T”；T 把它加入自己的前置集合，并进入挂起；已归档任务不直接返工 |
| 返工任务集合 | 所有任务记录中标注“返工来源 = 该任务”的任务，包含已归档任务；由扫描活动区与归档区派生（§4），不存储、不维护 ID 列表。用于判断挂起能否清除 |
| 替换发起 | 人决定替换并说明新任务范围（新任务标识由机制生成）；尚未写入任何状态 |
| 替换实施 | 机制写入旧任务账本“异常”并记录替换指向的第一步；实施后只向前完成，不回退 |
| 放弃发起 | 人决定放弃并给出原因；尚未写入任何状态 |
| 放弃实施 | 机制写入旧任务账本“异常”并记录放弃原因的第一步；实施后只向前完成，不回退 |
| 向前完成 | 替换/放弃实施后，按 §8 类型 5 补齐未完成步骤；不重跑实施前静态校验，不回退 |
| 对账修复 | 机制提供的唯一人工修复入口：人发起，机制执行；处理已归档但账本不是合法终态（无记录 / 挂起）、挂起无返工、正常未归档、无法解析或非法的记录 / 边、替换/放弃未完成等不一致；禁止手改账本 |

## 4. 事实源与产物

| 产物 | 性质 | 说明 |
|---|---|---|
| 前置集合 | 存储，唯一事实源 | 持久化在任务记录中 |
| 依赖账本 | 存储，状态事实源 | 新增“正常”只能由收尾逻辑或对账修复（仅已归档但账本无记录 / 挂起）写入；正常未归档的修复保持“正常”或改回“无记录” |
| 下一个集合 | 派生 | 状态变化后重建，不手工维护 |
| 返工任务集合 | 派生 | 扫描活动区与归档区的任务记录，按“返工来源”派生；不存储、不维护 ID 列表 |
| DAG 视图 | 派生 | 状态变化后重建，人只读不写 |

派生件损坏时，可以从“前置集合 + 账本”完整重建；账本中的“异常/挂起/替换指向”与任务记录中的“返工来源”不可由其他数据重建，因此必须纳入版本控制。本表与主设计 §7.3 对应。

**持久化**：账本、前置集合、替换指向与返工来源必须随机制动作持久化；持久化 = 写入 + 提交（§3）。机制只提交自己写入的状态，不代替基底提交工作改动。未持久化的写入不参与就绪判定，不重建视图；持久化失败按 §8 处理。

“返工任务集合”不另存：账本不记录“T 的返工任务有哪些”，任务记录也不保存返工任务 ID 列表。集合每次由活动区与归档区的任务记录重建，因而不存在“ID 列表与前置集合不一致”的额外对账分支与清理规则。扫描实现（顺序读取、缓存、索引）不属于设计层；设计层只要求覆盖两个区，且结果等价于逐个读取任务记录。

## 5. 状态与判定

| 账本状态 | 含义 | 对下游 |
|---|---|---|
| 无记录 | 从未登记，或记录已清除 | 不满足 |
| 挂起 | 返工中暂停 | 不满足 |
| 正常 | 人判后正常归档 | 满足 |
| 异常 | 替换、放弃或异常归档 | 不满足，需重连（替换 / 放弃） |

判定规则：**依赖满足 = 前置在账本中的状态为“正常”。** 未记录一律视为不满足。

**完整转移表**

| # | 从 | 到 | 触发 | 写入者 |
|---|---|---|---|---|
| 1 | 无记录 | 正常 | 正常收尾 | 收尾逻辑 |
| 2 | 无记录 | 挂起 | 发现返工 | 返工逻辑 |
| 3 | 挂起 | 无记录 | T 未归档、存在返工记录、无未归档返工、前置全正常 | 评估点见 §6.3 第 5 步（R 收尾、放弃/替换的删边与重连、启动对账、入口第二段） |
| 4 | 无记录 / 挂起 | 异常 | 替换 / 放弃实施 | 替换 / 放弃逻辑 |
| 5 | 已归档但账本为无记录 / 挂起 | 正常 / 异常 | 对账修复 | 人确认，机制补记 / 改写；确认正常时前置须全正常 |
| 6 | 正常但未归档 | 保持正常 / 无记录 | 对账修复 | 人确认重新归档并保持正常，或改回无记录 |
| 7 | 挂起（未归档） | 无记录 | 对账修复：无返工任务记录，人确认清除 | 对账修复（类型 2） |

**本表是账本写入的唯一合法转移集**：所有写入者（收尾、返工、替换、放弃、对账修复）在写入前都必须校验源状态；表中没有的转移拒绝并报告，不写入。对账修复的行 5/6/7 是修复专用转移，不适用普通动作的源状态校验；类型 4 的“修复无法解析或非法的记录 / 边”不是正常状态转移，不适用本表，按类型 4 的修复动作执行（修复记录或删边）。

**同一任务再次发现返工不是新的状态转移**：T 已挂起时只新建 R 并补边，不重复写“挂起”。

**归档终态约束**：已归档任务的账本终态只能是“正常”或“异常”；“正常”要求该任务的前置集合全部为“正常”。“无记录 / 挂起”是待修复的不一致态（类型 1）。

**没有“异常 → 无记录 / 正常”的转移**：替换/放弃一经实施，旧任务保持“异常”并完成归档；失败只向前完成（§8），不回退。

本表是完整状态表；主设计 §7.4 只保留“对下游”结论，不重复“含义”列。异常没有例外通道；下游只能通过重连继续。

## 6. 生命周期规则

### 6.0 项目层与链头

- 项目层任务 P 是链头，没有前置。
- P 产出全部任务、每个任务的前置集合、以及初始 DAG 视图。
- P 正常归档后，0→1 任务按 DAG 依次就绪。
- 收尾任务依赖最后一个实现任务；它是图里的普通节点，没有特殊判定。
- 已归档任务不可替换、不可放弃、不可重开；已归档任务不直接返工，其产物缺陷由当前未归档任务承载。

### 6.1 开工

1. 读取账本，校验前置是否全部为“正常”，且目标任务账本为“无记录”（挂起 / 异常 / 正常未归档一律拒绝并报告）。
2. 不满足：停在规划态，不进入执行。
3. 满足：登记当前任务（基底入口），进入执行。
4. 已实施但未完成的替换/放弃：先按 §8 的完成入口处理，不继续旧任务。

### 6.2 完成（可见性顺序 + 可恢复）

人判（基底 check 后的人工判断） → 校验源状态（账本为“无记录”，且前置集合全部为“正常”） → 归档 → 账本写“正常” + 持久化 → 重建 DAG 视图。

这组步骤按可见性顺序执行，不是跨系统原子事务：任一步失败都不能让下游看到“已正常”；失败按 §8 对账处理，不重放，不允许半途解锁下游。源状态校验失败时不归档、不写账本：挂起按 §6.3 / §6.5 的返工 / 放弃规则，异常按 §8 类型 5，正常未归档按类型 3，前置集合不全正常按 §8 组合表的“等待”行处置。

“正常”只由收尾逻辑或对账修复写入，不由 AI 自述；对账修复**新增“正常”**只用于已归档且账本无记录或挂起的历史任务（确认“正常”时前置须全正常）；正常未归档的修复保持“正常”或改回“无记录”；收尾动作必须由人发起或确认。

**持久化边界**：账本“正常”只有在按 §3 定义持久化成功后（写入 + 提交）才生效。归档成功但账本未持久化的，按“已归档但账本无记录”处理（§8），不放行下游。

### 6.3 返工

**适用范围**：返工只作用于**未归档任务**。T 必须未归档，且账本为“无记录”或“挂起”；否则拒绝并报告：已归档任务不直接返工（其产物缺陷由当前未归档任务承载），账本“异常”按 §8 类型 5 处置，账本“正常但未归档”按类型 3 处置。

返工由人判断并发起。

1. 校验通过后，账本把本任务 T 记为“挂起”并持久化（T 立即退出就绪集）；T 已挂起时不重复写状态，直接进入第 2 步。
2. 新建返工任务 R（返回任务），前置集合 = T 的当前前置集合；任务记录标注“返工来源 = T”；持久化。
3. 把 R 加入 T 的前置集合（不修改基底的任务状态字段）；持久化。
4. 执行 R 到完成；R 正常归档后，账本 R 记“正常”。
5. **R 的收尾动作在同一动作中评估 T 的挂起清除**：扫描活动区与归档区，取“返工来源 = T”的任务集合；若集合非空、其中没有未归档成员、且 T 的前置集合全部为正常，**清除 T 的挂起记录**（表 4-2 行 3）并提交；T 自动回到就绪（即使它此前已开工），重新校验依赖后继续。清除失败或崩溃不要求跨任务原子：启动时按同一条件评估并补做（§8）。

**崩溃窗口**：

- 1 后 2 前：T 挂起、无返工任务 → 按 §8 类型 2 对账修复（人确认补建 R 或清除挂起；清除挂起按表 4-2 行 7）。
- 2 后 3 前：T 挂起、R 已有返工来源 → 选择规则进入 R；返工任务收尾时若 T 的前置集合尚未包含对应的返工任务，先补边；若 T 没有未归档的返工任务且前置集合全正常，再清除挂起。
- 3 后：状态一致，按正常流程继续。
- **4 后 5 前**：R 已归档、账本 R 已“正常”，T 仍挂起 → 启动时按步骤 5 的条件评估并清除；这是正常派生动作，不按对账不一致处理。

**挂起清除的评估点**（表 4-2 行 3 的写入者）：R 的收尾动作、放弃/替换的删边与重连动作、启动对账、入口第二段（主设计 §9.1）；各评估点使用本步的同一条件，任一命中即清除。

存在返工任务记录时，挂起在“没有未归档的返工任务且前置集合全部为正常”后清除，不按单个 R 的归档时点清除；已归档的返工任务（正常、被替换或放弃）不再阻塞。

集合只从任务记录派生，不看归档先后：同一次判定里，已归档的 R 与未归档的 R 等价处理，结论只取决于“有没有未归档成员”。归档区是只读历史，R 归档后不再改写其记录，因此“返工来源”必须在归档前写入。扫描到的记录若无法解析，计入对账不一致（§8），不静默当作“没有返工任务”。

### 6.4 替换

替换只适用于**未归档任务**。已归档任务不可替换（主设计 §5.5）；已归档任务不直接返工，其产物缺陷由当前未归档任务承载（§6.3、主设计 §5.5）。

**发起（人）**：人决定替换并说明新任务范围；机制先生成新任务标识，并做实施前静态校验：

- 新任务继承的前置集合 = 旧任务当前前置集合；
- 重连后的边集不成环；
- 目标状态合法（新任务不存在、旧任务未归档，且旧任务账本为“无记录”或“挂起”）。

校验失败：不实施，旧任务不变，报告原因。此时尚未写入任何状态，不算“回退”。实施前静态校验只在发起时执行；实施后失败走 §8 的向前完成，不重跑该静态校验。

**实施（机制，一旦开始不可回退）**：

1. 旧任务账本记“异常”，替换指向 = 新任务标识，说明写替换；持久化；旧任务立即退出就绪集，不再可被选择；若旧任务持有会话当前任务指针，清除该指针（按基底入口）。
2. 创建新任务；新任务继承旧任务当前的前置集合；新任务从“无记录”开始。
3. 把所有未归档下游（包括夹在中间的返工任务）重连到新任务标识；从下游的前置集合中移除旧任务标识；边变更按 §6.7 校验。
4. 检环；静态校验已排除的环若仍出现，停止并报告，旧任务保持“异常”，由 §8 的完成入口向前处置。
5. 旧任务以异常归档离开活动列表（基底 archive）。
6. 重建视图，持久化。

**失败与修复（只向前）**：实施后崩溃，旧任务保持“异常”，下游保持阻断；按 §8 的“替换/放弃未完成”入口向前完成：

- **向前完成不重跑实施前静态校验的目标状态条件**：旧任务“异常”正是待修复状态本身；补建/重连仍做目标存在性、目标不是“异常”、成环校验；
- 旧任务未归档 → 归档旧任务；
- 新任务不存在 → 人确认后按向前完成补建（不重跑实施前静态校验），或改为放弃（放弃也向前，不恢复旧任务）；
- 新任务存在但部分下游仍指向旧任务 → 补齐重连；
- 边已重连但旧任务未归档 → 归档旧任务；
- 已实施的替换若人决定不再继续，只能把新任务按 §6.5 放弃并完成重连，**不能恢复旧任务**。

**挂起中的 T 被替换**：R 是 T 的前置，不属于“未归档下游”，**不重连**；R 留在图中按普通任务处置；新任务继承 T 的当前前置集合（含 R），因此仍等待 R；若人决定不再需要 R，按 §6.5 放弃 R。新任务的前置集合若后续出现异常成员（例如 R 被放弃），按 §6.5 的删边或 §6.4 的替换处置；异常前置不会因为被继承而获得豁免。

**替换返工任务 R**：新任务继承 R 的“返工来源”标记；R 归档异常但已归档，不再阻塞 T 的挂起（§6.3 只看未归档的返工任务）。新任务取代 R 的位置，T 的返工任务集合按“返工来源”派生。

替换任务本身从“无记录”开始；它完成正常收尾后才记“正常”。替换任务的内容、范围与依赖机制无关，机制只负责继承与重连。

### 6.5 放弃

放弃只适用于**未归档任务**。已归档任务不可放弃（主设计 §5.5）。

**发起（人）**：人决定放弃，给出原因；机制做实施前静态校验（旧任务未归档、旧任务账本为“无记录”或“挂起”、下游边删除/替代后不成环），校验失败则不实施，旧任务不变。

**实施（机制，一旦开始不可回退）**：

1. 旧任务账本记“异常”，说明写放弃原因，替换指向为空；持久化；旧任务立即退出就绪集；若旧任务持有会话当前任务指针，清除该指针（按基底入口）。
2. 两种处置由人决定：
   - **删边**：从所有未归档下游的前置集合中删除旧任务标识；记录影响与原因。
   - **新建替代**：下游改依赖替代任务；走 §6.4 的重连规则。
3. 重连后检环；失败则停止并报告，旧任务保持“异常”，由 §8 的完成入口向前处置。
4. 旧任务以异常归档离开活动列表。
5. 重建视图，持久化。

**失败与修复（只向前）**：实施后崩溃，旧任务保持“异常”，下游保持阻断；按 §8 的“替换/放弃未完成”入口向前完成：补齐删边/重连、归档旧任务；不恢复旧任务。

**放弃返工任务 R**：R 归档异常但已归档，不再阻塞 T 的挂起；T 的前置集合删去 R 边后若全部正常，挂起即可清除（按表 4-2 行 3 执行，条件见 §6.3）。若 T 已被替换或放弃，R 按“R 留在图中按普通任务处置”的规则处理。

### 6.6 异常任务归档

替换或放弃的任务使用原生归档动作离开活动列表，账本记“异常”。基底会显示它已归档，但依赖判定只认账本，不会因此解锁下游。

### 6.7 迭代期建边与边变更校验

- 后续阶段允许新建普通依赖边（非返工、非替换）；建边是机制的正常入口动作，不是基线变更，也不是旁路。边只表达“尚未满足的顺序”：
  - **两端都必须在活动区**。已归档任务不再被选择、不再收尾，给它挂前置改变不了任何判定，只会在归档终态上留下“前置非正常”的组合，所以不接新建边；已归档任务可作为前置，只来自继承或活动期建边后该前置归档——边建于两端都在活动区时，前置一侧随后归档，边继续有效。删边不受此限，可对归档目标执行。
  - **前置必须尚未完工**（账本为“无记录”或“挂起”），或为“正常但未归档”的任务；前置账本为“异常”的不得建边。
  - 目标账本为“异常”的不得建边（先按 §8 类型 5 向前完成）；目标账本为“正常但未归档”的，先按类型 3 修复。
  - 不得自环、不得成环（后置校验再检一次）。
  - **对未开工目标**：边立刻把目标挡在就绪之外，按 §8 组合表的“等待”行处理，前置完成后自动回到就绪。
  - **对进行中目标**：边不阻止它继续执行，只阻止它收尾；这类组合就是组合表的“等待”行，不算需要修复的不一致。
- 建边后按本节的暂存 / 后置校验 / 提交规则处理。
- **边变更统一校验**：建边、返工加边、替换/放弃的重连（新增或替换边）做前置校验（两端存在；目标不是异常；建边另要求两端在活动区、前置未完工（或为正常但未归档）；无自环/成环）→ **写入暂存（不提交）** → 后置校验（检环、重建视图）→ **通过后提交**；后置校验失败 → **回滚暂存、不提交、报告**；**删边同样先暂存、重建视图后提交**，因为被删的目标可以已经是“异常”、也可以在归档区；前置校验失败不写入。
- 不自动清理账本条目；“正常”条目长期保留，供类型 1 / 4 修复校验、终态判定与“前置是否已满足”的解析使用。

## 7. 选择规则

- 就绪集是**图内任务**的集合（含实现任务、返工任务、收尾任务；迭代期建过依赖边的任务也是图内任务）。
- 就绪集按**任务创建时间**排序，取最早的一个。
- 选择规则用于**没有当前任务**时；有当前任务时先继续当前任务（主设计 §9.1）。
- 0→1 阶段链式结构下，就绪集通常只有一个。
- 后续阶段出现多个组件或多个就绪节点时，仍用同一规则，不引入优先级。
- 返工任务与其他就绪任务按同一排序，不设优先级；任务入口选择以主设计 §9.1 为准。

## 8. 一致性与恢复

- **开工前对账**：前置集合、账本、派生视图三者一致才允许开工。
- **启动时对账**：先重建派生件，做**完整性自检**（按下文“账本 / 归档组合自检”表识别非法或不一致组合并标记为待对账修复，不自动修复），检查未完成的替换/放弃（标记为类型 5），按 §6.3 评估所有**未归档**的挂起（满足条件的直接清除并持久化），再判断就绪；除挂起清除外，这一步不写账本、不改变任务状态，不是对账修复。
- **绕过兜底**：
  - 任务已归档但账本不是合法终态（无记录 / 挂起）→ 标记“待对账修复”（类型 1），不放行；
  - 账本为“正常”但任务未归档 → 视为未满足并报告（类型 3）；
  - 活动区或归档区有无法解析或非法的任务记录 / 边 → 报告并计入对账不一致；按类型 4 处理，不静默跳过；
  - 账本 / 归档组合不满足主设计 §4.4 的归档终态约束（例如已归档“正常”任务的前置集合含非“正常”成员）→ 报告并计入对账不一致；按类型 4 处理，不静默放行。未归档任务前置集合不满足属“等待”，按组合表处置，不计入对账不一致；
  - 替换/放弃未完成（旧任务账本“异常”、有替换指向或放弃原因，但新任务/重连/归档未完成）→ 待对账修复，不放行。

**账本 / 归档组合自检**（启动时与每次对账前执行；读账本 + 基底任务状态）：

| 组合 | 判定 | 出口 |
|---|---|---|
| 已归档 + 正常 + 前置全正常 | 合法 | — |
| 已归档 + 正常 + 前置含非正常 | 非法 | 类型 4 |
| 已归档 + 挂起 | 非法 | 类型 1（人确认正常 / 异常后改写） |
| 已归档 + 无记录 | 非法 | 类型 1（人确认正常 / 异常后补记） |
| 已归档 + 异常 | 合法（替换 / 放弃结果） | — |
| 未归档 + 正常 | 不一致 | 类型 3 |
| 未归档 + 挂起（任意前置） | 合法（等待返工） | §6.3 评估 / 进入 R；前置不全正常时按挂起阶段的对账行 |
| 未归档 + 异常 | 替换 / 放弃未完成 | 类型 5 |
| 未归档 + 无记录 + 规划中 / 进行中 + 前置含非正常 | 等待 | 不修复，等前置完成；前置为异常时按删边或替换 / 放弃处置，仍无出口按类型 4 |
| 未归档 + 无记录 + 规划中 / 进行中 + 前置含“正常但未归档” | 等待（欠一次类型 3） | 先按类型 3 修复该前置 |

- **待对账修复的唯一出口**：由人发起、机制执行；禁止手改账本文件。按类型处理：
  1. 已归档但账本不是合法终态（无记录 / 挂起）→ 人确认“正常 / 异常”，机制补记或改写账本；确认“正常”时该任务的前置集合必须全部为“正常”，否则先按类型 4 修复边，或改为确认“异常”；确认“异常”时按主设计 §7.4 的异常规则处置其未归档下游；这是“正常”的合法修复写入；
  2. 未归档任务挂起但找不到返工任务 → 人确认补建返工任务或清除挂起；清除挂起按表 4-2 行 7 执行；
  3. 正常但未归档 → 人确认重新归档（账本保持“正常”）或改回“无记录”；机制执行并持久化；
  4. 无法解析或非法的记录 / 边（例如已归档“正常”任务的前置集合含非“正常”成员、账本记录无法解析）→ 人修复记录或删边；未归档任务可放弃并重连下游；机制验证后重建视图；无法修复时按阻断处理，不静默放行；
  5. 替换/放弃未完成 → 机制向前完成：补齐新任务创建、下游重连/删边、旧任务归档；**不回退**。向前完成不重跑实施前“旧任务账本为无记录/挂起”的校验（旧任务的“异常”正是待修复状态），但仍校验目标存在、目标不是“异常”、不成环；多个未完成项按旧任务创建时间先后逐个完成。
- **“正常”的写入者**：收尾逻辑与对账修复（仅类型 1）；类型 3 保持“正常”或改回“无记录”，不新增“正常”写入；类型 2、4、5 不写“正常”。
- **启动时挂起但条件未满足**（仅未归档任务）：有未归档 R → T 的恢复路径是进入 R（全局选择按主设计 §9.1）；无未归档 R 且存在返工记录、但前置集合不全正常 → 处理异常前置（替换 / 放弃或删边），挂起保留到条件满足；无返工记录 → 按类型 2 对账修复。
- **启动时进行中或规划中但前置含非正常**（未挂起）：工作继续，收尾等前置；前置为异常时按删边或替换 / 放弃处置。
- **不保留操作日志**：收尾失败时，按上述兜底规则恢复到确定状态，不重放。
- **账本不自动清理**：“正常”条目长期保留，供类型 1 / 4 修复校验、归档终态判定与“前置是否已满足”的解析使用。
- **持久化**：账本、前置集合、替换指向、返工来源随项目版本控制；写入后必须按 §3 定义持久化（写入 + 提交），未持久化的变更不参与判定。

机制自身不可用时，不在这里做降级；按主设计 §9.4 卸载模块。

## 9. 身份与解析

- 雪花 ID 写入任务记录；它不随基底内部 id 或目录名变化。
- **返工来源**记的是依赖标识（雪花 ID），不是基底内部 id 或目录名；任务归档或重命名后仍可解析。
- **替换指向**记的是新任务的依赖标识；放弃记原因。
- 解析器同时覆盖活动区与归档区，保证“前置已归档”可判定，也保证返工任务集合能取到已归档的成员。
- **允许重命名**；重命名后由机制按标识同步所有引用。
- 账本中的路径只作缓存，判定以解析结果为准。

## 10. 与基底的关系

- 不用基底的任务状态字段表达依赖状态。
- 只读取任务目录与归档位置，不修改基底的数据结构。
- 基底升级时，机制只需要“任务目录可解析、任务元数据保留”这两个稳定面。
- 账本与前置集合的写入必须持久化；派生件可重建，状态与替换指向不可重建。

## 11. 非目标

- 并行调度、自动派发、优先级、ETA。
- 跨项目依赖。
- 资源隔离。
- 验证证据链（完成 = 人判 + 归档，不是证据链）。
- 替换/放弃的回退（实施后只向前完成）。

## 12. 场景

| 场景 | 说明 |
|---|---|
| 0→1 | 必选；P 为链头；任务串行；收尾依赖最后任务 |
| 持续使用 | 可选；无依赖任务走原生流程；出现新依赖时形成新组件 |
| 探索型 0→1 | P 前细后粗、滚动规划；瀑布风险仍存在，只能缓解 |
| 多项目 | 账本按项目隔离；机制不跨项目 |
| 模块不可用 | 不降级；卸载模块（默认仅模块卸载，保留数据）；修复后重装；重装后按 §8 对账修复；卸载入口不依赖机制运行时；卸载步骤可重复执行 |
| 迭代期建边 | 允许；两端都在活动区；前置必须未完工；目标不能是异常；对未开工任务挡就绪、对进行中任务只挡收尾；先暂存、后置校验通过后提交 |
| 替换/放弃 | 只适用于未归档任务；实施前静态校验；实施后只向前完成；已归档任务不可替换/放弃 |
| 返工完成 | R 收尾时评估并清除 T 的挂起；启动时按同一条件补做，覆盖 4→5 崩溃窗口 |
| 非法状态写入 | 机制入口拒绝；启动时完整性自检按类型 1 / 4 处置 |
| 当前任务指针无效（按主设计 §3）或为空 | 视为无当前任务，按 DAG 与账本选择；未归档且账本“异常”由主设计 §9.1 第一段向前完成 |
| 边变更后置校验失败 | 回滚暂存、不提交、报告 |

## 13. 已确定的实现口径（设计层）

以下为实现层选择，不影响上述规则：

- 账本按需登记发生状态变化的图内任务；未登记的图内任务按“无记录”处理；“正常”条目长期保留，不自动清理；“异常/挂起/替换指向”长期保留。
- 对账修复是“正常”的第二个合法写入者，只用于已归档且账本无记录 / 挂起；确认“正常”时前置须全正常；正常未归档的修复保持“正常”或改回“无记录”，不新增“正常”写入；挂起清除、替换/放弃完成不写“正常”。
- 返工任务集合由扫描活动区与归档区派生，不单独存储，也不新增返工任务 ID 列表字段。
- 多组件共用一个 DAG 视图文件，按组件分区。
- 替换/放弃的异常归档使用原生归档动作，状态只在账本中表达；实施后不回退。
- 启动时对账；不保留操作日志；收尾失败按 §8 兜底规则恢复，不重放。
- 就绪选择按任务创建时间；不引入优先级字段。
- 解析器采用“任务元数据中的雪花 ID + 活动/归档双区扫描”，账本路径仅作缓存。
- 派生件每次状态变化后重建；对账不通过时禁止开工。
- 边变更统一走前置/后置校验；建边、返工加边、替换/放弃重连共用。
- 状态写入与边变更一样，在机制入口做统一校验；非法转移拒绝，不写入。
- 返工挂载点为未归档任务；已归档任务不直接返工。
- 当前任务指针是提示；指向已归档、规划中且前置未满足、未归档且账本“异常”，或账本正常未归档的任务时视为无当前任务，按 DAG 与账本选择。
- 启动时完整性自检读账本与基底任务状态；非法组合按类型 1 / 4 标记，不自动修复。
- 收尾、替换/放弃、返工不要求跨系统 / 跨任务原子；机制只保证自己写入的提交原子与下游可见顺序（主设计 §4.2）。
- 边变更先暂存、后置校验通过后提交；失败回滚并报告。
- 提交范围含账本、前置集合、替换指向、返工来源。
- 卸载脚本幂等，中断后重跑不产生副作用。
- 账本、前置集合、替换指向、返工来源的写入与对应机制动作一同按 §3 定义持久化（写入 + 提交）；未持久化不参与判定。
