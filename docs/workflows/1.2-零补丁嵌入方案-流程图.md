# 模块流程流转图（v4 · 单人单分支 · 原生优先）

> 本文件是 [1.2-零补丁嵌入方案.md](1.2-零补丁嵌入方案.md)（v4）的**图示版**，供人工审查流程是否正确。
> **图不引入新规则**：每处判定都标注了方案里的章节号；两者冲突时**以方案正文为准**。
> 本版新增**项目级契约**这一前置（`.wf/contract.yaml`，见方案 §4.2.1）——v20 §6.1 的"契约未定不应开任务"在图 1 顶部体现。

**图例**（四图通用）

| 形状 | 含义 |
|---|---|
| 圆角矩形 | **人**的动作或人工决策点 |
| 矩形 | `wf` 子命令（模块自己的 CLI） |
| 矩形内注明"调用 …" | 该步是 **Trellis 原生命令**，模块只是调用（图中不单设形状，避免与 `wf` 命令混淆） |
| 圆柱 | **状态或产物**（`task.json` 或文件系统） |
| 菱形 | **门禁**（fail-closed 判定） |

## 图 1：任务生命周期与证据有效期（主流程）

```mermaid
flowchart TD
    A(["人：项目已 trellis init，准备开始任务"]) --> B["wf route<br/>只读，输出入口分类与当前状态"]
    B --> C0{"契约已确认"}
    C0 -->|否| C1["拒绝开任务<br/>提示先做项目级定标<br/>wf contract init 然后 approve"]
    C1 --> C2["wf contract init<br/>生成契约草案"]
    C2 --> C3(["人逐项确认后<br/>wf contract approve"])
    C3 --> C0
    C0 -->|是| C{"需要开新任务"}
    C -->|是| D["wf task new<br/>调用 task.py create<br/>参数 workflow=wf，base-branch=当前分支"]
    C -->|否，继续已有任务| E

    D --> S0[("task.json<br/>status=planning")]
    S0 --> E["wf start<br/>调用 task.py start 加 allow-empty-context<br/>再调 task.py set-branch 写当前分支"]

    E --> S1[("status=wf-impl")]
    S1 --> F["人或 AI 实施并提交<br/>检查点提交，不 amend 不 rebase"]
    F --> G{"实现完成，可以声明了"}

    G -->|否| F
    G -->|是| H["wf declare<br/>写 status=wf-verify<br/>写 meta.wf.impl_sha 为当前 HEAD"]
    H --> S2[("status=wf-verify<br/>meta.wf.impl_sha")]

    S2 --> I["wf verify --checks lint,test<br/>质量审查仍用上游 trellis-check"]
    I --> J{"有声明，且 impl_sha 等于 HEAD"}
    J -->|否| K["拒绝，要求先 wf declare"] --> H
    J -->|是| L{"--checks 非空"}
    L -->|否| M["拒绝，不许空验证"] --> I
    L -->|是| N{"受管资产被本任务改过"}
    N -->|是| O["拒绝，先单独提交并确认<br/>v20 受管资产隔离"] --> I

    N -->|否| P["跑检查<br/>可选 quasi-clean 级别<br/>用 git worktree 临时检出"]
    P --> Q["写 status=wf-verified<br/>写 meta.wf.verification<br/>字段 sha checks result level at"]
    Q --> S3[("status=wf-verified<br/>meta.wf.verification")]

    S3 --> R{"证据是否有效，即 verification.sha 等于 HEAD"}
    R -->|是| T["模块内终态：已验证<br/>是否落到主干由人手动完成"]
    R -->|HEAD 已前移，验完又改了| U[("证据过期")]
    U --> V["wf state 提示重新 wf declare"] --> H

    T --> W["人自行决定提交，合并，推送<br/>模块不参与不检测"]

    W --> X["wf close，证据有效时才允许"]
    X --> Y{"证据有效且 result 等于 pass"}
    Y -->|否| Z["拒绝归档"] --> R
    Y -->|是| AA["调用 task.py archive<br/>上游写 status=completed 并移目录"]
    AA --> AB["调用 add_session.py<br/>上游写 journal 与 index"]
    AB --> S4[("归档到 tasks/archive 下<br/>meta.wf 原样保留")]
    S4 --> AC(["人：任务结束<br/>长期轨迹为原生 journal 与 Git 历史"])
```

**审查要点（图 1）**

| # | 要审的点 | 方案出处 |
|---|---|---|
| 1 | 模块内终态是 **`wf-verified` + 证据有效**；"落到主干"完全在人手里，模块不判定 | §4.3.3、D20 |
| 2 | 证据过期**不自动重验**，只提示重新 `declare`（决定权留给人） | §4.3.3、P12 |
| 3 | 三个 fail-closed 前置：无声明 / 空检查 / 受管资产被改 | §4.5 |
| 4 | `close` 的门只看证据，**不看"有没有合并"** | §4.7 |
| 5 | 归档由上游完成（写 `completed` 并移目录），模块不改上游行为 | §4.3 注 |
| 6 | **契约未确认时不许开任务**（v20 §6.1/§11.1 的硬前置）；`approve` 必须人执行 | **§4.2.1** |

## 图 2：旁路与恢复（阻塞 / 暂停 / 终止）

```mermaid
flowchart LR
    A[("status 为 wf-impl 或 wf-verify 或 wf-verified")] --> B{"发生什么"}
    B -->|环境阻塞| C["wf bypass block，带 reason"]
    B -->|主动中止| D["wf bypass pause，带 reason"]
    B -->|不再恢复| E["wf bypass terminate，带 reason"]

    C --> C2[("status=wf-blocked<br/>meta.wf.bypass.from_state")]
    D --> D2[("status=wf-paused<br/>meta.wf.bypass.from_state")]
    E --> E2[("status=wf-terminated 终态")]

    C2 --> F["环境恢复后"]
    D2 --> G["决定继续"]

    F --> H["wf bypass resume"]
    G --> H
    H --> I["写 task_resumed<br/>status 回到 from_state"]

    E2 --> J["之后拒绝 declare verify close<br/>除非新建任务"]

    I --> K{"from_state 是哪个节点"}
    K -->|wf-verify 等| L(["回到原节点继续"])
```

**审查要点（图 2）**

| # | 要审的点 | 方案出处 |
|---|---|---|
| 1 | 旁路**不参与**完成判定，也不清零或增加连续失败信号 | §4.5、v20 §5.1.1 |
| 2 | `from_state` 必须记录，否则恢复无落点 | §4.5 |
| 3 | `terminate` 是终态，走**人类专用入口**（TTY 加令牌） | §4.7 |
| 4 | 环境阻塞恢复后**不强制重跑集成链路**（该链路已删除） | D20 |

**审查要点（图 3）**

| # | 要审的点 | 方案出处 |
|---|---|---|
| 1 | 状态与证据都落在**原生 `task.json`**；没有第二套记录存储 | §0.4、V1 |

| 4 | 对上游只做调用：没有 hook 接管，也没有改 `workflow.md` | V5、§4.8 |

## 图 4：升级与拆卸（模块自身生命周期）

```mermaid
flowchart LR
    A(["模块源有新版本"]) --> B["wf upgrade --check<br/>三轴判定与入口状态矩阵"]
    B --> C{"可升级，即无活动任务且无夹生安装"}
    C -->|否| D["给出恢复路径<br/>收口任务，或 wf bypass pause"] --> E(["人处理后再来"])
    C -->|是| F["wf upgrade --plan<br/>列出实际写入清单"]

    F --> G(["人在交互式终端执行<br/>wf upgrade --apply 并给出模块源"])
    G --> H{"验证成功"}
    H -->|否| I["自动回滚到 plan 快照<br/>attempt 记 failed"] --> J(["人排查"])
    H -->|是| K["清除 attempt<br/>跑 wf upgrade --verify 与 wf doctor"]

    K --> L["之后可能发生 trellis update"]
    L --> M["trellis update，config.yaml 冲突选 skip"]
    M --> N["wf doctor<br/>漂移恰好 1 行，且解析到 wf 变体"]
    N -->|否| O["按 plan 预览回放那一行"] --> N
    N -->|是| P(["完成"])

    Q(["决定不再使用模块"]) --> R["wf uninstall"]
    R --> S["删自有路径，还原 config.yaml 那一行<br/>清除 developer 行，task pin 与 AGENTS 段"]
    S --> T["保留 meta.wf 证据与原生 journal"]
    T --> U(["上游流程可继续使用"])
```

**审查要点（图 4）**

| # | 要审的点 | 方案出处 |
|---|---|---|
| 1 | 升级**不自动提交**；`--apply` 必须人在交互式终端执行 | §5.5、§5.3 |
| 2 | 回滚范围等于 `--plan` 的实际写入清单（不再维护第二份手写路径表） | §5.5 |
| 3 | `trellis update` 之后必须跟 `wf doctor`（顺序可恢复，不是无关） | §4.8、§5.4C |
| 4 | 拆卸**保留** `meta.wf.*` 与原生 journal（它们已属项目历史） | §5.7 |

## 与 v20 的对应关系（一眼核对有没有跑偏）

| v20 节点 | 本模块的落点 | 图上位置 |
|---|---|---|
| 项目级**定标** | **有机制**：`.wf/contract.yaml` + `wf contract init/show/approve`；**未确认不许开任务** | 图 1 的 C0–C3 |
| 项目级**设计 / 计划** | **照常做、由人确认**，产物落宿主文档；模块不设机制（无可自动判定的完成态），但**流程上必须执行** | 未画（方案 §4.2.1） |
| 任务级：定标 → 实施 → 验证 → 收口 | `task new` → `start` → `declare/verify` → `close` | 图 1 |
| 完成由可复现证据派生 | `status=wf-verified` 且 `meta.wf.verification.sha == HEAD` | 图 1 的 R 与 T |
| 状态由记录派生 | 状态就在 `task.json.status`（原生字段，全 CLI 可见） | 图 1 |
| 手动只维护旁路 | `wf bypass {block, pause, terminate, resume}` | 图 2 |
| 合入链路（v2） | **由人手动完成**；模块不提供其命令与门禁 | 图 1 的 W |
| 三级验证 | 保留语义、收敛为两档：`in-place` 与 `quasi-clean`（`clean` 属 v6 条件层，届时再加） | 图 1 的 P |
| 有交集与重验分支 | **不存在**（不切分支、不合并） | — |
| 信任根与锚点 | `wf self-hash`、`--from-anchor` 加 blob 哈希断言 | 未画（属验证内部实现） |
| 发布（G-C，v6） | 属条件层：**有真实部署目标时启用**；模块提供 `wf release`，但执行权在人（独立终端） | 未画（P5） |
