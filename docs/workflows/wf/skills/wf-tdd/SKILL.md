# wf-tdd

开关由项目缺省 + 任务取值决定，Plan 末与人批准同批确认。文档/调查类任务用独立可观察产物验证，不人为造失败命令。

**适用性怎么定**：Plan 机读块写可选 `tdd_applicability`（`code` 缺省 / `docs` / `investigation`），它随批准一起被人确认。
取 `docs`/`investigation` 时机制不要求红绿，改要求该对象的每条验收项都有可消费证据（命令通过或人判决定）；
取 `code` 时红绿是硬要求。**判"这个对象算不算代码"是你的判断**，写进块里由人批；机制只核声明与证据形状。

## 做法

1. 先写针对目标行为的断言，运行并确认**因行为缺失**而失败（不是环境启动失败）。
   要让这次失败成为**可消费的红证据**，用 `task-check --run-verification <验证 id>` 跑它：
   该入口只跑这一条、只记一次运行（验证 id + 定义摘要 + 退出码 + 日志），不产生 Check 结论——
   **不必为了留痕提前跑整轮 Check**。
2. 最小实现使其通过；再补边界用例。
3. 把证据写成 `check.tdd_evidence`：`{assertion, red_command_ref, red_reason, green_command_ref, properties}`。
   `red_command_ref` 取那条失败运行的身份（验证 id），绿仍取**最终 Check** 里同一验证的通过运行。
4. `properties` 逐项说明：可红、确定性、快速、可无人执行。

## 不做

- 不把开关当全局强制，也不按任务类型自行开启。
- 不用生成测试凑数；不伪造红/绿运行记录。
  这不算违反：真实的红运行（`red_command_ref` 指向真实失败）正是证据的一部分；开关关闭或文档/调查类任务按独立可观察产物验证。

## 纪律

- 运行纪律见 `.wf/workflows/session-flow.md`「运行约定」：身份只经信封或宿主映射通道；不代人作答；入口输出是唯一判定源；解释器整会话固定、失效即停。
