## 0. 为什么这样设计（自我诊断）

| 观察 | 数据 | 证据强度 |
|---|---|---|
| **协议与状态是主要成本来源** | 4 次报告格式返工、2 次死路（两轮用尽）、2 次身份错配、2 次外来改动阻断、1 次归档编排失败；8 轮里 8 次人工转述"已在其他 agent 完成" | **客观可证**（次数、位置、耗时都能从记录复算） |
| **规则数量的增长缺少证据需求** | 61 条方案缺陷 / 50 项决策 / 40 条用例，而实际发生的失败类型只有上表那几类；规则大多在防"可能发生"的情形 | **可证**（每条规则都能问"它防的失败实际发生过吗"） |
| **模型的判断质量** | 8 轮 40 条 findings 中只有 1 条 blocking、39 条 suggestion | **不能用作证据**——severity 与 class 都是模型自己给的，用它们证明"模型判断准"是自证 |
| 用户的主观反馈 | "机械僵硬""为什么不执行修正操作""不需要这么机械" | 方向性证据，不构成量化结论 |

**结论（如实表述）**：**框架管事实、AI 管判断、人管取舍**这个方向成立，依据是"协议/状态失败客观可证 + 规则增长缺少证据需求 + 用户反馈"，**不是**"模型判断几乎没出错"。后者尚未被测量。

**收敛判据（v42 记录）**：v38（净删三处） → v39（零新增，只定一处口径） → v40（修规则冲突，未加机制） → v41/v42（固化防线、补两处边界）——**连续四轮没有任何新的"必须这样做"的规则进入内核**。若后续某轮再次出现"新增机制"，先按 §7.1 的两个问题自检：它防的失败现在由谁覆盖？那个覆盖在什么场景失效？答不出来就不加。

**§0.2 验证计划（试点期的质量评估手段，默认不进长期工作流）**

- **定位**：抽样只回答"这类判断最近有没有明显出错"，**不证明整体判断质量**；护栏降级按类进行。**试点期手段**——试点结束按结论决定"保留 / 只抽低频高危类 / 取消"，由**人**判定（门槛自动给建议，见末条）。
- **何时抽**：固定在 `archive` 前最后一次收工预览。**进入收工流程时框架先冻结事实骨架并持久化随机种子**（`seed` 写入**任务记录（committed）**——种子只占几字节，写运行态会让"当时抽的是哪条"无法复算，防操纵论证链断一环）——**冻结的是事件集，不是判断集（v28）**：漏报补写可以继续新增 judgment，但骨架事件与种子已固定，**选样结果不变**。选样用 `sha256(seed + 类名 + 序号)`，**结果可复算、AI 无法通过后续改动影响抽中哪一条**（冻结前新增的改动本身是事实，会出现在归属/规模判断里）。
- **抽什么（候选来自事实骨架，不来自 AI 的 judgments）**：归属←`changed_paths`、关闭←`closures`、沿用←`drift_diffs` 及其报告、扩面←`fix_scope`、标准变更←`standard_changes`、缺口←`class=requirement-gap` 的 findings、未核实←`unverified[]`、规模←`cumulative`。**AI 只解释事件，不能决定事件是否进池。**
- **每任务固定预算 2 条，不叠加（v34）**：无论有多少类处于强化抽样期，**每任务仍只抽 2 条**——强化类只提高**被选中优先级**，不追加条数。否则几个局部失误会堆成一轮大量人工复核。
- **抽哪两类（v27 明确到可唯一复算）**：
  1. **第 1 条**：给"最高危类"（**强化抽样期内的类在同级中优先**）——看**收尾时仍 open 的 `blocking`**：存在则"关闭"类第一；否则 标准变更 > 扩面 > 关闭 > 其余（同级按该类历史失败记录排序）。该类内按 `sha256(seed+类名+0)` 取事件。
  2. **第 2 条（v40 统一规则）**：**不排除第 1 条的类别**——两条各自按优先级链选，**只要求事件不同**。取值顺序：① 若存在「尚未履行的强化义务」（见下「强制占位」），第 2 条**先履行它**（取该类的**另一个**事件）；② 否则按 `sha256(seed+"class-2") % 本任务有事件的类数` 选类，再按 `sha256(seed+类名+1)` 取事件；③ 若取到与第 1 条相同的事件，序号 +1 顺延取下一个（同类不同事件合法）。
  3. **为什么不再「排除同类」**：当收尾有 open blocking 且强化类恰是「关闭」时，「第 1 条关闭 + 第 2 条排除关闭」会让强化义务无处落地——两条规则互相锁死。改为「只要求事件不同」后两条都能落地，总预算仍是 2 条。
  4. **预览先声明**：进入收工预览时即输出"本次抽哪两类、为什么（哪条规则命中）"，让人知道这次会看什么——防操纵靠确定性而非保密（公式与优先级本来就公开可复算）。
- **抽到"无判断"＝漏报失败**：骨架事件存在但该类下没有对应判断 → 记失败，消耗该类额度。**恢复路径**：AI 补写**两条** judgment——① `kind=漏报说明`（basis 写遗漏原因，引用被漏的骨架事件）；② `kind=<该类>` 的新判断。两条带 `backfill: true`、**不用 `supersedes`**、预览标 `[补]`——清单能看出"这里是补的"，历史不被重述。**原失败记录保留**；人只复核补写，不重做整轮；补写不阻断归档，失败仍计入该类计数；人若驳回补写，按 `challenged.rejected` 处理。**不合并成一条**（合并会把"遗漏原因"与"判断"混在一起）。
- **补写复核上限（v37 统一）**：**每任务补写复核 ≤2 条（即 1 类漏报）**；超出部分**按"二次失败"处理，但处置与第二层一致——记失败 + 交根因说明 + 由人裁**（不是自动升内核）。理由：一个任务漏报 3 类以上确实说明判断体系可能失灵，但"是否加约束"始终是人做的决定。
- **缺席**：某类本任务没有事件 → 标"本任务未覆盖"，不消耗额度（不清零、不计入"无失败"）。
- **怎么评**：`结论`（对/错）× `依据`（充分/不充分）二维；依据不充分即使结论对也计入失败侧。
- **降级门槛**：按类计数，**连续 5 个任务（该类样本 ≥10）无失败**才可把该类从指引降为"可选"；任一次失败即重置该类计数。
- **"回补"的两层定义（v27 修订第一层）**：
  - **首次失败 → 该类进入"强化抽样期"**，**而不是把该类每条判断都升级给人**（避免因一条失误把整类变成人工审批）。**额度口径（v37）**：强化期**不追加条数**——每任务仍是固定 **2 条总预算**，框架在"本任务待强化类"之间分配（优先给处于强化期且该类有事件的类别），因此不存在"每类各 2 条"。
  - **强制占位（v37/v42）**：强化类在**进入强化期后的下一个"该类有事件"的任务**，**强制占第 1 条（仅那一次）**——一次性插队，不是持续占位。**触发条件（v42 收紧）**：只在该任务**存在"尚未被抽过的该类事件"**时触发；若该类只有一个事件且已被第 1 条抽走，标「**无可履行事件**」、**顺延到下一个任务**，**不重复抽同一事件，也不阻塞归档**。**例外优先**：若该任务收尾存在 open `blocking`，"关闭"类仍占第 1 条（blocking 是当下正在流血的伤口，强化类是慢病），该强化类的强制占位**由第 2 条承接**——即那个任务的第 2 条直接给该强化类的**另一个事件**（v40，与上面的统一规则一致；不追加预算、不无限顺延）。
  - **期满前置条件（v28）**：强化抽样期的结束**以"人声明已看过预览"为前置**——这是一个**人的声明**，框架**不机械检测**（不追踪界面停留、翻页、点击）。只有"任务收工"不算期满；**未声明则顺延**到下一次声明为止。人可能自欺说看过了——**这没有办法，这是其本人的选择**，框架不替人承担这个判断（与"人不重复点头"同一条取舍的另一面）。期满后自动恢复常规抽样，并**在预览显式写出"该类强化抽样期已结束"**。
  - **同类第二次失败 → 先写"重复模式 + 根因"，由人裁（v34）**：AI 必须说明两次失败是否同一缺陷、根因是什么；**升内核是人做的决定**（选项：升内核 / 继续强化抽样 / 撤销该类监督），不再是机械触发——否则不同问题会被一并固化成强制规则，重回规则膨胀。
- **低频类不凑样本、不降级**：长期低频（一年两三次）就永远达不到 10 个样本——**这是默认安全位，不是待解决的问题**；禁止为凑样本制造该类事件，也**不做"跨任务累积补足 1 条"**（v34：没有事件就没有可复核对象，这是事实；风险由第二层兜底）。
- **试点结束视图**：`wf sampling report` 一屏输出按类的"样本数 / 失败数 / 连续无失败任务数 / 当前层级（指引/可选/内核）"；门槛命中时给建议，**最终由人判定**。**样本不足必须显式提示（v34）**：每行附"样本 N<10，门槛未激活"——否则"未命中"会被读成"没问题"。
- **首个任务只抽 1 条（v35 修正 v34）**：首任务**抽 1 条**：优先「关闭类」，**若本任务没有关闭事件则改抽「归属类」**（归属是每个任务必然存在的判断类型，正好覆盖「首次交付面」这个最易错的点），不做满 2 条——首任务无基线、最易出错，完全不抽等于把最危险的一次放在无人复核里；同时避免与"首任务必确认"叠成过重的一屏（确认行为会让后续抽样"一路点对"）。从第二个任务起恢复 2 条。
- **实现降级路径（v42）**：若"一次性强制占位"在实现中难以稳定执行（例如事件池与强化期状态耦合出歧义），**允许直接删去占位**，只保留「每任务固定 2 条 + 风险优先级 + 人评」——**不再增加新状态**。这条是给实现留的退路，不是给设计留的漏洞：删掉占位只会让强化期回到"可能抽不到"，而第二层（二次失败 → 写根因 → 人裁）仍在。
- **成本**：约 2 分钟/任务（试点期，不含首任务）。

## 2. 三条原则与一条授权边界

1. **框架只约束事实**：身份、状态、内容身份、证据存在性、不可逆动作、**审查独立性的主体关系**。
2. **判断归 AI**：够不够、算不算、要不要修、影响多大、值不值得扩面——由 AI 判断，但必须留下依据。
3. **一切判断可见**：收工时一屏"本任务的判断清单"，人只看这个。
4. **核心平台中立**：流程、判据、记录格式在运行期**不按平台分枝**（设计稿：「运行期不得分平台维护多套流程」「不搬 hooks、平台矩阵或分发 CLI」）。平台差异只允许出现在**安装期部署表**与**宿主适配层**两处；适配层只做「把上下文映射成请求」，不承载业务判定，也不因平台不同而改门禁。

**授权边界**：**一次任务批准 = 在批准范围内持续修改、运行验证、迭代的授权**。框架不再逐次确认工作树改动。只有这些动作要一次确认：

1. 提交 / 推送；
2. 删除数据；
3. 外发内容；
4. **越出批准面的修改**——AI 可以自主判断"需要扩面"并**提出**（4.4），但**修改发生在确认之后**：判断权不等于先改后补；
5. **仓库级规则文件的修改**（`.gitignore`、依赖清单、锁文件、CI/工具链配置）——改一次就改变所有后续任务的环境，集合由 `protocol` 声明。

标准本身的变更按 4.5 处理（说明改的是尺子还是判断）。

对前九版的处置：**保留**机械内核（§3）；**降级**为指引（§4）；**删除**判断替身规则（§7 对照表）。

## 3. 机械内核（10 条机制；K3 含 2 个子句、K4 含 3 个子句）

每条都回答同一个问题：**为什么不能交给判断。**

| # | 机制 | 为什么必须机械 | 规则 |
|---|---|---|---|
| K1 | 会话标识 | 不可观察：`/clear` 不换进程，模型无法自证"我是新会话" | 四档来源（DSH env / host hook / 祖先 cmdline / 无→terminal）；多源冲突不猜，问人一次并钉住 |
| K2 | 租约与写权 | 跨会话推导：谁持有写权必须由记录决定 | 写命令只作用于租约任务；接管 bump generation，旧持有者下次写入即失效 |
| K3a | revision 与 check 锚点 | 不可观察：内容是否变过 | 内容摘要 → revision；报告锚点必须等于当前 revision |
| K3b | 标准域锚定（本轮补回，解 a.2/b.3） | 不可观察 + 事实可判：标准集合变没变是纯事实 | 锚点同时绑定 `assertions_digest`；不符 → 报告被标记 `standard_drift` 并列出差异。**框架不替 AI 判决后果**：沿用/重发由 AI 判断并记录（4.7），**AI 判断不了 → `escalated` 交人**；框架保证两条机械事实——① 带 drift 且没有对应 judgment 的报告**不能产出 pass**；**若该 drift 来自 `broken-reference` 纠错，且报告锚点指向被纠错的 check，则该报告不得产出任何 verdict（含"沿用"）**，只能重发——理由是可判的事实：旧验证从未成功执行，"沿用"等于沿用一个未被验证支撑的结论；**锚点不指向该 check 的报告**（只引用了同一条规则、结论不依赖该验证）按 4.7 正常三条路处理；**一份报告有多个锚点时，只要有一个指向被纠错 check 就整份重发**（一个 verdict 由多项证据共同支撑，坏一条即塌；不引入"部分沿用"）。② 判"沿用"时 `evidence_refs` 必须包含漂移差异里的**具体位置**（`d:` 后可写 hunk / 字段路径 / 行号，只校验该位置存在于本次 `drift_diffs`），否则视为未判断。**digest 只算实质字段**：验收项 `statement`/`severity`/`verify.{kind,refs,covers,judged_by,env}`、spec 规则 `check`，**以及每个 `refs` 指向的验证定义本身的规范摘要（argv/cwd/inputs）**——命令或参数变了，标准的含义就变了。排版不计入；**`clauses[]` 计入（v20 修正）**——它可承载判定条件，若排除在外就会成为"第二套可改而不触发漂移的标准"。**写法约束（v21）**：clauses 只增不改——语义变化必须新建条目并把旧条置 `status=deprecated`（不得原地改字）；digest 只算 `status=active` 的条目。**阅读约定（v22）**：材料与预览只显示 active 条目全文，并提示"（N 条历史修订已折叠）"；`d:` 只能引用 active 条目（引用 deprecated 会被"位置不存在"拒绝）。**摘要规范**：每条 deprecated 在 frontmatter 保留一行 `deprecated_summary: <≤80 字符>`（新建条目时写入，`lint` 校验长度与必填；**v34**：lint 提示建议模板「旧条件一句；停用原因一句」，不强制格式）——一行摘要够追溯，又不把旧条件全文塞回阅读面。这类差异是否影响沿用由 AI 判断。**digest 清单的完整性由协议测试保证**：`protocol` 给每个字段标记 `affects_meaning`，测试逐一变更"影响含义"的字段并断言 digest 必变、变更"不影响含义"的字段并断言 digest 不变——新增字段漏标会直接红。blocking 引用的标准必须存在于**当前批准集合或活动 spec**（解 b.1-2） |
| K4a | 报告不可覆盖 | 不可逆：改一份已发布的审查结论等于改历史 | 同路径不同摘要即拒绝；修订只能出新文件/新轮次 |
| K4b | 关闭复核不得自证（本轮补回，解 b.1-1） | 事实可判 + 独立性前提：谁提的、谁复核的 | 关闭某条 finding 的复核，**不得由提出该 finding 的报告给出**；单 reviewer 场景退回人确认。**"不处置"不构成关闭**（v22）：blocking 无处置即 `unaddressed_blocking` 阻断项，只能走 resolved / reclassification / abandon |
| K4c | 规则不得自证（本轮新增，解 b.2） | 事实可判：这条规则是不是本轮写的 | 本任务内新增/修改的 spec 规则，**不得在同一次审查里充当 `assertion_ref`**——先经一轮独立可见，才能成为判据。**纠错豁免（v18）**：若修改只涉及 `check` 的机械纠错（旧 check 引用的路径/命令在当前环境**不存在**，机械可判）且声明 `check_fix_kind=broken-reference`，**不触发**本禁令；涉及 `statement` 或 `check` 语义变化（`semantic`）才触发。**判据不放宽（v19）**：子命令、参数、cwd 写错但路径存在，一律算 `semantic`——代价是多一轮审查（放宽到"必然失败"需要真跑一次旧命令，有副作用且慢）。**与 K3b 的协同（v20）**：`broken-reference` 豁免让规则可继续当判据，但引用该规则的**在途报告必须重发**（K3b 的纠错型 drift 不得沿用）——否则"省掉的一轮"会以"给每份报告补一条沿用判断"的形式回来 |
| K5 | vendor 边界 | 自指：框架既是工具又是被审对象时，规则会被自己改 | `.wf/**` 不进交付面、不进审查、不进业务提交；改动只记 `vendor_dirty` |
| K6 | 不可逆动作 | 不可逆：提交、删除、外发 | 仅这五类要一次显式确认并绑定变化摘要：① 提交/推送；② 删除数据；③ 外发内容；④ **越出批准面的修改（先确认后改）**；⑤ **仓库级规则文件**——初始集合 `{ .gitignore, 依赖清单（pyproject/requirements/package.json）, 锁文件, CI 配置, 工具链配置 }`，由 protocol 声明并**随 dogfood 增补**（判据：改了会影响所有后续任务的行为环境）。**批准范围内的普通修改与验证不再确认**（见 §2 授权边界） |
| K7 | 归档提交编排 | 不可逆 + 时序：谁先提交、提交哪些路径 | 入口计算三段（业务/记录/运行态）并逐段回报，失败给恢复点 |
| K8 | 投影可重建 | 一致性：本地缓存与事实漂移后无法区分 | `open-items`、`attribution_index`、判断清单的**事实骨架**均可删除并由记录重建，`--check` 断言等值 |
| K9 | 审计线索 | 事后追责 | 记录写链 + 链头锚定提交 trailer；**承诺只到"局部损坏/提交后改写可检出"** |
| K10 | 状态与出口 | 协议：machine-readable 的状态、错误码、出口 | 阶段只有 `plan/execute/fixing/finish` + 终态；每个拒绝至少一条可执行出口；**被驳回未处置的判断由框架列出并计数**；AI 只能 `resolved`（撤销/重做），**`waived` 只能由人给出**；**`escalated` 只阻断"最终结论与归档"**——相关判定挂起、报告照常导入、其余工作不受阻，直到人回答（见 5.4） |

**这 10 条之外，没有"必须由 AI 这样判断"的规则。** 但有一层**支撑面**（§3.5）——它不是门禁，而是让判断可执行、可审计的基础设施（材料怎么生成、报告写成什么、决定文件怎么收尾、提交怎么分三段）。支撑面同样只处理事实与格式，不替 AI 判断。

### 3.5 支撑面（13 条：机械，但不是门禁）

这些是让判断**可执行、可审计**的基础设施。它们只处理事实与格式，不判断"够不够/算不算"。v10 压缩时曾把它们一并删掉，导致若干原始问题失去落点（见 §12），v29 补回。

| # | 支撑 | 内容 |
|---|---|---|
| S1 | **交付面定义** | `object_set = owned ∩ (approved_glob ∪ fix_scope) − vendor − control`；变更种类：新增/修改/删除（前像摘要）/移动（配对）/权限/符号链接（拒绝）/生成物（须声明）。Check、材料、提交三处共用同一个函数 |
| S2 | **材料生成** | `materials/{diff.patch, prd.md, check.json, tests.json, assertions.json, open-findings.json}`；按 object_set 生成（含未跟踪、排除 vendor/控制记录）；`assertions.json` 带验收项 id/statement/`covers`、spec 规则 `check`、可引用契约条款 |
| S3 | **报告协议** | 头部状态行 + 五轴结论（`pass`/`fail`/`uncovered`）+ `findings[]`（`class`/`severity`/`assertion_ref`/`location`）+ `recheck[]`；`wf lint report` **一次列全**（命名/头部/轴枚举/引用存在/`d:` 位置/`backfill` 标记）。**判定句（v30 写死 B1 的边界）**：`verdict=fail` **仅当**存在 `severity=blocking` 的 finding；`uncovered` 轴**不等于 fail**，它产生"缺口"（走 4.8），不产生缺陷 |
| S4 | **decide 三态** | `invalid`（输入不成立：缺报告/锚点失配/格式/人数/依据不全 → **不改阶段、不产 verdict**，给补齐出口）/ `fail`（→ `fixing`）/ `pass`（→ `finish`）/ `unavailable`（异常归档）。**意义：协议错误不被当成业务缺陷** |
| S5 | **阶段与转移** | `plan → execute → fixing → finish`；`task-check` 通过产生 revision；**内容变化或 review 判 fail 进入 `fixing`**，由下一次 `task-check` 退出。**意义：审查失败不再需要 replan/approve** |
| S6 | **收敛谓词（单一定义）** | `done ⇔ check.pass(当前 revision) ∧ round(state=pass, revision=当前) ∧ ∄blocking∧open ∧ 全部 finding 已处置 ∧ 累积变更已确认 ∧ 无 required 未结案 ∧ 提交已授权`。SKILL 与门禁共用这一句 |
| S7 | **证据生命周期（两层半；脱敏为单向不变量）** | ① **授权/不可逆动作的确认原件 → committed，但必须脱敏**：保留 `{动作类型, 路径清单或变化摘要, 决策取值, 时间, 人, quote 摘要}`，**敏感原文（外发内容、删除清单明细、凭据类上下文）留 runtime**；脱敏后仍可复算——用 digest 对照而非原文比对。**脱敏是单向不变量（v36）**：只允许加严、不允许放松；放松需按「改不变量」走人审，不能作为普通配置修改；② 其余决定文件=输入通道：原件入 `.wf/.runtime/`，规范化内容进记录；③ 报告入库（committed）；材料与日志入 runtime；④ 脱敏与体积上限（密钥/URL 凭据遮罩、日志截断标记与上限）；⑤ 记录内保留 digest 与要点 |
| S8 | **验证结案** | `wf verify resolve`（含 `--kind inspection`）；`unverified[]` 为事件源、`open-items` 为可重建投影；required 未结案阻断收工 |
| S9 | **到位状态** | `wf review-status`：本轮已到 n/2、缺哪份、文件状态（不存在/未 done/stale）——人不必再当传声筒 |
| S10 | **三层存放与托管** | committed（`task.json`+任务文档+每轮报告）/ runtime（材料、日志、决定原件、投影、偏好）/ 记录内摘要；`.gitignore` 托管段 `/.wf/.runtime/`、`/.wf/session-bindings/`、`/.wf/writer.json`、`/.wf/.cache/`、`/.wf-lock`；归档三段提交（业务/记录/运行态）。**注（v37）**：K6 五类授权确认原件位于**任务目录（committed 层）**，路径与上述忽略项不重叠，**不在忽略清单内**——实现时不得因"运行态不入库"的直觉把它一并忽略 |
| S11 | **命名与技术标识** | 三层分离：显示名（中文）/ 源树目录（英文 `wf`）/ 技术标识（`wf`、`.wf/`、`wf-*` 不动）；脚本与测试从清单取路径，不硬编码中文绝对路径 |
| S12 | **平台知识只许出现在两处（口径 A，已定稿）** | 设计稿原文：「其可读 skill 根由该 CLI 在**目标项目内**的约定目录确定（各 CLI 的项目内目录表**由实现方案固定**，默认共享根为 `.agents/skills/`）…**运行期不得分平台维护多套流程**」，且「**不搬 hooks、平台矩阵或分发 CLI**」。**定稿口径**：① 平台→技能根是**实现方案的部署表**（不是核心协议）：`dsh` / `codex` / `zcode` / `pi` / `cursor` / `geminicli` / `copilot` 读共享根 `.agents/skills`（`zcode`、`pi` 为**用户声明**，行内必带 `source: official-docs|user-declared`），`claudecode` 读 `.claude/skills`；② 宿主配置落点表**从 `cli.py` 迁到适配层**，语义层不再出现平台矩阵，互斥检查改为读适配层声明；③ **未知平台 / 未知宿主一律不猜、也不硬拒**：走「适用性未知 → `WF_SEMANTIC_DECISION`」交人裁决，同时给 `--skill-root <相对路径>`（人声明目录，记入安装记录）与 `--platform none`（只装运行时、不投放技能）两条出口；④ **不同根的自有副本共享同一逻辑来源与版本，不得发展不同平台的流程或门禁规则**；⑤ **wf 本身不安装任何宿主 hook**——互斥检查是"读配置判断是否存在冲突"，不是"适配 hook" |

## 4. 判断指引（十条，SKILL 形态）

统一格式：**目标 / 你要判断什么 / 留下什么依据 / 人怎么挑战 / 本项目反例**。写进 SKILL 与 `wf help`，每条 ≤15 行，**不写进代码**。

### 4.1 交付面：哪些文件算"这次任务的交付"

- **目标**：交付面 = 我真正改的东西。多算＝把别人的工作提交了；少算＝漏审自己的交付。
- **你要判断**：逐路径归属（我改的 / 不确定 / 别人的）；"不确定"必须给理由。
- **留下**：路径清单 + 不确定项 + 理由。框架给信号（开工快照、提交 trailer、他人 WIP 声明、并发租约），**信号是输入，不是判决**。
- **人怎么挑战**：「这几条为什么算你的？如果我不认，会不会漏掉你自己的交付？」
- **本项目反例**：`.unipi/config/settings-version.json` 与 `.gitignore` 被框架判成"其他任务的改动"，连续阻断两次 Check——框架把归属当判决。

### 4.2 blocking 的关闭：这个缺陷真的修了吗

- **目标**：关闭证据必须能**指回那个问题**，不能拿"某条宽标准通过了"搪塞。
- **你要判断**：用哪条证据、它为什么覆盖该问题。
- **留下**：可点开的引用（验证 id + 位置：文件/符号/章节）。框架只核对"引用存在、指向内容确实变了、验证确实通过、复核人不是提出者（K4b）"，不判断"是否真修好"。
- **人怎么挑战**：「这条测试/这段改动，和这个问题是怎么对上的？」
- **本项目反例**：第 4 轮唯一那条 blocking，evidence 里只写了"PRD a5 未变"（自由文本）。

### 4.3 影响面：这个缺口能不能"接受风险"

- **目标**：影响用户验收、安全、数据完整性的缺口，不能被一次"我接受风险"掩盖。
- **你要判断**：谁受影响、什么后果、是否可回退；建议（补计划 / 接受 / 异常归档）。
- **与 4.9 的边界（v29 修冲突）**：这里的"接受"**不能覆盖 `required` 验收项**——required 只能按 4.9 收窄口径或异常归档；对 required 的"接受风险"不是选项。
- **留下**：影响说明 + 检索范围。
- **人怎么挑战**：「这个缺口影响谁？接受之后出问题谁负责？」
- **本项目反例**：归档把"Windows/macOS 未验证"与"日志截断可读性"混在同一句"未核实项"里。

### 4.4 扩面：修复需要碰批准面之外的文件

- **目标**：扩面必须与已发现的问题相关；不能借"修 bug"把范围滚大。
- **你要判断**：每条新路径对应哪个问题、为什么非改不可；总量是否该回计划重批。
- **留下**：路径→问题映射 + 总量。
- **顺序**：判断"需要扩面" → 提出 → 人确认 → **才修改**。越界修改属 K6 第五类动作，不能先改后补授权。
- **人怎么挑战**：「这些新文件是哪条问题逼出来的？总量是不是该回计划？」
- **本项目反例**：每轮修框架都靠 `task-replan` 扩触碰面，人每次只看到"这一批"。

### 4.5 标准变更：改的是"尺子"还是"判断"

- **目标**：不能用改标准来消除违反。
- **你要判断**：改的是验收标准/spec 规则本身，还是对判断的修正；受影响的未关闭项如何处理。
- **留下**：新旧差异摘要 + 受影响未关闭项清单。
- **人怎么挑战**：「这次是标准写错了，还是你在绕开它？」
- **本项目反例**：a5 在第 3→4 轮被收窄（"仅首轮匹配"）又回退，当时的 blocking 正是针对它。

### 4.6 变化规模：这次改了多少

- **目标**：范围与体量的变化要被人**一次看见**。
- **你要判断**：本次变化多大、是否需要人确认。
- **留下**：变化摘要（新增/删除/移动、净增删行、扩面条目、与批准面偏离）+ 一次确认覆盖所有需要确认的量。
- **事实托底（本轮新增，解 b §11#2）**：框架机械记录**自上次人确认以来的累计量**，并在预览中与"本项目历史上确认过的最大规模"对比；超出历史最大值时高亮。**不设绝对阈值**（200/800 全部删除），也不把防线全押在自觉上。
- **同类任务**：按**触碰面目录重叠度**（Jaccard）取重叠度最高的最近一次任务；重叠不足时视为"无同类"，差异段显示"无对照"。
- **首个任务**：项目第一个任务收工时必确认一次（成本一次，同时给"历史最大规模"建立初始锚；否则相对线在前几个任务里空转）。
- **人怎么挑战**：「这次一共动了多少？为什么不需要我看？」
- **本项目反例**：批准被拆成"规划批准 / 摘要重批 / 基线提案批准 / 收工确认"多段。

### 4.7 报告是否还有效

- **目标**：报告必须对应当前内容与当前标准。
- **你要判断**：内容或标准变了之后，旧报告还能不能代表现在。
- **三条路**：① **沿用**（说明为什么变更不影响该结论）；② **重发**（说明为什么影响）；③ **`escalated` 交人**（你判断不了时的默认出口——例如"标准漂移只影响一个我不知道业务上重不重要的子句"）。
- **留下**：判断 + 依据。内容与标准两个 digest 由 K3a/K3b 机械算出并列出差异；**框架不判决后果**，只保证"带 `standard_drift` 且没有 judgment 的报告不能产出 pass"。
- **判"沿用"必须点名位置（v15）**：`evidence_refs` 里要包含漂移差异中的具体位置，并说明为什么该处变化不影响结论。凡不引用具体位置的"沿用"一律视为未判断。
- **单一形态（v38 简化）**：`d:` 指**漂移差异中的一个具体位置**——hunk、字段路径（如 `d:a5#covers`）、行号都是合法形态，**按漂移的实际形态选精度**，不先判断"这是结构化还是文本"再套格式（那正是 dogfood 里格式返工的认知负担）。原先的"双层粒度 + 字段封闭清单 + 粒度 lint"三层机件一并删除：空引已由"位置必须存在于 `drift_diffs`"覆盖，粒度选择本就是判断。
- **框架只核对位置存在**：你引的 `d:` 必须在本次 `drift_diffs` 里；**位置是否与结论相关由人复核**（v39 已裁决：不设机械判据；人看 `basis` 与引用的对应即可判断）。
- **例外：纠错型漂移不给"沿用"这条路（v20/v21）**：若漂移来自 `broken-reference` 纠错（旧验证从未成功执行），**锚点指向被纠错 check 的报告**只能重发——这不是判断分歧，是证据不存在。三条路对这类报告退化为两条（重发 / escalated）。**其余报告**（引用了同一条规则但结论不依赖该验证）仍可正常沿用，但须引用 `d:` 并说明"该纠错不影响本结论"。判据是 check-anchor 绑定关系，机械可判。
- **不逼你算**：传递 digest 会把"改一下测试命令"放大成"全部在途报告漂移"——这种连锁后果**不需要你在机械层面判断**，按上面三条路走即可，判断不了就 `escalated`。
- **人怎么挑战**：「内容/标准变了，这份报告为什么还算数？」
- **本项目反例**：第 5 轮 pass 后改了代码，第 6 轮靠临时发明 `review-reauthorize` 才继续。

### 4.8 标准缺失：计划没写到的要求

- **目标**：计划没覆盖的真实缺口要被人看见。
- **你要判断**：检索了哪些标准、为什么认为没有覆盖、影响多大、建议补计划还是接受。
- **留下**：检索范围（标准 id 列表）+ 影响说明 + 建议。
- **人怎么挑战**：「你查了哪些标准就说没有？影响有多大？」
- **本项目反例**：多条框架缺陷（如审查材料漏未跟踪文件）没有任何验收项覆盖，以 suggestion 出现、靠人追问才落地。

### 4.9 未核实项

- **目标**：不能宣称"通过"却带着没人管的未核实项。
- **你要判断**：哪些验收项本机不可验证、影响多大、能否收窄口径、由谁在什么条件下补验。
- **留下**：清单 + 建议。
- **收窄验收的依据（本轮明确，解 a.4）**：收窄必须同时给出 ① 被收窄/去除的验收项 id；② 不可验证的客观原因（缺少什么环境/测量手段）；③ 影响面与被放弃的保障；④ 补偿措施（替代验证、人工核验、下游任务跟进）。这四项缺一，收窄不予接受。
- **人怎么挑战**：「这条没验证就归档，出问题怎么办？」
- **硬规则**：`required` 项**不得**以"接受风险"结案——只能收窄（按上述四项）或异常归档。
- **本项目反例**：基线写"CPU≤5%、RSS≤100MiB、跨三平台"，本机根本验不了，最终靠人判 passed 过关。

---

### 4.10 与用户限制冲突时：停下报告，不自行取舍

- **目标**：用户的明确限制（"别动 `.wf/`""不要提交""先别装依赖"）与流程要求冲突时，**不能靠自作聪明绕过，也不能默默违反**。
- **你要判断**：这是"流程必须做"还是"可以换一种做法"；能否在不违反限制的前提下达成目的。
- **留下**：冲突点（哪条限制 vs 哪个流程步骤）+ 你选的做法（换路 / 停做）+ 影响。
- **人怎么挑战**：「你为什么要绕？绕了之后我能知道吗？」
- **红线**：不得为了让流程通过而**修改限制本身**，也不得**隐瞒**冲突（例如把"没做"写成"做了"）。冲突无法调和时**停下并报告**，这是合法终态，不是失败。

## 5. 判断清单与收工预览

### 5.1 结构：事实骨架由框架生成，语义由 AI 填

```text
# 框架自动汇总（事实，不可由 AI 编造；AI 也不用手工维护）
judgment_skeleton = {
  changed_paths[], excluded_paths[],          # 变更与排除
  repo_rule_files[],                          # 仓库级规则文件（.gitignore/依赖/锁/CI）——预览单列
  findings[{id, severity, class}],            # 报告里的 findings
  closures[{finding_id, cited_verification, recheck_by}],
  fix_scope[], standard_changes[{id, old_digest, new_digest}],
  drift_diffs[{id: "d:…", where, before, after}],   # where = hunk（文本）或 验收项id#字段（结构化）
  verifications[{id, result}],                # 本次实际跑过的验证
  cumulative{since_last_authorized},          # 累计量（4.6 用）
  rejected_unresolved[{judgment_at, kind, decision}],   # 被驳回且未处置的判断
  unaddressed_findings[{finding_id, severity, reason?}], # reviewer 报了但无处置动作；reason 由 AI 的判断补（v21）
  waived_count                                # 本任务 waived 条数（只能由人给出）
}

# AI 的判断（只填语义与取舍；只增不撤）
judgments[] = {
  at, kind, decision, basis,
  evidence_refs[],        # 必须是骨架里的 id（v:… / f:… / p:path@digest），不接受自由路径
  outcome,                # applied | escalated
  escalated_question?,    # outcome=escalated 时必填：你判断不了的那个具体问题
  supersedes?,            # 更正先前判断时指向旧条目（旧条目保留，不删除）
  backfill?,              # 抽样漏报后的补写（true；补写是"漏报说明 + 新判断"两条，不用 supersedes）
  by?,                    # ai | human：人声明（如"已看过预览"）也进清单，作一类可审计判断（v34）
  impact?, challenged?
}

# 人的偏好（项目级，机器本地；不设则默认「AI 先判、判不了再升级」）
judgment_prefs = { kind: ask_always | ai_decides }
}
```

- 骨架由 K8 保证可重建：删掉也能从记录重算。
- **骨架同时是抽样池（v22）**：§0.2 的样本从这里的**事件**里选，不由 AI 的 `judgments[]` 决定——AI 只解释事件，事件本身由事实产生。
- AI 只回答"这些事实意味着什么、我认为哪些不确定"。
- **预览必须显式列出计数**：`归属判断：12 路径 / 不确定 0`——"0" 本身要显示，把"没写不确定项"从沉默变成显式断言（解 a.3）。
- **引用从事实派生（解 a.3）**：预览中的引用由框架从记录生成（revision / 验证结果 / 变更路径及其摘要），AI 只能**选用**这些 id 并解释为什么支持自己的判断；不在骨架里的引用一律拒绝。

### 5.2 只记三类（防止变成新的 32 个 JSON）

1. **改变了结果**：让某事通过/不通过、纳入/排除、作废/沿用；
2. **需要人复核**：影响面、扩面、标准变更、规模、不可验证项；
3. **推翻了自己先前的判断**：前后不一致必须留痕。

其余（措辞、命名、注释写法）不记。**骨架仍然完整**，所以"漏记"最多影响解释质量，不会影响事实可见性。

```text
           ↑ 以上只是提示，不算分、不设阈值；是否退步由你看下面的新旧依据对照
[依据对照] 关闭依据（直接读归档记录，不摘要化）：
           上次 basis 全文：…（v1 全量通过，覆盖 notify.py；复核人 zcode）
           本次 basis 全文：…（v1 全量通过，覆盖 notify.py#covers；复核人 dsh）
           refs：上次 [v:20261108-a1…, p:notify.py@3f2a] → 本次 [v:20261108-c9…, d:notify.py#covers]
```

- `wf status` 常驻：`pending_judgments=7, needs_review=2, rejected_unresolved=0`。
- 被驳回未处置的判断会列在预览里，并在 `wf status` 计数（`rejected_unresolved`）。AI 只能走 `resolved`（撤销/重做并更新 judgment）；若它认为无需处置，只能提 `waive_requested`，**由你在预览里确认后才算 waived**——你的明确异议不会被 AI 一句话带过。

### 5.4 与框架检查的关系

- 框架**不**判断 `decision` 对不对；只核对三件事：`evidence_refs` 是否属于骨架派生集合、是否指向当前 revision、`challenged.rejected` 是否已处理。
- 人挑战后写 `challenged = {by, at, conclusion: accepted|rejected|amended, note}`。`rejected` 时 **AI 只能做 `resolved`**（撤销/重做并更新 judgment）；若 AI 认为无需处置，只能提出 `waive_requested`，**由人在收工预览里确认后才记为 `waived`**（`waived_by: human, at, reason`）。**AI 不能自行豁免人的明确异议**；既无 resolved 也无 waived 的条目留在 `rejected_unresolved` 并在预览单列。
- **人的声明也进清单，但只作字段（v37）**：例如"我已看过预览"记一条 `by=human` 的 judgment，**归入其语义对应的既有类**（预览确认→该声明相关的判断类；quote 确认→授权类），**不新增"人的声明"这第十类**——类别枚举膨胀会拖累抽样分类与预览分组，字段标记已足够审计。
- **升级（escalated）**：AI 判断不了时写 `outcome=escalated` + 一个具体问题；该判断所依赖的动作**暂停**，在预览中列为"需你回答"。人回答后写回 `challenged`，判断转为 `applied`。这是"先交 AI、再交人"的固定顺序：**不因为条款难以机械判定就默认卡住，也不因为 AI 想省事就跳过判据**。
- **升级偏好（v15）**：`judgment_prefs[kind]` 两种取值——`ask_always`（该类型一律升级给人，用在你不想被代判的地方）、`ai_decides`（该类型由 AI 定，不得升级）。默认未设时按"AI 先判、判不了再升级"。若某类型设了 `ai_decides` 而 AI 认为问题实质已超出该类型，仍可升级，但**必须写 `why`（为什么判断不了）**；`pref_kind` 退化为可选标注、不做机械校验（v38）——原先的校验会制造"填错字段 → 升级被拒 → 判断退回 applied"的死角，与"偏好不是封条"自相矛盾。**偏好是减少反复升级的开关，不是禁止求助的封条**。
- **只增不撤（本轮新增，解 b §11③）**：`judgments[]` 是 append-only——更正只能新增条目并用 `supersedes` 指向旧条目，**任何条目不得删除或修改 `decision` 字段**。这样"AI 不再报告某类判断"会表现为条目缺失，而不是记录被抹掉；判断质量的跨任务差异也才有稳定基线。
- **判断质量对照是提示，不是分数（v18）**：每次收工把本次 `judgments[]` 与"上次同类任务"（重叠度最高者，数值照实显示）做差异，列出**类别增减、依据变弱条数、`waived`/`escalated`/「结构化差异只引 hunk」三类计数**，并给出**新旧依据并列对照**。**不计算分数、不设阈值、不据此自动判定"退步"**——是否退步由人看对照决定。
- **未处置的 finding 必须有理由（v21）**：`unaddressed_findings` 是纯事实（reviewer 报了、无任何处置动作），但**每条都要有一条对应的 judgment** 说明"为什么不处置"。缺理由的条目在预览中标 `缺理由`——否则这个字段只暴露"遗漏"，暴露不了"决策"。
- **三路职责分界（v22）**：`unaddressed+理由` 只对 `severity=suggestion` 合法。**blocking finding 没有任何处置动作 = 阻断项 `unaddressed_blocking`**，在预览强制单列，出口只有既有三条正路：`resolved`（按 K4b 由非提出者复核）/ `reclassification`（人确认）/ `task-abandon`。**"不处置"不是"关闭"**，不能用来绕开 K4b。
- **偏好可见（v18/v20）**：`judgment_prefs` 是机器本地（不入库），`wf status` 常驻显示当前生效偏好。缺失提示**只在"项目历史上有过偏好、本机缺失"时出现**（"历史上是否有过"从归档任务记录里查，可计算）——全新机器首次使用本就该回落默认，提示无信息量。

- 机制层**写死断言**；判断层**不写死行为断言**，改为保存 `judgments[]` 快照并做差异评审（差异自动进收工预览，见 5.3 末行）。
- **测试元规则（v38/v40）**：每条机制测试必须能回答「它防的失败实际发生过、或可具体推演吗」；答不出来的删除，而不是留着「以防万一」。**豁免**：已修好的历史缺陷对应的回归测试可答「发生过但已修复」，以 `defect id` 标注即可保留（否则「防回归」的测试会被误删）。理由与 §0 第二行同构——规则/测试的增长本身要有证据需求（v26→v37 从 59 涨到 76 条，其中约 15 条在测"防操纵的机制"而非产品问题，已按此规则回落）。

| **"引用标准属当前批准集合"（v9 第 4 条）** | **补回为 K3b** | 纯 id 校验，无判断 |
| **标准漂移的后果** | 框架只标 `standard_drift`；沿用/重发由 AI 判断，判断不了 `escalated` 交人 | 事实（变没变）机械，后果（还能不能用）是判断 |

| **`ai_decides` 下越界升级** | 必须写 `why`（为什么判断不了）；`pref_kind` 可选、不校验（v38） | 偏好是开关；原校验会造成「填错 → 求助被拒」 |
| **K4c 的粒度** | 收窄为"被修改的字段"：`check` 机械纠错不触发，语义变化才触发 | 纠错与改法是可区分的事实，与 4.5 同构 |
| **`escalated` 的阻断范围** | 只挂起最终结论与归档，不冻结中途动作 | 避免"判断不了"变成流程冻结 |
| **偏好与判断质量对照** | 偏好进 `status` 常驻（缺失提示只在"历史有过"时）；对照显示 basis 全文 + refs，不算分 | 丢失要可见；质量判断权归人 |
| **`clauses` 与 digest** | **纳入 digest**（v20 修正 v13 的判断）；**只增不改**，digest 只算 active（v21） | v13 的前提"实质约束由 statement 承载"不成立；只增不改让"改措辞"与"改条件"可区分 |
| **未处置 finding** | 骨架记 `unaddressed_findings`，**每条须有不处置理由**（v21）；**只对 suggestion 合法，blocking 无处置即阻断项**（v22） | 三路职责分界；"不处置"不能绕开 K4b 的非提出者复核 |
| **抽样候选集** | 由**事实骨架**生成，不由 AI 的 judgments 决定；低频高危类优先，出现 blocking 时关闭类第一 | 否则 AI 可通过增减 judgments 间接操纵抽样 |
| **抽到"无判断"** | 记漏报失败 + **补写判断、保留原记录、人只复核补写**（v24） | 漏报是要抓的失败模式，但不能把一次遗漏变成流程死路 |
| **"回补"** | 两层：首次 → **该类强化抽样期**（每任务 2 条，以**人声明看过预览**为结束前置，不机械检测）；二次 → 指引升内核（v27/v28） | 逐项升级会把一条失误放大为整类审批；回补效力以人的接触为前提，但"是否真看了"不代其判断 |
| **v10 压缩时误删的支撑面** | **v29 补回 §3.5 十一条**（交付面/材料/报告协议/三态/阶段转移/收敛谓词/证据生命周期/验证结案/到位状态/三层存放/命名） | 这些不是判断，是让判断可执行、可审计的基础设施；连同它们一起删掉会让原始问题失去落点 |
| **授权确认原件的层** | committed（v34）+ **强制脱敏**（v35），其余决定文件仍走 runtime | 授权是不可逆动作的绑定凭证；脱敏后仍可用 digest 复算，敏感原文不入库 |
| **执行器指纹判据** | 版本 + 路径身份为主，`size/mtime` 后备（v34） | 原判据会把正常升级当漂移，又会漏掉同版本替换 |
| **脱敏口径** | 升为**单向不变量**：只可加严（v36） | 脱敏错了同时造成泄露与无法复算，不能当普通配置改 |
| **强化期监督空窗** | 强化类在下一个"有该类事件"的任务**强制占 1 条（仅一次）**，遇 open blocking 顺延（v37） | 只提优先级 + 预算固定 + 低频，会让强化期实际零样本 |
| **二次失败的处置** | 统一为"记失败 + 写根因 + 人裁"（v37） | 自动升内核会把不同问题固化成同一条规则 |
| **`d:` 粒度体系** | **简化**：单一形态（hunk/字段/行号均可），删字段封闭清单与粒度 lint（v38） | 粒度是判断；空引已由"位置存在"覆盖 |
| **抽样去重重选** | **删除**该分支，允许第 2 条与第 1 条同类（v38） | 低概率分支，删掉不减覆盖力 |
| **`overrun` 校验** | 只要求 `why`；`pref_kind` 降为可选（v38） | 原校验会制造"填错 → 求助被拒"的死角 |
| **漏报补写** | 「漏报说明 + 新判断」两条、带 `backfill`、不用 `supersedes`、预览标 `[补]`（v25） | 补的是空位不是覆盖；清单要能看出"这是补的" |
| **抽样时点与类优先级** | 固定在 archive 前；第一类看**收尾仍 open 的 blocking**（v24） | 避免早期误报与"高频 blocking 项目只测关闭类" |
| **低频类** | 不凑样本、不降级，保持指引级 | 默认安全位，不是缺陷；同时堵住"为了降级刷类" |
| **抽样复核** | 框架确定性选取 + 类别轮换 + 二维评分 + 按类连续 5 任务门槛 | N=2 不能作为删护栏的许可；AI 挑样本会挑稳的 |
| **`escalated` 门槛** | 不设机械门槛；人可按类型设 `ask_always` / `ai_decides` 偏好 | 反复升级用"偏好开关"解决，而不是靠规则拦 |
| **被驳回判断的处置**（v11 的 K10 硬阻断） | **事实列出；AI 只能 resolved，`waived` 由人给出** | 存在未处置项是事实；人的明确异议不能被 AI 单方覆盖 |
| **K4c 规则不得自证** | 新增 | "立法与执法同体"是独立性事实，与 K4b 同源 |
| **K6 第五类：仓库级规则文件** | 新增 | 改一次影响所有后续任务，属影响面越界 |

## 10. 风险与对价

| 风险 | 对价 |
|---|---|
| 判断质量回归 | ① 骨架由事实生成（漏不掉事实）；② 预览强制显示计数（含"不确定 0"）；③ K4b 保证独立性；④ 判断质量差异并入预览常驻段 |
| `judgments[]` 变成负担 | 只记三类；骨架自动生成，AI 只填语义 |
| 授权边界被误解为"不用确认" | §2 明确五类动作仍需确认（提交/删除/外发/越界修改/仓库级规则文件）；K6 与之对齐 |
| 4.6 无绝对阈值 | 用"自上次确认累计量 vs 本项目历史最大值"；项目数据不足时（新项目）退化为"AI 主动提议确认" |
| 收窄验收滥用 | 4.9 四项依据（id/原因/影响/补偿）缺一不可 |
| 归属误收（非 wf 编辑者） | 无机械信号；靠"不确定项"显式（含 0 的显示）+ 人复核 |
| 判断层回归需人看差异 | 明确取舍；差异自动进预览，减少"从不被运行"的概率 |
| K6 第五类增加一次确认（改 `.gitignore` 之类） | 一次确认可覆盖多个规则文件；相比"改坏所有人的环境"，可接受 |
| `escalated` 泛滥（AI 遇事就交人） | 预览单列 + 判断质量段显示 escalated 条数；人可为单类判断设"不必再问"的偏好 |
| AI 每次漂移都判"沿用" | 属判断质量；现在至少必须引用具体位置（`d:`），把"随口沿用"变成"指名道姓"；其余靠 basis + 预览 + 跨任务差异 |
| 偏好设错（把该看的设成 `ai_decides`） | 偏好只是默认开关，AI 越界仍可升级（写 `why` 即可）；预览的 `[偏好]` 行常驻可见，随时可改 |
| 越界升级的 `why` 被写成套话（"情况特殊"） | 无法机械判定质量；靠预览单列 + 人可要求改写；与其余判断同一套治理 |
| `d:` 粒度放松后，可能有人引得很粗（只引文件级） | 有意取舍：粒度是判断，"位置存在"已挡空引；粗引用会在 `basis` 里暴露，由人复核 |
| "模型判断质量"仍未被独立测量（§0.2） | v18 本身作为 dogfood 方案，配人工抽样复核；**抽样不支持就回补护栏**，不靠论证 |
| K4c 的 `broken-reference` 可能被滥用（把语义变化声明成纠错） | 机械证据可查：旧 check 引用的路径/命令必须真的不存在；声明不符即拒绝 |
| 判据不放宽导致"参数写错"也要多跑一轮 | 有意取舍：宁可多一轮，也不引入"真跑旧命令"的副作用与歧义；一轮的代价在原型阶段可接受 |
| 纠错型漂移强制重发，可能一次性废掉多轮在途报告 | 属事实（那些结论本就没有有效验证支撑）；重发成本显性化，比"沿用未验证结论"可接受 |
| 抽样门槛"连续 5 任务"在任务稀疏的项目里推进很慢 | 有意取舍：宁可慢，也不拿 N=2 当许可；项目活跃度低时可把"任务"改成"审查轮次"计数 |
| `clauses` 只增不改会让条目累积（修一次加一条） | 可接受：验收项本来就少，条目数是几十量级；`deprecated` 条目不影响 digest 与 lint |
| 纠错型漂移的"锚点是否指向该 check"判断 | 机械可判（报告 `check-anchor.check_id` 与被纠错 check 的 id 比对），无判断成分 |
| "最高危类"的排序在项目早期无历史失败记录 | 用固定默认序（标准变更 > 扩面 > 关闭 > 其余）；有历史后按实际失败记录排序 |
| `unaddressed_blocking` 可能让任务卡在收工前 | 这正是设计意图（blocking 必须有人参与）；出口三条正路都在既有机制里 |
| 漏报后的"补写"可能变成事后补作业（写一句好听的 basis 交差） | 原失败记录保留；补写必须两条且标 `[补]`；同类二次失败直接升内核——补作业的成本高于当初写 |
| 强化抽样期结束依赖人的声明，人可能自欺说看过了 | 框架不检测（不追踪停留/翻页）；`status` 常驻显示"该类强化抽样期进行中"；这是**明确交给人的取舍**——与"机械僵硬"的病相反的选择 |
| 冻结骨架 + 种子后被抽中的事件正好是"无判断" | 走漏报补写路径（正路），不算作弊；补写仍留 `[补]` 标记 |
| 抽样本身是持续人工成本 | 明确定位为试点期手段，试点结束按结论决定保留/降频/取消；不默认成为长期步骤 |
| 审计承诺有限 | 只承诺"局部损坏/提交后改写可检出" |
| 执行器同版本二进制替换不可检出（v34 判据的代价） | 明确接受：版本+路径身份一致即放行；要抓同版本替换需要内容摘要，代价是每次启动算一次 hash——留作正式化闸门 |
| 授权原件入库会增加提交体积 | 量级 1–3 份/任务、纯文本；相比"授权无法复算"，可接受 |
| 脱敏过度会让授权无法复算 | 口径固定为「保留动作类型/路径或摘要/取值/时间/人/quote 摘要」；**脱敏为单向不变量**（v36）：可加严、不可放松，放松须走改不变量的人审 |
| 首任务单条抽样仍可能漏 | 有意取舍：宁可少抽也不错配成本；首任务的规模必确认仍在，两者互补 |
| 强制占位会挤掉一次其他高危类 | 每类在整个周期最多挤一次；且遇 open blocking 顺延，伤口优先 |
| `waive_requested` 堆积（AI 频繁请求豁免） | 预览单列；`waived` 计数进判断质量段；人可选择只批 resolved 以逼 AI 修 |
| K4b 单 reviewer 退化：人成为事实上的第二 reviewer | 明确取舍：只在降级场景发生；相比"自证关闭"，多一次人确认是可接受代价 |

**正式化闸门**：vendor 摘要硬校验；迁移与 upgrade；协议跨版本兼容；审计与材料保留合规；逐路径显式认领。
