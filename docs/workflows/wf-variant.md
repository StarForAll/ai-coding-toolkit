### 四段结构（设计稿 §4.1）

| 段 | 承载 | 产物 | 出口 | 机制入口 |
|---|---|---|---|---|
| 项目层（一次） | 项目层任务 P | 需求基线、技术基线、任务图、收尾任务定义 | 人确认 + P 正常归档 | `wf task new --role project` 建 P，`wf close` 收 P |
| 任务层（0→1，串行） | 实现任务 | 每个任务自身的需求、设计、计划与代码 | 人判 + 正常归档 | `wf route` 选任务，`wf start` 开工，`wf close` 收尾 |
| 收尾层（一次） | 收尾任务 | 验收、交付物、发布记录、复盘 | 人验收 + 归档 | `wf route` 选中后同样走 `wf start` / `wf close` |
| 持续使用 | 普通任务 | 按需 | 图外走原生流程，图内走机制入口 | 图外：原生 `task.py`；建过边后：`wf …` |

返工与替换/放弃不改这四段：返工任务插在被返工任务之前，是图内普通任务；替换/放弃只改变某个任务及其下游的走法。

### 入口：三段判定（设计稿 §9.1，实现口径见方案 §3.7）

逐段判定、命中即停；`wf route` 的 `segment` / `matched_row` 直接给出命中的是哪一段哪一行。

| 段 | 命中条件（摘要） | 下一步 |
|---|---|---|
| 第一段 全局旁路 | 模块不可用；完整性分流（字段/角色/登记信息非法，类型 4；有未完成返工登记，类型 2；未完成替换/放弃或类型 1 后续处分，类型 5；已归档但账本为无记录或挂起，类型 1）；需要改基线 | 停止普通选择：按输出走 `wf repair`（人类专用）或按设计稿 §9.4 卸载；改基线回设计稿 §5.5，本模块只给指引 |
| 第二段 挂起 | 第一段未命中，且当前任务挂起，或无当前任务但存在挂起任务（按创建时间取最早） | 按 `wf route` 的 `matched_row` 处理：进入返工任务 R、清挂起、逐项分流未完成前置、或 `wf repair` 类型 2 |
| 第三段 非挂起 | 前两段未命中 | 项目层未收尾：只执行 P / 取最早就绪图内任务 / 等前置；已收尾：取最早就绪图内任务（含返工与收尾），无就绪则判收尾是否完成，否则迭代期普通任务 |

### 机制入口（方案 §3.5，全部支持 `--json`）

| 入口 | 类别 | 什么时候用 | 不要做什么 |
|---|---|---|---|
| `wf route`、`wf state`、`wf dag`、`wf check`、`wf doctor`、`wf embed-state` | 只读 | 每次判定之前 | 不要自己按前置集合心算就绪或顺序 |
| `wf task new --role project` | 有副作用 | 启动项目层 | 不要用原生 `task.py create` 建图内任务 |
| `wf task new --from-graph <key>`、`--prereq <id\|slug>`、`--unrelated` | 有副作用 | P 归档后按图建任务、重定义收尾任务、插入图外工作 | 不要早于 P 归档建实现任务；`--from-graph` 必须按拓扑序 |
| `wf start` | 有副作用 | 图内任务开工 | 不要用原生 `task.py start` 开工图内任务 |
| `wf close` | 有副作用 | 图内任务收尾（人判之后） | 不要用原生 `task.py archive` 收尾图内任务 |
| `wf edge add`、`wf edge rm` | 有副作用 | 迭代期调整顺序 | 不要给已归档任务挂前置 |
| `wf rework` | 有副作用 | 任务未归档、发现返工 | 不要自己新建一个任务冒充返工任务 |
| `wf replace`、`wf abandon` | 有副作用 | 任务被取代 / 不再需要 | 实施后不要回退到替换前 |
| `wf baseline --light` | 有副作用 | 基线变了但工作仍成立 | 不要把旧任务直接归档 |
| `wf repair` | 有副作用（**人类专用**） | `wf check` 报出类型 1–5 | 不要手改账本文件 |

两条由机制入口内部承担的约定，不需要也不应该由你直接调用原生命令：`wf start` 固定带
`--allow-empty-context`（本模块不派子代理，上下文清单门没有保护对象）；`wf close` 固定带
`--skip-branch-validation`，且调用前先断言 `pr_url` 为空（单一工作线、不建 PR）。

### 自检与修复（方案 §3.8）

- `wf check` 只读；`wf route` 内部先跑一遍。
- 类型 1–5 的处分只能由人在交互式终端跑 `wf repair`（带令牌）；AI 不得代跑、不得设环境变量绕过。
- 启动自检只识别与报告：除"派生清除挂起"外不写账本、不改任务状态。

### 状态面包屑

[workflow-state:planning]
当前任务处于规划中。先跑 `wf route`（只读）取下一步，再按其 `matched_row` 行动。
建图内任务只用 `wf task new …`；不要用原生 `task.py create` / `task.py start` 代替机制入口。
规划产物落 `prd.md`（复杂任务另加 `design.md` / `implement.md`）；P 还要写任务图块与收尾任务定义。
[/workflow-state:planning]

[workflow-state:in_progress]
当前任务处于进行中。状态以 `wf state` 输出的"任务状态 × 账本状态"为准，不要用任务状态表达依赖状态。
收尾只走 `wf close`（人判之后）；返工走 `wf rework`；替换、放弃与对账修复走 `wf repair`（人类专用）。
前置未全正常时工作不停、只挡收尾：先按 `wf route` 给出的下沉目标开工，完成后回本任务收尾。
[/workflow-state:in_progress]

[workflow-state:completed]
当前任务已归档完成（账本为正常）。本任务不再改动，也不要重开。
下一个任务用 `wf route` 选；`wf` 不可用时按设计稿 §9.4 卸载，不绕过机制继续开工。
[/workflow-state:completed]

### Rules

1. 先 `wf route`，再行动；判据以它的 `segment` / `matched_row` / `next_action` / `why` 为准。
2. 图内任务的开工与收尾只走 `wf start` / `wf close`；原生入口只用于图外任务。
3. 账本（`.trellis/dependencies/ledger.json`）不许手改；修复只走 `wf repair`。
4. 任务状态只有规划中 / 进行中 / 已归档；"等待返工""替换未完成"是账本维度，看 `wf state`。
5. `wf` 不可用 → 按设计稿 §9.4 卸载（默认仅模块卸载），不降级、不绕过。

## Phase 1: Plan

本节 = 设计稿 §4.1 的**项目层**：具体开发代码之前的全部工作，由项目层任务 P 承载。

#### 1.1 立项与基线

- 没有项目层任务时：`wf task new --role project` 建 P。这是唯一不需要已归档 P 的建任务入口。
- 在 P 上写需求基线与技术基线；基线是活的（设计稿 §5.4），后续任务以项目文档与规格为准，不回去翻已归档任务。
- 完成判据：人确认基线"齐"（设计稿 §5.2 的四条）——这是人判，机制只留痕。

#### 1.2 任务图与收尾任务定义

- 在 P 的 `design.md` 写任务图块：每个实现任务的 key、其前置 key、以及收尾任务。
- 图是 DAG（不变量 4）：不得成环、不得引用图外 key、必须有收尾任务。
- 完成判据：`wf dag --check` 无偏差。

#### 1.3 项目层收尾

- 人确认基线齐 → `wf close` 收 P。任务图不齐时机制拒绝收尾，`wf route` 会指出缺什么。
- P 正常归档后，`wf task new --from-graph` 才可用；`0→1` 期间没有当前任务时按第三段"只执行 P"。

#### 1.4 按图建任务

- 按拓扑序逐条 `wf task new --from-graph <key>`；根节点的前置自动取 P 的依赖标识。
- 收尾任务也被重定义或补建时用 `wf task new --prereq <id\|slug> --role tail`。
- 不要一次性跳过中间节点：某 key 的前置尚未建出时，该入口拒绝。

## Phase 2: Execute

本节 = 设计稿 §4.1 的**任务层**（0→1，串行）。图外任务不走本节，按原生流程处理。

#### 2.1 取就绪任务

- 跑 `wf route`：第三段命中"取最早就绪的图内任务"时，按它的 `next_action` 做，不要自行排序。
- 有当前任务且有效 → 继续它，不要把指针换成"看起来更早"的任务。
- 前置没全正常但有该做的任务：按 `wf route` 的下沉目标先开工，完成后回本任务。

#### 2.2 开工

- `wf start`：符合"前置全正常 + 账本无记录"才放行；否则停在规划态并报告原因。
- 图外任务：走原生开工，不受本机制的门禁约束。

#### 2.3 执行与人判

- 按该任务的 `prd.md` / `design.md` / `implement.md` 实施；质量检查仍用基底的 check 环节（`trellis-check`）。
- 人判在 check 之后由人给出：决定是否进入收尾。人判是基底原生环节，不需要额外命令或记录。

#### 2.4 收尾

- 人判通过 → `wf close`：校验源状态（账本无记录 + 前置全正常）→ 归档 → 账本写"正常"。
- 顺序是可见性顺序：归档成功但账本未提交时，下游仍视为未满足；用 `wf state` 看是否"归档待对账"。
- `pr_url` 非空会被拒绝（机制不建 PR，出现值即说明有人走了别的路径）。

#### 2.5 返工

- 任务未归档、发现返工 → `wf rework`：登记、建返工任务 R、发布；T 的账本进入挂起，任务状态不变。
- R 是图内普通任务，按 2.1–2.4 走；R 收尾时按设计稿 §6.4 第 5 步评估能否清挂起，不要手动清。
- 不要在挂起期间把 T 当就绪任务继续；`wf route` 第二段就是为这件事存在的。

## Phase 3: Finish

本节 = 设计稿 §4.1 的**收尾层**（一次）。

#### 3.1 收尾任务

- 收尾任务依赖最后一个实现任务，是图内普通节点，没有额外判定：`wf route` 选中后 `wf start` → 执行 → `wf close`。
- 收尾任务被替换、或放弃后留有继任者时，继任者即收尾对象；放弃且无继任者时由人重新定义（`wf task new --prereq … --role tail`）。

#### 3.2 验收、交付与发布

- 验收由人做；交付物、发布记录与复盘写进收尾任务的产物。
- 推送与发布由人执行，机制不接管，也不参与完成判定。

#### 3.3 项目收尾判定

- 收尾完成（设计稿 §6.7）后，`wf route` 第三段转入"迭代期普通任务"。
- 无收尾对象或尾端异常已到终态：先 `wf check`，再由人用 `wf repair` 重定义收尾，不要新建一个"看起来像收尾"的任务。

## 持续使用

本节 = 设计稿 §4.1 的**第四段**。

#### 4.1 迭代任务

- 与任务图无依赖关系的任务：走原生 Trellis 流程，不适用挂起与前置行。
- 需要参与顺序时，先按 4.2 建边，之后它就成为图内任务，按 Phase 2 的规则走。

#### 4.2 建边与基线变更

- 迭代期建边：两端都在活动区、前置尚未完工 → `wf edge add`；删边用 `wf edge rm`（目标可在归档区）。
- 基线变更（设计稿 §5.5）：工作仍然成立 → `wf baseline --light`（新任务继承旧任务前置，未归档下游默认重连）；
  不再成立 → `wf replace` 或 `wf abandon`。两条路径互斥，由人在发起时选定，实施后只向前完成。
