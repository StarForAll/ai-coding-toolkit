## 缺陷判定边界

这套 workflow 的维护与修复，默认面向**个人正常使用 / 诚实使用路径**。

因此在当前合同里：

- 正常使用路径下会稳定触发、误导、拦错、漏拦、漂移或导致阶段闭环失败的问题，算真实缺陷
- 只有通过刻意篡改文件、故意绕过命令约束、手工伪造状态、主动关闭合同要求的保护面等**恶意绕过**方式才会触发，而正常使用路径下不存在的问题，不按当前 workflow 的漏洞/缺陷处理

换句话说：当前 workflow 不以“对抗恶意操作者”作为默认威胁模型；修复优先级以正常使用链路的真实性、稳定性和可维护性为准。

## 使用前提与安装时序

这套 workflow 的定位一直是：**在目标项目已经具备 Trellis 基线后，再做嵌入和增强**。

还要明确一个运行时边界：当前 workflow 的收尾链路使用 Trellis 原生 `/finish-work`，最终的 `archive` 直接调用目标项目 Trellis 基线里的 `python3 ./.trellis/scripts/task.py archive`。因此，目标项目应优先使用当前最新 Trellis 基线；至少要包含 archive metadata auto-commit 的 pathspec 修复，否则收尾阶段仍可能因为旧基线行为失败。

当前 source repo 中的兼容锚点固定为 `Trellis 0.5.17`。若目标项目 Trellis 基线低于或偏离该锚点，应先完成基线升级，再判断是否允许嵌入当前 workflow。

目标项目若要真正使用这套 workflow，必须同时满足：

- 目标项目本身是一个 Git 项目
- 目标项目的 `origin` 已至少配置两个 push URL（例如 GitHub + Gitee 多 push）
- 目标项目已经执行过 `trellis init`
- 能检测到 `trellis init` 产物，例如 `.trellis/.version`

参考配置命令：

```bash
git remote add origin <你的第一个远程仓库URL>
git remote set-url --add --push origin <第一个仓库URL>
git remote set-url --add --push origin <第二个仓库URL>
```

若 `origin` 已存在，跳过第一条。

如果任一前提不成立，就不应把后续命令、skills、hooks、阶段门禁视为“已经嵌入成功”。

当前 workflow 的嵌入执行必须遵循《[工作流嵌入执行规范](./工作流嵌入执行规范.md)》。

主链只有一条：

1. 目标项目先完成 `trellis init`
2. 先运行 `commands/detect-embed-state.py`，确认目标项目处于 `INITIAL_BASELINE_READY`
3. 再运行 `commands/install-workflow.py --dry-run`，且必须显式传入 `--profile`
4. 再运行正式安装，且必须显式传入同一个 `--profile`
5. 安装器按 Claude Code / OpenCode / Codex 各自官方原生格式，把 workflow 命令、skills、共享 helper 与对应 baseline patch 嵌入到目标项目；`.claude/settings*.json`、可选的 `opencode.json.instructions`、`.codex/hooks.json`、`.codex/hooks/*.py` 等手动维护资产不由安装器分发；对 `.codex/config.toml`，安装器只在文件已存在时追加/修正一条**窄补丁**：将 `features.multi_agent_v2.enabled` 压成 `false`，以落实当前 embedded workflow 的 main-session-only 合同，不接管其他项目级配置字段
6. 安装器自动导入 `pack.requirements-discovery-foundation`；若目标项目存在 `trellis init` 生成的 `00-bootstrap-guidelines`，则一并清理；若遗留的 repo-global `.current-task` 仍指向该 bootstrap task，也会同步做兼容清理；目标项目本就不存在该任务时跳过，`workflow-installed.json` 中的 `bootstrap_task_removed` 字段只记录"本次安装是否实际执行过删除"，`bootstrap_cleanup_status` 提供更细的清理状态（如 `removed` / `absent` / `dry-run-removed`），二者都不等同于"该任务历史上一定存在过"；同时 `initial_pack_cleanup_policy = retain-imported-assets` 明确记录：这批导入的 library 资产默认保留，不在 workflow 卸载时自动删除
   - 清理时机：requirements-foundation 导入完成后、安装记录写入前
   - 清理动作：删除 `.trellis/tasks/00-bootstrap-guidelines/`，并清理所有仍指向该 bootstrap task 的 `.trellis/.current-task` 与 `.trellis/.runtime/sessions/*.json` 引用
7. 正式安装开始后，安装器会先写入 `.trellis/workflow-embed-attempt.json`；只有装后自检通过后，该文件才会被清理
8. 安装完成后，先按《装后隐藏目录与托管边界核对清单》完成装后核对；至少确认 `.trellis/workflow-installed.json`、`.trellis/workflow-embed-attempt.json`、`.trellis/workflow.md`、`.trellis/library-lock.yaml`、`AGENTS.md` managed block、`.agents/skills/` 这个共享 skills 唯一主承载面的状态，以及 `.codex/skills/` 这个 secondary carrier 中是否只保留 Codex 独有 skills
9. 核对通过后，再在目标项目里按对应 CLI 的原生入口使用这套 workflow

### Workflow Commands vs Baseline Commands

当前 workflow 会在目标项目里新增、覆盖或禁用一部分命令。它们不是 Trellis 基线原生命令的一对一复制，而是“基线 + workflow 增强”的合成结果。

| 类别 | 说明 |
|------|------|
| Baseline commands | Trellis 基线已经存在的入口，例如 `continue`、`finish-work`，workflow 只做项目化补丁 |
| Overlay commands | workflow 在目标项目中覆盖的入口，例如 `brainstorm`、`check`，安装后以 workflow 版本为准 |
| Added commands | workflow 新增的入口，例如 `feasibility`、`design`、`plan`、`review-gate`、`project-audit`、`delivery` |
| Disabled commands | workflow 明确禁用的入口，例如 `parallel`，因为它与强门禁的单主线、单 active task、单次确认节奏冲突 |

`trellis-library` 导入的基础 spec pack 与当前 workflow 的关系也是同样的“基础 + 增强”模型：先通过 `trellis-library/cli.py assemble` 导入基础 pack，再由当前 workflow 在目标项目 `.trellis/spec/` 上做项目化完善；安装记录里的 `initial_pack_assets`、`initial_pack_cleanup_policy` 只是记录这次导入与保留策略，不表示用户不能在目标项目继续扩展自己的 spec。

`parallel` 被当前 workflow 明确禁用，是因为强门禁要求单条主线、单个当前 active task、单次确认点推进；后台并行 dispatch / worktree 完成路径会让阶段状态和确认点分裂，容易把“当前已确认阶段”与“后台并行中的候选分支”混在一起。

推荐安装方式：

```bash
WORKFLOW_EMBED_EXECUTOR_CONFIRMED=1 /ops/softwares/python/bin/python3 \
docs/workflows/新项目开发工作流/commands/install-workflow.py \
--project-root <target-project> \
--profile outsourcing
```

如需过滤 CLI：

```bash
WORKFLOW_EMBED_EXECUTOR_CONFIRMED=1 /ops/softwares/python/bin/python3 \
docs/workflows/新项目开发工作流/commands/install-workflow.py \
--project-root <target-project> \
--profile outsourcing \
--cli claude,opencode,codex
```

这里的关键点是：

- 必须先有 `trellis init`，再执行安装脚本
- `--profile` 不能省略；交互环境必须显式选择，非交互环境必须显式传入
- 只有纯净初始态目标项目才允许执行首次嵌入；非初始态一律阻断
- 安装脚本只负责 workflow-managed assets，不负责替项目补建手动维护的 hooks / settings / config
- 安装完成后必须先做装后核对，再视为 workflow 可直接使用

安装完成后，实际交流与执行时仍然可以采用**渐进性披露**：

- 先进入当前阶段
- 再按阶段按需展开对应命令、文档、MCP、skills 和平台配置
- 而不是在单轮上下文里一次性灌入所有材料

也就是说：

- `trellis init -> install-workflow.py -> 装后核对` 是**安装层**
- 安装完成后按阶段逐步展开，是**使用层的渐进性披露**

## 2026 核心方法论升级

> 本文档是 **AI 辅助开发实战工作流**，目标：更快交付、可验证正确、可控成本、可控风险。

### 核心理念升级（2026）

基于 2025 年 AI Coding 领域的实践经验，我们升级以下核心方法论：

#### 1. 规划先行 + 证据门禁

- **所有 AI 参与环节必须先规范后实现**
- 不允许"边想边做"的无序 AI 消耗
- 每个 AI 输出必须有对应的验证证据

#### 2. 先测试后编码

- 践行 **Test-First AI** 原则
- 测试用例是验收标准的客观载体
- AI 生成代码必须通过预先定义的测试集

#### 3. 实现后质量检查

- 引入基于 Trellis 原生 `check` 合并增强后的质量检查机制
- AI 实现后必须对照 spec、验证证据与风险清单完成检查
- 输出结构化检查结果供 `review-gate` / `delivery` / native `finish-work` 快速消费

#### 4. 人类最终责任

- 明确 AI 是"工具"而非"决策者"
- 关键节点必须"人类在环"
- 所有输出的人类最终责任不可转移

### 执行顺序铁律

> 需求冻结 → 意图确认 → 测试设计 → AI 实现 → 质量检查 → 补充审查 / 人工复核 → 证据回归

> **任何跳过验证环节的 AI 执行都是不被允许的**

## MCP / Skills 配置原则（安装完成后的渐进性披露）

这套 workflow 面向 **Claude Code / OpenCode / Codex** 的多 CLI 原生适配模型，而不是单一 CLI 的临时说明。因此，MCP 与 skills 的规则必须同时满足两件事：

1. 让多 CLI 在同一项目里共享一致的能力路由原则
2. 避免把大段平台细节直接塞进默认注入上下文，造成不必要的上下文占用

这里的 **渐进性披露** 专指：**workflow 已经安装到目标项目之后**，在实际使用时如何按阶段按需展开上下文，而不是替代安装动作本身。

默认采用 **渐进性披露**：

| 披露层级 | 主要载体 | 默认是否应进入主上下文 | 负责内容 |
|---------|---------|----------------------|---------|
| 主规则层 | `工作流总纲.md` | 是 | 能力路由原则、配置分层原则、降级与证据边界 |
| 映射层 | `命令映射.md` | 按阶段需要引用 | 阶段 × 场景 × 工具 / skill × 配置层矩阵 |
| 平台展开层 | `commands/claude/README.md` `commands/opencode/README.md` `commands/codex/README.md` | 否，按需查阅 | 各 CLI 的原生配置入口、承载方式、最小验证与注意事项 |

约束：

- 主规则层只保留**最小必要原则**，不内嵌大段平台配置样例
- 长配置示例、平台特有约束、验证命令放到对应平台 README
- 若某条规则只对单一 CLI 生效，不应反向污染所有 CLI 的默认上下文

### 配置分层原则

MCP / skills 的配置与使用，应拆成以下层次：

| 层次 | 典型载体 | 负责内容 |
|------|---------|---------|
| 项目长期稳定规则 | `AGENTS.md` | 证据优先、风险边界、工具优先级、何时必须联网、何时标记 `[Evidence Gap]` |
| workflow 规则与阶段路由 | `工作流总纲.md`、`命令映射.md`、各阶段命令文档 | 在什么阶段、遇到什么问题时应该优先调用哪类能力 |
| CLI 原生配置层 | Claude：`.claude/settings.json` / `.claude/settings.local.json` / `.claude/hooks/`；OpenCode：可选的 `opencode.json.instructions` 与平台原生配置；Codex：`.codex/config.toml` / `.codex/hooks.json` / `.codex/hooks/` / `.agents/skills/`（共享 skills 唯一主承载面，也是当前证据下 Codex 的 repo-scoped skills 主入口） / `.codex/skills/`（仅 Codex 独有或项目自定义 skills 的 secondary carrier） | 把规则真正挂接到对应 CLI：命令、hooks、权限、注入、skills、agents |
| 复用能力资产 | skills、agents、通用脚本 | 浏览器操作、需求评估、计划拆解、多 CLI 审查等可复用能力本身 |

补充边界：

- `.agents/skills/` 不是“所有 CLI 的共享技能目录”
- 当前已确认会受 `.agents/skills/` 影响的是：OpenCode、Codex
- Claude Code 官方技能目录是 `.claude/skills/`；当前没有官方证据表明 Claude Code 会读取 `.agents/skills/`
- 对当前 workflow 来说，OpenCode 的正式主入口仍是 `.opencode/commands/trellis/`；`.agents/skills/` 只表示这些共享 skills 会进入 OpenCode 的可发现范围，不代表它们是推荐或正式入口
- 判断 Claude/OpenCode 的阶段可用性时，必须先看 `.claude/commands/trellis/` / `.opencode/commands/trellis/` 这两个正式入口，再看各自 `skills/` 或 `.agents/skills/` 发现面；不能因为 skill 目录未镜像全部阶段入口就直接判成漏装
- 判断 Codex 的 carrier 完整性时，先看 `.agents/skills/` 主承载面，再看 `.codex/skills/` secondary carrier；缺少 `.codex/commands/` 不构成当前合同下的异常
- `.backup-original/` 在各 carrier 中默认是安装器/升级器保留的恢复面；存在本身不构成 defect，只有活动入口缺失、恢复配对断裂，或备份被误当现行合同，才继续升级处理
- 维护者侧例外：repo-local `workflow-audit` 当前阶段必须在 Claude Code / OpenCode 主会话中执行，不开放 agent 执行口；只有后续明确调整合同后才可放开

### 能力路由基线

以下规则属于**主规则层**，应被各 CLI 共同遵守：

- **代码上下文定位**：优先 `ace.search_context`
- **第三方库 / SDK / 框架官方文档**：优先 `Context7`（`resolve-library-id -> query-docs`）
- **最新信息 / 版本 / 新闻 / 今日或本周类事实**：必须走 live 检索，默认优先级为 `grok-search > exa > 内置 Web tools`
- **浏览器交互 / 页面操作 / 站点探索**：优先 `agent-browser` skill
- **需求模糊 / 增强**：优先 `ace.enhance_prompt`，回退 `sequential-thinking`
- **复杂多步推理（>3步）**：优先 `sequential-thinking`
- **GitHub 项目文档 / 架构理解**：优先 `deepwiki`，回退 `exa_web_search_exa`
- **深度研究 / 竞品分析 / 技术调研**：优先 `exa_web_search_advanced_exa(type=auto)`，回退 `grok-search`
- **知识可视化 / 流程图 / 依赖图**：优先 `markmap`
- **复杂多步问题**：优先结构化思考或分阶段 research，而不是在实现阶段边想边改
- **关键能力不可用**：必须显式写出 `[Evidence Gap]`、已尝试链路、当前降级路径，不能用猜测替代证据

### 配置边界

- workflow 文档负责定义“**应该用什么能力**”与“**能力优先级**”
- 各 CLI 原生配置负责定义“**这些能力如何被挂接、授权、注入和发现**”
- skills / agents 负责承载“**复用能力本身**”，不应把整份 skill 说明复制进阶段命令正文
- 若某能力需要凭据、MCP server 注册或本机权限，配置应留在 CLI 的原生配置面，而不是写进 `AGENTS.md`

## 📋 阶段一：项目可行性评估

### 1.1 合法性审查
- **法律合规性检查**：确认项目在当地法律法规框架下是否合规
- **决策点**：如果不符合法律法规，**终止项目**，不进行任何后续工作

### 1.2 粗略需求沟通
- 与客户进行初步沟通，明确大致需求方向和范围
- 识别核心功能点和技术难点

### 1.3 项目评估与报价
- 工作量评估：功能开发工时 + 评审工时 + 测试工时 + 文档工时
- 时间成本分析：按里程碑拆分，给出最早/最晚交付窗口
- 资源成本核算：人力、技术资源投入成本
- AI相关成本核算：
  - Token成本：纳入项目整体成本规划，合理估算
  - 重试预算：根据功能复杂度预留合理冗余
  - 缓存收益：合理设计前缀以优化成本
  - 评估成本：纳入整体成本规划
- 风险预判：
  - 技术风险、进度风险、依赖风险
  - AI特有风险：幻觉、提示词注入、上下文污染、模型不可用或限流
- 报价输出：给出基础版范围、变更单价规则、交付SLO草案
- 本阶段的时间/报价输出默认是**商务预判**与区间策略，不替代需求澄清后的正式项目级粗估；正式粗估必须在阶段二 `brainstorm` 收口前落盘

#### 1.3.1 进入需求发现前的门禁

- 对于**新项目 / 新客户需求**，在第一次进入当前 workflow 时，必须先完成一次可行性评估。
- 若目标项目是**新建仓库**，在**第一次进入当前 workflow** 时就应先确认本地主分支和初始分支为 `main`；若仓库尚无本地提交历史且当前不在 `main`，先修正分支，再继续 workflow。
- 若目标项目已经存在本地提交历史或已有存量开发内容，则不强制切换成 `main`，但应把当前分支策略作为初始化边界记录清楚。
- 可行性评估应至少产出 `assessment.md`，记录：
  - 总体决策：接 / 谈判后接 / 暂停 / 拒绝
  - 是否可做、是否值得做
  - 关键风险、必须谈判条件、最小补充信息集
  - 是否允许进入 `brainstorm`
- **风险分析执行**：
  - 使用 `/trellis:feasibility` 命令的 `--step risk-analysis` 步骤
  - 使用 Skill 工具执行 `demand-risk-assessment`，完成结构化风险评估
  - 评估流程：结构化抽取 → 踩坑信号扫描 → 冲突检测 → 红线检查 → 结构化评分 → Pre-mortem → 风险登记表 → 决策/谈判条件
  - 将分析结果写入 `assessment.md`，确保包含完整的风险评估结论
- 若结论为 `暂停`，应先补齐缺口后重新执行可行性评估，不应直接进入阶段二。
- 若结论为 `拒绝`，应终止该项目链路，仅保留评估记录。这里的 `拒绝` 指项目级接单/立项决策，不是冻结后变更场景中的”用户不接受并入当前轮次”。
- 只有 `assessment.md` 明确允许进入 `brainstorm`，或存在经确认仍有效且前提未变化的历史评估记录时，才应进入阶段二；这属于复用已完成阶段结果，不属于跳过 feasibility。

> **外包项目专用门禁**：外包、定制开发、新客户项目需要额外的可行性评估字段和交付控制机制，详见《[外包项目扩展](./外包项目扩展.md)》。

### 1.4 项目确认与初始化
- **客户确认继续推进与预算框架**：基于 feasibility 的商务预判，确认是否继续进入需求澄清与正式估算
- **签署合同/协议**：明确双方权责
- **项目级初始化**：
  - 若客户确认继续推进，则先进行项目状态初始化
  - 正式项目级粗估在阶段二 `brainstorm` 收口后补齐，并回写到 `task_dir/prd.md` 与目标项目 `customer-facing-prd.md`
  - 建立项目档案和后续追踪机制
  - 选择合适的AI开发工具链
  - 建立提示词模板库和上下文管理规范
  - 在目标项目根目录初始化 `todo.txt`
    - 默认初始化内容仅一条：`文档内容需要和实际当前的代码同步`
    - 该文件是 install-only 的协作提醒产物，用于记录项目常规定时任务与协作提醒；它不额外改变当前工作流阶段、门禁或命令链路，也不是卸载时必须恢复/清理的目标
    - 若目标项目维护根 `README.md`（默认中文）与 `README.en.md`（英文补充版），可补充说明 `todo.txt` 的存在与用途，避免协作者忽略该约定
  - 若已嵌入对应的自定义工作流，安装脚本应**立即通过脚本导入 `trellis-library` 中的需求发现基础资产**
    - 默认导入：`pack.requirements-discovery-foundation`
    - 导入方式：使用 `trellis-library/cli.py assemble`，不靠人工复制资产或自然语言提示“补装”
    - 导入完成后，若目标项目存在 `trellis init` 创建的 `00-bootstrap-guidelines`，则一并清理；若遗留的 repo-global `.current-task` 仍指向该 bootstrap task，也同步做兼容清理；目标项目本就不存在该任务时跳过
    - 最低要求：至少补齐需求发现核心规范 `problem-definition`、`scope-boundary`、`requirement-clarification`、`acceptance-criteria`，再补齐面向客户与面向开发人员的 PRD 规范、模板、检查清单，以及项目级 `README` 治理规则
    - 其中 `README` 治理规则默认要求：`README.md` 作为默认中文入口；若同时存在 `README.en.md`，任何 README 内容、结构、命令、路径、链接、状态说明变更都必须同步更新两份
    - 目的：在正式进入需求发现前，先建立统一的 PRD 与项目文档约束基线，避免后续只有流程没有规范

当前 workflow 的常规默认值里，作者归属保护继续按启用处理；除非项目明确写 `ownership_proof_required = no`，否则还应在 `assessment.md` 冻结：

- `source_watermark_level`
- `source_watermark_channels`
- `zero_width_watermark_enabled`
- `subtle_code_marker_enabled`
- `ownership_proof_required`

这组字段用于决定后续 design / plan / delivery 是否必须补齐源码水印与归属证明链。
它们适用于**所有项目**，不只适用于外部交付项目；若项目明确设置 `ownership_proof_required = no` 才可跳过。这里只是因为 `assessment.md` 的冻结动作在当前阶段一并说明。

离开 feasibility 前，至少还应形成一份可复核的”阶段出口快照”：

- 哪些字段已经冻结
- 哪些事项必须在 brainstorm 收口前重算
- 哪些前提变化会强制回到 feasibility

若启用了源码水印 / 归属证明链，建议立即执行：

```bash
python3 .trellis/scripts/workflow/ownership-proof-validate.py --phase feasibility --task-dir <task-dir>
```

不要等到 design / plan 再回填这些字段。

> **外包项目专用机制**：外包、定制开发、新客户项目需要额外的开工前置门禁、双轨交付控制、Spec 导入要求等机制，详见《[外包项目扩展](./外包项目扩展.md)》。

> 此阶段体现了”先调研再实现”的方法论，确保项目在启动前已充分评估。

## 🎯 阶段二：需求明确与确认

> **前置条件**：新项目默认已完成阶段一可行性评估，并且 `assessment.md` 明确允许进入需求发现；否则应先回到 `/trellis:feasibility` 补做评估，而不是直接开始 `brainstorm`。不存在按 profile 跳过 feasibility 的首次入口例外。
>
> **外包项目额外要求**：外包/对外交付项目的前置条件和门禁要求详见《[外包项目扩展](./外包项目扩展.md)》。

### 2.1 详细需求分析
- **Task-first**：先确保当前讨论落到 `task_dir/prd.md`，不让需求只停留在对话里
- **Action-before-asking**：先读仓库、文档、现有任务与历史约束，能查不问
- **Research-first**：涉及方案取舍、实现路径或行业约定时，先调研再收敛
- **Diverge → Converge**：先扩展边界、异常路径和演进场景，再收敛到本轮 MVP
- **AI可实现性评估**：评估需求的可 AI 化程度，区分可直接 AI 生成、需要人工设计、需要 RAG 增强、需要 Agent 架构等类型

### 2.1.1 `/trellis:brainstorm` 合并规则

`/trellis:brainstorm` 采用“**Trellis 原生需求发现主链 + 当前 workflow 门禁扩展**”的合并模型。

在生成任何具体任务、子任务或执行安排前，必须先沿用原生 `brainstorm` 的主链完成需求发现，再进入当前 workflow 的统一前置判定，不能直接跳到任务拆解或实现。

前置判定顺序固定为：

1. **先检查 feasibility / assessment 基线是否已满足**
   - 新项目：若缺少有效 `assessment.md`，或当前前提已变化，先回 `/trellis:feasibility`，不允许直接开始 `brainstorm`
   - 所有项目：缺少有效 `assessment.md` 时都不得直接进入 `brainstorm`
   - 若 assessment 仍有效，则复用既有评估结果继续需求发现，不需要重复执行 feasibility
   - **外包项目额外检查**：外包/对外交付项目需要额外检查开工款门禁等条件，详见《[外包项目扩展](./外包项目扩展.md)》

2. **先保证任务与工作底稿存在**
   - 若当前没有任务目录，先创建任务，再种下 `task_dir/prd.md`
   - 若当前已有任务目录，先复用并更新 `prd.md`

3. **先自动收集上下文，不先问低价值问题**
   - 先读取 `assessment.md`、现有 `prd.md` / `task_plan.md` 摘要、已存在的 task / 子任务列表、目标项目 `docs/requirements/*.md`
   - 先做仓库检查、模式对照和必要调研，再决定是否需要问用户
   - 问题只允许是阻塞型或偏好型，而且一次只问一个

4. **需求描述准确性校验**
   - 判断需求目标、范围、验收标准、关键边界是否足够清晰
   - 若仍存在明显歧义、缺失信息或隐含假设未处理，继续停留在 `brainstorm`，不生成具体任务

5. **复杂度统一分类（`L0/L1/L2`）**
   - `L0 简单任务`：需求已准确，当前事项无需继续细分即可达到合适任务粒度，通常只涉及 1-2 个文件或一个明确变更点
   - `L1 标准任务`：需求已准确，但涉及多文件、多步骤或明确依赖，需要进入 `plan` 拆任务
   - `L2 复杂任务`：跨模块、跨层、架构级、高风险或高不确定，需要先发散补充，再拆成多个子任务

6. **是否需要先发散补信息**
   - 若当前边界、相邻流程一致性、历史兼容约束、异常路径或跨层契约会影响拆分方式，先补信息，再进入具体任务生成
   - `L2` 默认必须先发散补充；`L1` 按需进行；`L0` 通常可直接收敛
   - 离开 `brainstorm` 前，至少要再补一次固定横切检查：
     - 是否存在独立 UI / 前端基线 lane
     - 是否存在跨平台 / 分发 / 打包承诺需要前置讨论
     - 是否存在必须提前建立的非功能探针（体积 / 启动时间 / 内存 / 性能）
     - 当前项目级粗估相对 feasibility 是否已经刷新；若没有变化，也必须写清原因
     - 是否已经形成 kill criteria / `P1` 降级候选

7. **是否需要拆 `sub task`**
   - 若当前事项仍需继续细分，才能达到合适的任务粒度，则必须拆成多个可独立验证、可独立收尾的子任务
   - 若当前事项已无需继续细分，且当前粒度已足够支撑单任务闭环，则允许作为单任务继续推进

8. **项目级正式需求文档门禁**
   - 在进入 `design` 之前，必须先在目标项目生成并同步：
     - `docs/requirements/customer-facing-prd.md`
   - 在离开 `brainstorm` 之前，还必须先产出**不可跳过的项目级粗估**：
     - `task_dir/prd.md` 中的 `## 项目级粗估`
     - `docs/requirements/customer-facing-prd.md` 中的 `## 项目级粗估摘要`
   - 若暂时无法给出单点值，也必须给出区间、置信度与适用前提；不得以“后续再估”为由跳过
   - `docs/requirements/developer-facing-prd.md` 不在架构确认前强制生成；它应在 design 阶段的技术架构确认后再正式落盘
   - `task_dir/prd.md` 仅作为当前任务的工作底稿，不可替代项目级正式需求文档
   - `task_dir/prd.md` 在离开 `brainstorm` 前还应补齐 `## 阶段出口快照`，至少记录：
     - `complexity_decision`
     - `ui_lane_decision`
     - `cross_platform_scope`
     - `estimate_refresh_result`
     - `kill_criteria`
     - `open_items`
   - 当前这组字段除 `complexity_decision` 外，主要仍服务于文档留痕、人工复核与 reopen 判断；但 `workflow-state.py` 已会校验它们是否存在且不是明显占位值
   - 当前 workflow 通过 `workflow-state.py validate` 将这条粗估门禁卡在 `design` 及后续阶段入口上；缺失时不得继续推进
  - 后续若命中 [需求变更管理执行卡](./需求变更管理执行卡.md) 且用户接受并入当前轮次，必须同步更新受影响的项目级正式文档
   - 若下一步进入 `design`，则在 `design -> 3.7 技术架构确认后的项目 Spec 对齐` 阶段必须明确项目自动化检查矩阵：采用 Sonar 的项目必须写真实命令，未采用时必须写替代门禁和原因

9. **阶段状态机与强门禁**
   - 当前 workflow 使用 `session-scoped active task -> 当前阶段任务 -> $TASK_DIR/workflow-state.json` 作为唯一阶段判定链
   - 其中 `feasibility` / `brainstorm` / `design` / `plan` 允许 parent coordinator task 持有阶段状态；进入 `implementation` 及其后的执行链前，必须先切到真实 leaf task
   - 每个阶段完成后都必须先进入 `awaiting_user_confirmation`，用户明确确认后才能切到下一阶段
   - `/trellis:continue` 只能重入当前已确认阶段，不能自动跨阶段推进；legacy `/trellis:start` 仅用于旧目标项目兼容

### 2.1.2 单任务单验收口径原则

- 单个上下文只负责一个任务，不允许在一个上下文里并行推进多个任务并混用验收口径。
- 这里描述的是执行阶段的会话隔离约束，不是 `plan` 阶段判断任务粒度的主判据。
- `L0` 任务允许在 `brainstorm` 完成后直接收敛为单任务执行，不强制先生成 `task_plan.md`。
- `L1/L2` 任务在进入实施前，必须先形成明确的拆解结果；其中 `L2` 先补信息，再拆多个子任务。
- 单个任务上下文必须覆盖完整闭环：**代码实现 → 代码检测 → 质量检测 → 代码修复**。
- 当前 workflow 对嵌入后的目标项目显式禁用 `trellis-research -> trellis-implement -> trellis-check` 这条 agent/subagent 执行路径；即使目标项目仍存在这些 Trellis 原生 carrier，也不得派发，research / implement / check 必须由主会话直接完成。
- 其中 `trellis-research` / `trellis-implement` / `trellis-check` 均保持 Trellis 原生基线；当前 workflow 不再额外同步增强版 research 内容。
- 这里的 `trellis-check` 属于 implementation 内部自检 agent，不等于正式 `/trellis:check` 阶段。
- implementation 内部链完成后，只能把 `/trellis:check` 作为候选下一阶段，等待用户明确确认，不得自动切换。

### 2.1.3 历史数据防漂移约束

- 新增规则默认只约束**后续新生成或重新确认的任务**，不回填或重写历史 `prd.md`、历史 `task_plan.md`、历史任务状态枚举和既有审查记录。
- 若旧任务、已冻结需求或已批准计划需要调整范围、拆分方式、验收标准或执行路径，统一走 [需求变更管理执行卡](./需求变更管理执行卡.md)，不允许静默修改历史基线。
- 在生成新任务或子任务前，先检查当前 `prd.md`、`task_creation_checklist.md`、`task_plan.md` 摘要和已存在的 task / 子任务列表；若已存在等价任务，则直接复用，避免重复建任务导致历史数据漂移。

### 2.2 需求说明书编制

#### 2.2.0 项目级正式需求文档落位（强制）

在当前 workflow 中，项目级正式需求文档统一放在目标项目：

```text
docs/requirements/
├── customer-facing-prd.md
└── developer-facing-prd.md
```

说明：

- 这是**新项目开发工作流**对使用方项目的要求，不是当前 workflow 仓库自身必须常驻生成这两份文件
- 当这套 workflow 被嵌入并运行在某个目标项目时，该规则才对目标项目生效

约束：

- `customer-facing-prd.md` 在进入 design 前必须存在
- `customer-facing-prd.md` 在进入 design 前还必须补齐 `## 项目级粗估摘要`
- `developer-facing-prd.md` 在技术架构确认前不强制生成；它应在 design 阶段技术架构确认后再正式落盘
- 两份文档最终覆盖项目中已确认的全部需求功能点
- 客户向与开发向文档的目标、范围、验收、边界含义必须一致
- `task_dir/prd.md` 只承担阶段内澄清与路由判断，不替代上述正式文档
- `task_dir/prd.md` 在离开 brainstorm 前必须补齐 `## 项目级粗估`，否则不得进入 design
- 后续正式需求变更若被用户接受并入当前轮次，必须持续同步回写受影响的正式文档

详细模板、扩展技术文档矩阵和示例正文已拆到
[阶段二：需求文档与变更模板](./阶段二：需求文档与变更模板.md)。
总纲这里只保留必须长期稳定的门禁约束，避免同一模板长期内联后在多处重复维护。

#### 项目级正式需求文档最小内容要求

- 客户版 PRD 必须覆盖：项目规则定义、用户故事、功能边界、验收标准、模糊点澄清记录、冻结与变更约定
- 开发版 PRD 必须覆盖：项目规则定义、模块结构说明、技术方案约束、数据与接口约束、依赖/集成/错误边界、验收标准、AI 实现要求
- 两份正式文档必须表达同一组已确认需求，不允许一份冻结、另一份漂移

#### 2.2.1 技术开发人员扩展文档规则（可选）

- 复杂项目可在 `docs/requirements/developer-facing-prd.md` 之外追加附属技术文档，例如 TAD / DDD / IDD / AID / ODD-dev / ODD-user / `design/STITCH-PROMPT.md` / `design/frontend-ui-spec.md`
- 这些扩展文档是补充材料，不替代开发向需求主文档
- 详细文档体系、依赖关系、维护责任与模板正文见 [阶段二：需求文档与变更模板](./阶段二：需求文档与变更模板.md)

### 2.3 需求确认循环

#### 客户版确认
```
客户版需求说明书 → 客户审核 → 反馈修改 → 再次确认
     ↑                                              ↓
     └───────────── 循环直到完全确认 ←──────────────┘
```
- 仅确认功能描述和验收标准
- 每轮确认结果都要回写 `docs/requirements/customer-facing-prd.md`

#### 开发人员版确认
```
开发版需求说明书 → 技术审核 → 反馈修改 → 再次确认
     ↑                                           ↓
     └───────────── 循环直到完全确认 ←────────────┘
```
- 确认功能 + AI实现方案 + 技术约束
- 每轮确认结果都要回写 `docs/requirements/developer-facing-prd.md`

### 2.4 需求冻结

> **核心原则：冻结的是"业务意图与验收证据"，而非"实现细节"**

#### 冻结对象（明确）

| 冻结内容 | 冻结程度 | 变更方式 |
|---------|---------|---------|
| **业务意图** | 绝对冻结 | 需走完整变更流程 |
| **验收证据** | 绝对冻结 | 需新增证据而非修改 |
| **接口契约** | 绝对冻结 | 需走技术变更评审 |
| ~~Prompt细节~~ | 不冻结 | 可持续优化 |
| ~~模型参数~~ | 不冻结 | 可调优 |

- 冻结对象：
  - 客户版PRD：`docs/requirements/customer-facing-prd.md`（业务范围与验收标准）
  - 开发版需求文档：`docs/requirements/developer-facing-prd.md`（需求实现说明、模块拆解与任务边界、场景/规则/验收映射；接口/数据库正文以跳转链接承接）
  - 评估基线（核心测试集与通过阈值）
- 非冻结对象：
  - Prompt细节、模型参数、工具调用策略允许迭代优化
- 优化前提：
  - 每次Prompt或模型调整必须记录变更原因
  - 必须通过评估基线回归后才能进入下一阶段
  - **Prompt迭代必须在评估基线回归后才能生效，不允许直接上线未评估的Prompt变更**
  - **模型版本升级视同重大变更，需重跑全量评估集**
  - **工具调用策略变更若影响输出格式或接口契约，必须进入2.5变更流程**
- 后续变更：
  - 涉及范围、接口、成本、工期变化时，必须进入2.5变更流程

#### 2.4.1 冻结后的跨阶段分流规则

从需求冻结完成开始，后续任一阶段（设计、计划、测试先行、实施、质量检查、交付）如再次出现需求讨论，先按“澄清 / 变更”分流，不得在当前阶段直接混入处理。

- **纯澄清**：允许留在当前阶段直接处理
  - 前提：不改变范围、接口契约、验收标准、成本、工期
  - 典型情况：解释原有需求含义、补充术语说明、确认已有描述指向什么行为
  - 若当前信息不足、影响仍有灰区，或无法稳定判断是否仍属纯澄清，默认按正式变更处理
- **正式变更**：统一进入 `2.5 需求变更管理`
  - 触发类型：新增需求、修改需求、删除需求
  - 处理要求：先评估影响范围、成本、工期、测试与回归范围；未确认前，不并入当前阶段继续推进

#### 2.4.2 澄清与变更的判定口径

不要按客户是否说出“新增”“修改”字样来判断，而按影响来判断。

只要命中以下任一项，就视为正式变更：

- 功能范围发生变化
- 页面或业务流程行为发生变化
- 接口契约或数据契约发生变化
- 验收标准或测试证据发生变化
- 成本发生变化
- 工期或里程碑发生变化

只有在**不改变**上述六项时，才可视为“纯澄清”，留在当前阶段处理。

#### 2.4.3 典型口语触发示例

以下口语表达，若发生在需求冻结后，默认按正式变更处理：

- “这个功能再加一个”
- “这个页面流程我要改一下”
- “这个接口字段得调整”
- “这个验收标准我想改”
- “这个功能先不做了”

以下口语表达，若不改变范围和验收，可按纯澄清处理：

- “这里我确认一下是什么意思”
- “这个描述对应的是不是原来那个流程”
- “我不是加功能，只是想确认你理解的是否和我一致”

#### 2.4.4 冻结后变更的执行出口

- 当前阶段的责任是**识别并中断**，而不是直接吸收正式变更继续推进
- 若判断为正式变更，先执行 `2.5 需求变更管理`
- 若用户接受并入当前轮次，再回到**受影响的最早阶段**继续，例如：
  - 影响业务范围或验收标准：回到需求/设计层
  - 影响任务拆解、排期、测试范围：回到计划或测试先行
  - 仅在用户接受并入当前轮次后影响实现与验证：回到实施或后续验证阶段

#### 2.4.5 AI 意图映射确认

在需求冻结前，增加"AI 意图映射确认"循环：

```
AI 意图映射流程：

① 需求冻结触发
    └── 开发者将客户需求输入 AI

② AI 生成结构化意图列表
    └── 格式：
    - 用户故事 → 核心意图 → 关键约束 → 验收证据

    示例：
    | 用户故事 | 核心意图 | 关键约束 | 验收证据 |
    |---------|---------|---------|---------|
    | 作为用户，我希望能... | 实现xxx功能 | 响应时间<200ms | 性能测试通过 |

③ 开发者复核
    └── 核对 AI 理解与客户描述是否一致
    └── 标记潜在误解或假设

④ 客户签字确认
    └── 客户确认意图理解正确
    └── 确认后纳入冻结范围

⑤ 后续争议仲裁
    └── 如实现过程中出现理解偏差
    └── 以 Intent.md 中签字确认的意图为准
```

> 这一阶段体现了"证据优先"和充分调研的原则，为后续工作奠定基础。

### 2.5 需求变更管理

当客户在需求冻结后提出新增需求、修改需求或删除需求时，需要通过规范化的变更管理流程进行处理。纯澄清若不改变范围、接口契约、验收标准、成本、工期，可留在当前阶段直接处理，不必升级为正式变更；若无法稳定判断，则默认按正式变更处理。

#### 2.5.1 变更类型定义

| 变更类型 | 定义 | 示例 |
|---------|------|------|
| **新增需求** | 在原有需求基础上增加全新的功能模块 | 增加用户评论功能、增加支付方式 |
| **修改需求** | 对已确认的需求内容进行修改 | 修改登录流程、调整页面布局 |
| **删除需求** | 移除已确认的需求功能 | 取消某个不需要的功能 |
| **需求澄清** | 对已有需求的模糊部分进行澄清 | 明确某个功能的详细行为 |

#### 2.5.2 变更影响评估（重大变更可选）

> 本节仅适用于**重大变更**（通常 >2 人天、改接口、改验收标准或明显影响排期）。轻微和一般变更默认走 `§2.5.3` 的轻量闭环。

重大变更建议至少回答这四类问题：

| 评估维度 | 需要回答的问题 |
|---------|-------------|
| **功能影响** | 影响哪些页面、流程、模块或接口？ |
| **技术影响** | 需要改哪些代码或结构？是否有明显技术风险？ |
| **测试影响** | 需要新增/修改哪些测试？回归范围多大？ |
| **项目影响** | 预计增加多少工时？是否影响当前里程碑、费用或交付节奏？ |

如项目明显依赖 AI 资产，可额外备注 Prompt、评估基线或上下文是否需要重建，但默认不要求单独维护一套 AI 系数表。

评估结论统一收敛为：**是否收费 / 用户是否接受 / 是否并入当前轮次**。

#### 2.5.3 变更处理流程

变更处理只保留一个核心闭环：**估价 → 确认 → 并入或忽略 → 验证**。

**核心流程（所有正式变更必走）**：

```text
① 估价
   └── 给出时间、费用、是否影响当前交付，以及是否收费的快速判断

② 确认
   └── 客户选择：
       接受并并入当前轮次 / 不接受，本轮忽略

③ 并入或忽略
   └── 接受时并入当前轮次；不接受时维持冻结基线，不混入当前交付

④ 验证
   └── 对已并入的变更完成必要验证与回归，再由客户确认
```

**按级别路由**：

| 变更级别 | 估价范围 | 流程路由 |
|---------|---------|---------|
| **轻微** | ≤0.5天 | 走完①②③④，口头确认即可，事后补一行记录 |
| **一般** | 0.5-2天 | 走完①②③④，使用**轻量变更单**（§2.5.5） |
| **重大** | >2天 或明显影响接口/验收/排期 | 走完①②③④，补充 **§2.5.2 影响评估**，并使用**完整变更单**（§2.5.5）或等效书面记录 |
| **紧急** | 不限 | 先止血，24小时内补齐①②③④记录 |

> 所有正式变更建议保留文字记录（微信/邮件/变更单均可），避免口头约定产生歧义。

**变更流程结束后的返回原则**：

- **用户不接受**：保持当前阶段冻结基线，不把变更混入当前交付，并按当前轮次忽略
- **用户接受并入当前轮次**：回到受影响的最早阶段，更新 PRD / 设计 / 计划 / 测试 / 实施基线后，再恢复主链路

#### 2.5.4 变更估价参考（可选）

快速估价的目标是**尽快报出可执行判断**，不是制造一套看起来精确但难以落地的计算公式。

建议按这个顺序估：

1. 先估算新增或返工的**基准工时**
2. 再判断当前阶段的**返工成本**（越晚提出，通常越贵）
3. 再判断是否存在**跨模块 / 跨层连锁影响**
4. 最后补上**测试与回归成本**

对外通常只需要明确三件事：

- 预计新增工期
- 预计新增费用
- 是否影响当前交付版本

> 如果短时间内无法给出精确数值，可以先给**区间报价**，不要为了“看起来专业”强行套复杂系数。

#### 2.5.5 变更单模板

个人开发或小团队场景，默认只保留两档模板：**轻量版（默认）** 和 **完整版（重大变更可选）**。

完整 Markdown 模板已拆到 [阶段二：需求文档与变更模板](./阶段二：需求文档与变更模板.md)。

**适用规则**：

| 场景 | 使用模板 |
|------|---------|
| 纯澄清 | 只需记录“客户诉求 + 我方理解 + 判定结果” |
| 一般正式变更 | 轻量变更单 |
| 重大正式变更 | 完整变更单 + §2.5.2 影响评估 |

#### 2.5.6 项目级需求文档更新规范（推荐执行细则）

用户接受并入当前轮次并执行后，按以下规范更新项目级双需求文档：

- `docs/requirements/customer-facing-prd.md`
- `docs/requirements/developer-facing-prd.md`

同步要求：

- 两份文档必须描述同一组已确认需求，禁止只更新其中一份导致语义漂移
- 客户向文档更新业务可见变化、范围边界、验收影响
- 开发向文档同步更新实现约束、接口/数据契约、测试与风险信息
- 若当前执行任务仍依赖 `task_dir/prd.md` 作为上下文依据，也应同步修正，但它不是正式项目基线

**版本号规则**
- 格式：`v主版本.次版本.修订号`
- 变更类型对应：
  - 新增/修改需求 → 次版本 +1（如 `v1.2.0 → v1.3.0`）
  - 需求澄清/错误修正 → 修订号 +1（如 `v1.2.0 → v1.2.1`）

**变更标记规范**
- 在 PRD 末尾新增“变更记录”章节
- 每次变更添加一行记录：

| 版本 | 日期 | 变更单号 | 变更内容摘要 | 变更人 |
|------|------|---------|-------------|--------|
| v1.3.0 | 2024-03-20 | CHANGE-003 | 增加订单导出功能 | 张三 |

- 在正文中用高亮标记变更部分：
  > [变更v1.3.0] 新增订单导出功能，支持 Excel 格式下载

**历史版本保留**
- 保留最近 3 个版本的正式需求文档文件
- 命名格式示例：
  - `customer-facing-prd-v1.3.0-2024-03-20.md`
  - `developer-facing-prd-v1.3.0-2024-03-20.md`
- 归档位置：`/docs/requirements/history/`

#### 2.5.7 对客沟通要点（简版）

冻结后谈变更，重点不是“强调收费”，而是守住三个目标：

- 本轮交付边界不被悄悄改写
- 客户知道“不是不能改，而是先评估再决定”
- 流程透明，可选择，不靠临时口头承诺推进

建议只保留三条表达原则：

- **先接住诉求，再判定澄清还是正式变更**
- **先说明不直接混入当前交付，再谈时间和费用**
- **给客户明确选项：本轮不动 / 接受后并入本轮并调整排期与费用**

推荐短话术：

> 这个想法可以做。为了不影响当前已经确认的交付，我先把它按正式变更评估一下，给你时间、费用和是否影响本轮排期的判断；你接受后，我再并入当前轮次执行。

---

> 版本历史按**实际变更落地时间**记录，不按版本号大小排序；因此后续补记的 `0.x` 版本可能出现在更早定义的 `1.x` 版本之后。

### 3.1 UI/UX设计

#### 3.1.1 AI 粗稿生成（如有条件）

**目的**：利用AI快速生成设计初稿，加速设计流程

**阶段提醒（强制）**：

- 只要项目已经进入“需要外部 UI 设计/页面原型设计”的阶段，就必须明确提醒用户离开当前 CLI，去外部设计站点完成 UI 设计动作。
- 只要进入 `UI 原型还原`、`设计稿落地`、`UI -> 首版代码界面` 这类任务，就先把 `ui-ux-pro-max` 作为基座 skill 必调；其他 UI 相关 skill 再按“平台 + 框架 + 样式栈 + 当前阶段”命中条件优先调用。
- Web 侧当前已验证适配的条件 skill：`shadcn-ui`、`vue-best-practices`、`unocss`、`agent-browser`、`webapp-testing`、`accessibility-a11y`；它们不组成固定 bundle。
- iOS 侧：`mobile-ios-design`、`ios-application-dev`；Android 侧：`mobile-android-design`、`android-native-dev`；Flutter 侧默认先调用 `flutter-expert`，只有在需要明显对齐 iOS / Android 原生视觉规范时才再叠加对应平台设计 skill。
- `agent-browser` 与 `webapp-testing` 不是二选一：前者偏浏览器 / 原型 / 页面交互，后者偏本地实现后的验收 / 回归。
- iOS / Android 原生端的可访问性默认由各自平台设计 / 开发 skill 覆盖，不额外挂通用 Web `accessibility-a11y`。
- 推荐固定链路：先去 `https://www.uiprompt.site/zh/styles` 获取 UI 风格提示词，再由当前 CLI 生成 `design/STITCH-PROMPT.md`，随后去 `https://stitch.withgoogle.com/` 按页面 / 流程生成首版 UI 原型，最后进入 Figma 做现代视觉风格参考与校正。
- 不允许只在当前对话里停留在抽象描述，却不提醒用户去实际完成外部 UI 原型。
- **执行边界（强制）**：
  - `UI 原型生成` 这一步禁止使用 Codex 作为主执行器
  - 允许作为主执行器的 CLI 只有 Claude Code / OpenCode
  - Codex 只能做文档整理、Prompt 文本润色、原型结果回收，不能承担视觉原型主执行入口

**执行流程**：
```
AI 粗稿生成流程：

① 输入准备
    ├── 需求文档（BRD/PRD）
    ├── 业务流程说明
    └── 目标用户画像

② AI 生成粗稿
    ├── 页面布局建议
    ├── 组件清单
    ├── 交互流程草图
    └── 配色方案参考

③ 人工初审
    ├── 审核设计方向
    ├── 标记需要调整的点
    └── 确认进入精细化设计
```

**AI 粗稿输出示例**已拆到
[阶段三四：设计与任务模板](./阶段三四：设计与任务模板.md)，

#### 3.1.2 外部工具精细化设计与 Stitch Prompt 固定模板

**推荐工具**：Stitch、Figma、Sketch 等

**执行流程**：
```
外部工具精细化设计：

① 外部 UI 提示词准备
    ├── 从 PRD/BRD 提取页面目标、核心流程、目标用户
    ├── 访问 https://www.uiprompt.site/zh/styles
    └── 获取或整理贴近目标风格的 UI 提示词
```

  - 每个工具入参必须做白名单校验和类型校验
  - **幂等性设计：写操作类工具调用必须保证幂等，避免重试导致重复副作用**
- 上下文策略：
  - 稳定前缀（规则、术语、不可变背景）前置，动态需求后置，优先命中缓存

  - **输出截断处理：输出长度接近限制时必须有截断检测，拒绝使用不完整的结构化输出**
- 回退策略：
  - 主模型失败或超时时，自动切换到备选模型或降级路径
- **Temperature管理**：
  - 代码生成、结构化输出：temperature=0 或 ≤0.2
  - 创意/多样性场景：temperature=0.7~1.0
  - 默认不要使用API默认值（通常为1.0），应显式声明
- **停止词配置**：
  - 结构化输出场景应配置明确的stop_sequences，防止越界生成

   - 从 `trellis-library` 中选择适配当前项目的 spec
   - 添加到当前项目 `.trellis/spec/`

2. **对当前项目 `.trellis/spec/` 做项目化完善**
   - 结合当前项目的作用、背景、业务边界、技术架构
   - 分析现有 `.trellis/spec/` 内容是否准确
   - 删除错误、不适用或冲突的内容
   - 补充缺失的项目约束、边界、验证要求

3. **对直接相关 spec 执行 `Context7` 错漏复核**
   - 复核对象是目标项目中与已确认技术架构直接相关的全部 spec
   - 能被第三方官方文档约束的 spec 内容，必须先经过 `Context7`
   - 纯内部流程规范、团队约定、项目私有约束不强制要求 `Context7`，但仍必须做人类可复核的本地静态分析
   - 错漏分析至少覆盖：
     - API / 配置过时
     - 能力假设错误
     - 缺少必要约束
     - 遗漏关键边界或失败路径
     - 与官方文档冲突
   - 若直接相关的第三方 spec 因 `Context7` 不可用而无法完成复核，必须标记 `[Evidence Gap]`，并阻断进入 `§4 plan`
   - 若复核发现错误、遗漏或冲突，必须先修正相关 spec 或明确记录阻断项，不得带着未处理缺口进入 `§4 plan`

4. **明确项目自动化检查矩阵**
   - 基于已确认的语言、框架、包管理器、部署方式、CI 能力与质量平台，写出当前项目真实执行的自动化检查清单
   - 每个检查项至少明确：检查类别、工具/命令、执行时机、通过标准、失败后的处理动作
   - 不再允许使用“默认 Lint”“基础检查已覆盖”这类模糊表述；必须写出项目实际会跑的检查
   - 必须有明确的质量平台门禁；采用 Sonar 的项目必须写真实命令，未采用时必须写替代门禁和原因
   - 若项目实际采用 SonarQube、ESLint、Ruff、golangci-lint、Checkstyle、SpotBugs、Build 校验、依赖漏洞扫描等，也必须显式写入
   - 当前项目 `.trellis/spec/`、设计文档或 `task_plan.md` 中，至少要有一处可直接查到这份检查矩阵

退出 design 前，`design/TAD.md` 至少还必须显式冻结：

- `runtime_host`
- `application_stack`
- `persistence_strategy`
- `primary_processing_stack`
- `distribution_strategy`
- `remaining_unfrozen_items`
- `reopen_conditions`

并且 `TAD.md` 中至少要有以下固定区块：

- `## 架构冻结清单`
- `## 系统边界与外部依赖`
- `## 风险与回退`
- `## 阶段出口快照`

5. **同步适配当前项目的 `/trellis:finish-work`**
   - 这是 `finish-work` 的**主适配阶段**
   - 必须基于任务 3 中已经写清的自动化检查矩阵，修正对应项目里的 `finish-work`
   - 至少补齐：真实 lint / typecheck / test / build / scan / delivery gate、失败后的处理动作、哪些场景必须更新 spec / checklist / docs
   - 当前 task 应能形成 `finish-work-checklist.md`，至少记录冻结验证矩阵、人工验证状态、spec/docs 同步结论，以及 child-task parent record sync（如适用）；若当前 task 尚未生成该文件，可先以 `.trellis/workflow-docs/finish-work-checklist-template.md` 为骨架
   - 不允许把通用模板原样留给项目继续使用，也不允许只写“按项目情况执行检查”

6. **同步适配当前项目的 close-out 基线**
   - 在进入任务拆解前，先明确当前项目记录 session 的基线规则
   - 至少补齐：close-out 主入口（当前 fresh baseline 为 Trellis 原生 `/finish-work` / `trellis-finish-work`）、是否要求 helper、何时允许进入 close-out、收尾顺序（delivery → Trellis 原生 `/finish-work`，archive 在 `/finish-work` 阶段执行）、哪些 `.trellis/` 元数据允许自动提交、哪些情况必须先阻断
   - 这里先完成**基线适配**，避免项目直到开发收尾时还沿用通用 close-out

若 `ownership_proof_required = yes`，任务 6 还必须补齐：

- `$TASK_DIR/design/source-watermark-plan.md`
- `WMID`
- 零宽字符水印边界（只允许注释 / 文档字符串 / Markdown）
- 不起眼代码标识的允许位置与禁区
- 若项目需要对后续源码修改建立水印保持面，再补充受保护水印片段清单，以及可自动修复的低风险片段与其插入锚点 / 修复规则
- 交付阶段的 `ownership-proof.md` / `source-watermark-verification.md` 最低契约
- 统一校验命令：`ownership-proof-validate.py`
- 后续源码保持/修复命令：`source-watermark-guard.py --mode check|repair`

7. **标记 `§4 plan` 后是否需要对 close-out 做轻量校正**
   - 若任务拆解完成后，“当前任务完成”的定义、归档节点、交付节点、会话记录粒度比 `§3.7` 更明确，可以再补一次轻量修正
   - 这一步只允许小范围校正，不应把 close-out 的首次项目化适配拖到 `§4` 或更后面
   - 一般不需要在 `§4` 后再次大改 `finish-work`，除非计划阶段新增了新的强制检查门禁

门禁要求：

- 任务 1 未完成，不进入任务 2
- 任务 1、任务 2 未完成，不进入任务 3
- 任务 1、任务 2、任务 3 未完成，不进入任务 4
- 任务 1、任务 2、任务 3、任务 4 未完成，不进入任务 5
- 任务 1、任务 2、任务 3、任务 4、任务 5 未完成，不进入任务 6
- 任务 1、任务 2、任务 3、任务 4、任务 5、任务 6 未完成，不进入任务 7
- 任务 1、任务 2、任务 3、任务 4、任务 5、任务 6 未完成，不进入 `/trellis:plan`
- `/trellis:plan` 只负责生成人工确认清单、真实 Trellis task 与 `task_plan.md` 摘要，不替代 spec 导入、spec 修订、自动化检查矩阵定义，以及 Trellis 原生 `/finish-work` 的项目化基线适配动作

目的：

- 先把通用规范映射到当前项目
- 再把当前项目自己的规则边界补完整
- 再把项目真实要执行的自动化门禁写具体
- 再把项目真实收尾门禁和会话记录规则绑定到对应命令
- 避免 AI 在任务拆解阶段只拿到通用设计文档，却缺少项目级 spec 约束与检查基线

## 📝 阶段四：任务分解与准备（Trellis task-first）

### 4.1 AI 驱动的任务自动拆解

#### 4.1.1 任务图生成机制

**原流程痛点**：把复杂执行长期堆在 `task_plan.md` 里，会让摘要文档承担运行态控制，逐步偏离 Trellis 的 task-first 主模型。

**修正方案**：`plan` 阶段优先拆成真实 Trellis task，`task_plan.md` 只保留任务图与门禁摘要。

**硬禁令**：`plan` 阶段必须强制避免执行具体任务。它只允许拆 task、写摘要、定依赖与门禁，不允许生成项目基础代码、不允许编写实现代码、不允许直接进入 implementation。

**状态机门禁**：`plan` 阶段 `checkpoints.execution_authorized` 必须保持 `false`；只有用户明确确认进入 `implementation` 后，才允许显式切换为 `true`。

**吸收 Trellis plan-agent 的优点，但不接入 dispatch 自动链**：

- 先做“是否已经可以拆”的 readiness gate，而不是一上来就硬拆 task
- 至少把当前推荐执行的 leaf task 补成 task-ready 状态，避免进入 Trellis 基线后被判定为 `NOT READY`
- 仍然保持当前 workflow 的人工确认门禁，不恢复 `plan -> dispatch -> create-pr` 自动流水线

**执行流程**：

```
AI 任务拆解流程：

① 输入准备
    ├── 一句话需求描述
    ├── 关联文档路径（BRD/TAD/DDD/IDD等）
    ├── 项目技术约束（技术栈、编码规范等）
    └── 已完成对齐的当前项目 `.trellis/spec/`

② AI 拆分就绪检查
    ├── 目标/范围/验收锚点是否清晰
    ├── 关键依赖与阻断项是否已识别
    ├── 当前事项是否过大，是否还要继续拆小
    └── 未通过时停在 plan，回 brainstorm/design，不进入 task 生成

③ AI 起草 task_creation_checklist.md
    ├── 列出拟创建的真实 Trellis task
    ├── 划分项目域 / lane（如适用）
    ├── 先冻结依赖关系草案
    ├── 明确是否需要在主干后保留 `性能回归与优化任务`
    └── 等待人工确认，不进入真实 task 创建

④ 人工确认后，AI 拆真实 Trellis task
    ├── 按“是否还应继续细分以达到合适任务粒度”拆 task / child task
    ├── 创建真实 task 与 child task
    ├── 定义依赖关系
    ├── 为当前推荐 leaf task 补最小 prd.md
    ├── 按 `post_mainline_performance_task` 条件加入主干后的 `性能回归与优化任务`
    └── 条件生成 PROJECT-AUDIT 与交付控制类 task

⑤ AI 生成摘要型 task_plan.md
    ├── 概述
    ├── 项目域执行策略
    ├── Trellis Task 清单
    ├── 依赖关系
    ├── 早期探针与骨架任务
    ├── 自动化策略摘要
    ├── 范围收敛与降级预案
    ├── 门禁摘要
    ├── 任务图摘要
    └── 阶段出口快照

⑥ 人工审核与调整
    ├── 审核 task 拆分是否已达到合适任务粒度
    ├── 审核依赖与项目域边界
    ├── 审核全局门禁摘要
    └── 批准进入执行
```

`task_creation_checklist.md` 与 `task_plan.md` 的完整模板已拆到
[阶段三四：设计与任务模板](./阶段三四：设计与任务模板.md)。
总纲保留任务图机制、粒度判断和门禁规则，长模板集中在单独文件维护。

#### 4.1.2 拆分原则

- 单个 task 独立可测试
- 任务粒度应以“是否还能继续合理细分”为主判断，而不是机械按单次上下文预算打分
- 先拆真实 task，再写摘要
- 先写 `task_creation_checklist.md` 并获得人工确认，再创建真实 task
- 当前推荐执行的 leaf task 至少要具备最小 `prd.md`
- `Trellis Task 清单` 建议在 `说明` 列显式写 `code_related=yes` / `code_related=no`；validator 会优先采用显式标记，再退回到保守关键词判断
- 同一项目域内默认串行
- 多项目域可分 lane，但 lane 内仍默认串行
- 串行不等于自动续跑
- 若当前事项仍可继续合理细分，且继续细分能更清楚地隔离闭环目标、依赖变化、验证方式或风险承担，就必须继续拆成多个串行 task
- 若 `post_mainline_performance_task = yes`，`性能回归与优化任务` 必须存在，且位于目标主干任务链之后；若为 `no`，必须记录理由并从摘要中移除
- **AI 可执行性**：标记哪些 task 可以由 AI 主导完成
- **人工介入点**：标记必须人工确认的关键节点

##### 执行顺序规则

- 有前置依赖的 task，只有前置 task 收口后才允许作为下一个候选
- 同一项目域内默认串行，不再把“推荐并行组”作为主链规划中心
- 若目标项目确有多个相对独立的项目域，可按项目域分别维护串行 lane
- 即使前一 task 已完成，也不会自动启动下一 task；必须重新进入 `start`

##### task_plan 的边界

- `task_plan.md` 是摘要层，不再记录运行态状态矩阵
- 真实执行状态依赖 Trellis tasks、session-scoped active task runtime、`before-dev.md`、`check.md`
- 不再把“当前可开始任务 / 等待中任务 / 推荐并行组 / 任务执行矩阵”作为计划文件的主结构

#### 4.1.3 任务规格模板（AI生成 + 人工确认）

单个任务规格定义：

| 项目 | 内容 |
|------|------|
| 任务编号 | TASK-001 |
| 任务名称 | [任务名称] |
| 所属模块 | [模块名称] |
| 任务类型 | 新增/修改/删除/重构 |
| 风险级别 | L0/L1/L2（低/中/高） |
| AI执行模式 | 自动生成/AI草拟+人工修订/纯人工 |
| 评估集ID | EVAL-xxx |
| 上下文管理 | 确保不超出模型处理能力 |
| 回退策略 | 模型失败后的备选路径 |
| 预估工时 | X小时或X人天 |

##### 具体需求

- 需求描述：清晰描述需要实现的功能
- 需求来源：来自哪个用户故事或需求
- 需求优先级：必须/重要/可选

##### 功能边界

- 包含范围：明确任务要做什么
- 排除范围：明确任务不做什么
- 边界条件：特殊的边界情况处理

##### 技术约束

- 技术要求：使用的技术栈
- 接口要求：涉及的接口
- 数据要求：涉及的数据表
- 性能要求：性能指标要求

##### 验收标准

- **功能验收**：
  - 验收点1：描述 → 测试方法 → 预期结果
  - 验收点2：...
- **边界验收**：
  - 边界点1：边界情况 → 测试方法 → 预期结果
- **异常验收**：
  - 异常场景1：异常情况 → 处理方式 → 提示文案
- **性能验收**（如果适用）：
  - 响应时间要求
  - 并发能力要求

##### 依赖关系

- 前置任务：需要先完成的 task
- 所属项目域：当前 task 属于哪个串行 lane
- 是否为终局任务：例如 PROJECT-AUDIT / 交付控制类 task

##### 执行条件

- 开始条件：前置 task 完成、输入资源就绪、无冲突确认点
- 进入实现前必须再次执行一次 before-dev
- before-dev 产出的 `$TASK_DIR/before-dev.md` 是本次进入实现前的有效门禁快照

##### Definition of Ready (DoR) — 开始前必须满足

- [ ] 需求描述无歧义，验收标准可测试
- [ ] 接口/数据契约已确认（或已有Mock）
- [ ] 依赖任务已完成或可并行进行
- [ ] 评估集ID已关联，回归用例不少于1条
- [ ] 任务粒度已复核，且若引用上下文预算则只作为辅助参考，不作为机械裁决规则

##### Definition of Done (DoD) — 完成标准

- [ ] 功能验收全部通过
- [ ] 本地门禁全通过（按项目自动化检查矩阵执行，如 ESLint/Ruff/TypeCheck/Build/质量平台/单测）
- [ ] 绑定的评估集回归通过
- [ ] 代码已经过风险分级对应的评审
- [ ] 无新增安全高危项

补充要求：
- 每个任务必须写明 `Definition of Ready (DoR)` 与 `Definition of Done (DoD)`
- 每个任务必须绑定至少1条回归用例
- 高风险任务必须指定人工评审人（单人项目可指定"次日复审"机制）

#### 4.1.4 任务边界明确清单（AI预检 + 人工确认）

每个任务在开始前必须确认以下内容：

**□ 需求理解确认**
- □ 需求描述清晰无歧义
- □ 业务规则完全理解
- □ 边界条件已明确

**□ 技术约束确认**
- □ 技术选型已确定
- □ 接口定义已明确
- □ 数据结构已确定

**□ 验收标准确认**
- □ 功能验收点已列出
- □ 边界验收点已列出
- □ 异常场景已列出

**□ 测试门禁确认**
- □ 项目级全局测试基线已明确
- □ 当前 task 的具体测试门禁将在进入实现前由 before-dev 补充
- □ 不在 plan 阶段提前虚构当前 task 的具体测试门禁

**□ 依赖关系确认**
- □ 前置 task 已明确
- □ 当前 task 所属项目域已明确
- □ 同项目域内的串行顺序已明确
- □ 若有多个项目域，域间边界已明确

**□ 模糊点确认**
- □ 所有模糊点已澄清
- □ 遗留问题已记录并跟进
- □ 无法确定的问题已上报

#### 4.1.5 验收标准模板（AI生成 + 人工确认）

| 验收项 | 验收条件 | 测试方法 | 优先级 | 状态 |
|-------|---------|---------|-------|------|
| 功能点1 | 描述 | 测试方法 | P0 | 待测试 |

**边界条件验收**：

| 边界条件 | 预期行为 | 测试方法 | 优先级 |
|---------|---------|---------|-------|
| 条件1 | 预期结果 | 测试方法 | P0 |

**异常场景验收**：

| 异常输入 | 预期处理 | 提示文案 | 优先级 |
|---------|---------|---------|-------|
| 场景1 | 处理方式 | 提示内容 | P0 |

### 4.2 任务排期（基于 task 图摘要）

- 基于 AI 生成的 task 图摘要进行排期
- 根据 task 优先级、项目域和依赖关系安排主链
- 多项目域时可以并行推进不同 lane，但每个 lane 内默认串行
- **AI 加速效应考虑**：AI 生成代码的审查时间预估（按代码行数/复杂度）

排期时应遵循以下最小规则：

- 先安排无可替代的前置 task，避免后续 task 整体空等
- 再安排真正独立的其他项目域 lane
- 并行只是优化手段，不是强制目标；边界不清晰时默认退回串行

### 4.3 测试驱动模式（可选）

测试驱动开发（TDD）不再是独立阶段，而是 `implementation` 阶段的可选模式。

默认主链中：

- task 级测试门禁不在 plan 阶段预造
- 进入某个 task 实现前，由 `/trellis:continue` 自动执行 `before-dev`
- 当前 task 的有效门禁快照落到：

```text
$TASK_DIR/before-dev.md
```

显式采用测试驱动模式的场景：

- 用户明确要求 TDD
- 需要先把某个 task 的验收标准转成测试
- `check` 明确指出应先补测试证据

## 🔄 阶段五：开发实施循环

### 5.1 单个需求开发流程（task-first + 自动 before-dev）

① 选定当前 task
- 优先基于真实 Trellis task 图选择本轮唯一 task
- 默认一次只推进一个具体 task
- 串行不等于自动续跑；即使前一个 task 已完成，也必须显式重新进入主链选定下一个 task

② 自动执行 before-dev
- `/trellis:continue` 在真正实现前自动执行一次 before-dev
- 不要求用户显式输入 `/trellis:before-dev`
- before-dev 负责读取当前 task 相关 spec / guides / 项目约束

③ 生成当前 task 的门禁快照
- 自动生成或刷新 `$TASK_DIR/before-dev.md`
- 记录：
  - 当前 task 适用的 spec / guides
  - 项目级全局测试基线中当前 task 必须继承的项
  - 当前 task 新补充的测试门禁
  - 当前不做的验证项及原因

④ DoR 检查
- 需求边界、输入输出、验收标准、回归范围明确后才开始实现
- 若 `before-dev.md` 未完成，不进入实现

⑤ AI 实现（可选多轮）
- 结构化 Prompt 生成代码草案
- 对关键输出启用 Schema 约束，减少格式与字段错误

⑥ 本地自动门禁
- 必须执行在阶段 3.7 已明确的项目自动化检查矩阵
- 不允许只跑默认 `Lint` 后就进入提交或交付
- 至少覆盖当前项目真实需要的静态分析、类型/编译检查、测试、安全扫描；必须有明确质量平台门禁

⑦ 风险分级评审
- L0 低风险：自动门禁通过即可进入 PR
- L1 中风险：增加人工快速审查
- L2 高风险：默认提高审查强度，但是否进入任务级 `review-gate` 仍以其硬条件与软条件判定为准

⑧ 当前 task 收口
- 当前 task 通过本轮完成条件后，才允许标记为已完成
- 若命中任务级多 CLI 补充审查门禁，必须先完成 `/trellis:review-gate`
- 当全部代码相关 task 完成且 `PROJECT-AUDIT` 尚未完成时，必须先进入 `/trellis:project-audit`
- `PROJECT-AUDIT` 完成后：
  - 若本轮发生代码修改，默认回到 `/trellis:check`
    - 若 formal `PROJECT-AUDIT` 是独立 carrier task，且 `project-audit.md` 中 `task_level_check_task` 指向其他 task，则这里的“回到”指的是先切回该任务级 owner，再在那个 task 上进入任务级 `check`
  - 若本轮无代码修改，且当前 active task 的 `check.md` 已闭环，则可直接进入 `/trellis:delivery`

⑨ 上下文健康检查与决策摘要（每轮时间盒结束时）
- 检查当前上下文是否包含矛盾指令、过期信息、幻觉累积
- 若检测到上下文污染迹象，必须开启新会话，重新注入稳定前缀
- 定期导出关键决策为结构化摘要，注入新会话而非依赖完整历史
  - 摘要格式：结构化 JSON/Markdown
  - 包含：决策内容、依据、预期影响

### 5.1.x 反思/批判阶段（新增）

#### 5.1.x.1 实现后质量检查机制

AI 实现后、提交前，必须执行一次实现后质量检查：

```
质量检查清单：
□ 对照 Spec 逐项核对实现完整性
□ 对照测试用例验证功能正确性
□ 边界场景覆盖度检查（空值、极值、异常值）
□ 安全风险检查（注入、越权、泄露）
□ 性能影响评估（计算复杂度、资源占用）
```

输出"检查结果"：
- 改动范围与适用 spec / guideline
- 验证命令的 pass / fail / not run 结果
- 与需求/设计不一致的点、未覆盖风险、建议人工关注模块

补充边界：

- 这里的正式 `/trellis:check` 仍负责单任务实现后的质量检查与本地验证
- 项目级统一代码漏洞检测与代码质量总检（例如依赖漏洞扫描、质量平台总检），允许集中在 `project-audit` 阶段完成，不要求每个 task 的 `check` 都重复执行
- `project-audit` 不是对任务级 `check` 的替代；`delivery` 需要按上游路径同时消费任务级和项目级证据
- 若 formal `PROJECT-AUDIT` 是独立 carrier task，项目级 `project-audit` 完成后回到任务级 `check` / `review-gate` 时，必须先切回 `task_level_check_task` 指向的任务级 owner；不要把项目级 carrier 误当成任务级 gate owner

#### 5.1.x.2 任务级多 CLI 补充审查门禁

当前 CLI 完成**当前任务的质量检查与本地验证**后，不是默认立即标记任务结束，而是要先判断是否需要进入“任务级多 CLI 补充审查层”。

这一层的定位是：**面向高风险、高不确定、高影响面任务的补充审查门禁**。它不是对 `check` 的重复执行，也不是常规任务的默认重流程。

触发顺序：

```
当前任务实现完成
  → 当前 CLI 完成质量检查（`check` / 本地门禁 / 当前任务验证）
  → `/trellis:review-gate` 判断是否触发任务级多 CLI 审查
  → 若触发：其他 CLI 产出报告 → 当前 CLI 汇总并只执行低回归修复 → 当前 CLI 重新验证
  → 任务才允许标记为已完成
```

角色分工：

- **当前 CLI**：协调者 + 唯一修复者
- **其他 CLI**：reviewer，只审查，不直接修改代码
- **用户**：手动在其他 CLI 中执行标准命令；在冲突、越界或超阈值时做最终决策

触发模型：

#### 判定模型：硬条件 + 软条件分层门槛

**硬条件（命中任一即触发 `required`）**

以下任一条件成立时，必须进入 review-gate：

1. **认证、授权、权限边界、敏感信息处理**
2. **数据迁移、schema 变更、删除与回填**
3. **公共 API、跨层 contract、外部系统集成**
4. **支付、消息队列、缓存一致性、并发状态**
5. **核心共享模块且 blast radius 明显**（见下方判定标准）
6. **用户显式要求使用 `review-gate`**

---

#### 关键判定标准 1：blast radius 明显

**只有**至少满足以下任一条件时，才能判定为”blast radius 明显”：

✅ **成立条件**：
- 改动落在多个 feature / module / package 共用的核心模块，且当前代码搜索已知下游消费者不少于 3 处
- 改动改变多个层之间共享的数据 contract / serialization / validation 语义
- 改动影响全局启动 / 构建 / runtime 初始化 / 全局状态一致性
- 一旦出错，影响不是局部功能退化，而是跨功能、跨任务或跨模块系统性失效

❌ **不成立**：
- 若以上证据无法从代码、配置、调用关系或任务上下文中成立，不得仅凭”感觉重要”命中该硬条件

---

#### 关键判定标准 2：测试或验证证据明显不足

**只有**至少满足以下任一条件时，才能判定为”测试或验证证据明显不足”：

✅ **成立条件**：
- 改变了行为或修复了 bug，但没有对应自动化测试，也没有明确的手工验证记录
- 改变了失败路径 / 异常分支 / 回退逻辑，但没有负向验证证据
- 改变了跨层 contract / serialization / integration 行为，但没有对应集成或边界验证
- 跳过了当前任务本应执行的关键验证命令，且没有等价替代证据

❌ **不成立**（以下情况默认不构成”证据不足”）：
- 一般性的覆盖率不够理想，但当前改动路径已有合理自动化或手工验证
- 纯文档改动
- 纯重构且未改变性能特征、序列化格式、缓存策略或其他非功能性行为
- 无行为变化改动
- 仅因为”理论上还能补更多测试”

---

#### ⚠️ Anti-Pattern：不得单独作为触发理由

以下情况**单独出现时**，不得作为进入 `review-gate` 的理由：

❌ “看起来复杂”
❌ “改动文件稍多”
❌ “CLI 想更稳一点”

---

#### 软条件门槛

当未命中硬条件时，综合评估以下维度：

- **复杂度层**：改动文件数、改动行数、涉及模块/层数、异常路径数量
- **影响面层**：公共模块、跨层边界、外部集成、blast radius
- **可信度层**：测试或验证证据明显不足、当前 CLI 不确定性高、AI 生成比例高、历史缺陷密度高

---

#### 判定结果与门槛

| 判定结果 | 触发条件 | 说明 |
|---------|---------|------|
| `required` | 命中任一硬条件 | 必须执行多 CLI 审查 |
| `recommended` | 未命中硬条件，但可信度层因”测试或验证证据明显不足”单独达到中门槛 | 建议执行；若现有验证已足够且用户接受风险，可跳过并写明原因 |
| `recommended` | 未命中硬条件，但多个软条件叠加达到现有中门槛 | 同上 |
| `skip` | 否则 | 无需执行，进入 `/trellis:delivery`；若当前轮还需要关闭当前 active task，再在 delivery 后进入 Trellis 原生 `/trellis:finish-work` |

---

#### 用户触发边界

- 若用户明确要求进入 `review-gate`，必须进入该阶段，AI 不得以”当前风险不高”为由拒绝。
- 但进入阶段后，当前轮判定结果仍可为 `skip` / `recommended` / `required`。
- 若用户明确要求”多 CLI 审查 / 让其他 CLI 再看一轮 / multi-cli-review”，则外部 reviewer 执行视为必需动作；若能力不可用，必须显式阻塞并说明依赖缺失，不得静默降级。

执行约束：

- `lite` 默认由用户手动调用 **1 个其他 CLI**
- `full` 默认由用户手动调用 **2 个其他 CLI**；必要时可扩展到 **4 个 reviewer**
- `recommended` 默认走 `lite`；`required` 默认走 `full`
- 建议优先在 **3 轮**内收敛；若问题仍未收敛，必须显式提示用户判断是否继续下一轮
- 若当前轮没有新的有效修复建议，可提前关闭
- reviewer 建议互斥、越出任务边界，或超过建议轮次后用户未明确要求继续时，必须停止自动推进并要求人工介入
- 进入该层前，目标 reviewer CLI 必须已具备 `multi-cli-review` 能力；当前 CLI 必须已具备 `multi-cli-review-action` 能力。若缺失，先补齐对应 skill，再进入补充审查
- reviewer 只消费当前 CLI 已创建好的目录结构；**reviewer 不负责创建目录**
- task-level reviewer-id 默认使用协调者分配的字母槽位：`a` / `b` / `c` / `d`
- 实际审查 CLI 身份由 reviewer 报告 frontmatter 中的 `source-cli` 记录，不能把 CLI 名直接混进 `reviewer-id`

交接协议：

- 当前 CLI 负责先创建 `tmp/multi-cli-review/<task-id>/review-round-<N>/`
- 当前 CLI 输出给其他 CLI 的**完整标准命令**，并显式给出 `--task-dir`、`--reviewer-id`、`--round`
- 其他 CLI 使用 `multi-cli-review` 写入各自的 `{reviewer-id}.md`，不得改代码、不得建目录、不得用 `--output` 或 legacy 参数绕开标准路径
- 当前 CLI 使用 `multi-cli-review-action` 先校验 reviewer 报告契约与本地上下文，再统一读取、去重、标记冲突并输出 `summary-round-<N>.md`
- 只有在用户确认汇总结果后，当前 CLI 才允许对 `adopted` 且不会明显引入新问题/回归的项执行修复，并更新 `action.md` 与 `.processed.json`
- 修复后，当前 CLI 必须重新跑该任务的质量检查 / 验证，之后才能关闭该任务

推荐输出物：

- `$TASK_DIR/review-gate/review-gate-round-<N>.md`：记录本轮为何触发 `required / recommended / skip`
- `$TASK_DIR/review-gate/reviewer-commands-round-<N>.md`：给其他 CLI 的标准命令模板
- `tmp/multi-cli-review/<task-id>/review-round-<N>/{reviewer-id}.md`：各 reviewer 报告
- `tmp/multi-cli-review/<task-id>/summary-round-<N>.md`：由 `multi-cli-review-action` 输出的聚合与决策摘要
- `tmp/multi-cli-review/<task-id>/action.md`：由 `multi-cli-review-action` 输出的当前 CLI 决策与执行记录
- `tmp/multi-cli-review/<task-id>/.processed.json`：由 `multi-cli-review-action` 维护的内部消费状态

#### 5.1.x.3 双模态执行原则

根据任务风险级别采用不同执行策略：

| 风险级别 | 任务类型 | 执行策略 |
|---------|---------|---------|
| **低风险** | 样板代码生成、测试用例生成、文档同步 | AI 激进执行 → 快速 Review → 自动门禁 |
| **中风险** | 功能实现、逻辑编写 | AI 主导 → 关键节点人工确认 |
| **高风险** | 核心算法、安全相关、数据迁移 | 人工主导 → AI 辅助 → 完整人工评审 |

#### 5.1.x.4 上下文污染检测升级

检测到污染迹象时的强化处理：
```
① 立即停止当前会话
② 基于最新决策摘要（而非完整历史）开启新会话
③ 标记本次会话异常供后续复盘
```

**时间盒规则**：
- 简单任务（L0，单文件修改）：根据复杂度合理设定
- 标准任务（L1，跨模块）：根据复杂度合理设定
- 复杂任务（L2，架构级）：拆分为多个子时间盒，确保单次可完成

**退出条件（按优先级）**：
① 证据通过（DoD满足）→ 正常退出
② 时间盒耗尽但进度>70% → 延长一个半时间盒，仍未完成进入5.2
③ 同类错误连续2轮未收敛 → 立即进入5.2，不等时间盒结束
④ 以"证据通过"作为退出条件，不使用主观置信度阈值

### 5.2 人工介入机制
- 触发条件1：同类缺陷连续2轮未解决
- 触发条件2：任务耗时超估算50%仍未达到DoD
- 触发条件3：出现安全高危、数据一致性风险、线上阻断风险
- 触发条件4：模型输出不稳定（同输入多次结果差异过大）
- 触发条件5：任务级多 CLI 审查超过建议轮次仍未收敛且用户未明确要求继续，或 reviewer 建议互斥 / 越界

介入动作：
- 先做根因分类（需求问题/设计问题/实现问题/评估问题）
- 调整策略（重写验收、拆任务、换模型、改Prompt、改工具链）
- 产出"介入结论记录"，作为后续同类任务模板

### 5.3 阶段性检查点
- 交付效率指标（建议周维度复盘）：
  - 部署频率
  - 变更前置时间（从提交到上线）
  - 变更失败率
  - 平均恢复时间（MTTR）
  - 返工率（rework）
- AI效率指标：
  - 首轮通过率（一次实现即通过DoD的比例）
  - 评估通过率（评估集通过比例）
  - 单任务Token成本（按被验收任务计）
  - 缓存命中率（`cached_tokens`占比）
  - 降级/回退触发率
- 要求：
  - 任一核心指标连续两周恶化，必须触发流程复盘

### 5.4 人工代码校验（风险分级必选）

- 低风险任务：抽样校验
- 中风险任务：必须人工审查关键逻辑与异常路径
- 高风险任务：必须完整人工审查、威胁建模、回归验证
- 单人项目执行方式：至少间隔30分钟后进行"冷启动复审"，避免同一上下文盲点

> 这一阶段体现了"实现后强制自检"和"优化-评审"的闭环思想。

### 5.5 代码与文档同步机制

#### 5.5.1 同步原则

- **任务粒度同步**：每个任务完成后，必须同步更新相关文档
- **上下文变更同步**：每次上下文有重大变更（如需求变更、架构调整），需同步更新文档
- **即时优先**：文档更新应尽可能在代码变更后立即完成，避免事后遗忘

#### 5.5.2 同步内容清单

| 变更类型 | 必须更新的文档 | 更新时机 |
|---------|--------------|---------|
| 新增功能 | 需求文档、功能规格说明、接口文档 | 功能验收通过后 |
| 代码重构 | 技术架构文档、模块说明 | 重构完成通过测试后 |
| 数据库变更 | 数据库设计文档、ER图、数据字典 | 迁移/变更生效后 |
| 接口变更 | 接口文档、集成说明 | 接口联调完成后 |
| Prompt调整 | 提示词模板库、评估集 | 评估基线回归通过后 |

#### 5.5.3 同步执行规范

```
代码与文档同步流程：

① 触发条件检测
    ├── 代码提交后检查是否有文档依赖变更
    ├── 上下文更新后检查文档时效性
    └── 任务验收通过后触发同步检查

② 文档受影响范围分析
    ├── 识别本次变更影响的文档范围
    ├── 区分必须更新/建议更新/无需更新
    └── 标记文档更新优先级

③ 执行文档同步
    ├── 按受影响范围逐项更新
    ├── 更新内容必须与代码/上下文一致
    └── 添加版本记录和变更说明

④ 同步验证
    ├── 检查文档与代码的一致性
    ├── 验证文档完整性
    └── 确认无遗漏项
```

#### 5.5.4 文档版本管理

- 所有文档采用与代码关联的版本号
- 重大变更需在文档中记录变更日志
- 保留历史版本以便追溯

### 5.6 单次对话任务闭环规范

#### 5.6.1 闭环定义

单次对话上下文内完成一个独立任务，包含完整的工作流程：

```
单次对话任务闭环流程：

① 任务理解与确认
    ├── 明确任务目标与验收标准
    ├── 确认DoR满足条件
    └── 与用户确认理解一致

② 代码实现
    ├── 按任务规格进行代码编写
    ├── 遵循项目编码规范
    └── 确保代码可运行

③ 代码质量检测（按项目自动化检查矩阵执行）
    ├── 静态分析/规范检查（如 ESLint、Ruff、Checkstyle）
    ├── 类型检查/编译校验（如 Type Check、mypy、Build）
    ├── 质量平台/安全扫描（如 SonarQube、依赖漏洞、敏感信息、注入风险）
    └── 单元/集成测试（核心逻辑覆盖）

④ 代码优化
    ├── 性能优化（减少不必要的计算/请求）
    ├── 可读性优化（命名、注释、结构）
    └── 重复代码提取

⑤ Bug修复（如有）
    ├── 根据测试反馈定位问题
    ├── 分析根因
    └── 修复并验证

⑥ 回归验证
    ├── 确保不破坏现有功能
    ├── 运行绑定评估集
    └── 确认满足DoD标准
```

#### 5.6.2 任务拆分原则

- 单次对话任务应在30-90分钟可完成
- 复杂任务需拆分为多个可闭环的子任务
- 跨对话任务必须有明确的状态传递机制

#### 5.6.3 上下文健康管理

- 每次任务开始前检查上下文清洁度
- 任务完成后导出关键结论到外部存储
- 新任务开始时优先从外部存储恢复上下文，而非依赖对话历史

### 6.6 Bug反馈学习机制

每个Bug修复完成后，需要进行反馈学习，避免同类问题再次出现。

#### 6.6.1 问题分类与根因分析

对修复的Bug进行分类和根因分析，形成知识沉淀：

| 字段 | 说明 |
|------|------|
| Bug编号 | BUG-001 |
| 问题分类 | 需求理解/设计缺陷/编码错误/测试遗漏/技术债务/其他 |
| 根因类型 | 遗漏/误解/疏忽/经验不足/流程问题/其他 |
| 根因描述 | 详细描述问题产生的根本原因 |
| 5Why分析 | 逐层追问为什么，直到找到根本原因 |

**示例 - 5Why分析：**
- 问题：用户登录后显示空页面
  - Why 1: 为什么显示空页面？→ 页面数据未加载
  - Why 2: 为什么数据未加载？→ API返回空数据
  - Why 3: 为什么API返回空数据？→ 数据库查询条件错误
  - Why 4: 为什么查询条件错误？→ 代码中使用了错误的字段名
  - Why 5: 为什么使用错误字段名？→ 需求文档和数据库设计文档字段名不一致，未核对
- 根本原因：需求文档和数据库设计文档字段名不一致，开发时未进行核对

- 影响
- 建议改哪里

是否要正式回流到 workflow 文档，由人工决定。

### 7.4 会话记录与元数据提交

- 代码、文档或配置变更已由人工测试并提交后，再执行会话记录
- 这里只有**当前执行任务已完成后的最终收尾记录**，才允许进入 Trellis 原生 `/finish-work` / `trellis-finish-work` 收尾入口；此阶段负责冻结 `finish-work-checklist.md` 与 close-out 证据
- 收尾顺序：delivery → Trellis 原生 `/finish-work`；`archive` 与 `add_session.py` 在 `/finish-work` 阶段执行。未完成任务不得因记录会话而误归档；**非当前任务**不得借本轮收尾顺手自动提交
- `workflow-state.py validate <task-dir>` 用于确认进入收尾前的 `delivery` 门禁已经满足；它不能替代 `archive`、`add_session.py` 与元数据清理本身
- `archive` 后，`.trellis/tasks` 与当前 session 的 active-task runtime 应已 clean
- 执行 `add_session.py` 前，staged 区未混入非目标变更；否则应中断
- session 记录应直接复用 Trellis 原生 `add_session.py`
- 不允许仅依据"task archived"或"session added successfully"字样就判定完成，必须以 git 状态为准

收尾校验：

```bash
git status --short .trellis/tasks .trellis/.runtime/sessions
git status --short .trellis/workspace .trellis/tasks
```

- 预期输出为空；若仍有 `.trellis/tasks`、`.trellis/workspace` 或 `.trellis/.runtime/sessions` 变更，说明归档/记录未真正闭环
- 若自动提交失败，应视为 session record 未完成，先处理 Trellis 基线写入失败原因，再结束本轮工作
- 若目标不是当前任务，或 staged 区存在非目标变更，应视为流程前置条件不满足，先清理边界问题，再继续收尾

> 这一阶段体现了"错误沉淀与复用"的方法论价值。
