# 外包项目扩展

> 本文档定义外包、定制开发、新客户项目的专用机制和门禁。
> 通用流程请参考《[工作流总纲](./工作流总纲.md)》。

---

## 适用范围

本扩展适用于以下项目类型：

- 外包项目
- 定制开发项目
- 新客户项目
- 对外交付项目

**不适用于**：

- 个人项目（personal profile）
- 内部项目
- 开源项目

---

## 双轨交付控制原则

对于外包、定制开发、新客户项目，默认采用以下"双轨交付控制"：

### 开工前置门禁

- 必须先冻结 `kickoff_payment_ratio`
- 启动款比例最低不少于 `30%`，默认建议 `30%` 或 `40%`
- 在 `kickoff_payment_received = yes` 前，不得进入 implementation

### 首选轨：托管部署

- **适用前提**：客户接受尾款前仅使用托管环境
- **尾款前保留**：
  - 源码仓库
  - 生产环境密钥
  - 管理员账号
  - 最终部署控制权
- **尾款前提供**：由开发者控制的演示/试运行环境，客户验证功能与流程
- **尾款到账后**：执行源码、部署权限、密钥、账号、运维材料的正式移交
- **机器字段**：`delivery_control_track = hosted_deployment`
- **必选资产**：`delivery-control` + `transfer-checklist`

### 备选轨：试运行授权

- **适用前提**：客户明确要求先拿可运行版本，且双方接受授权方案
- **必须披露**：在报价、合同、交付说明、验收口径中明确披露：
  - 试运行授权的期限
  - 续期方式
  - 到期行为
  - 永久授权触发条件
- **到期行为**：必须可预期，优先限制为"演示模式"或"只读模式"，不得破坏已有数据
- **尾款前保留**：永久授权、完整源码、最终控制权；并明确试运行限制
- **尾款到账后**：交付永久授权、源码及最终控制权
- **机器字段**：`delivery_control_track = trial_authorization`
- **必选资产**：`delivery-control` + `transfer-checklist` + `authorization-management`

### 条件资产

正式移交时若涉及密钥/配置，再加 `secrets-and-config`

---

## 禁止项

- ❌ 不得植入未披露的后门、隐藏开关、远程锁定或暗门控制逻辑
- ❌ 不得使用会破坏数据、阻断导出、导致客户无法恢复业务的失效机制
- ❌ 不得使用"不可解码交付文件"伪装为正常源码交付
- ❌ 若已明确交付的是试运行版，不得在流程或文档中表述为"正式无限制交付"

## 阶段一：可行性评估（Feasibility）

### 外部项目必须冻结的字段

在 `assessment.md` 中必须冻结以下字段：

**项目类别与支付门禁**：
- `project_engagement_type = external_outsourcing`
- `kickoff_payment_ratio`（最低 30%）
- `kickoff_payment_received`（yes/no）

**交付控制轨道**：
- `delivery_control_track`（hosted_deployment / trial_authorization）
- `delivery_control_handover_trigger`（一般为 final_payment_received）
- `delivery_control_retained_scope`（尾款前保留的控制范围）

**试运行授权（仅 trial_authorization 轨道）**：
- `trial_authorization_terms.duration`
- `trial_authorization_terms.renewal_policy`
- `trial_authorization_terms.expiry_behavior`
- `trial_authorization_terms.permanent_trigger`

### 离开 feasibility 前的检查

至少形成一份可复核的"阶段出口快照"：

- 哪些字段已经冻结
- 哪些事项必须在 brainstorm 收口前重算
- 哪些前提变化会强制回到 feasibility

## 阶段三：设计（Design）

### Spec 导入要求（外部项目专用）

进入设计阶段（`/trellis:design`）后，技术架构确认前，必须从 `trellis-library` 导入以下交付控制相关 spec 到当前项目 `.trellis/spec/`：

**外部项目基础必选**：
- `spec.universal-domains.project-governance.delivery-control`（交付控制总控规范）
- `checklist.universal-domains.project-governance.transfer-checklist`（交付事件 checklist）

**仅当交付轨道为 trial_authorization 时额外导入**：
- `spec.universal-domains.project-governance.authorization-management`（试运行授权规范）

**仅当本项目会发生密钥、环境变量、第三方平台配置等正式移交时，额外导入**：
- `spec.universal-domains.security.secrets-and-config`

这些 spec 定义了双轨交付控制的详细规则、验证方法和合规检查点。

**重要**：这一步只是在外部项目场景下，先补齐**交付控制基线资产**，避免设计阶段没有最基本的交付约束；它**不替代**技术架构确认后的项目级 spec 对齐。等技术架构被用户明确确认后，仍必须继续执行 `§3.7 技术架构确认后的项目 Spec 对齐`。

## 阶段四：计划（Plan）

### 外部项目必须拆出的任务

**开工授权确认任务**：
- 必须额外拆出开工授权确认任务
- 在 `kickoff_payment_received = yes` 前，不得放行 implementation
- 支付后移交任务不得提前进入执行候选

**交付事件任务**：
- 把试运行交付、永久授权切换、最终控制权移交拆成单独任务
- 移交任务不得早于触发条件

---

## 阶段六：交付（Delivery）

### 外部项目分支

这是必须显式分支的阶段：

**retained-control delivery**：
- 交付材料，但不移交最终控制权
- 验证：`delivery_control_handover_trigger` 触发状态

**final control transfer**：
- 只有触发条件满足后，才移交源码、永久授权、密钥、管理员权限
- 验证：尾款到账后方可最终移交

### 验证命令

```bash
python3 .trellis/scripts/workflow/ownership-proof-validate.py --phase delivery --task-dir <task-dir>
```

## 双轨交付控制速查表

| 决策点 | `hosted_deployment` | `trial_authorization` |
|---|---|---|
| 适用前提 | 客户接受尾款前仅使用托管环境 | 客户明确要求先拿可运行版本，且双方接受授权条款 |
| 开工前提 | `kickoff_payment_ratio >= 30%` 且 `kickoff_payment_received = yes` 后才允许 implementation | 同左 |
| 机器字段 | `delivery_control_track = hosted_deployment` | `delivery_control_track = trial_authorization` |
| 必选资产 | `delivery-control` + `transfer-checklist` | `delivery-control` + `transfer-checklist` + `authorization-management` |
| 条件资产 | 正式移交时若涉及密钥/配置，再加 `secrets-and-config` | 正式移交时若涉及密钥/配置，再加 `secrets-and-config` |
| 尾款前默认保留 | 源码、生产密钥、管理员账号、最终部署控制权 | 永久授权、完整源码、最终控制权；并明确试运行限制 |
| 最终移交触发 | 一般为 `final_payment_received` | 一般为 `final_payment_received` |

## 与通用流程的关系

- 外包项目**必须**遵循通用流程的所有阶段和门禁
- 本扩展文档**额外增加**外包项目专用的门禁和检查
- 当通用流程与本扩展冲突时，以**更严格**的要求为准
