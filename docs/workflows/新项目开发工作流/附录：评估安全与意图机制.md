## 🧪 附录一：AI评估驱动开发 (Evaluation-Driven Development)

在项目开始前，应建立 AI 评估体系作为基础。

### 附录1.1 评估指标定义
- **准确率/通过率**：AI 生成代码通过测试的比例
- **处理时间**：系统级 + 组件级响应时间
- **系统性能**：吞吐量、并发能力
- **幻觉率**：AI 产生错误输出的频率
- **上下文利用效率**：上下文窗口的有效利用率

### 附录1.2 测试用例设计

- **快乐路径用例**：核心功能场景
- **边界用例**：AI 易失败的场景
- **对抗用例**：提示词注入、恶意输入
- 使用 LLM 生成扩展测试用例

**评估集规模建议（参考 OpenAI Evals 和 Anthropic 内部实践）**：
- 最小可信评估集：≥50条（低于此数量，统计波动过大，结果不可信）
- 生产级评估集：200~500条（核心路径覆盖率≥80%）
- 对抗用例比例：≥15%（否则鲁棒性测试形同虚设）
- 评估集增长触发：每次线上故障、每次重大 Prompt 变更，至少沉淀5~10条新用例

**评估结果解读门槛**：
- 单次评估波动在±3%以内属正常，不应触发回滚
- 连续2次下降且累计超过5% → 触发回归阻断

### 附录1.3 评估方法选择
- **确定性检查**：结构、路径、工具调用正确性
- **语义检查**：使用 LLM-as-Judge 进行语义等价判断
- **混合策略**：轻量检查 + LLM 评估

### 附录1.4 评估自动化
- 建立持续评估 pipeline
- 配置评估频率（每次 commit / 每日 / 每周）
- 设定回归检测阈值

### 附录1.5 持续评估门禁
- PR 级快速评估：每次 PR 运行最小评估集（核心路径 + 最近高频缺陷）
- 夜间全量评估：每日运行完整评估集，跟踪趋势变化
- 回归阻断：关键指标低于阈值时阻断发布
- 评估集演进：每次线上故障与高优 Bug 必须沉淀为新评估用例

> 评估体系是 AI Workflow 的核心基础，没有评估就没有改进。

## 🔒 附录二：AI代码与AI应用安全审查（OWASP LLM Top 10 + Agentic Applications 2026 映射）

### 审查重点：OWASP LLM Top 10

- Prompt Injection（提示词注入）
- Sensitive Information Disclosure（敏感信息泄露）
- Supply Chain（供应链风险）
- Data/Model Poisoning（数据与模型投毒）
- Improper Output Handling（输出处理不当）
- Excessive Agency（过度代理权限）
- System Prompt Leakage（系统提示词泄露）
- Vector/Embedding Weaknesses（向量与嵌入弱点）
- Misinformation（错误信息）
- Unbounded Consumption（无界资源消耗）

### 审查重点：OWASP Top 10 for Agentic Applications 2025/2026（新增）

| 风险项 | 描述 | 防护建议 |
|-------|------|---------|
| **Tool Misuse** | 工具被错误调用或超出预期范围使用 | 工具入参必须白名单校验，权限最小化 |
| **Identity & Memory Management** | Agent 身份混淆、内存/上下文信息泄露 | 严格隔离不同任务上下文，会话状态加密 |
| **Autonomous Decision Errors** | Agent 过度自主决策导致错误结果 | 关键决策必须人工确认，输出必须可追溯 |
| **Goal Hierarchy Failure** | Agent 目标层级混乱，优先级误判 | 明确目标优先级，建立冲突仲裁机制 |
| **Unbounded Execution** | Agent 执行无外部边界限制 | 设置执行预算上限，超限强制中断 |

### agentic 工作流防护（新增）

1. **自主操作限制**：
   - 所有涉及外部系统写操作、敏感数据访问、费用产生等高影响行为，必须插入人工审批节点
   - Agent 不得在无确认情况下执行不可逆操作

2. **人类最终责任**：
   - 明确宣示：AI 生成内容的所有最终责任归人类决策者
   - 关键输出必须经过人类审核后方可生效
   - 建立"人类在环"（Human-in-the-Loop）机制作为强制门禁

3. **执行边界约束**：
   - 单次任务最大执行轮次设定上限
   - 累计资源消耗（Token、时间、费用）设定告警阈值
   - 连续失败自动触发人工介入流程

4. **审计追踪**：
   - 所有 AI 的工具调用（尤其是写操作）必须留有可追溯日志
   - 日志必须包含：输入摘要、调用时间、模型版本、输出结果、执行用户

**最低安全要求（可落地版）**：

1. **Prompt Injection 防护**：
   - 用户输入必须与系统指令在结构上隔离（使用角色分隔或 XML 标签，不拼接到 system prompt）
   - 禁止将外部内容（如用户上传文件、爬取内容）直接注入高权限上下文

2. **输出处理**：
   - AI 输出不得未经验证直接执行（eval、exec、shell 注入等）
   - 结构化输出必须经过 Schema 验证，验证失败必须拒绝而非降级处理

3. **敏感信息防护**：
   - 系统 Prompt 不得包含可被提取的密钥、内部路径或用户 PII
   - 生产环境 API Key 必须通过环境变量注入，不得硬编码在 Prompt 模板中

4. **访问控制**：
   - 工具调用的权限范围必须最小化（只读工具不赋写权限）
   - Agent 自主操作外部系统前，必须有人工审批节点或可撤销确认机制

## 📑 附录三：意图文档维护机制（新增）

### 意图文档定义

项目级 Intent.md 是高层次意图声明，包含：
- 项目业务目标与核心价值
- 关键设计决策及理由
- 重要约束与边界条件
- 已确认的验收证据基线

### 维护流程

```text
意图文档生命周期：

① 项目启动
    └── 基于确认的 BRD 生成初始 Intent.md

② 每次 AI 迭代后
    └── AI 自动同步更新以下内容：
        - 本次迭代产生的新的设计决策
        - 需求理解的澄清或修正
        - 验收标准的补充或调整
        - 与原意图的偏差说明（如有）

③ 人类复核
    └── 开发者在下一会话开始前复核更新
    └── 确认签字后生效

④ 长期项目维护
    └── 每季度或每重要里程碑后全面复核
    └── 清理过时假设，确保意图一致性
```

### Intent.md 模板

```markdown
# Intent.md - [项目名称]

## 业务目标
- 核心价值主张
- 关键成功指标

## 设计意图
- 架构决策及理由
- 技术选型约束
- 已排除的替代方案

## 验收证据基线
- 已确认的核心测试用例
- 性能/质量基线
- 关键风险及应对

## 意图变更日志
| 日期 | 变更内容 | 变更理由 | 确认人 |
|------|---------|---------|-------|
```
