# 装后隐藏目录与托管边界核对清单

> 用于在目标项目执行 `trellis init` + `install-workflow.py` 之后，核对隐藏目录、托管边界与历史漂移风险。
> 本文档只回答三件事：哪些资产由 `trellis init` 提供、哪些由当前 workflow 安装器托管、哪些仍需人工维护。

## 适用边界

本文档适用于两类场景：

1. 当前仓库在维护 `docs/workflows/新项目开发工作流/` 时，需要确认装后真实落盘结果
2. 某个目标项目已经嵌入本 workflow，需要做装后核对或升级后复查

本文档不替代：

- [工作流总纲](./工作流总纲.md) 中的主流程定义
- [CLI原生适配边界矩阵](./CLI原生适配边界矩阵.md) 中的按 CLI 边界说明
- [目标项目兼容升级方案指导](./目标项目兼容升级方案指导.md) 中的 `A/B/C` 三态分析

## 先分清三层来源

```text
trellis init baseline
  -> 目标项目的纯净 Trellis 隐藏目录与基线命令 / skills / hooks
workflow installer managed assets
  -> 当前 workflow 注入的命令、skills、共享 helper、workflow.md patch、AGENTS.md 路由块、安装记录
manual project-owned assets
  -> 项目自己维护的 settings / hooks / instructions / config / 非托管 agents
```

判断漂移前，先不要把这三层混在一起。

补充一个维护边界：

- `docs/workflows/新项目开发工作流/commands/workflow_assets.py` 是当前 workflow 托管资产常量的单一事实源
- `install-workflow.py`、`upgrade-compat.py`、`analyze-upgrade.py`、`test_workflow_installers.py` 都以这里的常量为准
- 若文档、安装器、升级器、测试之间出现"到底托管哪些命令 / helper / agents / patch"的口径冲突，先回到 `workflow_assets.py` 对照
- `工作流总纲.md`、`命令映射.md`、`阶段状态机与强门禁协议.md` 默认只保留产品 / 目标项目 runtime 语义；若需要当前仓库的 source-maintenance 或 direct-run 入口，统一看本文、`CLI原生适配边界矩阵.md`、`目标项目兼容升级方案指导.md`

## Step 1：先跑自动化核对

从当前仓库执行：

```bash
/ops/softwares/python/bin/python3 \
docs/workflows/新项目开发工作流/commands/upgrade-compat.py \
--project-root <target-project> \
--check
```

这一步负责检查：

- workflow 分发命令 / skills 是否与当前 source contract 一致
- 当前 Trellis 0.5 baseline patch 是否仍在：Claude / OpenCode 的 `continue` / `finish-work`，Codex 的 `trellis-continue` / `trellis-finish-work`
- legacy baseline `start` 只在旧目标项目兼容链路中检查，不作为 fresh baseline 要求
- `parallel` 入口移除状态是否漂移
- shared helper scripts 与 `.trellis/workflow.md` patch 是否仍在
- 已废弃的 workflow helper 是否仍残留在 `.trellis/scripts/workflow/`
- `AGENTS.md` 中的 `workflow-nl-routing` 区段是否缺失或内容漂移

边界：

- 若 `--check` 通过，命令内容一致性、shared helper scripts、一部分 patch 存在性可视为已完成自动化核对，后续人工步骤以抽检和边界补充为主
- 若 `--check` 失败，应先根据输出修复对应漂移，再继续人工核对
- `--check` 仍**不会**替代以下人工核对：`origin` 双 push URL、`.claude/settings*.json`、`opencode.json.instructions`、`.codex/hooks.json`、`.codex/hooks/inject-workflow-state.py` 等项目自维护资产

若这一步失败，不要直接跳过去人工脑补“应该没问题”。

## Step 2：逐项核对隐藏目录

### A. `trellis init` 基线产物

| 资产 | 期望状态 | 归属 |
|------|----------|------|
| `AGENTS.md` 内 `<!-- TRELLIS:START ... TRELLIS:END -->` | 必须存在 | `trellis init` 托管 |
| `.trellis/.version` | 必须存在 | `trellis init` 托管 |
| `.trellis/workflow.md` | 必须存在；之后允许被 workflow 安装器追加 patch | `trellis init` 基线 + workflow patch |
| `.claude/commands/trellis/continue.md` `finish-work.md` | Claude baseline 命令存在；legacy `start.md` 不作为 fresh baseline 要求 | `trellis init` 基线 |
| `.opencode/commands/trellis/continue.md` `finish-work.md` | OpenCode baseline 命令存在；legacy `start.md` 不作为 fresh baseline 要求 | `trellis init` 基线 |
| `.agents/skills/trellis-continue/SKILL.md` `trellis-finish-work/SKILL.md` | Codex 共享 baseline skills 存在；legacy `start` 不作为 fresh baseline 要求 | `trellis init` 基线 |
| `.codex/skills/parallel/SKILL.md` | 可能存在，也可能不存在；当前 fresh baseline 不应默认假定它存在，只有实际出现时才纳入影响面 | `trellis init` 可能创建的额外目录 |

注意：

- 不要要求 `.claude/skills/` 或 `.opencode/skills/` 另外再镜像 `trellis-start` / `trellis-continue` / `trellis-finish-work`
- 对 Claude/OpenCode，这些 fresh-baseline 入口仍应在命令目录中核对；legacy `start` 只按旧目标项目兼容处理
- 判断 Claude/OpenCode 的阶段能力时，必须先核对 `.claude/commands/trellis/` / `.opencode/commands/trellis/` 这两个正式命令入口；`.claude/skills/`、`.opencode/skills/`、`.agents/skills/` 只作为各自平台的技能面或共享发现面补充，不能单凭“少了若干 skill 目录”就判定漏装
- 看到各 carrier 下的 `.backup-original/` 时，默认先按 intentional restore surface 理解；只要活动入口仍健康、备份没有被误当成现行行为，该目录的存在本身不构成 residual defect

### B. 当前 workflow 安装器托管资产

| 资产 | 期望状态 | 归属 |
|------|----------|------|
| `.trellis/workflow-embed-attempt.json` | 正常成功嵌入后不应存在；若残留，说明目标项目存在未完成或失败的历史嵌入尝试 | workflow 安装器托管 |
| `.trellis/workflow-installed.json` | 必须存在，且字段完整；至少可见 `initial_pack`、`initial_pack_assets`、`initial_pack_target_paths`、`initial_pack_cleanup_policy`、`workflow_shared_docs`、`workflow_doc_cleanup_policy`、`bootstrap_task_removed`、`bootstrap_cleanup_status` | workflow 安装器托管 |
| `.trellis/library-lock.yaml` | 若安装器已成功导入 `pack.requirements-discovery-foundation`，应能看到对应导入记录；当前卸载策略默认保留它 | workflow 安装器导入结果 |
| `.trellis/workflow-docs/finish-work-checklist-template.md` | 必须存在；供目标项目生成 task-local `finish-work-checklist.md` 时作为固定骨架 | workflow 安装器托管 |
| `AGENTS.md` 内 `<!-- workflow-nl-routing-start ... workflow-nl-routing-end -->` | 必须存在 | workflow 安装器托管 |
| `.trellis/workflow.md` 中 workflow patch | 必须存在 | workflow 安装器托管 |
| `.trellis/scripts/workflow/*.py` | helper scripts 已分发 | workflow 安装器托管 |
| `.trellis/scripts/workflow/source-watermark-guard.py` | 若 workflow 默认启用了源码水印保持门禁，则必须存在 | workflow 安装器托管 |
| `.claude/commands/trellis/*.md` | 阶段命令已分发；`continue` / `finish-work` / `parallel` patch 正常；legacy `start` 仅兼容检查 | workflow 安装器托管 |
| `.opencode/commands/trellis/*.md` | 阶段命令已分发；`continue` / `finish-work` / `parallel` patch 正常；legacy `start` 仅兼容检查 | workflow 安装器托管 |
| `.agents/skills/<phase>/SKILL.md` | 阶段 skills 已同步 | workflow 安装器托管 |
| `.codex/skills/<phase>/SKILL.md` | 仅在 `.codex/skills/` 实际存在时才纳入核对；若出现 shared workflow skills，应视为重复副本而不是 fresh baseline 期望产物 | 项目人工维护 / 条件性漂移检查范围 |
| `.agents/skills/trellis-continue/SKILL.md` `.agents/skills/trellis-finish-work/SKILL.md` | 活动 skills 目录中的 Phase Router / finish-work patch 正常；legacy `start` 仅兼容检查 | workflow 安装器托管 |
| `.claude/commands/trellis/parallel.md` `.opencode/commands/trellis/parallel.md` `.agents/skills/parallel/SKILL.md` | 若 baseline 中存在，对应入口在嵌入完成后应已从入口面移除，且 `.backup-original` 保留 baseline 备份 | workflow 安装器托管 |
| `.codex/skills/parallel/SKILL.md` | 仅当 `.codex/skills/` 在目标项目中实际存在时才纳入同类核对；不存在不构成 fresh baseline 异常 | 条件性漂移检查范围 |

补充说明：

- `bootstrap_task_removed` 是向后兼容保留的布尔字段，只表示"本次安装是否实际执行过删除"
- `bootstrap_cleanup_status` 提供更细的状态，例如 `removed`、`absent`、`dry-run-removed`、`unknown`
- `initial_pack_cleanup_policy = retain-imported-assets` 表示 `pack.requirements-discovery-foundation` 导入出的 `spec / templates / checklists / library-lock / library-assets` 默认为**保留**
- `initial_pack_assets` / `initial_pack_target_paths` 用于显式记录这次自动导入 pack 的具体 asset ids 与目标路径，避免只看到 pack 名却不知道实际落了哪些文件
- 原因：这些 library 资产可能已经与目标项目后续手动导入或本地修改合并，workflow 卸载不会自动删除它们，以免误伤项目资产
- `workflow_doc_cleanup_policy = remove-on-uninstall` 表示 `.trellis/workflow-docs/` 下由 workflow 分发的执行卡与 checklist 模板属于 workflow 托管资产，卸载时应删除
- 判断 bootstrap task 的真实现状时，应结合 `.trellis/tasks/00-bootstrap-guidelines` 是否仍存在一起看，不要单看其中任一字段
- `.backup-original/` 目录的核对重点是“对应活动入口是否仍存在、恢复目标是否仍成对可用、备份内容是否被错误当成当前合同”，而不是“看到备份目录就直接记为脏残留”

### C. 仍需人工维护的项目资产

| 资产 | 期望状态 | 归属 |
|------|----------|------|
| `.claude/settings.json` `.claude/settings.local.json` | 与项目 MCP / 权限策略一致 | 项目人工维护 |
| `.claude/hooks/*.py` | 能继续做会话 / 子代理上下文注入 | 项目人工维护 |
| `opencode.json.instructions` | 若项目选择使用该配置面，应与当前主入口文档挂接关系一致；缺失不单独构成安装失败 | 项目人工维护 |
| `.opencode/plugins/*.js` `.opencode/package.json` | 能继续注入上下文 | 项目人工维护 / Trellis baseline |
| `.codex/config.toml` | `AGENTS.md` fallback 与项目配置正常 | 项目人工维护 |
| `.codex/hooks.json` `.codex/hooks/inject-workflow-state.py`（以及如仍接线则连同 `.codex/hooks/session-start.py`） | Codex 当前必需 carrier 是 turn hook；若项目额外保留并接线 `session-start.py`，该 startup 辅助面也必须保持强门禁语义，不能保留 legacy READY/NOT READY | 项目人工维护 / Trellis baseline |

- 不要把 `.codex/hooks/inject-subagent-context.py` 当作 Codex fresh-baseline 必需项去和 Claude/OpenCode 做同形态对比
- 当前主合同是 `codex.dispatch_mode = inline` + turn-level hook；显式 delegated / non-inline 路径的上下文读取由 agent/self-loading 或平台前导负责

## Step 3：Codex 双 skills 目录单独核对

这是最容易遗漏、也最容易产生历史漂移的点。

### 事实边界

- `.agents/skills/` 是共享 / 通用 workflow skills 的唯一主承载面，也是当前证据下 Codex 的 repo-scoped skills 主入口
- `.codex/skills/` 是 `trellis init` 之后**可能出现**的 secondary carrier；只有该目录实际存在时，才继续核对其中的 Codex 特有、本地侧 skills 或重复 shared skill 漂移
- 当前 workflow 安装器只向 `.agents/skills/` 写入共享阶段 skills
- **活动 skills 目录** = `resolve_codex_skills_dir(root)` 解析出的主目录，当前 `trellis init` 下通常是 `.agents/skills/`
- `trellis-continue` / `trellis-finish-work` patch 只打在**活动 skills 目录**
- `trellis-start` / `trellis-continue` / `trellis-finish-work` 若不在 `.codex/skills/`，应先检查 `.agents/skills/`；不要把 secondary carrier 的空目录或缺少 shared skill 直接判成漏装
- legacy `start` 仅作为旧目标项目兼容输入，不是当前 fresh baseline 要求
- Codex 当前合同不要求项目级 `.codex/commands/`；判断 `WS-008` 这类“Codex carrier incomplete”问题时，先看 `.agents/skills/` 主承载面与 hooks / agents，再看 `.codex/skills/` 这个 secondary carrier

### 最小核对命令

在目标项目根执行：

```bash
# 前 4 条是 workflow 通用前提与共享 patch 核对，不是 Codex 特有检查
git remote get-url --push --all origin | wc -l
rg -n "workflow-nl-routing-start|workflow-nl-routing-end" AGENTS.md
rg -n "<!-- workflow-projectization-patch -->" .trellis/workflow.md
rg -n "pack.requirements-discovery-foundation" .trellis/library-lock.yaml

# 下面才是 Codex skills 目录专项核对
test -d .agents/skills
test -d .codex/skills || true
test -f .agents/skills/trellis-continue/SKILL.md
test -f .agents/skills/trellis-finish-work/SKILL.md
ls .agents/skills/parallel/SKILL.md 2>/dev/null
ls .codex/skills/parallel/SKILL.md 2>/dev/null
test ! -f .claude/commands/trellis/parallel.md
test ! -f .opencode/commands/trellis/parallel.md
test ! -f .agents/skills/parallel/SKILL.md
test ! -f .codex/skills/parallel/SKILL.md
ls .claude/commands/trellis/.backup-original/parallel.md 2>/dev/null
ls .opencode/commands/trellis/.backup-original/parallel.md 2>/dev/null
ls .agents/skills/.backup-original/parallel/SKILL.md 2>/dev/null
ls .codex/skills/.backup-original/parallel/SKILL.md 2>/dev/null
```

核对规则：

- `git remote get-url --push --all origin | wc -l` 的结果应至少为 `2`
- `AGENTS.md` 中同时要能看到 `TRELLIS` managed block 与 `workflow-nl-routing` 区段；后者是 workflow 安装器托管面
- `.trellis/workflow.md` 应包含 `<!-- workflow-projectization-patch -->`
- `.trellis/library-lock.yaml` 是需求发现基础资产导入结果的直接证据；若该文件不存在，先回看安装器输出和 `trellis-library/cli.py assemble --auto` 的执行结果，不要直接把问题归因成命令 patch 漂移
- 若 `.trellis/library-lock.yaml` 存在但没有 `pack.requirements-discovery-foundation`，先对照 `.trellis/workflow-installed.json` 中的 `initial_pack`，再人工重跑一次 `trellis-library/cli.py assemble --target <project> --pack pack.requirements-discovery-foundation --auto`
- `.trellis/spec/universal-domains/project-governance/readme-governance/` 应存在；它是目标项目默认 README 双语治理规则的直接证据
- `workflow-state.py route` 的输出契约必须以 `stage` + `status` 为准；`Stage-Status` 只是 hook / session header 的展示字段，不是 route JSON 的主字段。若后续修改 workflow 或升级 Trellis，先核对 `commands/shell/workflow-state.py` 的 route 输出，再检查 `patch-inject-workflow-state.py`、`patch-session-start-strong-gate.py`、`patch-task-status-view-strong-gate.py` 是否仍按 `status` 读取
- 非活动目录中的 `trellis-continue` / `trellis-finish-work` 不属于当前 workflow patch 托管面，不应按“缺 patch = 漂移”处理；legacy `start` / `finish-work` 同理不构成 fresh-baseline 要求
- 当前 fresh baseline 默认应先观察到 `.agents/skills/`；`.codex/skills/` 只有实际存在时才继续检查其条件性影响面，不应预设为必然目录，也不应在装后“通过标准”中被默认要求存在
- 只要 baseline 里存在 `parallel`，安装后就应确认该入口已从嵌入面移除，同时 backup 仍在
- 只要 `.codex/skills/` 存在，就必须被算进装后影响面，而不是忽略
- 对 Codex 的 `start`/首次路由，不要把 `.codex/hooks.json` 未接 `SessionStart` 直接判成异常；当前默认主路径是 turn-level hook，只有目标项目额外接线时才把 `session-start.py` 视为 startup 辅助面
- 缺少 `.codex/commands/` 本身不构成 fresh-baseline 异常；只有共享主承载面、hook 挂接或 agent/self-loading 合同出现缺口时，才继续判定为 Codex carrier 不完整

### 双 skills 目录核对矩阵

| 资产类型 | `.agents/skills/` | `.codex/skills/` |
|----------|-------------------|------------------|
| 阶段 skills（`feasibility` 到 `delivery`） | 安装器写入的共享承载面，也是当前证据下 Codex 的 repo-scoped skills 唯一主承载面 | 不应出现重复 shared skills；若目录存在，只应作为 secondary carrier 出现 |
| `trellis-continue` / `trellis-finish-work` patch | 只在活动 skills 目录检查与增强 | 非活动目录默认不要求存在 patch |
| `parallel` 入口移除 | 命令/skill 应不存在，但 backup 应保留 | 命令/skill 应不存在，但 backup 应保留 |
| legacy `start` | 仅旧目标项目兼容检查 | 不应作为 fresh baseline 或 shared deployment 要求 |

## Step 4：收尾链路单独核对

当前 workflow 的 close-out 使用 Trellis 原生 `/finish-work`。当前 Trellis 0.5 fresh baseline 的真实收尾链路是 `delivery` → Trellis 原生 `/finish-work`。

至少确认：

- 当前 `finish-work` / `trellis-finish-work` close-out patch 正常
- `archive` 仍来自目标项目 Trellis baseline，而不是由当前 workflow 重新分发
- session record 直接复用 Trellis 原生 `add_session.py`

可用命令：

```bash
rg -n “add_session.py|task.py archive” .trellis/workflow.md .claude/commands/trellis/finish-work.md .opencode/commands/trellis/finish-work.md .agents/skills/trellis-finish-work/SKILL.md 2>/dev/null
```

## 通过标准

装后核对通过，至少应满足：

- `upgrade-compat.py --check` 通过
- `AGENTS.md` 的 `TRELLIS` managed block 与 `workflow-nl-routing` 区段都存在
- `.trellis/workflow-installed.json`、`.trellis/workflow.md`、`.trellis/library-lock.yaml` 状态正确
- `.agents/skills/` 已被实际检查过；`.codex/skills/` 仅在该目录真实存在时才继续检查其条件性影响面
- Claude/OpenCode 的阶段能力已按“命令目录优先、技能目录补充”的顺序判断，而不是只看 `.claude/skills/` / `.opencode/skills/`
- 各 carrier 的 `.backup-original/` 已按恢复面而非 residual defect 口径复核
- 手动维护资产未被误写成“安装器托管”

若以上任何一项无法证实，应明确记为“未验证”或“有漂移风险”，不要默认视为健康。
