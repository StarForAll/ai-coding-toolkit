## 图 0：两层分工总览

〔设计稿 §1.2〕基底（Trellis 机制层）负责"任务怎么走"；工作流模块只新增**依赖机制**，负责"项目怎么开始与结束、任务按什么顺序走"。

```mermaid

        B2["三阶段工作流<br/>Plan → Execute → Finish"]
        B3["上下文注入<br/>spec / jsonl 清单 / 面包屑"]
        B4["规格 .trellis/spec/<br/>会话日志 workspace/<br/>任务树 / 归档区"]
        B5["工作流可变体<br/>.trellis/workflows/&lt;id&gt;.md"]
    end
    subgraph WF["工作流模块（新增，虚线）〔设计稿 §7〕"]
        direction TB
        W1["依赖账本（状态事实源）"]
        W2["前置集合（唯一事实源）"]
        W3["DAG 视图 / 下一个集合 / 返工集合（派生）"]
    end
    BASE -.->|"模块复用基底，不重造任务状态机<br/>〔设计稿 不变量 1〕"| WF
```

基底关键机制（源码事实）：

- 任务生命周期命令：`task.py create`（写 `status=planning`，并自动设会话活动任务指针）、`start`（`planning`→`in_progress`）、`finish`（仅清除活动指针，不改状态）、`archive`（写 `status=completed` + `completedAt`，目录移入 `archive/{年-月}/`，删除指向它的会话指针，自动提交）。〔Trellis workflow.md / task.py `cmd_archive`〕
- 任务状态由生命周期命令写入的取值只有三个：`planning` / `in_progress` / `completed`。〔Trellis task.py〕（`list --status` 的帮助文字里还提到 `review` 过滤值，但没有任何生命周期命令会写入它，本图不使用。）
- 工作流三阶段：Phase 1 Plan（1.0 建任务 → 1.1 需求探索 → 1.2 研究 → 1.3 配置子代理上下文 → 1.4 激活）→ Phase 2 Execute（2.1 实施 → 2.2 质量检查 → 2.3 回退）→ Phase 3 Finish（3.2 调试复盘 → 3.3 规格更新 → 3.4 提交 → 3.5 收尾）。〔Trellis workflow.md〕
- 工作流变体：任务可用 `task.json.workflow` 钉住一个变体文件（`.trellis/workflows/<id>.md`）；解析优先级 per-task > personal(`.developer`) > `default_workflow` > 全局 `workflow.md`。〔Trellis config.yaml〕
- 生命周期 hooks：`after_create / after_start / after_finish / after_archive`。〔Trellis workflow.md / config.yaml〕

## 图 1：项目全生命周期（四段结构）

〔设计稿 §4.1〕一个项目从头到尾的四段：

```mermaid

    end
    subgraph SEG2["② 任务层（0→1，串行）"]

    end
    subgraph SEG3["③ 收尾层（一次）"]
        F["收尾任务<br/>验收 + 交付 + 发布 + 复盘"]
    end

        IT["迭代任务 / 无关任务<br/>（普通流程，可无依赖）"]
    end

    Tn -->|"链上全部完成"| F
    F -->|"项目完成 = 收尾任务完成<br/>〔设计稿 §4.3〕"| IT
```

各段出口（〔设计稿 §4.1 表〕）：

| 段 | 承载 | 出口 |
|---|---|---|
| 项目层 | 项目层任务 P | 人确认 + P 正常归档 |
| 任务层 | 实现任务 | 人判 + 正常归档 |
| 收尾层 | 收尾任务 | 人验收 + 归档 |
| 持续使用 | 普通任务 | 原生流程 |

> 返工不改四段结构：返工任务插在当前任务之前，是图内正常任务；"返工"动作通过依赖级挂起实现。〔设计稿 §4.1〕

## 图 2：单个任务完整生命周期（基底阶段 × 依赖机制）

这是全流程的核心图。左侧是基底三阶段（Trellis 源码事实），右侧标注依赖机制在各关卡插入的动作（设计稿）。**图内任务**（P、实现任务、返工任务、收尾任务）走完整路径；**图外任务**（无关任务、迭代任务）只走基底原生路径，不走依赖机制入口。〔设计稿 不变量 5、§9.2〕

```mermaid
flowchart TD
    A(["人：轮到该任务<br/>（图内任务：DAG 视图最早就绪）〔设计稿 §7.6、§9.1〕"]) --> A2{"开工前对账<br/>前置集合/账本/视图一致？〔设计稿 §7.7〕"}
    A2 -->|不一致| FIX["待对账修复：人发起、机制执行<br/>〔设计稿 §7.7〕"] --> A2
    A2 -->|一致| GATE{"开工门禁<br/>前置全部「正常」 + 规划确认<br/>〔设计稿 §4.5〕"}

    GATE -->|"前置不满足"| HOLD["停在规划态（不开工）<br/>〔设计稿 §7.5〕"]
    GATE -->|"满足（图外任务跳过此门禁，<br/>走原生入口）"| P1

    subgraph PHASE1["Phase 1 · Plan（任务状态：规划中/planning）〔Trellis workflow.md〕"]
        P1["1.0 task.py create<br/>status=planning，建目录+prd.md"]
        P1 --> P2["1.1 需求探索（brainstorm）<br/>prd.md；复杂任务补 design.md + implement.md"]
        P2 --> P3["1.2 研究（可选）<br/>产物写 research/"]
        P3 --> P4["1.3 配置子代理上下文<br/>implement.jsonl / check.jsonl"]
        P4 --> P5["1.4 规划评审门禁 + task.py start<br/>status: planning → in_progress"]
    end

    P5 --> S1[("task.json<br/>status=in_progress")]

    subgraph PHASE2["Phase 2 · Execute〔Trellis workflow.md〕"]
        S1 --> E1["2.1 实施<br/>（子代理 trellis-implement / 内联编辑）"]
        E1 --> E2["2.2 质量检查<br/>（trellis-check：spec 合规 + lint + typecheck；<br/>最后一轮须全范围检查）"]
        E2 --> E3{"检查发现 PRD 缺陷？"}
        E3 -->|是| E4["2.3 回退：回 Phase 1 修 prd.md 再实施"]
        E4 --> E1
        E3 -->|否| E5["3.2 调试复盘（按需）<br/>3.3 规格更新（必需）：经验写回 .trellis/spec/"]
    end

    E5 --> HC(["人判：check 之后<br/>由人决定是否继续收尾<br/>〔设计稿 §4.3 · 不新增记录类型〕"])

    HC -->|"不继续"| E1
    HC -->|"继续"| C1["3.4 提交：AI 按批次计划提交工作改动<br/>（不 amend、不 push）〔Trellis workflow.md〕"]

    C1 --> ARC["归档：task.py archive<br/>status=completed + 移入 archive/{年-月}/<br/>〔Trellis task.py〕"]
    ARC --> LEDGER["账本写「正常」〔设计稿 §5.3/§6.3〕"]
    LEDGER --> VIEW["重建 DAG 视图<br/>下游解锁〔设计稿 §7.5〕"]

    subgraph FINISH["3.5 finish-work（会话收尾）〔Trellis finish-work.md〕"]
        VIEW --> W1["get_context --mode record 盘点"]
        W1 --> W2["脏路径分类：当前任务未提交→回 3.4"]
        W2 --> W3["task.py archive（自动提交 archive commit）"]
        W3 --> W4["add_session.py 记会话日志（自动提交 journal commit）"]
    end

    W4 --> NEXT(["下一任务：<br/>DAG 视图最早就绪 / 收尾任务 / 迭代任务"])
```

**原子收尾**（〔设计稿 §5.3 / §6.3〕）：`人判 → 归档 → 账本写"正常" → 重建 DAG 视图` 四步是一个整体——任一步失败，下游都不能看到"已正常"；失败按对账恢复（图 6），不重放。

**完成的定义**（〔设计稿 §4.3〕）：

```text
任务完成 = 基底完成实施与检查 ∧ 人判 ∧ 已归档
项目完成 = 收尾任务完成
依赖满足 = 前置任务在账本中状态为「正常」
```

- 检查 = 基底 Phase 2.2 的 check（对应 Trellis 的 `trellis-check` 环节）；不要求 sha 级证据链；
- 人判 = check 之后由人决定是否继续收尾，是基底原生流程的一部分，痕迹在会话日志/任务记录中；
- 归档 = 基底 `task.py archive`；归档是完成的必要条件，也是账本写"正常"的前置；
- 推送不参与完成判定；推送由人执行。〔设计稿 §1.1〕

**会话收尾的提交顺序**（源码事实，〔Trellis finish-work.md〕）：`工作提交（Phase 3.4）→ chore(task): archive … → chore: record journal`。

## 图 3：双轨状态流转

〔设计稿 §4.2 / §4.4〕任务状态与依赖状态**分层不互写**：任务状态只由基底的建任务/开工/归档动作写；依赖状态只由机制的收尾/返工/替换/放弃/对账修复动作写。

### 3a 任务状态（基底承载，只有三态）

```mermaid
stateDiagram-v2
    [*] --> 规划中 : 建任务 task.py create〔Trellis task.py〕
    规划中 --> 进行中 : 开工 task.py start<br/>前置全部正常 + 规划确认〔设计稿 表4-1 行2〕
    规划中 --> 已归档 : 正常收尾（人判+归档）<br/>或异常归档（替换/放弃）〔设计稿 表4-1 行3〕
    进行中 --> 已归档 : 同上
```

任务内部的阶段回退（Phase 2.3 回 Phase 1）**不改变**任务状态。〔设计稿 §4.2〕

### 3b 依赖状态（账本承载，四态）

```mermaid
stateDiagram-v2
    [*] --> 正常 : 正常收尾<br/>（人判+归档+账本正常，原子）〔表4-2 行1〕
    [*] --> 挂起 : 发现返工<br/>先记挂起，再建返工任务〔表4-2 行2〕
    挂起 --> [*] : 存在返工任务记录 ∧ 无未归档返工任务<br/>∧ 前置集合全部正常 → 清除挂起〔表4-2 行3〕
    [*] --> 异常 : 替换/放弃<br/>下游重连，原任务异常归档〔表4-2 行4〕
```

对下游的结论（〔设计稿 §7.4〕）：`无记录`→不满足；`挂起`→不满足；`正常`→满足；`异常`→不满足，需重连。

- "正常"只由收尾逻辑或对账修复写入；
- "异常/挂起"不可由派生件重建，必须随版本库保存；账本不自动清理；
- **异常没有例外通道**：下游要继续，只能替换/放弃重连，或删边后不再等待。〔设计稿 §4.4、§7.4〕

## 图 4：返工子流程

〔设计稿 §6.4〕当前任务 T 在执行中发现问题需要返工时：

```mermaid
flowchart TD
    T(["任务 T 进行中，发现需返工的问题"]) --> S1["① 账本把 T 记为「挂起」<br/>T 立即退出就绪集"]
    S1 --> S2["② 新建返工任务 R<br/>R 的前置集合 = T 当前的前置集合（继承）<br/>R 的任务记录标注「返工来源 = T」"]
    S2 --> S3["③ 把 R 加入 T 的前置集合<br/>（不修改 T 的基底任务状态）"]
    S3 --> S4["④ 执行 R：走与普通任务完全相同的<br/>开工门禁 → 实施检查 → 人判 → 归档 → 账本「正常」"]
    S4 --> S5["⑤ 扫描活动区+归档区的任务记录，<br/>取「返工来源 = T」的集合"]
    S5 --> G{"集合非空 ∧ 无未归档成员<br/>∧ T 的前置集合全部正常？"}
    G -->|是| S6["清除 T 的「挂起」<br/>T 回到就绪（即使 T 此前已开工）<br/>重新校验后继续"]
    G -->|否| WAIT["继续等待（执行下一个未归档的返工任务）"] --> S5

    S1 -.->|"崩溃窗口①：挂起已记、R 未建"| CR1["按对账修复：人确认补建 R 或清除挂起〔§7.7〕"]
    S2 -.->|"崩溃窗口②：R 已建、边未加"| CR2["选择规则进入 R；R 收尾时若 T 前置未含 R 先补边"]
    S3 -.->|"崩溃窗口③：边已加"| CR3["状态一致，按正常流程继续"]
```

要点（源出设计稿 §6.4）：

- 返工任务是**图内正常任务**，遵守同一套开工/收尾；"返工"通过依赖级挂起实现，不是另一套任务生命周期；
- 挂起按"返工任务集合"整体清除，不按单个 R 的归档时点清除；已归档的返工任务（正常、被替换或放弃）不再阻塞；
- 集合只从任务记录派生（活动区+归档区），不存 ID 列表；无法解析的记录计入对账不一致，不静默当作"没有返工任务"；
- "返工来源"必须在归档前写入（归档区是只读历史）。

## 图 5：替换与放弃

〔设计稿 §6.5 / §6.6〕任务无法继续或不再需要时的两条处置路径，均属**任务级旁路**（改任务生命周期）：

```mermaid
flowchart TD
    A(["人决定处置任务 X"]) --> B{"方式"}
    B -->|替换| R1["① 新任务继承 X 当前的前置集合"]
    R1 --> R2["② 所有未归档下游（含夹在中间的返工任务）<br/>重连到新任务标识"]
    R2 --> R3["③ 重新检环"]
    R3 --> R4["④ X 的账本记「异常」，备注写新任务标识"]
    R4 --> R5["⑤ X 以异常归档离开活动列表"]
    B -->|放弃| D1{"处置"}
    D1 -->|删边| D2["下游不再等待该任务<br/>记录影响与原因，账本留痕"]
    D1 -->|新建替代| D3["下游改依赖替代任务<br/>走替换的重连规则"]
    D2 --> D4["重连后检环"]
    D3 --> D4
```

特殊情形（源出设计稿 §6.5 / §6.6）：

- 被替换/放弃的 T 处于**挂起**时：其前置 R 不属于"未归档下游"，**不重连**；R 留在图中按普通任务处置；新任务继承 T 的当前前置集合（含 R），仍等待 R；若人决定不再需要 R，按放弃处置 R。
- 替换返工任务 R 时：新任务继承 R 的"返工来源"标记；R 异常归档后不再阻塞 T 的挂起。
- 替换任务自身从"无记录"开始，正常收尾后才记"正常"。

## 图 6：对账与恢复

〔设计稿 §7.7〕三类对账入口 + 唯一修复出口：

```mermaid
flowchart TD
    subgraph CHECKS["对账入口"]
        C1["开工前对账：前置集合/账本/视图一致才允许开工"]
        C2["启动时对账：先重建派生件，再判断就绪"]
        C3["绕过兜底"]
    end
    C3 --> B1{"已归档但账本无记录？"}
    B1 -->|是| STUCK["待对账修复：不放行"]
    C3 --> B2{"账本「正常」但未归档？"}
    B2 -->|是| REP["视为未满足并报告"]
    C3 --> B3{"活动区/归档区有无法解析的任务记录？"}
    B3 -->|是| REP2["报告并计入对账不一致<br/>该记录不参与就绪判定"]

    STUCK --> FIX["对账修复（唯一出口）：<br/>由人发起、机制执行；禁止手改账本"]
    FIX --> F1["① 已归档无账本 → 人确认正常/异常，机制补记"]
    FIX --> F2["② 挂起但找不到返工任务 → 人确认补建 R 或清除挂起"]
    F1 --> REB["重建视图，再按本节对账"]
    F2 --> REB

    BROKEN["机制不可用（账本/入口损坏）"] -.->|"不降级、不绕过〔设计稿 §1.3〕"| UNLOAD["按 §9.4 卸载模块（见 图 8）"]
```

- 不保留操作日志：原子收尾失败时按上述规则恢复到确定状态，**不重放**；
- 仅模块卸载期间用原生流程归档的图内任务，重装后走"对账修复"入口补记账本——这是**设计允许的合法路径**，不是异常。〔设计稿 §9.4〕

## 图 7：入口路由（接手任何会话的第一步）

〔设计稿 §9.1〕任何新会话/新 CLI 接手时的路由表，配合接手四步（〔设计稿 §8.4〕）：

```mermaid
flowchart TD
    Q0(["会话启动 / 接手"]) --> Q1{"机制可用？"}
    Q1 -->|否| UNL["按 §9.4 卸载；修复后重装；不绕过"]
    Q1 -->|是| Q2{"有无项目层任务 P？"}
    Q2 -->|"无"| P0["启动 P：立项 + 基线 + 任务图"]
    Q2 -->|"P 存在且未归档"| P1["只执行 P"]
    Q2 -->|"P 已归档"| Q3{"有当前任务？"}
    Q3 -->|有| P2["继续当前任务"]
    Q3 -->|"无"| Q4{"链上任务全部完成？"}
    Q4 -->|否| P3["取 DAG 视图中最早就绪的实现任务<br/>（按任务创建时间排序）〔§7.6〕"]
    Q4 -->|是| P4["进入收尾任务"]
    P4 -.->|"收尾任务完成 = 项目完成"| P5
    Q2 -.->|"需要改基线"| BL["回到 §5.5 基线变更：<br/>更新项目文档 → 更新依赖图 → 不追溯已归档任务"]
```

**接手四步**（〔设计稿 §8.4〕）：① 读 DAG 视图确认就绪任务 → ② 读账本确认前置状态与挂起项 → ③ 读任务记录与基线确认要做什么 → ④ 异常按图 4 崩溃规则 / 图 6 对账修复处理，不直接放行。AI 的意图叙述只作补充，不作位置判定依据。

## 图 8：机制不可用与卸载

〔设计稿 §9.4〕机制不可用时**没有绕过的降级路径**，唯一恢复动作是卸载：

```mermaid
flowchart TD
    M(["机制不可用<br/>（账本/入口损坏）"]) --> D{"卸载模式（人显式选择）"}
    D -->|"仅模块卸载（默认）"| U1["删除：工作流模块与依赖机制入口<br/>保留：任务、账本、日志、规格、基线等项目数据"]
    D -->|"完全卸载"| U2["删除：模块 + 项目数据<br/>保留：仅基底与项目代码"]
    U1 --> U3["原生 Trellis 独立使用：<br/>建任务 / 开工 / 归档均可"]
    U2 --> U4["依赖历史不可恢复；<br/>重新使用需从零建图"]
    U1 -->|"修复后重装"| R1["按 §7.7 对账：账本与前置集合继续有效"]
    R1 --> R2["卸载期间用原生流程归档的图内任务<br/>→ 对账修复入口补记账本（合法路径）"]
```

- 卸载由人发起并选择模式；AI 可协助执行，但必须显式说明模式与影响，不得代替人决定完全卸载；
- 两种模式都必须满足：卸载后原生 Trellis 可独立建任务、开工、归档，不留下阻断原生流程的状态或文件。
