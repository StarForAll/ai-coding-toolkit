# 1.2 方向：零补丁嵌入方案（v4 · 单人单分支 · 原生优先）

> 定位：在 `trellis init --claude --codex --pi --dsh -y -u xzc`（可扩展）之后，把 v20 工作流作为**零补丁模块**嵌入目标项目。
> 依据：设计正文 [workflow-design.md](workflow-design.md)（v20）——**位置与引用口径见 §9 第 1 条**。标注：`实测` = 本机命令输出；`文件:行` = 源码；其余为推断并标明。
> **v4 = 依据使用者确定的工作场景（单人 · 同一工作线 · 不切分支 · 合入由人手动）做一次结构性收敛**：证据层压到最小可复核形态、合入链路整块移除、能用 Trellis 原生实现的全部改回原生（§0.2）。
> 路径约定：`IW`/`WA`/`SH` = 旧模块（**仍在 `docs/workflows/新项目开发工作流/`，P0 才整体移入 `tmp/`**，见 D6）的 `commands/install-workflow.py` / `commands/workflow_assets.py` / `commands/shell/*`；实验载体 `tmp/feas-a`、`tmp/feas-b`、`tmp/feas-multi`。

### 0.2 一句话结论

写入面 = **1 行**（`.trellis/config.yaml` 的 `default_workflow: wf`，D18）。**自造机制只剩两样**：一个薄 CLI（`.trellis/scripts/wf/**`，读写原生 `task.json` / 调用原生脚本）与一份流程变体（`.trellis/workflows/wf.md`）。相比 v3：**记录子系统（一记录一文件 + 哈希链 + 11 类记录）整体删除**，改为 Trellis 原生 `task.json` 的 `meta.wf.*`；**合入链路（候选 / 冒烟 / 判交集 / 闸门 / 推进主干 / 三类判因）整体删除**（D20）；**skill 从 3 个减到 2 个**；**自造 git hook 接管删除**。

## 2. 关键实证

### 2.1 零补丁拿到阶段注入（`tmp/feas-a`，实测）

变体 `.trellis/workflows/wf.md` + `.developer` 一行 `workflow=wf` + `task.json.status = design`，**未改任何上游文件**：面包屑注入自定义门禁文案、SessionStart 注入变体 Phase Index、`get_context.py --mode phase --step 1.1` 返回变体正文。机制：面包屑按 `task.json.status` **原样**查 `[workflow-state:<status>]`（字符集 `[A-Za-z0-9_-]+`，冒号非法）；`task.py:115` 只在 `status == "planning"` 时翻转。

### 2.2 受管文件编辑的漂移差异（实测 `trellis update --dry-run`）

| 编辑 | 结果 |
|---|---|
| `AGENTS.md` 在 `<!-- TRELLIS:START/END -->` **块外**追加 | **无漂移**（`update.ts` 的 `buildAgentsMdTemplate` 先把**当前文件**的块替换成新块再比较，块外字节原样保留 → 命中 `unchangedFiles`） |
| `.trellis/config.yaml` 追加/修改一行 | **有漂移**（`analyzeChanges` 只遍历模板文件集，`config.yaml` 在内；哈希不符 → `changedFiles`） |
| 新增**模板里没有**的路径（如 `.trellis/workflows/wf.md`、`.agents/skills/wf/`） | **不进漂移清单**（`analyzeChanges` 不扫目录树） |

→ 三条合起来就是"零补丁"的地基：**块外追加安全、`config.yaml` 那一行必被看见、新增路径不被管**。

| journal 有提交哈希（且 `add_session` **强制能解析**，否则中止），但 `Testing` 段是占位符 `- [OK] (Add test results)` | `add_session.py:391-416`、本仓库 `.trellis/workspace/xzc/journal-7.md` |

### 4.2.1 项目级契约（v20 §6.1/§11.1 的落地；D23）

**为什么单列**：v20 §6.1 规定了项目级三节点，其中**定标**的出口是"范围基线冻结 + 最小受管路径模式与验收面入口 + **契约获人确认（初始锚点）**"，并且写死一条硬前置——**"契约未定不应开任务"**；§11.1 又规定"契约未定则先做项目定标，**不开任务**"。同时契约是**术语级定义**（§3：范围基线 + 验收面 + 受管资产清单），被三处消费：`verify` 的验收项推导、受管资产判定、档位下限。

**结论**：契约必须有**可落盘、可确认、可被后续命令读取**的载体。它不能放进原生字段（`task.json` 是任务级；`meta` 的语义是任务元数据，§4.12 禁止挪用），也不能靠 `AGENTS.md` 的追加段（只能承载摘要，不能承载结构化清单）。因此**恰好恢复一个模块自有文件**：

```yaml
# .wf/contract.yaml —— 项目级定标的唯一产物（受管内容，随版本库）
scope_baseline: ["src/**", "tests/**", "docs/**"]     # 范围基线 + 最小受管路径模式（v20 §11.1 冷启动判下限）
acceptance:                                            # 验收面：验收项由它推导，不由人手填
  - { id: lint,      cmd: "pnpm lint",          level: required }
  - { id: typecheck, cmd: "pnpm typecheck",     level: required }
  - { id: test,      cmd: "pnpm test --run",    level: required }
managed_assets:                                        # 受管资产清单（G-A 单独确认的依据）
  - .trellis/scripts/wf/**
  - .trellis/workflows/wf.md
  - .wf/contract.yaml
integration_branch: main                               # v20 §3：必须由契约声明，不得硬编码
confirmed: { by: xzc, at: "2026-10-17T09:00:00Z", channel: "tty-token" }   # 初始锚点（人确认的证据）
```

**三个命令（最小集）**：

| 命令 | 作用 | 门禁 |
|---|---|---|
| `wf contract init` | 交互式生成草案：扫描仓库给出建议的 `scope_baseline` / `acceptance` / `managed_assets` | 已有契约则拒绝（除非 `--edit`）；**不写 `confirmed`** |
| `wf contract show` | 只读展示 + `--json` | — |
| `wf contract approve` | **人逐项确认**后写 `confirmed`（TTY + 令牌 `APPROVE-CONTRACT`） | **人类专用入口**；这是 v20 §13 的"初始锚点" |

**入口门禁矩阵（改为可执行判据）**：

| 命令 | 前置（fail-closed） | 违反时 |
|---|---|---|
| `wf task new` | 契约存在 **且** `confirmed` 非空 | 拒绝并指引："先做项目级定标：`wf contract init` → 逐项确认 → `wf contract approve`" |
| `wf verify`（不带 `--checks`） | — | 用契约 `acceptance` 中全部 `level: required` 的检查 |
| `wf verify --checks a,b` | 每个名字都在契约 `acceptance` 里 | 拒绝："契约里没有该检查项"（**不允许人手填契约外的检查**） |
| `wf verify`（受管资产判定） | — | 读契约 `managed_assets`，本任务若改过其中路径 → 拒绝并要求单独提交确认（v20 §5.5） |
| 档位下限（v20 §11.1） | — | 以 `scope_baseline` 判断"是否触碰受管路径"，据此判轻/常规 |
| `wf declare` / `wf close` | 契约仍存在且 `confirmed` 有效 | 契约被删或被改到未确认状态 → 拒绝（证据链断了） |

**与 v4 前几版的关系（如实登记）**：

| 版本 | 当时的做法 | 问题 |
|---|---|---|
| v3 | `.wf/{contract,checks,managed-paths,micro-whitelist,drift-allowlist,probes,run_config}.yaml` 七件套 | 过度设计（七个文件里有五个在最小形态下没有消费者） |
| v4 初版 | **七件套全删**，声称"验收面在 `prd.md`、检查项用 `--checks` 手填" | **过度收敛**：`prd.md` 是任务级件，撑不起项目级契约；`--checks` 手填使"从验收面推导"退化为人工记忆；且 `task new` 不再检查契约 → **直接违反 §6.1/§11.1** |
| **v4 修正（本版）** | **只保留 `contract.yaml` 一个**，七件套里其余六个仍删 | 契约有落点，门禁可执行，未引入多余文件 |

**项目级"设计"与"计划"两个节点**：v20 §6.1 要求它们的出口是"架构确认；发布与回滚策略"、"里程碑与交付物边界确认"，**均由人确认**，产物是宿主文档（`docs/` 或任务 `design.md`）。**模块不为它们造机制**（没有可自动判定的完成态），但**流程上必须执行**——这一点与"定标"不同：定标有契约这个可落盘的产物，所以模块给了机制；设计与计划没有，所以模块只承认它们由人承担，**不假装能验证**。

### 4.3 状态与门禁模型（D1 = A2）

**唯一权威**：`task.json.status`（Trellis 原生字段，所有 CLI 都读它），由 `wf` 写；**证据在 `meta.wf.*`**，由 `wf state` 读取并做"是否过期"判定。

| 语义 | `task.json.status` | 变体中的块 | 写入者 |
|---|---|---|---|
| 待办（已登记未开工） | `planning`（上游原生） | `[workflow-state:planning]` | `wf task new` |
| 实施中 | `wf-impl` | `[workflow-state:wf-impl]` | `wf start` |
| **待验证**（已声明完成） | `wf-verify` | `[workflow-state:wf-verify]` | `wf declare` |
| **已验证**（证据有效） | `wf-verified` | `[workflow-state:wf-verified]` | `wf verify` |
| 旁路：阻塞 / 暂停 / 终止 | `wf-blocked` / `wf-paused` / `wf-terminated` | 三个块 | `wf bypass` |
| 降级兜底：有人直调上游命令 | `in_progress` | `[workflow-state:wf-degraded]` | 上游 `task.py start` |
| 收口（归档会移走目录，块基本不会被看到） | `completed`（上游原生） | `[workflow-state:completed]` | `wf close` → 上游 `archive` |

**为什么保留自定义状态值**（而不是全部用原生三态）：上游 `planning`/`in_progress`/`completed` 无法表达"待验证 / 已验证"这两个证据状态，而**面包屑与 `task.py list` 都直接读 `status`**——把状态放在原生字段里，才能让**所有 CLI、所有原生命令**看见它（这是"原生优先"的用法，不是自造机制）。

> **注意上游的一个已知空白**（实测，`templates/trellis/workflow.md:131-134`）：`[workflow-state:completed]` **当前是死块**——`cmd_archive` 在同一次调用里改 `status` 并移走目录，解析器随即失去指针。所以收口后的状态不依赖面包屑，由 `task.py list-archive` 与 journal 呈现。

#### 4.3.1 任务生命周期与上游 `task.py` 的集成

`wf` **不重建任务系统**，只做三件事：固定参数、写状态、加门禁。命令分工：

| 动作 | 唯一入口 | 对上游的调用 | 写入 | 提交动作 |
|---|---|---|---|---|
| 建任务 | `wf task new` | **先查契约**（`.wf/contract.yaml` 存在且 `confirmed` 非空，否则拒绝）；再 `task.py create --description … --workflow wf --base-branch <当前分支>`（`--base-branch` 显式传，避免 `origin/HEAD` 推断与离线时的网络调用） | `task.json`（原生 create） | 由人/`session_auto_commit` 决定，见 §4.3.1.1 |
| 开工 | `wf start` | `task.py start --allow-empty-context` → `task.py set-branch <task> <当前分支>` → 写 `status=wf-impl` | `task.json`（`status`、`branch`） | 同上 |
| **声明完成** | `wf declare` | — | `status=wf-verify` + `meta.wf.impl_sha = <当前 HEAD>` | 同上 |
| 验证 | `wf verify --checks …` | 跑检查（**代码质量审查仍用上游 `trellis-check`**） | `status=wf-verified` + `meta.wf.verification = {sha, checks, result, at}` | 同上 |
| 收口 | `wf close` | 判定 → `task.py archive` → `add_session.py` | 原生归档（`status=completed`） | 上游 archive 自带的窄范围 auto-commit |
| 旁路 | `wf bypass {block\|pause\|terminate\|resume}` | — | `status=wf-*` + `meta.wf.bypass = {kind, reason, from_state, at}` | 同上 |

**上游三条约束的处置**（实测）：

| 上游约束 | 证据 | 处置 |
|---|---|---|
| `task.py start` 有 **context-manifest 门**：`implement.jsonl`/`check.jsonl` 已创建但无 curated 条目时拒绝 | `task.py:197-217` | `wf start` 固定传 `--allow-empty-context`——**明确决策不是绕过**：本工作流不派 Trellis 子代理，manifests 天然为空，该门保护的对象在本模块不存在 |
| `task.py archive` **先强制写 `status=completed` + `completedAt` 再移动目录** | `task_store.py:1382-1384` | 与 A2 终态一致，**不冲突**；`wf close` 的顺序必须是"**先判定证据有效 → 才调 archive**" |
| `task.py archive` 有**分支元数据门** | `task_store.py:1208-1275` | 见 §4.3.2 |

##### 4.3.1.1 提交与检查点的归属（原生优先）


**模块不新增提交机制**：

1. `session_auto_commit`（上游 `config.yaml`，默认 `true`）统辖两处原生自动提交——`add_session.py` 的 journal 与 `task.py archive` 的归档；两者路径由 `.trellis` 内部状态推导，**不含其他文件**；
2. 因此 `wf` 写进 `task.json` 的**状态与证据**（`status`、`meta.wf.*`）由**检查点提交**带走：与代码改动一起提交，或在 `wf close` 时随归档提交落地；
3. `wf verify`/`wf declare` **写完即提示一次**："`task.json` 有未提交的状态/证据变更"（人决定何时提交，**不自动 `git commit`**）；
4. **`amend`/`rebase`/`squash` 不禁止也不检测**——证据绑的是"提交 sha"，历史被改写只会让 sha 对不上而要求重验，属**自然失效**，不需要额外纪律；
5. `session_auto_commit: false` 时模块行为不变（它本来就只管上游那两处）。

> **v3 的"记录提交机制"整节随之删除**（V1）：那时记录是**独立文件**、必须由写它的命令自己提交，否则进不了合入范围；现在证据在 `task.json` 里，随任务检查点走，**没有独立提交问题**。

#### 4.3.2 分支相关：模块对分支零假设，但有三个原生字段要处理

**上游事实（实测）**：

1. `task.py archive` 的分支门有两条硬拒绝：① `branch == base_branch`（*"A PR cannot target its own branch"*，`task_store.py:1246-1255`）；② **`branch` 缺失 且 有 `base_branch` 且 仓库有 remote**（`task_store.py:1266-1275`）。另有一条**只告警不拦**的：已记录的 `branch` 在本地不存在（`:1233-1241`）；
2. `task.py start` 只在 `branch` 为空时填**当时 checked-out 的分支**，且自指只告警（`task.py:112-166`）；
3. `task.py set-branch` / `set-base-branch` 可任意写这两个字段；
4. `base_branch` 的推断顺序：显式 `--base-branch` → `resolve_default_branch()`（`origin/HEAD`，退化到 `git remote show origin`，**可能联网**）→ 当前分支（并告警）。

**处置（不改上游、不靠纪律）**：

- `wf task new` **显式传 `--base-branch <当前分支>`** → 永不产生"`branch` 缺失 + 有 `base_branch` + 有 remote"的组合，也避免联网推断；
- `wf start` 在调用原生 `start` 后，用原生 **`set-branch`** 把 `branch` 写成当前分支（幂等，覆盖旧值）→ 第二条门永不触发；单分支场景下 `branch == base_branch`，属上游**只告警**的情形；
- `wf close` **不传 `--skip-branch-validation`**（默认路径就能过门）；若某次因环境差异被拒，输出上游给的修复指引，`--skip-branch-validation` 只作**显式逃生口**并计入 `wf doctor` 的提示；
- **模块不要求、不检查、不记录"任务分支"**：不建分支、不切分支、不建工作单元；`task.json.branch` 只是上游字段，值等于当前工作线。

##### 4.3.2.1 准洁净验证的"独立工作单元"（原生实现）

v20 的准洁净要求"独立工作单元 + 按锁定装依赖 + 不读工作区未受管内容"。最小形态下**不引入工作单元映射**：

- 准洁净验证由 `wf verify --level quasi-clean` 触发，用**原生的 `git worktree add <临时路径> <当前 HEAD>`** 建一个临时检出，在其中装依赖、跑检查，**用完 `git worktree remove` 删除**；
- 临时路径写进 `.wf/.install-record.json` 的易失段（或直接用 `mktemp -d`），**不进版本库、不需要 `task.json` 字段**；
- 失败或中断时**必须自清理**（`trap`/`finally`）；残留由 `wf doctor` 提示 `git worktree prune`；
- 默认级别 = `in-place`（原地）；`--level quasi-clean` 由人显式指定（**不再有三级分级机制**，V2）。

> 这样既满足 v20 §5.7 的准洁净语义，又**没有自造工作单元子系统**。

#### 4.3.3 状态派生（最小实现）

派生只读三样：`task.json.status`、`meta.wf.*`、当前 `HEAD`。

| 派生结论 | 判据 |
|---|---|
| 待办 / 实施中 / 待验证 | 直接取 `status`（`planning` / `wf-impl` / `wf-verify`） |
| **已验证（证据有效）** | `status == wf-verified` **且** `meta.wf.verification.sha == 当前 HEAD` |
| **已验证（证据过期）** | `status == wf-verified` 但 `sha != HEAD` → 输出"证据过期，请重新 `wf declare` + `wf verify`" |
| 旁路 | `status ∈ {wf-blocked, wf-paused, wf-terminated}`，恢复落点取 `meta.wf.bypass.from_state` |
| 降级 | `status == in_progress`（有人直调上游）→ 提示运行 `wf sync` 修复 |
| 不一致告警 | `status == completed`（已归档）但**无** `meta.wf.verification` → 提示"该任务无验证证据"（只告警，不改状态） |

**这就是"完成判定"的全部**：模块内终态是 **`wf-verified` + 证据有效**；**是否落到主干由人负责，模块不判定**（D20）。

> **v3 的派生表（五态 + `task_integrated`）+ §4.11（变更集路径域 / 两个范围）+ §4.5.1（11 类记录）随之删除**（V1/V2/V3）。

**skill 集合（2 个，D15）**：

| skill | 触发意图（description 要点） | 调用的 `wf` 子命令 |
|---|---|---|
| `wf` | "下一步做什么 / 当前任务处于哪个节点 / **证据是否还有效** / 要不要开任务 / 交接" | `route`、`state`、`summary`（只读）；`task new`、`start`、`close`（有副作用） |
| `wf-verify` | "任务做完了 / 该验证了 / 要留证据 / **任务卡住了要暂停或阻塞**" | `declare`、`verify`、`bypass`（有副作用）；`records`（只读，输出 `meta.wf.*` 与检查历史） |

**description 必须写清与上游 skill 的分工**（否则模型会在同一意图上随机选）：

| 我们的 skill | 与它重叠的上游 skill | 分工写法（要点） |
|---|---|---|
| `wf` | `trellis-start`、`trellis-continue` | "本项目**下一步做什么以 `wf route` 为准**；`trellis-start/continue` 是上游 Trellis 流程的入口，本项目不使用其阶段语义" |
| `wf-verify` | `trellis-check` | "这是 wf 工作流的**证据与门禁**层（验证记录 / 版本绑定 / 旁路）；**代码质量检查**仍用上游 `trellis-check`" |

同一分工表同步写进 `AGENTS.md` 的 NL 路由段（§4.9）——skill 可能不被触发，而 `AGENTS.md` 每会话必读。

**分发机制（可扩展）**：`module.yaml` 内维护 **skill 根映射表**（数据，不是代码）：

```yaml
skill_roots:
  - { agent: claude-code, dir: .claude/skills }
  - { agent: codex,       dir: .agents/skills }   # D11：只用共享层
  - { agent: pi,          dir: .agents/skills }
  - { agent: dsh,         dir: .agents/skills }   # .dsh/skills 为 rank-100，会遮蔽共享层，故不投
```

**新增智能体的扩展契约**：加一行只是**登记**，接入一个平台必须同时满足四条，缺一即**声明该平台不受支持**：

| # | 契约项 | 判据 | 失败处置 |
|---|---|---|---|
| 1 | **skill 发现** | 该平台确实读取我们投放的根（真实会话中确认能被加载/触发） | 不投放该根，声明不受支持 |
| 2 | **frontmatter 兼容** | 渲染出的 frontmatter 被正确解析（未知字段静默忽略） | 退化为最小 `name`+`description` 并记录 |
| 3 | **变体解析**（**硬门槛**） | 该平台读 `.trellis/workflows/<id>.md`（可用哨兵串验证）——**只读全局 `.trellis/workflow.md` 的平台直接不适用** | **声明该平台不受支持**（不是降级使用） |
| 4 | **CLI 冒烟** | 在该平台的真实会话里跑通 `wf route`（只读）至少一次 | 未冒烟前不写入"已支持"清单 |

**渲染层（D14：同一份正文，按平台注入 frontmatter）**：

| 平台 | frontmatter 字段 | 正文 |
|---|---|---|
| Claude Code | `name` + `description` + `allowed-tools`（可选，减少授权打断） | 同一份 |
| Codex / Pi / DSH | `name` + `description` | 同一份 |
| 未知/未来平台 | 保守取 `name` + `description` | 同一份 |

正文占位符由渲染层替换：`{{PYTHON_CMD}}`、`{{MODULE_VERSION}}`、`{{VERIFIED_RANGE}}`、`{{CLI_PATH}}`。**正文不出现任何平台分支**。

> **为什么解释器要渲染而不是写死**：`python3` 在 Windows 上通常不存在（trellis 自身即由 `TRELLIS_PYTHON_CMD` 解析并渲染进 hooks/commands）。skill 若写死 `python3`，Windows 目标项目上整条链路不可执行。

### 4.5 证据层（V2：一条记录 + 一句断言）

**为什么还需要它**（第十轮的结论，见 §2.5）：Trellis 的任务级校验产出的是**文字报告**（`templates/trellis/agents/check.md`：审未提交 diff、输出 "Self-Check Complete" 报告、明令禁止 commit/push/merge），`task.json` 里**没有任何字段承载校验结果**（`commit` 字段全库无人写）；`task.py archive` **不检查证据**就能把 `status` 改成 `completed`。所以任务记录回答的是"它被声明完成了"，答不了"**凭什么算完成、验的是哪一版**"。

**最小形态（全部落在原生字段上）**：

```jsonc
// .trellis/tasks/<task>/task.json —— 只用到原生 status 与原生 meta
{
  "status": "wf-verified",
  "meta": {
    "wf": {
      "impl_sha": "3f9c1a2",                                  // wf declare 写入：声明完成时的 HEAD
      "verification": {                                       // wf verify 写入
        "sha": "3f9c1a2",                                     // 被验证的那一版
        "checks": ["lint", "typecheck", "test"],              // 跑了什么
        "result": "pass",                                     // pass | fail
        "level": "in-place",                                  // in-place | quasi-clean
        "at": "2026-10-17T09:12:44Z"
      },
      "bypass": { "kind": "block", "reason": "…", "from_state": "wf-verify", "at": "…" }
    }
  }
}
```

| 规则 | 内容 |
|---|---|
| 写入方式 | **只用原生 `task.py set-meta`**（`common/task_store.py:1946-1958`：read-modify-write，保留未知字段）。嵌套对象序列化为 JSON 字符串后作为 `value` 写入 |
| 为什么不新增顶层字段 | 上游 `create` 的固定 24 字段 schema（`schema.ts`，含 `--force` 会**重写成固定 schema**）；写进原生 `meta` 才不会被上游覆盖，也**不要求上游 schema 变更** |
| 不用 `commit` 字段 | 该字段全库无人写、语义未定义；用它等于定义私有语义 → **通用判据见 §4.12**（原生字段不写私有语义） |
| 有效期断言 | **`meta.wf.verification.sha` 必须等于当时的 `HEAD`**；不等 ⇒ 证据过期，`wf state` 输出提示，`wf declare`/`verify` 重新开始 |
| 为什么不再要指纹 | 单分支、验完不再改（D21）：**一个提交 sha 就够**。变更集指纹原本解决的是"工作区与主干分叉后，验证还算不算数"，该前提已不存在 |
| 记录保留 | `task.json` 随版本库；`archive` 是 read-modify-write，**`meta` 原样保留**；历史任务由 `.trellis/tasks/archive/**` + 原生 journal 承载 |
| 为什么不 append-only | 单写者（单人单分支）+ 证据就是当前状态，**保留历史不是需求**；旧值被覆盖属正常（要追溯用 Git 历史） |
| 校验级别 | 只有两档：`in-place`（默认，原地跑）与 `quasi-clean`（原生 `git worktree` 临时检出，§4.3.2.1）。**取消三级分级**（V2） |

**一票否决的四件事**（`wf verify` 的 fail-closed 前置）：

1. **无契约或契约未确认**（`.wf/contract.yaml` 缺失或 `confirmed` 为空）→ 拒绝（§4.2.1：未定标不许进入验证）；
2. **无声明**（`meta.wf.impl_sha` 缺失或与 `HEAD` 不符）→ 拒绝，提示先 `wf declare`；
3. **检查项不在契约里**：不带 `--checks` 时用契约 `acceptance` 的全部 `required` 项；带 `--checks` 时每一项都必须是契约里的 id。**两边都为空 → 拒绝**（防"什么都不跑就算验证过"）；
4. **受管资产被本任务改动** → 拒绝，要求**先单独提交并单独确认**（v20 §5.5 的"受管资产隔离"）。判定来源是契约的 `managed_assets`（**不再硬编码两条路径**）：

   ```
   git diff --name-only <impl_sha> -- $(契约 managed_assets 展开)
   ```

   非空 → 拒绝，并给出"这些路径属受管资产，请单独提交后用 `wf confirm --kind managed-asset` 留痕再重跑"；这同时是 `wf verify` 记录里 `managed_assets_changed` 字段的来源。

**信任根**（v20 §13 的最小落地）：

- `wf self-hash` 输出自身哈希；`wf --from-anchor` 用 `git show HEAD:<路径>` 加载锚点版本并打印自身哈希——**防止"用被本任务改过的脚本给自己判分"**；
- 断言：被执行的脚本 blob 哈希 == 工作线当前提交里该路径的 blob 哈希（"能读到锚点"不等于"用了锚点"）；
- 自测不依赖任何具体项目的契约内容与历史 sha。

> **v3 的 §4.5.1（11 类记录 / 链归属 / 派生表）、§4.5.2（`bypass` 记录类型与哈希链）、§4.11（变更集路径域 / `change_set` vs `merge scope`）整块删除**（V1/V2/V3）；旁路状态改由原生 `status` + `meta.wf.bypass` 表达。

#### 4.6.1 平台接入验收（G0）

"目录存在 + CLI 引用正确"不算支持一个平台。四个平台各自必须有**真实会话**里的最小验收，缺一即**不写入"已支持"清单**：

| 验收项 | 判据 | 说明 |
|---|---|---|
| skill 可加载 | 在该平台会话里 `wf` skill 能被加载（手动触发即可） | DSH/Pi 无 hook，只能靠 skill + CLI |
| 变体实际解析 | 会话里 `wf route` 的输出与 `get_context.py --mode phase` 的哨兵串一致 | 证明读到的是 `wf` 变体而非上游全局 `workflow.md` |
| CLI 冒烟 | 在该平台会话里成功跑通 `wf route`（只读）至少一次 | 排除"工作目录/解释器与预期不符" |
| 增强通道 | 面包屑/SessionStart **按能力分级**：支持的平台必须通过，不支持的记 N/A | 不设统一硬门槛；DSH 记 N/A |

**G0 的执行时点**：这四项验收**必须在 P0 内跑完**。理由：对 DSH/Pi 的 skill 根结论来自**读码**（§2.3），若该结论不成立，受影响的是**"四个智能体都支持"这个目标本身**，D16 也要改。

**跨 CLI 接手**：同一个任务由 CLI-A 实施 → CLI-B 接手 → 继续实施；判据是 `task.json` 的 `status` + `meta.wf.*` + 原生 `get_context.py` 输出在两端一致（P3.5）。

### 4.7 门禁为什么不能靠"谁触发"（skill-first 的安全前提）

skill 会被模型自动触发，而**没有任何平台能让 CLI 判断"调用者是模型还是人"**。因此：

1. **只读子命令**（`route`/`state`/`summary`/`records`/`doctor`/`embed-state`）—— 自动触发无风险，允许；**`upgrade --check` 默认不写盘**（要落盘须显式 `--report <path>`），凡会写盘的检查一律在**隔离夹具**中执行；
2. **有副作用子命令** —— 门禁**只依赖状态**（不依赖"谁触发"）：
   - `task new`：**契约存在且 `confirmed` 非空**（§4.2.1）；否则拒绝并给出定标指引；
   - `declare`：`status == wf-impl`（或旁路恢复后回到该状态）且工作区无未解决的冲突；写 `status=wf-verify` + `impl_sha`；
   - `verify`：要求契约已确认、`meta.wf.impl_sha == HEAD`、且检查项来自契约 `acceptance`（不带 `--checks` 取全部 `required`）；任一不满足即拒绝，不给"无声明直接验证"的路径；
   - `close`：要求**证据有效**（`status==wf-verified` 且 `verification.sha==HEAD` 且 `result==pass`）；随后调原生 `archive`；
   - `bypass`：`block`/`pause`/`resume` 要求该任务**已开工**且旁路状态可判定（重复声明幂等、无可恢复旁路则拒绝）；**`terminate`** 与 `release`/`anchor`/`upgrade --apply` 同级，需**人在交互式终端**执行（双 `isatty` + 手输令牌）；
   - `task.py start/archive` 只由 `wf` 内部调用（单写者）；
3. 每个 skill 正文显式标注其子命令属"只读"或"有副作用"，并在有副作用处写明"需先满足的状态"。

### 4.8 护栏：模块只保留**真的需要**的那一条

| 候选护栏 | 是否保留 | 理由 |
|---|---|---|
| 内容扫描（密钥/敏感串） | **不内置**，只在 `wf doctor` 里给一次建议 | 最小形态下模块**不接管 git hook**（V5）：接管 `core.hooksPath` 会让 husky/lefthook 失效，而单人自用场景下"提交前扫描"不是必需项。要用就自己装（README 给两条现成命令） |
| 非交互推送拦截 | **不保留** | v20 自己写明"AI 是唯一推送者，非交互必然走显式逃生口 → 该护栏对 AI 无效，仅剩提醒人勿误推的价值"；单人自用场景下这个价值不足以为它引入一整套 hook 机制 |
| 分支纪律/推送纪律 | **不保留** | D20：不切分支、合入由人手动 |
| 零受管写入的漂移防护 | **保留**（唯一） | 原生能力 + 一条解析断言：`wf doctor` 跑 `trellis update --dry-run`，断言 "Modified by you" **恰好只有 `.trellis/config.yaml`**；再加一条"当前解析结果确实是 `wf` 变体"的端到端断言（防"那一行被 overwrite 后静默回落上游"） |
| 探针写盘纪律 | **保留** | 凡写盘的检查在临时目录/临时 git 仓库中执行，用完即删（失败也删）；`wf doctor` **默认只读**，写回交给显式命令（`wf install --restore` / `wf repair …` / `wf upgrade --apply`） |
| 远端加固 | **只给建议命令**，不自动改远端 | v20 §1.3 明示"承认无法强制"；改远端是外部副作用 |

**顺序可恢复，而不是"顺序无关"**：

> **任何一次 `trellis update` 之后，必须立即跑 `wf doctor`；若发现 `default_workflow` 那一行丢失或解析结果不是 `wf` 变体，按 `wf upgrade --plan` 的预览回放那一行。**

两种顺序都支持，但**都要跟一次验证**：`trellis update → wf doctor`；或 `wf upgrade → trellis update → wf doctor`。验收场景见 §5.6C。

### 4.9 `AGENTS.md` 块外 NL 路由（作用与覆盖范围）

**它是什么**：`trellis init` 在 `AGENTS.md` 里写受管块 `<!-- TRELLIS:START -->…<!-- TRELLIS:END -->`；**块外内容由 `trellis update` 保留**（§2.2 实测）。模块在该块外追加一段带自有标记 `<!-- wf-nl-routing-start/end -->` 的"自然语言意图 → 入口"路由表。

**作用**（三条，都不依赖 hook 与 skill 触发）：

1. **补齐无 hook 平台的通道**：DSH 无项目级 hook、Codex 的 hook 需用户级开关+审批，两者在"hook 未生效"时唯一稳定的会话期通道就是 `AGENTS.md`；
2. **承载硬约束**：把"不得直接调用 `task.py start/archive` 改状态（单写者）""不得写 T0 受管文件""证据以 `meta.wf.*` 为准"放在所有平台都会读的位置；
3. **可发现性（含模块升级）**：给出人类可读的意图→入口映射，并写明**升级 skill 需要手工复制到 `.agents/skills/`**（它不随安装器分发，D7）。

**覆盖范围（实测 + 官方文档）**：

| 平台 | 是否读 `AGENTS.md` | 依据 |
|---|---|---|
| DSH | ✅ 每会话读 | 本会话系统提示即注入项目 `AGENTS.md` |
| Codex | ✅ | Trellis 平台表 + Codex 的 `project_doc_fallback_filenames`（init 写入 `.codex/config.toml`） |
| Pi | ✅ | 与 Codex 同族约定 |
| Claude Code | ⚠️ **条件性**：仓库无 `CLAUDE.md` 时把 `AGENTS.md` 当作项目指令（需 v2.1.277+，且 `/config` 的 Project instructions 可切为"只读 CLAUDE.md"） | code.claude.com 文档 |

→ 因 Claude Code 是条件性覆盖，**该表不是任何门禁的唯一载体**：它只承担"路由提示 + 硬约束声明"，权威判定一律在 `wf` CLI。

**安装期必查**：若目标项目根存在 `CLAUDE.md`，安装器与 `wf doctor` 必须**明确提示**"本模块的 NL 路由对 Claude Code **可能不生效**；如需生效请在 `CLAUDE.md` 中 import `AGENTS.md`，或把 Project instructions 切为'两个都读'"。

### 4.12 原生字段纪律（v4 通用判据：原生字段不写私有语义）

**判据**：模块**不得**在任何上游字段上定义自己的语义。可用空间**只有两个**：

| 空间 | 归属 | 允许的用法 | 不允许的用法 |
|---|---|---|---|
| `task.json.status` | 上游字段，但上游只解释 `planning`/`in_progress`/`completed` 三个值 | 写入 `wf-*` 自定义值让**原生面包屑与 `task.py list` 原样呈现**（这是"扩展取值"，不是"改写语义"） | 让上游用某个值的既有含义去承载我们的含义 |
| `task.json.meta` | 上游显式保留的自由区（`meta: Record<string,unknown>`） | `meta.wf.*` 存证据（嵌套对象序列化为 JSON 字符串，经原生 `set-meta` 写入） | — |

**明确禁止的一张表**：

| 上游字段 | 看似可用 | 为什么不允许 |
|---|---|---|
| `commit` | "正好可以存被验证的提交 sha" | **上游从未写入它**（`create` 写死 `null`，全库无写入点），语义未定义；我们写入 = 定义一个上游随时可能按自己的理解去用的字段（`finish-work` 已经在把它当"本任务工作提交"的人手抄写位）。**证据的 sha 一律放 `meta.wf.verification.sha`** |
| `pr_url` | — | 预留语义；模块不创建 PR |
| `worktree_path` | "存准洁净的临时检出路径" | 上游字段语义是"任务工作单元路径"；我们的临时检出**用完即删**，不构成任务身份，放本机态（§4.3.2.1） |
| `notes` / `relatedFiles` / `scope` 等 | — | 均属上游语义；模块只读不写（`scope` 由 `wf scope` 走原生 `set-scope`，语义与上游一致） |
| `.trellis/config.yaml` 的其他键 | — | 除 `default_workflow` 那一行（D18）外一律不碰 |

**之所以把它单列一节**：这与"原生优先"（§0.4）是同一原则的两面——**§0.4 管"别重实现"，本节管"别挪用"**。二者合起来才是 D22 的完整含义；漏掉本节就会出现"用原生字段装私有含义"这种看起来零补丁、实际把耦合藏进字段语义里的写法。

## 5. 升级机制

### 5.1 三轴版本模型

| 轴 | 来源 | 用途 |
|---|---|---|
| `T_target` | 目标项目 `.trellis/.version` | 目标所处 Trellis 代 |
| `M_inst` | **变体文件头部**：`.trellis/workflows/wf.md` 的 `<!-- wf:module_version=… -->` 注释行 | 已装模块版本（**不再需要 `.wf/module.lock.json`**，V6） |
| `M_src` + `[T_min,T_max]` | 模块源 `module.yaml` | 模块源版本与验证区间 |

**`T_min` 的设计输入**：`T_min = 0.7.0-beta.0`，已用参考仓库的 tag 直接验证：

```sh
# 在 ~/projects/other/Trellis 内（版本对齐的分支上）
git cat-file -e v0.6.0-rc.0:packages/cli/src/templates/trellis/scripts/common/workflow_selection.py  # → 不存在
git cat-file -e v0.7.0-beta.0:packages/cli/src/templates/trellis/scripts/common/workflow_selection.py # → 存在
git cat-file -e v0.7.0-beta.4:packages/cli/src/templates/trellis/scripts/common/workflow_selection.py # → 存在
```

即变体解析链在 `v0.7.0-beta.0` 首次出现、`v0.6.x` 没有。因此：

- `T_target < 0.7.0-beta.0` → 直接拒绝，要求先升到 `T_min`；
- `T_max` 保持**封闭区间**（只声明实测验证过的上界）；
- **治理提示**：该机制上游有 **revert 先例**（`c3596dd9` 引入 → `c143c260` revert → 0.7.0-beta.0 重新落地），说明仍在演化。故 `capability-digest.md` 必须登记这段历史，且每次升级都把 P1/P2（变体哨兵）当作"变体链还在不在"的哨兵。

**入口 × 状态矩阵（`wf upgrade --check` 的输出即此表）**：

| 状态 | `wf install` | `wf upgrade --check` | `wf upgrade --apply` |
|---|---|---|---|
| `INITIAL_BASELINE_READY`（未安装） | ✅ 允许 | ✅ 允许（只读） | ❌ 应先走 `install` |
| `ALREADY_VALID_EMBEDDED`（有效已安装） | ❌ 拒绝重复安装 | ✅ | ✅ |
| **安装/升级不完整**（`.wf/.upgrade-attempt.json` 的 `status ∈ {in_progress, failed}`） | ❌ | ✅（只读，并输出差异） | ❌ **拒绝**：先 `wf upgrade --rollback` 或人工清理 attempt 后重跑；不提供绕过开关 |
| **存在活动任务**（`status ∉ {planning, completed}` 且未处于「暂停」旁路） | —（新装无任务） | ✅（只读，并列出活动任务） | ❌ **拒绝**：先把任务收口，或按 `wf bypass pause <task> --reason …` 显式暂停后重跑 |

### 5.2 契约探针（黑盒行为断言；不看源码字符串、不存内容哈希）

**原则**：**能用原生命令判的，不再自造断言**（D22/V7）。

| # | 类别 | 断言 | 判据来源 |

| P4 | 必需 | `task.py set-meta` 写入 `meta.wf.*` 后能被读回，且 `archive` 后仍在归档的 `task.json` 里 | 原生命令 |
| P5 | 必需 | `task.json` 与 `.trellis/workspace/**` 未被 `.gitignore`/全局 excludes 命中 | `git check-ignore` |

### 5.5 升级的资产输入与回滚（D19）

| 项 | 规定 |
|---|---|
| 资产输入 | `wf upgrade --from <模块源目录>`；`wf install` 把该路径记进**本机** `.wf/.install-record.json`，升级 skill 以它作为默认值并要求人在预览里确认 |
| 版本判定 | 源 `module.yaml` 提供 `module_version` + `verified_trellis_range` + **资产哈希清单**；与变体文件头部记录的 `M_inst` + 当前工作区资产哈希比对，得出"新增/替换/删除"三类清单 |
| 完整性校验 | 应用前校验源资产哈希（源自身一致），应用后写新的 `M_inst` 与哈希；不符即拒绝应用（fail-closed） |
| 预览 | `--plan` 输出**唯一的"实际写入清单"**：将新增/替换/删除的每个文件 + `AGENTS.md` 追加段 + `config.yaml` 那一行。**该清单直接驱动快照与回滚** |
| 回滚 | 应用前对**清单里的每个路径**做快照，统一放 `.wf/.upgrade-backup-<ts>/`（含 `.trellis/scripts/wf/**`、变体、两个 skill 根、`AGENTS.md`、`.trellis/config.yaml`、本机记录）。任一步失败即自动回滚并保留现场；成功后保留最近一次备份，由 `wf doctor` 提示可清理 |
| 提交时机 | `--apply` **不自动提交**（提交是检查点）。`.wf/.upgrade-attempt.json` **只表示"进行中/失败"**：验证成功即**清除**。"升级已生效但尚未提交"**不额外写文件**，由 `wf doctor` **从 Git 工作区状态派生** |
| 失败语义 | 与安装一致：先写"升级尝试记录"（`status: in_progress`）→ 失败置 `failed` 并**保留**（下次 `--check` 判为"不完整"，拒绝再次 `--apply`）→ **验证成功即清除**；**不允许半升级后静默可用** |

### 8.1 变体选择器：采纳"写 `config.yaml` 的 `default_workflow: wf`"

**决定**：`.trellis/workflow.md` **保持上游原样**；流程内容放在变体 `.trellis/workflows/wf.md`；在 `.trellis/config.yaml` 写一行 `default_workflow: wf` 作为**团队级选择器**（D18）。

#### 8.1.1 三个层次（内容 / 选择器 / 兜底）

Trellis 的流程文本解析是**优先级链**（权威出处：`workflow_selection.py:1-25` 的模块注释）：

```
per-task pin（task.json.workflow）        ← 单任务级，最优先
      ↓ 未设置 / id 无效 / 文件不存在
个人默认（.trellis/.developer 的 workflow=）
      ↓ 同上
团队默认（.trellis/config.yaml 的 default_workflow:）
      ↓ 同上
全局 .trellis/workflow.md                 ← 兜底，永远存在
```

| 对象 | 是什么 | 归属 |
|---|---|---|
| `.trellis/workflow.md` | **上游的兜底流程文档** | 上游（我们保持它字节级不动） |
| `.trellis/workflows/wf.md` | **内容**：我们 v20 流程的变体 | 我们 |
| `config.yaml` 的 `default_workflow: wf` | **选择器**：告诉解析链"优先用 wf 这个变体" | 一行官方旋钮（D18） |

#### 8.1.2 为什么不直接把内容写进 `.trellis/workflow.md`

| | 直接改 `workflow.md`（旧模块的路） | 变体 + 选择器（本方案） |
|---|---|---|
| 该文件归谁 | 我们 | 上游，**字节级不动** |
| `trellis update` | 每次都是 "Modified by you"，**必须人工合并整份文档** | 自动更新、零冲突 |
| 上游改了 `workflow.md` | 要把我们的内容**重新移植**到新版全文 | 0 成本 |
| 卸载 | 需从备份恢复 | 删变体 + 还原那一行即可 |

本仓库就是这条代价的活证据：上游 `workflow.md` 在两个版本间从 35,919 字节涨到 42,347 字节，而因为本仓库也改了这个文件，就不得不维护 `merge-workflow-md.py`（23KB 合并器）+ 两份基线 + 当前副本相对全新模板的 79 行差异。

#### 8.1.3 为什么有了变体还必须写那一行

因为**变体只是库里的一份文件，必须有东西去选它**，而三个选择来源的持久性不同：

| 选择来源 | 位置 | 随版本库走 | 覆盖"无活动任务" | 缺失时 |
|---|---|---|---|---|
| per-task pin | `task.json.workflow` | ✅ | ❌（任务还不存在） | 落到下一级，**有告警** |
| 个人默认 | `.trellis/.developer` 的 `workflow=` | ❌ **gitignored** | ✅ | **静默**落到下一级 |
| 团队默认 | `.trellis/config.yaml` 的 `default_workflow:` | ✅ | ✅ | **静默**落到全局 `workflow.md` |

只有 `config.yaml` 这一级**既随版本库走、又能覆盖"还没有任务"的时刻**。缺了它，"新克隆 + 无活动任务"就会静默解析到上游原生工作流——而那正是 AI 决定"要不要建任务、怎么定标"的时刻。

**配套检查（必须做，因为回落是静默的）**：`wf doctor` 增加两条断言——P9（受管写入面恰好等于白名单）与 P1/P2（当前解析结果确实是 `wf` 变体）。没有 P1/P2，变体文件被删或改名后会静默回到上游流程。

### 8.2 为什么是 2 个 skill

| 维度 | 1 个 `wf` | **2 个（已采纳）** | 3 个（v3 旧口径，已废弃） |
|---|---|---|---|
| 描述条数与触发精度 | 1 条，必须覆盖路由+证据 → 描述变长、什么都能触发 | 2 条，各自聚焦 | 3 条（多出的一条只服务已删除的合入链路） |
| 门禁显著性 | 差：只读与有副作用子命令混在一份正文 | **好**：与"只读 / 有副作用"两条边界一一对应 | 好 |
| 漂移面（skill 文本 ↔ CLI） | 1 处 | 2 处（P11 机械校验） | 3 处 |

**拆分原则**：按"调用者意图"与"是否产生副作用"切，**不按子命令个数切**。**删除 `wf-integrate` 的理由**：它的全部职责是合入链路（判交集/候选/冒烟/推进主干），而 D20 已把合入交给人工——**保留一个没有对应操作的 skill 只会制造误触发**。

### 10.11 第十轮：按工作场景收敛（记录轨去自造 / 合入链路整体删除 / 原生优先）

**触发方式与前九轮都不同**：不是"外部送来一份审查清单"，也不是"结构型核对发现缺陷"，而是**使用者确定工作场景后要求做一次结构性收敛**——"单人 · 同一工作线 · 不切分支 · 合入由人手动"（D20）与"用 Trellis 原生已有机制实现，不要重复功能"（D22）。

### 10.12 第十一轮：项目级契约被误删（使用者指出的重大理解缺陷）

**触发方式**：使用者直接否定了 v4 初版对项目级的处理——"对比设计稿要求，项目级规划要求本模块是要求的，当前该文档理解存在重大问题"。

**核实结论：使用者判断正确，这是一处实质性缺陷，不是措辞问题。**

#### 一、设计稿的硬要求（逐条）

| # | 原文 | 位置 | 性质 |
|---|---|---|---|
| 1 | 项目级三节点：定标 → 设计 → 计划，出口含"范围基线冻结 + **最小受管路径模式与验收面入口** + 契约获人确认（初始锚点）" | v20 §6.1 | 一次性、必须做 |
| 2 | **"契约未定不应开任务"** | v20 §6.1 末句 | **硬前置** |

#### 二、v4 初版的错误

| 错误 | 表现 | 后果 |
|---|---|---|
| **把"模块不承载机制"当成"不需要落点"** | V6 把 `.wf/*.yaml` 七件套**全删**，声称"验收面在 `prd.md`" | `prd.md` 是**任务级**件，撑不起项目级契约；项目级定标没有产物 |
| **删掉硬前置的入口门禁** | `wf task new` 不检查任何契约 | **直接违反 v20 §6.1/§11.1**：契约未定也能开任务 |
| **验收项退化为人工记忆** | `wf verify --checks lint,test` 由人手填 | 违反 §6.2"验收项由脚本从验收面推导" |
| **受管资产判定硬编码** | `git diff --name-only … -- .trellis/scripts/wf .trellis/workflows` | 清单应来自契约（§3/§5.5），硬编码两条路径等于自己发明清单 |

**根因**：D22（原生优先）被过度应用。契约是 v20 **术语级**定义、是任务级流程的**前置条件**，它**没有**原生等价物；"不要重复实现原生能力"推不出"不要有项目级承载物"。

#### 三、处置（恢复恰好一个文件）

| 项 | 结论 |
|---|---|
| 契约载体 | **只恢复 `.wf/contract.yaml`**（受管内容，随版本库）；其余六个自造文件仍删 |
| 契约要素 | 范围基线（含最小受管路径模式）/ 验收面（含每项命令与 `level`）/ 受管资产清单 / `integration_branch` / **人的确认记录 `confirmed`** |
| 命令 | `wf contract init`（生成草案，不确认）/ `show`（只读）/ `approve`（**TTY + 令牌**，写 `confirmed`，即 v20 §13 的初始锚点） |
| 入口门禁 | `wf task new`：契约存在且 `confirmed` 非空，否则拒绝并给定标指引 |
| 验证门禁 | `wf verify` 的检查项**必须来自契约 `acceptance`**（不带 `--checks` 取全部 `required`；带则必须为子集）；受管资产判定读 `managed_assets` |
| 档位下限 | 以 `scope_baseline` 判"是否触碰受管路径"（v20 §11.1 冷启动） |
| 探针 | 新增 **P16（契约门禁）/ P17（验收项来自契约）/ P18（受管资产来自契约）**，均归 **P0** |
| 拆卸 | `uninstall` **默认保留** `.wf/contract.yaml`（它是人确认过的项目级产物），仅 `--drop-contract` 才删 |

#### 五、本轮的方法论教训（写进制度）

1. **"最小化"不能以删除术语级定义的前置条件为代价**：v20 §3 定义的术语（契约、验收面、受管资产）是**判据的输入**，删掉其载体 = 判据失去来源。
2. **"不用原生字段"与"删掉自有载体"是两件事**：§4.12 管"别挪用原生字段"，不等于"所有模块自有文件都该删"——**有消费者、且无原生等价物的自有文件必须留**。
3. **删任何载体前，先列出它的消费者**：契约的消费者有三处（验收项推导 / 受管资产判定 / 档位下限），此前一个都没清点。

**本轮未采纳的点**：无（使用者指出的缺陷成立，已按"恢复一个文件 + 补三条门禁 + 补三条探针"处置）。
