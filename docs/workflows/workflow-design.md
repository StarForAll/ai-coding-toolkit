# 工作流整体设计（v42 · 修订）

> 本文件是该工作流的骨干契约。它以 Trellis 提供的机制层为基底，只规定四件事：项目层怎么开始与结束、任务层怎么走、顺序怎么保障、记录与关卡怎么判定；不规定工具、文件、命令与实现细节。

## 0. 阅读约定

**定位**：一名开发者、一台开发机、**单一工作线**（不切分支、不合入）、多个 AI CLI 交替参与的项目开发工作流；覆盖 0→1 与之后的持续使用。

**三条前提**（全文前提，不可放宽）：

1. 单人 + 本机 + 单一工作线；
2. 只规定判定与流转，不规定工具、文件与命令；
3. 基底之外只新增一个机制——**依赖机制**（见 [依赖机制设计说明](./依赖机制设计说明.md)），其余一律复用基底；模块可卸载、可重装，卸载后基底仍可独立使用。

**怎么读**：认识 → §1 → §2 → §3；项目层 → §4 → §5；任务层 → §6；顺序 → §7；记录与接手 → §8；入口、旁路与卸载 → §9；演进 → §10。

**写作约定**：表内粗体是**判据要点**，规则唯一来源是正文；跨引用用 `§N` 与表内行号；**未规定的取值一律视为留白**；引用基底机制时只引用其保证，不复述其实现；**同一判定只在一处定义**，其余位置只许引用、不得复述条件（**表内判据要点除外**；附录 C 历史条目为记录性文字，不适用本句）；**同一动作序列只在一处定义**（含步骤顺序）；镜像可以保留同一序列，但必须与源逐字同序、并由源标注唯一源位置，出现第二份不同顺序的序列即视为未完成；**新增判定行须登记产生路径与遮蔽关系**，无产生路径的组合按防御态处理、不进入日常路由；**例外只能按状态登记，不得按来源、路径或角色逐格追加**——确需按来源枚举时，必须同版给出完备枚举与遮蔽关系（角色属性可单独成句，但同一角色只写一次）；**去重 / 收口（合并副本、降为引用）时，存活的那份必须显式登记全部例外（源处写「例外：…」），否则不得删除副本**；**改动一条判定或一条动作序列时，同版列出其全部副本（源、摘要、镜像）并逐份给出同步结果，清单缺行不得声明完成**；**新增或改写多步动作时，作者同版给出窗口表（残留态 → 识别字段 → 向前完成）与该动作的唯一源位置**，缺任一视为未写完、不得进入审查；**修订记录只记录「哪条源改了、哪些副本跟随」，不得与正文相反**，凡写「已补 / 已同步」必须能在同版正文中逐字核对；**凡写含「唯一 / 不再 / 一律 / 只」的封闭断言，同版必须列出该断言覆盖的全部产生路径并逐条核对**——列不出或对不上就改用字段谓词表述（例：见 §7.8 识别字段写入矩阵后的禁止式约束）。

**事实边界（有意取舍，审查时不得当作缺陷）**：

- 不担保人判的真实性，不做验证证据链；人判是基底 check 后的原生人工判断，痕迹在原生会话日志 / 任务记录中（§1.3、§4.3）。
- 不防对抗，只防意外与误报；AI 原生创建未登记任务这类绕过不可防（§1.3）。
- 机制不可用时**只卸载，不降级、不绕过**；卸载后基底可独立使用（§9.4）。
- 账本不自动清理；“正常”条目长期保留，供类型 1 / 4 修复校验与归档终态判定使用（§7.7）。
- **边只表达“尚未满足的顺序”**：建边的两端都必须在活动区；已归档任务作为前置出现，只来自继承（0→1 建图、返工与替换继承）或活动期建边后该前置归档，不再事后对归档任务挂边（§7.5）。
- 已归档任务不可替换、不可放弃、不可重开；已归档任务不直接返工，其产物缺陷由当前未归档任务承载（§5.5、§6.4）。
- 替换/放弃是**人发起的前向操作**：实施后只允许向前完成，不回退到替换前（§2 不变量 11、§6.5、§6.6）。
- 单工作线不并行编辑；无关任务与链任务只切换执行（§6.8）。
- **收敛声明只对已枚举的失效模式负责**：口径 10–14 与本节验收面覆盖的是已发生、已登记的失效类；验收通过不等于“不存在其他失效模式”。出现未被枚举的新失效时，按 §10 的修正来源（内部矛盾 / 跑不通 / 与不变量冲突 / 与真实场景不符）重新计入，不视为本版承诺被推翻。

### 0.1 设计稿自身的约束（审查与验收面）

本节是审查标准，也是**审查边界的声明**。其他 agent 审查本设计稿时先判“承载”，再判“是否满足”；设计稿只对本层负责，不代实现方案或目标项目受过。某一条在其承载层不满足，即视为该层未达标；不得把实现层或目标项目的未完成算到设计稿头上。

**审查口径（先读这一节，再逐条对照）**：

1. **先判承载**：表中“承载”列写明该条由设计稿 / 实现方案 / 目标项目负责。设计稿承载的条目按正文判定；实现方案 / 目标项目承载的条目，设计稿只检查“是否写清了交给谁、验收什么”，不要求设计稿给出命令、文件、探针或测试细节。
2. **只受理四类来源**：内部矛盾、跑不通、与不变量冲突、与真实场景不符。不受理：个人偏好、工具选型、实现细节、未规定的留白、要求新增机制。
3. **不把有意取舍当缺陷**：人判不新增记录、不做证据链、不防对抗、机制不可用只卸载、账本不自动清理、边两端限活动区、已归档任务不可替换/重开、替换/放弃实施后不回退、单工作线不并行——这些已在正文说明，审查时不得要求补机制或要求回退。
4. **不要求实现级证据**：设计稿只要求“判定可定位、出口存在、责任层明确”。命令、文件、行为探针、安装/卸载往返、目标项目同步 SOP 由实现方案承载。
5. **区分“未规定”与“规定不清”**：留白不算缺陷；同一规则两处不同、或一条规则没有出口，才算缺陷。
6. **审查对象是当前设计稿**：派生图、实现方案、目标项目文档只作交叉核对，不作为设计稿的判定依据；它们与设计稿不同版时，先报告版本不一致，再决定是否继续。
7. **每条结论必须引用具体 § / 表**；不能以“一般来说 / 最佳实践”为依据，也不能把实现层的选择当成设计层的缺失。
8. **版本核对只要求**：设计稿版本 = 配套文档 `design` 字段；模块 `implements_design` 与目标项目 pin 由实现方案 / 目标项目验证，实现方案未更新时只报告版本不一致，不判设计稿缺陷；不要求设计稿记录基底的具体 beta / commit，基底验证区间由实现方案记录（A2、A4）。
9. **审查输出格式**：约束编号（A/B/§）+ 证据（具体 §/表/行）+ 来源类型（内部矛盾 / 跑不通 / 与不变量冲突 / 与真实场景不符）+ 影响（会在哪个阶段被迫改）+ 建议（优先补判定 / 删重复 / 改措辞；若必须新增机制，标注“超出本设计，需单独决策”）。不满足格式的结论，不作为设计稿缺陷。
10. **审查前先做验收面全量审计**：不依赖“凭印象找候选”，先按固定六项全量扫一遍并把结果写进报告——①枚举全文人判点，逐个核对是否标明“由人决定”（B1）；②枚举项目层任务 P 的全部可达处置（正常完成、返工、替换、放弃、异常未完成、各归档前后态），核对每种都有入口与出口（A1），引用须核对其正常/异常输入域；③逐条复核对账修复类型 1–5 的产出态是否合法（B9）；④枚举同一情形被两条规则分别管辖的组合（情形矩阵，轴须含承重字段——如替换指向有/无 × 继任者已建/未建 × 归档前后，只按继任形态扫描会漏字段谓词冲突）；⑤枚举全文含「唯一 / 不再 / 一律 / 只」的封闭断言，逐条列出其覆盖的全部产生路径并核对（列不出或对不上即为缺陷，须改用字段谓词——写作侧义务见 §0 写作约定）；⑥按识别字段 × 角色 × 修复入口交叉扫描：识别条件依赖的每个字段（替换指向、说明、返工来源）须在 §7.8 识别字段写入矩阵有行，每个修复入口须核对角色不变量（如 P 的继任者不得丢失），允许写入与禁止条件逐项求交；多轮动作须复用同一对象回放，检查同一提交快照会否要求互斥恢复。**新增或改写的扫法，本版即须对本版执行一次并把结果写入审查报告；未执行不得声明审查完成**（示例：已归档异常任务的下游处置 §7.4 × §7.7；未收尾阶段的就绪选择 §9.1 × §7.6；继任者标识 §6.6 × §7.8）。任一项扫出缺口，与修复动作同版处理，不留到下一版。
11. **重复规则全量比对（主稿内部 + 跨文档）**：同一规则在主稿内与跨文档的每份副本都必须给出同步结果（已同步 / 有意不同并附理由，副本按 `§0 写作约定`降为引用也算同步）；比对以**判定规则、动作序列与状态清单**为枚举单位（即 §0「同一判定只在一处定义」「同一动作序列只在一处定义」所辖的对象），不以本次改动行的措辞为单位，同一规则出现两份定义或同一动作出现两种步骤顺序即算未完成。**作用域是每版全量、不是点同步**：至少覆盖①本次改动的判定 / 序列；②与之共享同一状态位的副本（即使本版没改）；③本项目自有的探针清单中标记为它的条目（探针本身由实现方案承载，见口径 4；维护了清单时本项为必查——须实际执行探针并逐条核对期望值，期望值随判定改动同版更新；未维护清单时本项不适用）。版本字段一致不等于内容一致，口径 8 不覆盖本条；比对结果以清单写入本次审查 / 修复任务的报告（如 `review-report.md` / `fix-notes.md`），逐行给出：对象（判定 / 动作序列 / 状态清单）/ 副本位置 / 结果（已同步 / 降为引用 / 有意不同并附理由），缺行即未完成；清单须随本次修订保存于版本库（可查），否则视为缺行。
12. **引用路径回放**：每条新写的“按 §N 执行 / 按 §N 处置”都要沿引用走到目标段，逐条对上一句的适用前提（例如 §6.5 开篇“只适用于未归档任务”）；走不通就与本条同版补豁免或补细则——“有入口、有出口”按名字核对不算通过；同版新增或改写的每一条「按 §N」都要回放，不以主修复点为界。
13. **多步写入须枚举崩溃窗口**：新增或改写“顺序 + 可恢复”的动作（对账修复各类型、替换 / 放弃实施、返工）时，必须同版逐窗口给出残留态的**识别项**（让该残留态在启动自检、类型识别句或组合表注记中被唯一命中的字段或行内文字）与向前完成，识别所依赖的标记（替换指向 / 原因 / 说明）随第一步写入；只写终态不算完成（写作侧的产出义务见 §0 写作约定；本条复核其存在与自洽，模板见 §6.4 崩溃窗口、§7.7 类型 1 与类型 5 的逐窗口）。
14. **残留态须落在识别项上**：每个窗口的残留态必须被启动自检、组合表行内注记或类型识别句唯一命中；只与会话完成态同格而不加注记，或只靠“报告阻塞”，都不算命中；命中不到即与本条同版补识别项；识别项由正文给出，审查只复核其存在与自洽，不代作者推断。

口径 10–14 同属审查动作；改动了跨文档镜像、主稿内重复副本，或新增 / 改写了多步写入路径、跨节引用的版本，未跑 10 ④–⑥ 与 11–14 不得声明审查完成；新增或改写的扫法在本版未执行的，同样不得声明审查完成（口径 10 末句）。写作侧的对应义务（窗口表、动作序列唯一源、记录不得与正文相反）见 §0 写作约定；审查只复核，不代替写作。

## 1. 环境与边界

### 1.1 环境

| 维度 | 取值 |
|---|---|
| 人员 | 单人 |
| 机器 | 一台开发机；可有一个私有远端 |
| **工作线** | **单一工作线**：不切分支、不建工作单元、不并行编辑 |
| **提交与推送** | 提交范围、写入归属与生效边界统一按 §3“持久化”；**推送由人执行** |
| AI | 多个 CLI 交替，能力不等、上下文不共享 |
| 交付 | 自用为主；交付指**自用交付物与发布记录**，对外交付到他人环境不在本设计内 |
| 平台能力 | 不假设受保护分支、必需检查、代码所有者、独立机器身份 |

### 1.2 基底与工作流的分工

| 层 | 提供什么 | 边界 |
|---|---|---|
| **基底**（Trellis 机制层） | 任务单元、阶段推进、上下文注入、规格、会话与日志、任务树、归档、工作流可变体 | 负责“任务怎么走”；不含项目层与任务间顺序 |
| **工作流** | 项目层（立项、基线、任务图、收尾）、顺序（依赖机制）、完成判定、记录口径 | 负责“项目怎么开始与结束、任务按什么顺序走”；不重造任务生命周期 |

**口径**：基底已经有完整任务闭环时，工作流不得为任务层再发明一套状态机；工作流的新增只允许落在项目层与顺序层。

**模块生命周期**：安装、升级、卸载的具体命令与文件布局由实现方案承载，不在本设计内。设计层只约束五件事：

1. 卸载后基底 Trellis 必须可独立使用；
2. 机制不可用时只能卸载，不得绕过机制继续开工（§9.4）；
3. 仅模块卸载必须保留项目数据，完全卸载必须由人显式选择；
4. **卸载入口不得依赖机制运行时、账本或机制入口脚本**；即使机制损坏，卸载也必须可执行；
5. 卸载必须恢复基底配置、移除机制 hook 与变体 pin，不得留下阻断原生流程的文件或状态。

### 1.3 能力边界（诚实分级）

| 想防的事 | 分级 | 说明 |
|---|---|---|
| 确认被 AI 代写 | **只留痕** | 人判是完成判定的输入，但不是证据 |
| **AI 谎称完成** | **只留痕** | 完成 = 人判 + 归档；设计不担保判断真实性，只让“跳过人判”可见 |
| AI 跳过依赖与顺序（已登记任务） | **机制保障（正常使用）** | 图内任务开工与收尾只走机制入口；绕过时对账会停在“待修复” |
| **AI 原生创建未登记任务** | **只留痕 / 不可防** | 未登记任务没有依赖标识，机制无法把它与合法图外任务区分；这是“不防对抗”的边界 |
| AI 改写已推送历史、删除远端分支 | 防意外 | 工作改动与归档提交由基底流程驱动，推送由人手动 |
| **AI 快进覆盖主干** | **不可防** | 单一工作线；只能靠 reflog 挽回 |
| AI 读到项目内密钥 | 可降低概率 | 密钥文件移出项目目录（人执行）；提交前扫描如需要，由人本地配置，工作流不内置 |
| AI 绕过发布入口 | **不可防** | 发布由人在独立终端执行 |
| **机制自身损坏**（账本/入口不可用） | **卸载执行** | 卸载模块；仅模块卸载保留数据，修复后重装；不提供绕过机制的开工路径（§9.4） |

**口径**：本设计只防意外与误报，**不防对抗**；上表中标为“只留痕”与“不可防”的行为，基底与工作流都没有阻断能力。

### 1.4 边界外

团队协作与审批流、跨机并发、多机身份隔离、多分支与合入调度、跨项目依赖、任务调度与并行派发、对外交付层（发布到他人环境）、替换/放弃的回退；以及模块安装、升级、卸载的实现细节（由实现方案承载）。

## 2. 核心不变量

| # | 不变量 | 强度 |
|---|---|---|
| 1 | **基底是任务生命周期的唯一承载**；工作流不另造任务状态机 | 硬 |
| 2 | **单一状态源**：任务状态由基底表达；依赖状态由依赖账本表达 | 硬 |
| 3 | **单一记录源**：任务产物 + 会话日志 + 规格 + **依赖账本**；除依赖账本外不新增记录类型 | 硬 |
| 4 | **顺序由依赖机制保障**；任务图是 DAG，不能有环 | 硬 |
| 5 | **图内任务的开工与收尾只走机制入口**；原生入口只用于图外任务 | 约定 |
| 6 | **完成 = 人判 + 归档**；人判是基底 check 后的原生人工判断；不做验证证据链 | 约定 |
| 7 | **项目层用任务承载**：项目 = 根任务 + 基线 + 任务图 | 硬 |
| 8 | **基线是活的**：项目文档 + 规格；归档任务只是记录，不是工作参考 | 硬 |
| 9 | **任一节点不依赖单一 CLI** | 硬 |
| 10 | **模块可卸载**：机制不可用时卸载而非绕过；卸载后基底可独立使用；仅模块卸载保留项目数据 | 硬 |
| 11 | **替换/放弃是前向操作**：人发起并实施后，只允许向前完成，不回退到替换前 | 硬 |
| 12 | **账本写入必须合法**：任何依赖状态写入都必须符合表 4-2 的合法转移；表中没有的转移一律拒绝，不写入 | 硬 |

**口径**：第 5、6 条属**防意外**；第 6 条只保证“跳过人判可见”，不保证判断为真。第 11 条不是新机制，是 §6.5 / §6.6 的完成规则；它保证失败时不会把已实施的替换/放弃倒回旧状态。第 12 条是机制入口的写入约束，与 §7.5 的边变更校验对称，不是新机制。

## 3. 术语

| 术语 | 定义 |
|---|---|
| **基底** | Trellis 提供的机制层：任务、阶段、规格、会话、任务树、归档、工作流可变体 |
| **项目层任务（P）** | 承载 0→1 代码前全部工作的任务；项目链头 |
| **基线** | 需求基线 + 技术基线 + 任务图；由项目文档与规格承载 |
| **任务图** | 由实现任务与依赖边组成的 DAG；是基线计划，不是第二事实源；事实源是前置集合与账本 |
| **依赖标识** | 全局唯一标识（雪花 ID），只用于依赖机制，映射到任务目录；不随目录名变化 |
| **前置集合** | 本任务依赖的任务标识集合；**唯一事实源** |
| **下一个集合** | 由前置集合派生，仅用于异常时重连下游；不手工维护 |
| **依赖账本** | 记录任务标识、依赖状态、说明、替换指向；**状态事实源** |
| **持久化** | **机制持久化范围（唯一源）**：依赖账本的状态与说明（含当前返工登记标记）、替换指向，以及任务记录中的依赖标识、前置集合、返工来源。它们是机制事实，不能由派生视图恢复；相关变更按各动作规定的提交组写入受版本控制的记录并完成提交，未提交的变更不参与判定，也不作为已生效输入重建视图。同一提交组内的字段一同生效；多步动作仍可有多个提交组，不把整个动作或基底创建/归档变成原子事务。**提交按必要变更划界，不按整份文件划界**：首次登记尚未入库的新记录时，机制字段及使该记录可解析、可定位所必需的基底初始元数据作为记录载体一同纳入相应提交组；记录已入库时，机制提交本次机制字段的变更，不把同文件中的其他变更一并提交。两种情况均不得捎带无关的任务产物、工作改动或暂存内容；基底仍负责创建/归档等生命周期写入及工作改动与归档提交，机制纳入必要载体不改变这些归属。具体选择性提交由实现方案承载。推送由人执行 |
| **暂存** | 把变更写入工作区但不提交；未提交的变更不参与判定，后置校验失败时回滚 |
| **DAG 视图** | 由前置集合与账本派生的就绪 / 阻塞视图 |
| **任务状态** | 基底表达的生命周期：规划中 / 进行中 / 已归档；只有这三个值 |
| **图内任务** | 参与依赖机制的任务：P、实现任务、返工任务、收尾任务，以及迭代期建过依赖边的任务；开工与收尾走机制入口 |
| **图外任务** | 不参与依赖机制的任务：无关任务、无依赖的迭代任务；走原生流程 |
| **活动区 / 归档区** | 活动区＝未归档任务集合，归档区＝已归档任务集合；建边两端限制（§7.5）与返工任务集合扫描范围（§7.3）的运算对象 |
| **当前任务** | 会话正在执行、由基底活动任务指针登记的任务；可能是图内任务，也可能是图外任务。指针是**提示**：指向已归档、规划中且前置未满足、未归档且账本为“异常”（替换/放弃未完成）、或账本为“正常但未归档”的任务时，视为无当前任务（“正常但未归档”按 §7.7 类型 3 处置）；入口判定以 DAG 视图与账本为准。指针在建任务 / 开工时可能登记，归档或替换 / 放弃实施第 1 步清除；重启或换 CLI 后可能为空，也可能残留 |
| **依赖状态** | 账本表达：无记录 / 挂起 / 正常 / 异常；表达该任务是否已满足前置、是否暂停等待返工，以及下游能否开工 |
| **就绪** | 前置集合全部为“正常”（满足判定按 §4.3），且该任务未完成、未归档，且账本为“无记录”（“正常但未归档”按 §7.7 类型 3 处理，“异常”属未完成的替换/放弃、按 §7.7 类型 5 处置，均不构成就绪）；挂起清除后，任务回到就绪（即使它此前已开工） |
| **挂起** | 依赖账本状态；该任务等待返工任务，暂不满足就绪；基底任务状态不变 |
| **当前返工登记** | 说明字段中的未完成登记意图；字段许可按 §7.8，序列与恢复按 §6.4；不是累计返工清单 |
| **返工任务（返回任务，简称 R）** | 为修复该任务发现的问题而新建的任务；**挂载点必须是未归档任务 T**；前置集合 = T 当前的前置集合；T 把它加入自己的前置集合，并进入挂起。已归档任务不直接返工，其产物缺陷由当前未归档任务承载 |
| **返工任务集合** | 所有任务记录中标注“返工来源 = 该任务”的任务，包含已归档任务；由**扫描活动区与归档区**的任务记录派生（§7.3），不单独存储、不维护 ID 列表。用于判断挂起能否清除，不单独作为依赖边 |
| **替换发起** | 人决定替换并说明新任务范围（新任务标识由机制生成）；此时尚未写入任何状态 |
| **替换实施** | 机制写入旧任务账本“异常”并记录替换指向的第一步；一旦实施，只向前完成，不回退 |
| **放弃发起** | 人决定放弃并给出原因；此时尚未写入任何状态 |
| **放弃实施** | 机制写入旧任务账本“异常”并记录放弃原因的第一步；一旦实施，只向前完成，不回退 |
| **向前完成** | 替换/放弃实施后，按 §7.7 类型 5 补齐未完成步骤的修复动作；不重跑实施前静态校验，不回退 |
| **替换任务 / 替代任务 / 继任任务** | 替换实施、放弃“新建替代”变体、类型 1 补建产生的新任务；从“无记录”开始；承接旧任务在图中的位置，特殊角色按其继任规则（P 见 §6.5、§7.7） |
| **实现任务** | 0→1 链上的具体开发任务 |
| **收尾任务** | 链尾任务：验收、交付、发布与复盘 |
| **无关任务** | 不依赖链、可插入的任务（插入时机见 §6.8） |
| **迭代任务** | 0→1 结束后按普通流程执行的任务 |
| **建边** | 迭代期给任务新增一条前置边的机制入口动作；两端都必须在活动区，只表达“尚未满足的顺序”（§7.5）。对未开工任务它把任务挡在门外，对进行中任务它只挡住收尾 |
| **规格回流** | 任务完成后把经验写回规格，供后续任务自动注入 |
| **SOP** | 标准作业程序：可照着一步步执行的操作规程。设计稿只在需要交给实现方案的场合使用它（升级 SOP、目标项目同步 SOP），本身不写步骤（§0.1 口径 4、§10） |
| **对账修复** | 机制提供的唯一人工修复入口：人发起，机制执行，处理已归档但账本不是合法终态（无记录 / 挂起）、挂起无返工、正常未归档、无法解析或非法的记录 / 边、替换/放弃未完成等不一致；仍禁止手改账本文件 |
| **模块卸载** | 移除工作流模块；两种模式：仅模块卸载（保留项目数据）与完全卸载（连项目数据一起删除）；两种模式都不得影响基底使用 |

## 4. 结构与状态

### 4.1 四段结构

```text
项目层（一次）            任务层（0→1，串行）                 收尾层（一次）        持续使用
P：立项 + 基线 + 任务图 → 实现任务 1 → 2 → … → N          →  收尾任务          →  普通任务（可无依赖）
   ↓ 正常归档                 每个任务：人判 + 归档               ↓ 项目收尾
```

| 段 | 承载 | 产物 | 出口 |
|---|---|---|---|
| 项目层 | 项目层任务 P | 需求基线、技术基线、任务图、收尾任务定义 | 人确认 + P 正常归档 |
| 任务层 | 实现任务 | 每个任务自身的需求、设计、计划与代码 | 人判 + 正常归档 |
| 收尾层 | 收尾任务 | 验收、交付物、发布记录、复盘 | 人验收 + 归档 |
| 持续使用 | 普通任务 | 按需 | 原生流程 |

**返工不改四段结构**：返工任务插在被返工任务之前，是图内正常任务；返工这个动作通过依赖级挂起实现（§6.4、§9.2）。

**替换/放弃不改四段结构**：它们是任务级旁路，只改变某个任务及其下游的走法；旧任务异常归档，新任务仍在图中（§6.5、§6.6）。

### 4.2 状态

**任务状态**由基底表达：规划中 / 进行中 / 已归档。只有这三个值；任务内部的阶段回退（例如执行回到规划）不改变任务状态。

**依赖状态**由依赖账本表达：无记录 / 挂起 / 正常 / 异常。依赖状态表达该任务是否已满足前置、是否暂停等待返工，以及下游能否开工；不写进任务状态字段。

| 状态维度 | 回答的问题 | 事实源 | 允许取值 |
|---|---|---|---|
| 任务状态 | 任务本身走到哪 | 基底 | 规划中 / 进行中 / 已归档 |
| 依赖状态 | 该任务是否已满足前置 / 是否暂停 / 下游能不能开工 | 依赖账本 | 无记录 / 挂起 / 正常 / 异常 |

**两层不互相写入**：任务状态只由基底的建任务 / 开工 / 归档动作写；依赖状态只由机制的收尾 / 返工 / 替换 / 放弃 / 对账修复动作写。挂起清除不是独立动作，是表 4-2 行 3 的转移，判据与评估点统一按 §6.4 第 5 步，不写“正常”；对账修复只处理对账不一致，不参与日常流转。禁止用任务状态表达依赖状态，也禁止用账本表达任务生命周期。

**写入即校验**：任何依赖状态写入都必须先通过表 4-2 的源状态校验（§4.4、§7.5）；校验失败不写入、不重建视图。

**写入即持久化**：各机制动作的提交范围、归属与生效统一按 §3“持久化”，不在本节另列字段集；持久化失败按 §7.7 分类恢复。

**原子性口径**：本设计只保证两类性质：①**提交原子**——每个机制提交组按 §3“持久化”生效；②**可见性顺序**——下游只能在归档完成且账本提交后看到“正常”。机制不嵌入基底内部事务，**归档与机制写入不保证跨系统原子**；部分失败按 §7.7 的对账类型恢复。替换/放弃、返工、对账修复本身是**顺序 + 可恢复**的动作，不要求原子。

**暂存**：把变更写入工作区但不提交；未提交的变更不参与判定，后置校验失败时回滚。

### 4.3 完成判定

```text
任务完成 = 基底完成实施与检查 ∧ 人判 ∧ 已归档
项目完成 = 收尾任务完成
依赖满足 = 前置任务已归档且在账本中的状态为“正常”
```

- **检查** = 基底在任务执行阶段的 check（基底 Phase 2.2 / `trellis-check` 环节）；不要求 sha 级证据，不做证据链；
- **人判** = check 之后由人决定是否继续下一步（继续执行收尾动作，而不是卡在检查）；这是基底原生流程的一部分，不需要额外命令或记录；
- **归档** = 基底 archive；归档是完成的必要条件，也是账本写“正常”的前置；
- 推送不参与完成判定；工作改动与归档提交由基底流程驱动，完成判定不额外要求 sha 级证据；
- 基底的完成状态只是输入，不单独构成完成；
- P 在项目层收尾时已归档，不参与项目完成判定；
- 替换/放弃的异常归档**不产生“正常”**，也不构成完成；它们只改变下游的等待关系；
- 依赖链传递的是人的判断，不是证据链（见 §1.3）。
- **“前置为正常”的满足判定不含“正常但未归档”**：该态属类型 3 不一致，视为未满足，先按 §7.7 类型 3 修复。

### 4.4 合法流转

**表 4-1 Trellis 任务状态流转（基底）**

| # | 从 | 到 | 触发 | 写入者 |
|---|---|---|---|---|
| 1 | 无任务 | 规划中 | 建任务 | 基底 |
| 2 | 规划中 | 进行中 | 开工：规划确认；前置与目标账本校验属机制关卡（§4.5 / §7.5） | 基底 |
| 3 | 规划中 / 进行中 | 已归档 | 正常收尾（人判 + 归档）、异常归档（替换 / 放弃实施），或对账修复的重新归档 / 类型 4 放弃（§7.7） | 基底 |

任务内部的阶段回退不改变任务状态；它不是这里的流转。

**表 4-2 依赖状态流转（账本）**

| # | 从 | 到 | 触发 | 写入者 / 说明 |
|---|---|---|---|---|
| 1 | 无记录 | 正常 | 正常收尾 | 收尾逻辑；人判 + 归档 + 账本正常，按 §5.3 / §6.3 的顺序执行 |
| 2 | 无记录 | 挂起 | 发现返工 | 按 §6.4 登记准备，同次持久化当前登记标记；未发布的 R 不可执行 |
| 3 | 挂起 | 无记录 | 按 §6.4 第 5 步判据（含无未完成登记） | 评估点与清除后续均按该处；不以历史返工完成覆盖本次登记 |
| 4 | 无记录 / 挂起 | 异常 | 替换 / 放弃实施 | 替换 / 放弃逻辑；下游重连或删边，原任务异常归档；放弃的新建替代变体在本行同次写入替换指向（§6.5、§6.6） |
| 5 | 已归档但账本为无记录 / 挂起 | 正常 / 异常 | 对账修复 | 人确认，机制补记 / 改写；确认“正常”时前置须全正常；确认“异常”时同写说明与（P 的）替换指向；只用于历史任务（§7.7） |
| 6 | 正常但未归档 | 保持正常 / 无记录 | 对账修复 | 人确认：重新归档并保持正常（前置须全正常），或改回无记录；机制执行（守卫见 §7.7） |
| 7 | 挂起（未归档） | 无记录 | 对账修复类型 2：无返工记录且无登记时人确认清除；或按 §6.4 取消尚未创建 R、登记前为无记录的当前登记 | 取消与标记消费同次提交；登记前挂起的取消不走本行、不清旧挂起 |

**表 4-2 是账本写入的唯一合法转移集**：完成、返工、替换、放弃与对账修复在写入前都必须校验源状态；表中没有的转移一律拒绝并报告，不写入、不重建视图。对账修复的行 5/6/7 是修复专用转移，不适用普通动作的源状态校验；类型 4 的“修复无法解析或非法的记录 / 边”不是正常状态转移，不适用本表，按类型 4 的修复动作执行（修复记录或删边）；类型 5 的字段改写（改判放弃的说明改写与替换指向置空）不改变依赖状态值（“异常”保持“异常”），不属状态转移，不适用本表校验，其时点与顺序按 §7.7 类型 5。

**同一任务再次发现返工不是新的状态转移**：T 已挂起时仍按 §6.4 登记本次意图，不重复写“挂起”；说明标记维护及状态值不变的其他字段维护不属状态转移，伴随状态变化时仍按本表校验。

**归档终态约束**：已归档任务的账本终态只能是“正常”或“异常”；“正常”要求该任务的前置集合全部为“正常”。“无记录 / 挂起”是待修复的不一致态（类型 1）。归档任务的前置集合只能来自继承（0→1 建图、返工、替换与放弃-新建替代、类型 1 补建的继承）或活动期建边后随任务归档；建边不再往归档任务上挂（§7.5）。

**替换/放弃是前向流转**：表 4-2 没有“异常 → 无记录 / 正常”的转移。替换/放弃一经实施，旧任务账本只能保持“异常”并完成归档；失败由 §7.7 的“替换/放弃未完成”入口向前完成，不回退。

**异常没有例外通道**：异常状态不会因下游动作而改写；下游要继续，按 §7.4 处置。

### 4.5 关卡

| 关卡 | 触发 | 判定 | 强度 |
|---|---|---|---|
| **项目层收尾** | P 的代码前工作完成 | 人确认 + 基线齐（§5.2） | 机制收尾为硬；“齐”由人确认，按 §1.3 只留痕 |
| **任务开工** | 任务轮到执行 | 前置全部正常 + 目标账本无记录 + 规划确认 | 硬（机制校验） |
| **任务完成** | 任务做完 | 人判 + 收尾（表 4-2 源状态校验 + 前置全正常 + 归档 + 账本正常 + 提交；可见性顺序） | 人判为约定 / 只留痕；源状态校验与收尾的可见性顺序为硬 |
| **项目收尾** | 链上任务全部完成 | 验收 + 交付 + 发布 | 人确认 |

任务内部的规划确认由基底承担，工作流不重复设卡。**卸载不是关卡**；它是机制不可用时的恢复动作（§9.4）。

**强度口径**：表中的“硬”只指**机制动作**（校验、归档、账本写入、持久化、重建视图）；依赖人判断的部分（人判、基线“齐”、验收）属于约定层，按 §1.3 只保证可见、不保证阻断，也不担保判断为真。“硬”不覆盖人判的真实性；也不包含归档与机制写入之间的跨系统原子（§4.2）。

## 5. 项目层

### 5.1 职责

项目层任务 P 完成**具体开发代码之前的全部工作**：立项判断、需求基线、技术基线、任务图、收尾任务定义、依赖关系与初始 DAG 视图。

P 是链头，初始没有前置（被返工时其前置为返工任务，§6.4）；它本身也是图内任务，走机制的收尾动作。

### 5.2 产物与“齐”的判据

| 产物 | 内容 | 齐的判据 |
|---|---|---|
| **需求基线** | 范围、明确不做的事、验收口径 | 三项均非空 |
| **技术基线** | 架构、外部依赖、风险与回退、规格骨架 | 四项均非空 |
| **任务图** | 全部实现任务、每个任务的前置集合、收尾任务定义 | 无孤立任务；无环；收尾任务存在 |
| **DAG 视图** | 初始就绪与阻塞 | 由前置集合 + 账本派生，可重建 |
| **基线载体** | 项目文档（人类可读正文） + 规格（AI 注入面） | 两者都存在且互相引用 |

**口径**：“齐”指有且能读懂，不规定篇幅；不设裁剪档位。缺任一行判据即不齐，P 不得收尾。

**任务图不是第二事实源**：项目文档里的任务图是基线计划，供人阅读与评审；真正的事实源是任务记录中的前置集合与依赖账本。两者不一致时，以前置集合与账本为准，任务图按需更新，不反向写入机制。

P 给每个实现任务写清**基础信息**：项目背景、基础要求、任务目标、验收锚点。实现任务轮到时再细化，不在 P 阶段把细节写死。

### 5.3 完成

人确认后执行**收尾**：

```text
人确认 → 校验源状态（账本为“无记录”，且前置集合全部为“正常”） → 归档 → 账本写“正常” + 持久化 → 重建 DAG 视图
```

这组步骤按**可见性顺序**执行：任一步失败都不能让下游看到“已正常”。这里的“整体”是对下游可见的顺序保证，不是跨系统原子事务（§4.2）；失败按 §7.7 对账恢复，不重放。源状态校验失败时不归档、不写账本：账本为“挂起”按 §6.4 / §6.6 的返工 / 放弃规则处置，为“异常”按 §7.7 类型 5，为“正常但未归档”按类型 3，前置集合不全正常按 §7.7 组合表的“等待”行处置。P 正常归档后，实现任务 1 就绪。

**持久化边界**：账本“正常”只有在按 §3 定义持久化成功后（写入 + 提交）才生效；未持久化的写入不参与就绪判定。若归档成功但账本写入/持久化失败，按“已归档但账本无记录”处理（§7.7），不放行下游。

### 5.4 基线

- 基线是**活的**：以项目文档与规格为准，由后续任务与迭代持续更新；
- P 归档后，它只是**记录**，不再是工作参考；
- 后续任务与迭代任务读取的是活文档与规格，不是归档任务目录。

### 5.5 基线变更

范围、架构、验收口径或契约发生变化时：

1. 回到项目文档更新基线；
2. 更新依赖图：先**由人决定**旧任务的工作在新基线下是否仍然成立，按决定走两条互斥路径之一；
   - **仍然成立**（其工作后续会被正常完成）——**轻量用法**：只适用于旧任务未归档且账本为“无记录”或“挂起”。旧任务账本为“正常但未归档”或“异常”时，先走各自出口、按出口终点接续：类型 3 修复改回“无记录” → 按轻量用法继续；类型 3 修复重新归档（工作已完成）→ 任务已归档，不再是本步对象，按第 3–4 步继续；向前完成（替换）→ 替换任务继承位置，以它为判定对象回到本步判定；向前完成（放弃）→ 按变体分：删边变体下游已删边、无重连对象，按第 3–4 步继续；新建替代变体（§6.6）替代任务继承位置，以它为判定对象回到本步判定。新建任务，不产生异常旧任务；新任务继承旧任务当前的前置集合（§6.5 实施第 2 步）。**重连范围由人决定**：默认把全部未归档下游重连到新任务（§6.5 实施第 3 步）；人决定保留部分下游在旧任务上时，只对要转移的下游按 §7.5 边变更逐条建边到新任务、自旧任务删边，旧任务保留剩余下游。边变更按 §7.5 校验。旧任务保留在图中，是否就绪统一按 §3；挂起者须先按 §6.4 清除挂起。旧任务与新任务都就绪且无当前任务时，按 §7.6 选择创建时间较早的旧任务，不靠已重连的下游边决定顺序；新建任务持有有效当前指针时按 §9.1 继续它。未满足就绪条件的旧任务留在图中等待或按对应入口处置，不因轻量用法直接进入就绪集；它的出口只有两个：按正常流程完成收尾，或在下一次基线变更时重新按本步判定。**不得把旧任务直接归档**（无收尾动作的归档是 §7.7 组合表的“已归档 + 无记录”非法组合，转类型 1）；**不得对旧任务自动放弃**（表 4-2 行 4 会把它写成“异常”，与“不产生异常旧任务”相悖；放弃属于下一条路径）；
   - **不再成立**（旧任务的工作不再按原计划成立：被新基线取代、裁剪或不再需要；无论旧任务是否已开工）——**替换 / 放弃**（§6.5 / §6.6）：旧任务异常归档，未归档下游重连到替换任务或删边。产生一个“异常”旧任务是替换 / 放弃的固有语义，不是基线变更的额外代价；旧任务若带已归档正常下游（仅类型 4 未修复的中间态会出现），放弃后该下游命中 §7.7 组合表行 2，按类型 4 删边修复。
3. 不追溯已归档任务；
4. 变更本身可以在迭代期以普通任务承载。

**已归档任务不可替换、不可放弃、不可重开**：归档区不作业务改写；损坏字段的受控恢复例外统一按 §7.8 类型 4 恢复边界，不改变任务生命周期。**已归档任务不直接返工**：其产物缺陷由当前未归档任务承载返工（§6.4）；维护期由普通任务承载。返工任务不改变旧任务的账本状态，只把修复工作挂到被返工任务之前。

### 5.6 P 在图中的位置

P 是链头；所有 0→1 实现任务直接或间接依赖 P。P 对象及项目层是否收尾按 §6.5 解析；正常完成后，链上前置已满足的第一个任务就绪，归档待对账不等于完成。

## 6. 任务层

### 6.1 任务集

- 0→1 的实现任务**全部由 P 产出**；
- 任务**串行、顺序固定**，由前置集合表达；
- 每个任务带基础信息与前置集合；
- 开工前校验前置是否全部“正常”；
- 顺序不靠编号，靠依赖边。

### 6.2 规划

- P 给基础信息，任务轮到时再细化设计、计划与验收锚点；
- 细化**不改变基线**；要改基线，走 §5.5；
- 后段任务先写轮廓，轮到时再细化，允许滚动规划；
- 未就绪的任务不做完整规划，避免基于过期前置做计划。

### 6.3 完成

```text
基底完成实施与检查 → 人在 check 后判断是否继续（人判） → 校验源状态（账本为“无记录”，且前置集合全部为“正常”） → 归档 → 账本写“正常” + 持久化 → 重建视图
```

与 P 的收尾相同的可见性顺序；完成后下游解锁。人判不需要额外命令或记录：它就是基底 check 后的原生人工环节。源状态校验失败时的处置与 §5.3 相同：挂起按 §6.4 / §6.6 的返工 / 放弃规则，异常按 §7.7 类型 5，正常未归档按类型 3，前置集合不全正常按 §7.7 组合表的“等待”行处置。

**持久化边界**：账本“正常”只有在按 §3 定义持久化成功后（写入 + 提交）才生效；归档成功但账本未持久化的，按“已归档但账本无记录”处理（§7.7）。

### 6.4 返工

**适用范围**：返工只作用于**未归档任务**。T 必须未归档，且账本为“无记录”或“挂起”；否则拒绝并报告：已归档任务不直接返工（其产物缺陷由当前未归档任务承载，§5.5），账本“异常”先按 §7.7 完整性分类再处置，账本“正常但未归档”按类型 3 处置。

**返工登记（动作序列与窗口的唯一源）**：由人判断并发起。复用账本说明中的当前登记标记（字段许可见 §7.8 矩阵），区分“本次 R 尚未登记”与“历史 R 全已完成”；不新增状态值、记录类型或返工 ID 列表。

1. **准备**：校验 T 的适用状态，且同一 T 没有未完成登记；预生成 R 的依赖标识及创建前可确定的稳定基底定位。T 记挂起与按矩阵（返工登记准备行）写入标记同次提交；T 原已挂起时只登记本次意图，不重复状态转移。提交后阻断普通选择，不能因旧 R 都已归档而清挂起。
2. **创建或找回**：按已提交标记中的稳定定位调用基底建 R，或读回该位置的同一个 R；位置占用、创建结果不明或无法唯一核对时停止，按类型 4 恢复已知信息，不另生成 ID、不盲目重复建任务。此时基底创建可能登记当前指针，但 R 未发布前不得执行，也不得当作图外任务继续；§9.1 全局旁路先接管。定位格式/命令由实现方案承载，不能假设跨系统原子或只靠创建后才写入的依赖标识找回 R。
3. **发布**：按 §7.5 暂存及后置校验，把 R 的预定依赖标识、返工来源（矩阵返工来源写入行）、继承前置、T 加 R 边，以及消费登记标记（矩阵返工登记发布行）同次提交。R 继承的是 T **已提交的当前前置集合**，不含本次暂存加入的 R 边，避免自环；不修改 T 的基底任务状态。登记未完成期间，除本登记的恢复/取消及类型 4 受控恢复外，禁止其他机制动作改 T、待登记 R 及其边，继承输入不被并行改写。后置失败只回滚本次未提交字段，保留已提交标记和已创建的基底任务；不发布半套来源或边。
4. **执行**：发布成功后按普通图内任务执行 R；完成与归档按 §6.3，归档成功但正常账本未持久化仍先修复 R，不能放行 T。
5. **挂起清除（唯一判据）**：T 未归档且挂起、**无未完成返工登记**、扫描活动区与归档区所得返工集合非空且无未归档成员、T 前置集合全部正常，才能按表 4-2 行 3 清挂起并提交。T 回到就绪（即使此前已开工）。评估点为 R 收尾、放弃/替换的删边与重连、启动对账、入口第二段；均引用本判据，清除失败/崩溃由下次评估补做，不要求跨任务原子。

**登记恢复与取消**：启动先识别登记标记，不自动创建 R。人选定类型 2 恢复入口后，按已有确认补齐本节步骤，不重做已完成确认；标记缺项/非法先类型 4。人决定取消且已确认本次 R 尚未创建时，按矩阵（返工登记取消行）与恢复 T 登记前状态同次提交：登记前无记录则用表 4-2 行 7，登记前挂起则仍挂起、不取消既有返工。R 已创建时先完成登记，再按 §6.6 放弃 R；不删掉任务冒充取消，也不扩大替换/放弃的回退权限。消费标记只移除本次结构化部分，保留原说明；状态值不变的维护不构成新转移。

合法登记要求 T 未归档且挂起，标记可唯一对应预定 R，且原状态在本节允许范围；不符先类型 4。多个未完成登记按挂载 T 的创建时间逐项恢复；同一 T 的后续新增请求先完成当前登记，不覆盖它。登记恢复不改变普通就绪任务的创建时间排序。

**逐窗口**：

| 窗口 | 已提交识别项 / 残留 | 恢复 |
|---|---|---|
| 准备提交前 | 无本次标记、状态未变 | 本次尚未实施，不声称已有返工 |
| 准备后、创建前 | T 挂起 + 当前标记；历史 R 是否存在不影响识别 | 类型 2 继续登记，或人确认尚未创建后取消 |
| 创建调用中断 / 已建未发布 | 标记含固定定位；R 可能已建、机制来源与边尚未提交 | 读回同一位置，找到即复用；不明则类型 4 阻断；不选择 R 执行 |
| 发布暂存 / 后置校验失败 / 提交前中断 | 已提交标记仍在，工作区有未生效字段 | 只读提交事实源；回滚本次暂存后按同一标记补齐发布，不删 R |
| 发布已提交、视图未重建 | 标记已消费，R 身份/来源/前置与 T 的 R 边一同生效 | 重建视图，按正常返工继续；不重复创建 |
| R 已归档、正常账本未提交 | R 未满足依赖 | 类型 1 修复 R；T 保持挂起 |
| R 正常已提交、T 未清挂起 | 无当前标记，R 已归档正常，T 仍挂起 | 按步骤 5 评估；有其他活动 R/未满足前置则不清 |
| 取消提交前 / 后 | 前：标记保留；后：标记已消费且原状态已恢复 | 前仍按登记恢复，后不重复取消；原挂起不得误清 |

**旧口径移交**：v41 及更早的无标记存量挂起，可能是历史 R 完成待清，也可能是新一轮未建 R；现有字段不足以区分。启用本口径前须由人确认每项意图，再正常评估或按本节补登记；无法确认时阻断。版本识别、移交入口与验证由实现方案承载。移交完成后，新准备/发布遵守本节，不把无标记的旧歧义静默算作完成。

**返工挂载点是未归档任务**：附录 B 的 T2 就是挂载点；不得把挂起落到已归档任务上。

**返工任务是图内正常任务**，遵守同一套开工/收尾；返工通过依赖级挂起实现，不是另一套任务生命周期。挂起清除引用步骤 5，不按某个历史 R 的归档时点或集合非空一项推断。

返工集合从已提交的任务记录派生，成员是否已归档按步骤 5 使用；待登记意图不是已完成 R 的 ID 清单。返工来源在登记发布/继承时写入，归档后不再作业务改写；**例外：损坏记录可按 §7.8 类型 4 恢复边界受控恢复**。记录无法解析时按 §7.7 计入对账不一致，不静默算作“没有返工任务”。

### 6.5 替换

替换只适用于**未归档任务**。已归档任务不可替换（§5.5）；已归档任务不直接返工，其产物缺陷由当前未归档任务承载（§5.5、§6.4）。

**发起（人）**：人决定替换并说明新任务范围；机制先生成新任务标识，并做**实施前静态校验**：

- 新任务继承的前置集合 = 旧任务**当前**前置集合；
- 重连后的边集不成环；
- 目标状态合法（新任务不存在、旧任务未归档，且旧任务账本为“无记录”或“挂起”）。

校验失败：不实施，旧任务不变，报告原因。此时尚未写入任何状态，不算“回退”。实施前静态校验只在发起时执行；实施后失败走 §7.7 的向前完成，不重跑该静态校验。

**实施（机制，一旦开始不可回退）**：

1. 旧任务账本记“异常”，说明与替换指向按 §7.8 识别字段写入矩阵（替换实施行）写入；持久化；旧任务立即退出就绪集，不再可被选择；若旧任务持有会话当前任务指针，清除该指针（按基底入口）；
2. 创建新任务；新任务继承旧任务当前的前置集合；新任务从“无记录”开始；
3. 把所有未归档下游（包括夹在中间的返工任务）重连到新任务标识；从下游的前置集合中移除旧任务标识；边变更按 §7.5 校验；
4. 检环；静态校验已排除的环若仍出现，停止并报告，旧任务保持“异常”，由 §7.7 的完成入口向前处置；
5. 旧任务以异常归档离开活动列表（基底 archive）；
6. 重建视图，持久化。

**失败与修复（只向前）**：实施后崩溃，旧任务保持“异常”，下游保持阻断；**识别与向前完成的动作序列、步骤顺序与逐窗口以 §7.7 类型 5 为唯一源**，本节不另写一份序列，只保留本任务侧的两条结论：

- **向前完成不重跑实施前静态校验的目标状态条件**：旧任务“异常”正是待修复状态本身；补建 / 重连仍做目标存在性、目标不是“异常”、成环校验；
- **替换一经实施就不能回到实施前**：继任者已存在而人决定不再继续时，只能把继任者按 §6.6 的变体放弃并完成相应的重连 / 删边；继任者不存在时由人确认走向，按 §7.7 类型 5 补建或改判放弃——**不能恢复旧任务**。

**挂起中的 T 被替换**：R 是 T 的前置，不属于“未归档下游”，**不重连**；R 留在图中按普通任务处置；新任务继承 T 的当前前置集合（含 R），因此仍等待 R；若人决定不再需要 R，按 §6.6 放弃 R。新任务的前置集合若后续出现异常成员（例如 R 被放弃），按 §6.6 的删边或 §6.5 的替换处置；异常前置不会因为被继承而获得豁免。

**替换返工任务 R**：新任务继承 R 的“返工来源”标记；R 归档后其成员状态按 §6.4 第 5 步评估；不能跳过待登记标记或其他前置条件。新任务取代 R 的位置，T 的返工任务集合按“返工来源”派生。

**替换 / 放弃项目层任务 P**：P 的继任者即新的 P——替换时是替换任务；放弃时走新建替代变体，替代任务即新的 P（§6.6）；类型 1 补建时是补建的新 P（§7.7）。旧 P 异常归档，不再承担项目层；§5.6 与 §9.1 的项目层判定、§4.5 项目层关卡一律以继任者为对象（P 按角色解析，换过 ID 不改变判定）。基线产物（项目文档、任务图）由继任者续写。

**P 角色解析（唯一源）**：普通路由前先完成 §7.7 的完整性分类与 §6.4 的登记阻断检查，再沿已经确立的继任关系逐任解析，不把正常完成当作异常处分：

| 节点情况 | 判定对象 / 出口 |
|---|---|
| 未归档，账本无记录 / 挂起 | 当前 P，项目层未收尾；按普通 / 返工入口继续 |
| 未归档，账本正常 | 类型 3，修复前不判项目层已收尾 |
| 已归档，账本正常，且前置满足 §4.3 | 正常完成的 P 终点，项目层已收尾；保留下游依赖边，不要求满足异常处分谓词 |
| 已归档，账本正常，但前置未满足 | 类型 4；不提前判已收尾 |
| 已归档，账本无记录 / 挂起 | 类型 1；确认异常时仍由其 P 分支建立继任关系 |
| 账本异常，合法预写指向在，但处分未完成（§7.4） | 类型 5 先补建 / 重连 / 归档，不继续旧 P |
| 已归档，账本异常，处分已完成（按 §7.4），指向合法继任者 | 沿指向继续解析，最终项目层判定由链尾决定 |
| 账本异常，指向丢失 / 非法，不能确定原预写继任关系 | 角色完整性不一致，先类型 4 恢复既有关系；无据则阻断，不走一般任务无指向删边分支 |

**角色完整性守卫**：异常 P 的指向丢失 / 非法先于类型 5 分流；合法预写标识在而目标尚未创建属于类型 5，不因目标未建误算非法关系。原值无法确认、身份环或角色无法唯一解析均按类型 4 阻断。已是异常的 P 不符合类型 1 的源状态，不能用类型 1 或类型 4 新造继任关系来摆脱阻断。§9.1 只消费本节的 P 对象与已收尾结果。

替换任务本身从“无记录”开始；它完成正常收尾后才记“正常”。替换任务的内容与依赖机制无关，机制只负责继承与重连。

### 6.6 放弃

放弃只适用于**未归档任务**（发起时）；已归档任务不可放弃（§5.5）。**例外**：旧任务账本已是「异常」且处分未完成（§7.4 的字段句）时，不重新发起放弃——旧任务可能已归档、也可能仍处于实施未完成态，一律按 §7.7 类型 5 向前完成，不走本节的发起与实施第 1 步。

**发起（人）**：人决定放弃、给出原因，并选定处置变体（**删边** / **新建替代**）；机制做实施前静态校验（旧任务未归档、旧任务账本为“无记录”或“挂起”、下游边删除/替代后不成环；新建替代变体另校验新任务继承的前置集合 = 旧任务当前前置集合），新建替代变体同时预生成替代任务的依赖标识；校验失败则不实施，旧任务不变。

**实施（机制，一旦开始不可回退）**：

1. 旧任务账本记“异常”，说明与替换指向按 §7.8 识别字段写入矩阵（放弃两变体行）写入；持久化；旧任务立即退出就绪集；若旧任务持有会话当前任务指针，清除该指针（按基底入口）；
2. 按发起时选定的变体执行（不再在本步决定）：
   - **删边**：从所有未归档下游的前置集合中删除旧任务标识；记录影响与原因；
   - **新建替代**：用第 1 步预写的标识创建替代任务，继承旧任务当前的前置集合，再把下游重连到替代任务（§6.5 实施第 2–3 步）；
3. 重连后检环；失败则停止并报告，旧任务保持“异常”，由 §7.7 的完成入口向前处置；
4. 旧任务以异常归档离开活动列表；
5. 重建视图，持久化。

**失败与修复（只向前）**：实施后崩溃，旧任务保持“异常”，下游保持阻断；按 §7.7 类型 5 向前完成（识别、序列与窗口以该处为唯一源）；不恢复旧任务。

**放弃返工任务 R**：删边变体完成后，T 是否清挂起统一按 §6.4 第 5 步（表 4-2 行 3）评估；新建替代变体按 §7.8 返工来源写入行继承返工身份，T 的集合继续包含未归档替代 R。若 T 已被替换或放弃，R 按“R 留在图中按普通任务处置”的规则处理。

**放弃项目层任务 P**：只允许新建替代变体——删边变体不留继任者，项目层判定会失去对象（继任规则见 §6.5）。

### 6.7 收尾任务

- 位于链尾，依赖最后一个实现任务；
- P 阶段只定义它“存在”与“怎么做”，不定死验收、交付与发布；
- 到收尾时再按基线与现状细化验收口径、交付物与发布方式；
- 收尾任务完成 = 项目完成；
- 最后任务被替换时，收尾任务的前置随重连规则更新；
- 收尾任务自身被替换或放弃时，由人重新定义收尾任务；项目完成判定以新的收尾任务为准；
- **交付**指自用交付物与发布记录；对外交付到他人环境不在本设计内。

### 6.8 无关任务

- 不依赖链，也不被链依赖；插入时机（由人决定）：**P 归档后**可随时插入；P 未归档时不新插入无关任务，已持有的图外当前任务先做完再回 P（§9.1 不中断已持有的当前任务）；
- 只提交自身范围内的改动；
- 若触碰基线（范围、架构、验收、契约），回到 §5.5；
- 单一工作线：无关任务与链任务**不并行编辑**，只切换执行。

## 7. 依赖机制

> 完整规则见 [依赖机制设计说明](./依赖机制设计说明.md)。本节只规定设计层必须遵守的约束；配套文档与本文同版，机制细节冲突以配套文档为准，设计层约束冲突以本文为准。

### 7.1 目的与适用

- 0→1 阶段**必选**；
- 后续阶段**可选**；只要使用，就遵守同一套规则；
- 用途只有一个：保障顺序。

### 7.2 边界

- 任务是 DAG，不能有环；
- 不调度、不并行、不设优先级、不跨项目、不隔离资源；
- 只表达“谁必须在谁之前完成”；
- 替换/放弃不回退；已实施的操作只向前完成。

### 7.3 事实源

| 产物 | 性质 |
|---|---|
| 前置集合 | 存储，**唯一事实源** |
| 依赖账本 | 存储，**状态事实源**（新增“正常”只由收尾逻辑或对账修复的类型 1 写入） |
| 依赖标识 / 返工来源 | 存储，任务记录中的机制事实；含义按 §7.8，持久化按 §3 |
| 下一个集合 | 派生（见 §3） |
| 返工任务集合 | 派生（扫描活动区与归档区的任务记录，按“返工来源”派生；不存储、不维护 ID 列表） |
| DAG 视图 | 派生 |

**返工任务集合不另存一份**：账本不保存“T 的累计返工任务列表”，当前未完成登记意图按 §6.4；任务记录也不保存返工任务 ID 列表。集合每次从**活动区与归档区**的任务记录重建，所以不存在“ID 列表与前置集合不一致”这一类额外对账分支，也不需要为它定义清理规则。扫描方式（顺序读取、缓存、索引）属于实现选择，设计层只要求范围覆盖两个区，且结果等价于逐个读取任务记录。

**事实与派生**：机制事实的范围及持久化按 §3；本表的派生件由已提交事实重建，不能反向替代原事实。

### 7.4 状态与判定

完整状态表与判定以配套文档 §5 为准；本设计只保留对下游的结论：

| 账本状态 | 对下游 |
|---|---|
| 无记录 | 不满足 |
| 挂起 | 不满足 |
| 正常 | 满足（“正常但未归档”除外，满足判定见 §4.3） |
| 异常 | 不满足。按字段判处分，**下游范围为未归档下游**：**处分未完成**（有合法替换指向而继任者未建、未归档下游仍指向该任务、该任务未归档——三者任一）→ 按 §7.7 类型 5 向前完成；**处分已到终态**（已归档，且未归档下游已不指向它，且（无替换指向 或 继任者已建））→ 无需处分动作。字段非法 / P 角色完整性失效先走类型 4（P 守卫见 §6.5）；已归档正常下游含异常前置仍是类型 4，不因本行忽略归档历史边而放行。已归档任务不可再发起替换 / 放弃；已实施部分按类型 5 完成 |

- “正常”只由收尾逻辑或对账修复写入；对账修复**新增“正常”**只用于已归档且账本无记录或挂起的修复（确认“正常”时前置须全正常）；“正常但未归档”的修复是重新归档并保持“正常”，或改回“无记录”；“挂起无返工任务”只清挂起或补建 R，不写“正常”；
- 机制事实的保存与不可由派生件恢复的边界统一按 §3“持久化”；
- 异常没有例外通道；下游要继续，只能通过替换 / 放弃重连到新任务，或删边后不再等待。**处分按字段定、不按来源枚举**，终态 / 未完成的字段谓词**以表行（上文）为唯一源**（配套 §5 同此口径）：未完成 → 按 §7.7 类型 5 向前完成；已到终态 → 无需动作；替换指向的写入与清空时点按 §7.8 识别字段写入矩阵；已归档任务不可再发起替换 / 放弃（实施后未完成的部分按 §7.7 类型 5）；P 的角色完整性与解析按 §6.5，类型 1 的 P 分支仅处理其合法源状态；
- 替换/放弃实施后，旧任务的“异常”不能改回“正常 / 无记录”；失败只向前完成。

### 7.5 生命周期

**统一入口前置**：以下开工、完成、返工、替换/放弃和边变更，在各自静态校验之前先按 §9.1 第一段分流；登记期间涉及 T / 待登记 R 的受控操作按 §6.4，不能通过另一机制动作改写登记输入。类型 4 的字段许可与例外按 §7.8；普通动作不得借类型 4 名义跳过守卫。

- **开工**：校验前置全部“正常”，且目标任务账本为“无记录”（挂起 / 异常 / 正常未归档一律拒绝并报告）；普通入口须先完成 §9.1 全局旁路分流，登记未发布的 R 不得按图外任务继续；满足后登记当前任务（基底入口），否则停在规划态；
- **完成**：人判 → 校验源状态（账本为“无记录”，且前置集合全部为“正常”） → 归档 → 账本“正常” + 持久化 → 重建视图，按 §5.3 / §6.3 执行；
- **返工**：走 §6.4；T 必须未归档，且账本为“无记录”或“挂起”；
- **替换 / 放弃**：走 §6.5、§6.6；只适用于未归档任务；实施前静态校验就是状态校验的特例；实施后只向前完成；
- **迭代期建边**：后续阶段允许新建普通依赖边（非返工、非替换；由人发起）；建边是机制的正常入口动作，不是基线变更，也不是旁路。边只表达“尚未满足的顺序”，据此定边界、校验与两种目标下的效果：
  - **两端都必须在活动区**。已归档任务不再被选择、不再收尾，给它挂前置改变不了任何判定，只会在归档终态上留下“前置非正常”的组合，所以不接新建边；已归档任务可作为前置，只来自继承（0→1 建图、返工与替换继承）或活动期建边后该前置归档——边建于两端都在活动区时，前置一侧随后归档，边继续有效。删边不受此限，可对归档目标执行（类型 4 修复要用）；**迭代期删边同样由人发起**，只改顺序约束、不改变任何任务的账本状态，校验见下文“边变更的统一校验”。
  - **前置必须尚未完工**（账本为“无记录”、“挂起”或“正常但未归档”——该态按 §4.3 视为未满足，建边是允许表达顺序，不等于已满足）；前置账本为“异常”的不得建边。
  - 目标账本为“异常”的不得建边（先按 §7.7 类型 5 向前完成）；目标账本为“正常但未归档”的，先按类型 3 修复。
  - 不得自环、不得成环（后置校验再检一次）。
  - **对未开工目标**：边立刻把目标挡在就绪之外，目标按 §7.7 组合表的“等待”行处理，前置完成后自动回到就绪。
  - **对进行中目标**：边不阻止它继续执行，只阻止它收尾（§6.3 的收尾要求前置全正常）。这类组合就是 §7.7 组合表里的“等待”行，不算需要修复的不一致；前置一直不完成时，人按删边或替换 / 放弃处置。
  - 建边后按本节的暂存 / 后置校验 / 提交规则处理；
- **边变更的统一校验**：建边、返工加边、替换/放弃的重连（新增或替换边）做前置校验（两端存在；目标不是异常；建边另要求两端在活动区、前置未完工（含“正常但未归档”）；无自环/成环）→ **写入暂存（不提交）** → 后置校验（检环、重建视图）→ **通过后提交**；后置校验失败 → **回滚暂存、不提交、报告**；**删边同样先暂存、重建视图后提交**，因为被删的目标可以已经是“异常”、也可以在归档区；前置校验失败不写入；
- **状态变更的统一校验**：完成、返工、替换、放弃、对账修复在写入账本前，必须校验本次写入在表 4-2 中有对应的源状态与目标状态；表中没有的转移一律拒绝并报告，不写入、不重建视图。开工的前置与账本状态校验见上；替换/放弃的实施前静态校验、对账修复的行 5/6/7 是这条规则的特例；类型 4 的“修复无法解析或非法的记录 / 边”不是正常状态转移，不适用源状态校验，按类型 4 的修复动作执行（修复记录或删边）；类型 2 的“清除挂起”按表 4-2 行 7 执行；类型 5 的字段改写（改判放弃的说明改写与替换指向置空）不改变依赖状态值，不属状态转移，不适用本条校验（§4.4 同款登记）。校验只作用于机制入口；绕过机制直接调用基底动作不在本设计的防护范围内（§1.3）；
- **异常归档**：替换或放弃的任务以异常归档离开活动列表，判定以账本为准。

### 7.6 选择

- 就绪集是**图内任务**的集合（含实现任务、返工任务、收尾任务；迭代期建过依赖边的任务也是图内任务）；
- 就绪集按**任务创建时间**排序，取最早；
- 选择规则用于**没有当前任务**时；有当前任务时先继续当前任务（§9.1）；
- 0→1 链式结构下通常只有一个就绪任务；
- 多组件或多就绪节点时使用同一规则；
- 返工任务与其他就绪任务按同一规则排序，不设优先级；任务入口选择以 §9.1 为准。

### 7.7 一致性与恢复

- **开工前对账**：前置集合、账本、派生视图一致才允许开工；
- **启动时对账**：先读提交事实源并做下表完整性分类：未完成返工登记按 §6.4 识别为类型 2，标记/定位损坏先类型 4；异常 P 的角色完整性按 §6.5 分流；其余字段非法按类型 4，替换/放弃及类型 1 确认后的未完成处分按 §7.4 识别为类型 5。派生视图可重建，但这些全局待恢复项处理前不进入普通选择、不自动创建任务。已移交旧口径后，对无登记阻断的未归档挂起按 §6.4 第 5 步评估并持久化；除此派生清除外，启动只识别/报告，不写账本、不改任务状态，不自动执行对账修复；
- **启动时挂起但条件未满足**：先排除上述全局项，再由 §9.1 第二段选择；异常前置按 §7.4，正常但未归档前置按类型 3；不因当前指针指向待登记 R 而绕过恢复；
- **绕过兜底**：
  - 已归档但账本为无记录 / 挂起 → 类型 1，不放行；
  - 正常但未归档 → 类型 3，视为依赖未满足；
  - 无法解析或非法的记录 / 边、已归档正常但前置未满足 → 类型 4，不静默跳过；
  - 合法可解析的异常处分按 §7.4 表行判断；异常 P 还须先通过 §6.5 角色完整性守卫。有指向缺说明或指向与说明双缺失均先按类型 4、§7.8 恢复必要字段，再判断是否需要类型 5；一般任务有合法原因且无指向的未完成处分按类型 5 无指向分支。不能把合法预写但目标未建判成非法指向，也不能为无法确认的指向猜造继任关系；

**账本 / 归档组合自检**（启动时与每次对账前执行；读账本 + 基底任务状态）：

**分类前置守卫**：表中普通组合须先排除 §6.4 的未完成登记/旧口径移交，以及 §6.5 / §7.8 的字段与角色完整性不一致；分别走其类型 2 / 4 入口。组合合法只代表此维度合法，不覆盖这些守卫。不得把异常 P 的无指向状态先落入一般处分分支。

| 组合 | 判定 | 出口 |
|---|---|---|
| 已归档 + 正常 + 前置全正常 | 合法 | — |
| 已归档 + 正常 + 前置含非正常 | 非法 | 类型 4 |
| 已归档 + 挂起 | 非法 | 类型 1（人确认正常 / 异常后改写） |
| 已归档 + 无记录 | 非法 | 类型 1（人确认正常 / 异常后补记） |
| 已归档 + 异常 | 合法（替换 / 放弃结果；未完成的按类型 5） | — |
| 未归档 + 正常 | 不一致 | 类型 3 |
| 未归档 + 挂起（任意前置） | 合法（等待返工） | §6.4 评估 / 进入 R；前置不全正常时按挂起阶段的对账行 |
| 未归档 + 异常 | 替换 / 放弃未完成 | 类型 5 |
| 未归档 + 无记录 + 规划中 / 进行中 + 前置全正常 | 合法（就绪） | — |
| 未归档 + 无记录 + 规划中 / 进行中 + 前置含非正常（“正常但未归档”见下一行） | 等待 | 不修复，等前置完成；前置为异常时按 §7.4 处置，仍无出口按类型 4 |
| 未归档 + 无记录 + 规划中 / 进行中 + 前置含“正常但未归档” | 等待（欠一次类型 3） | 先按类型 3 修复该前置 |

- **待对账修复的唯一出口**：由人发起、机制执行；仍禁止手改账本文件。

  **修复的写入纪律**：任一修复类型若含多步写入，识别所依赖的标记（替换指向 / 原因 / 说明）必须与第一步状态写入同次持久化，并逐窗口给出残留态的识别项与向前完成，不得只写终态；识别不得依赖后置字段。向前完成一律不回退、不重跑已完成的确认步骤。单步或崩溃后即收敛的修复（类型 3 的重新归档）不需要额外窗口；类型 2 的登记恢复、补建与取消沿用 §6.4 的序列和窗口。

  按不一致类型处理：
  1. **已归档但账本不是合法终态（无记录 / 挂起）** → 人确认“正常 / 异常”，机制补记或改写账本；确认“正常”时该任务的前置集合必须全部为“正常”，否则先按类型 4 修复边，或改为确认“异常”；这是“正常”的合法修复写入。确认“异常”时**先落账本（含标记）、再动下游**：
     - **一般任务**：账本写“异常”，说明按 §7.8 识别字段写入矩阵（类型 1 一般任务行）写入并持久化；随后按 §7.4 处置其未归档下游（本类型没有替换指向，处分未完成时按 §7.7 类型 5 的“无替换指向”分支补齐删边与旧任务归档）。
     - **项目层任务 P 且尚无继任者**：账本写“异常”，说明与替换指向按 §7.8 识别字段写入矩阵（类型 1 P 分支行）同次写入；随后按 §6.5 的继任规则建新 P（**用替换指向里的标识建任务**；不再走 §6.5 的替换发起与实施第 1 步——实施前校验的“旧任务未归档”“账本为无记录 / 挂起”在此必然不成立）、按 §6.5 实施第 2 步继承旧 P 的当前前置集合、按实施第 3 步把旧 P 的未归档下游重连到新 P，重连前做目标存在性、目标不是“异常”、不成环校验（与类型 5 同款）。不补继任者则项目层判定失去对象。
     - **逐窗口**（残留一律按类型 5 向前完成，不回退、不重跑确认）：确认前失败 → 状态未变，重走本类型；确认后、下游未处置完（一般任务）→ 按类型 5 补齐删边；P 分支见下两个窗口；P 的替换指向已写而新 P 未建 → 按类型 5 补建；新 P 已建、下游未重连完 → 按类型 5 补齐重连。
  2. **返工登记未完成，或未归档任务挂起但找不到返工任务** → 有合法登记标记时按 §6.4 的原序列恢复/取消，不重跑已确认的人判；标记有损先类型 4。无标记且已完成旧口径移交后，人确认补建（按 §6.4 新登记）或在确无返工记录时按表 4-2 行 7 清挂起。旧口径的无标记存量挂起先按 §6.4 的移交条款确认，不拿历史 R 记录替代本次登记意图；
  3. **正常但未归档** → 人确认重新归档（账本保持“正常”；**该任务前置集合须全部为“正常”，否则先按类型 4 修复边，或改回“无记录”**）或改回“无记录”；机制执行并持久化；
  4. **无法解析或非法的记录 / 边**（含角色完整性/登记标记不一致） → 人发起，机制按 §7.8 矩阵的类型 4 行及恢复边界修复字段，或按 §7.5 删非法边；不另复述字段终值。恢复字段同次提交，提交前失败仍是原不一致，提交后重新分类；预写指向恢复后如目标未建转类型 5，登记标记恢复后转类型 2，不借修复新建任务/关系。未归档任务确需放弃时，先恢复到普通放弃守卫可接受的状态，并先完成该任务的未完成登记，再按 §6.6 处分；不能用放弃掩盖未解决的身份。无法恢复时阻断，不静默放行；
  5. **替换/放弃未完成** → 机制向前完成（按人确认的走向）。**本项是「向前完成」的唯一源：动作序列、步骤顺序与逐窗口都在此定义，其他位置只许引用**。顺序固定为**先补建 / 重连、后归档**——先归档会让补建变成“对已归档任务替换”，与本设计的“已归档不可替换”相冲突：
     - **补建**：用替换指向里的标识建新任务，按 §6.5 实施第 2 步继承旧任务当前的前置集合、按第 3 步重连未归档下游；继任者已建时只补齐重连；最后归档旧任务。不重跑实施前“旧任务账本为无记录 / 挂起”的校验（旧任务的“异常”正是待修复状态），但仍校验目标存在、目标不是“异常”、不成环；
     - **改判为放弃**（只在继任者不存在时，由人决定）：**一般任务**——说明与替换指向按 §7.8 识别字段写入矩阵（改判放弃-一般行）写入与置空，按 §6.6 实施第 2 步的删边变体删除未归档下游的前置边（只借用该步的删边动作，不重新发起放弃），最后归档旧任务；**项目层任务 P**——沿用已预写的替换指向建替代任务并重连（按 §7.8 识别字段写入矩阵，改判放弃-P 行不新增写入），最后归档旧任务；旧 P 已归档或仍为实施未完成态，均不再走 §6.6 的发起与实施第 1 步；两路都向前，不恢复旧任务；
     - **无替换指向**（有原因、无指向）：补齐下游删边与旧任务归档——识别按字段，不枚举来源；**指向与说明双双缺失**时，先按类型 4 记录修复补写说明（§7.8 识别字段写入矩阵的类型 4 行），再回本分支；
     - **逐窗口**（残留一律按本项向前完成，不回退、不重跑已完成的确认）：① 人确认后未写入 → 仍是“有指向 + 继任者不存在”，重走本项；② 指向按矩阵置空 / 说明改写后未删边 → “无指向 + 有原因”，走“无替换指向”；③ 删边后未归档 → 补归档；④ 继任者已建、下游未重连完 → 补齐重连；⑤ 按 §7.4 表行判处分终态（未归档下游范围同该源，归档非法组合另计类型 4）→ 组合表“已归档 + 异常”合法，处分收敛；
     - 多个未完成项按旧任务创建时间先后逐个完成；类型 1 确认“异常”后未完成的动作同样从这里接续（**P 若改为放弃，由人决定**）。
- **“正常”的写入者**：收尾逻辑与对账修复（仅类型 1）；类型 3 保持“正常”或改回“无记录”，不新增“正常”写入；类型 2、4、5 不写“正常”；
- **不保留操作日志**：收尾失败时，按上述对账规则恢复到确定状态，不重放；
- **账本不自动清理**：“正常”条目长期保留，供类型 1 / 4 的修复校验、归档终态判定与“前置是否已满足”的解析使用；清理会把这些判定变成猜；
- **持久化**：恢复写入的范围与生效按 §3，分步顺序仍由各修复入口规定；

机制自身不可用时，不在这里做降级；按 §9.4 卸载模块。

### 7.8 身份与解析

- 依赖标识是雪花 ID，写入任务记录，不随基底内部 id 或目录名变化；其首次登记与后续机制变更的提交范围按 §3“持久化”，不能作为可重建缓存丢弃；
- **返工来源**记的是依赖标识，不是基底内部 id 或目录名；
- **替换指向**记的是新任务的依赖标识；业务预写与受控恢复的时点、终值与清空**以下文识别字段写入矩阵为唯一规则源**，各动作步与镜像只许引用、不得复述终值；
- **替换指向与说明的双重用途与生命周期**：替换指向既是向前完成的补建识别标记，又是继任关系的持久身份记录（P 的角色解析沿它逐任进行，§6.5）；两个用途都不要求用后清空（终态判定见 §7.4 表行），继任者以“指向可解析到已存在任务”判定。**识别字段写入矩阵**（本表是替换指向、说明与返工来源这三个识别字段的写入与清空的唯一规则源，其他位置只许引用；写入时点由各行动作规定，写入后按 §7.4 判定）：

| 写入路径 | 写入时点 | 指向终值 | 说明 / 原因终值 | 依据 |
|---|---|---|---|---|
| 替换实施（§6.5） | 实施第 1 步（随“异常”同次持久化） | 新任务标识，保留 | 写替换 | 发起时生成 |
| 放弃-新建替代（§6.6） | 实施第 1 步（随“异常”同次持久化） | 预生成替代标识，保留 | 写放弃原因 | 发起时预生成 |
| 放弃-删边变体（§6.6） | 实施第 1 步（随“异常”同次持久化） | 空 | 写放弃原因 | 变体固有 |
| 类型 1 确认异常（P 分支，§7.7） | 确认写入“异常”的同次持久化 | 预生成新 P 标识，保留 | 写确认原因 | 随“异常”同次预写 |
| 类型 1 确认异常（一般任务，§7.7） | 同上 | 无（不写指向） | 写确认原因 | 从未有指向 |
| 类型 5 补建（§7.7） | 不新增写入（沿用已有指向） | 保留 | 保留 | 补建用指向里的标识 |
| 类型 5 改判放弃（一般任务，§7.7） | 说明改写的同次持久化（归档前） | 置空 | 改写为放弃原因 | 正常处分中的清空动作；与恢复既有合法空值分域 |
| 类型 5 改判放弃（P，§7.7） | 不新增写入（沿用预写指向） | 保留 | 保留 | 身份记录用途 |
| 类型 4 记录修复（§7.7） | 人发起，机制验证后同次提交本次恢复字段 | 恢复当前阶段仍合法的原有指向或原合法空值；**已确立的 P 继任关系不得置空** | 恢复当前仍必需的说明；异常原因不得缺失；未完成返工登记按本节恢复边界保留 | 不得借修复新建继任关系；具体恢复边界见表后段 |
| 返工来源写入（§6.4 发布、§6.5 继承） | 新建 R 的登记发布，或替换/替代 R 的继承写入，均在归档前 | — | 任务记录记返工来源 = 挂载 T 的依赖标识 | 同时继承前置；不得借修复移除或改变原有返工身份，受控恢复见表后段 |
| 返工登记准备（§6.4） | 随 T 挂起同次提交；原已挂起则不重写状态值 | 不改变替换指向 | 保留原说明，加入当前登记标记：R 的依赖标识、预定稳定基底定位、T 登记前状态 | 标记归属说明字段；同一 T 不覆盖未完成登记；不保存已完成 R 列表 |
| 返工登记发布（§6.4） | 随 R 的身份/来源/继承前置与 T 加 R 边同次提交 | 不改变替换指向 | 消费当前登记标记，保留其余说明 | 消费后不再作为未完成登记识别 |
| 返工登记取消（§6.4） | 人确认 R 尚未创建，随恢复 T 登记前状态同次提交 | 不改变替换指向 | 消费当前登记标记，保留其余说明 | R 已创建时不适用；不取消既有返工 |

  状态值不变的字段维护不触发表 4-2；伴随状态变化的准备/取消仍须校验相应转移（§4.4）。本矩阵登记写入许可，动作序列与窗口归 §6.4 / §7.7，不在这里另定义执行顺序。正常/挂起任务没有必需说明时可为空，不能把异常原因约束扩大到所有任务。

**类型 4 恢复边界（唯一源）**：由人依据现有项目记录或版本库确认原关系，机制验证该关系在当前阶段仍合法后恢复；不是任选一条旧值回滚已经完成的替换/放弃。替换指向可恢复到已确立的存在任务，也可恢复原已确认预写、但目标尚未创建的标识（再交类型 5 补建）；原本合法为空也可恢复为空。仅“目标存在”不足以建立继任关系；禁止改指无原有关系的任务、形成继任环、清空已确立的 P 继任关系，项目层已收尾也不豁免。返工来源可恢复原挂载点，不能移除/改变返工身份或凭空新增身份。说明须保留仍必需的异常原因与未完成登记意图；类型 4 不能代替登记取消。无法确认、多个候选或当前关系仍非法时阻断，不猜测，不新增证据链。

**正常写入与受控恢复分域**：未在矩阵登记的业务写入/清空不允许；异常处分终态后的业务字段写入不允许。**例外：类型 4 按上段恢复既有合法关系**，可修复已归档记录及终态记录的识别字段，不改任务/账本状态、不重开生命周期、不改已作出的人判。归档只读、归档后来源不再写入均指正常业务，受控恢复统一引用此例外。
- 解析覆盖活动区与归档区：因此归档、重命名后“返工来源”仍能对上，返工任务集合能取到已归档成员；
- **允许重命名**：重命名后由机制按标识同步所有引用；账本中的路径只作缓存。

| 记录 | 内容 | 归属 |

| **任务记录** | 任务状态、产物、前置集合、依赖标识、返工来源（仅返工任务） | 基底 + 机制 |
| **依赖账本** | 任务标识、依赖状态、说明（含当前返工登记意图）、替换指向 | 依赖机制 |
| **项目基线** | 需求基线、技术基线、任务图 | 项目文档 + 规格 |
| **会话日志** | 每次会话的过程记录 | 基底 |
| **规格** | 可复用约定，自动注入后续任务 | 基底 |

**人判不新增记录类型**：它是基底 check 后的原生人工环节，痕迹在会话日志 / 任务记录中；审计以这些原生记录 + 版本库为准。

**持久化**：本表中机制负责写入的事实按 §3 持久化；记录归属不改变提交范围。

### 8.2 写入纪律

- 覆盖式更新；历史以版本库为准；
- 机制写入的提交范围、写入归属、提交组与生效均按 §3“持久化”；
- 不设追加式对账记录、不做证据链；
- 不保留操作日志；收尾失败按 §7.7 对账；
- 禁止手改账本；替换/放弃实施后禁止回退到替换前。

### 8.3 视图

- **DAG 视图**：就绪 / 阻塞，由机制生成，人只读；
- **任务列表**：基底视图，用于查看未归档任务；
- 两者不互相替代；异常归档的任务在基底列表里显示已归档，但依赖判定只认账本。

### 8.4 接手（跨会话 / 跨 CLI）

1. 先按 §7.7 完整性分类，再读 DAG 视图，确认当前可选任务；会话的当前任务指针只作**提示**，有效与无效按 §3 判定；指针为空或残留一律以 DAG 视图与账本为准；
2. 读账本，确认前置状态、挂起项与未完成的替换/放弃及类型 1 未完成动作；
3. 读任务记录与基线，确认要做什么；
4. 若发现异常，按三段顺序处理，不直接放行（以下“T 挂起 / T 进行中”均指未归档任务）：
   - **第一段 全局旁路**：按 §9.1 第一段选择恢复入口；登记/角色完整性分类以 §7.7 为准，不另列一套优先级；
   - **第二段 挂起**（已排除第一段全局项；当前任务挂起，或已视为无当前任务且存在挂起任务；无当前任务时按创建时间取最早的挂起任务）：
     - 有未归档 R → 进入 R（R 自身未就绪时按本段以外的方式处理 R 的前置）；
     - 满足 §6.4 第 5 步条件 → 清除挂起（表 4-2 行 3），继续 T；
     - 存在返工任务记录、无未归档 R、但前置集合不全正常 → 按 §7.7 对账；异常前置按 §7.4 处置；
     - 找不到返工任务记录 → 按 §7.7 类型 2 对账修复；
   - **第三段 非挂起**：有当前任务、按 §3 有效且非挂起 → 继续当前任务，工作不停、只等收尾；指针按 §3 无效时视为无当前任务（未归档“异常”由第一段接管，“正常但未归档”按 §7.7 类型 3 处置；§9.1 两表同口径）；无当前任务时按 §9.1 第三段的两张表选择下一步；异常前置按 §7.4 处置；已归档任务的非法账本组合按类型 1 / 4 处理；
5. 若机制不可用，按 §9.4 卸载，不尝试绕过；
6. AI 的意图叙述只作补充，不作位置判定依据。

## 9. 入口、旁路与卸载

### 9.1 入口

入口分三段，逐段判定，命中即停止：第一段是全局旁路，第二段只处理挂起，第三段处理其余全部情况。挂起与“进行中”因此不再并列，表内不再出现重叠条件。

**第一段 全局旁路**（这些不是状态行，不参与后两段）：

- **模块不可用** → 按 §9.4 卸载；修复后重装；不绕过机制。
- **完整性与恢复分流** → 按 §7.7 分类前置守卫：字段/角色/登记信息非法先类型 4；有合法未完成返工登记先类型 2（本段在当前指针与 P 解析之前）；其他未完成替换/放弃或类型 1 后续处分走类型 5。存在这些项时不继续旧任务、不进行普通选择。
- **旧口径存量挂起尚未移交** → 按 §6.4 人确认后才能评估与选择；不静默清挂起。
- **需要改基线** → 回到 §5.5。

**第二段 挂起**。第一段全局项已排除后，进入条件：当前任务按 §3 判定有效且挂起；或当前任务无效（指针为空，或按 §3 视为无当前任务）而存在挂起任务——后者按任务创建时间取最早的挂起任务作为本段上下文。本段只处理“该任务等待返工”这一件事，下一列的“对应 T”即当前任务或该挂起任务：

| 当前情况 | 下一步 |
|---|---|
| 对应 T 有未归档返工任务 R | 进入 R；R 自身未就绪时按第三段处理 R 的前置 |
| 对应 T 满足 §6.4 第 5 步清除条件 | 清除挂起（表 4-2 行 3），继续 T |
| 存在返工任务记录、无未归档 R，但 T 的前置集合不全正常 | 按 §7.7 对账；异常前置按 §7.4 处置 |
| 找不到返工任务记录 | 按 §7.7 类型 2 对账修复 |

**第三段 非挂起**。项目层 P 对象及是否收尾统一按 §6.5 解析，待类型 1/4/5 的 P 输入先恢复，不因归档而提前进入已收尾表；正常但未归档的 P 保留未收尾表类型 3 专行指引；其余分两张表，行内不再出现挂起条件。

项目层未收尾（按 §6.5 的未归档 P）：

| 当前情况 | 下一步 |
|---|---|
| 有当前任务、按 §3 有效且非挂起 | 继续当前任务（含 P 自身、P 的返工任务、其他图内任务与图外任务）；进行中且前置不全正常时工作不停、收尾等前置；“只执行 P”约束的是没有当前任务时的选择，不中断已持有的当前任务 |
| 有当前任务，但按 §3 无效（未归档“异常”的指针已由第一段接管） | 视为无当前任务，看下面各行 |
| 无当前任务（含视为无当前任务）、无项目层任务 | 启动 P：立项 + 基线 + 任务图 |
| 无当前任务，P 存在且未归档，账本为“正常但未归档” | 按 §7.7 类型 3 修复后再继续 |
| 无当前任务，P 存在且未归档，前置全部正常，账本为“无记录” | 只执行 P |
| 无当前任务，P 存在且未归档，账本为“无记录”，前置含非正常且存在就绪的图内任务 | 取最早就绪的图内任务（按 §7.6，含直接返工、嵌套返工及其继任任务） |
| 无当前任务，P 存在且未归档，账本为“无记录”，前置含非正常且无就绪图内任务 | 等前置；前置为“正常但未归档”时先按类型 3 修复该前置，异常前置按 §7.4 处置 |

项目层已收尾（按 §6.5 判定）：

| 当前情况 | 下一步 |
|---|---|
| 有当前任务、按 §3 有效且非挂起 | 继续当前任务；进行中且前置不全正常时工作不停、收尾等前置 |
| 有当前任务，但按 §3 无效（未归档“异常”的指针已由第一段接管） | 视为无当前任务，看下面三行 |
| 无当前任务（含视为无当前任务），且存在就绪的图内任务（含返工任务、收尾任务） | 取 DAG 视图中最早就绪的图内任务（按创建时间） |
| 无当前任务、无就绪图内任务，且收尾完成 | 迭代期普通任务 |
| 无当前任务、无就绪图内任务，且收尾未完成 | 按 §7.7 完整性自检 / 对账；异常前置按 §7.4 处置；仍无出口则报告阻塞 |

**说明**：

- 三段互斥，命中即停止；同一情况只在其中一段出现。
- “当前任务”按 §3 判定，指针只是**提示**；指针为空或按 §3 无效时，视为无当前任务。进行中任务不因前置未满足而失效（§3 无效清单不含此情形），它继续跑、只等收尾；规划中且前置未满足在 §3 无效清单内，两表的“按 §3 无效”行与之同口径。指针无效或为空时先走第二段（有挂起任务时），再按第三段选择就绪任务。
- 第三段“最早就绪”是任务选择的唯一路由（未收尾、已收尾两表同口径）；§7.7 / §8.4 的“进入 R”只描述 T 自身的恢复路径，不构成跨任务优先级，R 与其他就绪任务同等参与排序。
- “收尾完成”只在无当前任务、无就绪图内任务时命中；有就绪的迭代任务时先选任务，避免把迭代任务重新路由回收尾。
- P 按角色解析：替换任务、放弃后的替代任务或类型 1 补建的继任任务即新的 P（§6.5、§7.7），本表与 §4.5 的项目层判定不因 P 换过 ID 而落空。
- 未收尾表中“无当前任务，P 账本为‘正常但未归档’”有专行而非删去：P 的状态决定本表的项目层判定与“只执行 P”选择，须就地引导修复；非 P 任务处于同一防御态时不设专行——按 §3 视为无当前任务后进入本表“无当前任务”各行，修复由 §7.7 启动对账标记、类型 3 人发起承载，不进日常路由。
- 图外任务按原生流程处理，不适用挂起 / 前置行；它命中“继续当前任务”（未收尾、已收尾两表同口径），或由原生流程处理。

### 9.2 旁路

**表 9-1 任务级旁路（改任务生命周期）**

| 旁路 | 用途 | 恢复 |
|---|---|---|
| 无关任务 | 插入图外工作 | 完成后回到 DAG 顺序 |
| 迭代任务 | 0→1 后的持续使用 | 普通流程，可无依赖 |
| 替换 / 放弃 | 任务被取代或不再需要 | 旧任务异常归档；下游重连或删边；实施后只向前完成 |

**表 9-2 依赖级旁路（只改账本与前置边）**

| 旁路 | 用途 | 恢复 |
|---|---|---|
| 挂起 | 返工暂停 | 按 §6.4 第 5 步评估清除；原任务回到就绪 |
| 建边 / 删边（均由人发起） | 迭代期调整顺序 | 建边两端限活动区、前置须未完工，按 §7.5 全套校验，先暂存、后置校验通过后提交；删边先暂存、重建视图后提交，目标可以已是异常、也可以在归档区 |
| 重连 | 替换 / 放弃的依赖侧动作 | 补齐下游前置边或删边；检环；不改变原任务已实施的“异常” |

**分层口径**：替换/放弃是**任务级动作**；表 9-2 只描述它的依赖侧表现（账本异常 + 下游重连/删边），不是另一套操作。任务级旁路改任务生命周期，依赖级旁路只改账本与前置边；两者是同一动作的两个侧面。

### 9.3 禁止路径

- 用基底的任务状态字段表达依赖状态；
- 图内任务走原生开工或原生收尾（卸载期间除外，§9.4）；
- 手动编辑账本或 DAG 视图；
- 跨项目建立依赖；
- 用编号顺序替代依赖边；
- 把异常状态改写成“正常”以绕过重连；
- **写入表 4-2 中不存在的账本转移**（含对挂起任务直接收尾、对已归档任务直接返工）；
- **替换/放弃实施后试图回退到替换前**（只能向前完成）；
- **机制不可用时绕过机制继续开工**（只能卸载，§9.4）；
- **卸载时留下阻断基底的文件或状态**。

### 9.4 机制不可用与卸载

机制不可用时，**不提供绕过机制继续开工的降级路径**。唯一恢复动作是卸载模块，回到原生 Trellis 使用；修复后重新安装。机制不可用时默认走**仅模块卸载**，不删除相关数据。

卸载有两种模式，由人显式选择：

| 模式 | 删除什么 | 保留什么 | 适用 |
|---|---|---|---|
| **仅模块卸载**（默认） | 工作流模块与依赖机制入口 | 任务、账本、日志、规格、基线等项目数据 | 机制故障、临时停用；重装后可复用账本 |
| **完全卸载** | 模块 + 项目数据 | 仅基底与项目代码 | 项目结束、确认不再使用依赖机制 |

两种模式都必须满足：卸载后原生 Trellis 可独立完成建任务、开工、归档；不得留下阻断原生流程的状态或文件。

**卸载健壮性**：卸载入口不得依赖机制运行时、账本或机制入口脚本；即使机制损坏，卸载也必须可执行。卸载必须恢复基底配置、移除机制 hook 与变体 pin；不得把机制状态留在基底会读取的位置。**卸载步骤必须可重复执行**：中断后重跑不产生副作用；每一步完成后基底仍可用。

- 卸载由人发起并选择模式；AI 可以协助执行，但必须显式说明模式与影响，不得代替人决定完全卸载；
- 仅模块卸载后重装：按 §7.7 对账，账本与前置集合继续有效；
- 仅模块卸载期间用原生流程归档的图内任务，重装后按 §7.7 的对账修复入口补记账本；这是设计允许的合法路径，不是异常；
- 完全卸载后：依赖历史不可恢复；重新使用需从零建图。

## 10. 演进规则

- **本文件不扩张**：不再为本文件新增章节或机制；模块层扩展以独立配套文档 + 版本化承载，且必须满足 §0.1 A6；扩展不得改写已有判定。这里的“不扩张”只约束本文件，不约束模块层的独立扩展。
- **修正需来源**：只受理内部矛盾、跑不通、与不变量冲突、与真实场景不符；不受理凭偏好的改动。
- **收口标准**：满足以下四条即视为设计层收口，收口后只按「修正需来源」受理新发现，不再做预防性结构改造——①连续两版无骨架级 / 角色级缺陷；②全部探针可满足且注释与实测一致；③每个唯一源 / 矩阵都有对应引用位清单，且修订记录与正文逐条一致；④新增闸口对引入版有执行记录。
- **类迁移义务**：修一处缺陷时，同版检查同类载体——为字段建规则时检查其余识别字段（识别条件依赖的每个字段——替换指向、说明、返工来源——都须在 §7.8 识别字段写入矩阵有行）；为修复入口登记守卫时检查其余角色不变量（如 P 的继任者不得丢失）；为写作侧加闸口时检查审查侧有无对应扫法（§0.1）。**规则新增版即首个自检版**：新规则（扫法、义务、守卫、矩阵行）不对引入它的那一版豁免，须在本版内执行一次并留执行记录，否则该规则视为未落地。只修被点到的那一处、不查同类，视为未完成。
- **净复杂度不增**：任何修正须使文档更少或更清；能用删重复、补出口、改措辞解决的，不新增机制。
- **基底版本锚定**：基底升级时，只要求“任务目录可解析、任务元数据保留”；实现方案必须用行为探针确认变体 / 任务 / 归档机制仍可用，探针失败不得声明兼容。实现方案必须记录验证区间并 pin 具体 tag/commit；beta 分支行为不作为稳定契约。
- **升级 SOP**：实现方案必须给出基底升级的标准作业程序（顺序、回滚点、探针失败时的停手条件），且探针失败不得声明兼容。设计层只要求这份 SOP 存在且被遵守，步骤由实现方案写。
- **迁移不改判定**：旧模块迁移不得自行改写本版设计判定（状态、转移、出口）；设计修订显式改变旧口径时，按本版移交义务实施，不把无从区分的存量状态自动猜判。实现迁移不额外创设判定，冲突先回设计稿。迁移路径与迁移后验证由实现方案承载。
- **机制与设计同步**：依赖机制的任何规则变化，必须同步更新本文件 §7 与配套文档；重复规则必须同版同步，不得只改一处。
- **版本可追溯**：设计稿、模块、目标项目三轴版本；目标项目记录其模块与基底版本；模块的 `implements_design` 必须等于本文件 frontmatter 版本（v42）；配套文档的 `design` 字段必须写明本文件版本（`workflow-design.md v42`）。
- **非目标**：任务调度、并行派发、优先级、跨项目依赖、资源隔离、验证证据链、替换/放弃的回退。

**本版连续场景**：同一任务完成返工后再次返工，在登记准备后、基底创建中、发布前后逐处中断并恢复；追加返工的取消须保留原挂起，已建 R 则登记后放弃；替换 P 后使继任 P 正常完成并保留合法下游边，再跨 CLI 接手；修复丢失的已预写未建继任指向、归档 R 来源，且拒绝清空已确立 P 继任关系；替换挂起任务后再处分其 R，保留归档异常任务的历史边；旧口径存量挂起先人工移交。设计审查可按字段推演，真实基底创建/定位和移交验证由实现方案承载；两种证据不得混报。

**自检**：在一个真实项目上跑通 0→1 开机 → 链式任务 → 一次返工 → 一次替换或放弃 → 一次替换/放弃中断后的向前完成（不回退）→ 一次拒绝非法状态写入（对挂起任务收尾、对已归档任务返工）→ 一次入口兜底（替换挂起任务后继续）→ 一次指针为空时的挂起路由 → 一次边变更后置校验失败（回滚、不提交、报告）→ 一次给进行中任务建边（只阻收尾、不阻继续）→ 一次被拒的归档目标建边 → 一次替换项目层任务 P 后继续（继任者承担项目层、不重新立项）→ 一次放弃项目层任务 P（新建替代）→ 一次替换**挂起中的 P** 后继续（新 P 继承 R 并进入 R）→ 一次放弃 P（新建替代）后**跨 CLI 接手**（P 解析到替代任务）→ 一次已归档无记录 P 确认异常 → 补建继任者 → 下游重连 → 一次替换中断后改判为放弃（一般任务：替换指向置空、下游删边、旧任务归档；项目层任务 P：新建替代、沿用预写指向不置空）→ 一次替换**正常完成**后重启（§7.4 判处分已到终态、不重入类型 5）→ 一次放弃-新建替代**正常完成**后重启（同上）→ 一次对前置不全正常的“正常但未归档”任务重新归档（先修复边或改回无记录）→ 收尾 → 两次迭代任务（其中一次新建依赖边）；再跑一次“仅模块卸载 → 原生 Trellis 归档一个任务 → 重新安装 → 对账修复”，以及一次“卸载中断后重跑”。以上场景都通过（另含：一次修复中途崩溃后按识别项向前完成而不回退；一次主稿内重复判定与动作序列比对，并按口径 11 的清单格式出示结果与多步动作窗口表，缺行不得声明完成），且按 §0.1 口径 10–14 做过一次验收面全量审计（人判点全枚举、P 的全部处置路径、类型 1–5 修复产出态与崩溃窗口复核、重复副本与动作序列清单比对（**每版一次全量，含同一状态位的旧副本**）、情形矩阵（**继任形态 × 归档前后 × 替换指向有/无，逐格**）、封闭断言路径核对（口径 10⑤）、识别字段 × 角色 × 修复入口交叉核对（口径 10⑥，含返工来源）、引用路径回放、残留态命中自检），才算本版可用。

|---|---|---|---|

| **迭代任务** | 图外 / 可选 | 自身产物 | 原生流程 |

## 附录 B：0→1 任务图样例

```text
P
└─→ T1 ─→ T2 ─→ T3 ─→ 收尾

返工：T2 执行中发现 T1 的接口问题
P ─→ T1 ─→ T2 ─→ T3 ─→ 收尾
        └─→ R ──↗

R 的前置集合 = T1（T2 原来的前置集合）
T2 的前置集合 = {T1, R}；T2 账本记“挂起”
R 正常归档后，T2 清除挂起，回到就绪（即使 T2 已开工），继续 T2 → T3 → 收尾
```

**归档任务不参与替换**：T1 已归档，保持“正常”，不替换、不重开；T1 的接口问题由 R 返工修复。替换只作用于未归档的任务（例如替换 T2），替换实施后新任务继承 T2 的前置集合（含 R），T2 的下游重连到新任务，T2 保持“异常”并归档，不回退。
