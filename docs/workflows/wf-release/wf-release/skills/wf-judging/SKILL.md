# wf 判断指引（十条）

**本技能的位置**：机械部分（字段、引用校验、门禁）在代码里；这里只讲**怎么判断、留什么依据、人怎么挑战**。
写 `judgments add` 前读与你相关的那几条即可——不必全读。

**统一格式**：目标 / 你要判断什么 / 留下什么依据 / 人怎么挑战 / 本项目反例。

---

## 0. 机制管什么、我管什么（先读这段，再读十条）

wf 的机制只做五类事：**不可观察的事实**（内容摘要、代次、锚点、扫描前后比对）、**不可逆动作**
（提交/推送、删除数据、外发内容、越界修改、仓库级规则文件）、**跨会话或跨进程一致性**
（绑定、写权与代次、实例游标与任务映射）、**可被伪造的声明**（人的决定只记录、不判真伪）、
**需要审计留痕的判定**（谁、何时、依据什么）。入口返回的 `tier`/`code`/`facts`/`next` 就是这些事实
与失效结论。

因此，干活时按这个分界用：

- **机制已经判过的事，不要重新论证，也不要找路绕过**：归属分类、范围核对、锚点失效、写权代次、
  实例游标、输入必填与类型 —— 这些是事实与阻断，不是"建议"。按 `facts` 修正，或按 `next` 换路；
  被阻断时不要改参数重试同一效果、不要手改记录让门禁通过。
- **机制不替你判的事，必须你判并留依据**：哪门交付够不够、这条 finding 真的修好了吗、这个缺口
  能不能接受、要不要扩面、标准变没变、旧报告还能不能沿用、计划没覆盖的缺口影响多大、哪些验收本机
  验不了、人和流程冲突时怎么办 —— 本文件 4.1–4.10 就是这十件事的口径。
- **判不了时的正确动作是交人**（`escalated`，或按 `WF_SEMANTIC_DECISION` 的出口陈述争点），
  不是编一条看起来完整的依据。机制不评你的判断质量，但要求判断**可见、可被挑战**。
- **不要用"满足格式"代替"解决问题"**：机制只校验形状（字段、枚举、引用存在性、顺序），语义对错由你负责。
  反过来，也别为了显得严谨而给机制喂它不需要的东西（自建证据文件、自述性清单）——那只会让记录膨胀。

一句话：**机制负责"事实不会错"，你负责"错的决定会被看见"，人负责取舍。**
各场景的判读口径：实例推进见 `wf-continue`，定义与准备见 `wf-start`，知识变更见 `wf-spec-update`，
审查失败后的处置见 `wf-repair-loop`。

## 4.1 交付面：哪些文件算"这次任务的交付"

- **目标**：交付面 = 我真正改的东西。多算＝把别人的工作提交了；少算＝漏审自己的交付。
- **你要判断**：逐路径归属（我改的 / 不确定 / 别人的）；"不确定"必须给理由。
- **留下**：路径清单 + 不确定项 + 理由。框架给信号（开工快照、提交 trailer、他人 WIP 声明、并发租约），**信号是输入，不是判决**。
- **人怎么挑战**：「这几条为什么算你的？如果我不认，会不会漏掉你自己的交付？」
- **本项目反例**：把 `.gitignore` 判成"其他任务的改动"，连续阻断两次 Check——框架把归属当判决。

## 4.2 blocking 的关闭：这个缺陷真的修了吗

- **目标**：关闭证据必须能**指回那个问题**，不能拿"某条宽标准通过了"搪塞。
- **你要判断**：用哪条证据、它为什么覆盖该问题。
- **留下**：可点开的引用（验证 id + 位置：文件/符号/章节）。框架只核对"引用存在、指向内容确实变了、验证确实通过、复核人不是提出者（K4b）"，**不判断是否真修好**。
- **人怎么挑战**：「这条测试/这段改动，和这个问题是怎么对上的？」
- **本项目反例**：唯一那条 blocking，evidence 里只写了"PRD a5 未变"（自由文本）。

## 4.3 影响面：这个缺口能不能"接受风险"

- **目标**：影响用户验收、安全、数据完整性的缺口，不能被一次"我接受风险"掩盖。
- **你要判断**：谁受影响、什么后果、是否可回退；建议（补计划 / 接受 / 异常归档）。
- **边界**：这里的"接受"**不能覆盖 `required` 验收项**——required 只能按 4.9 收窄口径或异常归档。
- **留下**：影响说明 + 检索范围。
- **人怎么挑战**：「这个缺口影响谁？接受之后出问题谁负责？」
- **本项目反例**：把"Windows/macOS 未验证"与"日志截断可读性"混在同一句"未核实项"里。

## 4.4 扩面：修复需要碰批准面之外的文件

- **目标**：扩面必须与已发现的问题相关；不能借"修 bug"把范围滚大。
- **你要判断**：每条新路径对应哪个问题、为什么非改不可；总量是否该回计划重批。
- **顺序**：判断需要扩面 → 提出 → **人确认 → 才修改**。先改后补授权属越界动作。
- **留下**：路径→问题映射 + 总量。
- **人怎么挑战**：「这些新文件是哪条问题逼出来的？总量是不是该回计划？」
- **本项目反例**：每轮修框架都靠扩触碰面推进，人每次只看到"这一批"。

## 4.5 标准变更：改的是"尺子"还是"判断"

- **目标**：不能用改标准来消除违反。
- **你要判断**：改的是验收标准/spec 规则本身，还是对判断的修正；受影响的未关闭项如何处理。
- **留下**：新旧差异摘要 + 受影响未关闭项清单。
- **人怎么挑战**：「这次是标准写错了，还是你在绕开它？」
- **本项目反例**：a5 被收窄又回退，当时的 blocking 正是针对它。

## 4.6 变化规模：这次改了多少

- **目标**：范围与体量的变化要被人**一次看见**。
- **你要判断**：本次变化多大、是否需要人确认。
- **留下**：变化摘要（新增/删除/移动、净增删行、扩面条目、与批准面偏离）+ 一次确认覆盖所有需要确认的量。
- **事实托底**：框架机械记录自上次确认以来的累计量，并与"本项目历史最大规模"对比，超出时高亮；**不设绝对阈值**。
- **首个任务**：项目第一个任务收工时必确认一次（建立"历史最大"锚）。确认入口：`wf sampling confirm --task <id>`。
- **人怎么挑战**：「这次一共动了多少？为什么不需要我看？」
- **本项目反例**：批准被拆成"规划批准 / 摘要重批 / 收工确认"多段。

## 4.7 报告是否还有效

- **目标**：报告必须对应当前内容与当前标准。
- **三条路**：① **沿用**（说明为什么变更不影响该结论）；② **重发**（说明为什么影响）；③ **`escalated` 交人**（你判断不了时的默认出口）。
- **判"沿用"必须点名位置**：`evidence_refs` 里要含漂移差异中的具体位置（`d:`），并说明为什么该处变化不影响结论。不引位置的"沿用"视为未判断。
- **例外**：纠错型漂移（旧验证从未成功执行）**不给"沿用"**——锚点指向被纠错 check 的报告只能重发或 escalated。
- **不逼你算**：判断不了就 `escalated`；框架只保证"带 `standard_drift` 且没有 judgment 的报告不能产出 pass"。
- **人怎么挑战**：「内容/标准变了，这份报告为什么还算数？」
- **本项目反例**：pass 后改了代码，靠临时发明一个命令才继续。

## 4.8 标准缺失：计划没写到的要求

- **目标**：计划没覆盖的真实缺口要被人看见。
- **你要判断**：检索了哪些标准、为什么认为没有覆盖、影响多大、建议补计划还是接受。
- **留下**：检索范围（标准 id 列表）+ 影响说明 + 建议。
- **人怎么挑战**：「你查了哪些标准就说没有？影响有多大？」
- **本项目反例**：多条框架缺陷没有任何验收项覆盖，以 suggestion 出现、靠人追问才落地。

## 4.9 未核实项

- **目标**：不能宣称"通过"却带着没人管的未核实项。
- **你要判断**：哪些验收项本机不可验证、影响多大、能否收窄口径、由谁在什么条件下补验。
- **收窄验收的四个依据（缺一不予接受）**：① 被收窄/去除的验收项 id；② 不可验证的客观原因（缺什么环境/测量手段）；③ 影响面与被放弃的保障；④ 补偿措施（替代验证/人工核验/下游任务跟进）。
- **硬规则**：`required` 项**不得**以"接受风险"结案——只能收窄（按上述四项）或异常归档。
- **留下**：清单 + 建议。
- **人怎么挑战**：「这条没验证就归档，出问题怎么办？」
- **本项目反例**：基线写"CPU≤5%、RSS≤100MiB、跨三平台"，本机根本验不了，最终靠人判 passed 过关。

## 4.10 与用户限制冲突时：停下报告，不自行取舍

- **目标**：用户的明确限制（"别动 `.wf/`""不要提交""先别装依赖"）与流程要求冲突时，**不能靠自作聪明绕过，也不能默默违反**。
- **你要判断**：这是"流程必须做"还是"可以换一种做法"；能否在不违反限制的前提下达成目的。
- **留下**：冲突点（哪条限制 vs 哪个流程步骤）+ 你选的做法（换路 / 停做）+ 影响。
- **人怎么挑战**：「你为什么要绕？绕了之后我能知道吗？」
- **红线**：不得为了让流程通过而**修改限制本身**，也不得**隐瞒**冲突（例如把"没做"写成"做了"）。冲突无法调和时**停下并报告**，这是合法终态，不是失败。

---

## 怎么用（最短路径）

1. 要写 judgment 时：先看它属于上面哪一条，照"留下什么依据"准备 refs；
2. 拿不准结论时：写 `outcome=escalated` + 一个**具体问题**（不要写"需要人确认"这种空话）；
3. 框架拒绝你的引用时：不要改措辞绕过去——先确认引用的 id 是否在骨架里（`wf judgments show` 会列）；
4. 人挑战后：只能新增条目并用 `supersedes` 指向旧条目，**不要改旧条目的 decision**。
