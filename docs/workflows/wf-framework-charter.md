# wf 框架基调与边界（charter）

本文件约束 wf 框架的全部设计与演进：它规定能力为何存在、边界在哪里、何时允许扩展、何时必须停止。它只声明能力边界与判断标准，不定义状态、门禁、字段、命令或脚本的具体构成；这些由 [wf 框架设计](./wf-framework-design.md) 定义。

## T1 定位与效力

**判据分工**：本文件是“要不要做、做到哪里”的判据所有者，[wf 框架设计](./wf-framework-design.md) 是“怎么做、如何验收”的判据所有者。两者不互相复制条目：设计文档引用本文件时写 `charter Tn`，本文件引用设计文档时写“设计稿 §x.y”。

**效力与遵循（唯一定义）**：设计文档与本文件冲突时以本文件为准；执行者发现冲突，按设计稿 §1.5 输出阻断三要素并交人裁决，不按本文件自行删改设计文档条款，也不按设计文档执行本文件已排除的能力。适用范围是独立框架自身的全部资产——本文件、设计稿，以及其后的机制设计、实现方案、使用文档与框架代码；这些文档在演进中受本文件约束；遵循关系由各文档在自身正文声明——设计稿的声明在设计稿 §0，机制设计、实现方案与使用文档在产出时按设计稿 §8.1 的交付要求声明。Trellis 内嵌模块的旧工作流文档族（`workflow-design.md`、`workflow-implementation.md`、`wf-variant.md` 等）不在适用范围内，这些文档内部关于“唯一权威”的声明不延伸到独立框架，其归属按设计稿 §0 另行裁决。

先例适用顺序：本文件的目标与边界先于设计文档的机制条款；设计文档的机制条款先于实现方案与使用文档的描述。上位判据未给出答案时，下位文档按设计稿 §1.5 输出需人裁决，不自行补一条新判据。

正例：设计稿 §2.2 只写边界落点、条目内容在 T3 → 允许。
反例：两份文档各写一份边界清单 → 拒绝；执行者按本文件自行删改设计稿条款 → 拒绝。

## T2 目标与非理由

**目标（唯一定义）**：只有四项，构成闭集——单人长期使用（设计稿 §1.1）、新旧项目接入（设计稿 §3）、spec 持续沉淀（设计稿 §6）、单任务执行可控（设计稿 §4）。具体能力项以设计稿 §2.1 为准，本节不另列清单。

**目标归类**：设计稿 §2.1 的纳入范围按目标归类——四阶段、任务记录与依赖、会话绑定、串行写入与跨会话接续属单任务执行可控；spec 体系与知识治理属持续沉淀（设计稿 §6；其中最终门禁属单任务执行可控）；初始化、接入与用户声明式工作流属新旧项目接入；安装、升级、卸载、受控修复与 authoring 来源登记属长期使用的支撑机制，不单独构成目标。新增能力须归入四项目标之一，或证明它是其中某一目标成立的必要条件——缺少它该目标无法成立；“有帮助”“顺手”不构成支撑，归不进去即不属本框架范围。

**非理由**：下列任一项都不构成纳入理由——上游或其他框架已有该能力、其他人需要、理论上更完备、将来可能扩展、当前实现成本低。

正例：为“单任务执行可控”补一条可机检的门禁，且复用既有记录字段 → 缺口明确、不新增机制，允许。
反例：因上游有并行任务调度而引入调度器 → 目标外，拒绝。反例：因修改顺手而新增一个入口 → 非理由，拒绝。

## T3 边界与边界外出口

**边界（唯一定义）**：不做清单、能力上限、两条长期边界与边界外需求出口以下文为全部内容；新增或删除条目按 T7 走人审。

**归类判据**：边界条目只写能力级的不做——长期不提供某类能力，且不依赖具体入口、字段或脚本即可判定。依赖具体手段的负向约束（例如不写宿主指示文件的托管块、不建常驻检测、不搬特定实现）留在设计稿对应章节，属该机制自身的约束，不构成第二份边界清单，也不得据此新增边界条目；确需升格为边界时按 T7 人审。

**不做清单（长期，不因实现进度改变）**：团队与审批组织；多机与多分支协同；并行 worktree 与自动合并；跨项目依赖；调度与子代理派发；共享工作区同时写入；实时工具拦截；常驻服务；外部 MCP 依赖；对外 marketplace 分发。

**能力上限**：用户工作流定义只表达顺序工作与显式输入/产物引用，不支持任意代码、插件、开放式 DSL、嵌套、循环、条件跳转或并发执行；格式内的落点契约见设计稿 §5.7。

### B1 多分支只由人处理

不做：分支级任务、记录、状态或批准；按分支隔离的 spec、基线与配置；自动 checkout/merge/rebase；分支命名、切换与生命周期管理；合并冲突处置；worktree 并行。

分支操作只由人执行：wf 不做任何分支状态变更（切换、创建、删除、改名、合并、rebase、worktree 管理），也不新增与分支处理相关联的功能；只读观测与禁止操作的边界见设计稿 §1.1（分支边界与只读观测），记录层面的处置见设计稿 §5.4。

分支变化属外部操作，不形成 wf 机制；提交层面的影响按设计稿 §4.2 的外部变更处置核对，记录层面的影响按设计稿 §5.4 核对。

记录随分支回退或缺失时的判定与出口见设计稿 §5.4；wf 不承诺跨分支的任务连续性。

正例：人切到其他分支处理杂务后切回原分支继续 → 记录未变，无需处置。
反例：为按分支隔离任务而在记录中增加 branch 字段 → 超出边界，拒绝。

### B2 不实现嵌套仓库与子项目

不做：submodule 递归；嵌套 `.git` 的工作树扫描；跨仓库任务、依赖与 spec 合并；子仓库级安装、升级或卸载；按子仓库划分触碰面。

嵌套仓库根是硬边界：触碰路径、spec `paths`、检查对象与升级扫描一律以本仓库工作树为界；边界判定见设计稿 §6.1，阻断口径见设计稿 §4.2。

一个项目只以一个仓库接入；多仓库协作归入“跨项目依赖”。

正例：子仓库作为外部资产存在，父仓库路径不跨越其边界 → 允许。
反例：把 vendored 子仓库路径写进 `touch_paths`，让非法条目被静默忽略 → 拒绝。

### B3 边界外需求的三种出口

边界外需求只能在三个出口中择一，不另开通道：候选、暂不采纳、直接不做。候选与暂不采纳的记录、可重议条件与复审见设计稿 §8.3；裁定为这两类的请求，由人按该表格式新增一行并填类型、依据与可重议条件，重提时从该行开始对照事实差异。直接不做用于不构成边界判断对象的请求（与 wf 无关，或已被既有条目覆盖）：它不新增记录，重提时先找覆盖它的既有条目；没有覆盖时按当时请求重新判断。裁定不是执行许可。项目内的知识拒绝是另一对象，按设计稿 §6.3 处理。

正例：需求登记为候选项并注明缺口尚未证实 → 允许。
反例：以“临时试验”为名在框架内实现被排除的能力 → 拒绝。

## T4 最小完整闭环

**闭环（唯一定义）**：“小”指职责集中、机制数量受控；“完整”指四条同时成立——正常执行、异常退出、恢复、知识回流。

**不可削减项**：失败与阻断输出、异常终态、中断恢复、检查有效性、复杂任务审查（设计稿 §6.5）、必要验证、人调用的完成门禁、知识回流（知识处置留痕，设计稿 §6.5 第 5 项）。成本不构成削减理由；已接受的审查强度不因追求轻量而降低。本条禁止删除必要控制或降低其效果，不禁止等效替换：具体步骤、入口与记录形式可在保持同一检查面、人判责任与失败出口的前提下替换或收敛，替换须有最近正反例证明效果未降；撤回承诺须经 T7.3 人审并记理由。审查步骤、审查面与人判点必须保留。复杂任务正常归档必须有对应当前对象的实际审查 pass；审查环境不具备本身不改变任务分级——任务仍属复杂时只能暂停或按设计稿 §6.5 异常归档，只有在范围、契约影响或风险确实降低、经人重新评估符合轻量判据时才可降级并留理由。不以“不可用留痕”替代审查，也不据此宣称该对象达到生产可用。

**实现件尺度**：实现件保持小型、自包含，不以机制数量或体量换取完整性；具体实现约束、落点与交付义务见设计稿 §1.1、设计稿 §8.1。

正例：把重复确认合并为一次批量确认、审查内容不变 → 允许。
反例：为减少确认次数删掉复杂任务审查 → 拒绝。

## T5 设计与演进基调

**设计与演进基调（唯一定义）**：

1. 尺度：一切判断以单人长期使用为尺度。
2. 缺口先行：新增机制须回答三问——当前哪个受支持场景无法成立、既有机制为何不能解决、新增后改变什么结果。三问缺一即不成立。“无法成立”包括在真实使用中无法长期维持：操作次数、等待或切换负担使该场景实际上被放弃；该判断只接受设计稿 §8.2 的观察记录，不接受估算。
3. 证据检验：证据须能指向真实事实；不要求先发生事故，“将来可能需要”不构成证据。可作为证据的类型沿用设计稿 §6.3 的口径；证据是否充分按第 2 条的三问判断，不另设分级。
4. 承诺限定：“已承诺”指本文件与设计文档正文的明文承诺，以及写入项目基线或 spec 的约定。普通任务的 PRD 批准、范围与实现选择只在任务内受设计稿 §4.2 保护，不因一次批准变成跨任务义务；要把某个规划决定提升为跨任务承诺，须写进上述正文或载体，否则随任务归档失效。口头提及、将来打算、上游做法不算。
5. 局部优先：优先澄清规则、修正实现、复用既有记录与入口；项目差异由基线、spec 或项目配置承载（落点分工见设计稿 §1.1）。新增状态、记录、入口或依赖，须比局部修正给出更充分的理由；不为个别项目发展另一套流程分支或通用扩展体系。
6. 成本位置：是否扩展由目标、缺口与承诺决定，成本不参与该判断；成本只用于同一目标下的实现方式、规模与顺序选择。成本低不构成纳入理由，成本高不构成删减承诺的理由。可选功能仍要维护，开关不消除其复杂度；不以代码行数、确认次数或命令次数单独判定设计优劣（观察口径见设计稿 §8.2）。
7. 判断顺序：先定承诺是否保留，再定缺口是否成立，最后才选实现方式与规模；三者冲突按此序裁决，不互相抵消。

正例：缺口成立且复用既有记录实现 → 允许。
反例：以“实现成本低、顺手就做”加入新入口 → 拒绝。反例：以“全生命周期成本高”删掉异常退出路径 → 拒绝。

## T6 减法与停止

**减法与停止（唯一定义）**：

1. 允许减法：机制失去作用、被替代或与既有契约重复时收敛或删除；不要求“新增一条必须删除一条”。替换或收敛后仍须满足 T4 的等效条件，整体移除只在控制本身失去作用或经 T7.3 人审撤回时成立。
2. 删除判断：删除前先问它会破坏什么承诺；候选不是删除许可。已被代码或 spec 覆盖的条目合并或移除，不建墓碑。
3. 修复顺序：先删过时规则，再改既有产物，再造确定性机械检查，最后才新增规则；往长期规则加一行前先找一行可删；无具体依据不凑建议。
4. 候选不囤积：长期无证据的候选项在修订时删除；候选清单是待裁决记录，不充当待办池。复审时点、证据位置与删除权限见设计稿 §8.3 的复审规则与 T7.3；该清理自首个发行版本起适用；设计阶段不做机械判定，但不排除人按 T7.3 就具体候选作出删除判断。
5. 停止条件：既定目标已满足、必要验证已完成、无范围内阻塞时结束本轮改进；没有新增事实不重复开启全面加固与审查。
6. 保留机制必答：任何保留的机制须能回答检测什么、改变什么、缺证据如何处置、删除会破坏什么承诺。
7. 不建的机制：独立依赖账本、雪花 ID、双库对账类型学、调度队列。

正例：本轮目标与验收已满足即结束；外部事实变化时只针对该对象复检 → 允许。
反例：以“再加固一遍更稳”重启全面审查 → 拒绝。

## T7 本文件变更程序

**变更程序（唯一定义）**：

1. 自约束：每条须能指出它改变的那个具体决定，并附一个反例；给不出就按第 3 条提出删除，不自行删除。只写不改变行为的正确话不收。
2. 同批完成：本文件条目、设计文档的消费位点、验收场景行、索引登记与机检覆盖在同一变更内成对出现，缺一视为未完成修订。
3. 语义变更：新增、改写或删除任何条目的全部或部分（含目标、边界、判据、停止条件与本程序）均属语义变更，须人审并在任务记录或提交说明写明缺口、影响与出口（与设计稿 §0 的修订史口径一致）；执行者不得自行增删改。
4. 资产归属：本文件与设计文档属 authoring 文档族，不进入安装清单、不投放目标项目。
5. 复审：修订后按设计稿 §0 的复审规则交未参与修订的会话复审，结论只按已覆盖轴表述。

正例：同一变更内更新本文件条目、设计稿消费位点、设计稿 §8.2 场景行与索引 → 允许。
反例：只改本文件条目而消费位点、场景行、索引未动 → 视为未完成修订；执行者按第 1 条自行删条 → 拒绝。
