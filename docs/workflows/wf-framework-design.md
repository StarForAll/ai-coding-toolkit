# wf 框架设计

wf 是一个主动调用的独立单人流程控制框架。它用项目内的文件保存任务与知识，用 skill 组织步骤，用普通本地脚本检查可机械判断的条件。它不依赖 Trellis 基底、外部 MCP、hook 或常驻服务。

## 0. 文档定位与阅读方式

本文件回答框架管理什么、任务如何推进、知识如何积累，以及异常时如何恢复；字段编码、命令参数和脚本布局由后续机制设计与实现方案承载。文中给出的入口名称与路径边界是接口约定，不表示实现已存在。

**上位判据**：[wf 框架基调与边界](./wf-framework-charter.md)（charter）定义要不要做、边界在哪里、何时停止；本文件定义怎么做与如何验收。冲突时以 charter 为准并交人裁决（charter T1）。本文件在各章只写落点与消费动作，不复述 charter 的条目；修订本文件须与 charter T7 的要求同批完成。

[workflow-design.md](./workflow-design.md) 与 [workflow-implementation.md](./workflow-implementation.md) 描述较早的 Trellis 内嵌 wf 模块；本文件描述独立框架。两者共享部分顺序语义，不能混用账本、命令或安装规则。内嵌模块的去留另行裁决，本轮不修改它。

本文件按规则的所有者组织：第 1–3 章规定定位与使用环境，第 4 章规定单任务，第 5 章规定记录与依赖，第 6 章规定 spec 与最终门禁，第 7 章规定资产生命周期，第 8 章规定交付与验收。

**维护协议**：每项判据只在一个位置定义，其余位置引用。新增或改变机制入口、判定字段、状态值、登记类、产物类，都必须在本次变更记录登记定义、写者、消费点、失败出口和正反例，并同步对应正文与索引；同步是双向回扫——既在定义条目登记新消费点，也回写被消费条目的语义列，不能只对新入口履行登记。历史修订理由写任务记录与 Git，不堆入产品规则。

配套[唯一定义索引表](./wf-framework-design.index.md)分别保留机器生成的词面候选和人工标注的语义消费点，区分“未核对”和“已核对无跨节消费”。门禁、状态、指针、记录和资产的修改必须反查两列并重验对应场景。`scripts/validate-wf-design.py` 的七项检查与覆盖率断言仍为必需（含 charter 章节、定义登记、指针悬空与迁移残留）；其消费命中率只表示已登记词面候选或指针未漏，不证明语义消费完整。新增语义项由人/修订会话对照正文确认，标“已消费”须能反向定位到正文实际动作，不能把应补的动作当作已实现的消费，也不能由同一词面生成器自证。修订后仍须交未参与修订的会话复审，未获人确认不得宣称定稿；复审须声明覆盖轴与未覆盖项并绑定被审内容的版本，结论只按已覆盖轴表述，未覆盖轴不得推出“无缺陷”。**写作规则**：禁止句须写明手段与对象，并给一个「这不算违反」的正例；术语在定义处补一句「它不是什么」，避免读者把分散陈述读成缺失、把限定手段读成全面禁止。

## 1. 定位与基础契约

### 1.1 核心原则

| 原则 | 契约 |
|---|---|
| 单人长期使用 | 项目知识持续积累，任务可暂停、接续与归档；不引入团队身份、审批组织或调度器 |
| 主动触发 | 本会话由人调用 `/wf-start` 后才按 wf 推进；未启用的会话可使用普通开发或其他流程 |
| 独立持久化 | 目标项目的任务、spec、基线与恢复材料保存在 `.wf/`，换 CLI 后读取同一份项目文件 |
| 本地完整路径 | 流程判断与 spec 操作通过文件、Git、现有本地验证和普通脚本完成；外部服务不是前置 |
| 强度如实声明 | 脚本核验结构，skill 约束执行纪律，人判断意图与结果；不宣称防对抗或保证人判真实 |

**设计与演进基调**：见 charter T5。目标与非理由见 charter T2，边界与出口见 charter T3，闭环与不可削减项见 charter T4，减法与停止条件见 charter T6。本文件不复述这些条目，只保留其落点：复杂任务审查强度按 §6.5 执行，候选增强按 §8.3 登记。

**指令分工**：skill 正文承载入口、授权、路由和必须遵守的纪律，框架步骤细节集中在目标项目 `.wf/workflows/` 的流程文档。该目录是框架资产，随 skill、脚本组成同一发行集，按 §7.2 三方升级；项目特有约定放项目基线、spec 或项目配置，用户定义的工作流按 §5.7 存放，不另造流程分支（判断依据见 charter T5）。skill 正文写作遵守两条：禁用否定式禁令句——把被禁行为拉进上下文不如正面表述应做的动作；每句通过“删掉它行为是否改变”检验，无行为改变的句子删除。允许人修改框架流程副本，但作为本地偏离受升级保护，不能以项目数据为由漏掉版本兼容核对。索引只能定位，不能替代读取被引用正文。

**实现件约束**：框架自有脚本仅用 Python 标准库，不引入第三方运行时依赖，卸载与 repair 保持单文件且不导入框架运行时（§7.3）；skill 不复制脚本可直接查询的事实；脚本不替人决定范围、架构或验收意图；项目已有构建/测试工具由项目自身管理。体量取舍尺度见 charter T4，交付核对见 §8.1。

**执行器解析（唯一定义）**：面向目标项目的安装、升级、卸载、repair 与日常入口脚本统一经解析出的 Python 执行器运行；最外层只读引导与两个独立恢复入口的启动例外按下述命令启动契约执行。解析顺序：项目配置的 `python_executable` 键 → 全局配置文件 `~/.wf/config.json` 同名键 → 系统 `python3`；全局配置是单机用户层配置，由人在本机直接维护，不进 Git、不随发行资产投放、不经 §3 项目数据通道变更，缺失等同于未设置。

两个键的取值规则：全局键只接受绝对路径（它不属于任何项目）；项目键接受绝对路径，或相对项目根且不以 `..` 越出项目根的路径。两者都不做变量展开、不接管道或 shell 片段。解析分两步、先不执行候选：①路径可解析且存在（解析符号链接后得到真实路径，再按配置值形式取路径身份）、该文件可执行、取大小与修改时间，并与本机确认记录的元组比对——全部匹配即直接使用；②未确认或元组失配时阻断日常命令，进入**人显式执行的确认动作**：该动作启动候选取 `--version`，确认是 Python 3 才写入确认记录，探测不出 Python 3 的候选按不可用处理，不以“能执行”为由采用。日常解析不自行探测版本，确认记录里的版本用于展示与核对。首次设置与每次改值都由人确认。确认对象是**实际解释器**而不是路径字符串：本机确认记录按项目标识（全局键不按项目）加键名、配置值、**路径身份**、探测到的版本与该可执行文件的轻量指纹（大小与修改时间，算法由机制设计固定）登记，并记确认时间。路径身份随配置值形式而定：绝对路径取解析后的真实路径；项目相对路径取解析后**相对项目根的位置**（解析结果落在项目外时退回真实路径）。因此项目键用相对路径时，目录整体移动不改变路径身份、确认不失效；绝对路径键在项目移动时同样不变。路径身份、大小、修改时间或版本任一变化即失配。记录按**完整元组保存为集合**，不按「项目标识 + 键名」只留一条——同一项目的不同 clone 用不同解释器时，各自的记录并存，查找按元组精确匹配，写入不得覆盖其他元组的记录。轻量指纹只作**漂移检测**：它能发现体积或修改时间变化引起的失配，不宣称证明解释器身份（§1.5）；同大小、同时间戳的替换超出普通文件检查可识别的范围，属已声明边界，不据此宣称防伪。判定按**可观测字段**：配置值、**路径身份**、版本、大小与修改时间任一变化即失配（改配置值、符号链接改指向、解释器升级都体现为这些字段变化）。路径身份按上文规则取：绝对路径取真实路径，项目相对路径取相对项目根的位置——因此项目整体移动不改变相对配置的身份，只有绝对路径配置才以真实路径变化为失配条件。确认覆盖的是**解释器二进制**而非 venv 环境——框架脚本只用标准库，venv 内已装包不影响执行，因此重建 venv 只在解析结果或文件元数据随之变化时才算变更、才触发失配。因此同一项目的多个 clone 只在各项全部相同时共享确认记录，否则各自确认；目录移动不失效，同一路径换成另一个项目（项目标识不同）时旧记录不套用，purge 后重建得到新项目标识、须重新确认，保留数据重装沿用原标识。项目键另需 Git 侧批准记录：初始化/接入首次写入时由已批准的 PRD 或基线提案逐项列出键名与配置值（也可不写该键，未设置即回落系统 `python3`）；此后改值只走 §4.2 基线通道。项目标识经 §5.5 repair 重建时，旧确认记录由该动作显式失效；证据缺失、任一项失配、值被手工改动或项目标识缺失时按 §1.5 输出需人裁决，出口是「确认为当前解释器 / 换成另一个已批准的解释器 / 回到未设置」（全局键与从未设置过的项目键可回到未设置，即回落系统 `python3`）。确认动作由人在终端执行，入口脚本写入本机记录；用户层配置只由人显式执行的入口动作或人工编辑写入，模型不写、不代填确认记录，失效记录的清理也由人执行。解析出的执行器不可用时按 §1.5 输出阻断三要素，仅阻断依赖脚本执行的门禁与入口，不得因已设置项失效而继续试用低优先级项；系统 `python3` 不存在且两级键均未设置时，输出由人把已核实可用的 Python 绝对路径配置到现有全局 `python_executable` 后重入的出口，已设置的项目键失效则按原项目配置/repair 通道修复，不新增第四档回退。卸载与 repair 入口不导入框架运行时，允许在自定义执行器失效时，以系统或人显式选择的已可用 Python 直接运行自身，保证退出与受控修复始终可达；该回退只授权这两个入口，不延伸到其他脚本。执行器选择不改变判定字段写者与标记语义（§5.3）；脚本使用的最低 Python 小版本由机制设计随语法确定并写入发行说明。authoring 侧设计期机检的环境与投放边界见 §8.1。

**命令启动（唯一定义）**：目标项目常规入口为仅用标准库的 `.wf/bin/wf.py`。在项目根完整调用为 `python3 .wf/bin/wf.py <操作>`；其他 cwd 使用该脚本绝对路径，文中 `wf <操作>` 只是短称，不要求 PATH 或 shell shim。已安装入口及独立恢复脚本按自身真实安装位置解析项目根并核对 `.wf/bin` 布局和边界，不用 cwd 选择项目；布局/目标无法确认则阻断。系统 `python3` 不可用时，人或宿主可显式给已核实可用的 Python 绝对路径启动同一脚本，它只作引导，不改变上述执行器解析。引导段只定位目标、只读解析配置及校验所选执行器，再把常规子命令交给该执行器；失败按 §1.5 输出明确配置/修复出口，不在引导解释器中继续门禁判定或业务写入。`wf repair`、`wf uninstall` 分别转交独立的 `.wf/bin/repair.py`、`.wf/bin/uninstall.py`，不先导入运行时或要求自定义配置可用；坏运行时按 §7.3 的恢复说明，用系统或人明确选择的可用 Python 直接运行相应单文件。安装前或从发行源码重取恢复入口时，使用人明确给定的目标项目绝对路径，不把源码目录/cwd 当目标，也不要求目标 `.wf/` 已存在。脚本及重取路径登记在安装清单/恢复说明；引导例外不授权常规操作绕过所选执行器。

**分支边界与只读观测（唯一定义）**：wf 不接管分支管理——不做任何分支状态变更（切换、创建、删除、改名、合并、rebase、worktree 管理），也不新增以分支为对象的记录；判定所需的观测只用不改变仓库状态的只读查询（解析当前引用、判断提交可达性、按路径查历史），结果只用于当前判定。授权范围内的暂存、提交与初始化不属本条限制，按 §4.2、§7.1 执行。分支管理只由人执行（charter T3）。

**固定流转程序化（唯一定义）**：流程语义已固定、无语义分叉的流转环节一律由入口脚本实现，不写入 skill 正文交 AI 临场决定。固定清单：状态/阶段迁移、门禁结构判定、会话绑定与实例内步骤定位、暂停写入、项目写入权获取/释放/交接、工作流定义准备/校验、实例推进与终止处置、归档移动、建边/删边校验、三方升级匹配。§8.1 的 required 步骤 enforcement 行核对照本清单执行，清单内步骤缺脚本实现按缺口处理。语义分叉点（范围语义存疑、规划语义变更、知识准入冲突等）仍按 §1.5 由人裁决或输出需人裁决档，本清单不吞并脚本核结构、人判语义的分工。

**本地 spec 契约（唯一定义）**：初始化、新增、修改、拆分、合并、改名、删除、索引与元数据维护，以及这些操作的取证、校验、加载和收尾，全程不得依赖外部 MCP。默认流程不探测 MCP，不要求安装 GitNexus/ABCoder、配置服务、准备知识图谱索引或等待远端分析。普通本地读取与匹配不是降级替代，而是完整主路径。用户自行使用的辅助工具不改变此契约，框架不为其增加必需适配层；本条不要求 AI 宿主离线。

### 1.2 最小宿主适配

**skill 投放**：安装时由人声明实际使用的 CLI 与其可读 skill 根，默认候选为 `.agents/skills/`；只投放已确认的根，不假设所有宿主都支持共享根；宿主可发现性要求 skill 主体落在上述根，`.wf/` 只承载流程文档、脚本与数据。运行期不得分平台维护多套流程。

**调用权声明**：user-invoked 入口使用宿主支持的禁止隐式调用声明；不识别时，以正文“仅人显式调用生效”约束。user-invoked skill 的 description 写成人面向的一行摘要，不写触发词；model-invoked skill 的 description 每个触发分支一个触发词且首词前置，不复制正文已承载的内容。安装自检核对 frontmatter 可解析、入口齐全；字段支持与实际发现能力须在目标宿主核实，不能以 YAML 可解析等同可用。

**会话启用**：只能由当前会话中人的显式调用确定。活动指针与持久绑定不能证明本会话已启用；绑定和项目写入权分别按 §1.3、§4.4 核验，也不充当人调用的机器证明。无宿主拦截时启用仍属纪律约定，不建常驻检测。需要人在现场裁决、批准或作答的环节，模型不得代人作答或以推断的“人会如何答”继续。

### 1.3 入口、状态与选择基础

**调用权分层（唯一定义）**：

| skill | 调用权 | 职责 |
|---|---|---|
| `wf-start` | user-invoked | 启用并检查当前会话，可保持未绑定；按人选择准备定义、创建普通任务/实例或恢复原对象，核验并取得/接收相应写权 |
| `wf-bootstrap` | user-invoked | start 启用后，存量项目首次建立项目基线与初始知识 |
| `wf-finish` | user-invoked | 人判后执行最终校验与任务归档 |
| `wf-continue` | model-invoked | 已启用会话内核验绑定和写入权，处理当前对象的推进、暂停/收工与基线/配置变更子路由 |
| `wf-spec-update` | model-invoked | 已启用会话内执行 spec 变更与处置留痕 |

user-invoked 入口不得被其他 skill 代调；需要它时提示人调用。model-invoked 入口先确认本会话已启用，再按下述会话绑定核验目标；无可恢复绑定时提示 `/wf-start` 并停止，指针损坏时从持久记录重建。绑定检查是结构检查，不构成人类调用的机器证明。原语由编排层加载，不互相派发或编排其他入口。

**任务状态（唯一定义）**：`未开工`、`执行中`、`已归档`。阶段位置另为 `Plan`、`Execute`、`Check`、`Finish`；暂停、挂起、异常终态是独立标记。阶段回退不重写任务身份，也不把执行中的任务重新解释成未开工。

**会话身份（唯一定义）**：采用经目标宿主核实、压缩后保持不变且新会话不同的稳定标识；宿主不能提供时，使用 wf 显式签发、由该会话携带的唯一会话标识。后者是路由标识而非凭据或人批准证明，复制到另一会话不构成接管许可。绑定记录同时保存首次绑定时生成的会话实例标识（非凭据、非人批准证明）；同一身份出现不同实例标识时按 §1.5 输出需人裁决，不直接按已绑定处理。能力、传递与恢复方式在机制实现时核实；无法稳定区分会话即阻断绑定与推进，给出受支持身份路径或新会话显式恢复出口，不猜环境变量、不退回项目全局指针。

**会话绑定（唯一定义）**：项目数据 `.wf/session-bindings/<session-key>.json` 保存会话身份与唯一对象的绑定事实，对象只能是一个普通任务 id 或一个 §5.7 工作流实例 id。首次绑定由人明确选择、入口脚本持久化；完成、暂停、失败或失去写入权均不解除绑定，同一会话终身不能换对象。实例正常或异常结束都保留此历史绑定；结束不继续占用写入权。压缩仍用原身份与绑定；新会话独立选择，接续既有对象须按 §4.4 释放/交接写入权。对象可有先后接续的会话，绑定本身不授予任何会话写权限。记录缺失或冲突时保留事实并走 §5.5，不将同一身份重新解释为未绑定。

**活动任务集**：全部未归档任务。**执行候选（唯一定义）**：状态为执行中且未挂起、未暂停的任务；全项目数量不得大于一，且推进时必须属于项目写入者绑定的普通任务或实例当前任务。其他已绑定会话可以查看和准备，待恢复任务须保持暂停。挂起任务可与一个执行候选共存。

**活动任务指针**：每会话在 `.wf/.runtime/sessions/<session-key>.json` 保存可丢弃的定位缓存，只能由其持久绑定及实例游标重建；可指向 Plan 中未开工、暂停/挂起或已完成对象，以便如实报告。绑定普通任务时只定位该任务；实例所属的未完任务通常只能经实例接续，§5.9 明确保留为独立执行的例外仍只绑定该任务。绑定实例时只定位其当前步骤/所属任务。指针缺失不从全局唯一候选推断绑定；候选与绑定冲突或多个候选走 §5.5。

**绑定内定位**：普通任务绑定没有跨任务切换。实例内步骤或所属任务的定位按 §5.8 顺序推进、依赖和人判条件完成；它不改变会话绑定。要执行另一普通任务或另一实例，先按 §4.4 暂停/完成并释放写入权，再在新会话中选择。暂停、挂起解除与定位更新走入口脚本，恢复须人确认并复核当前内容与前置；实例异常终止后的独立任务例外按 §5.9 留痕，不改原会话绑定。

**机制入口清单**：机制操作归属以下 skill 路由，不另构成 skill 或额外授权。start 负责只启用/只读检查、未绑定会话的准备定义、创建普通任务/实例及首次绑定，并处理所选对象的写权获取/交接接收；continue 在已有绑定内处理规划批准、开工、暂停/恢复与收工、绑定内定位、归属裁决、建边/删边、返工/替换/放弃、Check/审查结论/策展记录、已绑定任务范围内的定义编辑/校验、实例推进/暂停/正常结束/异常终止及相关写权操作。初始化任务由 continue 推进，存量接入由人调用 bootstrap；二者承担基线/配置首次建立。后续变更使用 continue 的 `wf baseline` 子操作，批准与写入按 §4.2，不供未绑定会话直接修改。spec 处置归 spec-update，人调用 finish 才能正常归档；start 和归档后的挂起复评按 §5.4。每个推进入口核对当前绑定与目标，项目写操作另核对 §4.4 所有者及代次；准备与首次创建仅在各自授权范围内例外于“已有绑定”，不例外于写权。定义查询/编辑、其他对象完成和写权释放不隐式改绑。`wf spec --file <path>` 只读正文并写本会话运行态留痕，状态/视图查询只读。人直调入口为发行安装入口、`wf upgrade --apply`、`wf repair`、`wf uninstall`；升级应用、repair 与 `wf uninstall --purge` 须交互终端确认并输入本次预览令牌，模型不代跑（预览令牌由入口在预览时生成并随本次预览输出到终端，只覆盖该次预览范围；重跑预览即失效，应用前在同一互斥内校验）。常规维护应用按 §4.4 登记具名维护写者后执行；损坏 writer 时仅 §4.4 定义的独立卸载出口可不伪造代次，仍须遵守其最小互斥和人确认条件，不以无会话身份绕过其他写权要求。命令完整形态见 §1.1；新增入口与字段依第 0 章登记，未登记的判定字段写入一律拒绝。

### 1.4 借鉴来源与取舍

取证基线、原文件与证据边界集中在稳定的[来源说明](./wf-framework-design.sources.md)。这些是固定提交的本地快照，不声明远端最新状态；正文不链接会随归档移动的活动任务目录，也不使用脱离轮次的发现编号代替规则。

- Trellis：借任务产物、阶段纪律、索引指针、结构化 Code-Spec 与按路径读取的形状；不搬 hooks、宿主身份实现、团队 workspace、平台矩阵或分发 CLI；本框架自行满足 §1.3 的会话身份契约。
- skills：借小原语、需求澄清、双轴检查与写作纪律；不把其上游贡献的“真实失败”门槛搬成项目知识的唯一准入条件。
- stop-that-shit：借当前责任、具体缺口、停止条件与最近正反例；不搬 Guard 或宣称 skill 等价于工具拦截。
- mcode-stack：借真实状态交接、上下文三分桶和人工介入成本观察；不接管缓存、压缩、后台进程或定时采集。

依赖语义来源为 workflow-design.md：依赖满足、异常终态、五条件挂起清除与前向替换/放弃；独立框架不继承其双存储账本。Trellis 的 spec-bootstrap 推荐分析工具不成为 wf 依赖，常规 update-spec 也不应被概括为必需 GitNexus。

### 1.5 强制力与输出

**强制力模型**：合法入口可保证字段取值、引用、前置、产物与内容指纹的结构核验；会话中间范围溢出、遗漏步骤靠纪律与后续检查；模型伪造测试结果、人判或批准记录不能靠普通文件可靠辨别。写入标记能发现意外直改，不是防伪签名。本框架不建立验证证据链。

**阻断协议**：输出原因码、决定性事实、下一步出口三项，任务以“名称（id）”呈现。检查失败须给失败命令、关键错误、影响与下一步，不能称基本通过。必要检查未跑不等于 pass。门禁输出取三档：通过、阻断（含上述三要素）、需人裁决（含待决事实与出口）；机器不能定夺的语义边界输出需人裁决，不在放行与阻断间二选一。阻断类输出同时写明禁止的修复动作，防止从日志重造同类事故。**原因码**由机制设计交付固定码表（码值语义一经发布不改，只能新增），输出与码表不一致按阻断处理。

**降级可见性**：凡截断、未加载、未核实、未运行或审查不可用，都输出对应对象、影响和处置方式；新降级默认可见，不因未列入某个清单而静默跳过。典型对象包括非法 glob、预算挤出的正文/提醒/汇总、spec 内容变化、Check 失效和框架资产缺失。仅经明确人判可留痕放行的情形由对应规则定义，WARN 本身不授予豁免。

## 2. 范围与依赖边界

### 2.1 纳入范围

单任务四阶段；本地 spec 的沉淀、加载和治理；多任务时的前置 DAG；用户声明式工作流及其独立实例；会话固定绑定、共享工作区串行写入与跨会话接续；安装、升级、卸载和受控恢复；authoring 仓库侧的上游来源登记。

**控制范围**是明确创建或接入 wf 的任务与 wf 自有资产。安装到仓库不表示接管仓库全部开发，也不授权改动用户文件、提交、推送或调用其他系统。

### 2.2 明确不做

**能力边界**：不做清单、能力上限、两条长期边界（多分支只由人处理、不实现嵌套仓库与子项目）与边界外需求的三种出口，定义在 charter T3（[wf 框架基调与边界](./wf-framework-charter.md)）。本章不重复这些条目，也不新增或放宽边界；边界在本文件中的落点为：共享工作区串行写入见 §4.4，工作流定义的格式能力上限见 §5.7，本地 spec 主路径见 §1.1，资产与安装范围见 §7.1。

**审查依赖边界**：复杂任务的异种 CLI 人工审查使用 `multi-cli-review` / `multi-cli-review-action` 的文件协议，契约见 §6.5。审查在复杂任务的正常完成条件中是强制的（§6.5 的完成条件与最终门禁）；本条只排除它成为 spec 文件操作与本地校验的必需工具——这两类工作不因审查不可用而停摆，无 MCP 环境下仍有正常单人完成路径。

结构借鉴使用自写文本与自建实现；vendor 副本登记来源、版本、许可并保留所需声明。不能仅凭“未复制代码”断言不存在许可义务；具体引用文件及第三方 NOTICE 在改编时核对，不将根许可证推及所有子资产。

## 3. 新建、存量与长期使用

**使用环境**：单人、本机、单一共享工作区，多会话分别绑定、串行写入；推送由人执行。源码在本仓库 authoring 层，经人推送至 §7.5 登记的私有 Forgejo 发行源后安装/升级到目标项目；仅接受 §7.2 已登记发行身份的发行引用，提交哈希只用于核验内容，不单独作为安装入口，不以本机 file 路径作发行源。skill 与流程正文中文，项目 spec 按项目语言形成。

**项目基线（唯一定义）**：需求范围、明确不做、验收口径、技术架构、外部依赖与风险/回退，加治理面和本地验证命令，保存在 `.wf/` 的活文档；任务内规划是变更提案或历史快照，不替代活基线。

**治理面登记**：基线内受特别约束的路径，初始候选包括 spec、构建配置、对外接口、记录 schema；由人审定，不因这些路径存在就自动制造额外任务。变更须在当前 PRD 明确声明。

**项目配置（唯一定义）**：目标项目 `.wf/project-config.json` 为 Git 跟踪的项目数据，保存体积/复杂度提醒阈值、调试复盘阈值、spec 核实周期、回收窗口与巡检节奏、spec 加载/输出软预算（码点）、Python 执行器路径 `python_executable`（解析顺序、路径语义、首次写入证据与确认记录见 §1.1 执行器解析）、项目标识 `project_id`（初始化/接入时生成，格式与生成算法由机制设计固定（随机生成、实际不重复、重建不复用旧值）；它表示**项目谱系身份**：随项目数据留存，Git clone 或目录复制沿用同一标识，不同项目各自独立，生成后不改，只有 §5.5 repair 经人确认可重建；不可读或缺失时按 §1.5 阻断依赖它的确认匹配，其余记录照常使用）、TDD 默认开关（缺省关闭，按任务取值覆盖）、各配置键的类型与缺省等结构化参数（`python_executable` 不带骨架缺省值，未设置即回落系统 `python3`；`project_id` 由初始化/接入生成而非骨架提供）；不存流程正文或重复的需求范围。初次由初始化/bootstrap 任务按已审基线生成，此后与基线经同一 continue 的 `wf baseline` 通道变更，只应用已批准提案中实际变化的文件，并成组校验和提交，中断按 §5.4 恢复；不为改一个阈值强制造两份内容改动。脚本检查类型/范围，周期和任务数等须为正值，码点预算须为正整数。框架升级不得覆盖它；新增配置键按记录版本提供明确兼容缺省，缺省值随发行模板的项目配置骨架提供并按 §7.2 三方升级——初始化/接入任务自举时“已声明的发行缺省”即指该骨架值；预算键、计数范围及明确数值缺省须在机制设计和同版发行骨架中给出并经夹具验证，不带占位进入可运行发行；消费见 §6.2。未知/非法项仅阻断依赖该项的判断，不能静默放宽门禁。后文“项目可配/项目阈值”均指此文件。

**初始化任务**：新项目装完后首个普通任务，产出项目基线、项目配置、治理面、目录约定、验证命令与 spec 三段索引骨架。它的开工以已批准的初始化 PRD 为范围依据，豁免“项目基线/项目配置已存在”这一自举前置，相关参数暂用发行模板项目配置骨架中已声明的缺省；不豁免人批准、Git 就绪和基本检查。骨架示例是模板，不算已核实知识。

**存量 bootstrap**：基线尚缺时，start 可按下述自举链路准备/选择实例，业务推进仅路由接入规划；由人调用 bootstrap，先清点代码、测试、已有业务文档与本地命令，再起草初始 spec、项目基线与项目配置。接入任务与初始化任务同用已批准 PRD 自举，不以尚不存在的项目基线/配置阻断自身；人审范围后落盘。从代码推断的技术事实标 `verified_at: extracted`，人的明确范围/治理决策单独记录，不假装由源码推导出产品意图。没有现成命令的项标缺失并给核验出口。全部依 §1.1 的本地 spec 契约执行。

**工作流自举链路（唯一定义）**：全新项目按顺序完成以下路径；存量项目缺基线时用 bootstrap 任务替代初始化任务，仍由人实际调用 bootstrap。

1. 按 §7.1 安装、自检并在授权内建立 Git HEAD；首次安装按 §4.4 先登记维护持有，投放完成后释放为空闲；安装记录保留其结果。未完成 Git 就绪时只准备/诊断，不开业务任务。
2. 人调用 start 启用会话后，可保持未绑定，经其准备定义子路由按 §5.7 编写定义，或只读选择已有定义。准备权限结束、工作区去向明确后，再经 start 的实例创建子路由由人确认版本和输入，创建实例并首次绑定。
3. 无基线/配置不阻断实例创建并停在规划；定义的首个任务步骤须是初始化/接入。它可先有不改交付物的人判步骤，但不能先开其他业务任务。已有独立初始化任务的项目先在其原任务中完成自举，再在新会话选择工作流，不将旧任务收养进实例。
4. 实例生成初始化任务并起草规划，人批准 PRD/复杂度后才按 §4.2 开工；暂用发行缺省，仅豁免基线/配置已存在，不豁免身份、单写入权、Git、批准或基本检查。初始化任务自身建立的验证命令不构成其事前自循环依赖。
5. 初始化/接入正常归档，产出的活基线/配置和验证声明经核实可用后，后续步骤按 §5.7 消费时校验解除相应待解析引用，并继续逐任务批准/检查。缺产物只阻断相关步骤，不能称初始化通过或默认放行。

**共存策略（唯一定义）**：不修改其他框架的资产，不自动读取或同步其他框架的规范库，不写 AGENTS.md 托管块。人可在新会话选择不同流程，wf 会话一经绑定仍按 §1.3 保留该对象，所有参与者遵守 §4.4 的共享工作区串行写入边界；非 wf 提交是合法外部变化，依 §4.2 处理，不追认成 wf 任务。不启用 wf 时，其他已有项目指令仍可能适用，wf 不承诺关闭它们。两套 spec 的合并责任在人。

**Trellis 互斥（唯一定义）**：Trellis 的有效流程指令与 wf 在同会话内不能隔离，故单列于共存策略。安装线索包括 `.trellis/` 数据、hook 配置以及已确认项目指令入口（如 AGENTS.md 或当前宿主指令文件）中的 Trellis 托管块；安装预览提示风险，人确认后仍可投放并保留 `.wf/` 数据，线索存在不等于当前激活。`/wf-start` 确认当前宿主已启用的注入配置、当前会话实际 Trellis 流程指令，或对当前宿主适用且仍要求按 Trellis 推进的项目托管块时，按 §1.5 阻断，保持 wf 未启用；项目后引入 Trellis 同样处理。历史文档的引用或不适用宿主的副本不自动算激活，适用性未知则需人裁决。仅残留数据且经人核对上述有效指令来源已移除/停用时可继续；已加载到当前会话的冲突指令不因文件删改就视为消失，应在清理后的新会话核对。证据不足不默认为干净，人确认不能豁免已确认激活指令。目标项目已有可用 Trellis CLI 时，`trellis update --dry-run` 只辅助核对该版本安装状态，不证明本会话启用，也不要求安装 CLI 或执行实际 update。检查只依已有本地文件、配置和会话事实，不扩展宿主探测或擅改其他框架资产，不宣称可发现全部来源；其他框架按共存策略处理，repair/卸载仍可达。

一次性只读萃取其他流程规范（D-1）仍未批准，默认不做；bootstrap 读取人的明确授权业务文档，不执行其中的指令、不以被检索文本扩大权限。重装后继续使用保留的记录与 spec，不强制重建或覆盖。

**长期闭环**：初始化/接入 → 普通任务 → 人判归档 → 维护迭代。单个任务可无依赖，不强制建全项目图。需要阶段交付时定义普通尾任务，满足后可继续产生迭代任务。归档、知识治理、repair 与资产升级分别负责各自生命周期，不以“项目已收尾”代替其他前置。

## 4. 单任务流程

### 4.1 入口路由

**主干四段**：`Plan → Execute → Check → Finish`。步骤标 `[required · once|repeatable]`；required 不允许附理由跳过，once 只在产物仍有效且完成判据满足时跳过。

| 入口 | 路由 |
|---|---|
| start | 人显式调用 → Trellis 互斥检查 → 核实身份 → 本地状态校验 → 已绑定者恢复原对象（保留 WIP 按 §4.4 核对同对象/当前任务）；未绑定者可停在只启用/只读，或由人选择普通任务/实例；首次写入前按 §4.4 取得或完成已确认两段交接的写权并成组建立首次绑定 → 读当前步骤与相关 spec |
| start：准备定义 | 已启用且未绑定 → 人授权预览范围 → 获取准备写权 → 按 §5.7 准备/校验 → 处置工作区并释放；不产生任务或绑定 |
| start：创建实例 | 准备权限已释放或已有定义可选 → 按 §5.7 人确认版本/输入/展开规则 → 核验写权和首次绑定条件 → 固定快照、创建实例并绑定；仅产生规划权限 |
| continue | 确认已启用及绑定一致 → 读当前任务/实例及步骤正文 → 核对写权、阶段与门禁 → 推进当前对象；人要求暂停/收工时转 §4.4 日常收工，不代调 finish |
| continue：基线/配置 | 当前初始化任务按第 3 章建立骨架；后续变更经 `wf baseline` 按 §4.2 应用已审提案 → 检查新状态，不绕过当前任务批准 |
| bootstrap | 本地清点 → 人审范围 → 建立基线与知识 → 检查产物；作为接入任务保留记录 |
| finish | 人调用 → 核对绑定与写入权 → 知识处置确认 → 最终门禁 → 授权范围内提交与归档 → 更新实例步骤/交接；变更失效则回 Check |

bootstrap 与 finish 同样先确认本会话已调用 start；未启用时只提示人调用，不代调。暂停中的当前任务只提示人恢复，挂起中的当前任务按 §5.4 给返工出口，未开工任务只推进 Plan；有效指针不授权跳过这些状态约束。工作流实例按 §5.8 定位所属任务，不能将其他实例/任务的步骤、批准、产物或失败状态加载成当前指令；绑定对象已正常/异常结束时只报告结果，不在本会话选另一个。

**路由输出**至少含当前位置、下一步、门禁结论、出口；正常简短输出可合并为一句，阻断三要素不可省。复杂任务 Check pass 后输出异种 reviewer 调用命令，是否发起及不可用声明由人决定。

常规人工介入为 Plan 末的规划/分级一起确认、复杂任务审查发起与决策、finish 人判；只有范围变化、歧义归属、异常或人直调操作才增加确认。已有授权在同一范围内持续有效，不能每步重复请求。

### 4.2 规划、归属与检查有效性

**规划产物**：PRD 写目标、范围、触碰面、验收与不做项；复杂任务另有 design 与 implement，分别写方案取舍和执行/验证顺序。触碰面按下述机读规则表达，文档任务也列出预期交付与知识路径；不为满足格式猜造完整文件名单。未决的人所有决策先澄清；能从本地项目查到的事实先调查。

**机读触碰面（唯一定义）**：PRD 的 `touch_paths` 为仓库相对 glob 列表，覆盖任务允许改动的业务、文档、spec、基线/配置等交付路径，复用 §6.1 的安全路径语法；此处任一非法条目即阻断批准/开工，不按 spec 路由的“单条失效”放宽授权。人批准后由开工命令保存版本对应的列表，不自动从实际 diff 扩大。纯调查可显式为空；任务自身规划、控制记录、审查报告及运行态由固定职责授权，不强塞入交付 glob；§6.3 的改名同步与其他活动任务策展引用的依赖解除写入同属固定职责授权，且只限引用路径、哈希与解除标记。除上述两类外，不因此获得修改其他任务内容或扩大触碰面的权限。其他框架资产和项目禁止项仍受原边界约束，glob 命中不授予额外权限。路径非法条件与仓库边界沿用 §6.1；此处任一非法条目（含落在嵌套仓库根之下的条目）即阻断批准/开工，不静默跳过、不读取其内容（不做嵌套仓库属 charter T3 的边界）。

**规划批准（唯一定义）**：实例创建/展开授权只许可形成任务规划，不包含任何任务的开工批准。人明确批准当前规划与复杂度后，入口脚本记录批准范围、规划快照及对应版本。建任务许可不含开工许可。范围、契约、风险、验收或方案取舍实质改变须回 Plan 重新批准；只修排版、进度勾选或不改语义的说明时，可记录理由并衔接快照，不重复问人。语义是否改变属于人/模型纪律判断，脚本仅核对快照与留痕；不能把“文件存在”当批准。规划批准只对当前任务与当前版本有效；需要跨任务长期生效的决定，写入项目基线、spec 或本文件正文（承诺范围见 charter T5），不靠 PRD 的一次批准传递。

**开工门禁（唯一定义）**：规划产物存在且必填项非模板占位（模板占位指发行模板给出的未填字段标记集，标记集随发行模板按 §7.2 三方升级，脚本按该集判定）、规划批准与当前版本对应、机读触碰面合法且已批准、状态/阶段合法、无未决范围问题、前置满足、无挂起/暂停、项目基线与项目配置可用（初始化/接入任务例外见第 3 章）、Git 有 HEAD、工作区边界已确认，当前会话绑定匹配且持有 §4.4 项目写入权。仅首次从未开工进入 Execute 时登记当前 HEAD 为任务基线提交，并保存批准的触碰面快照；执行中任务回 Plan 后再入 Execute 保留首次基线，按当前有效批准核对并保存新的触碰面快照。首次基线缺失或不可达走 §5.4 的记录锚点核对，不用当前 HEAD 静默覆盖。任务归属仍按本节标记/裁决判断，不能把首次基线之后全部提交追认为本任务；不得先改业务代码后补开工。

**工作区边界**：开工、实例内转入另一任务、获取/释放/交接写权前，逐路径核对业务和其他任务的改动；换对象、实例下一任务及普通升级仍要求这些改动已获授权提交或由人完成实际处置。“由人处理完毕”须有具体去向和当前状态可核验，不能只写一句同意就把脏工作区当干净。当前任务已声明的 `.wf/` 规划/控制记录、当前实例/绑定/写权记录、本次依赖动作有标记的关联控制记录，以及由 §4.4 的维护变更持久化规则按 §5.3 登记、路径和当前状态可核对的 upgrade/repair 变更，可作为彼此分开的待提交组；逐路径核写者/归属，不豁免整个 `.wf/`。`.wf/writer.json` 是共享控制记录：公共写权字段（状态、写者类别与标识、代次、检查点）不属维护组，任何写者在自己的写权事务中更新它们并原样保留维护回执字段；回执字段属维护组。该文件整体提交须有明确覆盖维护组的授权；未结回执期间公共字段差异按待提交控制记录保留，不因此阻断推进或开工门禁——门禁核记录内容而非提交状态，也不把整文件算作维护组路径。维护组不能被其他任务重分类、暂存或提交；其他任务仅可处理不与该组路径重叠的范围，拟触及同一路径或发现状态与登记不符时先交人处置，复用 §5.6 的提交、已完成反向修正或具名任务承接出口；由入口把人确认的去向和实际路径状态写回原维护结果，未落实时仍保持待处理。维护组的提交/实际处置按 §4.4、§5.3 及各操作入口规则完成。运行态因 gitignore 不参与。收工保留当前对象 WIP 的唯一狭义例外见 §4.4：只允许该对象释放和恢复，不允许其他任务或升级套用。“写权空闲”不表示“工作区干净”。外来、无归属、跨任务混杂或冲突未决的未提交改动不纳入例外，先报告并交人处理；不自动 stash、丢弃、捎带或提交。

**任务归属（唯一定义）**：本任务提交通过 `wf-task: <任务id>` trailer 标识，遗漏时人可经归属裁决补记。一个提交至多归属一个任务，不接受互相冲突的 trailer 与裁决；裁决仅指向未归档任务。框架自己的控制记录提交按实际资产路径识别，不要求伪挂业务任务。

**触碰路径（唯一定义）** = 本任务标记提交的路径 ∪ 归属裁决提交的路径 ∪ 替换继承路径 ∪ 当前明确归属本任务的未提交路径（未提交路径的归属以命中已批准的 `touch_paths` 为准；命中但语义存疑按 §1.5 需人裁决）。删文件、改名旧路径与新路径都计入。任务基线提交只供差异与接续参考，不能把基线至今所有提交都自动算给本任务。

**外部变更处置（唯一定义）**：没有 wf 标记或裁决的提交不自动判违规，也不自动算入任务。恢复/Check 时从任务基线到当前 HEAD 的提交中，列出触及本任务触碰路径或已声明范围的未归属提交供核对：确属本任务的遗漏则裁决归属；属于其他流程则保留外部属性，检查内容影响；无交集者不阻断任务。若外部变化影响范围或验收，回 Plan；影响既有检查则按内容指纹重检。不能机械区分“漏标”与“外部工作”是已声明边界，不做全仓历史合规追认。

**内容指纹（唯一定义）**：一律取检查对象在工作树的实际状态：存在时取文件内容，缺失时记删除。HEAD 和暂存区只供识别差异、归属及待提交事实，不作替代内容源；每项包括路径、存在/删除、文件类型、可执行位及内容或符号链接目标的哈希。检查对象为触碰路径中的交付文件、变更 spec/基线/项目配置，以及本任务使用的相关 spec/基线与有效项目配置。仅任务规划/进度、控制字段、实例游标/执行结果、会话绑定、写入权、审查报告与运行态不属于交付指纹；用户工作流定义及固定快照若影响当前执行条件，属于本任务使用的规则输入，同样核对版本/哈希。该排除不能涵盖 spec、基线、配置或产品交付物。

**检查有效性（唯一定义）**：Check pass 必须对应同一触碰路径集合、内容指纹、相关规范/配置版本、批准触碰面与验收口径。任何来源的同路径修改/删除/改名都可能使旧结果失效；来源是其他任务不能豁免。无关路径改变不自动失效，但涉及依赖/环境等已知验收影响仍须补查。框架发行集改变后先核对尚未归档任务使用的规则兼容性，规则变化影响门禁/检查项时重跑对应步骤；不能沿用旧版 pass 声称满足新版要求。指纹只能证明已列对象未变，不能证明测试完整或所有间接影响不存在。

Check 先确认归属与范围，逐路径比对实际交付改动与已批准机读触碰面，删除/改名两端、继承路径同样参与；全部在范围内才执行检查，结束时确认对象未变，由脚本写 pass/fail、逐项命令/摘要和内容指纹。必要命令失败、未跑或未结束不能 pass；不适用项须给理由，不能用无关命令补位。检查中的任何修复后重跑相关项，旧结果不得挪用。

**范围闸门**：任务 PRD 的意图与机读触碰面、项目基线与治理面共同限界。准备编辑时发现需要范围外路径，或 continue/Check/Finish 检出已发生的越界，均阻断继续执行，回 Plan 扩范围或确认必要变更；glob 命中但范围语义存疑时按 §1.5 输出需人裁决，不在放行与阻断间二选一。不自动修改 glob、不以命中宽目录证明语义合规。已发生的改动保留供人判，不擅自回滚。无 hook 只能在这些步骤与入口检查，不能实时阻止直接编辑。

项目基线与项目配置的后续变更经 continue 路由的 `wf baseline` 子操作：在声明相应路径且已批准的任务中，人审当前提案，入口核对绑定、写权及提案版本后成组应用活文件并检查新状态，再走该任务的 Check/归档；不得直接手改其判定性内容。首次建立由初始化任务或 bootstrap 按第 3 章自举；更新现存基线时按已批准提案核对，不让“旧基线尚不允许新状态”阻断已审变更本身。

**提交顺序**：框架仅在用户已授权时提交，按具体路径暂存；业务/spec/基线/配置变更与任务记录归属明确后提交，随后核对最终门禁，归档记录最后单独成组。无提交许可则停在已检查待人处理，不自行归档或推送。提交仅改变 Git 表示而内容与路径集合不变时可保留 Check；提交过程改变内容则失效。归档提交中断按 §5.4 的恢复规则处理。

### 4.3 按需纪律与任务体积

**复杂度分级**：Plan 末人批准轻量/复杂；轻量 PRD-only，复杂三件套。分级按事实核对、不按任务名或代码量，四项任一为是即按复杂：①触碰路径命中治理面；②改变对外契约、状态门禁、判定字段或记录 schema；③相对项目基线与已批准的 Plan，验收口径、回退方案或审查面发生变化（新任务首次定义自己的验收不算变化）；④范围在 Plan 后明显扩张。文件数 ≥3 或单文件净增删 ≥80 行只作提醒评估的信号，不单独代替判断。正例：改一条内部实现并补齐既有测试、未触碰治理面 → 轻量；新增一个只碰业务代码的普通功能、验收项由本任务自行定义且不改基线口径 → 轻量。反例：只改两个文件，但改动 `touch_paths` 语义或门禁判定 → 复杂。分不清时按复杂处理并记录理由（审级宁高不低），Check 再按事实复核。审查环境暂缺不影响分级：按事实定为复杂即按复杂要求推进，完成条件按 §6.5。若实质超出已批准规划仍须先回 Plan，不能只补事后三件套掩盖越界。降级由人留理由，且只在任务本身确实变轻时成立——缩范围、拆分或重新评估后符合轻量判据；审查环境不可用本身不构成降级理由，也不得据此把仍触碰治理面或改变外部契约的任务改判轻量。降级须在 Check 前决定并按轻量任务的产物与检查要求执行；若在 Check 后才发现审查不可用，只有缩范围并重新执行对应检查后才按轻量完成。已有产物保留、不回填也不删除；任务仍属复杂时只能暂停或按 §5.6 异常归档。

**体积判据**：默认 ≥8 个文件、累计净增删 ≥400 行或整文件重写时停下评估拆分；默认低于 10 行且不能独立验证时优先合并相邻工作。阈值可项目化，只触发判断。按可独立验证的垂直行为切片，宽范围迁移采用扩展兼容形式→分批迁移→删除旧形式，不按前后端层次硬切。

| 原语 | 触发 | 完成信号 |
|---|---|---|
| grilling | 复杂任务或需求有未决歧义 | 人所有决策已澄清，事实已调查，规划可批准。每个待决问题编号并附推荐答案，措辞使“是”即接受推荐项；可逆细节由模型自决并在结果中列出，人在一轮内批量作答；模型不得代人作答人判侧 |
| TDD | 本任务开关为开启 | 针对真实行为的红→绿反馈；完成信号按可检验属性组表述（可红、确定性、快速、可无人执行）且已实际运行过一次；不把文档任务强制改造成代码测试 |
| 调试循环 | 同一问题重复失败 | 建反馈、最小化、假设与定向探测、回归；无法复现如实报告 |
| code-review | Check 内 | 同会话顺序检查标准轴与需求轴，分别给结论，不以一轴掩盖另一轴 |

**TDD 开关归属**：项目配置给出默认（缺省关闭），任务记录保存本任务取值与理由；Plan 末与复杂度一并由人确认并写入批准记录。未设置按项目默认，项目无键按关闭；模型不因任务类型自行开启，也不设隐式全局默认。开关只决定是否要求红→绿证据，TDD 的完成信号仍按上表。

**段内回退**：本任务缺陷回 Execute；方案/范围有误回 Plan；未归档上游缺陷或两轮审查整改按 §5.6 建返工。机械修复在范围内直接做，设计取舍或无法判定者交人判断。

**反例纪律**：新门禁与原语纪律须有最近正反例，只改变一个决定性事实就应翻转允许/拒绝结论。行为新增或缺陷修复适用红→绿；纯文档、调查等任务用独立可观察产物验证，不要求人为造一个必失败的代码命令。

### 4.4 接续、暂停与复盘

**项目写入权（唯一定义）**：共享工作区同一时刻只有一个写者。持久项目记录 `.wf/writer.json` 保存空闲/持有/待恢复、写者类别（会话/维护）与所有者标识、递增代次和最后核实检查点；会话写者另带绑定对象或授权准备范围，维护写者另带本次操作类型/预览范围与维护操作标识。维护标识可由操作和代次派生，具体编码交机制设计，不伪造会话、不建立任务或 session-bindings。获取、释放、交接与维护应用都在同一原子互斥内完成：先核验旧值，再更新。互斥是运行态设施，只协调操作、不作所有权事实源；锁对象固定为项目根的 `.wf-lock`（位于 `.wf/` 之外，纳入 §7.1 的 `.gitignore` 托管段，不提供改名的替代落点），`.wf/writer.json` 记录所有权事实、不是锁本身。锁文件带固定标记并在创建时写入，已存在且带标记的文件直接复用、不改写内容，内容不可识别即不视为锁对象；锁对象在框架生命周期内只创建、不删除：删除锁路径会让已持有旧文件的等待者与新进程各自锁住不同的文件对象，等于出现两把锁；因此卸载与 purge 都不删除锁文件，`.wf/` 数据删除后它连同标记作为运行态文件保留，由卸载预览报告存在，人在确认无 wf 进程后可手工清理（属人工清理，不是卸载步骤；锁文件被外部删除时按缺锁处理，不当作空闲）。互斥只用 Python 标准库实现，支持的系统范围与退化行为由机制设计声明；未声明支持的系统按不支持处理，不退回无锁运行。等锁有界：等待超时输出持锁者标识与检查点后退出，不抢写、不改记录；持锁者异常退出（进程消失但记录未释放）时，按「持锁标记 + 存活探测 + 人工确认」在同一互斥内恢复，超时或进程消失都不直接当空闲。缺锁不等于空闲——`.wf/writer.json` 显示持有或待恢复时，即使锁对象不存在也按占用处理。所有项目写入核对相应写者标识、类别、范围及代次，入口/步骤检查点重验；旧代次失效后停止写。未持有者只读或在项目树外准备，不推进项目状态；本会话临时读取留痕不推进项目状态，且按会话隔离、不属项目写入权的控制对象：无写权会话可写本会话侧车，不得写其他会话侧车或任何判定字段；侧车写失败按 §6.2 只降级可见，不阻断读取。

空闲时，会话的人选目标与首次绑定可随写权获取一并校验/落盘，跨记录写入按 §5.4；获取仍须先核 §4.2 工作区边界及本节保留 WIP 的对象限制。已有会话或维护写者时报告标识、对象/操作、范围及检查点，其他会话等待或走已确认交接/恢复出口，不建队列。准备定义权限只给已启用且未绑定会话，完成/取消后处置工作区并释放，不冒充任务绑定。正常释放要求对象已暂停/合法终态（准备完成/取消）、真实交接已写、工作区满足边界或下述同对象 WIP 例外；释放只更新写权，不解除历史绑定。实例当前任务的常规推进仍须核任务门禁，存在保留 WIP 时不能转入下一任务。

**写权交接（唯一定义）**：显式交接分两段，均使用本节同一互斥和持久记录。旧会话由 continue（准备者用 start 准备子路由）按人已确认的接收会话/同一对象保存进度、暂停和工作区/WIP 处置，核对后使旧代次失效并写待恢复及接收范围；接收会话的 start 验证自身绑定或合法首次绑定条件、接收者/对象/范围和真实工作区，再授予新代次；准备范围交接只核准备授权，不凭准备范围建立任务/实例绑定。中间态不是空闲，双方均不做业务写入；中断按 §5.4 检查点补齐，不重复索取同范围有效批准。接收者已绑不同对象即拒绝，旧会话不改绑。正常释放为空闲后再由新会话选择是另一条路径，不混称显式交接。

**维护写者（唯一定义）**：人直调安装、升级、repair、卸载先按各自契约预览/确认，再在本节互斥内重核预览事实、旧所有者及工作区边界，登记本次维护持有和新代次，才开始应用；预览后状态变更不得带旧许可径直写入。维护期间其他会话按已有所有者处理；维护步骤核验本次标识/范围/代次，不以维护身份推进业务任务。普通维护先核无人正在执行，已有会话须按其暂停/释放或受控恢复路径停止；不能以获得维护标识代替人确认旧写者已停。upgrade/repair 的结果持久化与释放按下述唯一规则执行；其他维护按各自 §7.x 条款处理。操作中断且结果不完整或不明时保持待恢复，不先按成功结果释放；按 §5.4、§5.5 核对已落盘步骤，恢复至可确认的完整结果后再执行对应出口，不因 PID 消失/超时当空闲。独立卸载的损坏 writer 例外只按 §7.3 执行：不登记伪代次，但必须同一最小互斥、人确认及限制在预览退出范围内；它不豁免卸载之外的维护写入条件。首次安装确认无既有 wf 数据后，在同一最小协调范围先建立初始维护持有，再投放并释放为空闲；这只豁免初始化协调记录前置，不授权业务写入或省略安装确认。首装协调记录与后续写权记录同址：安装入口在目标项目创建 `.wf/` 与 `.wf/writer.json` 作为首次写入并列入预览清单；`.wf/` 不存在时不在项目树外另建协调文件。

**维护变更持久化（唯一定义）**：适用于 §7.2 upgrade 与 §5.5 repair 产生的 Git 跟踪资产/控制记录变更。完整应用并核验后，按 §5.3 在现有 `.wf/writer.json` 维护结果字段记录操作标识、精确变更路径、操作前后状态/哈希（粒度按 §4.2 内容指纹）、暂存区/HEAD 差异和结果；该回执路径本身不纳入自身哈希，直接核对其 Git 状态，不另建账本。Git 提交授权必须单独明确覆盖本次提交及其精确路径；upgrade/repair 预览令牌只批准维护变更，不构成提交授权。获得提交授权后只持久化预览及结果清单中的对应路径。无提交授权时不提交，保存待持久化路径和状态、报告后释放维护所有权；提交尝试失败但结果可核实时转为待持久化并报告后释放，结果不明则保持待恢复。应用/验证中断且结果不完整或无法核实时保持待恢复，不能直接释放为空闲；按 §5.4、§5.5 恢复至可确认的完整结果后再决定持久化或释放。已记录的维护组可与不重叠任务并存，但其他任务不得重分类、暂存或提交；拟触及同一路径或发现状态与记录不符时交人处理。启动依 §5.4 核对实际状态：登记的最终状态已在 HEAD 且工作树/暂存区无额外差异时视为已持久化，无须改写回执；否则保留为独立待处理组；经人按 §5.6 明确提交、已完成反向修正或具名任务承接，并由入口将去向/归属及真实路径状态写回原维护结果后，才解除待处理。状态与记录不符则交人裁决。

未知旧写者是否仍活动、记录损坏/缺失或交接/维护结果不明时，阻断相关写入；核对 Git、原始记录、绑定、任务/实例及已落盘步骤后，由人按 §5.5 预览确认旧写者停止、恢复已能核实的事实并续增代次，不删锁/缓存抢占。原文不可解析时保留原文；代次/范围无法核实时不伪造可继续记录。独立卸载的损坏退出按 §7.3 保留，不要求先解析任务/spec。所有操作仅约束合法入口和纪律，无实时拦截时不能阻止直接工具写入；下个检查点发现外来改动即保留并交人处理，不宣称防对抗。

**交接记录**：普通任务的持久内容中保存目标/验收、当前有效批准范围、已做决策及理由、状态/卡点/下一步、未决事项、Ruled out、验证命令/结果与证据位置，以及本节收工保留 WIP 的人选择、逐路径状态和待处置项；工作流实例另保存 §5.7 的固定定义、输入、步骤及关联任务引用，任务批准仍查任务记录。先查本地 Git、产物与真实验证结果再写，不凭会话记忆；不可核实就标明。释放/交接写入权前及关键步骤结束时更新。start 从这些项目记录恢复并先复述目标、批准范围、当前位置与下一步，不要求用户重述已落盘事实。

**上下文处置**：可重取的旧工具输出丢弃，会话过程概括，不能丢的决策与进度写盘。压缩后按 §1.3 保留同一绑定，复读项目记录、核对写入权代次及 Git/文件真实状态；新会话经显式选择和上述交接路径接续，既有同范围有效批准可复用，不能仅因换会话反复索要。指针/聊天丢失不丢任务与工作流进度；结果不明先核对 §5.4 已落盘事实，不盲目重做。共享路径、spec/基线/配置或验收相关状态变化按 §4.2 检查有效性使受影响结果失效。多次压缩仍重问/重做或丢约束时，先保存交接并释放写入权，再换新会话。不要求特定宿主支持自动压缩、记忆或后台结果。

**任务暂停**是人的休息决定，挂起是等待返工；两标记可并存，清挂起不清暂停。暂停任务不参与就绪选择；恢复按 §1.3 的执行候选与 §4.2 的工作区边界处理，并取得本节写入权。暂停/恢复与写入权释放/交接不改变会话绑定；实例暂停须保存当前任务的暂停或等待原因及当前步骤，不能只移动游标绕过任务门禁。

**日常收工（唯一定义）**：人要求暂时结束工作时，已绑定者由 continue 停止业务推进，未绑定准备者由 start 准备子路由完成/取消本次准备；两者预览逐路径归属、工作树/暂存区状态、待验证项与风险。人可选择已授权提交、保留未提交 WIP、在既有许可内反向修正，或具名对象承接；选择不等于已落实，反向修正/承接未完成则保留待决，模型不因收工自动提交、stash、丢弃、反向改动或新建承接任务。

保留后释放仅适用于当前任务批准范围内且归属明确的 WIP，或当前授权准备范围的定义草稿；入口在现有任务/准备交接材料中记录人选择、具体对象/任务或准备范围、具体路径、存在/删除、类型/内容哈希等可核对状态摘要、暂存事实、未验证风险及待处置项，写合法暂停/准备进度后释放。实例绑定须记录具体当前任务/步骤，不能凭同一实例推进下一任务。它不复制 WIP 到新存储、不含秘密正文、不构成 Check pass 或备份；保留内容仍占共享工作区，其他对象和普通升级按 §4.2 先处理 WIP。

同一对象恢复或显式交接接收前，逐路径核对真实 WIP、归属和原记录；状态未变且批准有效可按原许可继续，有变化重核范围/归属/检查。Check pass 的有效性一律按 §4.2 判定；本节只要求核实真实 WIP 与归属，不自动还原快照或改变旧 pass 的状态。WIP 已提交或已由人实际处置后，原入口核对真实路径/归属并更新原交接中的待处置结论；只有实际边界满足才解除换对象/升级限制，不因保留说明被手删或过时而放行。外来/无归属/跨任务混杂/冲突未决改动不走保留例外；未满足处置或记录条件不称释放成功。独立 repair/uninstall 在各自明确预览确认范围内保护既有 WIP，不能借维护覆盖/删除或称业务已验收。收工仅保存进度、暂停和释放，保留绑定/未决事项，不代 finish/归档。直接关闭终端/CLI、崩溃或未完成这些动作不算释放；原会话恢复核身份/代次，新会话按 §5.5 确认旧写者停止、核对 Git/产物/WIP 去向后恢复，不按超时抢占、不补称关闭前已交接。

**历史回退**：默认在授权范围内用新提交反向修正，保留引用。直接 reset 只在用户明确授权且不移除任何任务/资产记录所引用的提交、也不改写任务归属历史时允许；未知按不允许处理。引用被破坏走 repair，不自动猜新锚点。

**复盘**：返工、审查 fail 或同一问题重复调试达到项目阈值时，在归档前回看真实轨迹；其余任务可选。关注未验证假设、错误工具、绕路重试、漏信号和压缩丢约束。每条引用本任务事实；纯判断性结论才沉淀为 spec，能机械化的写成检查不写散文。修复顺序、删除判断与“无依据不凑建议”见 charter T6。

## 5. 任务记录、顺序与恢复

### 5.1 依赖与项目完成

**前置集合**是任务间顺序的唯一事实源，就绪/阻塞视图由此派生，必须无自环且是 DAG。

**依赖满足（唯一定义）**：前置任务已归档且终态正常。异常归档本身不满足，须重连继任者或删除多余边。

**归档终态（唯一定义）**：只取正常/异常；正常要求实施/检查、人判与最终门禁通过，且前置全部满足、无未决暂停/挂起。异常用于替换/放弃，不冒充完成。归档后无常规写入路径，只有人确认 repair 可修记录；产物缺陷由新维护任务承载。

**项目判定**：阶段尾任务正常归档表示该阶段收尾，不要求活动任务集为空；维护任务只要求缺陷原任务已归档，不要求整个项目收尾；升级与卸载前置分别见第 7 章。首尾角色是人的约定，不建立角色继任解析器。

仍需阶段交付而没有尾任务时，由人新建普通任务承担；已有尾任务被替换时继任者承接职责，放弃时按 §5.6 明确保留交付目标并承接，或由人明确撤回该目标；单纯删边不能表示阶段完成。日常独立维护不因“没有尾任务”永久阻断。

### 5.2 单一事实源与减法

每任务只有一份结构化任务记录，保存生命周期、前置、批准、检查、处置及可选所属实例 id；§5.7 的实例只保存编排事实和任务引用，§1.3 的绑定只保存会话归属，§4.4 的写权只保存所有权类事实（写者类别/所有者标识/范围/代次/检查点）与维护变更持久化的回执及待处理状态，各自不复制任务状态/批准；实例终止后的保留许可写在任务记录，原所属实例只作历史来源。PRD/design/implement 是内容产物，不另存第二套状态。视图、摘要、指针和索引不得成为与任务记录竞争的事实源。

本节不建新的账本、标识或队列类机制（清单与减法依据见 charter T6）。任务目录含年份，创建/改名核对活动区与归档区防撞名；具体 id 与 schema 编码留机制文档。

有意取舍：不扫描安装以来全部业务提交，不用时间区间定义任务归属，不用归属隔离检查有效性，不把一次观察失败设为所有知识的唯一入口。保留机制须回答的事项与删除判断见 charter T6。

### 5.3 写者与持久化

**写者纪律（唯一定义）**：

| 对象 | 写者与约束 |
|---|---|
| 判定字段 | 入口脚本：状态/阶段、暂停/挂起、前置、返工来源、异常指向、放弃改动处置、复杂度、TDD 取值、任务基线提交、规划批准及触碰面快照、归属裁决/继承路径、Check/审查结论、策展和知识处置记录、所属实例引用、实例终止后的独立接续许可、收工保留 WIP 的人决定/对象/逐路径状态/待处置及实际解除结论 |
| 工作流定义 | 已绑定会话按授权任务编辑；未绑定会话按 §5.7 准备定义通道操作。准备授权/进度及收工 WIP 控制留痕由通用入口按 §4.4 写入，不靠手改草稿解除写权限制。通用校验器分时核对结构/实际就绪，现有实例仍读固定快照 |
| 实例/会话绑定/项目写入权 | 通用入口按类别/标识/范围/代次写入；会话绑定与准备权限遵守原门禁，维护写者的操作类型/预览范围/操作标识、实际变更路径/状态摘要/待持久化状态/人的处置结论与具名任务承接引用、两段交接接收者与检查点由 §4.4 指定入口写入，不造伪会话或业务许可 |
| 任务内容 | AI 按已授权范围起草 PRD/design/implement、决策与进展；不能靠手改内容字段覆盖控制字段 |
| 基线/项目配置 | 人审提案后由当前初始化/bootstrap 任务或 continue 的 `wf baseline` 子操作成组写入；应用先于最终检查，框架升级不覆盖；`project_id` 生成后不改，只有 §5.5 repair 经人确认可重建 |
| spec 与索引 | AI 依 §6.3 的本地流程编辑；脚本同步校验结构、路径、引用与元数据，不替人判断语义 |
| 资产清单与偏离/删除登记 | 安装/升级/修复入口按人确认写入；不把接受偏离当作“本地等于发行模板” |
| 归档记录 | 归档动作及人确认 repair；归档前置不满足不得写正常终态 |

**记录分类**：任务记录（含持久策展清单）、用户工作流定义及准备记录、实例记录及固定快照、会话绑定、项目写入权记录、spec、索引、活基线、项目配置、资产清单与裁决登记进 Git。框架流程文档属于发行资产，不混入用户记录类配置。活动指针、读取留痕、互斥锁对象（短时持有，文件可留存）与临时缓存属运行态，gitignore；不能承担跨任务回收统计。运行态不承载不可重建的唯一事实，丢失后从持久绑定/实例/写入权记录重建或重读，不能重新绑定或假定无人持有写入权；运行态参与缓存判断须保守失效，不能因缺缓存而绕过门禁。单机用户层记录（`~/.wf/config.json` 及其执行器确认记录）是第三类：不进项目 Git、也不属运行态，跨会话与换检出持久但只对本机成立；写者仅为人显式执行的入口动作或人工编辑，模型不写；它不承载项目判定事实，缺失或损坏只影响执行器解析与确认匹配，按 §1.1 的出口处理。upgrade/repair 尚未提交的变更由 §4.4 维护变更持久化规则和现有 `.wf/writer.json` 维护结果字段保存操作标识、精确路径、按 §4.2 内容指纹解释的操作前后状态/哈希、暂存区状态与待持久化/已处置事实；`.wf/writer.json` 作为该结果的承载记录，不对自身递归计算内容哈希，其当前工作树/暂存区差异另按实际状态核验。释放维护所有权不删除这些结果，后续写者须保留未结结果。它是写权记录的一部分，不另建维护账本；不能核实旧格式或路径归属时，按无归属改动交人处理。

**写入标记**：判定字段每次变更记录命令、写入前 HEAD 与本次变更摘要/标识；脚本保留所有不属本操作的字段。核对变更与 Git 历史，旧标记不能替新一轮直改作证。未提交标记按当前待提交差异核对，不能要求刚写入的记录已经在历史中。伪造不可防，不给该标记密码学授权含义。

**schema 演进**：旧字段不删、不改语义，新字段提供旧记录的解释/缺省规则；读到不能理解的字段保留原样，只阻断依赖该字段的判断。写者脚本整记录重写时同样必须保留未知字段，不得因读路径未理解而丢弃；schema 演进的承诺由读写两侧共同成立。旧归档按需读取，不强制迁移整库；不能把新字段缺失静默解释成批准或检查通过。

**归档分层**：任务按 `archive/{YYYY-MM}/` 移动，引用按稳定 id 定位，路径变化不改身份；活动区常规校验，归档任务仅被引用时解析，周期巡检补长期检查。会话绑定保留 §1.3 的稳定逐身份路径，不随任务移动或按月合并；启动只读当前会话、当前写者及本次判定实际引用的绑定，首次绑定先直接查该身份路径；这不豁免 §5.4 对活动区保留 WIP 和写权限制的检查。无关历史绑定不逐一读入；被引用时核对原绑定事实，已知应有记录却缺失/冲突仍走 §5.5，不把缓存缺失或未扫描历史解释成可重新绑定。周期巡检覆盖历史绑定及引用，不改变终身不改绑约束。

### 5.4 一致性校验与中断恢复

**启动校验**：核对本次判定所需的记录/schema/取值、执行候选唯一性、会话写者与绑定的对应、维护写者与本次预览范围/操作的对应、当前会话绑定、写者类别/标识/代次/准备或维护范围/恢复状态、未结束实例的快照/游标/任务归属及结束中断、DAG、被引用归档任务的终态、写者标记（历史可达性按下述记录锚点核对处理）和框架资产可用性。核对活动任务/准备交接记录中的未处置保留 WIP 及其对象/具体任务范围，按 §4.4 仅供同对象恢复，不因 writer 空闲漏掉该边界。启动还按 §4.4 的维护变更持久化规则和 §5.3 的写入记录核对 upgrade/repair 待持久化路径、实际状态及暂存区/HEAD 差异；能对应操作且未冲突的结果作为独立待处理组保留，不授权其他任务接管或提交，状态不符则交人处置。`.wf/writer.json` 回执本身不递归哈希，其状态直接按 HEAD、暂存区和工作树核对。工作树中合法未提交记录按下述记录锚点核对视为存在；维护持有/待恢复不向会话授予业务写权。绑定读取范围按 §5.3，不扫描无关历史会话；读取结果不授权当前会话取得其他对象。已结束实例按 §5.9 读稳定终态摘要，只在当前绑定、活动记录引用或巡检时解析所需历史，不逐步重跑无关旧流程。保留任务独立接续只核对保留许可及必要历史引用，不再等待原实例推进。归档终态仅解析被活动任务前置或返工引用的成员，其余留周期巡检；凡当前判定依赖的任务、提交、文件引用均核验。已删除路径与经登记的资产删除是显式状态，不因文件不存在误判为悬空；未知记录/引用不得默默跳过。

**记录锚点核对**：当前记录存在性以工作树为准：未提交但实际存在、结构/写者/引用可核对的记录算存在，其待提交事实单列；历史只核来源、标记和引用，不要求刚写的记录先在历史中。预期记录在工作树确实缺失时才报记录缺失，即使旧历史有它也不自动补回或当作存在；最后写入标记的 HEAD 不可达时，先报告“记录锚点需核对”，它本身不证明切错分支或内容失效。只读列出事实及返回相符历史、人工补齐记录、经人确认 repair 的出口，不自动重建、按用户删除处理或猜测分支意图。人确认历史重写后按 §5.5 预览，核对当前仍需使用的记录、任务基线、归属提交和引用，保留旧标记及核对依据，只受控恢复可证明的定位关系，不自动改写 Git 历史或全历史追认归属。内容及所需引用均可核验的判断可继续，不能仅凭“文件还在”豁免缺失依据，也不把修复锚点当作旧批准/Check 自动有效，仍按 §4.2 核验。不能核实的相关判断保持阻断，不扩张到无关已可核验判断；写权不明仍按 §4.4 恢复。只读观测遵守 §1.1，分支边界由 charter T3 约束，不承诺历史改写后无损接续。

关键非法组合包括：多个执行候选或会话推进时候选不属写者绑定；维护持有与会话写入并存、维护操作/范围/代次不匹配或未获维护持有即应用；同会话绑定冲突、实例认领其他实例的任务、未完任务无明确处置却记录实例终态、非保留任务绕过实例独立执行、写入权记录与已落盘交接矛盾；未归档且异常转移未完成；挂起但返工集合为空；归档却残留未决挂起/暂停；批准与规划版本不对应。候选、绑定/写入权及异常转移问题按事实恢复，批准失效回 Plan，其余给具体 repair 出口。T 挂起、R 执行是合法组合，不因此报并发。

**中断恢复**：单记录写入用原子替换；写权动作按 §4.4 在原互斥内核类别、标识、范围和代次：两段写权交接未完成授予时保留接收者/对象/待恢复检查点，维护中断保留操作标识与已落盘步骤，不能重当空闲或两边继续写。保留 WIP 的同对象恢复先核真实文件和交接，不凭指针恢复旧检查。准备定义、实例创建/结束及跨任务/实例/绑定动作先校验完整候选结果——包括全部目标位置的存在与碰撞——才开始第一次状态写入，落盘阶段按固定顺序执行并持久化步骤标识，重入只补未完成部分；先改状态后发现碰撞需要手工撤销属本协议禁止的顺序。失败不报成功，也不无痕回滚已提交事实。归档移动/记录已落盘而归档提交未完成时，保留“待持久化”恢复状态，下次启动先核对工作区及历史、经已有提交授权完成或交人处理，不再当作另一个正常任务重复归档。完成报告只在归档步骤全部成功后给出。

**挂起路由**：绑定对象的当前任务为挂起 T 时列出未归档返工成员与阻塞原因；同实例内可按 §5.8 定位返工 R，普通任务绑定则保存交接、暂停并释放写入权，由新会话选择 R，不在原会话改绑。不在 T 上继续业务修改；T 的未决等待不阻断新会话取得写入权后执行独立就绪任务。挂起复评在每次归档成功后及启动结构校验通过后执行，按 §5.6 的挂起清除判断；失败/中断先恢复，不先清挂起掩盖残留。复评只在当前会话持有 §4.4 项目写入权且目标在其可写范围内时执行；未持权时只输出「待复评」事实与取得写权后的重入出口，不改任务记录。

**周期巡检**：人发起，或正常归档任务累计数达到项目配置巡检节奏的整数倍（默认 10；按归档时间排序计数，同时间用任务 id 稳定排序，异常归档不计入也不重置，人工巡检不改变计数——计数可从归档记录完全重建，不设运行态标记；阶段收尾伴随人的主动意图，由人发起承载，不设阶段尾任务归档触发）时，检查归档引用、终态、重复 id 与知识治理，共享一次遍历。发现问题交 repair，不重开旧任务。

### 5.5 受控修复

**repair 契约**：只修普通入口无法处置的非法结构、损坏记录、资产缺失和中断事实，包括未收工关闭的写权、绑定/写权不明、维护/交接残留、实例推进及 §5.4 记录锚点核对中经人确认需恢复的定位。预览对象、现状、目标态和影响，在终端确认后按 §4.4 取得维护写者；旧写者存在/状态不明时，先核实其停止和 Git/原始记录/改动去向，在同一互斥中受控恢复能证明的写权事实再应用，不造伪会话或改绑。不能确认代次/范围则不伪造可继续记录，保留只读诊断及 §7.3 独立卸载出口。候选修复须核全图/引用一致，保存旧标记和变更记录，并按 §4.4 的维护变更持久化规则、§5.3 记录逐路径变化及结果状态；repair 确认不等于 Git 提交授权。应用/验证中断且结果不完整或无法核实时按 §5.4 保持待恢复，不先释放为空闲；完整核验成功后的提交、待持久化与释放按 §4.4 处理。未核实依据不变成通过，原 WIP 仅按 §4.4 保护及同对象恢复，不被 repair 自动提交/清除/验收。合法多余边走删边，repair 不替代普通操作、批准或业务修复。

**重建项目标识**：重建 `project_id` 时，预览列出旧标识与按旧标识登记的确认记录，人确认后由入口删除或标记这些记录为失效，并在项目侧 repair 记录留痕；只靠后续哈希不匹配不算完成失效处理，也不得在未确认时静默复用旧标识。

**不可解析记录**：先保留原文并呈现安全的相关片段，人对照 Git 判读；不得新建同名任务覆盖。repair 可按人指定事实重建，不要求原记录先能解析；单记录删除前核验活动/归档前置、返工和继任引用均无悬空风险。整体运行时损坏则用独立卸载入口保留数据后重装，再修复。输出须去除秘密，不能为了呈现原文泄露凭据。

引用不完整时拒绝相关判定并保留只读诊断；修复是明确授权后的状态一致化，不自动推测人意图。升级缺文件尊重删除，repair 恢复缺失资产则必须有单独的人确认，二者不能互相偷换。

### 5.6 就绪、变更边与返工

**就绪选择**：未归档、无暂停/挂起、无异常转移残留、前置全部满足的任务可选。存在有效当前任务则先按其状态与阶段路由：暂停等待恢复、挂起转返工出口、其他正常继续；执行中的任务新增前置时可继续执行，但不能收尾。已有持久绑定时仅恢复该对象；实例候选限其所属任务，无指针不能改绑。真正未绑定的新会话按创建时间给出最早就绪建议，人可选另一个；落盘前仍须取得 §4.4 写入权；无候选时报告具体阻塞或允许建新独立任务，不靠无穷下沉猜测。

**建边/删边**：独立图变更由人发起；实例内顺序边按 §5.8 已确认的展开规则由通用入口创建，不重复逐边请求。两类均由脚本先校验再落盘。建边两端限活动区，前置须未归档，无自环无环；已经正常归档的任务可在新任务定义时作为历史前置，异常终态不能新增绑定。删边只修改未归档持有侧，目标可在归档区；无法解析的死引用走 repair。进行中任务新增边只挡收尾；不得修改已归档持有侧。操作失败不留下未声明的半条边。

**返工流程**：人确认缺陷与范围 → 建 R，继承 T 原前置并记来源 T → 同一受控动作给未归档 T 加 R 前置和挂起 → 执行 R → 复评。若 T 属当前实例，R 同属该实例并按 §5.8 的受控插入记录人确认及游标位置；普通任务绑定则按 §4.4 暂停/释放，由新会话绑定 R，不能会话内改绑。T 可以是当前任务自身，也可以是未归档前置；已归档缺陷用维护任务。挂起不改 T 的任务状态，同实例内定位 R 不给 T 强加暂停；跨会话释放写入权仍须按 §4.4 显式暂停。wf 内的紧急任务仍遵守原有批准、范围与门禁，紧迫感不授予先做后补的许可。wf 外已经发生的应急改动按 §4.2 的外部变更处置接入，保留外部属性并核对影响；确有返工、清理或复盘欠项时再立普通任务承载，事后立案不追认此前的动作授权。

**挂起清除（唯一定义）**：`T 未归档 ∧ T 挂起 ∧ 返工集合非空 ∧ 返工集合无未归档成员 ∧ T 前置全部满足`。返工集合为来源指向 T 的全部活动/归档任务；正常或异常归档均算归档。清挂起保留暂停；若 T 将成为执行候选且已有其他执行候选，同一动作给 T 记“等待人恢复”的暂停，避免复评同时唤醒多个任务。多个 T 同次满足时按创建时间顺序评估并应用，后续按更新后的候选集判定。清除不自动抢占当前任务，之后按就绪选择恢复。

**替换/放弃**：两个动作都由人明确决定、入口脚本预览并核验状态/图/引用及改动处置后实施。替换保持继任责任；放弃表示停止原任务，不能要求原任务先取得规划批准、Check pass 或满足原前置才能退出。暂停/挂起不是放弃的阻碍：放弃动作明确取消原任务后续执行与等待，保存原因，不把取消等待记为前置或返工成功。

替换只作用于未归档且已处理暂停、未挂起的任务；挂起者先明确返工处置。预览在继任者 PRD 列明继承路径，由人确认 `touch_paths` 覆盖；不覆盖就不实施、不自动扩大快照，继任者开工仍按 §4.2。实施时继任者承接原前置、已有提交触碰路径、返工来源及仍在执行的所属实例（若有），下游按确认方案重连；原任务异常归档，来源/异常指向保留，继承的来源提交进入继任者检查对象。已按 §5.9 独立接续的保留任务发生替换/返工时，新任务按普通任务建立，只保存来源引用、不重新加入已结束实例；原任务历史归属不改。

放弃可作用于任一未归档任务。预览列出未完返工、下游引用、阶段尾任务职责及已有提交/未提交改动；人确认停止后不再推进其业务。返工与下游可以保留各自合法的阻塞引用，或在另有明确确认时放弃、删边、重连；原任务的放弃不自动取消这些对象，也不视为依赖满足。若仍要达成该阶段目标，尾职责由具名后续任务承接；人明确连同阶段目标也放弃时，记录目标撤回与影响，不强造替代任务，也不把阶段标为完成。实例批量终止按 §5.9 统一预览，但仍逐任务保存决定和处置。

改动处置选择为保留现状并列未验证项/风险、以新提交反向修正，或具名任务承接；无实际改动记“无改动”。修正须已完成或有具名承接，未提交改动须在授权内提交或由人处理完毕；由脚本写处置结论、依据和引用。去向未决则冻结业务并交人裁决，处置未落实只阻断异常归档，不撤回停止决定，不自动回滚，也不以删边代替改动处置。

异常归档核验本节的人确认、合法最终状态、图与引用一致、改动处置和 §5.3 写者纪律；授权提交及持久化/中断仍按 §4.2、§5.4。原暂停/挂起以“本次放弃取消”记历史，在异常归档时清为已处置，不能残留成普通未决等待。它不套用 §6.5 正常完成最终门禁，成功只报告替换/放弃已处理，不称遗留代码已验收。

所属实例仍在执行时，返工/替换同步核对实例任务映射与游标；放弃不自动满足必需步骤，后续按 §5.8 的继任/略过或 §5.9 的异常终止处理。跨对象只写预览中必要关联控制记录，不授予执行其他任务或消费其批准的权限；普通任务绑定不因替换/放弃而改绑继任者。

**前向恢复**：上述跨任务替换/放弃与返工动作均依 §5.4 的中断恢复，实施后只补齐，不倒回已成立事实。返工 R 被替换时新 R 继承来源，T 继续等待；R 被删边放弃则异常归档并复评 T。任何重连都先检查候选图无环，不能先改到一半再发现无合法出口。

### 5.7 工作流定义、准备与实例创建

**用户工作流定义（唯一定义）**：目标项目 `.wf/user-workflows/<workflow-id>.md` 是 Git 跟踪的用户数据。统一格式含格式版本、稳定工作流 id、内容版本、用途/适用条件、输入、有限顺序步骤、完成条件和由各任务步骤 verifications 承载的必要验证。每个步骤含唯一 id、类型（任务步骤/人判步骤）、输入与产物引用及落点、必需/可略声明和人判点；可略项还声明省略条件，以及下游是否不消费其产物或使用什么明确替代，执行语义按 §5.8。框架提供同一套通用解析、校验和执行器；在支持能力内，0→1、重构、审查等流程只需编写定义，不改框架代码、Trellis/宿主受管资产、平台变体，不加流程专用脚本或另写集成方案。

定义只表达顺序工作和显式输入/产物引用；格式能力上限见 charter T3。路径复用 §6.1 安全语法并核对真实落点，输入不拼接成可执行代码；凭据只保存可用引用。定义是工作内容，不授予任务开工、提交、外发等动作权限。新能力超出格式时先按 charter T5 说明具体缺口。

**准备定义通道（唯一定义）**：安装完成后，未绑定会话可经人明确授权准备首份或其他工作流定义；这不是任务执行，也不产生任务/实例绑定。通用入口先核实身份、工作区及 §4.4 写入权，持有仅限本次预览路径的准备权限，才允许人或 AI 起草/导入 `.wf/user-workflows/` 定义。记录授权范围、内容版本、校验结果和未决项；该准备记录随定义保留为项目数据，具体文件编码由机制设计确定。正常已绑定会话编辑定义仍走其已批准任务范围，不借准备通道改绑。

准备通道只写定义、准备记录与必要写入权记录，不执行流程、不改业务/spec/基线，不自动创建或批准任务，也不授权提交。准备完成或由人取消后，只要未提交内容逐路径明确处置就释放准备权限；未通过静态校验的草稿可以保留，但不能启动实例。同一未绑定会话随后可请人确认创建实例并建立首次绑定。已有定义的人可只读选择；外部手改/导入的用户数据先核对内容和来源，不能自动算成已批准的执行版本；修改定义仍遵守单写入者纪律。准备中断按 §5.4 核对已落盘记录后恢复或退出，不将准备权限当作执行授权。

**定义校验时点（唯一定义）**：创建实例前核对格式/支持版本、必填项、步骤 id/类型、顺序引用、步骤级输入/产物路径、可略条件及下游替代、完成条件、验证和人判声明；校验按 §5.8 已有两类步骤解释，不引入可编程条件。静态校验只确认可解释且引用有来源，不把尚未产出的文件或命令判为已存在。验证来源只允许三类：已有项目命令、当前任务 Plan 将给出的检查、前序步骤将建立的命令声明。后两类可在创建时待解析，须指出建立声明/设施的任务或动作、持久落点与首个消费时点；建立先于消费，不能以未来结果满足当前门禁或用自由文本占位代替来源。

初始化任务须在批准 PRD 中给出开工时立即可用的基本核验；本任务建立的测试设施可在建成后用于 Check，不反过来作为自身开工前置。创建时的待解析验证按下述消费边界在真正使用前核对，不因“定义有效”免跑必要检查。

**动作与验证消费边界（唯一定义）**：任务动作是供 AI 在当前任务批准范围内执行的有限工作说明，人判仍由人实际回答；通用脚本管理固定控制流，不把定义正文或输入求值成程序。执行前按本节定义校验时点的来源清单核对真实文件和声明：跨步骤引用须由正常完成的前序工作建立，任务内检查须已纳入当前批准规划并实际可运行；在任务规划/验证材料中固定本次来源版本、具体调用、工作目录与输入绑定，实例只引用这些任务事实，不新建命令注册库或复制任务检查结果。输入作为数据传递，不拼接到可执行正文；项目已有脚本和构建/测试工具仍按项目及当前任务授权调用，不把其存在当作工作流新增可执行类型。定义不授予工具、提交、外发或扩范围的权限；调用语义、范围或验收实质变化回 §4.2，固定执行语义变化按本节迁移规则处理。确定不支持的类型、无来源引用、缺失输入或未就绪命令输出阻断；来源、授权或恢复语义存疑输出 §1.5 的需人裁决，保留待决事实，不自动换命令或记 pass。检查失败、未跑或未结束按 §4.2 处理。恢复复用 §4.4 交接、实例步骤与真实产物/结果，结果不明先核对，不盲目重放副作用未明的业务动作；§5.4 的控制流幂等承诺不扩张到任意业务命令。

**工作流实例（唯一定义）**：每次执行有独立 run id；`.wf/workflow-runs/<run-id>.json` 保存定义身份、完整快照路径及哈希、输入值/引用、当前步骤、步骤结果、关联任务/产物、决策与下一步。快照保存在 `.wf/workflow-runs/<run-id>/definition.md`，连同记录属于项目数据；仅有哈希而无可读快照不满足恢复。编排记录不复制任务状态、批准、触碰面、Check/审查与归档终态，只引用各任务的唯一记录。

**实例创建授权（唯一定义）**：人明确选择定义的确切版本/哈希、输入、步骤适用性与顺序展开规则后，通用入口完成静态校验；在 §1.3 会话可首次绑定且取得 §4.4 写入权的条件下，成组固定快照、输入及授权记录并创建实例。初始化前可创建规划状态的实例，不要求基线/配置或尚未产出的验证命令先存在；依赖参数暂用第 3 章的发行缺省。它只允许编排及产生规划任务，任何交付改动仍等相应任务开工门禁通过。项目基线/配置尚缺时，定义的首个任务步骤须是初始化/接入（可先有不动交付物的人判步骤），否则不创建实例，出口是改定义或先按第 3 章接入。

**定义维护与迁移（唯一定义）**：源定义每次内容变化均有可识别的版本/哈希，新实例采用所选版本；编辑源文件与迁移在途实例是两个操作。修错字、调整排版乃至另写方案，都不改变任何既有快照，不要求停止在途实例。只修文字且不改步骤、输入/输出、完成条件、验证或人判语义时，按 §4.2 机械修订纪律留理由，不另要一次执行迁移批准；是否改变语义存疑则交人判断。

既有实例继续使用原快照。人确实要求采用不同执行语义时，先审差异、既有产物/批准和未完任务处置，再按 §5.9 实例退出与新建路径承接；新实例只读引用旧产物，重新核验当前有效性并新建所需任务，不重新认领旧任务，也不把旧游标套到新步骤。格式不兼容按 §7.2 保留数据和显式迁移，不强制改写整库。

### 5.8 步骤与任务编排

**工作流任务归属（唯一定义）**：普通任务默认独立。实例通过通用入口新建任务时，在任务唯一记录中写入所属实例 id，归档后保留历史；一个任务至多属于一个实例。首版不接管既有独立任务或其他实例任务。本文“接续任务”仅指恢复本实例已生成、尚未正常结束的任务或其按 §5.6 产生的同实例继任者；不是新的步骤类型，也不是收养无主任务。一个任务步骤覆盖一个普通任务的完整四阶段，可在该任务内声明顺序动作及人判点；单任务流程只有一个这样的任务步骤，多任务流程依次产生多个。另可有不改交付物的人判步骤。内部动作不是独立任务或嵌套工作流，不能因为“生成任务”动作完成就越过该任务步骤；产生交付改动的动作均须属于当前任务并通过 §4.2。

**顺序建任务与依赖（唯一定义）**：人在创建实例时确认固定定义、输入、展开规则及由此产生的顺序依赖，入口将该授权与快照一并保存；它只许可生成规划任务及对应依赖，不代替逐任务规划批准。执行器首次抵达一个任务步骤时，按固定规则原子创建任务、写所属实例及步骤映射、添加对前面已生成任务的顺序前置，复用 §5.1 的唯一前置集合。首个任务无顺序前置；以后直接依赖前一个未略过的任务步骤所对应的正常归档任务（有替换则为确认后的继任者），跨越独立人判步骤不另造任务/依赖；同一任务内的动作不加任务间依赖。已正常归档前置在新任务创建时作为历史前置登记，不尝试以普通建边入口修改已归档任务。

上述范围内自动建边是已确认流程的确定性展开，不逐边再次询问；仍须按 §5.6 核验合法引用与 DAG。定义之外的增删边、外部前置和返工/替换另按其人发起规则；当前任务的批准不能自动授给下一任务。重入按实例 id/步骤 id 查已有映射，只补未完成控制动作，不重建同一任务。任务替换后顺序引用指向已确认的继任者，保留原历史。

跨流程复用仅显式只读引用产物，不能认领、推进、批准或归档来源任务。编排产物按实例/步骤分别落盘；业务代码与 spec 等共享路径须逐任务明确批准，实例隔离不免除 §4.2 的检查有效性核对。既有产物可在当前步骤按完成条件核实后复用，但存在同名文件不等于已经验收。

**步骤决策与略过（唯一定义）**：步骤及任务内部动作默认必需；可略项须在固定定义中声明允许省略的条件，以及下游是否允许不消费其产物或使用什么明确替代。人判点的答复按以下处置记录，含对象、依据、适用的版本和后续出口；未答复就保持待决，模型不代答。

| 人的决定 | 允许的推进与约束 |
|---|---|
| 继续/认可已有成果 | 核实当前完成条件、必要验证和实际产物；已有 LICENSE 等合格产物可复用，记“复用满足”，不伪造新执行，也不免除所关联任务的检查和正常归档 |
| 暂停/稍后决定 | 保存未决事实与下一步；按 §4.4 处理工作区并释放写入权，保留游标与绑定 |
| 换方案 | 任务内且符合固定流程的方案变化回 Plan 重批；返工/替换按 §5.6。要改变固定步骤/输入输出/验收语义时按 §5.7 新版本新实例路径处理 |
| 略过 | 仅固定定义已声明可略且条件成立，人确认原因、产物及下游影响后记录“已略过”；必需项改走满足条件或新实例路径 |
| 整体停止 | 走 §5.9 异常终止，不把剩余步骤写为完成 |

略过不是 pass。可略任务步骤应在生成任务前决定是否省略；已生成任务时先按 §5.6 明确其放弃/替换及改动处置，不留下未完任务被游标绕过；已有任务正常归档则按实际完成记录，不再改称略过。下游缺少必需输入就阻断相关步骤；省略独立任务步骤时，下一个任务依赖前面未略过且已正常完成的任务步骤（替换时使用确认后的继任者），不建立对“已略过”记录的任务边。框架四阶段的 required 门禁、必要验证、复杂审查和人调用 finish 均不属于可略项。语义存疑按 §1.5 输出需人裁决，不凭“人说跳过”扩大已批准范围。

**工作流推进（唯一定义）**：每次核验 §1.3 会话绑定、§4.4 写入权、固定快照及哈希、当前步骤结果和任务归属，按 §5.7 的动作与验证消费边界核对来源、调用、目录、输入和恢复事实，按实际结论放行、阻断或等待人裁决。任务步骤内先继续当前任务四阶段与内部动作；只有该任务正常归档且前置满足，或已按上文合法略过并处置关联任务，才进入下一步骤。独立人判步骤只按实际答复及适用条件推进。结果、必要验证与决策由通用入口写入后再更新游标，不以 AI 自报完成或单次创建任务代替整个步骤完成。

失败/待决先停当前步骤，不自动终止实例或污染其他对象；可在当前批准范围内修复后重检，范围变更回 Plan。已放弃任务不满足必需步骤：继续同实例时须有按 §5.6 确认的继任者，合法可略项走略过规则，不继续则走异常终止。返工/替换由人确认后记录受控执行序列修订（来源、位置及关联任务），固定定义不变；它不允许任意跳步、循环或绕开人判。跨记录写入按 §5.4，结果不明先核对，不盲目重做。

### 5.9 实例终态与异常退出

**实例终态（唯一定义）**：实例在未结束时记录当前步骤、暂停/失败/待决事实；结束动作有持久的“结束处理中”检查点，最终只取正常或异常。正常表示所有必需步骤已满足、可略项已合法处置、关联任务均有相符终态且所需人判已完成；异常表示人已决定不再执行该实例且未完任务/改动已逐项处置。实例结果只描述编排结局，不复制任务状态、不表示项目全部完成，也不将保留代码或异常归档任务说成已验收。

正常结束由通用入口核验并记录全部步骤结果及任务引用，不能代调 `wf-finish`。实例/任务最终记录在 §4.2 授权边界内提交持久化、工作区处理完后按 §4.4 释放写入权；无提交许可则如实停在待人处理，不报告全部结束成功。结束处理中断按 §5.4 恢复；终态记录仍在原稳定 id 路径保留，历史会话绑定继续可查但不占用写入权，同一会话不能另选对象。

**实例异常终止（唯一定义）**：方向不再适用、用户放弃或版本迁移都使用同一通用退出入口。人可对任一未结束实例发起，包括刚创建停在规划、尚未生成任务，以及运行、暂停、失败或待决的实例；无需先开工、制造失败或取得步骤成功、任务 Check pass、原前置满足。入口先核对绑定及写入权，预览已生成任务（包括返工/继任者）、未生成步骤、已有提交/未提交改动、对外依赖及承接去向；人逐项选择放弃或保留，可一次确认整个批量计划。

| 对象 | 终止时的处置 |
|---|---|
| 已正常/异常归档任务 | 保留原终态、产物与历史引用，不重开、不重认领 |
| 人确认放弃的未完任务 | 复用 §5.6 放弃通道，直接取消其后续执行与等待，落实已有改动处置后异常归档；不为退出强造替代任务 |
| 人选择保留的未完任务 | 保留原实例历史归属，在任务记录写明本次保留决定与“实例终止后可独立接续”；状态为执行中的任务先暂停，未开工任务保持未开工，不按 Plan 阶段重写任务状态；挂起/依赖如实保留 |
| 尚未生成的步骤/任务 | 记未执行及终止原因，不生成空壳任务，不标成功 |
| 改动及外部依赖 | 未提交改动先在授权内提交或由人处理，已有提交可按人确认保留并列风险、反向修正或具名承接；对已放弃前置的外部/保留任务，保留合法阻塞引用或按人确认删边/重连，不自动当依赖已满足 |

保留的任务在新会话中可作为独立任务绑定、通过既有恢复/批准/依赖门禁继续；它不能被另一实例认领，后续完成也不重开或改变旧实例的异常终态。实例记录保存的是终止时的处置快照和任务引用，任务当前状态仍只查任务记录。终止批量计划只修改已列对象及必要关联控制记录，不能顺带取消外部任务或项目/阶段目标；这些范围须另有明确人决策。

人的停止决定立即约束本会话停止业务；只有身份和写入权有效时才落盘终止请求。身份/写权不明时仅保留当前请求并只读诊断，恢复权限后再记入项目；有权限但改动去向或引用未决时，保存结束处理中检查点与待决事实，可按工作区边界暂停释放写入权。阻断结案不构成继续执行许可。脚本先校验完整候选图/归属/终态与改动计划，再按 §5.4 幂等落实逐任务处置、记录实例异常终态并释放写入权；中断只补未完成部分，不再要求重弃已归档任务。成功仅报告“实例已异常终止”及保留/放弃任务与风险，不称流程正常完成。

## 6. 本地 spec 体系与最终门禁

### 6.1 知识文件与路径

**spec 单位**：一个原子文件一个规则/约定族，通常 30–60 行；按需加载整文件，不设计文件内部切片。单层起步，实际包/边界形成后再拆目录。

**spec 元数据**：`paths`、`status`、`verified_at`、`schema_version`、`author`、`counterexample`。status 至少区分模板、有效候选与已停用；模板/停用不当当前规则加载。`verified_at` 为核实日期或 `extracted`；字段编码及合法组合由 schema 明确，不能任意词串冒充日期。author 区分 human/ai，仅用于复核优先级，不决定真伪。

**paths 契约**：仓库相对 glob，有界解析后规范化，按枚举拒绝条件判定非法——绝对路径、`..` 段、反斜杠分隔、控制字符；其余形状（含作用域标记与非 ASCII）不因“未能识别”而拒绝，避免真实仓库路径被 allow-list 误拒。非法 glob 按条失效并输出，整段解析不可靠则整文件标不可路由。仓库边界：除本仓库根外，工作树内任一目录含 `.git`（目录或 gitfile）即视为嵌套仓库根；本仓库根的 `.git` 是合法边界起点，不参与嵌套判定；判定按规范化后的真实路径进行，符号链接先解析目标、不跟随跨边界；判定作用于条目的字面前缀、匹配结果与登记的托管路径，不遍历未涉及的目录。落在该根之下的路径不可路由，按非法处理并输出（不做嵌套仓库见 charter T3）。无合法 paths 的知识必须经策展/索引明确加载，不能悄悄消失或声称覆盖了代码。

**spec 索引**：索引表、开发前 checklist、质量检查三段，条目只写说明与指针。新增/删改文件必须同步入口；不要把同一规则复制进索引。项目已有 wf 入口就原地维护，不另造第二套知识目录。

### 6.2 三时点加载

**策展清单**：任务记录中的持久引用集合，入口脚本保存 spec 路径、内容哈希、用途与引用时点，随任务进 Git/归档。Plan 先按批准触碰面与 spec 索引选择正文，Execute/Check 新发现相关规则时补入同一集合；已选条目在本任务内保留，便于复原曾声明依赖的知识。它统计的是“任务选用/引用”，不证明已读或执行。首次没有集合先读索引再选，无需知识图谱；零引用须显式保存空集合，字段缺失不能解释为零。开工前读正文，换会话重新加载。

| 时点 | 本地动作 |
|---|---|
| start/开工 | 按策展清单读相关 spec、基线；无清单时先策展 |
| Execute | 编辑前运行 `wf spec --file <path>` 读取命中规则并留痕；遗漏由 Check 兜底 |
| Check | 按真实触碰路径重新匹配，核对读取记录、版本、过期与缺失 |

**读取留痕**：记录 spec 路径、内容哈希、时间于运行态侧车，不因单次阅读弄脏任务记录；丢失则重读，写失败只降级可见并重读，不放大为任务阻断。被预算降级截断的条目不得记为完整读取，须标记未完整装载，由 Check 判定重读。它只供当前会话加载与 Check 核对，不供跨任务回收统计。持久策展清单提供引用和恢复位置，不是跨会话已读证明。当前哈希与所读不符，或没有读取记录，须先重读；新选用规则的策展写入是独立的记录动作，不冒充纯读取。AI 伪造留痕属于不可防边界。

**匹配排序**：精确/窄范围优先于宽泛 glob，以字面段数、通配符数量与长度确定顺序，最后按路径作稳定 tie-break；排序不表示窄规则可自动推翻宽规则中的禁止项，语义冲突须人裁决。

**预算降级**：读取第 3 章项目配置中的 spec 加载/输出软预算，缺配置的初始化/接入采用同版发行骨架的数值缺省；按码点计数，具体键和每次输出的计数范围由 §8.1 机制设计固定并以夹具核验。未知/非法预算不静默当作无限，按项目配置的局部阻断规则处理。超预算优先缩小本次策展范围，再退到索引/短提醒/汇总；截断或未装入的对象在正常输出可见，不能只写 stderr。提醒不算完整读取，必需正文在依赖前仍须完整读取，可按文件分次加载（指跨文件分次，单文件不切块）；预算只约束一次加载的多文件总量，单个必需文件大于预算时允许完整超额输出并标注「超预算完整读取」，不截断正文，也不改写或拆分知识文件；预算不授权跳过规则；且只覆盖 spec 正文与提醒，流程文档、基线、项目配置与 skill 正文不受削减，读取不完整即阻断。

### 6.3 准入与完整变更流程

**知识准入（唯一定义）**：有可追溯的真实项目依据，且有后续消费场景、与现有 spec/拒绝项不重复冲突。依据可为已观察失败、已实现并验证的契约/模式、人的明确长期约定、真实数据或明确边界；不要求先发生事故。每条说明不遵守会造成什么，并给正反例；假设性“最佳实践”或删掉也无影响的空话不收。

**Code-Spec/Guide**：前者写怎么实现，包括适用场景、签名/字段、校验/错误矩阵、Good/Base/Bad 例子和断言点；后者写怎么思考，短 checklist 指向具体规范。机械可核验的条件给本地命令/字段，不只写散文。知识是简报而非日志转录，记录被排除方案及原因，敏感内容不沉淀。

**spec 变更流程（唯一定义）**：读取现有索引/相关知识与本地依据 → 判准入与影响范围 → 提出当前任务授权内的变更 → 编辑原文件/新文件 → 同步索引、paths 和元数据 → 本地检查引用、重复入口、占位符及路径 → 用相应项目验证核实契约 → 记录新增/更新/合并/改名/删除或无更新的结论。语义冲突、删除/合并/降级由人裁决；不在任务范围的知识改造另建任务。

改名同步所有当前索引与活跃策展引用（只写路径与哈希）；删除不得静默移除引用——仍被活动任务（含暂停、挂起）引用的文件，删除前须逐个解除依赖：由人在该任务策展清单记「已解除依赖：路径 + 哈希 + 理由」，该写入属 §4.2 的固定职责授权；未解除时删除阻断，给出三个出口：先解除、推迟删除、指定替代文件。已归档任务的旧路径是历史证据，按记录版本/对应提交解释，不强改旧档案。不把知识路径重命名误报成历史损坏。读取缓存失效，受影响任务下次加载须读新版。

**知识处置留痕**：Finish 必经，可合法记录“本次无更新”；无更新不跳过判断，也不为交差造规则。尽量在最终 Check 前准备已知知识变更，Finish 只核对处置齐全。Finish 中确实新增/更改 spec、基线或项目配置时，按检查有效性回到 Check；涉及审查对象变更则重审，不循环制造新规则。§1.1 的本地 spec 契约覆盖全部动作，缺 MCP 不产生任何 unavailable 或跳过理由。

**拒绝项**：此处是项目内的知识拒绝，与框架边界出口（charter T3）不是同一对象；`.wf/out-of-scope/` 一概念一文件，记原因与可重议条件；原因须持久（临时性困难属搁置不是拒绝，搁置项在任务记录里登记）。重提先对照旧拒绝的事实差异，并追加进旧文件的既往请求记录，不为每次重提另建文件。已被代码/spec 覆盖的条目合并到原知识或移除，不为“已经做过”持续堆墓碑。临时进度放任务，不放长期 spec。

### 6.4 核实、冲突与回收

**核实周期**：默认 90 天，项目可配；本任务命中的到期条目须核实或明确记录“依赖但未核实”及原因，交 finish 人判。内容变化须重读，不能仅刷新日期冒充读过；核实日期只能在实际对照证据后更新。

**extracted**：表示从存量内容推断、永久待核实，不参与日期计算；本任务依赖时按未核实处置，人核实后才能转日期。无法从本地资料证明的外部行为同样标未核实，不要求安装 MCP 才能记录或完成诚实处置；必要业务验证缺失仍须按其自身要求阻断。

**周期清点**：巡检节奏触发或人发起时（阶段收尾伴随人的主动意图，由人发起承载，不设阶段收尾触发），从活动与归档任务记录的策展清单统计引用情况，连同过期与路径漂移输出；报告名称用“策展引用统计”，不用“实际加载次数”。读取侧车清理/丢失不改变结果。按 paths 交集列“需人工比对”，不冒称机械识别了语义矛盾；缺链、孤儿页和被新证据替代的断言同步清理。

**低价值回收**：以当前项目配置中的窗口 N（默认 5）为准，仅当该 spec 已存在期间、最近连续 N 个正常归档任务的完整策展清单均未引用它，且无活动任务引用时，列为人工回收候选。按归档时间排序、同时间用任务 id 稳定排序，未开工/异常归档任务不充作已完成的观察样本；样本不足、旧记录缺清单或知识改名/合并无法可靠映射时报告“统计不足/未知”，不能当零。改名映射据 Git 与 spec 变更记录核对，不为统计改写归档任务。

候选不是删除许可：先检查是否只是路径漂移或相关工作尚未发生，再按 charter T6 判断删除会破坏什么承诺。合并/降级/删除由人决定，Git 保存历史；AI 条目优先复核，人的旧约定也不能豁免核实。无需在 spec 元数据维护可变累计计数。

### 6.5 审查契约与最终门禁

**辅助审查**：复杂任务在 Check pass 后、人判前，由人打开顺序独立的异种 CLI 审查会话。审查材料分两个范围，都由主会话在发起时声明并记入审查结论留痕：**提交材料**只有 diff、需求与测试结果三类，不传作者会话、规划过程或自评；**允许自主读取**限于业务代码、spec 与作为需求材料的任务 PRD，reviewer 可只读仓库以覆盖固定检查面（范围、验收、契约/spec、跨层回归、可测性），读取用途限于这些检查面。两个范围共同排除凭据、私密配置、项目外路径与其他任务的任务目录；reviewer 需要范围外材料时停止并回报，不自行扩大，主会话也不以“审查需要”为由补发未授权材料。材料外发须人明确授权本次范围。这些边界是过程约束与事后核对对象，不是机器拦截（§1.5）：普通文件无法阻止 reviewer 读取仓库内其他内容，故以“发起声明 + 报告自述 + 主会话核对”作为可核对事实，核对不一致按审查未通过处理。主会话是唯一修订者；reviewer 只写自己的报告，不改源码/任务控制字段、不提交。驳回的报告发现须记录具体原因，供下一轮不再重提。报告是数据，逐条本地核实后才采用。

**审查文件协议**：以本仓库 `skills/multi-cli-review*` 为一次性适配源；协议最终由框架自有副本承载（框架资产，随发行投放、随卸载移除，纳入 §7.2 三方升级）。reviewer 不写项目树：报告产在项目树外的暂存目录（由框架入口按任务、轮次与 reviewer 槽位隔离给出），主会话向 reviewer 给出该暂存路径与 `--reviewer-id`、`--round`、`--task-id`，`--review-focus` 是 wf 侧约定总是提供的参数、reviewer 侧契约为可选；主会话在发起时把本次**检查对象锚点**交给 reviewer：Check 内容指纹（按 §4.2 覆盖触碰路径与相关 spec/基线/项目配置）、规划批准版本、相关 spec 与项目配置的内容哈希；report 字段含 task-id/round/reviewer-id/source-cli/review-time/review-focus/protocol 与这些锚点。导入前主会话再次计算当前锚点并与报告核对：不一致即该报告失效，按审查未通过处理、重新发起，不导入为有效结论；这只让新鲜度可核对，不防伪造（§1.5）。主会话在**自己持有 §4.4 项目写入权**时核验暂存报告与槽位字段，再导入 `{task-dir}/review/review-round-{N}/{reviewer-id}.md`；导入期间写权不转移、不释放，reviewer 不需要也不取得项目写权。两侧须加性支持 `--task-id`，不从嵌套 `review/` 名推断任务身份；未适配前不宣称可用。action 侧读取指定轮并先汇总再决策。

**审查人数与轮次**：复杂任务要求两个与本次实施 CLI 不同、且彼此不同的审查 CLI。人在发起时声明本次实施 CLI、两个 reviewer CLI 与槽位——实施 CLI 声明为单个；若本次实施实际使用过多个 CLI，须在声明中列全，审查 CLI 与其中每一个都不同；主会话核对声明、调用情况和报告，由入口在现有审查结论留痕中保存人工声明来源、时间及对应轮次/检查对象。报告 `source-cli` 是 reviewer 自报字段，仅用于与该声明核对，不是独立身份认证；声明缺失或两侧矛盾时不能判 pass，普通文件仍无法防伪（§1.5）。只能凑到一个时，可执行单 reviewer 并标 `degraded: single-provider` 供参考，但该结果不满足复杂任务的完成条件，按本节的不可用处置处理；同 CLI 换模型不算独立补位。轮次跨返工递增，每次审查绑定当次检查对象与规划/规范版本；旧报告不能因轮次文件还在而复用到已变化的对象。同一实施尝试最多两轮，仍 fail 则由人发起自身返工；返工后尝试计数重置，文件轮号不重置，避免已消费报告冲突。

**审查判定**：存在阻塞项、未决人工决策、必要验证 fail/未跑、报告缺失/元数据非法、人工身份声明缺失/冲突、身份/人数不合格（含只有单 reviewer）均 fail；否则 pass。纯建议可留档。fail 就地修复后重跑 Check，再发下一轮。vendor 双轴自审是 Check 内部步骤，不替代此异种检查；两类结论分开保留。

**不可用处置**：无异种 CLI、只能凑到一个 reviewer、skill 未装/加载失败或 CLI 起不来，由人声明情形与证据；主会话核对并保存 unavailable 及声明来源和时间。复杂任务此时不得正常归档：任务仍属复杂时只能暂停等待可用环境，或按 §5.6 异常归档；只有经人重新规划后确实符合轻量判据（缩范围、拆分、降低契约影响）才按 §4.3 降级并重新 Check，已有产物保留，审查结果只作参考、不构成审查 pass。留痕记录的是“未审查”，不得据此宣称审查已通过或该对象达到生产可用。无需 MCP 安装诊断；该处置不能替代必要业务检查，也不能把两轮实际 fail 伪装成不可用。

**最终门禁（唯一定义）**：仅规定正常归档动作的前置与任务正常完成的后置；替换/放弃的异常归档按 §5.6 执行，不套用以下完成条件。不另设相冲突的收尾清单。

1. 当前规划批准及触碰面快照有效，实际交付路径均匹配，范围/治理面未越界，复杂度与所需产物已复核；归档动作之前的 required 步骤全完成。
2. Check 为 pass，必要检查有命令/结果；内容指纹与当前交付状态、验收和相关规范版本一致。
3. 复杂任务有对应当前对象的审查 pass，且参与审查的是两个与实施 CLI 不同、彼此也不同的审查 CLI；已按 §4.3 判据降级为轻量任务的，按轻量要求执行 Check 内部审查。不可用留痕不替代本条。
4. 命中 spec 已读当前内容；过期/extracted 已核实或留痕并经人判接受，必要验证缺失不能借此放行。
5. 知识处置留痕存在（允许无更新），策展清单含本任务选用规则或显式为空，所有最终 spec/基线/配置变更已纳入检查；需复盘者已完成。
6. 前置集合全部满足，无未决挂起/暂停或异常转移；判定字段写者与标记可核对。
7. 本任务改动归属明确；在已有授权下提交完成、工作区无本任务未处理改动，外来改动未被捎带；非 wf 提交本身不构成拒绝理由。
8. 人在了解结果与未核实项后明确调用 finish；归档动作及最后的归档提交成功，才报告任务完成。前七项是动作前置，第八项中的归档成功是完成后置；动作中断按 §5.4 恢复，不制造自指门禁。

仍在执行的所属实例按 §5.8 同步步骤结果；已结束实例保留终止快照，所保留任务后续状态只写任务记录。实例终态另按 §5.9 核验，任务/实例结束后按 §4.4 保存交接和释放写入权，保留会话绑定。

## 7. 安装、升级与退出

### 7.1 接入与资产边界

**资产边界（唯一定义）**：框架资产是安装清单精确登记的 skill、脚本、`.wf/workflows/` 流程文档和发行模板，全部纳入 §7.2 三方升级。项目数据是任务记录及其内容、`.wf/user-workflows/` 用户定义及准备记录、`.wf/workflow-runs/` 实例及固定快照、`.wf/session-bindings/` 会话绑定、`.wf/writer.json` 写入权记录、spec 实体/索引、项目基线、`.wf/project-config.json`、裁决和归档。两类路径互斥；“安装时创建”不决定所有权。发行模板保留在发行资产区，由它首次生成的 spec/index/项目配置实例才是项目数据；复制到 `.wf/workflows/` 的流程仍是发行资产，不能借“生成文件”改变归属。`.gitignore` 只托管 wf 标记段，其余内容属用户。charter 与设计文档属 authoring 文档族，不在安装清单内、不投放目标项目（charter T7）。

**安装路径**：人将发行引用检出至系统临时目录，向终端自包含安装入口明确给定目标项目绝对路径；入口先按 §7.2 核验发行身份（版本、源提交、清单及源资产内容），未登记发行的裸提交或同版异内容在投放前拒绝，再预览目标、文件、Git 动作（首装时预览清单含 `.wf/` 目录与 `.wf/writer.json`），由人确认；按 §4.4 重验预览事实并取得维护持有后投放已声明的宿主 skill 根与 `.wf/` 骨架（skill 根按 §1.2 声明；`.wf/` 不承载可被宿主发现的 skill 主体），自检成功保存结果并释放，失败保留维护检查点，重入不盲目重复投放。无既有数据的初始写权按该节自举例外协调；既有数据/安装记录不按新项目重置。随后按授权清理临时源码。预览含 Trellis 互斥风险提示：检测到 Trellis 资产时列出共存影响，人确认后仍可安装。已存在项目数据存在即跳过；同名未知文件先报冲突，不能自动收编成框架资产；已存在的 `.wf-lock` 只在内容匹配 wf 锁标记时按运行态锁对象复用、不阻止安装；不匹配或不可读时按同名未知文件报冲突，由人决定移走或改名，安装器不覆盖、不接管其所有权；人选择保留该文件时安装不继续——`.wf-lock` 是固定保留路径，框架不提供改名的替代落点，冲突只能由人移走或改名解决。重复安装不得覆盖既有文件或绕过 §7.2 的本地偏离保护。**分支来源核对**：投放前若项目数据或同名框架资产在当前分支缺失、但在其他分支存在，按 §1.5 的需人裁决档报告具体分支名、推荐分支与继续条件；人确认后可在当前分支继续，按新安装处理，未确认前不继续投放。核对只用 §1.1 的分支边界与只读观测允许的只读查询。

**Git 就绪**：新项目在明确授权后 `git init`，仅按资产清单暂存骨架并产生首个 HEAD；README/LICENSE 等既有文件不自动卷入。无提交许可、Git 身份缺失或用户脏文件未处理时，只落盘并报告待就绪，尚不允许业务任务开工；不擅自设置身份或丢弃工作。已有仓库只加入获授权的 wf 文件；不再为全历史扫描建立安装锚点或二次自指登记。

**运行态忽略**：向 `.gitignore` 追加唯一 wf 托管段（覆盖运行态目录与锁对象 `.wf-lock`），重复运行核对已有段，不复制覆盖整文件；升级/卸载按段处理。卸载移除托管段时保留 `/.wf-lock` 一行，直到人手工清理锁文件后与该文件一并移除；保留行只忽略该文件，不构成项目指令或 hook。自检需确认运行态确被忽略，规则顺序被后续否定时报告具体匹配问题，不能只检查标记存在。

**安装自检**：投放后按发行清单核对目标框架资产的内容哈希，重装/保留的本地偏离须与已确认记录对应，并通过 §7.2 的发行集一致性核对 skill 路由、流程步骤可达与脚本接口；部分投放、无记录错配或必需步骤不可达时拒绝启用，保留明确重试/修复出口。另核对 §1.1 命令启动的常规引导及独立 repair/uninstall 在坏配置下仍可达、skill/调用权元数据、脚本/记录骨架、路径边界、未决冲突与运行态忽略；首次路由还须实际确认宿主可发现入口。清单区分必需与可选资产，未知按必需；必需资产缺失导致相关入口不可用，不能靠“人确认删除”假称功能完整。未知字段不作为已支持的证明。存量项目以 bootstrap 任务进入，既有流程照第 3 章共存，不自动探测其规范或改写其资产。

### 7.2 三方升级与偏离管理

**升级前置**：按 §4.4 预览/确认后在原互斥内重核无人持有、预览事实和工作区状态，取得具名维护写者及新代次后才应用；期间会话不得写入。活动任务均已暂停或未开工，挂起任务也须明确暂停；§4.4 收工保留的业务 WIP 不能仅因写权已释放就被升级豁免，先按 §4.2 完成实际处置，控制记录仍逐路径核对。按 §7.1 的分支来源核对再预览精确写入/删除范围，不改变任务/实例/绑定等业务数据；writer 只为本次维护控制按专门入口更新，不参与 O/L/N 替换。应用后按 §4.4 的维护变更持久化规则和 §5.3 写入操作结果、提交/待提交状态；无提交授权时释放维护所有权但不把变更归入后续任务，应用中断按 §5.4 保留维护事实并恢复。旧 schema 按 §5.3 解释，不借升级迁移/重置项目记录。用户定义/实例/绑定/写权均非发行替换对象；格式不兼容保留原文，阻断相关实例并给迁移预览及人确认出口；迁移走已授权数据任务，不阻断仍兼容的无关普通任务。

**发行身份（唯一定义）**：一个发行版本绑定不可变源提交与发行资产清单（路径、类型、内容哈希及兼容声明）。发行清单与 skill frontmatter 的描述等组件性字段只在一处定义，清单只登记路径与哈希，不在汇总层复制组件内容，避免两处定义漂移。相对上一发行，只要发行资产内容/路径/调用契约或清单改变，形成新发行时必须递增版本；未发布的日常编辑不要求每次 bump。同版号不同清单是身份冲突，拒绝当作普通升级。新版 N 以该固定清单的实际内容确定，版本号只作可发现标识，不能代替哈希或自动代表兼容；未正式可用的版本保持 `0.x.y`。发行登记由 authoring 侧专用发行 Git 引用及其目标提交内的资产清单共同承载：专用引用表达已发行版本并定位固定提交，清单校验该提交的版本/资产内容；引用命名与清单路径由机制设计固定，不另设含自身 SHA 的手写登记表。安装器接收人提供的确切专用发行引用，在已检出的本地发行仓库只读解析到提交并核对清单，不调用外部发布服务；裸 SHA、未登记引用或同版异内容均拒绝。源内容获取仍走第 3 章登记源；不把提交哈希写回同一提交制造自指，也不把引用名本身当内容/来源真实性证明。

**三方升级（唯一定义）**：每个已托管路径分别保留旧版发行模板 O、本地内容 L、新版模板 N 的身份/哈希；另保存已接受偏离（本地指纹、所见上游版本/指纹、原因）。偏离不改写 O，缺失登记不等于清除所有权依据。下表适用于新版仍包含的路径，按顺序匹配，每条资产/托管段独立处理；新版已删除的路径直接走表后的删除分支。

| 条件 | 动作 |
|---|---|
| 本地缺失，曾安装 | 先经 §7.1 的分支来源核对；确认是用户删除后尊重删除、不恢复；首次明确提示并由人登记，后续同态不重复；必需资产仍缺时报告 wf 功能不可用，不能称升级已恢复它 |
| 新增路径，本地不存在 | 预览后安装 |
| 新版新增路径在本地已存在、未属旧托管清单 | 先报所有权冲突，即使内容等于 N 也须人确认，不自动认领用户文件 |
| L = N | 内容无需写入，更新发行记录并清除已不成立的偏离 |
| L = O 且上游更新 | 安全更新为 N；没有上游变化则无动作 |
| 本地偏离且 N 与已确认上游内容相同、L 与已确认偏离相同 | 保留，不重复询问；记录本次版本观察 |
| 其他存在态，包括上游新增碰撞、本地再次改变、偏离遇到上游新内容 | 冲突：预览差异，人选择保留/恢复/合并；落盘裁决后更新相应记录 |

上游删除资产单独预览：只有本地等于旧发行内容且无用户新增内容才可作为可删候选；偏离或目录含未知文件则人裁决。资产移动按来源所有权与目标碰撞检查，目录先深后浅，不覆盖用户目的地；不因新路径被创建就丢失旧路径的偏离。裁决后重新核对实际状态，不重试含糊失败。

**资产完整性**：清单缺失/损坏或目标越界时拒绝写入与批量删除，保留诊断。按已安装发行版本重取原始模板可恢复发行依据，但不能凭远端通用清单推导本机曾投放的根与用户偏离；本地安装记录丢失时由人确认重建清单，再操作。旧发行引用不可取得且本地无可用 O 内容时，按 §1.5 输出阻断并给三个出口：人提供该发行副本、仅按已存哈希判定、放弃该路径的恢复；不猜造模板内容。路径按真实落点核对，禁止通过符号链接写出项目边界；登记的托管路径落在嵌套仓库根之下时按 §6.1 的仓库边界判断并拒绝安装/升级，不静默跳过（边界见 charter T3）。

**发行集一致性**：首次安装、升级和重装投放后统一核对 skill 路由、流程步骤及脚本接口能对应到同一兼容发行集。未解决的偏离/冲突导致某必需步骤不存在或不兼容时，不启用或推进依赖它的任务；报告具体对象并由人保留旧集或解决冲突，不以“文件都还在”冒充投放成功。项目特有约定与阈值仍读取项目数据，不能顺手覆盖配置来迎合新流程。投放中断按已落盘事实恢复一致发行集后再启用或恢复任务。

### 7.3 卸载与重装

**独立卸载**：单文件、仅标准库，不导入运行时、不解析任务或 spec；只读独立安装清单、必要资产状态和最小写权协调材料。正常可核验时按 §4.4 登记维护写者，在确认范围内执行并释放；原 writer 损坏/不可解析时保留原文，人明确确认所有其他写者已停止，在同一最小互斥范围内执行已预览的独立退出，不为卸载伪造代次或要求先修好任务/记录。此例外只允许卸载预览列出的资产/托管段（purge 另行确认），常规入口遇未知写权仍阻断；代次恢复无法证明时不能把该退出例外借给常规写入。无任务完成状态前置，活动/损坏任务可退出；默认卸载保留用户 WIP，涉及本地偏离资产或 `.wf/` 数据 purge 的处置另按专门预览由人决定，本条不授予删除许可。独立脚本和恢复说明随清单保留，脚本可从相应发行重取，源码入口使用显式目标。自定义执行器失效时按 §1.1 用系统或人显式选择的可用 Python 直接启动，不因运行时/配置损坏失去退出路径。

**默认卸载**：预览并只移除准确登记的框架资产与 `.gitignore` 托管段，但保留 `/.wf-lock` 一行（§7.1）；保留项目数据、安装/偏离记录和恢复材料。运行态锁对象不随卸载删除（删除锁路径会造成新旧文件对象并存，§4.4），预览须报告其存在、保留的忽略行，以及“确认无 wf 进程后手工清理锁文件并移除该行”的一步。资产被本地修改或同目录有用户文件时先报告并由人决定保留/移走/删除，不递归吞掉未知文件。卸载后普通开发可继续，wf 不留 hook 或项目指令阻断。

**purge**：显式人直调 `wf uninstall --purge` 才删除 `.wf/` 内项目数据；终端预览与令牌须覆盖数据丢失、备份位置与运行态锁对象的保留状态，模型不代跑。清单不可靠时不得猜删非本框架投放的 skill 根或用户文件；人可先取回清单/确认精确根后移除入口，再选择是否 purge 数据。维护互斥覆盖全部删除步骤；锁对象在 `.wf/` 之外（§4.4），删除项目数据不会让新进程另建一把锁。`.wf/writer.json` 等协调材料按预览保留到最后一步，与 `.wf/` 一同删除后，再由卸载入口在同一互斥内释放锁；锁文件本身不删除（§4.4），托管段按默认卸载保留 `/.wf-lock` 一行，预览须列出这一保留状态与人工清理步骤，核实预览目标已移除才结束互斥；最终删除后不重建空 writer，也不把它记为正常空闲。中断仍保留已落盘事实，不把含糊结果当成功。破坏性清空不是默认恢复手段。

**保留数据重装**：按 §4.4 维护写者和 §7.1 目标核验完成投放后，核验既有任务/schema/本地偏离及用户定义、实例快照、绑定和写入权，按 §4.4 从新会话显式接续原对象；运行态丢失不重置绑定或代次，损坏则先恢复；保留 WIP 仍按 §4.4 核对，不因重装换对象或消除归属；卸载期间的普通提交按外部变更处理，不要求补建任务。已修改资产仍按三方升级保护，重装不构成覆盖许可。离线且清单仍在时可按恢复说明人工移除自有入口；无法安全辨识则停在诊断，不能承诺无依据也能自动删净。

### 7.4 自带原语与改编

**原语集合**：grilling、tdd、diagnosing-bugs、code-review 随安装提供自有副本，不依赖全局同名 skills。按原语本身的任务触发条件加载，不一次读全库。

改编必须转成单会话顺序执行、工具直接取证，删除子代理派发与必需的外部 MCP/知识图谱前置；双轴检查保留独立结论。保留用户的动作授权与提交边界，不能 vendor 后继承上游“自动提交”等越权句。每副本登记来源、许可、基线、差异和最近正反例。

**审查适配交付**：§6.5 的成对审查参数与文件协议须同批验收；未交付时不得完成复杂任务：任务仍属复杂则按 §6.5 暂停或异常归档，确实缩范围变轻的才按 §4.3 降级并重新 Check。审查对取本框架自有副本（reviewer 侧与 action 侧各一），作为发行资产交付、纳入 §7.2 三方升级、随卸载移除；本仓库全局 `skills/multi-cli-review*` 只作一次性适配源，适配完成后由原产物按既有清理计划移除，清理不得早于自有副本投放与验收完成。自有副本须实现 §6.5 的暂存落点：reviewer 侧只写项目树外目录，导入由持写权的主会话完成；报告须产出对象锚点字段（Check 内容指纹、规划版本、相关 spec 与项目配置哈希）。两产物的协调记录进 authoring 来源/决策记录，不改写任一侧的验收要求。

### 7.5 上游监控与吸收

**来源登记**仅在 authoring 仓库：本框架当前发行源登记为 `ssh://git@forgejo.xzc.com/xzc/ai-coding-toolkit.git`，保持第 3 章的私有源选择，不因此开放任意源或本机 file 安装；发行引用与清单按 §7.2 核验。借鉴上游另登记仓库地址、基线提交/版本、许可/NOTICE、吸收内容、差异与裁决，使用稳定来源文件和不可变提交，不让任务归档造成断链。检查只报告变化，人决定跳过或吸收；发行前核对身份与版本递增。目标项目不自行跟上游、不运行后台监控；安装/升级只获取已裁决发行成果，不把上游下载或 MCP 查询放入 spec 写入链路。

### 8.2 必需的验收场景

三个隔离夹具：全新项目、存量无流程、存量有其他流程。每个夹具须给出初始状态、触发入口与预期输出（记录状态或三档输出三要素），缺任一项不算已定义。各跑正常任务与人为构造的拒绝，再做真实项目 dogfood。框架测试不得要求外部 MCP，目标项目仍可保留自身必要业务依赖。

**分轮验收**：首轮以最小安装/自检达到可运行状态为前提，再验证普通任务完整闭环、本地无 MCP 路径、会话绑定/暂停接续，形成最小可运行候选；第二轮覆盖定义准备/自举、多任务编排、依赖与中断恢复；第三轮完成安装/升级/退出的完整验收矩阵、全部适用三夹具场景及真实项目 dogfood/使用观察。每轮均检查已改变门禁及其正反例；初始化、批准、必要检查与复杂任务审查按实际对象照常执行，不因分轮省略。前轮通过不代表整框架通过，各场景标实际通过/失败/未运行；全部约定覆盖完成并经独立复核后才可声称实现可用。

无 MCP 夹具须覆盖新增/更新/拆分/合并/改名/删除、index 与元数据同步、本地验证、加载/过期处置、Check/Finish；不只是“文件可以手工编辑”。已知本地证据不足时标未核实，只对必要验证本身按规则阻断。

**夹具绑定**：场景表多数行三夹具均适用；夹具特有的验收面为——全新项目：表中“初始化自举”“Git 就绪”“准备定义与自举”“验证分时解析”四行；存量无流程：表中“extracted 生命周期”行与 §3 的存量 bootstrap 接入；存量有其他流程：表中“共存与重装”行（正例方向含其他流程提交经外部变更处置核对后无交集不阻断）。“无 MCP 全流程”至少在存量无流程夹具完整执行。三个夹具不得退化为同一套场景重复三遍；夹具特有的正反例缺失按该夹具验收未完成处理。

真实使用观察覆盖轻任务确认次数、命令/加载成本、跨会话正确率及暂停插单的准备/交接/恢复成本；另记录复杂任务每次审查发起所需 CLI 的实际可用/不足、阻断/等待时长，各宿主会话身份能力的核实结果与身份不可用导致的阻断次数与时长，以及未完成收工的关闭/恢复次数、人工核对/确认动作、耗时与结果。样本取自本任务审查声明、验证/交接及本地观察，不采集跨项目私有日志；计算可用率/恢复频率须列完整样本数与口径，缺失标未知，不以未记录当零。按 §1.3 会话绑定运行连续独立短任务/短实例时，还须记录每个对象结束后新开会话、调用 start、选择下一对象及重新加载上下文的实际次数与耗时；这些是当前固定绑定的使用成本，不预先认定可忽略，也不以更少动作单独当成功。每项结果标实际通过、失败或未运行，记录版本与环境。标为“未运行”或“放弃”的对象还须记原因分类（至少包括：因使用负担放弃、需求消失、场景不适用、外部阻塞、尚未安排）并记支撑该判断的依据（次数、耗时、等待或替代做法）；未给原因的“未运行”不作为场景“实际被放弃”的证据，也不进入缺口判断。临时控制模拟可用于设计推演，须区分模拟批准/人判、独立进程重载与实际人的操作/新 AI 会话，不能替代真实框架运行验收。尚未做这些验收时只称设计/实现候选，不称生产可用。观察结论的用途限于：作为 §8.3 候选行的可重议条件证据，或作为 charter T5 第 2 条判断“场景是否无法长期维持”的输入；不以成本单独构成新增理由，也不以成本删减承诺；环境不足或恢复负担不撤销 charter T4 的复杂审查承诺，也不自动新增放宽候选。候选重议依赖观察数据，dogfood 与观察应尽早启动，不推迟到全部验收完成。

### 8.3 候选与暂不采纳

以下不是执行门禁，按真实使用证据逐项裁决；表格同时是复审与清理的执行面。

| 条目 | 类型 | 依据与证据 | 可重议条件 |
|---|---|---|---|
| 固定会话绑定的显式解绑/重绑 | 候选 | 待 §8.2 的切换与加载成本观察；当前无数据 | §8.2 记录显示该绑定方式使连续短任务实际上被放弃，或多次切换引发接续错误 |
| setup 分轮问答形状、fog of war、ADR 三条件 | 候选 | 无，仅形状设想 | 现有规划/知识载体出现具体空白，先放入已有载体 |
| spec 证据分级与反例三元组编码 | 候选 | 现保留依据、最近反例与未核实说明；字段尚无消费需求 | 出现需要区分证据等级的判断冲突 |
| 人工介入六角色与加载样本成本比较 | 候选 | 仅用于 authoring dogfood，不采集跨项目私有日志、不引入调度 | dogfood 记录显示角色分工改变结论 |
| 更细的自动 lint 与清单孤儿项修剪 | 候选 | 现有纪律已覆盖同类风险，尚未出现漏检实例 | 出现漏检且人工检查重复失败 |
| 提交描述模板与复盘分类扩展 | 候选 | 原语改编验证中；脚本输出内嵌反例已纳入 §1.5，不另加普遍确认步骤 | 改编暴露描述或分类不足 |
| proof 型结构化验证停止条件、dogfood 三臂归因、幂等指纹编码 | 候选 | 无，待 dogfood 与机制设计 | dogfood 或机制设计给出真实证据 |
| D-1 跨流程一次性只读萃取 | 暂不采纳 | 与共存策略的边界冲突风险 | 人明确授权且有具体萃取对象与用途 |
| D-2 观察期与时间态 | 暂不采纳 | 无时间态需求，不设时间态以避免状态漂移 | 出现必须按时间触发且无法用事件替代的场景 |
| 术语表作为独立资产类 | 暂不采纳 | 现有 spec 可承载 | 出现跨包术语冲突且 spec 内联失效；届时先作为 spec 的“术语与命名约定”族起步，按第 0 章登记后再升格 |

**复审与清理**：自首个发行版本起（含 0.x.y 的预正式发行），每次发行版本递增（§7.2）或人发起时逐行复核；尚未发行、尚未登记发行身份的阶段不做机械判定，只按人发起复核；“长期无证据”指连续两次发行递增均未在依据列补充新证据，且无人主张该候选。依据列写观察结论、任务 id 或 §8.2 场景，没有证据时写“无，仅设想”，不写将来可能的用途。执行者只能标注证据状态，删除或改判由人按 charter T7.3 确认。

已明确授权的控制范围、批准、内容有效性、返工、知识准入、升级与本地 spec 契约均直接执行，不以候选项推迟。增强的准入、证据与停止条件见 charter T5、charter T6；边界外需求先按 charter T3 裁决：裁定为候选或暂不采纳的，由人按上表格式新增一行并填类型、依据与可重议条件，重提时从该行开始对照；尚未裁决的请求与裁定为直接不做的请求都不进入本表。本节候选的复审与清理按上面的复审规则执行，不作为待办池。
