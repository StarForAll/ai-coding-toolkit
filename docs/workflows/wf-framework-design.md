# wf 框架设计

> wf 是一个**独立的单人流程控制框架**：以 skill 为核心、agent 无关、主动触发。
> 本文件回答三件事：它是什么（§1–§2）、在什么背景下用（§3）、包含哪些功能（§4–§7）；
> 机制细节与实现方案由后续实现文档承载，本文件不规定具体文件、命令与代码。

## 0. 与同仓库 "wf" 前缀文档的关系

本仓库 `docs/workflows/` 下另有一组 **Trellis 内嵌 wf 模块**的文档（[workflow-design.md](./workflow-design.md)、[workflow-implementation.md](./workflow-implementation.md)、[wf-variant.md](./wf-variant.md)）：那是把 wf 语义装进 `.trellis/` 基底的**早期落地形态**（命令 `wf route` / `wf close`、账本 `.trellis/dependencies/ledger.json`），与本文的**独立框架**是两个产物，共用 `wf` 前缀与相近命令名纯属渊源。关系按"**先建后定**"处理：独立框架（本文）先建成，内嵌模块的去留待框架稳定后再决；现阶段两者并存、互不修改，本文的依赖语义与审查契约均以概念同源的方式吸收自该组文档，而非复制其实现。命名冲突的最终裁决（改名 / 合并 / 退役内嵌模块）是框架稳定后的独立决策，不在本文件内预定结论。

**本文件的维护纪律**（设计文档自身，不是 wf 机制）：

1. **外部事实断言须带来源**：凡断言外部事实（平台行为、上游契约、安装 / 卸载默认、本机实测），须注明来源（文件:行 / 命令 / 日期 / 会话证据位置），未核实的标 `[未核实]` 并在实现前核实——"核过"与"记得"在正文里必须可分辨（历史印证：F1 类平台事实错误存活九轮即此根因）；
2. **修订后由未参与修订的会话重审一遍**：修订者不能自证——§7.4 验收纪律对本文档自身的推广；十轮自审漏掉的实质缺陷由外部审查命中即实证；
3. 修订史进 git 提交记录与任务档案，不进 frontmatter（`status` 保持一行 + 指针）；**设计期机检器已建成并对当前基线跑通**（`scripts/validate-wf-design.py`）——**"跑通"的定义 = 四条检查通过 且 覆盖率达标**（定义命中率、消费点命中率 ≥ 90% 阈值，引用检查残差输出不设阈值——校验器必须断言并输出自己的覆盖面，校验器自身的漏检没有更上层能发现，"网眼开在静默侧等于没有网"对校验器本身同样成立）。其后的**每轮修订以机检器通过为收尾条件**（不通过即修订未完成）；**非 P1 的改进诉求进候选清单**（§8 第 7 项），不直接改正文。问题的性质已从"认知缺口"转为"执行带宽缺口"——治理面（§1.3 单一登记表）+ 索引表（`wf-framework-design.index.md`）+ 机检器三者是把"防漂移"从纪律的自我引用升级为机械校验的出口。

## 1. 定位陈述

**一句话**：wf 是一个不依赖任何 agent 宿主运行时特性的单人流程控制框架——想用就显式调用它的 start skill，装在任何 agent、任何项目（新建或存量）里即用；它管理单任务生命周期、沉淀 spec、在多任务场景下用依赖图保障顺序。

### 1.1 定位原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **skill 为核心，agent 无关** | skill 是唯一接口与控制层。允许携带两类实现件：①**skill 指示调用的普通脚本**（stdlib-only Python 等）；②**人直调实现件**——仅限四个入口：`install`（首次安装时 skill 尚不存在，天然人直调）、`upgrade --apply`、`wf repair`、`uninstall --purge`（后三者在交互式终端直调 + 令牌确认，模型不得代跑，见 §5.5、§7）。**禁止**的是 hook、常驻进程、平台分支逻辑 |
| 2 | **主动触发制** | 必须由人显式调用 start skill 才生效；不调用即等于不存在。不写 AGENTS.md 提示、不做任何后台或被动触发。一旦启用即严格遵循（强度按 §1.5 分级） |
| 3 | **通用层 `.wf/`** | 一切状态、任务、spec、依赖信息存放在目标项目内的 `.wf/` 目录；不依赖任何特定 agent 的机制。任何 agent 调用入口后自行读取所需上下文——多 CLI 信息共享由此解决 |
| 4 | **独立框架** | 不是 Trellis 的 fork，不依赖任何基底。机制层借鉴其已验证的骨架；复杂度上剔除多平台适配、团队功能、分发 CLI（边界划定见 §1.4） |

**权威关系**：skill 正文是**唯一指令源**；`.wf/` 内的流程文档只承载步骤详情与索引（供 skill 指示读取），不承载第二套指令——防止两份"流程正文"长期分裂（正是 §6.1 反对的入口分裂）。

**skill 正文的份额纪律**：skill 正文只承载纪律、路由与触发判据（含各入口的防误触声明与 description 口径），不承载步骤详情。skill 正文膨胀成第二份流程文档，是 §6.1 反对的入口分裂在框架自身的形态。参照上游实测：Trellis 每轮注入仅几十字、skills 仓库的 implement skill 正文仅 9 行——skill 的价值在短而准，不在全。

**原则 2 的精确语义与降级链**："人显式调用"由 skill 调用权字段承载（§1.3），不是口头期望。框架自身不发起任何被动触达：不写 AGENTS.md、不装 hook、不设后台提醒。换新会话后是否启用 wf，完全由人是否调用 start 决定——这是有意设计，不是缺陷。

调用权字段在**不识别该字段的宿主上会被静默忽略**，此时"只能人调用"退化为三层兜底，**分层诚实声明**（不许把约定说成机制）：

1. ① start 正文首句自带"本 skill 只有被人显式调用才生效；被模型自行加载时，输出提示并停止"——**约定层**；
2. ② `wf-continue` / `wf-spec-update` 首步自检（§1.3）——**机制层，但只覆盖这两个 skill 自身**：自检内容是"`.wf/` 内存在有效活动任务指针"（§1.3 唯一定义），无指针即拒绝工作。它不依赖宿主，但**不覆盖 user-invoked 的 skill**（start / finish / bootstrap 的防误触只剩①与③），也不覆盖"从未 start 的项目里指针被手改伪造"的场景（伪造指针属 §1.5 第四行"不可防（可发现）"的越轨面）；
3. ③ 这两个 model-invoked skill 的 description 必须写明"仅在 wf 会话内使用"（description 是模型可见面，口径与调用权同步维护）——**约定层**。

三层合起来的诚实边界：**从未 start 的项目里，模型误拉起 model-invoked skill 会被②挡住；误拉起 user-invoked skill 只能靠①③的措辞约束**。②是唯一不依赖宿主的机制兜底，其覆盖面以此为限，不夸大。

### 1.2 适配面最小集（唯一允许的平台面）

"人显式调用"与"skill 能被发现"在事实层面各需要一小块宿主适配，无法归零。wf 承认并**仅限**以下两项：

| 适配项 | 内容 | 位置 |
|---|---|---|
| **skill 根投放** | 把 `wf-*` skill 目录放进目标项目实际使用的各 agent 的 skill 根。**默认投 `.agents/skills/`**（共享根：Codex、Gemini CLI、Pi、Kimi Code、DSH 等写入；支持 agentskills.io 的工具也可读，但**不假定每个平台都读**——本机 ZCode 实测可读〔2026-10-30 会话证据：ZCode 会话加载了项目 `.agents/skills/` 下的 skill，会话上下文可见；平台表另记 ZCode 托管根为 `.zcode/skills/`，见 `.claude/skills/trellis-meta/references/platform-files/platform-map.md`〕）。**安装时由人声明实际使用的 CLI 清单**，安装器按清单为各 CLI 追加其专属根（如 Claude Code → `.claude/skills/`、ZCode → `.zcode/skills/`——Trellis 托管 skill 的既有先例）。清单外的平台不做投放，运行时无任何平台条件逻辑 | 目标项目 |
| **frontmatter 调用权字段** | user-invoked skill 携带宿主识别的调用权声明（如 `disable-model-invocation: true`；有对应机制的宿主配 `policy.allow_implicit_invocation: false`）。两个字段保持同步：一个 skill 在所有宿主上同为 user-invoked 或同为 model-invoked。不识别该字段的宿主按 §1.1 降级链处理 | skill frontmatter |

除上表外，任何"为某平台做分支"的做法都在禁止之列。frontmatter 的**技能**字段只用最小集（`name` + `description`），未知字段静默忽略（调用权字段是唯一例外：它不被识别时必须有 §1.1 的降级路径，不能只是"忽略"）。**skill frontmatter 必须可解析**（YAML 语法错误会使 skill 被加载器静默跳过——上游实测教训：skills 仓库 #911，6 个 skill 因 description 未加引号长期不可用才发现）；`装完自检`（§7.1）以此为一项。spec frontmatter 的字段集独立于本条，见 §6.1。

### 1.3 调用权分层（编排拓扑的唯一规则）

沿 skills 仓库的 user-invoked / model-invoked 二分：

| skill | 调用权 | 生效条件 |
|---|---|---|
| `wf-start` | **user-invoked** | 人显式调用才生效；正文首句自带防误触声明（§1.1 降级链） |
| `wf-finish` | **user-invoked** | 人显式调用；"完成 = 人判 + 归档"中的人判由调用权直接承载——模型不能自行收尾任何任务 |
| `wf-continue` | model-invoked | **首步自检**：读 `.wf/` 无**有效活动任务指针**（§1.3 唯一定义）→ 输出"请先运行 `/wf-start`"并停止，不做任何路由、不读任务细节。自检通过才继续 |
| `wf-spec-update` | model-invoked | 同上首步自检；由 finish 流程指示调用 |
| `wf-bootstrap` | user-invoked | 存量项目一次性初始化，人发起 |

**机制名登记**：以下机制名**不是 skill**——它们是机制入口命令（脚本命令或命令模式），由 skill 指示调用或人直调，不在本表登记调用权。**本文出现的全部机制名以此为完整清单**，按**写者职能**分三类列出（**计数不硬编码**——新增机制名必须同步登记本节或 §1.1，并按"完整/唯一/仅限声明随新增项复核"的纪律回扫相关规则句）：

- **日常流转命令**（skill 指示调用，含全部判定字段写者）：建任务带前置、开工（记任务基线提交，§4.2）、建边、删边、返工实施、替换实施（含继任者继承路径字段写入，§5.6）、放弃实施、Check 结果写入（受控取值 + 触碰路径指纹）、策展清单写入（含 spec 内容哈希，§6.2）、`wf spec --file <path>`（读取 + 运行态留痕：写读取留痕侧车（§5.3），**非判定字段写者**——不触碰任务记录，§6.2）、审查结论写入、spec 处置留痕写入、归档（含基线移交）、归属裁决写入（未归属提交的人裁归属，§4.2）、**框架资产豁免确认写入（抑制型登记，两类条目：提交豁免 / 缺失豁免，属人确认通道，§4.2/§5.3/§6.1）**、`wf-baseline`（基线变更通道，§4.2）；
- **人直调命令**（§1.1 第二类）：`install`、`upgrade --apply`、`wf repair`（§5.5）、`uninstall --purge`、安装锚点登记（安装 / bootstrap 入口登记扫描下界，§4.2/§7.1——接入流程的人直调步骤，非 skill 指示调用）；
- **只读查询命令**（skill 指示调用，无副作用）：（当前无成员——`wf spec` 已升级为"读取 + 运行态留痕"，移入日常流转类；后续新增只读命令入此类，本清单随之扩充。）

**机制登记与回扫协议（单一登记表，唯一定义）**：新增或修订任何机制（判定字段 / 状态值 / 登记类 / 机制名 / 产物类）时，按**一张登记表**逐行核对并落盘——通用行（每个机制必答）+ 条件行（命中条件才答）；不再另设并列清单（治理面增殖超过人工同步带宽的教训见下）：

| 行 | 何时必答 | 落点 |
|---|---|---|
| ① 写者纪律表 | 通用：新增任何字段 / 登记 / 产物类 | §5.3 |
| ② 记录分类（记录 vs 运行态） | 通用：同上——它落哪一类、是否入判定字段 | §5.3 二分 |
| ③ 机制名清单 | 通用：新增机制名 / 命令 | 本节 |
| ④ 引用核验对象 | 通用：该量持有引用 | §5.4 |
| ⑤ 可发现面输出 | 通用：它的缺失 / 首次出现需要输出 | §1.5 |
| ⑥ 组合识别 | 通用：它参与非法组合 | §5.4 |
| ⑦ 变更影响面自问 | 通用：**本条修订是否改变了既有命令的副作用或语义**（不新增机制名、不新增字段的那类变更也算——如 install 从"复制文件"变为"git init + 提交"） | 若按 §1.3 单一登记表⑦行"变更影响面自问"命中，用唯一定义索引表（`wf-framework-design.index.md`，已建最小版）的消费点列反查全部受影响条款（提交分类 / 引用语义 / 骨架内容都在射程内；索引表是"新增阶段登记表"兼"修复阶段反查工具"的唯一落点） |
| 抑制型四处 + 沉降 | **条件**：它属抑制型产物 | §1.3 证据面 9 / §4.2 |
| 状态 × 操作矩阵 | **条件**：它是状态值 / 标记 | §1.3 证据面 3 |
| 路由位置 | **条件**：它改变入口指引 | §4.1 |
| 术语 | **条件**：同一实体有多个称呼 | §1.4 |
| 门禁 / 校验定义 | **条件**：它触碰判定 | §6.5 |

任一必答行未回答即视为机制未成立，不得写入正文。**本表是登记协议的唯一形态**——历史印证：第十轮四个新机制各漏一面（安装锚点漏①②、指针运行态漏⑥、spec_sha 漏①④、用户删除态漏⑤与抑制型登记），第十一轮修复"用户删除态漏⑤"时又漏⑤（可发现面清单）——同一轮修订要人工同步多处清单，漏一处即静默缺项，多清单并列正是温床（R5 根因）；单表 + 机检器（§8 第 0 项**只认本表**）是其解。**九类证据面（下）是修订回扫的核对方法，本表是核对结果的落点索引——两者由机检器统一消费，不互相替代**。

**修订时另须并排核对九类证据面**（回扫清单的组成部分，缺一即回扫不完整——防"压缩式继承"丢条件）：

1. **源条件并排**：凡压缩改写自 workflow-design.md 的判据句，与源句并排核对**全部条件项**（逐条列出，不许摘要合并）——"读起来更强势的转述"往往是丢掉保护条件的信号；
2. **定义与消费核对**：凡点名外部 skill / 资产，读其**现行正文**核实路径、参数与目录约定，不凭记忆或"同源"印象断言形状；**凡断言外部事实**（平台行为、上游契约、安装 / 卸载默认、本机实测），**须带来源**（文件:行 / 命令 / 日期 / 会话证据位置），未核实的标 `[未核实]` 并在实现前核实——"核过"与"记得"在正文里必须可分辨（历史印证：F1 类平台事实错误存活九轮即此根因；第十轮顺手写"本机 ZCode 实测可读"未带证据位置是同一根因的复发，已按本条补正）；**同一量（派生量、集合、判据）只允许一个构造语句**——公式之外出现"初始化为 / 追加 / 特例构造"该量的语句即为第二定义点，回扫时按违规处理（消费点用错只是行为不一致，再定义点会让"唯一定义"名存实亡）；
3. **状态 × 操作矩阵**：状态字段（挂起标记、暂停标记、异常终态标记与指向、返工来源）× 操作（**归档、替换、放弃、删边、返工加边、挂起清除、指针切换**——七操作全覆盖，不许只对其中几个操作成立）逐一核对收尾语义；
4. **规则 × 场景叠加**：两条各自自洽的规则叠加到同一场景时是否仍成立——单工作线场景至少核对四个组合：**返工叠加**（任务挂起期间其他任务的提交，会不会混进被挂起任务的触碰路径/指纹——§4.2 任务归属按提交 trailer 判定即为解）、**交替叠加**（未收尾任务切换后，归档顺序会不会被指纹一致性约束逼成固定次序——§4.2 指纹按归属而非时间区间判定即为解）、**归属交叉**（未提交/未标记改动对下游判定的串味——§4.2 干净门禁与未归属提交处置即为解）、**替换叠加**（旧任务异常归档后，其已提交路径还在不在任何消费面内——§5.6 替换实施的路径继承即为解）。状态×操作矩阵只能校验单规则自洽，叠加缺陷须独立核对；
5. **裁决沉降**：凡"由人裁决"型机制（资产冲突、归属裁决、repair 目标态、降级确认），核对裁决结果是否落盘并改变后续判定的输入（decision-without-persistence 禁止——只解决当下这一次、下次还报同一件事的裁决，会在几轮之后退化为例行确认）；

6. **补集核对**：凡定义了一个分类（提交归属、任务状态、机制操作、裁决类型、Check / 审查结论取值、**升级对账的资产变更类型**），必须显式回答"**不属于任何类别的元素如何处置**"，并给出扫描/判定时的 catch-all 规则。**补集答案必须是覆盖式的（全集断言 + 划分不重不漏），不是成员枚举**——枚举的反面永远还有一面：每补一个例外就暴露两个新例外。历史印证：状态机曾缺"项目终态"（状态补集）、操作矩阵曾缺"返工加边/挂起清除"（操作补集）、提交归属曾缺"系统提交"（归属补集）、后者的答案曾用枚举又漏"空窗期提交"、升级对账曾缺"用户已删除"（资产变更补集，§6.1 第三态）——历次都是补集未定义或未全覆盖。
7. **新规则自检（立规处自检）**：每写一条"从此以后 X 必须满足 Y"的纪律，**立即用 Y 检查写下这条纪律的那一段本身一次**——人写规则时注意力在旧问题上，天然不会用新规则审自己，因此这一步必须显式执行且可机械检查。**自检对象 = 新规则句 + 它落盘的容器**（表格、清单、章节）：第九轮立"抑制型产物四处登记"时只检了规则句，漏了承载它的写者纪律表自身出现两行同名登记——容器失检使"该产物在表内登记几处"的计数失效，即本教训的实例。必查两项：①新公式是否包含该段其余语句所需的**全部项**（漏项会让同一段的两句话自相矛盾，且静默失效）；②新覆盖断言的**两个端点是否只在一处定义**（两处定义且含无承载的从句时，实现必然退化为未覆盖）。历史印证：第六轮立"派生量只允许一个构造语句"时该公式自身漏了"裁决提交的归属"项；同轮立"补集必须覆盖式"时该区间在两处定义不一且第二处含无水位字段承载的从句——两次都是刚立的规则自己违反了自己。
8. **静默侧清单的失败方向**：凡由"新增成员"扩展的枚举集合（可发现面输出清单、机制名清单、判定字段清单、引用核验对象、裁决类型、check / 审查结论取值），其漏项后果分两侧——**会吵的一侧**（漏项落进"违规/未登记"→ 报错或阻断）不会累积；**静默的一侧**（漏项被跳过、不告警、不核验）必然漂移。因此每个枚举集合必须二选一：给出**覆盖式定义**（全集 + 划分不重不漏），或给出**"未登记即失败"的失败方向**（未登记的引用 → 启动校验直接报错；未登记的写者 → 写入拒绝；未登记的输出 → 先告警再沉降，不许无声跳过）。**核验对象集合优先按类型覆盖而非枚举**——它是发现悬空引用的唯一一道网。可复用判句：网眼开在静默侧等于没有网。
9. **抑制型产物的登记纪律**：凡其存在会**关闭**某项检查或告警的产物（豁免清单、已确认登记、白名单、跳过标记、抑制型字段），与触发型产物（告警、门禁、阻断）的危险性**不对称**：触发型漏登记 → 该发生的没发生 → 会吵、很快被发现；抑制型漏登记 → **该发生的没发生且无任何信号**，即"漏登记"本身就是一次静默失效。因此抑制型产物必须同时登记于**四处**（写者纪律表 §5.3——谁可写该产物类 / 豁免分级引用 §4.2——该产物抑制哪个检查与何时沉降 / 机制名清单 §1.3——产生它的写入命令已登记 / 引用核验对象 §5.4——其持有的提交哈希被核验；**四处是四个互不重叠的文档与核验面，不以同一表格的两行充数**），**四处任一缺失即视为该产物无效，不得据其抑制任何输出**；写者限定为人直调入口或人确认后的入口脚本，AI 不得写入，且不得由任务记录承载。可复用判句：先给失败定方向，再谈规则内容。


不变量：**user-invoked skill 永不可被任何其他 skill 调用**（包括以 Skill 工具点名方式；在识别调用权字段的宿主上由宿主保证，不识别的宿主上由 §1.1 降级链保证）；user-invoked 可以在其正文中指示调用 model-invoked；model-invoked 之间不互相编排（原语只被编排层指示加载，原语之间不互相调用）。当某步骤的前置是 user-invoked skill 时，措辞必须是"请人运行 `/wf-xxx`"，不得写成对模型的调用指令。

**两个基础定义**（多处门禁的依赖，在此唯一定义）：

- **活动任务指针**：单数。`.wf/` 内记录的"当前正在执行的任务"（存储属运行态，gitignore，§5.3 二分），由 start / 开工命令登记、归档与放弃时清除；**有效 = 指向未归档且记录可解析的任务**，指向已归档、不可解析或非法状态时视为无活动任务。**指针切换**：人可在 start / 开工命令中显式切换到另一就绪任务；被切走的任务若处于执行中，自动记暂停标记（含切换原因），恢复由人清除——不留"两个 in_progress 并行"的假象。**例外**：被切走的是**挂起任务时不记暂停**（挂起本身就是等待语义，§5.4 挂起路由的特例）。**切换前置：工作区干净门禁**（§4.2）；
- **活动任务集**：全部未归档任务的集合（可多个）。continue 的首步自检查**指针**；就绪选择（§5.6）在**无有效指针**时从活动任务集运算；升级前置（§7.2）要求活动任务集为空或全部暂停。

**任务状态取值集（唯一定义）**：`未开工` / `执行中` / `已归档`（三值）。**源对照（带来源）**：workflow-design.md §4.2 为**正式三值表**——"任务状态由基底表达：规划中 / 进行中 / 已归档。只有这三个值"——wf 的"未开工 / 执行中"是**术语改名**（规划中→未开工、进行中→执行中，语义不变），改名登记于 §1.4 来源修正；源另设"依赖状态"维度（无记录 / 挂起 / 正常 / 异常，账本侧表达）——wf 中其对应物由前置集合派生（满足判定，§5.1）与挂起 / 异常终态标记（§5.3）承载，不设独立状态字段。挂起 / 暂停 / 异常终态是**独立标记**（非状态值，§5.3 判定字段）；**阶段位置**（Plan / Execute / Check / Finish，§4.2）是另一字段。就绪判定与指针推导（本节）消费状态与标记的**组合**（非法组合由 §5.4 组合识别捕获）。

model-invoked skill 的 description 统一口径："仅在 wf 会话内使用"——description 是模型决定是否自动加载的唯一依据，必须把边界写进去，防止无关会话（如同一项目里的 Trellis 会话，`.agents/skills/` 为两边共用）误触发。

措辞约定：本文所有"指示"均指 skill 正文中的指令句，由模型读到后遵行；不存在任何 hook 或注入通道。

### 1.4 与上游项目的关系（借鉴与边界）

**吸收的骨架**（已在 Trellis 中被验证）：

- markdown 定义流程，脚本只做解析器（流程改动不改代码）；
- 任务状态字段驱动的阶段状态机；步骤带 `[required · once|repeatable]` 标记——required 不可跳过、可重复；`[once]` 步骤在产物已存在时跳过；
- **建任务许可 ≠ 实现许可**：批准建任务只进入规划，实现要等开工门禁通过之后；
- spec 体系的 index 三段式（索引表 + 开发前 checklist + 质量检查），且**索引只是指针**——索引行不含规则正文，加载必须落到 spec 文件本身；
- spec 更新作为收尾必经步骤；Trellis update-spec skill 的结构化输出模板（签名、契约、校验与错误矩阵、Good/Base/Bad 对照、断言点）——wf 的对应承载是 `wf-spec-update`；
- 紧凑注入原则（只给状态与索引，详情按需拉取）；
- 任务归档分月目录（`archive/{YYYY-MM}/`）；
- **记录不可读时的处置口径**（`task_error` 面包屑的教训）：不新建任务、保留既有字段、判不准就问人——落到 §5.4；
- **check 阶段审查契约的流程形状**（workflow-implementation.md §8.5：任务标识入参、轮次目录、检查面五项、结论两档、上限 2 轮、unavailable 留痕）——wf 的审查机制（§6.5）与其流程形状同源对齐；**目录与参数形状以全局 skill 的实际契约为准，差异由 §2.2 的适配清单闭合**（适配全部加性、skill 零改动），不以"同源"为由跳过核实。

**来源修正**：本框架的**依赖语义概念集**（前置集合、就绪/阻塞、返工挂起、替换/放弃前向、归档终态）来自本项目 workflow-design.md 的设计，**Trellis 没有对应实施可参照**——它明确声明任务树不是依赖系统（`workflow.md`），要顺序就写进 PRD。Trellis 在此只提供反例证据（不做什么），不提供正面先例。**判据的源语义以 workflow-design.md 为准，压缩不得改变语义**（回扫纪律见 §1.3）。**术语改名登记**：任务状态三值在源中为"规划中 / 进行中 / 已归档"（§4.2 正式三值表），wf 改名"未开工 / 执行中 / 已归档"（§1.3 取值集）——语义不变，仅措辞统一；源另设的"依赖状态"维度（无记录 / 挂起 / 正常 / 异常）在 wf 中由前置集合派生与挂起 / 异常终态标记承载，不设独立状态字段。核心判据的完整源条件清单：

- **依赖满足**（源 §4.3）：前置任务已归档 ∧ 该前置终态为正常；
- **归档终态约束**（源 §4.4 表后段）：已归档任务终态只能是"正常"或"异常"；**"正常"要求该任务的前置集合全部满足**——本文 §5.1 / §6.5 为其落点；
- **挂起清除**（源 §6.4 第 5 步）：T 未归档 ∧ T 挂起 ∧ 无未完成返工登记（wf 无登记窗口机制，对应物为返工集合无未归档成员）∧ 返工集合非空 ∧ 集合无未归档成员 ∧ T 前置集合全部满足——本文 §5.6 步 5 是其完整压缩，五条件一项不减；
- **检查与完成**（源 §4.3）：完成 = 实施与检查完成 ∧ 人判 ∧ 已归档；检查不要求 sha 级证据（wf 的对应强化为 §4.2 触碰路径指纹——结构层的最小证据，不构成证据链）。

**不吸收的复杂度**（为多平台 / 团队 / 分发付出的部分）及其与自建机制的分界：

- 多平台目录拷贝、平台探测、差异分支、回归测试矩阵（§1.2 的最小适配面是全部）；
- 团队功能：developer 身份、assignee / priority、多人 workspace、Linear 同步、PR 流程；
- channel 多代理协作运行时、跨平台会话记忆；
- 四层工作流变体解析链（wf 只有一层：全局主干 + 任务级开关）；
- 会话隔离身份梯子与会话票据（Trellis 的 shell-ticket：会话身份桥接机制，与本文的"spec 提醒行"无关，见 §6.2 术语区分）——单会话当前任务指针即可；
- **整个分发 CLI**。边界分界：wf 自带一个**小型升级对账脚本**（版本文件 + 框架资产清单哈希，见 §7.2）——它服务于单项目、单版本升级、单目录资产，不含跨平台矩阵、模板迁移系统、marketplace 与发布链路。这个量级的脚本属实现件，不构成"吸收分发 CLI"。**卸载默认保留数据**与 Trellis 相反（Trellis 卸载默认连 spec / tasks / journal 全删）——这是 wf 的有意改进，不是先例继承，实现时勿去 Trellis 找参照。

### 1.5 强制力模型（诚实分级）

| 想防的事 | 分级 | 机制 |
|---|---|---|
| 缺产物的任务开工、前置未满足就开工/收尾、check 结果非 pass 时 finish 被拒绝、review 结论非 pass 且无留痕时 finish 被拒绝 | **机制保障（正常使用）**〔自建门禁，无上游先例：Trellis 的 `start` 只卡 jsonl 策展且 `--allow-empty-context` 可绕过，`create` 缺 PRD 时自动生成默认内容——产物存在性门禁是 wf 自己造的，校验对象见 §4.2/§6.5〕 | 开工 / 收尾入口的脚本门禁 fail-closed，校验对象为受控取值与结构化产物 |
| 会话中间静默跳步、范围溢出 | **纪律 + 事后可发现** | 主干判据 checklist（§4.2）+ 下次入口校验发现结构性越轨并阻断 |
| AI 谎称完成 / 代写人判 | **只留痕，结构性不可防** | 谎称完成的外壳（全勾 checklist + 伪造 check 摘要）与正常完成**完全同形**，任何无 hook 的校验都无法区分。完成的真实性由 finish 的人敲调用权与人判承载，框架不担保。**无 hook 上限的论证**（沿 mcode-stack）："必须强制的规则归 hook，不归 memory"——wf 无 hook，故其强制力上限就是"状态门禁 + 留痕"，不假装更强 |
| 绕过入口直改状态文件 | **不可防（可发现）** | 启动一致性校验（§5.4）+ finish 门禁的写入标记核对（§6.5 第 6 项）双重发现；写者纪律（§5.3）缩小可利用面；"不防对抗" |

口径：**结构性越轨可发现，语义越轨不可发现**。这是无 hook、无拦截层的诚实代价，与 workflow-design.md §1.3"只防意外，不防对抗"同口径。审查与 check 的门禁**永远校验结构性齐备（受控取值、产物存在），不向证据链方向演进**——这是本设计的硬边界，防止"让机制显得更强"的漂移。

**阻断统一协议**（所有门禁的"报告并阻断"都遵守，缺一即不完整）：

1. **原因码**：违反了哪条规则（引用本文章节）；
2. **决定性事实**：校验读到了什么（缺失的产物、未满足的前置、非法的状态组合）；
3. **下一步出口**：要解除阻断该做什么（补产物 / 走 repair / 走返工 / 找人判）。

输出中任务一律以"**任务名（含 id）**"呈现（如 `构建登录接口（10-30-xxx）`），不出裸 id 墙——纯 id 序列人读不可辨，名字包裹 id 是上游验证过的呈现纪律。

**可发现面输出清单**（"未生效必须喊出来"的落地枚举，触发即输出 `[WARN]` 行，不留在姿态层；**清单条目可与阻断并存**——同一事实既触发可发现面输出、也可触发门禁拒绝，如指纹失配既是本清单项又触发 finish 门禁第 1 项拒绝）：spec 超预算被截断、glob 非法（按条失效，§6.1）、**spec 提醒行（wf 对上游 "spec ticket" 概念的对应物：指向 spec 文件的一行短提醒，见 §6.2 降级链；与 Trellis 的会话票据 shell-ticket 无关）被预算挤掉**、汇总行被预算挤掉、review 走 unavailable 回退、check 有未跑项、**框架资产提交（首次出现告警，人确认后记入已登记项、后续跳过，§4.2 豁免分级与沉降）**、**check 指纹失配（Check 之后触碰路径又被修改，证据过期，§4.2）**、spec 命中过期未刷新、**spec 内容与策展记录哈希不符（须重读，§6.2）**、**框架资产缺失（首次出现，升级按用户删除处置，§6.1/§5.4）**。**清单外输出一律视为未登记违规**（失败方向见 §1.3 证据面 8——网眼开在静默侧等于没有网）；新增条目需给触发判据并登记本清单——只在别处写"WARN"而不登记本清单，属"纪律写了、容器没改"（§1.3 证据面 7，第十一轮 G4 即第二次同型复发）。

配套姿态：

- **未知从严**——无法证明是只读的操作按写处理；
- **未生效必须喊出来**——任何机制未生效时必须在输出中声明（按上表清单），不许静默降级、不许以"基本完成"收场。失败即失败：报告失败必须含失败命令、关键错误、影响与下一步，不许讲成"基本通过"；
- **新机制四问**（改编自 stop-that-shit 的 Stop Ladder 第 4 步及其相邻段落的重述；上游历史名"防御四问"）：想新增一个机制时先回答——它检测什么？触发后改变什么？缺证据时如何处置？删掉它会破坏哪条现存承诺？四问答不上来的机制不加。

## 2. 边界

### 2.1 边界内

- 单任务生命周期（Plan → Execute → Check → Finish，含按需模块与段内回退）；
- spec 沉淀、加载、过期与回收治理；
- 依赖机制 / 任务图（多任务场景）；
- 安装 / 升级 / 卸载（含与既有流程的共存策略）；
- authoring 仓库侧的上游监控与吸收。

### 2.2 边界外

- 团队协作与审批流；
- 跨机并发、多机身份隔离；
- **同一工作区的并发会话**（单指针 + 干净门禁在并发下互相踩：A 切走指针、B 的指纹与基线随之错位；wf 声明不支持且**不做运行时检测**——锁需要过期判据（崩溃残留的 stale lock），为单人自发的罕见场景引入常驻判定面，性价比低；属结构性不可防，与 §1.5 的诚实口径一致）；
- 多分支与合入调度、跨项目依赖；
- 任务调度与并行派发、**子代理派发**（明确不考虑；vendor 原语的改编纪律见 §7.4）；
- 会话中间实时拦截（无 hook，见 §1.5）；
- 对外发布 / 分发到他人环境（自用框架，经私有 forgejo 远端安装）；
- 管理或修改其他流程控制框架的资产（共存边界见 §3）。

**已知外部依赖与适配责任**（唯一的例外，属有意决策）：多 agent 审查建立在全局 `multi-cli-review` / `multi-cli-review-action` 成对 skill 上，需按 wf 契约做**加性适配**（清单见 §6.5 与 §8）。**适配全部加性、skill 零改动**——报告目录的隔离不经改写该 skill 的目录契约达成，而是经 `--task-dir` 参数指向嵌套子目录：wf 传 `--task-dir {task-dir}/review/`，该 skill 的现行输出契约 `{task-dir}/review-round-{N}/{reviewer-id}.md` 使产物自然落 `{task-dir}/review/review-round-{N}/{reviewer-id}.md`——嵌套目的达成，skill 的规范路径、参数与全部 task-level 用法不变。适配的具体项：①**`--task-id` 新增参数**（reviewer 与 action 两侧同加；该 skill 现行契约**无此参数**，但其 reviewer frontmatter 已要求 `task-id` 字段且无入参可传——此参数补上的是**现行契约缺失的传值通道**，不是锦上添花的可选便利项；提供时写进报告 frontmatter，不提供时维持该 skill 现行的目录名推断）；②**wf 侧约定**：coordinator 总是提供 `--review-focus`（该 skill 现行标注为可选参数，"总是提供"是 wf 侧收紧约定，不改 skill）；③轮次号跨返工继续递增、不重置（wf 侧纪律，§6.5——规避该 skill action 侧 `.processed.json` 消费账本"已消费默认跳过"的语义）。适配实施以**本仓库 `skills/multi-cli-review*` 为权威源**（各宿主根的副本由既有安装投放承载——适配零改动后无需为 wf 分发契约变更）；与"wf 不管理其他工具资产"（§2.2 末行）的关系：该 skill 是 wf 自有依赖的显式适配对象，属例外且仅限此项。适配责任在 authoring 仓库，清单落 §8 且**排 P0 段**（适配完成前审查门禁恒空转，见 §8 的排期约束）；适配完成前该依赖不可用，走 unavailable 留痕回退，不阻断其余功能。审查机制的**流程形状**（任务标识入参、轮次与槽位、结论两档、上限 2 轮、unavailable 留痕）与 workflow-implementation.md §8.5 同源对齐；**目录与参数形状以全局 skill 现行契约为准**——不得以"同源"为由跳过对其正文的核实。

**同仓生命周期冲突（已登记，未裁决）**：workflow-implementation.md §8.5.7 计划在内嵌 wf 模块的内部审查 skill 落地后**全面移除**全局 `multi-cli-review*`（全仓 grep 清零）。若该计划先于本框架的适配执行，本节的 P0 依赖对象即消失，须重新裁决；**适配为零改动后冲突的影响已大幅缩小**——回退方案是 vendor 自有副本（把 `skills/multi-cli-review*` 复制进框架资产，无契约改写、无加性参数丢失，§7.4 vendor 纪律适用），不再是"契约改写重做"。裁决记入 §7.5 源注册表；本文件不预设结论，裁决前两产物的既定计划并存。

**许可边界**：skills 仓库为 MIT（vendor 时保留原许可文本）、Trellis 为 AGPL-3.0（**只借结构与判断句，不复制代码**——不构成派生）；stop-that-shit 与 mcode-stack 同此纪律：结构可借、文本自写。源注册表（§7.5）每源登记许可。

## 3. 使用背景

| 维度 | 约定 |
|---|---|
| 人员 | 单人，一台开发机 |
| 工作线 | 单一工作线：不切分支、不合入；推送由人执行 |
| AI 环境 | 多个 AI CLI 交替，能力不等、上下文不共享 |
| 项目形态 | 全新项目与存量项目均可用；存量项目分"无既有流程"与"有既有流程"两种情况（见下） |
| 使用周期 | 长期：spec 持续沉淀 + 过期与回收治理；多任务时依赖图保障顺序 |
| 分发 | 框架源在 ai-coding-toolkit（authoring 源）；推送到 forgejo 远端（`ssh://git@forgejo.xzc.com/xzc/ai-coding-toolkit.git`）后供安装/升级；不指定本地 file 路径 |
| 语言 | skill 正文与流程文档用中文；spec 内容按项目自然形成 |

**存量项目共存策略**（目标项目已有其他流程控制，如 `.trellis/` + AGENTS.md 托管块）：**共存，不替换**。

- `.wf/` 是独立目录，wf 不读、不写、不检测其他流程的任何资产；skill 命名天然带 `wf-` 前缀，与 `trellis-*` 等不冲突；
- wf 不在 AGENTS.md 写任何内容（原则 2 不因共存放宽）；两套流程在同一 git 仓库并存，由人在每个会话选择调用哪套；
- 共存的诚实代价（完整口径）：①不调用 wf-start 的会话不受 wf 任何约束，其他流程的指令继续生效（§1.3 的首步自检保证模型即使误拉起 model-invoked wf skill 也无法在那种会话里推进 wf）；②**同一项目里两套 spec 体系并行维护**（`.wf/` 与 `.trellis/spec/` 等），重复条目的**合并责任在人**，wf 不做跨流程同步——两套 spec 可能各自沉淀出相似规则，人不主动比对就会漂移分叉；③安装器只在文档层面说明以上两点，不做检测与干预。**如需一次性只读萃取既有流程的规范进 `.wf/`**（知识迁移入口），属对本节"不读"边界的显式放宽——是待用户决策项（D-1），本文件未裁决，裁决前不实现；**裁决记录落 §7.5 源注册表（D-1 / D-2 观察模式对应条目），正文对应节随裁决同步**——裁决必须沉降（§1.3 证据面 5），不允许只裁决不落盘。

**新项目 0→1 落地**：安装后引导创建**初始化任务**（约定俗成的首任务，见 §5.1），其产物为后续任务开工的必要输入：

| 产物 | 内容 |
|---|---|
| **项目层基线（活文档）** | 需求基线（范围、**明确不做的事**、验收口径）与技术基线（架构、外部依赖、风险与回退、规格骨架）——范围闸门的**项目级锚点**（§4.2 范围闸门同时挂任务 PRD 与本基线）。**基线是活的**：落 `.wf/` 通用层的独立活文档；**移交**：初始化任务 finish 归档动作内联执行"基线从任务产物移交为 `.wf/` 活文档"（由入口脚本写入，§5.3 写者纪律），移交后任务内产物转为只读快照；此后由 `wf-baseline` 变更通道更新（§4.2），git 历史为变更记录 |
| 初始 spec 骨架 | 空目录 + **index 三段完整骨架**（索引表 + 开发前 checklist + 质量检查三段模板；发行模板常见的"只有第一段"形态属缺失，由一致性校验报出）+ 最小示例文件（标注为模板，非已核实知识） |
| **治理面登记** | 项目中受特别治理约束的路径清单（默认含：spec 目录、构建配置、对外接口 / CLI 入口、记录 schema；项目可增删），**人审定后由初始化任务写入 `.wf/`**——它是 §6.5 复杂度判据"契约面"行的项目化数据源，也是范围闸门（§4.2）的第三块锚点之一 |
| 构建 / 测试命令登记 | 探测并登记项目的构建、测试、lint 命令（供 Check 阶段默认检查面使用；探测不到的项留空并声明） |
| 目录约定 | 源码 / 文档 / 实验产物各归何处 |
| **git 就绪** | 新项目由**安装入口**完成（`git init` + 骨架首次提交，该提交即安装锚点，§7.1）；存量项目走 §7.1 git 前提校验（尚无 git 时先 `git init` + 首次提交）——Check 用 git diff、一致性校验比对 git 历史、Finish 有提交顺序约定，均以 git 存在为前提 |

初始化任务本身走完整主干（轻量级），归档后项目进入正常任务流（先建任务图与尾任务定义，见 §5.1 提示出口）。

四条原始需求与机制的对应：

| 需求 | 承载机制 |
|---|---|
| 1. 在一个项目中长期使用 | 通用层持久化 + spec 沉淀闭环 + 过期与回收治理 + 归档分层 + 记录 schema 版本 + repair 入口 + 巡检 + 基线活文档 + 升级不触碰项目数据 |
| 2. 新项目 / 存量项目均可用 | 安装器两种入口 + 新项目初始化任务（基线 + 治理面 + git 就绪）+ 存量 bootstrap（git 前提 + 萃取 + 基线与治理面初版，带质量约束与注入防护）+ 既有流程共存策略 |
| 3. spec 持续沉淀 | `wf-spec-update` 必经步骤 + 准入门槛 + 回收治理 |
| 4. 单任务流程执行可控 | 固定主干 + 完成判据（含证据有效期）+ 范围闸门（任务 PRD + 项目基线 + 治理面）+ 体积上下限 + 段内回退 + 开工/收尾门禁 + Check 独立关卡 + 就绪选择规则 + 依赖满足判定 |

## 4. 功能清单 · 入口与生命周期

### 4.1 入口技能与路由纪律

技能清单与调用权见 §1.3。**人视角速查**（时刻 → 唯一入口；模型视角的路由在下文，此表解决"人什么时候该调哪个"）：

| 时刻 | 唯一入口 | 是否需要人判 / 令牌 |
|---|---|---|
| 首次安装 / 升级 / 卸载 / 异常修复 | `install` / `upgrade --apply` / `uninstall --purge` / `wf repair` | **交互终端 + 手输令牌**（模型不得代跑） |
| 开始或恢复工作（含换会话、换 CLI） | `/wf-start` | 人调用（无令牌） |
| 会话内推进 / 路由下一步 | `wf-continue`（模型按指示调用） | 无——门禁自动校验 |
| 存量项目初始化 | `/wf-bootstrap` | 人发起（一次性） |
| 任务收尾 | continue 在门禁满足时**提示人调用** `/wf-finish` | **人调用（人判）** |
| spec 更新 | `wf-spec-update`（finish 流程指示调用） | 留痕（无需令牌） |
| 基线 / 治理面变更 | 新建变更任务 + `wf-baseline`（收尾时脚本写入） | 人审 PRD |
| 多 agent 审查 | continue 输出 reviewer 命令 → 人开异种 agent 会话 | 人发起 |

**每个任务预期的人工介入点**（让"太重就简化"有据可依）：分级判定（Plan 末）→ 审查发起（Check 后，仅复杂任务）→ 人判（finish）→ 归属裁决（仅出现未归属提交时）→ 令牌确认（仅人直调命令）。轻量任务最少只需两级：分级判定 + finish 人判；超出此清单的介入点出现即属异常，按阻断协议报告。

路由纪律（模型视角）：

- `wf-start`：读通用层状态 → 一致性校验（§5.4）→ 恢复上下文（含跨会话接续，§4.4）→ 选定任务（按 §5.6 就绪选择规则）→ 加载策展 spec；
- `wf-continue`：首步自检（§1.3）→ 路由"下一步做什么" + 执行门禁校验。**当前任务挂起时按 §5.4 挂起状态的路由**（输出挂起状态、列出返工集合中未归档的返工任务、给切换建议）。**路由前必读被路由目标（skill 或模块文档）的正文，不许凭记忆复述**——摘要只作定位，正文才是指令。**审查发起也在此**：当前任务为复杂任务且 Check 结果为 pass 时，continue 的输出必须包含 reviewer 侧调用命令（按 §6.5 的 coordinator 职责生成，五参：`--task-id`、`--task-dir`（指向嵌套 review 子目录）、`--reviewer-id`、`--round`、`--review-focus`——见 §6.5），提示人开异种 agent 会话执行；
- `wf-finish`：check 校验 → 审查校验（§6.5）→ spec 更新 → 提交顺序约定 → 归档。continue 在门禁满足时**提示人调用** finish，不代调。

**路由输出最小集**：continue 每次输出至少含四项——当前状态、下一步动作、门禁结论（通过 / 被拒及原因码）、出口（解除阻断该做什么）；超预算时降级为一行汇总（状态 + 下一步），但门禁被拒时**四项不可省**。skill 正文与路由输出都不承载步骤详情（§1.1 份额纪律）。

### 4.2 任务生命周期（固定主干 + 按需模块）

```text
Plan ──→ Execute ──→ Check ──→ Finish
              ↑⇋↓        (段内回退)
```

- **主干四段固定**：Plan → Execute → Check → Finish。步骤带 `[required · once|repeatable]` 标记——required 步骤**不可跳过、不可以"附理由"豁免**（required 的语义就是无条件；附理由的不勾只允许出现在非 required 的 checklist 项上，见 §6.5 门禁第 2 项的措辞）；
- **复杂度分级（双时点）**：分级是**任务记录字段**，不是即时判据。**时点一（Plan 末，开工门禁前）**：由人判定并写入字段——依据是 PRD 中的**触碰面声明**（计划触碰哪些文件/目录、是否命中治理面登记的路径、预估规模），轻量/复杂二值。复杂任务的产物为 prd + design + implement 三件套，轻量任务 PRD-only。**时点二（Check 时，按事实复核）**：按本任务触碰路径（§4.2 任务归属的定义——不取基线区间 diff，避免串味）复核（判据见 §6.5 复杂度判据表），命中而字段为轻量 → **升级为复杂**（补 design.md 与 implement.md——在 Check 时点补记架构与实施要点，不回退执行）并触发强制审查；只升不降，降级须人裁决并留理由。两时点不一致不构成矛盾：开工门禁校验的是**时点一的分级**（它决定产物要求），Check 校验的是**事实**（它决定审查与升级）；
- **开工门禁的校验对象（自建，无上游先例）**：`prd.md` **文件存在**（复杂任务另加 `design.md` / `implement.md` 存在）+ 阶段受控取值合法（状态与阶段位置的取值集见 §1.3 基础定义）+ 前置满足（§5.1 判定式）+ **任务基线提交登记**（见下）。注意上游 Trellis 的门禁不校验产物存在性，此门禁为 wf 自建，实现不得参照 Trellis 行为放宽；
- **建任务许可 ≠ 实现许可**：人批准建任务只进入规划；开工门禁通过（产物存在 + 前置满足 + 基线登记）才进入 Execute；
- **任务归属（唯一定义）**：单工作线下"哪些改动属于哪个任务"是**内容集合问题**，不能用时间起点（基线提交）表达——返工与未收尾交替都会让"基线以来的 diff"混入其他任务的提交。归属的承载：**任务内提交携带归属标记**（commit trailer `wf-task: <任务id>`，由 skill 指示 AI 在每次提交时写入；写者属纪律约定层——AI 忘写不阻断当次提交，但属可发现越轨，见下）；**本任务触碰路径 = 归属标记指向本任务的提交所涉路径 ∪ 归属裁决指向本任务的提交所涉路径 ∪ 继承路径字段 ∪ 工作区未提交改动**（第三项由替换实施命令写入，见 §5.6——继任者承接旧任务已提交路径的载体；第二项承载未带 trailer 的提交经人裁决后的归属——裁决必须让这批路径**进入**证据面而非仅让告警消失，见下条；第四项在 **Check 时点通常非空**——检查先于提交，Execute 产生的未提交改动正是检查对象——由提交顺序约定①在收尾前转为已提交项，同一批文件在归档时点仍可比对；工作区干净门禁只在开工 / 指针切换时点生效，不作用于 Check）。**此公式是触碰路径的唯一构造语句——公式之外不允许存在任何"初始化为 / 追加 / 特例构造"触碰路径的语句**（派生量不许有第二定义点，见 §1.3 回扫对象二；**公式项数完整性按 §1.3 证据面 7 自检**：本段其余语句所需的每一类路径都必须在此公式内）。**任务基线提交**（开工命令登记的当前 HEAD）用途收窄为两项：①**未提交改动的归属判读参照**、②**reset 排除判据项**（§4.4 走错路回退——被引用提交的判定依据之一）——**它不再是触碰路径的定义成分，也不是扫描下界**（扫描下界是安装锚点，见下条；锚点缺失不回退到任务基线——首个任务开工前基线集合为空，空集最小值未定义，正是 §1.3 证据面 6 要防的补集缺口，故缺失走框架资产完整性处置而非回退）；
- **未归属提交的扫描与系统提交的补集（唯一定义）**：把提交二分为"归属某任务 / 未归属"时，必须显式回答"不属于任何任务的提交怎么办"。**覆盖式断言（不枚举）**：**扫描范围 = 安装锚点提交的**后继**至 HEAD 的连续区间——锚点提交自身是边界、不入扫描面**（其内容全部为框架落盘、先于一切任务，归属判定对其无意义；内容纯度由安装入口的受限 staging 保证，§7.1；**接入提交因此不触发框架资产 WARN**——锚点提交不入面，锚点登记提交仅触碰 `.wf/` 完全豁免）（**安装锚点（唯一定义）**：项目接入 wf 后的首个 git 提交，**由接入流程产生并登记**——新项目：**安装入口**执行 `git init` + 骨架首次提交，该提交即锚点（先于初始化任务开工，使其基线登记可满足）；存量：安装 / bootstrap 入口在落盘后产生的首个提交（git 前提校验保证 git 已存在）。**登记**：安装 / bootstrap 入口写入 `.wf/` 通用层的单一小文件（记录类，git 跟踪，§5.3；**写者统一为安装 / bootstrap 入口**——人直调通道，§1.3；三处表述以此为准）。**两次提交时序（防自指，唯一定义）**：骨架首次提交**在前**（= 锚点，其内容**不含锚点文件**——文件内容依赖该提交的哈希，先入库即自指，物理上不可产生；与写入标记"不是自指的本次提交哈希"（§5.3）同一自指意识）、锚点登记提交**在后**（仅触碰 `.wf/`，完全豁免）——安装产生**两次提交**。**静态起点，不随任务移动、不是水位**。**锚点缺失的出口（补集，覆盖式二分支，两分支覆盖存量过渡态）**：①接入流程进行中——**新项目：初始化任务未归档；存量：锚点登记待完成（安装时工作区未净、人尚未重跑登记，§7.1）**——属正常过渡态，不扫描、不阻断（未 start 的会话不受 wf 约束，原则 2，既有开发流照常）；②接入完成后仍缺失 → 启动校验按"框架资产完整性"（§5.4）阻断，出口 repair。**空集出口**：锚点存在但区间为空（无提交）→ 扫描通过。**不取各任务区间的并集**——空窗期与任务交替的间隙都在覆盖内），**该区间只在本处定义一次，由每次归档时的全区间重扫保证覆盖，不依赖任何水位 / 游标字段**（重扫的 O(提交数) 代价是**有意选择**，登记在案：覆盖式断言不依赖水位换取的固定开销；实测可接受量级由实现面给出，超量级时由人裁决是否引入水位——那是重开"覆盖式断言"的决策，走 §5.2 否决记录），该区间内每个提交必属且仅属三类之一：**任务提交**（带 `wf-task` trailer 或有归属裁决记录）、**系统提交**（满足下述豁免属性）、**违规提交**（其余——扫描与阻断对象）。**空窗期纪律**：无活动任务期间不得产生业务提交（要改就先建任务）——空窗期提交既非任务提交也不满足豁免属性，按违规提交捕获；**"缺证据 ≠ 不必要"通则在此适用**：安装锚点之前的提交不被扫描，**不等于**那段历史无违规——其内容仅可能触碰框架资产与 `.wf/`（已由豁免属性覆盖；若发现其他改动，属项目接入 wf 之前的既有历史，不属 wf 判定面）。框架自身的五种**系统提交**：repair 修复提交（§5.5）、升级提交（§7.2）、归档提交（§4.2 提交顺序③）、基线移交提交（§5.3 写者纪律）、**接入提交**（安装 / bootstrap 入口产生：骨架首次提交（= 安装锚点）与锚点登记提交，§7.1）——它们不携带 `wf-task` trailer，且五者即"记录类框架写者的提交"（§5.3 记录与运行态二分）的全部成员（覆盖式断言，无例外括注）。处置：①**系统提交豁免（分级，可判路径属性，非标记）**：提交的 diff **仅触碰 `.wf/` 路径**的提交**完全豁免**——判定中立（这些路径本就被指纹排除，§4.2 Check 关卡），伪出这种提交不影响任何判定、不构成逃逸；提交的 diff **含框架资产清单内路径（§6.1 路径边界）且不含其他路径**的提交**扫描通过**，首次出现输出 `[WARN]` 框架资产提交（豁免立论的诚实边界：框架资产在 `.wf/` 之外、不被指纹排除——任务改框架资产若忘带 trailer 属结构性可发现的逃逸，WARN 即其可发现面）。**WARN 必须沉降（与证据面 5 同律）**：全区间重扫会让同一条历史提交在之后每次归档 / 启动校验里重复告警、随升级次数线性累积，而重复出现的提示会在几轮之后被忽略——因此人确认（或人直调入口执行时自动生成）后记入 `.wf/` 的『已确认框架资产豁免登记』（**抑制型登记，两类条目**：**提交哈希**（框架资产提交豁免，本条）+ **缺失路径**（§6.1 第三态的用户删除豁免）；各含原因 + 时间），**后续扫描跳过已登记项**：WARN 对每条提交 / 每条缺失只出现一次，可发现面保留（未登记的仍告警），噪音不累积；②**未归属扫描（唯一定义）**：按上段覆盖式断言执行——对象 = 覆盖区间内**不满足豁免属性且无 `wf-task` trailer 且无归属裁决记录**的提交——发现即按阻断协议报告（决定性事实：提交哈希、涉及路径），出口：人裁决归属到哪一任务（**裁决只能指向未归档任务**——归档记录无常规写路径，归属裁决记录是判定字段，对已归档任务无写入通道；因此扫描前移到归档门禁（见提交顺序约定②），保证归档逃逸不可能发生、已归档任务无出口的死角不可达）；裁决写入该任务记录，**裁决即沉淀**——后续触碰路径运算直接消费，不再重复报告同一提交。归到进行中任务的后果如实声明：该提交路径并入其触碰路径，其已记录的 Check 指纹失配、须重跑 Check（证据有效期语义的正确行为，不是误报）；
- **任务基线提交与工作区干净门禁**：开工命令登记任务基线提交（当前 HEAD，用途见上条）；**开工与指针切换（§1.3）时校验工作区干净**（`git status` 无未提交改动；有未提交改动即阻断，出口：提交、或人显式确认归属到哪一任务后再继续）——单工作线下未提交改动会串味下一个任务的指纹与归属，此门禁是结构性的，不降级为 WARN。例外：`.wf/` 内由入口脚本原子写入的**运行态文件**（§5.3 记录与运行态二分：指针等，gitignore）不参与干净门禁（它们的写入与门禁校验同属一次命令调用）；
- **Check 是独立关卡**：Check 结果是**受控取值**（`pass` / `fail`）+ 检查项列表（每项：命令 + 结果摘要）+ **触碰路径指纹**（检查时点，本任务触碰路径（§4.2 任务归属的定义）中**非 `.wf/` 路径**的内容哈希集合——已提交路径取提交内容哈希，未提交路径取工作区内容哈希，无论已提交与否都入指纹；spec 与任务记录的后续收尾写入不入指纹、不破坏证据），由入口脚本写入任务记录（写者纪律见 §5.3）。`fail` 时 finish 拒绝归档并按段内回退回 Execute；自由文本摘要不构成"已通过"——没有受控取值的 Check 记录视同未检查；**指纹与归档时点不一致视同未检查**（Check 之后又改了代码，旧绿灯对最终状态不再有效——按归属定义，只有归属本任务的后续提交才触发失配，其他任务的提交不串味本任务指纹）；
- **Finish 内容**：spec 更新（必经）→ **提交顺序约定** → **复盘** → 归档。**提交顺序约定（唯一定义，三条）**：①本任务的全部改动提交完毕（工作区对归属本任务的路径干净；**无法归属的未提交改动单独列出交人裁决，绝不静默捎带进提交**——单人多 CLI 环境下工作区常有非本会话改动，静默捎带是真实风险）；②**未归属扫描通过**——按 §4.2 覆盖式断言的**同一区间**（锚点提交的后继 → HEAD，锚点提交不入面，见 §4.2 扫描范围）全量重扫，全部提交带 `wf-task` trailer、或已有归属裁决记录、或满足系统提交豁免属性（§4.2 覆盖式断言与豁免分级；**扫描在此处收口**，保证归档后不再有未裁决提交——归档逃逸不可能发生；框架资产提交以 WARN 放行，见该处）；③归档提交（含归档动作写入的记录变更，属系统提交豁免面）最后单独成组——顺序违反即归档动作拒绝执行并报告。continue 在门禁满足时提示人调用 finish。**归档前一次性校验 = §6.5 finish 门禁六项 + 本约定三条**（门禁六项在 §6.5 唯一定义，此处不另列防漂移；本约定三条是任务侧收尾校验，与门禁六项分属两个定义源，合计构成归档前完整校验面）。**复盘（有形状，非劝告）**：回看本任务轨迹而非只看结果——逐项过候选面：未验证假设、绕路重试、错误工具或参数、漏看信号、**压缩后丢约束（指令漂移）**；每项发现映射"最廉价的持久修复"（进 spec 准入 §6.3 / out-of-scope 拒绝项 / 治理面变更 `wf-baseline`，三条既有出路）。**触发条件**：返工后、审查 fail 后、同一问题连续调试 ≥ N 次（项目层可配）的任务**必须复盘**；其余任务可选但鼓励。**两条执行纪律**：复盘在归档**之前**执行（归档后人会忘记会话中段的挣扎，编造通用建议填满分类——上游实测教训）；每项发现须引用任务记录中的具体条目（与 §6.3 准入①"真实失败"同律），引用不出的发现丢弃。

**每段完成判据**（写入任务记录的阶段字段——纯文本 checklist，人与模型同读同核；finish 门禁校验其第 2 项）：

- 判据形式为可勾选核对项 + 显式反模式（"发现自己在做 X 即停下"），不是劝告；**质量尺**（沿 skills 写作指引）：每条判据必须能判 done / not-done——"提高质量""考虑周全"这类无法判定的措辞不许进 checklist；
- 完成的判据（wf 口径，吸收自 stop-that-shit 的 Ladder 第 5 步表述）：**请求的结果存在 + 必要证据支持且对最终状态仍有效 + 无已知在范围内阻塞**。计划、或计划的更小子集，不算完成；**证据过期（指纹失配）不算"证据支持"**——Check 之后代码又被改过而未重跑 Check，旧绿灯不再是证据；
- **反例成对**：主干与 vendor 原语的每条纪律附一个最近真实反例（违反它的具体场景），写在纪律正文旁的反例段（结构承载——**spec 文件的 `counterexample` frontmatter 字段**（§6.1）或流程文档的反例小节，不进 skill frontmatter）；改一个事实结论该反例就应颠倒，写不出反例的纪律标 `needs-counterexample` 待补——防止纪律退化成无人能解释的套话；
- Plan 段核心反模式：未过需求澄清（grilling 纪律，触发条件见 §4.3）就写死设计；Execute 段核心反模式：改动溢出 PRD 不停；Check 段核心反模式：失败被表述成"基本通过"，或拿不相关的成功命令顶替缺失的证据。

**范围闸门（三层锚点）**：任务 PRD **与项目层基线**（§3 活文档，含"明确不做的事"）**与治理面登记**（§3，受特别治理路径清单）共同构成范围基线。执行中改动溢出任务 PRD、触碰项目基线的"明确不做"清单、或触碰治理面登记的路径而 PRD 未声明即停——扩展需求走"改 PRD（回 Plan）或新建任务"；**改基线走 `wf-baseline` 变更通道**：新建普通任务承载基线变更（其 PRD 记变更内容与理由），任务收尾时入口脚本把变更写入基线活文档（§5.3 写者纪律——活文档的判定性内容只经 `wf-baseline` 通道写入，AI 不得直接编辑）——基线的修改与任务的归档解耦，活文档不受归档只读约束；治理面登记的变更走同一通道（它属基线活文档的组成部分）；项目级验收口径作为 Check 的对照面之一。

**单任务体积上下限**：改动规模显著超出预期即触发"应拆分"检查点。默认阈值：本任务触碰路径（§4.2 任务归属的定义）≥ 8 个文件，或累计净增删 ≥ 400 行，或单个文件被整体重写——命中即停下评估是否拆分为多任务（阈值可在项目层配置）。**下限判据（防拆太碎）**：预估净改动低于下限（默认 10 行）且不产生独立可验证产物的任务，宜与相邻任务合并——碎片任务把主干固定开销（plan 产物、开工门禁、Check、finish 六项门禁）放大成主要成本，并使任务图迅速膨胀。与 §6.5 复杂度判据的关系：复杂判据（≥3 文件或 ±80 行等）触发**强制审查**，体积上限触发**拆分检查**，两者作用不同、可同时命中。**"信号不是授权"**（沿 stop-that-shit 的贡献纪律）：上述数字是**信号与检查点触发器，不是判定本身**——命中只触发停下评估，不直接产出结论；拆不拆、是否升级，由触碰路径与治理面的事实给出，不凭行数自动裁决。**切分判据（怎么拆）**：①**垂直切片**——按用户可见行为切，不按技术分层切（每层一个任务的"水平切"无法独立验证）；②**每个切片独立可验证、大小适配一个全新上下文窗口**；③**expand–contract 序**（同文件宽改）：先扩展（新增兼容旧接口的形式）→ 分批迁移调用方（每批一个任务，旧形式仍在、检查恒绿）→ 收缩（删除旧形式，被全部迁移批阻塞）——存量项目改造任务的切分直接套用；④验收基线：每个切片的验收判据在开工者所基的提交处**已经为红**（跑不过才证明判据测的是本次改动），否则是伪判据。

**段内回退**：Check 失败 → 回 Execute 修复（同任务内，required 步骤可重复执行）；缺陷属其他未归档任务的产物才走跨任务返工（§5.6）。回退不改变任务状态，只记录阶段位置。

**Check 段的分工纪律**：机械项（格式、lint、可直接定位的报错）直接修复后重跑；设计项（架构取舍、契约变更、判不准的问题）停手，按 §1.5 阻断协议报告并交人判——不许把设计问题当机械项顺手改掉。

### 4.3 按需模块

| 模块 | 挂载点 | 触发方式 |
|---|---|---|
| grilling | Plan | **触发式（不是自觉）**：任务为复杂级、或需求描述存在可识别的歧义 / 未决点（判据由 skill 正文给出）时强制进入；轻量且无歧义的任务可跳过并留一句跳过理由 |
| TDD | Execute | 任务级开关（任务记录字段），开启后作为执行纪律 |
| 调试循环 | Execute | 触发式：同一问题重复失败即强制进入（不再盲目重试） |
| 返工判定 | Execute / Check 内 | **模型发现未归档任务（前置任务或本任务自身）的产物缺陷 → 报告缺陷与建议，由人确认发起**跨任务返工（§5.6 步 1——返工是人发起的前向操作，模型不代发起）；挂载点已归档时走维护任务入口（§5.3 末） |

### 4.4 会话管理与跨会话接续

不设独立 journal，任务记录是唯一恢复源（含状态、产物、决策、Ruled out 与进展备注）；换会话或换 CLI 时调 wf-start 从中恢复，git 历史为佐证，不造第二份记录源。补齐会话卫生纪律（沿 mcode-stack long-session-check）：

- **上下文三分桶**：过时内容丢掉、在用内容概括、持久结论写盘（写进任务记录或 spec），上下文窗口是工作台不是仓库；
- **换会话判据**：多次压缩后仍出现上下文漂移（重复问已答的问题、重做已完成的检查）→ 停止压缩，换新会话并调 wf-start 恢复；
- **走错路回退（唯一定义，两种形态）**：发现走错路时回退到犯错之前，而不是压缩后带着错误继续。框架的判定以**提交为锚**（§4.2 任务归属、§5.3 写入标记、§5.6 继承路径），历史被改写会让这些锚点悬空，因此必须区分两种形态：①**revert（保留历史与引用）——默认且始终允许**：新增一个反向提交，被回退的提交仍在历史中，全部引用继续可解析；②**reset（摧毁历史）——仅条件允许**：仅当**被回退区间内不含任何被引用的提交**时才可直接 reset（机械判据——被引用提交的六类，一条不漏：该区间内无带 `wf-task` trailer 的提交、无归属裁决指向的提交、无任务基线提交、无写入标记引用的 HEAD 提交、无继承路径字段来源的提交、**无抑制型登记持有的提交哈希**（已确认框架资产豁免登记，§4.2——漏此类则 reset 后登记里留下悬空哈希，其"跳过"行为会静默作用在一个不存在的提交上；此六类与 §5.4 引用完整性核验的对象同源，reset 判据是其子集消费点））；不满足条件而执行 reset 后，必须走 `wf repair` 重建引用并留痕（§5.5）——单工作线下本地 reset 是低成本操作，属真实场景不是理论场景；
- **任务暂停**：人可对任务记暂停标记（含原因）；暂停任务不参与就绪选择，恢复由人清除。暂停是休息语义，不是放弃。**挂起 × 暂停组合**：挂起清除时若 T 带暂停标记，两者不冲突、不互斥——挂起清除只移除等待约束，暂停标记独立保留，T 在暂停期间不参与就绪选择，恢复由人清除（两标记分属"等待返工"与"休息"两个正交维度，§5.4 状态×操作矩阵含此组合）；
- **进展备注的交接骨架**（沿 mcode-stack handoff-doc，固定模板）：已完成的决策与理由 / 当前卡点与下一步 / **排除的方案（Ruled out）** / 未验证项（明确列出尚未核实的假设）。简报而非逐字稿。**两条执行纪律**：写交接（进展备注）前先从 `git status / log / diff` 与真实测试结果收集，不可核实的标 unverified，**不凭对话记忆写**；新会话接续时（wf-start 恢复后）**先复述 goal 与下一步再动手**——跨 CLI 场景下两句成本极低。

## 5. 功能清单 · 依赖机制与任务图

> 概念保留自本项目 workflow-design.md（见 §1.4 来源修正），实现重造：**全部落在 `.wf/` 通用层的单一任务记录文件上**，不设独立账本、不设雪花 ID、不设对账修复类型学。

### 5.1 语义总纲

- 前置集合为唯一顺序事实源；就绪 / 阻塞视图由前置集合派生（DAG，无环）；
- **依赖满足判定（唯一定义）**：前置任务**已归档且终态为正常**才算满足。异常归档（替换/放弃的结果）**不构成满足**——下游必须等重连到继任者或删边后按新前置判定；"已归档"本身不是满足，"正常归档"才是；
- **归档终态约束（源约束继承，唯一定义）**：已归档任务终态只能是"正常"或"异常"；**"正常"要求该任务的前置集合全部满足（§5.1 判定式）**——前置未满足而归档属非法终态，启动校验（§5.4"归档终态合法"）以此判据发现，处置走 repair。前置未满足 → finish 门禁第 5 项拒绝归档（§6.5），这是第一道防线；校验发现是第二道（补线）；
- **返工（跨任务，完整操作定义见 §5.6）**：依赖级挂起——返工任务插在被返工任务之前，被返工任务等待其完成后回就绪；
- **替换 / 放弃（跨任务，完整操作定义见 §5.6）**：前向操作，只适用于未归档任务；一经实施不回退；
- **建边 / 删边（迭代期顺序调整，完整操作定义见 §5.6）**：依赖图在初始化后的生长与修剪通道；
- 归档终态：**归档记录本身无常规写路径**（不可重开、产物只读），例外**有且只有一类**：`wf repair` 按人确认直达修复（§5.5）。**删边指向归档目标时不属归档写路径**——它修改的是未归档一侧任务的前置集合（写者纪律 §5.3 行 1），归档记录本身不变；§5.6 删边的"目标可已归档"指删除动作允许作用于这种边，不指写归档记录。"上个月的东西坏了"既能新建维护任务，也能由 repair 修旧记录的错误；
- 项目结构 = 约定俗成的首任务（新项目为初始化任务，§3）与尾任务 + 通用 DAG。**项目状态的两类判定相互独立，不互相衍生**：①**项目收尾判定** = 尾任务归档且终态正常（**不要求活动任务集为空**——迭代期新任务、暂停任务可与已收尾状态并存，这是"持续使用"的正常形态，不是不一致）；②**维护任务入口条件** = 缺陷挂载点已归档（**不要求项目已收尾**——详见 §5.3 末）；③**升级前置** = 活动任务集为空或全部暂停（§7.2）；④**卸载前置** = 无前置（§7.3）。四者各答各的问题，不得互相代入；
- **尾任务缺位或失锚的处置**：wf 不设角色解析机器。路由发现"**无就绪任务且项目未收尾**"时，按阻断协议提示，出口按现状二选一并列给出——**从未建过任务图 / 尾任务**（如新项目初始化任务刚归档）→ 建任务（含尾任务定义）；**曾有尾任务但因删边变体的放弃失去继任者**（失锚）→ 由人重定义尾任务：新建普通任务承接收尾职责，前置按需指向最后的实现任务（属任务定义类，不走建边校验，仅要求无自环无环）。中途阶段（有未归档实现任务在跑）"无尾任务"是正常状态，不阻断。

### 5.2 砍掉的复杂度与明确否决的替代方案

**砍掉的机制**（多为双事实源 / 团队 / 分发付出的复杂度）及其理由：

| 砍掉的机制 | 理由 |
|---|---|
| 独立依赖账本 + 双事实源 | 新框架从零建，任务生命周期与依赖状态写进同一份任务记录，双事实源问题不存在 |
| 雪花 ID / 标识占用校验 / 逐窗口恢复表 | 它们是"账本与基底分离后的崩溃恢复"的产物；单一记录下无此问题 |
| **对账修复类型 1–5 的分类学** | 类型学是双事实源的产物；但**修复入口保留**（§5.5 的 `wf repair`，人直调、按人确认一致化），只砍分类不砍入口 |
| P 角色机器（角色解析、继任链） | 首尾任务用约定承载，无需机器解析；缺位与失锚场景按 §5.1 末由人建 / 重定义 |

**明确否决的替代方案**（设计决策的 Ruled out——本文对 spec 要求"Ruled out 排除方案与原因"（§6.3），对自己的设计决策同律；每条一句否决理由，防止长期维护时"为什么当初不这么做"被反复重开）：

| 决策 | 被否决的替代方案 | 否决理由 |
|---|---|---|
| 任务归属用 commit trailer | ①时间区间（基线以来的 diff）；②独立归属账本 | ①返工与未收尾交替会让区间混入其他任务的提交（§4.2 已述）；②双事实源，与单一任务记录冲突 |
| 单一任务记录文件 | 独立账本 + 崩溃恢复表 | 见上表"砍掉的机制"前两行 |
| 活动任务指针单数 | 多任务并行（多指针） | 单工作线语义（§3）；并行属边界外（§2.2） |
| 删边允许指向已归档目标 | 一律禁止删边到归档 | 巡检与修复需要（§5.5/§5.6）；删边改的是未归档一侧的前置集合，不触归档记录 |
| 卸载默认保留项目数据 | 连数据全删（Trellis 默认） | 有意改进（§1.4）：数据是用户资产，流程可重装 |
| 审查轮次号跨返工递增、不重置 | 返工后重置为 1 | 重置会与 reviewer 侧"目标文件已存在即停"的现行契约及 action 侧 `.processed.json` 消费账本冲突（§6.5）；按"实施尝试"计上限即可，无需重置轮次号 |
| 过期 spec 留痕可放行 | 一律硬拦（必须先核实） | 留痕是刻意的降级通路（§6.5 门禁第 4 项）——有些 spec 在当次任务里核实代价过高（需跑长实验等），留痕交人判复核是诚实且可行的出口 |
| 报告目录经 `--task-dir` 嵌套达成隔离 | 改写该 skill 的目录契约（`review-round-{N}` → `review/round-{N}`） | 后者是非加性变更、影响该 skill 全部 task-level 用法；前者达成同一目的且 skill 零改动（§2.2） |
| 克隆安装（clone + 临时目录入口） | 分发 CLI / 包管理器 | §1.4 已述：分发链路是为他人环境付出的复杂度 |

### 5.3 记录的长期形态与写者纪律

**写者纪律**（单文件方案能否站住的关键，逐字段划界；依赖状态字段与生命周期字段同表管辖，**含横跨任务记录的活文档**）：

| 记录 / 字段类 | 写者 | 说明 |
|---|---|---|
| **任务记录判定字段**：状态、挂起标记、异常终态标记与指向、前置集合、返工来源、暂停标记、复杂度分级字段、任务基线提交、归属裁决记录（未归属提交的人裁归属，§4.2）、继承路径字段（替换实施写入，§5.6/§4.2 公式第三项）、Check 受控取值与触碰路径指纹、审查结论受控取值、策展清单、阶段位置 | **入口脚本**（含开工 / 返工 / 替换 / 放弃 / 建边 / 删边 / Check 写入 / 归档 / `wf-baseline` 的实施命令） | 生命周期与判定字段只能经命令写入；AI 不得以编辑文件方式改写。挂起、异常终态与返工来源是就绪判定与挂起清除的直接输入（§5.1、§5.6），与状态同列判定字段 |
| **基线活文档的判定性内容**（范围、"明确不做"清单、验收口径、技术基线、治理面登记） | **`wf-baseline` 变更通道**（任务收尾时入口脚本写入，§4.2）；初始化移交同理由入口脚本执行 | 活文档的**落盘**只经通道写入，AI 不得直接编辑活文档文件——**内容本身由变更任务的 PRD 提供**（架构取舍等判断性内容在 PRD 里由 AI 起草、人审阅，通道只负责把已审内容写入），范围闸门的项目级锚点由此可信 |
| **任务记录内容字段**：产物（prd / design / implement）、叙述、决策、Ruled out、进展备注 | **AI（按 skill 指示）** | 内容性字段自由撰写 |
| **抑制型登记**（其存在会关闭某项检查或告警的产物，落 `.wf/` 通用层、独立于任务记录：如已确认框架资产豁免登记（§4.2/§6.1，两类条目：提交哈希 / 缺失路径，各含原因 + 时间）、未来任何白名单 / 豁免 / 跳过类登记） | **人直调入口，或人确认后由入口脚本写入**；**AI 不得写入**，且**不得由任务记录承载**（避免与任务判定字段混写、被任务归档只读约束牵连） | 抑制型产物的危险不对称：触发型产物漏登记会吵，抑制型产物漏登记会静默放行；一旦被 AI 写入就永久关掉一个可发现面（§4.2 最在意的逃逸方向）。**登记纪律**：凡抑制型产物必须同时登记于四处——写者纪律表（本行，§5.3）/ 豁免分级引用（§4.2，该产物抑制哪个检查与何时沉降）/ 机制名清单（§1.3）/ 引用核验对象（§5.4）；**四处任一缺失即视为该产物无效，不得据其抑制任何输出** |
| **安装锚点文件**（扫描下界提交的登记，§4.2 唯一定义） | **安装 / bootstrap 入口**（人直调通道，§1.3） | 静态起点、非水位；由接入流程（新项目：**安装入口** `git init` + 骨架首次提交 / 存量：安装落盘提交）产生并登记一次，此后不变；缺失按 §5.4"框架资产完整性"处置（不回退到任务基线——空集最小值未定义，§1.3 证据面 6） |
| **归档终态** | 入口脚本（归档动作）、返工 / 替换 / 放弃的实施命令（异常终态）、或 `wf repair`（人确认的修复） | 归档后无常规写路径；例外有且只有一类（对归档记录本身的写入：repair。删边指向归档目标时改的是**未归档一侧任务的前置集合**——行 1 的字段与写者已覆盖，不属对归档记录的写入；§5.1 归档终态条对此有归属澄清） |

**记录与运行态二分（git 噪音与例外蔓延的控制，唯一定义）**：`.wf/` 内的文件分两类——

- **记录类**：任务记录、基线活文档、spec 实体、抑制型登记、框架资产清单、**安装锚点文件**（扫描下界，§4.2）——**git 跟踪**，只在任务提交 / §4.2 五类系统提交（即"记录类框架写者的提交"；接入提交含锚点登记，§7.1）中变化；
- **运行态**：活动任务指针、**读取留痕侧车**（§6.2——`wf spec` 的读取留痕，一 spec 一行）、临时缓存——**gitignore**（ignore 规则由 `.gitignore` **托管段**承载（追加式投放，§7.1），不入任何判定字段、不入 §5.4 引用核验对象、不产生待提交差异；**指针真值可由任务记录重新推导**（状态为执行中且未挂起 / 暂停的任务）；**推导出多个候选即视为指针失效**（非法组合，§5.4 组合识别③阻断 + repair）——唯一性不靠约定，由组合识别兜底；运行态丢失不破坏"任务记录是唯一恢复源"（§4.4；读取侧车丢失的代价是重读一次，同样自愈）。§4.2 干净门禁的 `.wf/` 运行态豁免即指此类；§1.3 活动任务指针的"存储属运行态"即指此类。

**写入标记（判定字段的伴生证据）**：入口脚本每次写入判定字段，同次在任务记录留**写入标记**（写入命令名 + 写入时点的 **HEAD 哈希**——标记记录的是"写入时工作区所基的提交"，该提交在此之前已存在，不产生自指；**它不是任务基线提交字段**——两者是不同的量：任务基线是开工命令登记的那一次 HEAD，写入标记是每次写入时的 HEAD；字段形状落 §8 机制文档）。这是"写者纪律与 git 历史无矛盾"这条启动校验的**判据**：判定字段的变更提交携带写入标记即合法写入；无标记的判定字段变更按无标记越轨报告（§5.4）。伪造标记属蓄意越轨——与"全勾 checklist 的谎称完成"同形，按 §1.5"结构性可发现、语义不可防"的口径，不假装更强。**核对时点双保险**：启动校验（§5.4）与 finish 门禁第 6 项（§6.5）都核对——手改 Check 取值若想骗过 finish 门禁，须同时伪造受控取值与写入标记，而写入标记的 HEAD 哈希必须与 git 历史对得上。

手工直改判定字段不可防（§1.5 第四行），但属可发现的越轨：判据即上述写入标记。写者纪律把"AI 把任务记录当文档顺手改"这个最大风险面收窄为"明确知道自己在越轨（且要伪造标记）"。

**记录的分层与不可解析记录的出路**：

- **schema 版本**：任务记录与 spec 索引各带 `schema_version`。字段演进纪律：**只增不改**——旧字段不删不改语义，新增字段必须可被旧版本忽略；升级**不迁移**旧记录，读取方按记录自声明版本解释；
- **异版记录（可解析、版本不同）**：读取方按记录自声明版本解释；读到无法解释的**字段**时，该字段**按原样展示**，只阻断依赖该字段的判定，不阻断整个任务或全局路由（升级后旧归档记录仍被前置 / 返工引用命中，全局阻断会让整个项目卡死在一条旧记录上）；读到无法解释的**整份记录**时，按"不可解析记录"处置（见下）。**从严口径**统一为：无法解释 → 不参与判定（不是"整条跳过当作不存在"——按原样展示 + 阻断依赖判定，记录本身可见）；
- **不可解析记录（无法解析的整份记录）**：**三层递进出路，不允许死锁**——①按 §1.5 阻断协议报告（呈现读到的原文），人对照 git 历史判读；②判读后走 `wf repair` 修复（repair 的"校验写入后一致性可过才落盘"以人指定的目标态为准——人给出目标态（如该记录按历史事实记为异常归档）后，脚本按人指定重建记录并校验全图一致性，不需要原记录可解析）；③repair 也不可用（如框架整体损坏）时，按 §7.3 卸载（默认保留数据，卸载脚本自包含、不读 `.wf/`）→ 重装后**用 repair 执行单记录删除**（repair 读 `.wf/`，机器核验"该记录不再被任何前置/返工引用"，核验不过即拒绝删除——引用完整性核验落在 repair 而非卸载脚本上，两者职责互斥不冲突）。写者纪律禁止的"手改"是指 AI / 非授权通道的编辑，repair 是人确认通道，不属手改；
- **归档分层**：归档任务移入 `.wf/` 下按月分层的归档目录（沿 Trellis `archive/{YYYY-MM}/` 模式）。启动一致性校验**只扫活动区**；归档区按需解析——仅当前置引用、返工来源指向归档任务时才定位该记录。集合只增不减的长期成本由此控制；
- **命名撞名防护**：任务目录名含日期但**必须含年份**（避免 Trellis 跨年同名踩坑的教训），且 create / rename 时扫描活动区与归档区比对目录名，撞名即拒绝换序号——不在归档后才发现撞名；
- **维护任务入口**（缺陷挂载点已归档时的修复承载）：新建普通任务承载，不依赖返工挂起（挂载点必须是未归档任务）；其前置按需指向相关归档任务（解析归档记录，仅表达顺序参考）。**入口条件 = 缺陷挂载点已归档**，与"项目是否收尾"无关（§5.1 ②）——已归档产物的缺陷在任何阶段都可能需要修，不要求等整个项目收尾。项目已收尾时同样适用此入口。

### 5.4 一致性、恢复与巡检（唯一的恢复机制面）

**启动时校验**（wf-start 调用入口脚本时）**活动区**任务记录一致性：状态值合法（取值集见 §1.3 基础定义）、**引用完整性按类型覆盖（不枚举）**：凡判定字段中出现的**提交 / 任务 / 路径引用**一律核验可解析——含前置与返工来源（含归档区定位）、归属裁决指向的提交、继承路径字段的提交来源、任务基线提交、写入标记的 HEAD 哈希、扫描下界提交（安装锚点）、**抑制型登记持有的提交哈希（已确认框架资产豁免登记，§4.2——否则 reset 后登记里留下悬空哈希，其"跳过"行为会静默作用在一个不存在的提交上）**；任一不可解析即按阻断协议报告（出口 repair），**不得静默跳过**——核验对象是发现悬空引用的唯一一道网，网眼开在静默侧等于没有网。**核验口径限定为"记录引用"**（提交 / 任务 / 记录内路径——它们必须可解析）：豁免登记的**提交哈希类条目**入本核验（提交必须存在），**缺失路径类条目不属引用核验对象**——其"不可解析"正是其语义（登记的就是不存在的资产路径），由本段"框架资产完整性"项按"存在性 + 豁免登记"判据处置，**两套判据不混用**（混用则豁免自我阻断：登记缺失反而触发悬空引用，§1.3 证据面 4 的规则叠加缺陷）；DAG 无环、归档终态合法（含 §5.1 归档终态约束——已归档且正常者前置须全部满足）、**判定字段的写入标记与 git 历史无矛盾**（判据见 §5.3 写入标记）、**无未归属提交**（按 §4.2 覆盖式断言的同一判据——锚点提交之后的覆盖区间内无违规提交，判据与扫描范围以 §4.2 唯一定义为准，发现即按其处置路径阻断——归档门禁已收口，此处为跨会话补线；重扫的 O(提交数) 代价按 §4.2 登记在案）、**框架资产完整性**（清单内路径——skill 投放根 + `.wf/` 骨架文件，§6.1——文件存在性比对；缺失项按 §6.1 第三态处置：已登记缺失（用户已删除，豁免登记内）→ 跳过、可发现面已留痕；未登记缺失（意外丢失）→ 按阻断协议报告，出口：`wf repair` **恢复框架资产**（人确认，从 forgejo 远端重新获取后按清单重放缺失路径，§5.5——可执行的出口，不是空引用）或登记豁免（人确认确属自己删除——区别处置，两种出口分别对应"意外"与"意愿"两种事实；upgrade 不承担恢复——其第三态按定义尊重删除，见 §7.2）。"运行期框架资产是否齐全"由本项覆盖，不再只有装完自检（一次性）与升级对账（按清单）两个面），**外加组合识别以下各项（计数不硬编码，新增项须同步本清单并按 §1.3 登记协议回扫）**：①**未归档 + 异常终态标记**（替换 / 放弃实施中断的残留态，处置按 §5.6 失败窗口）；②**未归档 + 挂起 + 返工集合为空**（挂起失去对象——返工来源被删或从未写入，对应源设计对账类型 2 的组合；处置：按阻断协议报告，出口 repair，由人确认补建返工任务或清除挂起，不得按真空真值放行）；③**多个执行中且未暂停的任务**（指针运行态化后，唯一性由"至多一个执行中未暂停"的推导前提承载——多个候选即指针失效，属非法组合；处置：按阻断协议报告 + repair，由人确认保留哪个或合并）。不一致 → 按 §1.5 阻断协议**报告并阻断**（含下一步出口——出口的承载者是 `wf repair`，§5.5），不自动修复、不静默放行。

**挂起状态的路由**（状态→路由，唯一定义）：活动任务指针指向挂起任务 T 时——路由**不停留在 T**：continue 输出"当前任务挂起，等待返工"，并列出返工集合中的未归档返工任务 R（**含被替换 / 新建替代后的继任者**——继任者继承返工来源，仍是集合成员，§5.6；若 R 就绪，给出切换建议）；人确认切换后按 §1.3 指针切换语义执行（被挂起的 T 不记暂停——挂起本身就是等待语义）。无有效指针时，就绪选择照常运算（R 作为普通就绪任务参与排序，§5.6），选中的可能是 R 也可能是其他任务。挂起不清除、T 不推进也不阻断其他任务——挂起只挡 T 的收尾，不挡任何别的工作。

**状态字段的生命周期收尾（通用规则，唯一定义）**：随任务产生的状态字段分两类。**未决状态标记**（挂起标记、暂停标记）在承载记录被归档 / 替换 / 放弃时必须已收尾，不留语义悬空的残留：**归档动作的前置校验要求"无未收决的未决标记"**（挂起未清除、暂停未恢复的任务不得归档——要收尾它就先把状态处理干净；此要求已并入 §6.5 finish 门禁第 5 项）；启动校验的"归档终态合法"含"归档记录无未收决的未决标记"——"已归档 + 挂起标记残留"在校验层就是非法，不会流入归档区。**挂起任务的替换 / 放弃守卫（唯一定案）**：挂起未清除时**不得替换 / 放弃**——先按 §5.4 挂起路由推进 R（或按建边/删边调整）使挂起清除，或先把 R 按 §5.6 放弃（R 异常归档后挂起复评按集合语义转真、自然清除），才允许对 T 发起替换 / 放弃。（曾有替代方案"实施时同步清挂起、R 留图中"，因与 §5.6 步 5 清除判据的"T 未归档"前提冲突而否决——T 已归档则判据永不再评，R 会悬空在已归档异常任务上。）**历史事实字段**（返工来源、异常终态标记与指向）**归档后不改写、不删除**：返工来源记在返工任务 R 的记录上，"我为谁返工"是历史事实，T 的后续命运（含被替换 / 放弃）不改写它——挂起复评按集合运算消费它（§5.6 步 5）；异常终态标记与指向由实施命令写入并保留为终态记录。**继任者的继承**：替换 / 放弃-新建替代的实施命令建继任者时，继任者继承旧任务的**前置集合**；旧任务本身是返工任务时，继任者**同时继承其返工来源**——挂载点的挂起因此继续等待继任者，不悬空。**暂停的有意设计**：归档要求暂停已恢复，不是漏项——暂停是"休息语义"（§4.4），休息态的任务本来就不该收尾；要归档就先恢复并走完剩余流程。

**挂起复评**（§5.6 挂起清除判据的触发时机，唯一定义）：挂起任务的清除条件在**每次任务归档动作成功完成后内联评估**（含返工任务与其他任何任务的归档；**归档动作自身失败或中断时不评估**——失败即失败，按 §1.5 阻断协议报告并处置失败，处置完成后下一次归档或启动再评估）+ **每次启动校验通过后评估**（活动区扫描时顺带判定）。启动校验**不一致被阻断时，复评不执行**——阻断优先，先修复一致性问题（repair）再谈挂起清除；评估点不限于 R 的归档——T 可能有多个前置（含非返工前置），任何一个归档都可能使条件转真；两个评估点之外条件不成立则保持挂起，继续等待。**"无泄漏路径"的完整口径**：R 未归档（含继任者未归档）则集合含未归档成员，挂起保持；R 已归档（正常或异常）则集合无未归档成员，挂起按判据处置；**集合为空**的挂起不由复评清除——它属非法组合，由启动校验组合识别②捕获并走 repair。泄漏只可能经 repair 的人确认发生，那是处置不是泄漏。

**周期性巡检**（补"归档区坏掉无发现时机"的缺口）：每次项目收尾（尾任务归档）或人工发起时，**跨归档区**校验被前置 / 返工来源指向的归档记录的终态合法性与引用可解析性（含 §5.1 归档终态约束）——与 §6.4 的 spec 周期性清点同期执行，共享一次扫描。发现即报告，处置走 repair。

**记录不可读时的处置**（沿 Trellis `task_error` 的教训）：记录损坏或无法解析时——不新建任务顶替、不删除或改写既有字段、把读到的原文呈现给人，判不准就问人。处置路径按 §5.3"不可解析记录的三层递进出路"（报告人判 → repair 重建 → 卸载重装后由 repair 删单条记录）。机制整体不可用时按 §7.3 卸载。

### 5.5 异常处置入口（`wf repair`）

**定位**：一致性校验发现的**无法用常规入口处置的**结构性不一致（DAG 成环、前置引用断链、归档终态非法、异版不可解释、挂起失去对象等）的修复承载者；§5.4 阻断出口的承载者。没有它，"可读但静态不一致"的记录既不能手改（§5.3 写者纪律）也没有命令改，项目永久卡住——只砍掉了对账类型学，不砍修复入口。**与删边的分工**（唯一定义）：删边处置的是**结构合法但顺序多余**的边（含指向已归档目标的合法边——巡检与修复的常规动作）；`wf repair` 处置的是**结构非法**的记录与边（解析不到任务、环、非法终态、空集合挂起）——遇非法边一律走 repair（删边命令的前置校验会拒绝非法边，正好兜住误用）。两者不重叠：删边是常规通道，repair 是异常通道。**repair 对不可解析记录的能力**（§5.3 三层出路之二）：repair 的目标态由人指定，脚本按人指定**重建**记录并校验全图一致性——不要求原记录可解析；"校验一致性可过"的对象是重建后的全图，不是原文。

| 项 | 规定 |
|---|---|
| 调用权 | **人直调实现件**（§1.1 原则 1 第二类）：交互式终端（双 isatty）+ 手输令牌，模型不得代跑、不得设 env 绕过 |
| 动作面 | 只做"按人确认的一致化写入"：人对照报告指定目标态（如删除非法边、补终态、改指向、重建不可解析记录、确认清除挂起或补建返工任务、**重建被 reset 摧毁的提交引用**（§4.4 回退形态②——重建后须使 §5.4 引用完整性核验通过）、**恢复框架资产**（§5.4 框架资产完整性——人确认后从 forgejo 远端重新获取，按清单重放缺失路径；与 §7.3 卸载脚本丢失的恢复路径同源，远端是权威源）），脚本校验写入后一致性可过才落盘。**单记录删除**（§5.3 三层出路之三）：人指定删除某条不可解析记录，脚本机器核验"该记录不再被任何前置 / 返工引用"后执行删除并校验全图一致性——核验不过即拒绝（防悬空引用） |
| 不做 | 不自动推断目标态（判不准就报告并把原文呈现给人，§5.4）；不提供"改回实施前"类回退语义 |
| 提交 | 修复写入单独成一个提交组，提交消息含原因码与确认人 |

### 5.6 跨任务操作与就绪选择（完整操作定义）

**就绪选择规则**（多就绪任务并存时的唯一路由，沿 workflow-design.md §7.6）：无有效活动任务指针时，就绪集按**任务创建时间升序取最早**；不引入优先级字段、不设人工排序。返工任务与其他就绪任务同规则排序。单一工作线：不并行执行，只选择与切换（切换语义按 §1.3 活动任务指针的定义——切走的执行中任务自动记暂停）。

**建任务带前置（任务定义类，非建边）**：建任务命令可随任务定义一并写入前置集合（新项目任务图、尾任务定义、维护任务的前置均走此通道）。属任务定义：不要求两端都在活动区（前置可指向归档任务），仅要求无自环、不成环，**且前置目标不得为异常归档**（异常归档任务先重连或删边后再引用——与建边校验同口径；维护任务指向归档任务时同样适用）。与"迭代期建边"（下条）分属两个入口。

**建边 / 删边（迭代期顺序调整，完整操作定义）**——初始化建图之后调整"谁在谁之前"的唯一通道。术语统一：一条边两端的称呼——**前置侧**（被依赖的任务，建边时须未归档）与**持有侧**（前置集合里含该前置的任务，删边动作作用于持有侧的前置集合）：

| 项 | 规则 |
|---|---|
| 发起 | 人发起（模型可建议，不代发起）；建边与删边都属前向顺序调整 |
| 建边校验（fail-closed，失败不落盘） | 两端**都在活动区**（已归档任务不再被挂前置——无论其终态正常还是异常：正常的对象没有表达顺序的意义，**异常归档的对象须先重连到继任者或删边**（§5.1 满足判定），对它建边会把下游绑在一个永不满足的前置上）；**前置侧尚未完工**（未归档）；无自环、不成环。**两套口径并列（判据来源：§5.1 满足判定）**：建边要求前置侧未归档（异常归档的对象永不满足、故拒），删边无此要求——**写入新前置要求对象可满足，删除旧前置不产生新绑定**；两者不矛盾，是同一原则的两面 |
| 删边校验 | **前置侧可已归档**（巡检与修复需要；持有侧已归档时无删边必要——其前置集合已随归档只读，本就无人消费）；无自环；删除后不产生孤儿引用——孤儿引用指**任务记录前置集合中解析不到任何任务的死标识**（视图不落盘、无缓存孤儿；具体检测方式属机制文档） |
| 对持有侧的效果 | 未开工持有侧：立刻被挡在就绪之外，前置完成后自动回就绪；进行中持有侧：不挡执行、只挡收尾（收尾门禁要求前置满足，即 finish 门禁第 5 项，§6.5） |
| 实施与失败语义 | 校验通过 → 写入 → 检环 → 单独提交组提交；中途失败不落盘、不重建视图，按阻断协议报告（修复走 repair） |
| 写者 | 实施命令（脚本），§5.3 判定字段划界 |

**返工（依赖级挂起，完整操作定义）**——发现**未归档任务 T** 的产物缺陷时。**挂载点 T 的两种来源**：①**前置任务**——本任务执行 / Check 中发现上游产物缺陷（§4.3 返工判定模块）；②**本任务自身**——审查 2 轮 `fail` 后的整改返工（§6.5：审查挑出的通常是本任务自身的问题，此时不存在可挂载的前置任务）：

| 步 | 动作 | 约束 |
|---|---|---|
| 1 | **模型报告缺陷与建议 → 人确认发起**（说明缺陷与修复范围） | 挂载点 T 必须未归档；已归档缺陷走维护任务入口（§5.3 末）或 repair。返工是人发起的前向操作，模型不代发起 |
| 2 | 建返工任务 R，**前置继承 T 的当前前置集合**，R 记返工来源 = T | R 是图内普通任务，走同一套开工 / 收尾。挂载点为本任务自身时，继承的是本任务当前的前置集合，且继承发生在加边之前，无自环 |
| 3 | T 加入 R 为前置 + **T 记挂起标记**（同一次命令写入，§5.3 写者纪律） | 挂起由实施命令写入，非手改；T 的任务状态不变（执行中照常，只挡收尾；挂起路由会把工作导向 R，§5.4） |
| 4 | 执行并完成 R | R 完成走 §6.5 finish 门禁六项，与其他任务无异 |
| 5 | **挂起清除（唯一定义）**：`T 未归档 ∧ T 挂起 ∧ 返工集合非空 ∧ 返工集合无未归档成员 ∧ T 前置集合全部满足（§5.1 判定式）` → 清挂起，T 回就绪（即使 T 已开工；T 若带暂停标记则保留暂停语义，§4.4 挂起×暂停组合） | **返工集合** = 返工来源指向 T 的全部任务（活动区 + 归档区；**正常归档与异常归档成员均计为已归档**）：**放弃 R（删边变体）后 R 异常归档，仍在集合中且非未归档成员，挂起可清**——人放弃 R 即裁决该轮返工不再需要；**替换 / 新建替代 R 后，继任者继承返工来源、仍未归档，集合含未归档成员，T 继续等继任者**。**"非空"是保护项**：空集合的挂起不得按真空真值清除——属非法组合，由 §5.4 启动校验组合识别②捕获、走 repair。复评时机见 §5.4 挂起复评（每次任务归档 + 每次启动校验，不限于 R 的归档——T 可能有多个前置）；条件不成立保持挂起，无泄漏路径 |

**替换 / 放弃（任务级前向操作，完整操作定义）**：

| 项 | 规则 |
|---|---|
| 适用 | **仅未归档任务**；已归档走 repair（终态修复）或维护任务（产物缺陷）。**挂起未清除的任务不得替换 / 放弃**（§5.4 状态收尾的守卫）——先清除挂起再发起。**对返工任务 R 本身发起替换 / 放弃是合法操作**（R 不携带挂起标记，守卫挂在挂起点 T 上；§5.4 挂起路由把被替换 R 的继任者列为集合成员供选择），其结果按 §5.6 步 5 的集合语义处置：继任者继承来源则 T 继续等；删边放弃则 R 异常归档、挂起复评转真 |
| 发起 | 人发起并说明新范围（替换）或原因（放弃）+ 选变体（替换＝建继任者；放弃＝删边或新建替代） |
| 实施（一经开始不回退） | ①旧任务记异常标记与指向（若有继任者）→ ②建继任者并继承前置（**旧任务本身是返工任务时，继任者同时继承其返工来源**，§5.4 状态收尾）**及旧任务的已提交触碰路径**（实施命令把旧任务已提交路径**写入继任者的继承路径字段**（§4.2 任务归属公式的第三项——不构造第二定义，触碰路径仍按唯一公式派生，继承字段使旧路径进入派生结果）；旧任务已异常归档、不再消费任何门禁，其写入树中的代码的验收 / spec 匹配 / 复杂度判定由继任者的 Check 承接，防止覆盖漏洞）/ 或从下游删边 → ③下游前置改指继任者或移除 → ④检环 → ⑤旧任务异常归档。**旧任务记录上的返工来源是历史事实，归档（正常或异常）后不改写、不删除**。中途失败按已提交事实向前补齐，不回退 |
| 门禁 | 实施前校验：旧任务未归档、未挂起（§5.4 守卫）、变体合法（尾任务被放弃只允许新建替代——删边会失锚）、重连后无环 |
| **失败窗口** | 实施命令是**分步提交**：每步落盘即成提交组，后续步骤按已提交事实继续补齐。中断后重启时，一致性校验识别"未归档 + 异常标记"的组合 → 按 §1.5 阻断协议报告已完成到哪一步、剩余步骤清单；补齐动作沿用同一实施命令（幂等重入：已完成步骤跳过——**幂等键的识别方式（异常标记 + 指向 + 下游是否已改指，或独立步骤标记）属机制文档的实现面**，§8 有落点）。不回退、不重做已提交步骤——与 §5.5 repair 的"不做回退"同口径 |
| 入口 | 机制入口命令（脚本写入，§5.3 写者纪律）；与返工共用"异常 / 挂起属脚本写入的判定字段"的划界 |

## 6. 功能清单 · spec 体系

> 核心要点：**加载到上下文中的 spec 可以少，但必须准确。** 预算的目的是给代码推理留足空间。

### 6.1 颗粒度与治理

- 颗粒度单位 = **原子文件**：一个 spec 文件只写一个规则 / 约定族（约 30–60 行）。不做文件内分节加载；
- **spec frontmatter 字段集**（独立于 §1.2 的 skill frontmatter 最小集）：`paths`（治理哪些仓库路径）、`status`、`verified_at`、`schema_version`、`author`（`human` / `ai`）、`counterexample`（反例字段，§4.2 反例成对的结构承载）；
- `paths` 校验（沿 Trellis spec-injection 的守卫）：必须为仓库相对路径的 glob，**拒绝绝对路径与 `..`**，解析前做路径规范化；**非法 glob 按条失效**（沿 Trellis spec_match 的校验粒度）：某条 `paths` 值非法时，仅该条失效并进 §1.5 的可发现面输出清单，该 spec 的其余 `paths` 条目与整份文件照常参与匹配——不因一条坏 glob 废掉整份 spec；
- 简化单层目录起步；index 三段式（索引表 + 开发前 checklist + 质量检查），**索引只是指针**——索引行不含规则正文，加载必须落到 spec 文件本身。**三段完整是规范形态**：初始化任务产出三段完整骨架（§3），发行模板只含第一段的形态属缺失，由一致性校验报出；
- **框架资产与项目数据的路径边界（规范性定义，唯一定义）**：**框架资产** = 安装器投放且升级对账清单登记的路径（skill 投放根、脚本、流程文档、**spec/index 骨架的初始模板文件**）；**项目数据** = `.wf/` 内的一切其余内容（任务记录、spec 实体文件、index 实体、基线活文档、out-of-scope、归档区）。升级对账对每个清单内路径的**变更判定是覆盖式三态（全集断言 + 划分不重不漏）**：①**文件存在且内容与模板一致** → 不变（unchanged），不进冲突面；②**文件存在但被本地修改过（哈希不符）** → **报冲突、不覆盖**，由人裁决（保留本地版 / 恢复模板版），**裁决必须沉降**（decision-without-persistence 禁止）：裁决结果由 `upgrade --apply` 写回资产清单——选"保留本地版"则该路径的基线哈希更新为本地版当前哈希并记"已接受偏离 + 原因 + 时间"，选"恢复模板版"则覆盖后哈希恢复为模板值；**同一冲突只报一次**，下次升级按新基线判定；③**文件缺失（被用户删除，哈希在清单里）** → **尊重删除、不重建、不报冲突**——删除是意愿（区别于"修改是冲突须裁决"）；**但它是抑制型判定，必须带可发现面**（§1.3 证据面 8-9）：**首次出现输出 `[WARN]` 框架资产缺失：\<path\>（升级按用户删除处置）**，人确认后记入『已确认框架资产豁免登记』（§4.2——抑制型登记，缺失路径类条目），后续跳过：可发现面保留（未登记缺失仍告警——含意外丢失与登记被绕过两种情形），噪音不累积；升级对账记为"用户已删除"并跳过该路径（清单记录保留，供审计参照）。由此补集闭合（§1.3 证据面 6）：清单内路径的任何状态（存在 / 修改 / 缺失）都有唯一处置，且缺失态不再静默（对照：没有 WARN + 沉降时，"skill 层残缺而全部门禁沉默"是本态的最大风险）。**骨架模板按"存在即跳过"安装**——目标路径已有文件（无论它是否被项目原地改写过）一律不覆盖（**唯一显式例外：`.gitignore` 托管段为追加式投放**，§7.1——存在即跳过会使运行态 ignore 规则在有自有 `.gitignore` 的项目里永远落不了地；例外在此显式登记，非隐式突破）。由此 §6.1"原地改不建第二份"与 §7.2"升级不触碰项目数据"在同一张边界表上自洽：index 一经安装即属项目数据，升级永不覆盖它；
- **已有入口文件就原地改，不新建第二份**（沿 skills 仓库 setup 的纪律）：**wf 自有的入口文件**（spec、index、out-of-scope 条目等）已存在时更新原文件。多 CLI 环境下"另建一份"是入口分裂、知识漂移的最大来源。此纪律只覆盖 wf 自有文件——项目里属其他工具的入口（如 AGENTS.md）不因本条获得写入许可（原则 2 与 §3 共存策略优先）。

### 6.2 加载协议（三时点拉取制）

Trellis 0.7 动态 Spec 加载的无 hook 适配：保留 `paths:` 治理声明与纯库匹配引擎（frontmatter 有界解析 + glob 匹配 + 特异性排序），把 hook 事件触发的注入改为三个拉取时点：

| 时点 | 动作 |
|---|---|
| ① start / 开工 | 按任务策展清单加载；**策展发生在 Plan 段（含首次开工时的补策展）**：对照 index 挑选本任务相关 spec 写入任务记录。**新任务的首次策展**：开工前任务尚无策展清单，开工命令输出 index 索引表本身（或其命中治理面/PRD 触碰面声明的子集）供 Plan 阶段策展——策展面向的是 index 的**指针层**而非 spec 内容，不存在"需要先读 spec 才能策展"的循环；策展完成后进入 Plan 正文 |
| ② Execute（纪律约定） | 编辑某文件前先 `wf spec --file <path>` 查看治理该文件的 spec——**读取即留痕**：该命令同时把本次读取写进**读取留痕侧车**（`.wf/` 运行态，gitignore，一 spec 一行：路径 + `spec_sha` + 读取时间；写者 = 该命令，§5.3）——读取**不触碰任务记录与 git 工作区**（不产生待提交差异、不弄脏干净门禁、不冲刷写入标记）；侧车丢失 → 门禁判据不满足 → 重读一次即自愈（读取是廉价操作）；侧车被 AI 直改属伪造证据（与伪造 check 摘要同形，§1.5 口径）；AI 偶尔漏调由时点③兜住（诚实代价，§1.5） |
| ③ Check | 按本任务实际触碰路径（§4.2 任务归属的定义）批量匹配 + 过期校验（对照 `verified_at`，含 §6.4 的到期强制复核）+ **内容哈希比对**（§6.5 门禁第 4 项） |

- **匹配排序（特异性排序）**：多份 spec 同时命中同一文件时，按 **glob 具体度排序**——精确与窄范围匹配必须胜过宽泛的树 glob（沿 Trellis spec_match 的评分：无通配符优先、字面段数多者优先、通配符少者优先、字面长度长者优先），字母序仅作确定性 tie-break。排序是纯函数，属实现面；
- **策展记录项**：策展（时点①）把每条命中 spec 写入任务记录策展清单——路径 + **内容哈希（`spec_sha`）** + 命中时点（写者 = 入口脚本，判定字段）；`wf spec` 读取（时点②）写**运行态读取侧车**（§5.3，非判定字段——wf spec 不是判定字段写者，不触碰任务记录）。**两者都是 §6.5 门禁第 4 项内容哈希比对的判据来源**：spec 的当前内容哈希与（策展记录 ∪ 读取侧车）中的 `spec_sha` 比对，不符或两侧皆无记录 → 须重读（经 `wf spec`，读取即留痕，读后侧车即刷新——无"读了但门禁仍判旧"的空转）；策展记录同时是 §6.4 回收统计的数据来源，不另设计数机制。**"刷新 `verified_at`"不是合规处置**（内容变了与只是日期到期是两种事实：前者必须重读，后者刷新日期即可）；
- 码点软预算（CJK 友好，避免 3 倍惩罚）：单次注入 spec 总量控制，超预算收紧策展而非塞满上下文；**预算的契约式写法**：每条 spec 附一段"不改会怎样"（为什么需要它），预算取舍时按此判断谁该留；
- 降级链：截断 → 索引行 → 一条汇总指引；最轻一档是**spec 提醒行**（上游称 "spec ticket"：指向 spec 文件的一行短提醒，模型自行 Read。注意与 Trellis 的会话票据 "shell-ticket"——会话身份桥接机制——是两个无关概念，本文只在 §1.4 不吸收清单的历史语境里提及后者）：预算内放不下索引行时退为此档。**极端预算下提醒行与汇总行也可能被丢弃，且上游告警仅到 stderr（多数事件不进模型上下文）**——这是上游实测行为，wf 的对应缓解是把"spec 超预算被截断 / 提醒行被挤掉 / 汇总行被挤掉"列入 §1.5 的可发现面输出清单，触发即在正常输出中可见。

### 6.3 沉淀纪律

- `wf-spec-update` 是 Finish **必经步骤**（结论"无可更新"也要走判断留痕；**允许零结果**——如实记录"本次无更新"即是合法产出，不为交差硬凑条目）；
- Code-Spec（"怎么写"，可执行契约）与 Guide（"怎么想"）二分。Code-Spec 的输出有固定形状（沿 Trellis update-spec 模板）：签名 / 契约、校验与错误矩阵、Good-Base-Bad 对照、断言点。**一条判据**（沿 skills retro 的纪律）：机械能判的（存在性、取值、路径合法性）不许只写散文——写成可核对的字段或命令，散文只留给机械判不了的；
- 写入纪律："简报而非转录" + **Ruled out**（排除的方案及原因，防止下次重蹈覆辙）+ §6.1 的"原地改不建第二份"；
- **准入双门槛**（沿 skills 仓库 SCOPE 的准入标准）：①**真实失败**——描述真实会话中发生过的问题（跑了什么、结果是什么、期望是什么），假设性的"这样更好"不过门；②**不与现存冲突**——不与现有 spec 或 `.wf/out-of-scope/` 中的拒绝项重复或矛盾。收录前自问（沿 mcode-stack 的审查问句）："删掉这条，agent 会在哪儿出错？"答不上来就不收；
- **拒绝项落地**：`.wf/out-of-scope/` 一概念一文件，理由必须持久化（为什么拒绝、什么条件下可重议）——防止同一被拒概念反复回锅。**重提纪律**：重提被拒概念时必须先在原拒绝文件上追加"本次与当时的差异"再议，不许无视旧账重开；**墓碑纪律**：已被现有 spec / 代码实现覆盖的旧条目不写墓碑文件——更新原条目或删除，防止目录被"已做过的"污染去重。

### 6.4 回收治理（spec 只增不减的解药）

| 治理项 | 规则 |
|---|---|
| **到期强制复核** | `verified_at` 超过复核周期（默认 90 天，项目层可配）的 spec 进入待核实清单；Check 门禁要求本任务触碰路径命中的过期 spec **先核实，或在 finish 门禁第 4 项留痕后按未核实依赖**（留痕是刻意的降级通路，§6.5——两条口径以门禁第 4 项为准，不各自为政）；不触碰则进周期性清点（独立出口见下行） |
| **周期性清点** | 每次项目收尾（尾任务归档）或人工发起时，**跨归档区**统计（加载记录分布在各任务记录中，含已归档任务）输出待核实清单与加载统计，由人逐条处置：刷新 `verified_at` / 合并 / 降级 / 删除。清点范围覆盖归档区，与 §5.4"启动校验只扫活动区"是两回事——前者是知识治理动作，后者是开工门禁。清点与 §5.4 巡检同期执行 |
| **冲突检测** | 周期性清点时**按 `paths` 交集聚合**：命中同一路径的多条 spec 列入"需人工比对"清单（两条 spec 对同一路径给出矛盾规则，是单层目录长期增长的必然产物；这是纯结构性检查——只做路径交集，不做语义分析，符合 §1.5 的硬边界）；比对后由人处置：合并 / 收窄 paths / 删除其一 |
| **低价值回收（含删除判据）** | 连续 N 个任务（默认 5）未被任何策展清单加载的 spec 列入待归档，由人在周期性清点时决定去留；`author: ai` 的条目优先复核。**删除要成对判断**（沿 stop-that-shit）：加载次数低不是删除依据本身——先答"缺证据≠不必要"（这条 spec 治理的路径没被加载，可能是路径漂移而非无用）与"删掉它会破坏哪条现存承诺"，两问过不了才删。**"缺证据 ≠ 不必要"是通则**（不止删 spec 时用）：一切"因为没看到所以不需要 / 不存在"的推断——未归属扫描无发现、spec 未命中、check 项缺失——都按此律处理（§4.2 未归属扫描已含此口径） |
| **萃取产物** | `verified_at: extracted` **不是日期，不参与 90 天周期计算**：天然永久处于待核实状态，直到人核实后刷新为日期。它比任何过期日期都"更待核实"，且**计入 finish 校验对象**（§6.5） |
| **删除 / 合并 / 降级** | 均为人的决策；删除前过 §6.3 的"删掉这条会怎样"自问；处置记录写进 out-of-scope 或 spec 历史（git 为准） |

### 6.5 复杂度判据、finish 门禁（唯一定义）与多 agent 辅助审查

**复杂度判据**（Check 时点按本任务触碰路径（§4.2 任务归属的定义）复核用；Plan 时点的初判依据是其"触碰面声明"版：预估规模、是否命中治理面、是否触碰对外契约）。命中任一即复杂，触发三件套分级（升级）与强制审查：

| 信号 | 判据 |
|---|---|
| 改动规模 | 增删文件 ≥ 3 个，或单文件净增/删 ≥ 80 行 |
| 契约面 | 触碰治理面登记的路径（§3 治理面登记：spec 目录、构建配置、对外接口 / CLI 入口、记录 schema——项目初始化时人审定，通用项目与 wf 自身研发同构适用） |
| 状态机 | 改动会改变判定、门禁或提交顺序（触碰 `.wf/` 记录 schema 或门禁脚本） |
| 前一轮 fail | 同一任务上一轮审查为 fail，本轮必须再审 |

**"信号不是授权"**（沿 stop-that-shit 的贡献纪律）：上表判据是**信号与检查点触发器，不是判定本身**——LOC、文件数、行数命中只触发"停下评估"，不单独充当结论；是否升级、审查范围多大，由触碰路径与治理面的事实给出。

**finish 门禁的完整校验对象**（机器可判的结构性齐备；**门禁六项在此唯一定义**。归档前的完整校验面 = 门禁六项 + §4.2 提交顺序约定三条，两个定义源合计构成，各处只引用不另列清单防两份枚举漂移）：

1. Check 受控取值为 `pass` + 检查项列表存在 + **触碰路径指纹与归档时点一致**（§4.2 证据有效期；指纹失配视同未检查）；
2. 阶段判据 checklist 全勾或附不勾理由（**required 项不适用"附理由"豁免**——required 项不勾即拒绝，理由字段只给非 required 项）；
3. 复杂任务的审查结论为 `pass`（判定式见下），或 unavailable 留痕存在；
4. **本任务触碰路径命中的过期 / extracted spec 已处置**——处置的合法形态二选一：`verified_at` 已刷新（含 extracted 转为日期），或**留痕**：任务记录的 spec 处置字段记"该 spec 依赖但未核实"及原因（由 Check 入口脚本写入，§5.3 写者纪律；含原因的留痕可被人判复核，未留痕则门禁拒绝）。**外加内容哈希比对**：触碰路径命中的 spec 的当前内容哈希，与**策展记录或读取留痕侧车**（§6.2）中该 spec 的 `spec_sha` 比对——**不符或两侧皆无记录 → 该 spec 须重读后再依赖**（重读经 `wf spec --file`，读取即留痕，读后侧车即刷新——写者已定义，无空转）；重读前按未处置处理——"策展时读过、之后被改"的 spec，其旧内容不再是准确知识；
5. **前置集合全部满足（§5.1 判定式）∧ 无未收决的未决状态标记**（挂起未清除、暂停未恢复——§5.4 状态收尾的通用规则；这是归档前置条件，与状态收尾规则、§5.1 归档终态约束同源）；
6. **本任务记录的判定字段携带合法写入标记**（§5.3 写入标记；与启动校验同判据——手改判定字段若无标记，finish 当场拒绝，不等下次 start）。

**多 agent 辅助审查**（Check 通过后、人判之前；复杂任务适用），建立在**加性适配后的**全局 `multi-cli-review` / `multi-cli-review-action` 成对 skill 上（适配清单见 §2.2、§8——**全部加性、skill 零改动**），wf 不新造 review skill。审查机制的**流程形状**与 workflow-implementation.md §8.5 同源对齐（任务标识入参、轮次与槽位、结论两档、上限 2 轮、unavailable 留痕）：

- **与 vendor code-review 原语的关系（唯一定义）**：两者**串联、先后执行、结论独立**——Check 段内先跑 vendor 的 code-review（双轴自审，同一会话顺序执行，§7.4），作为 Check 关卡的一部分（其发现按 Check 段分工纪律处置：机械项直接修、设计项交人判）；Check 通过后、人判之前，复杂任务再走本节的多 agent 辅助审查（异种 agent 的第二双眼睛）。**门禁第 3 项只认多 agent 审查结论**——vendor 自审是 Check 的内部步骤，不替代异种审查（它的发现已消化进 Check 结果；两个机制的防的东西不同：前者防"自己看漏"，后者防"同 agent 系统性盲区"）；
- **适配方式（全部加性，逐项声明）**：①**`--task-id` 新增参数**（reviewer 与 action 两侧同加）——该 skill 现行契约无此参数，但其 reviewer frontmatter 已要求 `task-id` 字段且无入参可传，此参数补上缺失的传值通道；提供时写进报告 frontmatter 的 `task-id` 字段（wf 约定总是提供），不提供时维持该 skill 现行的目录名推断，此项加性、无流程分支逻辑；②**wf 侧约定**：coordinator 总是提供 `--review-focus`（该 skill 现行标注为可选，"总是提供"是 wf 侧收紧约定，不改 skill）；③**目录隔离经 `--task-dir` 嵌套达成，skill 零改动**：wf 传 `--task-dir {task-dir}/review/`，产物按该 skill 现行契约落 `{task-dir}/review/review-round-{N}/{reviewer-id}.md`；④**轮次号跨返工继续递增、不重置**（见 fail 处置路径）。若未来适配还需不兼容改动，按 §7.5 源注册表记决策并说明影响面；
- **目录契约（零改动，全按该 skill 现行契约）**：审查产物落 `{task-dir}/review/review-round-{N}/{reviewer-id}.md`（wf 的 `--task-dir` 值 = `{task-dir}/review/`）。轮次目录由 coordinator 预建（**reviewer 侧**不得自建目录——该 skill 现行契约本就如此约定；**action 侧从不创建目录**，只按 `--round` 读取——两侧的目录创建责任按事实写清，不许混读成"两侧都不自建"）；`reviewer-id` 为槽位字母（`a`–`d`），真实 agent 身份记 `source-cli`（该 skill 现行契约）；报告 frontmatter 按该 skill 现行契约外加 `task-id`（`task-id`、`round`、`reviewer-id`、`source-cli`、`review-time`、`review-focus`、`protocol: task-level`）；
- **角色分工**：wf（主会话）是 coordinator——预建轮次目录、在 continue 输出中给出 reviewer 侧调用命令（发起时机见 §4.1；命令为**五参**：`--task-id`、`--task-dir`（嵌套 review 子目录）、`--reviewer-id`、`--round`、`--review-focus`——`--task-id` 与后四参是现行协议入参或 wf 侧约定总提供的参数，由 coordinator 指定，reviewer 不得自行推断轮次或槽位）。reviewer 是**异种 agent 的另一个会话**，由人发起、加载适配后的 `multi-cli-review`，按报告契约（文件名 `{reviewer-id}.md` + frontmatter）写自己那一份。汇总与修复决策由主会话按适配后的 `multi-cli-review-action` 执行——**以 `--task-id` 入参与 reviewer 侧对齐；`--task-dir` 仍是两侧的路径参数**（action 侧读轮次目录仍靠它，`--task-id` 只进 frontmatter，不承担路径解析）（先 summary、逐条本地复核、人确认后才改码）。同一 agent 换会话不算合格的异种补位；**仅有一个异种 agent 可用时降级为单人审查并在 summary 记 `degraded: single-provider`**（沿 workflow-implementation.md §8.5.3 的降级留痕）。**action 侧的内部消费账本**：`.processed.json`（已消费报告默认跳过、`--force` 才重消费，action 侧现行契约）是 action 的内部状态，不属 wf 判定面——wf 的轮次号纪律（不重置）保证每轮新目录，不与账本冲突（§5.2 否决记录）；
- **结论的产生**：成对契约产出 findings 与逐条决策（adopted / ignored / manual-decision / blocked）及验证结果（`pass` / `fail` / `not run`），没有"本轮总结论"字段。审查结论由 coordinator（主会话）按 action 侧 `summary-round-{N}.md` 判定并写入任务记录的**审查结论受控字段**（写者纪律 §5.3）。**fail 的判定式（唯一定义，四条）**：①存在任一 `blocked` 项；②存在任一**未决的 `manual-decision`** 项；③任一验证结果为 `fail`；④**审查未成立**——报告缺失、frontmatter 非法、reviewer 与实施者同 agent、槽位不足且未按前述规则降级留痕。四者其一即 `fail`，全部未命中才为 `pass`。**fail 的处置路径（完整，唯一定义）**：`fail` → 段内回退**就地修复**（不新增审查轮次——轮次只在下一次审查发起时递增）→ 重跑 Check（受控取值 + 指纹重记，§4.2）→ 下一轮审查；**同一实施尝试最多连续 2 轮审查仍 `fail`** → 按 §1.5 阻断协议报告，由人确认发起**返工，挂载点 = 本任务自身**（§5.6 返工的"本任务自身"情形）。返工完成后**实施尝试计数重置、轮次号继续递增不重置**（从新的下一轮继续计）——**轮次号不重置的理由（§5.2 否决记录）**：重置为 1 会与 reviewer 侧"目标文件已存在即停"的现行契约冲突（旧 `review-round-1/a.md` 还在），也会撞上 action 侧 `.processed.json` 的已消费记录；轮次号递增则每轮新目录，天然无冲突；
- **finish 门禁校验**：见上文六项清单第 3 项。报告内容的真伪、审查是否认真，属语义层，只留痕不可校验（§1.5）；
- **不可用回退**（wf 侧补充约定，**不属于成对契约**；契约文件里没有这个概念）：该机没有异种 agent，或适配后的 `multi-cli-review*` skill 未安装 / 加载失败——**由人向主会话声明情形与证据，主会话核验后在任务记录留"人声明"标记（声明人、时间、情形），再落 `unavailable.md` 留痕**后按普通流程走，**不得声称"已审查通过"**。审查豁免的授予链是人→留痕，主会话只承载记录——与 finish 的人判同一结构（§1.5 "代写人判只留痕"的口径下，模型伪造"人声明"标记与伪造 check 摘要同形，属结构性不可防，不假装更强）。skill 缺失属 §2.2 声明的已知外部依赖的正常回退路径；
- **备注：当前人工链路是基础；后续补充自动审查机制，coordinator 角色与适配后的成对契约即为自动化预留的接口。**

## 7. 功能清单 · 框架机制

### 7.1 安装

- **来源**：forgejo 远端（见 §3），不指定本地 file 路径。**最小安装路径**（无分发 CLI 的自建面）：`git clone` 远端到系统临时目录 → **人在终端运行临时目录内的安装入口（单脚本，属 §1.1 人直调实现件；首次安装时 wf skill 尚不存在，只能人直调）**→ 复制 skill 层 + `.wf/` 骨架 → **装完自检**（skill 文件齐全、**各 skill frontmatter 可解析**（YAML 失效会使 skill 被加载器静默跳过——§1.2）、骨架可解析、目录无既有流程冲突时报告共存提示）→ 删除临时目录。入口命令与自检判据落实现方案，但路径形状在本节定死：**clone 在外、入口在临时目录内、自检在删除临时目录前**；
- **动作**：把 skill 层（`wf-*` skill 目录，按 §1.2 人声明的 CLI 清单投放对应根）+ `.wf/` 通用层骨架（流程文档、脚本、spec/index 骨架模板、schema 版本文件、框架资产清单、**`.gitignore` 托管段——运行态 ignore 规则的承载（追加式投放，覆盖式断言的唯一显式例外）**：运行态文件的 ignore 规则（活动任务指针、读取留痕侧车等，§5.3）**不以整文件投放**——存量项目几乎必有自有 `.gitignore`，"存在即跳过"会让规则永远落不了地（规则装了等于没装，J2）；改为**向目标 `.gitignore` 追加 wf 托管段**（`## BEGIN wf-managed` … `## END wf-managed`，已存在托管段则跳过——幂等）。托管段属框架资产，升级对账**按段内容哈希判定**（整文件的其余改动不进冲突面——它本是用户文件）；此例外是 §6.1"存在即跳过"的显式登记，不是隐式突破）复制进目标项目，git 管理。**骨架按"存在即跳过"投放**（§6.1 路径边界，`.gitignore` 托管段为唯一例外，见上）——目标路径已有文件不覆盖，保护存量项目的原地改写。**装完自检增项：`.gitignore` 托管段存在且含运行态规则**（无自有 `.gitignore` 的项目由骨架整文件投放，有者经追加段落地——两种路径自检同判）。**安装锚点登记**：由接入流程产生并登记（§4.2 唯一定义）——**存量**：安装 / bootstrap 入口落盘后登记（git 前提校验已保证 git 存在；工作区脏时按存量入口的前置处置只落盘不登记）；**新项目**：安装入口执行 `git init` + 骨架首次提交，该提交即安装锚点，由安装入口登记（扫描下界，静态起点、非水位）；
- **新项目入口**：装骨架 → **安装入口执行 `git init` + 骨架首次提交**（新项目安装时还不是 git 仓库、无 HEAD——"git 就绪"前提由安装入口在此补齐：该提交即安装锚点，也使初始化任务的开工门禁（任务基线提交 = 当前 HEAD）可满足；若留给初始化任务去做，任务会断在自己的开工门禁上）。**受限 staging（接入提交的内容纯度）**：骨架首次提交只暂存框架资产与 `.wf/` 骨架（按清单路径显式 add，**绝不 `git add -A`**）——新项目目录里用户既有的文件（README、LICENSE 等）保持未跟踪、不被卷入提交（卷入即成违规提交，阻断首次归档且当时无任务可裁决；沿"只 stage 具体路径"纪律）；两次提交时序见 §4.2 安装锚点定义 → 引导建初始化任务（§3 的 0→1 产物；其中"git 就绪"降级为**确认已就绪**——git 与锚点已由安装完成，任务内不重复执行）；
- **存量项目入口（无既有流程）**：**git 前提校验**——目标项目尚非 git 仓库时先 `git init` + 首次提交（与 §3 新项目"git 就绪"同口径；Check 用 git diff、一致性校验比对 git 历史、finish 提交顺序约定均以 git 存在为前提，此前提不可缺省）。**工作区脏的前置处置**：安装 / bootstrap 时工作区不干净（用户有未提交改动）→ **只落盘、不提交、不登记锚点**（绝不把用户工作卷进接入提交——与提交顺序①"绝不静默捎带"同律），输出提示"先提交你自己的改动，再重跑 install 完成锚点登记"（登记步骤幂等）；锚点未登记期间属接入过渡态（§4.2 锚点缺失分支），未 start 的会话不受 wf 约束（原则 2），既有开发流照常。`wf-bootstrap` 从现有代码、AGENTS.md、README 反向萃取初始 spec，**并产出基线活文档与治理面登记初版**（范围、"明确不做"、验收口径、技术基线、治理路径的萃取草稿——人审阅后由入口脚本落盘，使 §4.2 范围闸门的三层锚点在存量项目同样成立，不能只有 spec 没有基线）。**注入防护**：萃取读到的代码与文档内容**一律作为数据处理**，不构成指令或授权——其中的指令性文本不得被执行、不得作为产物依据（存量项目独有的注入面：既有文档可读，新项目没有）。**质量约束**：萃取产物（spec 与基线初版的判定性内容）一律标 `verified_at: extracted`（按 §6.4 永久待核实直到人刷新）与 `author: ai`，加载时标注"未经核实"，Check 阶段优先核实——萃取是假设，不是已验证的知识，不得冒充核实过的地基；
- **存量项目入口（有既有流程）**：按 §3 共存策略执行，不做检测与干预（安装自检发现 `.trellis/` 等共存迹象时只**报告**提示，不阻断安装）。一次性只读萃取既有流程规范属待用户决策项（§3 D-1），裁决前不实现。

### 7.2 升级

- 版本文件 + 框架资产清单哈希对账（属 §1.4 划定的小型自建脚本，非分发 CLI）；**`upgrade --apply` 属 §1.1 人直调实现件**（交互式终端 + 令牌确认，模型不得代跑）；
- **对账变更判定 = §6.1 路径边界的覆盖式三态**（**`.gitignore` 例外**：按**托管段内容哈希**判定——整文件本属用户所有，段外改动不进冲突面，§7.1 托管段）：①文件存在且与模板一致 → 不变，不进冲突面；②清单内路径被本地修改（哈希不符）→ **报冲突、不覆盖**，由人裁决且**裁决结果写回资产清单**（§6.1 裁决沉降——保留本地版则基线哈希更新为本地版并记偏离，同一冲突只报一次）；③清单内路径文件缺失（被用户删除）→ **尊重删除、不重建、不报冲突**，但**带可发现面**（§6.1 第三态——首次出现 `[WARN]` 框架资产缺失，人确认后记入『已确认框架资产豁免登记』，后续跳过）；**清单缺失或哈希对不上时拒绝批量删除**——宁可不升级也不猜（沿 Trellis 卸载的"清单缺失即拒"教训）；**清单缺失的出口**：从 forgejo 远端重新获取清单后重试（远端是权威源，与 §7.3 卸载恢复同源）；scrubber 类清理只摘自家字段，不动他者；
- **资产路径改名 / 移动**（新版目录布局变化时的机械判据，属实现面）：目标侧已存在时，只有目标侧内容**逐字节等于当前模板**才允许源覆盖目标；目录改名按**路径深度降序**执行、且排在删除类操作之前——嵌套目录的执行顺序由深度决定，不引入运行时；
- 升级前置：活动任务集为空或全部暂停（§1.3 定义）；记录 schema 按 §5.3 只增不改、不迁移；不兼容字段按只读降级处理；
- **挂起任务的升级死锁出口**：挂起 ≠ 暂停，有挂起任务时不满足升级前置。若当前挂起的修复恰需新版本（如修 bug 的机制在新版里），按顺序走：先 §7.3 默认卸载（保留项目数据，无前置条件）→ `install` 新版 → 项目数据续用（`.wf/` 记录与 spec 原地保留）。卸载-重装是既有机制的组合，不新增升级旁路。

### 7.3 卸载

- 单一独立入口，**不依赖 `.wf/` 运行时可用**：卸载脚本是**单文件、零 import（仅标准库）、不读取 `.wf/` 内任何其他文件**的自包含实现——通用层其余部分损坏（正是最需要卸载的时机）也不影响其执行；**卸载无前置条件**（§5.1 ④）——不需要活动区为空或任何项目状态，随时可退回"普通项目"。**"无前置条件"与"清单缺失即拒绝"不冲突**：前者是项目状态，后者是执行依据——框架资产清单意外缺失时（如被手删），默认卸载**拒绝执行并报告**（无法区分框架资产与用户数据，fail-closed，沿 Trellis 卸载教训）；**非死锁出口（二选一，显式给出）**：①从 forgejo 远端重新获取清单后执行（远端是权威源——与"卸载脚本本身丢失时"的恢复路径同源）；②改用 `--purge`（整目录删除，不依赖清单精度）。两条出口保证升级侧"尊重删除不恢复"与卸载侧"清单缺失即拒绝"叠加时不会卡死——用户永远有退出路径；
- 卸载脚本本身丢失时的恢复路径（按顺序）：①从 forgejo 远端重新获取后执行（远端是权威源）；②远端不可达时，按安装时留下的**框架资产清单**（随项目数据保留、卸载不删）手工移除清单内路径——清单在，卸载就不依赖任何单一执行体；
- 默认仅移除框架资产（skill 投放、脚本、流程文档，按 §6.1 路径边界），保留项目数据（任务 / spec / 通用层记录）；`--purge` 才删项目数据，且**属人直调实现件**（§1.1 原则 1 第二类：交互式终端 + 令牌），模型不得代跑。**`--purge` 只有一种粒度**：整体删除全部项目数据——**单条坏记录的删除不经卸载脚本**（卸载脚本自包含、不读 `.wf/`，无法核验引用完整性；单记录删除是 `wf repair` 的一个动作面，由 repair 机器核验"无前置/返工引用"后执行，§5.3 三层出路之三）。此默认与 Trellis 相反（见 §1.4 差异标注），系 wf 的有意改进；
- 卸载不留阻断原项目正常开发的残留；卸载后项目回退为"从未用过 wf"的普通项目（数据在，流程不存在）。

### 7.4 vendor 原语库（自包含 + 改编纪律）

首轮吸收四个（改编自 skills 仓库），随安装自带，装完即用——不依赖用户环境里已装的全局 skills（唯一例外是 §2.2 声明的审查 skill 对——按 wf 契约**加性适配、skill 零改动**，属适配而非 vendor）。**许可纪律**（§2.2）：skills 为 MIT，vendor 副本保留原许可文本；结构借鉴的来源统一"只借结构与判断句、文本自写"。

**改编总纪律**（所有 vendor 副本必须遵守，逐副本在改编时核对）：

- **子代理 / 并行派发一律改编为单会话顺序执行**。例：code-review 原版是双轴并行子代理（Standards 轴与 Spec 轴各起一个子代理）——改编为**同会话先后跑两轴**，两轴结论**不合并、不重排**（原版明确写了为什么不能合并：一轴通过另一轴失败时，合并会让强轴掩盖弱轴；wf 改顺序执行后"并行子代理上下文互不污染"的原论证不再适用，改编差异说明按 wf 的实际执行形态改写理由，验收时不得拿原版理由自证）；
- grilling 原版"事实由子代理查"改编为"事实由当前会话用工具直接查"；
- 每个副本记录上游出处、基线版本与许可，改编差异写明；**验收纪律**：改编后的原语不由改编者自证——由未参与改编的会话（理想为异种 agent）按门控判据实测通过才算完成，报告留档。

**wf 自建件同此验收纪律，并加一条负向测试要求**：门禁、`wf repair`、安装器、卸载、**升级对账（拒绝批量删除、冲突不覆盖、尊重删除三处 fail-closed）**的每个 fail-closed 行为须配至少一条**会红的负向测试**（构造非法输入、断言拒绝与阻断输出三要素齐全，§1.5 阻断协议）——只有正向通过的测试不构成验收（沿同仓 workflow-implementation.md 的探针与夹具纪律）。

| 原语 | 挂载点 | 用途 |
|---|---|---|
| grilling | Plan | 需求澄清纪律（设计树 + 分轮追问 + 推荐答案；触发条件见 §4.3） |
| tdd | Execute | 红-绿循环执行纪律（任务级开关） |
| diagnosing-bugs | Execute | 触发式调试循环（门控 checklist） |
| code-review | Check | 双轴审查（改编为顺序执行，见上；作为 Check 内部步骤，与 §6.5 多 agent 审查串联，见 §6.5 关系定义） |

### 7.5 上游监控与吸收（authoring 仓库侧）

机制改编自 dsh-plugins/dsh-trellis 的版本监控（源注册表 + 基线比较），落点在 **authoring 仓库**，不随安装进入目标项目：

- **源注册表**：登记所有吸收过优点的上游——skills、Trellis、stop-that-shit、mcode-stack 及未来新增；每源记录仓库地址、基线版本与**许可**；同仓冲突裁决（§2.2）与待用户决策项（§3 D-1 共存萃取、D-2 观察模式）的**裁决记录均落本表对应条目**——裁决必须沉降，不允许只裁决不落盘；
- **检查**：检查命令对比基线，发现新版本只**报告**（列出上游变动），不自动吸收；
- **决策记录**：每版由人决定并在注册表中记录——**跳过（附原因）或吸收（附要点）**，基线随之推进；候选吸收清单（§8）的逐项裁决走同一流程；
- 监控与吸收只发生在 authoring 仓库；目标项目通过 `wf upgrade` 从 forgejo 远端拿吸收后的成果。`multi-cli-review*` 的上游演进（若该 skill 另有上游）同样登记于此，适配修改（如有）的再同步走同一决策流程。
