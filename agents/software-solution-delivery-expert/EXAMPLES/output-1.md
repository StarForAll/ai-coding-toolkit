# Output 1

说明：以下为**期望输出格式示例**，不是本仓库内一次真实 live verification 的运行记录。

## 1. Outcome

给出一个“可先接但要带条件”的 intake 结论，并输出 MVP 范围、澄清问题、
阶段计划与主要风险。

## 2. Evidence Status

`Stable knowledge`

说明：当前输出基于通用软件交付经验与稳定架构常识，没有引用实时供应商价格、
模型能力上限或最新合规政策；如果要承诺具体厂商选型、预算或上线要求，应先做
`Verified live` 补充核验。

## 3. Scope View

- 当前阶段：新单 intake / 方案收敛
- 已确认事实：
  - 4 周内必须能演示
  - 需要文档导入、权限控制、知识库问答
  - 技术栈未定
  - 预算未锁
- 工作假设：
  - 第一阶段目标是“能演示核心流程”，不是一次性做完整企业知识平台
  - 客户可以接受受控上传格式和有限权限模型
- 主要未知：
  - 用户数量、文档体量、问答准确率要求
  - 是否涉及敏感数据或内网部署
  - 是否已有账号体系或 CRM / 工单系统集成需求

## 4. Deliverable

### Intake 判断

- 建议：`可接，但必须先做范围锁定`
- 原因：
  - 需求有明确演示窗口，适合先收敛 MVP
  - 技术栈和预算都未定，不能直接给死报价
  - 权限与问答效果是最容易失控的两块，必须先定义“够用”标准

### 建议的 MVP 范围

1. 管理员上传有限格式文档并建立知识库
2. 后台支持最小可用的角色权限
3. 用户能按指定知识库提问并看到引用片段
4. 保留基础问答日志，便于演示和排错

明确不放进第一阶段：

- 复杂工作流审批
- 多组织层级权限
- 高级检索调优后台
- 企业级 BI 报表
- 大范围第三方系统集成

### 关键澄清问题

1. 第一版演示面向多少名内部用户，是否必须多人并发？
2. 文档主要是什么格式，体量大概多少？
3. 是否有敏感数据、私有化部署或地区合规要求？
4. 权限控制是“管理员/普通成员”两级，还是多层级组织权限？
5. 演示成功的标准是什么：上传成功、回答正确率、响应时间，还是可审计性？
6. 后续正式版是否需要接现有账号体系、工单系统或客服平台？

### 阶段计划

- 第 1 阶段：需求锁定与技术选型边界
  - 输出：范围说明、风险清单、演示成功标准
- 第 2 阶段：骨架搭建
  - 输出：认证、文档上传、知识库索引基础链路
- 第 3 阶段：问答与权限闭环
  - 输出：最小可演示问答链路、角色权限、日志
- 第 4 阶段：演示打磨与验收准备
  - 输出：演示脚本、已知限制说明、验收清单

### 主要风险

- 预算未锁：不能把“方案讨论”误写成“固定报价”
- 权限复杂度失控：多组织、多角色会迅速扩大工期
- 文档质量问题：原始资料脏乱会直接影响检索与问答效果
- 外部依赖不明：如果后面临时加入私有化、SSO、工单系统联动，会明显改范围

- 下一步先拿到澄清问题答案，再给技术栈与工时区间。
- 如果客户要求“具体供应商价格、模型选择、最新合规边界”，必须补一轮
  `Verified live` 核验后再承诺。
