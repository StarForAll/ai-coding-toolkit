1. 前置校验:
使用该工作流的项目必须是一个git项目且存在多个remote仓库,其对应添加远程仓库参考命令如下:
git remote set-url --add --push origin git@github.com:xxx/yyy.git
git remote set-url --add --push origin git@gitee.com:xxx/yyy.git

2. 初始阶段导入的spec应该是使用对应的脚本进行导入而非用户输入提示进行安装

3. trellis init创建的任务00-bootstrap-guidelines在安装这个工作流之后需要删除，finish-work中的 pnpm校验删除，后续技术架构确定之后补充明确的内容

4. 在 Brainstorm 阶段确认完成并准备进入 design 前，需要在目标项目 `docs/requirements/` 下补齐项目级需求文档结构；其中 `customer-facing-prd.md` 必须先可用并补齐 `## 项目级粗估摘要`，`developer-facing-prd.md` 改为在 design 阶段技术架构确认后再正式生成

5. 开启新的任务时需要判断对应的任务是否要求前一个任务必须完成，如果是则需要先进行校验，如果前一个任务完成了才真正开始当前任务

6. 初始阶段校验当前分支是 main（仅对无本地提交历史的新建项目强制）；技术架构确认后需要在项目自动化检查矩阵中明确真实质量门禁，采用 Sonar / SonarQube 的项目必须写真实命令，未采用时必须写替代门禁和原因

7. 任务信息分配给具体的任务不能挤压到 task_plan.md 文件中而是使用trellis的任务机制且每一个具体的任务需要在执行前补充其任务相关的测试门禁

8. 项目包含多种文档以及禁止codex使用原型实现前端界面,design阶段需要尽可能完善在stitch生成原型所需要的提示词

9. 工作流每一阶段进入下一阶段必须严格遵循要求,需要用户确认才能进入下一阶段;design 阶段技术架构明确之后补充文档和spec

10. plan 阶段如果任务足够复杂则需要细分成多个子任务,需要满足单个上下文就能够完成任务;参考因素:任务复杂度，任务所需要涉及到的文件数量，任务所需要涉及到的修改实现内容多少...

11. design 阶段产出的 UI 只是作为项目的参考，该UI所包含的源码编程语言不能作为实际实现的编程语言参考,这个是根据实际技术架构决定的
该阶段的原型到具体样式的实现阶段不能使用codex且自动选择当前目标项目下合适的skill

12. plan 阶段需要强制要求避免执行具体的任务,不能进行具体的代码实现而是执行当前阶段的任务划分

13. 在具体任务开始前必须输出对应的任务说明

14. feasibility 阶段不可跳过性,在初始时必须经过该阶段

15. 项目初始化时必须强制分析法律风险

16. 项目个人水印,防止项目被冒用或者个人水印

17. 项目总工时估算

18. 外包项目全款收取的保险措施

19. 工作流任务实现使用trellis原生能力,research -> implement -> check

20. 初始化项目之后嵌入该工作流 .current-task 应该为空 且在 git 没有两个远程仓库时提示对应的远程仓库创建命令
注: 这里只是在记录旧 workflow/目标项目嵌入问题的历史修复点，不代表当前本仓库 `.trellis` 运行时仍以 `.current-task` 作为 active task 真源；当前主机制以 session-scoped runtime 为准。

21. 目标项目中安装后的 `trellis-research` agent 需要与当前项目正在使用的加强版 `trellis-research` 保持同等级能力：内部代码优先 `ace.search_context`，外部搜索按场景使用 `exa` / `grok-search` / `deepwiki` / `Context7`；其中实时/最新信息优先 `grok-search`，通用与深度检索优先 `exa`，GitHub 仓库理解优先 `deepwiki`，库文档优先 `Context7`

22. 补充 AI CLI 所需要使用的工作流嵌入规范指导文档

23. 双语言版本README

24. 目标项目必须包含性能优化子任务

25. 使用原生 trellis agents

26. 工作流顺序执行[in-line],不使用 agents

27. 非技术性面向人查看的文档需要使用 humanizer-zh skill 优化

28. trellis 原生 continue 命令 和当前工作流嵌入之后使用不冲突,是兼容的
目标项目嵌入工作流之后,对应的AGENTS.md和实际的工作流不冲突兼容的;

29. 具体任务在check时必须进行代码可用性和代码漏洞检测和代码质量检测，前两者是强门禁
